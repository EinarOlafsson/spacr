**Evidence levels.** “Source-proven” means a literal/default or a complete local drawing branch establishes the difference. “Inherited” means the existing renderer owns the decision. “Render-dependent” includes actual overlap, clipping, legend occlusion, font fallback, final physical axis aspect and density readability. None of those visual failures is claimed as observed. Exposure is qualitative code fan-out (shared widget versus opt-in screen), not telemetry, frequency or measured scientific impact.

**Screen versus saved figure.** Dark backgrounds, hover halos, gate handles and selection dimming can be intentional interaction policy. They still need an explicit export boundary if the output is to satisfy the paper style. The authoritative skill is not a reason to change a scientific model, crop, measurement, statistical test or gate. Paper-only requirements such as A4 composition, status legends and per-panel data/stats sidecars do not apply to an icon or a transient slider histogram.

## Shared routes and highest-exposure differences

None of the owned source modules directly imports the copied `spacr_figstyle.py`. That is not in itself a defect: the repository already has shared `figures.style`, `figures.bundle`, `plot.save_figure`, `figure_style`, and GUI chart primitives. Consolidate at those existing seams rather than introducing a second plotting system.

The GUI's `graph_builder._draw_with_user_style` (`spacr/qt/widgets/graph_builder.py:525`) calls `figures.style._style_new_content`. Crucially, `_apply_user_style` at `spacr/figures/style.py:421` applies **only changed preference values** and returns without changing artists when no preference differs (line 452). Consequently local 6/7 pt, opacity and geometry defaults below are not automatically repaired on first display. A later user customization can alter the final output; it does not make the default compliant. Conversely, the shared saved-figure route can change screen ink/background, so screen-white text alone is not evidence of a defective printed page.

## Minimal render options for the parent (not executed)

1. **Training/evaluation, CPU-only:** call existing `train_compare.plot_curves` on tiny in-memory `Comparison`/`Series` objects with 3–5 epochs and one fold-mean band; call `classifier_evaluation._write_confusion_figure` on a 2×2 normalized DataFrame and `_write_calibration_figure` on two classes × three bins. No model fitting, checkpoint load, image dataset or network. Write to a fresh owned audit directory. Check actual plot-area aspect, alpha/text objects, PDF/PNG save policy and then visually inspect.
2. **High-fan-out GUI primitives:** one offscreen QApplication, existing `GraphCanvas` and `grouped_plot.GroupedPlot`, two small categorical frames with n=5 and n=21, then a 2×3 heatmap including a real zero and a missing category. Use the normal snapshot/export methods only; no source patch. Confirm automatic mark choice versus explicit user choice, same physical width/spacing, zero/missing distinction and default/user preference paths. Reset/redirect preference storage so no live user settings are mutated. Parent must own the scheduled process and scope resource caps.
3. **Small pure creator:** `hyperparam._trial_figure` with a tiny supplied embedding and score, or `render_motility_figure` with 2–3 synthetic tracks and a known `Calibration`. No UMAP fitting, tracking, segmentation, training or plate run. This isolates 7pt/.8/jet-or-image-range concerns from algorithm cost. It remains a synthetic diagnostic, not representative scientific evidence.

No full GUI launch, broad regeneration, timing panel, external data download or actual model training is necessary to establish these styling differences. A later implementation should preserve numerical arrays/statistics and compare the same synthetic inputs before and after, but this audit itself reports only source deductions and render-dependent questions.
