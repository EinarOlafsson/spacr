# Addendum — 2026-08-02: three Qt stability findings, all pre-existing

Found while verifying the stability batch, not by looking for them. **All three
were A/B'd against a clean worktree at `00784615` and reproduce there**, so none
is a regression from that work. They are recorded here because the audit above
missed them: the first full run's sharding happened never to put the triggering
files in one process.

They are almost certainly one family. `spacr_fixes` F32 already records the
shape — `bridge.py` double-owning a pipeline worker, segfaulting 3-in-8.

### A. `tests/qt/test_onboarding.py` live-locks after certain Qt tests
Deterministic, not flaky: the same stall point every run. **137 threads at
107% CPU, no forward progress** — a spin, not a deadlock. Passes alone in 13 s.
A thread count that high says workers are not being retired.

### B. A 30-file Qt shard dumps core (SIGSEGV, `exit=139`)
Reproduces at `00784615` and at HEAD, identically, at 63% of the shard.
File list: `scratchpad/cov3/shard_07.txt` — `test_all_module_smoke`,
`test_annotate`, `test_foreign_screen`, `test_main_window`, `test_e2e_pipeline`
and 25 others. This invalidated the final coverage measurement: the crash
discards the shard's coverage data, which reads downstream as "these modules
lost coverage" when in fact their tests never finished.

**Watch for this when measuring coverage**: a segfaulting shard looks exactly
like a coverage regression. `qt/screens/foreign.py` appeared to drop 99.8% ->
39.2% with an unchanged statement count, which is the tell — statements
unchanged, coverage collapsed, means tests did not run.

### C. `_DropzoneFilter.eventFilter` raised into the Qt event loop — FIXED
`spacr/qt/dnd.py:133`. Qt keeps delivering events to an installed filter after
the target's C++ half is destroyed; PySide6 clears the wrapper's `__dict__`, so
`self._target` raised `AttributeError` from inside the event loop where no
Python caller can catch it. Four in a row from one drag. Fixed in `effab339`
with a test that fails against the old code.

### What to do
Treat A and B as one investigation, not three bugs. The productive next step is
a teardown audit of the Qt worker lifecycle — who owns a `QThread`, who calls
`deleteLater`, and what happens when a screen is destroyed while a run is in
flight — rather than chasing either symptom. `bridge.py` is where F32 lived and
is the place to start.
