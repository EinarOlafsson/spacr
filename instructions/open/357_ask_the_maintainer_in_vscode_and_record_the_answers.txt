357-Q1  IS `Core` STILL THE PIPELINE?
        Core now holds nine modules, not six:

            Mask, Measure, Annotate, Classify, Map Barcodes, Regression
            + Training Runs, Prediction Profiler, Investigate Hit

        The last three read as results/analysis rather than as steps of a
        run, and all three ALSO appear as folded children (Training Runs and
        Feature Explorer under Classify; Investigate Hit and Prediction
        Profiler under Regression) -- so they are on Home twice, once as a
        Core tile and once inside a host.

        WHY IT MATTERS BEYOND TIDINESS: Core is the category the dock opens
        by default and the one a new user reads first, and the order IS the
        pipeline. It also pushed variant 01 of the Home layout study past
        1440x900 (see 288 and the ledger in test_home_variants).

        WHAT WAS DONE MEANWHILE: nothing. `test_core_lists_the_pipeline_in_
        order` no longer pins Core's exact membership -- it asserts the
        pipeline six come FIRST and in order -- so the category can hold
        more without failing a test, and re-categorising later costs
        nothing. The duplication is untouched.

        OPTIONS: (a) leave it; (b) move the three out of Core, keeping them
        as folded children only; (c) keep them in Core and remove them from
        the folds.

357-Q2  XGBOOST, OR THE GRADIENT BOOSTING ALREADY INSTALLED?
        The Suggest request named XGBoost. `_build_round_model` offers
        logistic regression, random forest and `gradient_boosting`, which is
        sklearn's `HistGradientBoostingClassifier` -- the same
        gradient-boosted-trees method, already a dependency, and already
        understood by the round machinery (grouped split, model card, saved
        joblib). Suggest asks for that.

        The question is whether the actual `xgboost` package is wanted. It
        would be a new dependency for an algorithm already present, and this
        path is explicitly the one that must run "on the machine the
        annotator is sitting at, without a GPU". Recommend NO unless there is
        a reason beyond the name.

357-Q3  DOES THE SUGGESTION SCHEME EXTEND PAST TWO CLASSES? (= 379-C)
        Still open, and now SAFE while it stays open: `write_suggestions`
        refuses any class value at or above `SUGGESTION_OFFSET` (10), because
        a suggested 1 and an answered 11 are the same integer and a bulk KEEP
        would rewrite one as the other with nothing able to tell. So a third
        class works today as long as it is below 10.

        The decision only becomes urgent if a screen ever needs ten or more
        classes, at which point the offset has to become a separate column
        rather than a bigger number.

        case it is the setting's own `set_default_*` function in
        `spacr.settings`. Nothing reads the value back. The dynamic reads
        that would make that claim wrong were checked by hand -- the
        greying tables in `classify` and `stream_dataset` are not reads,
        two same-named function parameters are not called with the
        setting, and `align`'s `normalization` is a local loop variable.

        THE QUESTION IS NOT THE SAME FOR ALL EIGHT, which is why it is
        here rather than decided. `save_to_db`, `normalize_plots` and
        `visualize` look like controls that lost their consumer. But
        `denoise` and `normalization` name capabilities spaCR HAS -- so
        the control may be a promise the pipeline never kept, which is
        worse than a dead setting rather than better, and retiring it
        would remove the evidence that it was meant to work.

        WHAT IS NEEDED: for each, retire or wire. A yes/no per name is
        enough; the retirement machinery (`RETIRED_SETTINGS` plus a
        message) already exists and was used for `gradient_accumulation`
        the same day.

357-Q6  `control_wells` IS ONE KEY WITH TWO MEANINGS. RENAME, OR SPLIT?
        ANSWERED 2026-09-09: SPLIT IT INTO TWO KEYS, as recommended.
        Found 2026-09-09 while landing 364's approved renames, and it stops
        that one rename until it is answered.

        The approved table says `control_wells -> stain_baseline_wells`.
        That name fits ONE of its two consumers and not the other, and the
        shipped tooltip says both out loud:

          "These wells set the empirical negative distribution for the
           PRE-PERMEABILISATION STAIN and are excluded from efficiency
           calculations ... SCREEN REGRESSION REUSES THIS KEY for a list
           matching filter_value."

        THE TWO USES ARE NOT THE SAME THING.

          * The invasion assay defaults it to None and uses it as a stain
            baseline -- `stain_baseline_wells` is exactly right for this.
          * Regression and sequencing default it to `filter_value` plus the
            declared control blocks, iterate it, and DROP those wells from
            the count table before the threshold sweep. It is a
            "wells the analysis must not see" list, and calling that a
            stain baseline would be wrong.

        `settings.py` carries a long comment saying the two must agree with
        `filter_value` or "the threshold is fitted on wells the regression
        never sees" -- so the shared key is load-bearing for one of them and
        incidental to the other.

        WHY IT MATTERS BEYOND THE NAME: one key with two meanings is the
        exact shape of the silent-divergence bugs this instruction was filed
        to remove. A user setting it for the stain changes what Regression
        drops, with nothing saying so.

        THE OPTIONS:
          (a) SPLIT. `stain_baseline_wells` for the invasion assay,
              a separate name for the regression list (`excluded_wells` or
              similar). Two keys, two tooltips, and the migration sends an
              old value to BOTH -- which preserves today's behaviour exactly.
          (b) RENAME ONLY. One key, new name, and the tooltip goes on
              documenting two meanings under a name that fits one.
          (c) LEAVE IT. `control_wells` is at least neutral between them.

        RECOMMEND (a). It is the only one that removes the divergence, and
        the migration is the same fold the other renames use.

        NOT GUESSED AT. The other six renames are unambiguous and are being
        landed; this one is held.
