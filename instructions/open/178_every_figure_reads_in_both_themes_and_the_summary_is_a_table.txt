C. DARK MODE EVERYWHERE, AND A STYLED SAVE
--------------------------------------------------------------------------------

HOW TO KNOW IT WORKED

* Switch to the light theme and back: no figure has invisible text at either
  setting, and nothing is hard-coded black or white.
* Right-click a count figure: seven plot types, and picking each redraws it.
* A summary reads as an aligned two-column table that uses the panel's width,
  with working save and copy buttons.
* Right-click -> Save opens a preview whose settings change the FILE and not
  the figure on screen.

2026-08-20 -- C.2 IS NOW BOTH BACKENDS.
--------------------------------------------------------------------------------

The matplotlib half previewed on a pickled COPY. That is not available for a
pyqtgraph plot: it is a live scene graph of Qt objects, it does not pickle,
and rebuilding one from its data items would be a second implementation of
every plot in `fast_plots` -- guaranteed to drift from the first.

SO THE LIVE PLOT IS DRESSED AND UNDRESSED around one render, and the reason
that is safe is that nothing repaints in between: both callers render the
SCENE into an offscreen image synchronously and no event loop runs inside the
block. `finally` restores unconditionally, so a write that raises leaves the
screen exactly as it was -- which is the property the instruction is actually
about.

`styled_snapshot` and `export_styled` wear the same styling through the same
context manager, so THE PREVIEW IS THE RENDER THE FILE GETS rather than an
approximation of it. A preview that came from a different code path is a
preview that can be wrong.

The dialog takes either backend, recognising a plot BY WHAT IT CAN DO rather
than by its class. What it cannot honestly offer it disables and explains:
TIFF is absent because `FastPlot.export` routes anything that is not .pdf or
.svg through the ImageExporter, which writes PNG -- a file whose name and
contents disagree is worse than a missing format. Size and resolution are
greyed because the page is set in millimetres on the plot's own menu and read
by all three of its export paths; offering a second answer in inches would be
two controls for one quantity with no way to tell which won.

"Save styled…" sits beside "Export…" rather than replacing it: the styled
route is three more clicks for a user who only wants the picture in front of
them.

2026-08-20 -- D: THE ARROWS COME OFF, AND THE CONDITION FOR THAT WAS CHECKED.
--------------------------------------------------------------------------------

They had been STYLED rather than removed, on the reasoning that "a bar that
genuinely overflows still needs a way along it". The ask already answered
that: "the user can allways scrole and they should also be able to use the
arrow keys". So the question was never whether to trust the claim -- it was
whether the claim is TRUE.

DRIVEN ON A 14-TAB BAR TOO NARROW TO HOLD ITS TABS:

    two Right keys on the focused bar   ->  tab 0 to tab 2
    one wheel notch over the bar        ->  tab 2 to tab 3
    setCurrentIndex(19) of 20           ->  that tab is on the visible bar

Qt scrolls the bar to reveal the current tab whichever way it moves, so a tab
reached by key or wheel is a tab the user can SEE -- which is what made the
arrows a third way to do what two already do.

`theme.take_the_scroll_arrows_off(root)` turns them off across a whole widget
tree, called by `AppScreen.__init__` and by `MainWindow`. Every QTabWidget on
the regression screen reports `usesScrollButtons() == False`.

THE STYLESHEET RULES STAY, deliberately. A bar built later, or one this sweep
does not reach, still has arrows that belong to the theme rather than to Qt's
default palette -- which is the thing that made them black in the first place.
The styling is the floor and this is the improvement on it, and a test holds
the floor so nobody removes it as now-dead code.

2026-08-20 (later) -- A's PLOT TYPES: THE THREE COMPOSITES WERE MISSING.
--------------------------------------------------------------------------------

"i should be able to right click on them and show them as: line, bar,
jitter-bar, jitter-box, jitter, box, violin plots"

Five of the seven were on the menu. `line`, `jitter_bar` and `jitter_box` were
not -- and offering `jitter` and `box` separately is NOT the same request. A
jitter-box is the box AND the observations at once: the box summarises and the
points are the evidence, which is exactly the argument 139 B makes for making
it the DEFAULT of the generated figures. Two pictures and no way to see both
is what the composite exists to fix.

THE SUMMARY FIRST, THE POINTS ON TOP, so the observations are not hidden
behind the shape that summarises them. AND THE POINTS KEEP THEIR ROWS, which
is what makes a composite the honest default rather than a nicer-looking one:
a bare box or bar stands for many rows and cannot honestly select one of them
-- the panel says so in its own mark note -- while a jitter-box lets the
reader see the distribution AND click any observation in it.

THE JOINING IS THE PANEL'S, NOT THE MARK'S. `add_group_mark` draws one group
at a time and cannot see its neighbours, so a line chart made of per-group
calls would be a row of unconnected markers. The panel joins them once every
group is drawn, and only when there are two -- a "line" through one point is a
point.

E IS DONE and was done by HIDING rather than deleting: the Results panel's
`colour by` combo is `setVisible(False)`, and it stays in the widget tree
because `plot_state` reads its `currentData()` -- so a run's remembered
colouring and 180's saved workspace still round-trip through it. The control
the user reaches is the volcano's own right-click entry, which is where it
belongs.
