================================================================================
THE IMPORT MODULE MUST ACCEPT ANY IMAGES, IN ANY LAYOUT, FROM ANY MICROSCOPE
================================================================================

Status:    END TO END IN CODE: corpus, inference, file metadata, reviewable
           plan, saved plans and project writing all work, and all 10 corpus
           layouts import to a plate spaCR's own parser reads -- against 2 of
           10 for the fixed convention list. The GUI screen is not started. The reviewable table, reading inside files, and
           writing the project are not started. Filed as 360, renumbered to 363 the
           same day (see 362 for why).
Requested: 2026-09-02, verbatim -- "spacr has an import data module, this
           module should make it easy for users to import their images
           irrespective of format or naming structure into spacr so that the
           images can be re formated into a spacr project that can be read by
           the core image modules. in mask there is a setting called
           consolidate which kind of does this. Develope the data import
           module so it is easy to import any number, of any formatted,
           images, with any number of dimensions (channel, z plane, time,
           tiles), with any folder or file metadata structure. this is a key
           module because it will determine if people can use spacr or not so
           this module needs to be extremely versatile and intuitive."
Owner:     spacr/foreign.py, spacr/qt/screens/foreign.py, spacr/io.py,
           spacr/convert.py.
Priority:  HIGHEST OF THE OPEN ITEMS. Every other module is downstream of a
           user getting their own images in. A tool that cannot read your data
           has no features.

--------------------------------------------------------------------------------
WHAT EXISTS TODAY, AND WHY IT IS NOT ENOUGH
--------------------------------------------------------------------------------

There are THREE separate half-answers, none of which is the module the
maintainer is describing, and the first job is to understand that they are
three answers to one question.

1. `metadata_type` in Mask. A CLOSED LIST of filename conventions:
   'cellvoyager', 'cq1', 'custom' (hand-written regex), 'auto'. This is the
   real import path today, and it is a Mask SETTING rather than a module. Its
   own tooltip states the failure mode: "An incorrect convention can misassign
   plate, well, field, or channel identifiers and place images in incorrect
   channel folders." A user whose microscope is not Yokogawa or CQ1 is asked
   to write a regular expression with named groups, having been given no way
   to see whether it worked until masks come out wrong.

2. `consolidate` in Mask. Recursively copies every image under `src` into one
   `<src>/consolidated` folder, prefixing each filename with its subfolder
   names so nothing collides, then repoints `src` there. This is the
   maintainer's "kind of does this". It flattens a FOLDER structure but throws
   the structure away rather than reading it -- the subfolder names become
   part of a filename and are then parsed, if at all, by the same closed regex
   list. It also copies, so disk use roughly doubles.

3. `spacr/foreign.py` and the Import screen. Genuinely good, and about the
   WRONG HALF of the problem: it is built for adopting somebody else's MASKS
   and MEASUREMENT TABLES -- a reviewable column mapping, unit conversion
   (their µm² against spaCR's px²), conflict detection against spaCR's own
   feature names. Its docstring is explicit that the mapping table is the
   middle of the screen because a human has to look at it. That review-first
   design is exactly right and is the model for this work. What it does not
   do is take a pile of raw images with an unknown naming scheme and produce a
   spaCR project.

So: the reviewable-import machinery exists but points at tables, and the
image-import machinery is a closed list of regexes hidden in a Mask setting.

--------------------------------------------------------------------------------
WHAT "ANY" HAS TO MEAN
--------------------------------------------------------------------------------

The maintainer named four axes. Each is a separate failure today.

  FORMAT. `.tif .tiff .png .jpg .jpeg .bmp .nd2 .czi .lif` are read somewhere
  in `io.py`. OME-TIFF, and whether a multi-page TIFF is Z, T, C or tiles, is
  the ambiguity that actually bites -- a page index means nothing on its own.

  NUMBER. "any number" includes one field and includes a 400-plate archive.
  These are not the same program: one wants a dialog, the other must not hold
  a file list in memory or copy 8 TB to flatten a folder.

  DIMENSIONS. channel, z, time, tile. Any subset, in any nesting, expressed
  in EITHER the filename OR the folder path OR inside the file's own metadata,
  and frequently split across all three (plate in the folder, well and field
  in the name, channel in the TIFF tag).

  METADATA STRUCTURE. This is the hard one and it is where the closed regex
  list fails. The information is the same everywhere -- plate, well, field,
  channel, z, t -- and only its ENCODING differs.

--------------------------------------------------------------------------------
THE SHAPE THE ANSWER SHOULD TAKE
--------------------------------------------------------------------------------

INFER, THEN SHOW, THEN LET THE USER CORRECT. Not "choose your convention from
this list", and not "write a regex". The module should:

  1. Walk a sample of the tree -- a sample, not all of it, so a 400-plate
     archive is as fast to inspect as one plate.
  2. Propose a parse: which path segments and which filename fragments carry
     plate / well / field / channel / z / t, read from the varying parts. A
     token that is constant across every file carries no information; a token
     that varies with exactly 4 values across 4 folders is probably the plate.
     This is inference from the data, not a lookup table, and it is what makes
     an unknown microscope work on the first try.
  3. SHOW THE PROPOSAL AS A TABLE the user can edit, the way the existing
     Import screen shows its column mapping -- with real example filenames
     beside the fields they were parsed into, so a wrong guess is visible
     BEFORE anything is written. This is the single most important
     requirement in this file. `metadata_type` is unusable today not because
     its regexes are bad but because the user cannot see what they did.
  4. Report what it could NOT place, by count and with examples. Silence about
     unparsed files is how a plate imports with a third of its fields missing.
  5. Write the project. Only after the user presses a separate button.

REUSE `foreign.py`'s PLAN/APPLY SPLIT. `plan_import` scans and verifies and
writes nothing; `Import` is a second press; edits re-run the checks in memory.
That is the correct architecture and it already exists -- extend it to images
rather than building a second one beside it.

SAVE AND REUSE THE MAPPING. A lab images the same way every week. The plan
must be savable and loadable, like the existing column mapping, so the second
import is one press. This is also what makes it scriptable and testable.

DO NOT COPY IF YOU CAN AVOID IT. `consolidate` doubles disk use to rearrange
names. Prefer recording where each image IS over moving it; where a copy or
conversion is genuinely needed, say how much space it will take before
starting.

--------------------------------------------------------------------------------
WHAT SHOULD HAPPEN TO THE THREE HALF-ANSWERS
--------------------------------------------------------------------------------

Once this exists, `metadata_type` and `consolidate` are import concerns
sitting in Mask's settings, and Mask should read a project that is already a
project. Retiring them is the natural end of this work -- but NOT in the same
change: they are the only working path today, and removing them before the
replacement is proven strands every existing user and every settings file in
the wild. Land the module, migrate, then retire, and record the retirement in
`RETIRED_SETTINGS` the way `corrected_manders` was.

--------------------------------------------------------------------------------
THE CORPUS EXISTS, AND THE GAP IS TWO OF TEN
--------------------------------------------------------------------------------

`tests/import_corpus.py` builds ten synthetic acquisitions from real
microscope conventions, and
`tests/test_the_import_corpus_is_the_specification.py` measures the current
parser against them. Built FIRST, deliberately: "accepts any format" has no
meaning as a requirement until "any" is a list of concrete trees, and the
failure this guards against is an importer that handles the shapes someone
imagined rather than the ones microscopes emit.

MEASURED 2026-09-02, with spaCR's default convention where no built-in one
claims the tree:

    layout               files  parsed  outcome
    cellvoyager              8       8  OK
    cq1                      8       8  OK
    harmony                  8       0  nothing recovered
    imagexpress              8       0  nothing recovered
    flat_ome                 4       0  nothing recovered
    per_well_folder          8       0  nothing recovered
    per_channel_folder       8       0  nothing recovered
    z_stack_in_file          8       0  nothing recovered
    time_in_file             8       0  nothing recovered
    tiled                   32       0  nothing recovered

  TWO OF TEN. And the eight are not exotic: Opera Phenix and ImageXpress are
  two of the most common high-content platforms in the field, and
  per-well-folder and per-channel-folder trees are what people produce by
  hand.

  THE ONE PIECE OF GOOD NEWS, and it is load-bearing for the rewrite: not one
  of the eight produced a PARTIAL answer. They recover nothing, which is
  visible, rather than half a plate, which is not. The existing parser fails
  honestly, and whatever replaces it must keep that property -- the
  `consolidate` bugs below are what the alternative looks like.

  WHAT EACH TREE IS FOR is written in `import_corpus.py`'s docstring, one
  sentence each, e.g. harmony encodes row and column SEPARATELY so the
  string "A01" never appears, and z_stack_in_file and time_in_file are
  byte-identical in layout so that only the file's own metadata says which
  a page index means.

  `CURRENTLY_PARSED = ("cellvoyager", "cq1")` in the test file is a RATCHET.
  Adding a layout adds a name; a name disappearing is a regression and is the
  only thing in that file that fails on an ordinary day.

--------------------------------------------------------------------------------
THE INFERENCE PASS EXISTS: 8 OF 10, AND TWO HONEST REFUSALS
--------------------------------------------------------------------------------

`spacr/image_import.py` -- `infer_layout(root)`. Reads what VARIES across a
sample of the folder rather than matching a whole filename against one of N
templates.

    fixed convention list          2 of 10 parse, 8 recover nothing
    inference from names           8 of 10
    plus reading inside the file   9 of 10
    plus ONE user answer          10 of 10

  THE OTHER TWO ARE REFUSALS, NOT FAILURES, and this is the design working:
    * `flat_ome` -- the channel is a PAGE INSIDE THE FILE. No name can carry
      it. Well and field are resolved and no channel is claimed.
    * `per_channel_folder` -- the channel is a folder named `DAPI`/`GFP`.
      That is a real axis and nothing maps a dye to an index, so it is
      reported in `unplaced` WITH ITS VALUES, which is what lets a caller ask
      rather than decide for the user.

  THE PRINCIPLE THAT DID THE WORK: a token that is the same in every file
  carries no information; a token that varies is an axis. `L01` in
  `plate1_A01_T0001F001L01A01Z01C01` is a constant and identifies nothing.
  Variance says a token IS an axis; the marker letter in front says WHICH.

  TWO BUGS FOUND BY MEASURING RATHER THAN REASONING, both worth keeping in
  mind for the rest of this work, and both caught only because the corpus
  existed first:

    * The first cut scored 1 of 10 -- WORSE than the fixed list it replaced.
      The name-shape used to group files of one convention included the
      alphabetic runs, but the WELL LETTER is alphabetic and varies, so
      `..._A01_...` and `..._B02_...` were two conventions, the majority won,
      and half of every plate vanished before anything was inferred.
    * Wells were matched on shape -- one uppercase letter plus two digits --
      which in the CellVoyager name matches `A01`, `L01`, `A01` and `C01`.
      All four became wells, the last overwriting the channel, so every plate
      had four wells and no channels. Only `A` varies; the rest are the
      convention's punctuation.

  Both are pinned by tests named for the symptom, and
  `test_no_file_is_silently_dropped` exists because placed-plus-skipped is
  the only total that catches the first one.

  READING INSIDE THE FILE closes `flat_ome`: `read_axes_inside(path)` takes
  the axes from the file's own metadata, so an OME-TIFF's two channels are
  found, and -- the pair the corpus exists to separate -- a Z-stack and a
  timelapse with IDENTICAL filenames and the same page count are told apart,
  z=5 against t=5. Nothing but the file can do that.

  IT REFUSES TO GUESS, and a test caught the first version doing so. A
  three-page TIFF with no axis metadata could be Z, T or C. tifffile reports
  its axes as `QYX`, and `Q` is tifffile's word for "these pages exist and I
  do not know what they are" -- the first `declared` check accepted any axis
  letter that was not Y, X or S, so `Q` passed and an unlabelled stack came
  back as known. `declared` now means a NAMED C, Z or T axis was found and
  nothing weaker; `is_ome` / `is_imagej` are not sufficient either, since a
  file can carry either container and still not say what its pages mean.

  THE REVIEWABLE PLAN EXISTS -- `plan_import(root)` returns an `ImportPlan`,
  and it is the piece this file called the single most important
  requirement. It writes NOTHING; `problems()` states every fault at once in
  plain sentences; `table()` prints example filenames BESIDE the fields they
  were parsed into, because a wrong guess is only visible next to the name it
  came from; and `with_mapping()` returns a NEW plan resolved in memory, so
  correcting a guess is instant and free.

  THE LAST LAYOUT CLOSES WITH ONE ANSWER. `per_channel_folder`'s dye folders
  are reported as "Token 0 varies across the folder (DAPI, GFP) and nothing
  says what it means", and `with_mapping({0: {"DAPI": 1, "GFP": 2}})`
  resolves it. Ten of ten, with the one thing only a person can know supplied
  by a person.

  A DISTINCTION THE PLAN KEEPS AND THE FIRST MEASUREMENT OF IT DID NOT: a
  COUNT is not a POSITION. `flat_ome` holds two channels IN EACH FILE, so
  `c_count=2` on every row -- one distinct value, not two. Scoring that as
  "one channel" is wrong, and writing it as `channel=2` would be worse: it
  would claim each file is channel 2. The plan carries `<axis>_count`
  separately for exactly this reason.

  THE PROJECT IS WRITTEN, AND SPACR'S OWN PARSER READS IT. `apply_import`
  names every image in the convention `utils._get_regex('cellvoyager')`
  already speaks, so every downstream module works unchanged. All ten corpus
  layouts import to a plate the shipped parser reads -- that is the measure
  that says the import is finished rather than finished-shaped.

  IT LINKS RATHER THAN COPIES. `consolidate` copies every image to rearrange
  its name, so a 300 GB plate costs 600 GB to import; nothing about renaming
  requires duplicating bytes. Symlinks by default, per-file fallback to a
  copy where they are unavailable, and the result reports what linking saved.

  IT REFUSES A PLAN WITH PROBLEMS. The import is the irreversible half, and
  every stated problem is a way for the result to be quietly wrong.

  A SAVED PLAN REPRODUCES AN IMPORT, from the CLI, with no GUI -- a lab
  images the same way every week and re-answering the same questions each
  time is how a tool stops being used. The plan is re-derived from the folder
  and the saved MAPPING rather than from a saved file table: the folder may
  have gained images since, and replaying a stale table would silently import
  last week's files.

  FOUND BY DOING IT: SPACR'S FILENAME HAS NO TILE SLOT. The convention is
  plate/well/T/field/L/A/Z/channel, so a field split into four tiles produces
  four images with ONE canonical name and three would be overwritten. The
  tiled tree resolves `tile: 4` perfectly and then cannot be written. By
  default those images are SKIPPED WITH A REASON rather than overwritten, and
  `tiles_as_fields=True` gives each tile its own field -- opt-in, because
  turning tiles into fields discards the fact that they are one field, and
  anything that stitches or measures per field is then wrong with nothing
  announcing it. Stitching is the other answer and belongs elsewhere.

  STILL TO DO for this part: the GUI screen over this, and deciding whether
  the canonical filename should grow a tile slot.

--------------------------------------------------------------------------------
ALREADY FIXED WHILE WRITING THIS FILE
--------------------------------------------------------------------------------

Commit 4f87b6259 fixes two bugs in `consolidate`, both found by RUNNING
`generate_image_path_map` rather than reading it, and both of which make
images disappear rather than fail:

  * `os.path.relpath(root, root)` is `'.'`, not `''`, so an image sitting
    directly in `src` was copied to `._name.tif` -- a hidden file on Unix,
    the AppleDouble resource-fork convention on macOS, and `spacr.io`
    skips anything beginning with a dot. Consolidating a FLAT folder
    therefore dropped every image in it silently.
  * the `consolidated` folder is created inside the folder being walked,
    so a second run consolidated the first run's output, prefixing it
    again and doubling the plate on every run.

Both are worth reading before starting this work, because they are the
kind of defect this module has to stop producing: no error, no message,
just fewer fields than the user supplied. The existing test asserted only
that the function returned something non-None, which is how they survived.

HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* A corpus of synthetic trees -- Yokogawa, CQ1, Opera/Harmony, ImageXpress,
  a flat folder of OME-TIFFs, a per-well folder tree, a per-channel folder
  tree, a multi-page TIFF that is Z and one that is T, one with tiles -- and
  each imports to the correct plate/well/field/channel/z/t WITHOUT the user
  naming a convention. Build the corpus first: it is the specification.
* A tree deliberately mixed and partly unparseable imports what it can and
  REPORTS the rest, with counts and example names.
* Nothing is written before the user confirms the plan.
* A saved plan reproduces an import exactly, from the CLI, with no GUI.
* Inspecting a large archive is sub-linear in file count.
