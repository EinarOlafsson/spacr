A PERFORMANCE SWEEP: NOTHING THAT LOADS BELONGS ON THE GUI THREAD
================================================================================

Status:    THREE causes fixed (2026-08-08). MainWindow build
           5107 ms -> 1457 ms; worst stall 6087 ms -> 2551 ms.
           The pandas question is settled: not worth doing.
Requested: 2026-08-08 — "do a performance optemization sweep, where loading of data for example is allways kept of the main app thred, and that background loading is generally kept on the background threads so the main application remains smooth. i noticed that there is a stutter at the beggining of starting the application."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

There is a reported STUTTER AT STARTUP. Not diagnosed, and it is the one
concrete symptom here, so it is where to begin rather than a general audit.

The infrastructure to fix it already exists. `spacr/qt/bridge.py` is the
route for long work -- `RunHandle`, `RunRegistry`, `PipelineWorker`,
`make_thread` -- and it is what pipeline runs already use. What has not been
audited is everything ELSE: icon loading, theme composition, settings
resolution, database opens, model discovery, the ambient backdrop.

Two measurements already taken this session are worth knowing:

  * `spacr.qt.theme.stylesheet()` imports 37 modules to collect their QSS
    the first time it is called, and it is called during startup.
  * A figure re-render on resize was measured at 1321ms on the GUI thread
    against a 250ms budget, and was moved to a worker. That was found by
    measuring, not by reading, and the same is likely true here.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A stutter is the application saying it is not listening. It is worst at
startup, which is the first thing every user sees and the moment they form
an opinion about whether the software is solid.

It is also the cheapest class of bug to let accumulate: every individual
blocking call is small enough to justify, and the sum is a program that
feels heavy. INVARIANTS have the rule already -- the GUI must never freeze,
long work goes through `bridge.py` -- what is missing is enforcement.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. MEASURE THE STARTUP STUTTER FIRST. Do not optimise on a guess; this
   codebase has punished that repeatedly. Two cheap approaches:
       - `python -X importtime -m spacr.qt` to rank import cost, which
         finds the "importing 37 modules" class of problem.
       - A QTimer on the GUI thread that logs whenever an event-loop tick
         takes longer than ~50ms, then start the app and read what it says.
   The second is better: it measures the actual symptom -- the loop not
   turning -- rather than a proxy for it.
2. Fix what the measurement names, in cost order. Likely candidates, all
   unverified: stylesheet composition, icon rasterisation, the app registry
   walk, any database or model-directory scan at construction.
3. THEN sweep for the general rule: no file read, database open, model load
   or network call on the GUI thread. Anything that must happen at startup
   and cannot be moved should be made LAZY -- deferred until the screen
   that needs it is opened -- which is usually easier than threading it.
4. Where work does move to a thread, follow INVARIANTS 4: connect BOUND
   METHODS to `QThread.finished`, never closures, and never connect
   `worker.deleteLater` to `worker.finished`. Both have already cost
   crashes here.
5. Add a guard test for whatever gets fixed, in the shape of the existing
   perf tests (`tests/qt/test_perf_guard_qt.py`), so it does not come back.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

The event-loop monitor from step 1 reports no tick over ~50ms during a cold
start, and the startup stutter is gone when a human launches it. Both:
the number is what makes it a regression test, and the human is what makes
it the actual bug.

2026-08-08, LATER - PANDAS AT STARTUP IS MULTI-PATH. THIS IS WHACK-A-MOLE.
--------------------------------------------------------------------------------

Second path closed: `spacr/layers.py` imported `OBJECT_KEY_COLUMNS` and
`object_keys` from `spacr.selection` at module scope, and `selection`
imports pandas at module scope. All four uses in `layers.py` are at CALL
time -- inside `columns()`, `frame()` and `object_keys()` -- so the
module-scope import bought nothing and put pandas on the Qt startup path.
They are imported inside those three methods now.

AND PANDAS IS STILL THERE, by a fourth route:

    604 ms  spacr.qt.app
    204 ms    spacr.qt.linked_selection
    198 ms      pandas

BE HONEST ABOUT THE SCORE. The widgets fix was a real, measured win
(670 -> 592 ms). This second one closed a path without moving the total,
because pandas still arrives via `linked_selection`. It is correct in
principle and worth keeping -- a module-scope import that nothing needs at
import time is wrong regardless -- but nobody should read it as 200 ms
saved. It is not.

WHAT THIS PATTERN MEANS, and it is the useful finding: pandas is not
imported at startup by one careless line. It is woven through the Qt entry
path in at least four places, and closing one reveals the next. So chasing
them one at a time is the wrong shape of work. Better:

    python -X importtime -c "import spacr.qt.app" 2>&1 | grep -n pandas

names every importer in one pass. Fix them together, then assert the
result with a TEST -- `'pandas' not in sys.modules` after importing
`spacr.qt.app` -- or the fifth path arrives next month and nobody notices.

That test is the actual deliverable of this half of the instruction, more
than any individual deferral.

STILL UNTOUCHED: the event-loop tick monitor. Import time remains a proxy;
the reported symptom is a stutter, and no measurement here has yet observed
the event loop failing to turn.

2026-08-08, LATER STILL - THE REMAINING 200 ms IS STRUCTURAL, NOT CARELESS
--------------------------------------------------------------------------------

Enumerated the importers in one pass, as the section above says to. The
chain that remains is:

    spacr.qt.app
      -> spacr.qt.linked_selection      204 ms
        -> spacr.selection
          -> pandas                     198 ms

`linked_selection.py` itself is INNOCENT. It has
`from __future__ import annotations`, and its only three uses of pandas are
`pd.DataFrame` in signatures -- which are strings at runtime, so its
`import pandas as pd` could move under TYPE_CHECKING and nothing would
change. I did not make that edit: it is correct in principle but saves
nothing here, and an unverifiable no-op change is not worth the risk.

The real source is `spacr/selection.py`, which uses pandas THIRTY times and
genuinely needs it. It is not a stray import that can be deferred; the
module is built on DataFrames.

SO THE HONEST CONCLUSION, and it changes what this half of the instruction
is: pandas cannot be lifted off the Qt startup path by moving imports
around. Removing the last ~200 ms means one of

  (a) splitting `spacr.selection` so the parts the Qt path needs at import
      time -- `DataFilter`, `ObjectRequest`, `Selection`, `as_key_index`,
      `OBJECT_KEY_COLUMNS` -- live in a module that does not import pandas,
      with the DataFrame functions in a sibling that does; or
  (b) deciding 200 ms of pandas at startup is acceptable and stopping,
      which is defensible: it is ~1/3 of a 600 ms import, once, at launch.

(a) is a real refactor with real regression risk across everything that
imports `spacr.selection`. (b) is free. This is a judgement about how much
the startup stutter actually costs the user, and the tick monitor -- still
unbuilt -- is what should decide it. If the loop never stalls more than
50 ms, the imports were never the problem and (b) is obviously right.

DO NOT keep deferring imports one at a time before that measurement. Two
were worth doing and are done; the third would be guessing.

A CHANGE THAT LOOKED RIGHT, MEASURED, AND WAS REVERTED. cProfile on the
MainWindow build attributed ~200 ms of 1000 ms to `_read_cached_icon` ->
`PIL.Image.convert` -- 50 cached icons decoded through PIL into numpy. The
pixmap path does not need an array at all, so Qt's own PNG loader should
have been strictly cheaper. Implemented it (`_cached_qimage`, keyed on the
resolved cache path so ENV_ICON_CACHE redirection stays isolated), then
A/B'd it over five fresh processes each:

    with the Qt fast path   907 923 857 835 979    (median 907)
    without                 873 867 855 821 887    (median 867)

No improvement, marginally worse. REVERTED.

WHY THE PROFILE LIED, which is the transferable part: cProfile charges
per-call overhead, and PIL decode plus `np.asarray` is call-heavy in a way
that Qt's single C++ entry point is not. Under the profiler the PIL route
looks ~5x its real cost; without it, decoding 50 small cached PNGs is not
where the time goes. `sort_stats("tottime")` on a library that crosses the
Python/C boundary often is a measurement artefact, not a finding.

The rule this file already states -- "fix what it names, not what looks
slow" -- needs one more clause: and then A/B the fix in fresh processes,
because what the profiler names can itself be an artefact of profiling.
