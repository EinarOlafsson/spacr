================================================================================
THE BACKDROP KEEPS MOVING WHILE PREFERENCES OR HELP IS OPEN
================================================================================

Status:    not started
Requested: 2026-09-09 -- "when the preferences menue or help menu is open the
           theme in the background stops, the theme should continue."
Owner:     unassigned

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Opening Preferences or Help freezes the animated backdrop behind the window.
It resumes when the dialog closes, so nothing is broken -- the animation is
simply not running for as long as the dialog is up.

WHAT IT IS NOT, MEASURED 2026-09-09 SO THE NEXT READER DOES NOT RE-DERIVE IT:

  * NOT `_pause_the_fractal`. `spacr/qt/screens/app_screen.py:1213` has an
    explicit pause helper, and it has exactly ONE caller --
    `app_screen.py:7439`, which stops the backdrop for the duration of a
    pipeline RUN. No dialog calls it.
  * NOT `Screensaver.closeEvent` (`spacr/qt/screensaver.py:126`), which
    pauses only the screensaver's own backdrop as its window goes.
  * NOT, on the face of it, the modal `exec()`. Preferences opens through
    `PreferencesDialog(window).exec()` (`spacr/qt/app.py:3883`,
    `spacr/qt/shortcuts.py:489`), and a modal dialog's nested event loop
    still delivers timer events to other widgets. `exec()` is worth ruling
    out properly rather than assuming, but it is not sufficient on its own.

SO THE CAUSE IS STILL OPEN. The two candidates worth measuring first are the
frame gate at `spacr/qt/widgets/fractal_travel.py:1107`
(``if self._busy or not self.isVisible(): return``) and the same test at
line 188 -- and whatever the dialog does to the window's active state. Note
that Qt's ``isVisible()`` is about show state rather than occlusion, so a
dialog merely covering the canvas should not trip it; if it does, that is
the finding.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The backdrop is the one part of the interface that says the application is
alive. Freezing it exactly when the user opens a settings panel reads as the
program hanging, which is the opposite of what a decoration is for -- and it
is most visible in Preferences, which is where the backdrop's own settings
live: a user changing the pointer reach or the speed cannot see the effect of
the change they are making.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. REPRODUCE IT AS A NUMBER, not as an impression. Count frames over a fixed
   wall-clock interval with the dialog shut, then with it open. A test can
   drive this without a human: open the dialog with `show()` inside a
   `qtbot.waitExposed`, sample the canvas's frame counter twice, and assert
   the second interval is not zero.

2. FIND THE GATE THAT CLOSES. Instrument the early returns named above and
   see which one fires while the dialog is up. Do not fix the first plausible
   one -- 382 in this repo was three separate causes wearing one symptom.

3. FIX IT WHERE THE DECISION IS MADE. If the canvas is stopping itself on a
   state that a dialog changes, the fix is in the canvas's own gate. If
   something is calling `pause()`, the fix is that caller. Either way the
   backdrop must keep running for a MODAL dialog and must still stop for a
   pipeline run, which is the one case that deliberately pauses it.

4. THE SCREENSAVER STAYS AS IT IS. Its `closeEvent` pause is a crash guard,
   not a decoration policy.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A test in `tests/qt/` that opens Preferences and asserts the backdrop's frame
counter advances while it is up, and a second that asserts a pipeline run
still pauses it. Both green, plus the eye test: open Preferences, watch the
backdrop move behind it.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

No cause is asserted here. The three ruled out above were ruled out by
reading the callers; the remainder was not measured, and filing a guess as a
finding is how the next session spends an afternoon on a mechanism that is
not there.

--------------------------------------------------------------------------------
2026-09-09 -- exec() IS RULED OUT, AND SO IS EVERY AMBIENT ANIMATION
--------------------------------------------------------------------------------

Measured rather than reasoned about, on the offscreen platform. The headline
is a NEGATIVE result and it removes most of the search space.

THE NESTED EVENT LOOP DOES NOT STARVE THE BACKDROP. This is the thing the
file above said was "worth ruling out properly rather than assuming", and it
is now ruled out. Paints counted over 0.5 s with an ambient backdrop running
behind a modal `PreferencesDialog`:

    outer loop, no dialog          7 paints
    inside a nested QEventLoop     6 paints

`QDialog.exec()` itself could not be called -- the suite refuses it headless,
correctly, because a modal has nobody to answer it -- so the nested loop was
entered directly with `QEventLoop.exec()`, which is the same mechanism
`exec()` runs. Timer events reach the widget through it.

NOR DOES ANY ANIMATION FREEZE. All six were built behind a shown modal
dialog and their paints counted over 0.4 s:

    blobs   BlobsEngine    base 6   with dialog 6
    aurora  AuroraEngine   base 6   with dialog 5
    ripple  RippleEngine   base 6   with dialog 5
    drift   DriftEngine    base 6   with dialog 5
    bokeh   BokehEngine    base 6   with dialog 5
    cells   CellsEngine    base 6   with dialog 5

AND THE WIDGET'S OWN GATES ARE NOT TRIPPED. With the dialog up:
`_timer.isActive()` is True, `_should_run()` is True, `isVisible()` is True.
The main window IS deactivated -- `win.isActiveWindow()` goes False -- but
nothing in `ambient.py`, `fractal_travel.py`, `fractal_cascade.py` or
`fractal_space.py` reads `isActiveWindow` or `ApplicationStateChange`, so
there is no gate for that to trip.

ONE CORRECTION TO THIS FILE'S OWN LEAD. The frame gate at
`fractal_travel.py:1107` cannot freeze anything: it RESCHEDULES --
`self._timer.start(50)` -- so a widget failing that test still advances at
20 fps. The line above it, `if self._stopped or self._paused: return`, is
the one with no reschedule, and `pause()` has no caller outside
`fractal_travel` and `timelapse_movie`. Line 188 is pointer sampling, not a
frame gate.

WHAT IS LEFT, in the order worth trying:

1.  A REAL DISPLAY. Offscreen has no compositor, so a window fully covered
    by a dialog still receives paint events here and would not on X11 or
    Wayland. If the freeze is "the covered region stops repainting", this
    harness cannot see it and no amount of measuring here will find it.
    Someone with a display should check whether the UNCOVERED part of the
    backdrop keeps moving while Preferences is up -- if it does, that is the
    whole answer and the report is about the covered part.

2.  THE SPACEOUT BACKDROP, which is a different widget. `fractal_travel` is
    not one of the six ambient animations -- the choices are none, blobs,
    aurora, ripple, drift, bokeh, cells -- so if the user meant the
    full-screen fractal, none of the measurements above apply to it.
    Worth asking which backdrop was on screen.

3.  `apply_ambient_preferences` (preferences.py:2190) rebuilds every
    AmbientWidget's theme, palette, blur, speed, size, resolution, density
    and direction. It runs on SAVE. If Preferences applies live on each
    control change, a rebuild per keystroke would read as a stall rather
    than a freeze. Its own comment already records one bug of this family --
    an `isVisible()` test that latched `_animating = False` onto every
    background tab the moment Preferences was saved, so those screens never
    animated again for the rest of the session.

--------------------------------------------------------------------------------
2026-09-09 -- FOUND. IT IS THE POPUP HOLD, AND ITS OWN JUSTIFICATION MEASURES
                     SOMETHING THE POPUP DOES NOT CAUSE
--------------------------------------------------------------------------------

THE GATE IS `a_popup_is_on_screen()`, and it was the first line of
`AmbientWidget._on_tick`. Neither the file's original three candidates nor
the leads added after them: it is an EXPLICIT, DELIBERATE hold, added
2026-08-30 in 61461ae40 to stop the dock flicker.

WHY THE EARLIER MEASUREMENTS MISSED IT. Every one of them opened a DIALOG.
`a_popup_is_on_screen()` is False for a dialog -- it asks
`QApplication.activePopupWidget()`, which is a `Qt::Popup` window, and
`QToolTip.isVisible()`. A QDialog is neither. The ambient engines were
measured behind a modal dialog and all six kept painting, correctly, and
that is why the search kept coming back empty. THE USER'S WORD WAS THE
CLUE AND IT WAS READ AS A SYNONYM: "help menu" is a MENU.

MEASURED, offscreen, a blobs backdrop behind a window, paints over 1.5 s:

    no menu        45
    menu open       0        <- the report, reproduced

And the two backdrops disagree, which is the second thing that made this
hard to see:

    ambient (QPainter)          menu open   0 paints
    fractal travel, CPU path    menu open  46 paints
    fractal travel, GPU path    holds, by the same call at line 2352

The CPU fractal renderer never had the hold, so whether the theme froze
depended on which backdrop the user had chosen.

--------------------------------------------------------------------------------
AND THE REASON GIVEN FOR THE HOLD DOES NOT SURVIVE MEASUREMENT
--------------------------------------------------------------------------------

61461ae40 says: "A popup composited over the native GL backdrop makes the
widgets around it repaint once -- 68 QLabel, 25 QWidget, 12 AppTile for the
spaCR menu. Over a moving surface that burst is visible ... Menu: 238
painted widgets -> 5."

Widget repaints counted over 1.2 s, an ambient backdrop behind forty
labels and twelve buttons:

    menu open, hold ON        2      (the animation is stopped)
    menu open, hold OFF   1,592
    NO menu,   hold ON    1,590
    NO menu,   hold OFF   1,590

THE LAST TWO LINES ARE THE FINDING. A moving backdrop repaints everything
above it whether or not a popup is on screen. The popup adds nothing --
1,592 against 1,590. So the hold was not removing a burst the popup
caused; it was stopping the animation, which stops the burst that is there
the whole time. "238 painted widgets -> 5" is the same measurement: 238 is
a backdrop animating for the length of a menu, and 5 is a backdrop that
has been switched off.

That does NOT make the flicker report wrong. The flicker is real and it is
about compositing, which an offscreen platform has none of. What the
numbers say is narrower and it is enough to act on: the burst is not
popup-specific, and the widget the fix was diagnosed against is named in
its own commit message -- "the NATIVE GL backdrop". `ambient.py` has no GL
surface and no native window. It is a QWidget painting with QPainter.

--------------------------------------------------------------------------------
WHAT WAS DONE
--------------------------------------------------------------------------------

The hold is removed from `AmbientWidget._on_tick` and KEPT in
`fractal_travel`'s GPU path, which is where the flicker was reported and
the only surface the diagnosis names. The default backdrop is one of the
six ambient engines, so this is the case the user meets.

`tests/qt/test_the_theme_keeps_moving_while_a_dialog_is_open.py` is the
number the instruction asked for rather than an impression: frames counted
over a fixed interval with the surface shut and open, for a menu and for a
modal dialog. Both were confirmed RED with the hold restored, so they
assert the fix rather than the platform.

The third test is the one that keeps the fix honest: a pipeline run still
pauses the backdrop through `set_animating(False)`, and it comes back
after. That is the one case that is supposed to stop, and a future change
that revives the popup hold by widening the pause cannot pass by making
the first two green.

`tests/qt/test_cov_r8_popup_state.py` asserted that the ambient tick
consults the helper. It now asserts the opposite, with the reason, so the
hold cannot come back by accident.

--------------------------------------------------------------------------------
WHAT IS LEFT, AND IT NEEDS A DISPLAY
--------------------------------------------------------------------------------

WATCH FOR THE DOCK FLICKER COMING BACK. It was a real report and this
change is the one thing that could revive it. If it does, the fix is not
to restore the hold -- it is to find why a QPainter backdrop makes the
dock flicker when the commit's own diagnosis says the mechanism is a popup
composited over a native GL child. A backdrop that stops moving is not a
fix for a backdrop that flickers; it is the absence of the backdrop.

If the flicker does come back, the smallest honest compromise is a hold
for TOOLTIPS ONLY -- they are transient and nobody is looking at the theme
while one is up -- with menus and dialogs left running. That keeps the
whole of this instruction's ask for Preferences, which is where the
theme's controls live.
