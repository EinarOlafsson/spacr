================================================================================
THE BACKDROP KEEPS MOVING WHILE PREFERENCES OR HELP IS OPEN
================================================================================

Status:    not started
Requested: 2026-09-09 -- "when the preferences menue or help menu is open the
           theme in the background stops, the theme should continue."
Owner:     unassigned

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Opening Preferences or Help freezes the animated backdrop behind the window.
It resumes when the dialog closes, so nothing is broken -- the animation is
simply not running for as long as the dialog is up.

WHAT IT IS NOT, MEASURED 2026-09-09 SO THE NEXT READER DOES NOT RE-DERIVE IT:

  * NOT `_pause_the_fractal`. `spacr/qt/screens/app_screen.py:1213` has an
    explicit pause helper, and it has exactly ONE caller --
    `app_screen.py:7439`, which stops the backdrop for the duration of a
    pipeline RUN. No dialog calls it.
  * NOT `Screensaver.closeEvent` (`spacr/qt/screensaver.py:126`), which
    pauses only the screensaver's own backdrop as its window goes.
  * NOT, on the face of it, the modal `exec()`. Preferences opens through
    `PreferencesDialog(window).exec()` (`spacr/qt/app.py:3883`,
    `spacr/qt/shortcuts.py:489`), and a modal dialog's nested event loop
    still delivers timer events to other widgets. `exec()` is worth ruling
    out properly rather than assuming, but it is not sufficient on its own.

SO THE CAUSE IS STILL OPEN. The two candidates worth measuring first are the
frame gate at `spacr/qt/widgets/fractal_travel.py:1107`
(``if self._busy or not self.isVisible(): return``) and the same test at
line 188 -- and whatever the dialog does to the window's active state. Note
that Qt's ``isVisible()`` is about show state rather than occlusion, so a
dialog merely covering the canvas should not trip it; if it does, that is
the finding.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The backdrop is the one part of the interface that says the application is
alive. Freezing it exactly when the user opens a settings panel reads as the
program hanging, which is the opposite of what a decoration is for -- and it
is most visible in Preferences, which is where the backdrop's own settings
live: a user changing the pointer reach or the speed cannot see the effect of
the change they are making.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. REPRODUCE IT AS A NUMBER, not as an impression. Count frames over a fixed
   wall-clock interval with the dialog shut, then with it open. A test can
   drive this without a human: open the dialog with `show()` inside a
   `qtbot.waitExposed`, sample the canvas's frame counter twice, and assert
   the second interval is not zero.

2. FIND THE GATE THAT CLOSES. Instrument the early returns named above and
   see which one fires while the dialog is up. Do not fix the first plausible
   one -- 382 in this repo was three separate causes wearing one symptom.

3. FIX IT WHERE THE DECISION IS MADE. If the canvas is stopping itself on a
   state that a dialog changes, the fix is in the canvas's own gate. If
   something is calling `pause()`, the fix is that caller. Either way the
   backdrop must keep running for a MODAL dialog and must still stop for a
   pipeline run, which is the one case that deliberately pauses it.

4. THE SCREENSAVER STAYS AS IT IS. Its `closeEvent` pause is a crash guard,
   not a decoration policy.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A test in `tests/qt/` that opens Preferences and asserts the backdrop's frame
counter advances while it is up, and a second that asserts a pipeline run
still pauses it. Both green, plus the eye test: open Preferences, watch the
backdrop move behind it.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

No cause is asserted here. The three ruled out above were ruled out by
reading the callers; the remainder was not measured, and filing a guess as a
finding is how the next session spends an afternoon on a mechanism that is
not there.

--------------------------------------------------------------------------------
2026-09-09 -- exec() IS RULED OUT, AND SO IS EVERY AMBIENT ANIMATION
--------------------------------------------------------------------------------

Measured rather than reasoned about, on the offscreen platform. The headline
is a NEGATIVE result and it removes most of the search space.

THE NESTED EVENT LOOP DOES NOT STARVE THE BACKDROP. This is the thing the
file above said was "worth ruling out properly rather than assuming", and it
is now ruled out. Paints counted over 0.5 s with an ambient backdrop running
behind a modal `PreferencesDialog`:

    outer loop, no dialog          7 paints
    inside a nested QEventLoop     6 paints

`QDialog.exec()` itself could not be called -- the suite refuses it headless,
correctly, because a modal has nobody to answer it -- so the nested loop was
entered directly with `QEventLoop.exec()`, which is the same mechanism
`exec()` runs. Timer events reach the widget through it.

NOR DOES ANY ANIMATION FREEZE. All six were built behind a shown modal
dialog and their paints counted over 0.4 s:

    blobs   BlobsEngine    base 6   with dialog 6
    aurora  AuroraEngine   base 6   with dialog 5
    ripple  RippleEngine   base 6   with dialog 5
    drift   DriftEngine    base 6   with dialog 5
    bokeh   BokehEngine    base 6   with dialog 5
    cells   CellsEngine    base 6   with dialog 5

AND THE WIDGET'S OWN GATES ARE NOT TRIPPED. With the dialog up:
`_timer.isActive()` is True, `_should_run()` is True, `isVisible()` is True.
The main window IS deactivated -- `win.isActiveWindow()` goes False -- but
nothing in `ambient.py`, `fractal_travel.py`, `fractal_cascade.py` or
`fractal_space.py` reads `isActiveWindow` or `ApplicationStateChange`, so
there is no gate for that to trip.

ONE CORRECTION TO THIS FILE'S OWN LEAD. The frame gate at
`fractal_travel.py:1107` cannot freeze anything: it RESCHEDULES --
`self._timer.start(50)` -- so a widget failing that test still advances at
20 fps. The line above it, `if self._stopped or self._paused: return`, is
the one with no reschedule, and `pause()` has no caller outside
`fractal_travel` and `timelapse_movie`. Line 188 is pointer sampling, not a
frame gate.

WHAT IS LEFT, in the order worth trying:

1.  A REAL DISPLAY. Offscreen has no compositor, so a window fully covered
    by a dialog still receives paint events here and would not on X11 or
    Wayland. If the freeze is "the covered region stops repainting", this
    harness cannot see it and no amount of measuring here will find it.
    Someone with a display should check whether the UNCOVERED part of the
    backdrop keeps moving while Preferences is up -- if it does, that is the
    whole answer and the report is about the covered part.

2.  THE SPACEOUT BACKDROP, which is a different widget. `fractal_travel` is
    not one of the six ambient animations -- the choices are none, blobs,
    aurora, ripple, drift, bokeh, cells -- so if the user meant the
    full-screen fractal, none of the measurements above apply to it.
    Worth asking which backdrop was on screen.

3.  `apply_ambient_preferences` (preferences.py:2190) rebuilds every
    AmbientWidget's theme, palette, blur, speed, size, resolution, density
    and direction. It runs on SAVE. If Preferences applies live on each
    control change, a rebuild per keystroke would read as a stall rather
    than a freeze. Its own comment already records one bug of this family --
    an `isVisible()` test that latched `_animating = False` onto every
    background tab the moment Preferences was saved, so those screens never
    animated again for the rest of the session.

--------------------------------------------------------------------------------
2026-09-09 (later) -- A REAL X SERVER RULES OUT OCCLUSION, AND ONE REAL FREEZE
IS MEASURED: 902 ms ON THE FIRST OPEN
--------------------------------------------------------------------------------

The previous note said offscreen "cannot see" an occlusion freeze and that
"someone with a display should check". That is now done WITHOUT a display and
without touching the maintainer's screen: `xvfb-run` is a real X server, so a
window covered by another window is genuinely covered, exactly as it is on
`:0`. Both are non-compositing X11.

OCCLUSION IS NOT IT. A modal `QDialog` LARGER than the host, positioned over
it and raised, counted against the backdrop's own paint events (an event
filter on `QEvent.Paint`, not the widget's internal counter -- see the trap
below):

    widget                     base   covered   after
    spaceout fractal (cpu)      27      28       27      paints/s
    ambient blobs               25      25       25
    ambient aurora              25      25       25
    ambient ripple              25      25       25
    ambient drift               25      25       25
    ambient bokeh               25      25       25
    ambient cells               25      25       25

Fully covered, on a real X server, every backdrop keeps painting at its full
rate. Candidate 1 of the previous note is closed.

A TRAP FOR WHOEVER MEASURES THIS NEXT. The fractal's `self._frames` is
incremented where a worker frame ARRIVES (`fractal_travel.py:1194`), not in
`paintEvent`. It therefore counts computation, not drawing, and would keep
climbing while the screen showed a stale image. Count `QEvent.Paint` on the
widget instead; the two numbers are not the same measurement.

CANDIDATE 3 IS ALSO CLOSED, by reading rather than by timing.
`apply_ambient_preferences` has exactly ONE production caller --
`apply_preferences_to_app` (`preferences.py:4156`) -- and that is called from
`_save` (`preferences.py:6717`), which runs on OK and then `dlg.accept()`s.
Nothing applies it per keystroke, so there is no rebuild-per-control stall.
The `isVisible()` latch its comment describes was already fixed and now reads
`widget.set_animating(True)` unconditionally.

WHAT *IS* REAL, AND IT IS A FREEZE THE REPORT WOULD FIT: building the dialog
blocks the GUI thread for most of a second, and the backdrop gets NOTHING
during it.

    backdrop alone                 25 paints/s
    PreferencesDialog(...) build  902 ms, 0 backdrop paints during it
    dialog shown, non-modal        25 paints/s
    dialog shown, modal            26 paints/s
    dialog closed                  25 paints/s

A dead stop of nearly a second, at exactly the moment the user asks for
Preferences, on a backdrop whose whole job is to say the application is
alive.

BUT IT IS A FIRST-OPEN COST, NOT A PER-OPEN ONE, so it is probably not the
whole report. Profiled with the imports already warm, the SECOND build of the
same dialog is **55 ms** -- sixteen times cheaper. The 902 ms is import work
(`figure_settings`, the settings model, the i18n catalogs) that the first
`PreferencesDialog(...)` in a session pays for. Worth fixing on its own: it is
a visible stall and the imports could be warmed off the GUI thread at launch,
the way the backdrop's own heavy import already is (`_HeavyImportInProgress`).

The recurring 55 ms also has a cheap, obvious component: 346 `tr()` calls each
re-deriving `current_language()` through `_settings()`, 415 QSettings reads in
one dialog build. That is a memoisation away and it is 40% of what is left.

THE LEADING REMAINING CANDIDATE IS THE GPU BACKEND, and it is the one thing
this harness structurally cannot reach. Everything above used the CPU
renderer, because Xvfb has no GPU. On the maintainer's machine
`create_fractal_widget` takes the `gpu_is_available()` branch and returns
`_make_gpu_widget`, a vispy canvas with a NATIVE window and its own GL
surface. A native GL surface is the one kind of widget an X server can
genuinely stop feeding when it is obscured -- buffer swaps on an unmapped or
fully-obscured surface are allowed to block or be discarded -- and that would
match the report exactly: stops while covered, resumes when uncovered, and
never reproduces under the CPU renderer or offscreen.

TO TEST IT, and this needs the machine with the GPU:

    from spacr.qt.widgets.fractal_travel import gpu_is_available
    gpu_is_available()          # must be True, or this candidate is void

then repeat the paint count above with `Settings(backend='gpu')`. If the
covered column collapses to zero there and stayed at 27 here, that is the
finding and the fix is in the GL canvas's swap policy, not in any gate in
`ambient.py`.

STILL NOT ASSERTED: which backdrop the maintainer had on screen. The previous
note's question stands and it decides which of the two widgets above is even
being described.

--------------------------------------------------------------------------------
2026-09-09 -- THE ONE FREEZE THAT WAS MEASURABLE IS FIXED; THE ITEM STAYS OPEN
--------------------------------------------------------------------------------

The 902 ms dead stop on the first Preferences open is gone. Two changes,
both recorded with their numbers in instruction 380:

  * `settings_model` and `imagery` join `launch`'s existing background
    prewarm, moving 557 ms of import off the GUI thread.
  * `PreferencesDialog` builds inside `i18n.ui_language_resolved_once()`,
    which takes the recurring build from 55 ms to 30 ms.

    first open, cold        902 ms  ->  139 ms
    second open              55 ms  ->   30 ms

That is a real freeze of the backdrop removed, and it is the shape of the
report -- the backdrop stops at the moment Preferences is asked for. It is
NOT proof that this was what the maintainer saw, and this item does not
close on it: a 900 ms stall is not "the theme stops while the menu is open",
and nothing here explains a freeze that lasts as long as the dialog is up.

WHAT WOULD CLOSE IT is still the GPU test in the previous note, on the
machine with the card. Everything measured so far used the CPU renderer.

--------------------------------------------------------------------------------
2026-09-10 -- THE GPU CANDIDATE IS ALSO CLOSED. XVFB HAS A GL PATH.
--------------------------------------------------------------------------------

The previous note said the GPU backend was "the one thing this harness
structurally cannot reach". That was wrong, and cheaply so:

    gpu_is_available()  ->  True, under xvfb-run

Mesa's llvmpipe gives a real GLX context on a real X server. It is software
rendering, so it says nothing about how FAST a card draws -- but the question
here was never speed. It was whether an X server stops feeding a NATIVE GL
SURFACE that is fully obscured, and llvmpipe's surface is native in exactly
the same way a driver's is.

    backend: gpu, pattern orbit, 600x460 behind a 760x600 modal dialog

    base             94 draws / 1.5 s
    fully covered    94 draws / 1.5 s
    uncovered again  94 draws / 1.5 s

Not one frame lost. The GPU backdrop does not stop when a dialog covers it.

AND A COUNTER THAT READS ZERO IS NOT A FREEZE. The first attempt at this
counted `QEvent.Paint` on the wrapper widget and got 0 in every column,
BASE INCLUDED -- a vispy canvas draws through its own GL surface and never
delivers a Qt paint event to the QWidget around it. Reported without the
base column that would have read as "the GPU backdrop is completely
frozen", which is the failure mode this file has now avoided twice. The
draw count comes from hooking the canvas's own `on_draw`.

WHERE THAT LEAVES 385. Every mechanism this file has named is now measured
and none of them freezes anything:

    the modal nested event loop     ruled out 2026-09-09
    all six ambient engines         ruled out 2026-09-09
    the widget's own gates          ruled out 2026-09-09
    apply_ambient_preferences       ruled out 2026-09-09 (one caller, on save)
    occlusion, CPU renderer         ruled out 2026-09-09 (real X server)
    occlusion, GPU renderer         ruled out 2026-09-10 (this note)

ONE REAL FREEZE WAS FOUND AND FIXED: 902 ms of dialog construction with the
backdrop stopped for all of it, now 139 ms. See 380.

WHAT IS LEFT IS A QUESTION FOR THE MAINTAINER, not another measurement.
Everything above is on Mesa's software GL with no compositor. The remaining
difference from the report is a real NVIDIA driver, a compositing desktop,
and a 4K screen. The useful thing to ask -- and it decides whether there is
anything left to fix at all -- is whether the UNCOVERED part of the backdrop
keeps moving while Preferences is up. If it does, the report is about the
covered part and the answer is "that is the window manager, and it is
correct". If the whole thing stops, that is a driver-level buffer-swap
policy and the fix is in the GL canvas, not in any gate in this package.
