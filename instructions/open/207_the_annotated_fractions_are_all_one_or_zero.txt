================================================================================
THE ANNOTATED FRACTIONS ARE ALL ONE OR ZERO
================================================================================

Status:    filed 2026-08-21, not started.
Requested: 2026-08-21 -- "i think there is a problem with the gRNA annotation
           alorithms or the graphing logic. if i pick tob py score, pick
           225160 on the volcano plot, and jitter plot and cell level i see a
           tone of dotts at 1 and a tone of datapoints at 0. this would bean
           that either 225160 has a fraction of 1 in the wells it is found in,
           which the image tabs indicate as all are circled".
Owner:     Sequencing annotation, cell table graphs

--------------------------------------------------------------------------------
A. THE SYMPTOM
--------------------------------------------------------------------------------

Top-by-score, guide 225160, cell level, jitter: the points pile at exactly 1
and exactly 0 and nowhere between. A continuous fraction that only ever takes
its two extreme values is not a fraction; it is a label being plotted as a
number, or a denominator that is always the numerator.

--------------------------------------------------------------------------------
B. THE MAINTAINER'S OWN DIAGNOSIS, WHICH IS THE PLACE TO START
--------------------------------------------------------------------------------

    "actually the problem might be the show_all_in_well option ... if that is
     off then all the images are annotated as gRNA because only those are
     shown."

That is a complete and self-consistent explanation of the symptom: with
`show_all_in_well` off, the only objects on the screen are the ones already
annotated to the guide, so every visible object is a hit and every visible
fraction is 1. The 0s are then the well-mates of some OTHER guide, drawn
because they are in frame and annotated to nothing.

CHECK IT BEFORE FIXING ANYTHING ELSE. It costs one query -- the fraction
distribution with the option on and off -- and it decides whether there is an
annotation bug at all.

  1. `show_all_in_well` DEFAULTS ON. Asked for directly ("change that to
     default by the way"), and it is the honest default: a view showing only
     the objects that agree with the annotation cannot disagree with it.

  2. THE UNANNOTATED ARE SHOWN AND LABELLED `Non_annotated`, not dropped and
     not silently counted as zero. "eaven if this is shown i an the non
     annotated datapoints to be annotated as Non_annotated and shown."
     A dropped object is invisible in the plot AND in the denominator, which
     is how a fraction reaches 1.

--------------------------------------------------------------------------------
C. WHICH METHODS CAN HAVE UNANNOTATED CELLS AT ALL
--------------------------------------------------------------------------------

The maintainer's reasoning, to be confirmed against the code and corrected in
writing if wrong:

  * `top_by_score`   -- YES. It picks a winner per object, so an object whose
                        best score is not the chosen guide is annotated to
                        something else, and one with no score at all is
                        annotated to nothing.
  * `assigned`       -- NO, expected: "given that fractions will be
                        normalized to 1 then nothing should be Non_assigned".
  * `multivariate`   -- NO, same reasoning.
  * `attributed`     -- UNKNOWN, stated as unknown. Settle it and say which.

Where a method genuinely cannot produce an unannotated object, the
`Non_annotated` group must be ABSENT rather than empty -- an empty group in a
legend is a question the reader has to answer.

--------------------------------------------------------------------------------
D. NORMALISED OR RAW FRACTIONS, THE USER'S CHOICE
--------------------------------------------------------------------------------

    "if i am wirite then for top by score would pick up low scoring cells
     because the fraction for 225160 is normalized to a value that is to
     high. there fore the user should be able to use values based on the
     regression normalized gRNA fractions or the Non normalized gRNA
     fractions, that would be the more conservative fraction, because
     spurious barcodes would be included."

The mechanism named here is real and worth stating plainly: normalising a
well's guide fractions to sum to 1 REDISTRIBUTES the reads of every guide
that was filtered out onto the ones that remain. A guide with few reads in a
well can come out of that with a high normalised fraction, and top-by-score
then annotates cells to it on the strength of a number that normalisation
created.

So the fraction the annotation runs on becomes a SETTING with two values:

  * normalised -- today's behaviour, fractions summing to 1 per well;
  * raw -- the guide's reads over ALL reads in the well including the ones
    normalisation discards. Lower, and conservative for the stated reason:
    spurious barcodes stay in the denominator where they can dilute a
    marginal guide instead of being handed to it.

BOTH ARE DEFENSIBLE and neither is right for every screen, which is why it is
a choice and not a fix. The plot must say which one it used.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* The fraction distribution for 225160 at cell level is reported with
  `show_all_in_well` on and off, and the difference between them is the
  answer to whether there was ever an annotation bug.
* `show_all_in_well` defaults on.
* Unannotated objects are drawn and labelled `Non_annotated` wherever a
  method can produce them, and the group is absent where it cannot.
* Raw and normalised fractions are both selectable, both documented, and the
  figure says which it drew.
* The four methods' capacity for unannotated objects is settled IN WRITING
  against the code, including `attributed`, which is currently unknown.

--------------------------------------------------------------------------------
AND THE SCREEN'S OWN CEILING, MEASURED 2026-08-21
--------------------------------------------------------------------------------

Asked for alongside this: "for each method i want as many cells as the
method can reasonably annotate annotated ... with no method can we annotate
every cell, for that we would need a much largesr screen."

COVERAGE IS NOT A GOAL. A method that annotates every cell has not done
well, it has declined to abstain. `spacr/annotation_power.py` computes what
a screen can support at all, before any method is run.

The limit is arithmetic. A phenotype-positive cell carries guide `g` with

    P = pi se / ( pi se + (1 - pi)(1 - sp) )

and false positives are a share of the NEGATIVES -- so when a guide is rare
almost every cell in the well is a negative, and a small false-positive rate
on nearly everything outnumbers a large true-positive rate on almost
nothing. Below

    pi* = t(1 - sp) / ( se(1 - t) + t(1 - sp) )

no method using that evidence can do better. It is not the algorithm.

RUN ON PLATE 1 OF THE tsg101 SCREEN, with its own measured classifier and
its own counts, at t = 0.55:

    floor pi*                        1.9% of a well
    well-guide pairs clearing it     1,430 of 172,756  (0.8%)
    guides reachable anywhere        451 of 1,379     (32.7%)
    guides reachable NOWHERE         928

    now     384 wells, 440 guides in a typical well
    needed   52 guides per well, so 3,308 wells -- 8.6x the plates
    or       hold the wells and cut the library to 160 guides
    or       raise specificity to 0.9982 at the current shape

MORE CELLS PER WELL MOVE NONE OF IT. The fraction is a share, so imaging
more fields gives more annotated cells at the same rate and never a better
rate. Worth printing before anyone images more.

This also reframes section A. The reported pile-up at 1 and 0 sits on a
screen where two thirds of the guides cannot be annotated at all, so a
method appearing to annotate them confidently is the first thing to
disbelieve.

--------------------------------------------------------------------------------
THE THRESHOLD CAN BE MEASURED INSTEAD OF GUESSED (proposed 2026-08-21)
--------------------------------------------------------------------------------

    "another way to calculate the gRNA fraction threshold is measure the
     total fraction and the individual guide fractions in that are detected
     in the first 3 columns."

RIGHT, AND THE ANSWER IS THE PER-GUIDE FACTOR RATHER THAN THE SINGLE VALUE.
`spacr/read_background.py` implements it. A column of known composition is a
direct measurement of the spurious rate: every read that is not the intended
guide is noise by construction.

WHAT THE PLATE ACTUALLY CONTAINS, checked before anything was built on the
description, because it differs from it in three ways that matter:

  * column 1 is 56-73% `TGGT1_233460_4`, not 100%;
  * column 2 is 55-87% `TGGT1_239740_1`. The request named 249730; the reads
    say 239740. Worth confirming which is meant;
  * column 3 is the stated mix, and
  * `TGGT1_220950_1` IS IN ALL 48 CONTROL WELLS at 4-16%, where the request
    says there should be no other guides. It is also the largest guide in
    column 4 at 23%.

Measured over the 48 control wells:

    spurious mass per well        median 31.1%  (4.9% - 69.8%)
    median guide background            0.0133%
    99th percentile (outliers out)     0.147%
    TGGT1_220950_1                     9.22%  --  693x the median, 48/48 wells

SO A SINGLE THRESHOLD CANNOT SERVE BOTH POPULATIONS. The diffuse haze is
trace-level and the current 2% constant is more than an order of magnitude
above it -- it deletes real biology to remove noise that 0.15% would have
removed. And no threshold low enough to be sensible touches 220950, which
sails through at 9%.

THE READS CANNOT SAY WHAT 220950 IS. Either a sequencing artefact -- index
hopping, a barcode collision -- or a guide genuinely over-represented in the
library and really in those cells. The correction is opposite in the two
cases. The IMAGING can separate them: a guide really present moves its
cells' phenotype and an artefact does not. `suspicious()` reports the
candidate and refuses the verdict.

AND THE CONTROL COLUMNS OVERSTATE THE BACKGROUND FOR AN ORDINARY WELL. Index
hopping scales with the abundance of the source, and a control well has one
guide at seventy per cent where an ordinary well's largest is five.
`subtract_background` takes a `scale` for that reason and 1.0 is the
conservative end.

A FAULT THE TESTS CAUGHT IN THE FIRST IMPLEMENTATION: the suggested
threshold took a quantile over ALL the backgrounds, so it was contaminated
by exactly the outliers it was meant to exclude. On a 42-guide fixture one
outlier at 9% dragged the 99th percentile to 6.6%. On the real 1,325-guide
screen the same outlier hid inside the quantile instead, which is worse --
nothing looked wrong. The outliers are now removed before the quantile, by
the same rule `suspicious` uses.

--------------------------------------------------------------------------------
THE OUTLIER IS RESOLVED: IT IS CONTAMINATION, SO IT IS EXCLUDED
--------------------------------------------------------------------------------

Answered 2026-08-21: "TGGT1_220950_1 is primer/grna plasmid contamination.
we should add an exclude to the controlls and filters and exclude
TGGT1_220950_1". The control composition was confirmed at the same time --
column 1 is 100% TGGT1_233460_4, column 2 100% TGGT1_239740_1, column 3 both,
and everything else in them is noise. The guide named in the original request
as 249730 is TGGT1_239740_1.

EXCLUSION, NOT SUBTRACTION, and the distinction is the operation rather than
a nicety. Background subtraction says some of a guide's reads here are
spurious copies of a real guide. Exclusion says the SEQUENCE IS NOT A GUIDE
IN A CELL AT ALL -- it is in the library prep and never in a nucleus -- so it
does not belong in the denominator either. The survivors are renormalised
over what remains.

IT IS NOT A TIDYING STEP. TGGT1_220950_1 is 19.88% OF ALL PLATE-1 READS.
Removing it:

    control purity (median)     68.9%  ->  77.0%
    spurious mass per well      31.1%  ->  23.0%
    guides flagged as outliers    one  ->  none
    every real guide's fraction        x1.25

That quarter moves guides across the annotatability floor, so it changes the
reachability arithmetic recorded above and not only the tidiness of a table.

Implemented as the `exclude_grnas` setting, applied by `drop_guides` before
fractions are formed and honoured by `_well_guide_fractions`. THE DEFINITIVE
PLACE IS UPSTREAM, at count-table construction, so that every reader of the
table sees the same denominator; the annotation path is wired now because it
is what these instructions are about.

A CORRECTION MADE WHILE TESTING, recorded because the first version of the
test asserted the opposite: subtracting a guide's FULL background and
renormalising is arithmetically identical to excluding it. The difference is
narrower than it looks -- the background is a MEDIAN over control wells, so
in any well where the contaminant runs above its median, subtraction leaves
the excess behind and calls it a real guide. Exclusion does not care how much
there is.

--------------------------------------------------------------------------------
THE EXCLUSION IS ONE POINT, ABOVE EVERYTHING, AND TAKES GENES
--------------------------------------------------------------------------------

    "this should be moved to controls and filters, and make sure it is
     removed first. right?" ... "in the exclude i should be able to put in
     several guides or genes."

RIGHT, AND THE FIRST VERSION WAS WRONG IN EXACTLY THE WAY THAT QUESTION
ANTICIPATES. It filtered inside `_well_guide_fractions`, which the posterior
pickers read -- but `select_montage` computes `well_totals` by summing the
fraction column over the FULL count table, and `normalised_share` divides by
that sum. The contaminant was still in that denominator, so `rank` -- the
default picker -- kept every real guide's share held down by the
contaminant's own.

There is now exactly ONE exclusion point, on the count table itself, before
`well_totals`, before the per-well fractions, before any posterior. Measured
on a synthetic well: excluding a 50% contaminant doubles the cells expected
for a guide at 30%, which is the suppression the ordering prevents.

GENES AND GUIDES, several of each, resolved by `control_names.rows_for` --
the same resolver `controls`, `positive_control` and `negative_control` use,
so an exclusion is typed in the spelling those already accept. A gene takes
all of its guides, so excluding a contaminated amplicon does not mean listing
four of its five.

A MISSPELLED EXCLUSION EXCLUDES NOTHING AND LOOKS LIKE IT WORKED, which is
how a known contaminant survives the filter meant to remove it.
`unmatched_exclusions` names them and the montage notes carry it.

Moved from the trailing "Other" section -- where an uncategorised setting
lands -- into "Plate Layout & Controls", beside `controls` and the two
control settings.

--------------------------------------------------------------------------------
AND A LIVE BUG FOUND ON THE WAY: THE GENE COLUMN BRANCH OF `matches`
--------------------------------------------------------------------------------

NOT ABOUT EXCLUSION. `control_names.matches` has three branches, and both
outer ones carry long comments about `resolve_control` stripping the measured
organism prefix off what the user typed, so each compares against the
stripped AND the unstripped spelling. THE BRANCH BETWEEN THEM DID NOT.

It is the branch a screen WITH a gene column takes. A gene column spelling a
gene `TGGT1_220950` against a spec whose value is `220950` matched NOTHING --
and `controls`, `positive_control` and `negative_control` all arrive through
`rows_for`, so a gene-level control on such a screen selected zero rows in
silence, leaving the thresholds to fall back and the baseline at zero while
the run finished normally.

Fixed, with a test that the two paths -- gene column present and absent --
reach the same rows, because which columns a screen happens to carry must not
change which cells are controls.
