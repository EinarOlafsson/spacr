Requested: 2026-09-10, verbatim -- "in generate masks, the intensity

           threshold. remove these settings: Max intensity pct, Min intensity

           also in the live view in mask generation i see a field in the top

Owner:     unassigned. `spacr/utils.py` and `spacr/object.py` hold the

--------------------------------------------------------------------------------
PART ONE: THE THRESHOLD IS RELATIVE AND THE USER WANTS IT ABSOLUTE
--------------------------------------------------------------------------------

WHAT IT DOES TODAY. `_merge_by_intensity` in `spacr/utils.py` decides whether
two touching objects are really one by comparing the mean intensity along
their shared boundary to a reference taken from the DIMMER of the two
objects. `intensity_threshold_method` picks which reference:

    'mean'        ref = min(mean of A's interior, mean of B's interior)
    'percentile'  ref = min(Nth percentile of A, Nth percentile of B),
                  where N is `intensity_percentile`, default 75

Both are relative to the objects in the field. Neither is a number the user
can read off an image and type in. That is the complaint: a threshold the
user cannot state in the units the image is in is a threshold the user cannot
set deliberately, only tune by trial.

THE SAME IS TRUE OF THE OTHER PAIR. `_filter_objects` takes
`min_intensity_percentile` / `max_intensity_percentile` (default 0 / 100) and
drops objects outside that quantile band of the field's own distribution. A
0/99 setting drops the brightest object in every field WHATEVER its intensity
-- with two objects in a field it drops one of them, unconditionally. The
comment already in `live_preview.py` records that this was a live defect once
(the preview defaulted to 1/99 where the pipeline used 0/100), which is the
same class of surprise: a quantile always removes something.

WHAT TO DO. Replace the relative scheme with ONE absolute intensity
threshold, in the image's own intensity units. Remove the method dropdown,
both percentile bands and the percentile value, per the list below.

  * THE UNITS ARE RAW IMAGE INTENSITY -- answered by the maintainer
    2026-09-10. The numbers in the TIFF, the ones a pixel inspector shows.
    Its known cost is accepted: a threshold in raw counts does NOT carry
    between acquisitions taken at different exposure or gain, and the
    setting must say so in its tooltip rather than let a user assume it
    travels. That cost is the price of the thing that was asked for -- a
    number that can be read off an image and typed in.
  * PER OBJECT TYPE, like everything else here: `cell_`, `nucleus_`,
    `pathogen_`, `organelle_` all carry their own copy. There are four of
    every setting named here, not one.
  * IT MUST BE ABLE TO REFUSE. An absolute threshold set above everything in
    the field merges nothing and one set below everything merges all of it,
    and both are silent today. Say which happened.

--------------------------------------------------------------------------------
PART TWO: THE FIVE SETTINGS TO REMOVE
--------------------------------------------------------------------------------

Each has four copies (cell/nucleus/pathogen/organelle) in
`spacr/settings.py`, an entry in the type map around line 4062, a row in
`COMPARTMENT_FIELDS` in `spacr/qt/widgets/live_preview.py`, and a label and
tooltip in all ten runtime catalogs.

    GUI label              key suffix                        where it is read
    ---------------------  --------------------------------  ----------------
    Max intensity pct      _max_intensity_percentile         _filter_objects
    Min intensity pct      _min_intensity_percentile         _filter_objects
    Intensity percentile   _intensity_percentile             _merge_by_intensity
    Intensity threshold    _intensity_threshold_method       _merge_by_intensity
    Area multiplier        _area_multiplier                  _split_by_watershed

`_split_by_watershed` computes `threshold = max(area_multiplier *
median_area, min_object_area)`. REMOVING `area_multiplier` REMOVES THE MEDIAN
TERM, so the split threshold becomes the absolute `min_split_area` alone.
That is a behaviour change, not only a settings change, and it is the right
one for the same reason as Part One -- a multiple of the median means the
threshold moves when the field changes -- but it must be stated in the
release notes rather than discovered.

DELETING A SETTING IS NOT DELETING ITS ROW. 364 established that a rename or
removal strands every generated table keyed by setting name: the notebooks
table, the settings_flow page, the settings_flow index and
setting_api_targets. Four settings went missing from the API that way. Run
the 364 checklist after this, and the docs audit must be green before it is
called done.

--------------------------------------------------------------------------------
PART THREE: THE TWO RENAMES
--------------------------------------------------------------------------------

    "Min object area"  ->  "Minimum area to split"
    "Min distance"     ->  "Minimum watershed distance"

Both are honest corrections rather than cosmetics. `min_split_area` is NOT a
minimum object area -- an object smaller than it is kept, it is simply never
split -- and a user reading "Min object area" would reasonably expect small
objects to be discarded. `min_distance` is the minimum separation between
watershed seeds and means nothing outside that algorithm.

THE KEYS ARE RENAMED TOO -- answered by the maintainer 2026-09-10, who chose
keys as well as labels over labels alone. So:

    cell_min_distance      ->  cell_min_watershed_distance      (x4 objects)
    cell_min_split_area    ->  cell_minimum_area_to_split       (x4 objects)

and that choice buys two obligations that the label-only option would not
have:

  * THE FULL 364 CHECKLIST. A rename strands the notebooks table, the
    settings_flow page, the settings_flow index and setting_api_targets.
    Four settings went missing from the API exactly this way. The docs audit
    must be green before this is called done.
  * A MIGRATION FOR SAVED SETTINGS. Every settings CSV already written in
    the field names the old key, and this is the maintainer's own working
    data. Read the old name, write the new one, and do NOT silently drop an
    unrecognised key -- a settings file that quietly loses a value the user
    set is worse than one that refuses to load.

PART FOUR: THE STRAY FIELD OVER THE PATH -- THE THIRD TIME
--------------------------------------------------------------------------------

Reported as "a black field which has a 3 in it" at the top left of the live
view, drawn over the loaded-path label.

THIS EXACT BUG HAS BEEN FIXED TWICE AND IS NOW BACK. Both previous fixes are
recorded in comments in `live_preview.py` and both were fixes to ONE widget:

  * the path label's own eliding, because a label whose sizeHint is the full
    path pushes the rest of the row off the panel;
  * `_fov_box` and `_channel_box`, which were "parented to `self` and never
    added to a layout, and a widget in that state occupies (0, 0) -- the top
    left, exactly where the loaded-path label sits". They were moved into a
    deliberately invisible `_offscreen_controls` container.

THE CLASS IS NOT FIXED, ONLY TWO INSTANCES OF IT. Measured 2026-09-10 on a
headless build of `LivePreviewPanel`:

    direct children of the panel: 113
    of those, in no layout at all:  96
    their classes: QComboBox, QDoubleSpinBox, QSpinBox, QWidget, Toggle

Ninety-six widgets are one stray `show()` away from being drawn at (0, 0).
Every one of them defaults to geometry (0, 0, 100, 30), which is the size and
position of what the maintainer is seeing. Several are spin boxes; the one
reading 3 has not been identified because the offending state does not
reproduce with no image loaded.

WHAT TO DO, and the first is worth more than the second:

  1. A TEST THAT KILLS THE CLASS. Every QWidget parented to the panel is
     either in a layout or inside the one container that is deliberately
     never shown. That invariant is checkable headlessly in a few lines, it
     fails today on 96 widgets, and it is the only thing that stops a fourth
     report. Expect to move widgets into `_offscreen_controls` (or delete
     them) until it passes -- that IS the fix, and the test is how you know
     you got all of them rather than the one that was visible.
  2. Identify the one showing 3 by reproducing the maintainer's state: an
     image loaded in Generate Masks, which is what the headless build lacks.
     If step 1 is done first this may already be gone, and step 1 should be
     done first for that reason.

DO NOT "FIX" IT BY HIDING IT. `setVisible(False)` is what the second fix
already relied on, and the comment says why that was not enough: it is "one
stray show() away from a combo box drawn over the path, which is how this was
reported twice". Out of the panel, not merely hidden.

PART FIVE: THE NORMALISATION PERCENTILES ARE CAPPED AT TWO DECIMALS
--------------------------------------------------------------------------------

Requested 2026-09-10 -- "the normalization percentiles should be able to have
as many desimals as the user wants, now they are capped at 2 desimals."

WHERE IT IS. `spacr/qt/widgets/live_preview.py`, around line 1575:

    self._lo_pct = QDoubleSpinBox(self)
    self._lo_pct.setRange(0, 50); self._lo_pct.setValue(2.0)
    self._hi_pct = QDoubleSpinBox(self)
    self._hi_pct.setRange(50, 100); self._hi_pct.setValue(98.0)

Neither calls `setDecimals`, and `QDoubleSpinBox` defaults to 2. So the cap is
not a deliberate choice anywhere; it is Qt's default, never overridden.

THE CAP DOES NOT MERELY ROUND THE DISPLAY, IT ROUNDS THE VALUE. A
`QDoubleSpinBox` at two decimals stores what it shows, so a user who types
99.995 gets 100.0 -- the upper end of the range -- and the stretch they asked
for is not the stretch they get. It fails silently, which is the part that
makes it worth fixing rather than documenting.

WHY IT MATTERS AT THE TOP END SPECIFICALLY. The whole purpose of an upper
percentile is to clip a handful of saturated or hot pixels without touching
real signal. On a 4-megapixel field, 99.9 spares 4,000 pixels, 99.99 spares
400 and 99.999 spares 40 -- three very different images, and two decimals
cannot express the difference between the last two at all. A user chasing a
few hot pixels has no setting between "99.99" and "off".

WHAT TO DO. Give both boxes enough decimals to reach the pixel count (6 is
ample: 99.999999 on a 4 MP field is under one pixel) and a step that does not
make the arrow buttons useless at that precision -- a fixed `setSingleStep` of
0.000001 would need a million clicks to cross a percent. Qt does not adapt the
step to the cursor position on its own; if that behaviour is wanted it has to
be written.

CHECK THE SAME CAP ELSEWHERE BEFORE CALLING IT DONE. Twenty-odd
`setDecimals` calls exist across `spacr/qt/**` at 1, 2, 3 and 4, and each was
presumably chosen for its own field -- but the ones that were never set at all
are the ones carrying Qt's default by accident, exactly as these two were. The
percentile boxes are what was reported; they are unlikely to be the only pair.

PART SIX: "REMOVE BACKGROUND" IS NOT REFLECTED IN THE LIVE IMAGE
--------------------------------------------------------------------------------

Requested 2026-09-10 -- "the remove backfground if true should be reflected in
the live images so the user can see whet the cutoff lokks like live."

THE FEATURE IS ALREADY BUILT AND IT IS GATED ON THE WRONG SETTING. This is
not missing work; it is a one-key mismatch, and the mismatch is why it looks
missing.

`_apply_display_background` exists, does exactly what was asked, and its own
docstring states the intent: "Show the intensity image the segmentation
actually ran on ... the one pane that could show you *why* the objects changed
was the pane still displaying the original pixels."

But the two paths read DIFFERENT KEYS:

    the worker  (live_preview.py ~932)   remove_background_{obj}   per object
    the display (live_preview.py ~2516)  remove_background         one global

So the display is switched on and off by a setting the worker never consults,
and vice versa.

THE DEFAULTS MAKE THIS THE OUT-OF-THE-BOX STATE, which is almost certainly
what was seen. In `spacr/settings.py`:

    remove_background            False     <- what the DISPLAY gates on
    remove_background_cell       False
    remove_background_nucleus    False
    remove_background_pathogen   True      <- what the WORKER gates on

With a pathogen channel selected and nothing touched, the worker removes the
pathogen background and the display never shows it. The masks move; the image
they are drawn over does not. That is the reported symptom exactly.

WHAT TO DO. `_background_for_channel` already resolves a channel to its object
type -- it loops `self._selected_object_types()` and matches the channel -- so
it is one line from correct: gate on `remove_background_{obj}` for the object
it just matched, not on the global key, and take that object's
`{obj}_background` the way the worker does.

  * THE GLOBAL KEY IS NOT NECESSARILY DEAD. `remove_background` is read
    elsewhere in the pipeline (settings.py has it in three separate default
    blocks). Find out whether the panel's common widget is meant to drive the
    per-object keys or is a leftover, and say which in the fix. Silently
    ignoring a control the user can still see and click would be a second
    version of this same bug.
  * THE TEST IS THE POINT. Assert that for a given channel and settings, the
    display path and the worker path make the SAME decision and use the SAME
    threshold. Two code paths that must agree, and did not, is the whole
    defect -- a test on either one alone would have passed throughout.

--------------------------------------------------------------------------------
MAINTAINER ANSWERS, 2026-09-10 -- BOTH SETTLED, NOTHING LEFT TO ASK
--------------------------------------------------------------------------------

Q. What are the units of the absolute intensity threshold?
A. RAW IMAGE INTENSITY. The numbers in the TIFF. Chosen over a normalised
   0-1 scale knowing it does not carry between exposures, because a
   normalised threshold is a relative measure wearing a different name and
   would re-introduce the objection that prompted the item.

Q. Rename the labels only, or the keys as well?
A. LABELS AND KEYS. The more expensive option, taken deliberately: it costs
   the 364 table rebuild and a saved-settings migration, and it leaves the
   keys saying what the settings actually do.

HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * The five settings are gone from `settings.py`, its type map,
    `COMPARTMENT_FIELDS`, and all ten runtime catalogs, and the API docs
    audit is green -- which is the 364 check, and the one that was missed
    last time.
  * A saved settings CSV written before this change still loads, with the
    removed keys ignored rather than raising.
  * The two renamed labels read correctly in all ten locales, with reviewed
    evidence for any the machine gets wrong. "Watershed" is a term of art and
    machine translation mangles those -- 388 has just been through this.
  * An absolute threshold set above every pixel in the field merges nothing
    AND SAYS SO.
  * The layout invariant test passes: no widget parented to
    `LivePreviewPanel` outside a layout except in the one container that is
    never shown. It fails on 96 widgets today, so a passing run is evidence.
  * Typing 99.995 into the upper normalisation percentile leaves 99.995 in
    it, and the rendered image differs from the one 99.99 produces.
  * With stock defaults and a pathogen channel selected, switching background
    removal on visibly changes the displayed image and not only the masks --
    and a test asserts the display path and the worker path reach the same
    decision from the same settings.
