WHAT IS THERE NOW, AND WHAT THE README HAS THAT IT DOES NOT
--------------------------------------------------------------------------------

THEY ALREADY SHARE THE GRID, which is worth knowing before anything is
rebuilt: `docs/source/_autoapi_templates/index.rst` does

    .. include:: ../_generated/workflow_grid.rst

and that is the same 21-tile block the README draws, written by
`packaging/generate_readme_visuals.py`. So the tiles, their order, their
artwork and their destinations are already one thing in two places. DO NOT
FORK IT.

What the API homepage is missing is everything AROUND the grid.

    the README                         the API homepage
    -------------------------------------------------------------------
    "Core workflow" names the SIX      nothing says which six are the
    primary modules with a sentence    pipeline; all 21 tiles are equal
    each

    "Make Masks" gets a section, and   no per-module prose at all
    366 part 2 moves the rest of the
    per-module explanation INTO the
    API, which has not happened yet

    the grid is grouped and read as    the grid is a flat 6-per-row block
    a pipeline in prose above it       with no section headings (0 of them)

AND THE PART THAT IS ACTIVELY MISLEADING: the "Complete module reference"
section lists every top-level object autoapi found, alphabetically. That is
**215 top-level Python modules** out of 537 files in the package. It is a
list of FILES, and it has no relationship to the structure a user knows.
Somebody who used Mask and wants its API has to already know that Mask is
`spacr.core`; somebody who used Recruitment has to know it is a function
inside `spacr.submodules`.

THE NESTING IS ABSENT TOO. Ten modules are folded into a host screen and 23
are tileless in total -- Timelapse under Mask, Illumination under Measure,
Cellpose Workbench and Model Compare and Curate under Make Masks, Classifier
Evaluation and Explain CV under Classify, and so on. The Home screen shows
that nesting, instruction 369 is about the dock showing it, and the API
homepage shows none of it.

--------------------------------------------------------------------------------
WHAT "REFLECT THE MODULE STRUCTURE" HAS TO MEAN HERE
--------------------------------------------------------------------------------

A reader arriving at the API homepage should be able to find a module BY THE
NAME THEY USED IT UNDER, and see how it relates to the others, without
already knowing which Python file implements it.

THREE THINGS, in the order they are worth doing:

1. GROUP THE GRID BY SECTION. The Home registry already has the sections --
   Core, Data, Results & QC, Explore, Assays, Design -- and
   `generate_readme_visuals._grouped_apps()` already reads and VALIDATES them
   against the Home layout, raising when the two disagree. So the grouping is
   available and enforced; it is simply not emitted into the grid.

   Emit it as a second generated block rather than changing `workflow_grid`,
   OR add section headings to the existing one and let the README take them
   too. Decide which, and say why here. The README's own grid is flat today
   and the request says the API should be like the README, so a change that
   improves both is preferable to one that makes them differ again.

2. SHOW THE NESTING. A folded module needs to appear UNDER its host, not
   missing and not floating beside it. `FOLDED_APPS` on each host screen and
   `TILELESS_APPS` in `spacr/qt/app.py` are the two lists that answer this,
   and `spacr/qt/screens/map_barcodes.fold_description` gives the name and
   sentence for a key whose registry row is gone.

3. MAKE THE COMPLETE REFERENCE SECONDARY, NOT ABSENT. 215 alphabetical
   module links are useful to a contributor and useless to a user, and the
   template already says as much: "Application code should prefer the
   curated workflow entry points above." Put it behind a collapsed section
   or a separate page, and keep every link -- this is a demotion, not a
   deletion.

2026-09-03: ALL THREE PARTS DONE. WHAT WAS CHOSEN, AND WHY.
--------------------------------------------------------------------------------

THE HOMEPAGE NOW READS, top to bottom:

    API reference
      Applications and workflow
        spaCR modules
          Core     -- the six pipeline tiles, under Home's own Core note
          Data     -- six tiles
          Tools    -- five tiles
          Assays   -- four tiles
      Modules reached from another screen
        Opened from a host's masthead   -- 35 folds under their 12 hosts
        Opened from the Help menu       -- 10 modules
      Stability

CORRECTION TO THIS FILE'S OWN NUMBERS. It says the Home registry has SIX
sections -- Core, Data, Results & QC, Explore, Assays, Design. It has FOUR,
and has since the 2026-08-31 restructure: `SECTION_ORDER` is
`(Core, Data, Tools, Assays)`, which is what
`test_the_readme_describes_the_build_that_ships` already pins by name. The
other five constants still exist in `spacr/qt/app.py` because screens, saved
state and tests name them, and a section with no apps simply does not draw.
`docs/source/index.rst` still recites the stale six in prose; that is not
this item's file to edit and is left for whoever owns that paragraph.

The acceptance criterion is met in the form that matters -- the homepage
groups by the sections HOME has, whatever they are, and a test fails when the
two disagree -- rather than by hard-coding a count that was already wrong the
day this was filed.

PART 1, THE GROUPING: HEADINGS IN THE EXISTING SHARED BLOCK, NOT A SECOND
BLOCK. Both options in this file were tried on paper and the shared one wins
for a reason bigger than tidiness: a second block is a second thing to
regenerate, and the failure that produced this item was the README and the
API homepage drifting. There is now ONE builder, `_grid_markup`, called twice
with the only two things the two surfaces are allowed to differ in -- the
substitution namespace (`Module` / `DocModule`, because the tests tell the
files apart by it) and the asset root (repository-relative icons for GitHub,
`/_static` for Sphinx). Everything else -- section order, band membership,
row width, alt text shape, every destination -- comes out of one function, so
a heading cannot land on one page and not the other.

The band titles removed on 2026-09-02 are NOT being put back. What was
removed was a hand-typed copy: a `SECTION_ORDER` tuple and an `APP_ORDER`
table written into the generator, which kept advertising seven sections and
thirty-eight tiles for a fortnight after Home became four and twenty-one.
`_grouped_apps` closed that hole before this item was filed -- it reads
`SECTION_ORDER` and `SECTION_TILE_ORDER` out of `spacr.qt.app` and RAISES
when the registry and the documented order disagree -- so the grouping was
already the registry's own answer and was simply not emitted. The old
`**Data**` form stays forbidden by
`tests/test_readme_presentation.py`; the derived heading is now required by
the same test.

Each band also carries Home's own tab description, from `SECTION_NOTES`.
That is what answers this file's first complaint -- "nothing says which six
are the pipeline". A four-word heading over six tiles does not say it; "Core
sequence from microscopy images through segmentation, measurements,
annotations, classification, barcode mapping and regression" does, and it is
the sentence the running GUI shows on that tab, so it cannot say something
the product does not.

THE UNDERLINE IS `^` ON BOTH SURFACES, and that is load-bearing rather than
cosmetic. RST binds a heading LEVEL to an underline CHARACTER by order of
first appearance in the document, and this one block is included into three
files whose ladders were decided elsewhere. README.rst introduces `=`, then
`~`, then `-` -- so `~` there is a level ABOVE `-`, and a band heading
written with it would break out of the "spaCR modules" section it belongs
to. `^` appears in none of the three, so wherever the block lands it is
introduced directly beneath the heading above it and becomes that heading's
child. Verified with docutils: README.rst parses with zero messages and the
outline nests Core/Data/Tools/Assays under "spaCR modules".

PART 2, THE NESTING: THE FOLD REFERENCE ALREADY EXISTED AND WAS INCLUDED BY
NOTHING. `docs/source/_generated/folded_modules.rst` was being generated,
and `tests/test_every_module_is_reachable_and_documented.py` was checking it
under the name "the API page's fold reference", and no page in the
documentation included it. That is the whole of why the nesting was absent:
not a missing table, an unwired one. `_autoapi_templates/index.rst` now
includes it directly under the grid.

THE FOURTH COPY OF THE FOLD TABLES IS GONE, and removing it found six
missing modules. `_fold_hosts` in the generator did its own walk over
`map_barcodes.FOLD_HOST_MODULES` -- a DIFFERENT table that happens to share
its name with the one in `fold_strip`, mapping host keys to screen module
names -- reading only `FOLDED_APPS`. Make Masks spells its list `FOLD_ORDER`,
so Cellpose Workbench, Mask the whole folder, Model Compare, Model Zoo,
Curate and Napari Bridge were folded in the product and absent from the
documentation of what is folded. This file names three of those six as
examples of the nesting that is missing, so it was right twice over.

The page now asks the two resolvers the application itself uses, and the
union is needed because NEITHER IS COMPLETE:

  * `spacr.qt.app.folded_children` -- what the dock and the menu bar draw --
    covers eleven hosts including Make Masks and handles both spellings, but
    keys its answer by the host module's `APP_KEY`/`HOST_KEY`, and
    `spacr/qt/screens/annotate.py` declares neither. Annotator Agreement
    falls out of it, and out of the dock with it.
  * `spacr.qt.widgets.fold_strip.folded_modules` keys by host MODULE so it
    keeps Annotator Agreement, but its own docstring records that it walks
    eight hosts while the dock draws eleven: the seven folds on Graph
    Builder, QC Dashboard and Database Browser are missing from it.

A module name is turned into a host key only when it IS a registered key, so
the union cannot invent a host. 28 folds became 35, under 12 hosts.

WORTH A SEPARATE ITEM, NOT DONE HERE: giving `annotate.py` an `APP_KEY`
would make the second half of that union unnecessary AND put Annotator
Agreement back in the dock, which is 369's surface. It is `spacr/` source and
outside this item's remit.

One more thing was fixed while wiring it. Fourteen folds came out as BARE
TEXT, because the URL table was keyed on the registry and a module folded
hard enough loses its registry row. Asking `api_docs_url` directly -- the
resolver the application's own Help button calls -- finds the page for all
but five. Hit List, Methods & Results, Diagnostics, Import Images and Napari
Bridge resolve to the API index itself, so they are left unlinked rather than
pointed back at the page the reader is on; the set is pinned by test, so
giving one of them a page has to be noticed.

PART 3, THE DEMOTION: A `dropdown` ON THE SAME PAGE, NOT A NEW ONE. AutoAPI
renders exactly one `index.rst` from its template directory, so "its own
page" would have meant a hand-written page duplicating the loop over
`pages|selectattr("is_top_level_object")` -- a second copy of the one thing
that must stay complete. The collapsed section keeps one loop.
`sphinx_design` is already an extension and
`_autoapi_templates/python/module.rst` already uses `.. dropdown::` for the
same purpose, so this is the pattern the tree had.

NOTHING WAS DELETED. The hidden toctree stays beside the dropdown and walks
the same expression, which is what keeps the 215 pages in the document tree;
dropping it would turn 215 resolving links into 215 Sphinx warnings, and the
docs workflow builds with `-W`. The section's prose now also names the
problem this file described: Mask is `spacr.core` and Recruitment is a
function inside `spacr.submodules`, and neither is findable in an alphabetical
list of files by the name the user knows -- so start from a tile.

NO TILE DESTINATION CHANGED. Verified by extracting every `image::` path and
every `:target:` from README.rst and `workflow_grid.rst` before and after and
diffing: identical, in the same order, in both files. 366 part 3's six
anchors (mask, umap, analyze_plaques, recruitment, invasion, replication) are
additionally pinned as LITERALS in the new test file -- every other check in
the repository asks whether the grid agrees with `api_docs_url`, which is the
right question for drift and the wrong one here, because a change to the
resolver would move the tile and the expectation together.

WHAT NOW FAILS IF SOMETHING SLIPS:
  tests/test_the_api_homepage_shows_the_module_structure.py
    * the emitted bands, parsed from the committed page, must equal Home's

    * the README grid and the docs grid must agree on bands, order and every

    * every fold must be listed under its host, and linked where it has a

    * the complete reference must still be inside the dropdown with its

    * the landing page's category names must match `SECTION_ORDER`.
  tests/test_readme_presentation.py
    * hand-typed band titles stay forbidden, derived ones are required;
    * six tiles a row, with a short row allowed only at the end of a BAND
      (it used to be allowed only at the end of the grid, which a band of
      five cannot satisfy).

ONE THING FIXED THAT WAS NOT ASKED FOR, because grouping the grid created
it: `docs/source/index.rst` includes the same grid and introduced it with
"six categories: Core, Data, Results & QC, Explore, Assays, Design". Home has
had four since 2026-08-31. That paragraph was survivable while the grid below
it was flat -- a reader had nothing to compare it against -- and became a
contradiction on one screen the moment the bands appeared. It now names the
four, and a test compares the names it prints against the live `SECTION_ORDER`
and fails if a retired one comes back.

NOT DONE, DELIBERATELY: `tools/readme_i18n.py` carries a
`WORKFLOW_SECTION_LABELS` table for the old `**Data**` band titles, still
listing the retired six, so the new headings reach the nine localized READMEs
in English. Both are translation-owned files with a job live in them and were
left alone; the generator was run and `docs/i18n/readme/` restored with
`git checkout` afterwards, so the localized READMEs are untouched by this
change and will pick the headings up the next time that job runs.
