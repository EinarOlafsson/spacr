================================================================================
A TOOLTIP AND DOCUMENTATION SWEEP: SHORT, INFORMATIVE, CORRECTLY REFERENCED
================================================================================

Status:    the links are VERIFIED CLEAN against a real build
           (2026-08-08). Only the tooltip TEXT sweep is open.
Requested: 2026-08-08 — "do a full documentation and tooltips sweep to make the tool tips short and informative (not to short) with the correct api reference."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Tooltips come from one place -- the descriptions table in
`spacr/settings.py` (`descriptions` / `get_tooltips`), rendered by
`format_tooltip` and attached by `attach_api_tooltip` in
`spacr/qt/screens/settings_model.py`. So a sweep edits data, not widgets.

The quality is uneven by construction, because the entries were written at
different times to different standards. Both failure directions are present
today, and both are visible in `settings.py`:

  TOO LONG   `annotated_classes` runs to a full paragraph explaining its own
             deprecation history -- accurate, and nobody reads it hovering.
  TOO SHORT  entries that restate the setting name and add nothing:
             a tooltip that says "the source folder" for `src` costs a
             hover and returns nothing.

The API reference part is checkable rather than a matter of taste: the
tooltip's link is built from the app key and setting key, and a link that
points at a page or anchor that does not exist is a dead end the user
finds at the moment they needed help.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The settings panels are the product's real interface -- a module screen is
a hundred numbered choices, and the tooltip is the only explanation of what
each one does. A wrong or empty one does not merely fail to help: it makes
the user guess, and a guessed segmentation parameter produces a plausible
wrong answer rather than an error.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Decide the shape ONCE and apply it everywhere, so the panel reads as one
   voice. Proposed, and worth keeping unless there is a reason not to:
       "(type) - what it does, in one sentence. When to change it.
        Default X."
   That is roughly the shape the good entries already have.
2. One or two sentences. "Not too short" is the request's own qualifier:
   the test is whether someone who does not already know the setting could
   choose a value from the tooltip alone.
3. Say the DEFAULT, and say the UNIT. A number without a unit is the most
   common way these fail -- pixels or microns, seconds or frames.
4. Verify every API link resolves. Write this as a TEST rather than a
   read-through: generate every tooltip, extract every href, and assert the
   target exists in the built docs. A sweep done by eye will be stale
   within a month; a test will not.
5. Where a setting is genuinely obscure, say what it interacts with. Half
   the confusing settings here are confusing because they only matter when
   another one is set.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Every setting in every module has a tooltip of one or two sentences that
names the type, the default and the unit; every API link in every tooltip
resolves to a real page, asserted by a test rather than checked by hand.

--------------------------------------------------------------------------------
2026-08-08 - THE LINK TEST IS WRITTEN, AND IT CANNOT RUN BY DEFAULT
--------------------------------------------------------------------------------

`tests/test_tooltip_api_links_resolve.py`. It walks every setting of every
module, extracts every href from `format_tooltip`, and checks them. Two
kinds of check, deliberately separated:

  ALWAYS   the link is on the documentation domain, and every setting gets
           SOME link -- including a key with no entry in the descriptions
           table, which is the case that would otherwise leave a settings
           row with no route to the docs at all.

  OPT-IN   the link resolves to a page that EXISTS. Gated behind
           SPACR_DOCS_BUILT=1.

WHY THE SECOND ONE IS GATED, because it looked like a major finding for
about a minute and was not. Running it against the working tree reported
dozens of dead links -- `core`, `sequencing`, `submodules`, `timelapse`
and more. Then:

    git ls-files docs/api/spacr | wc -l   ->   0

`docs/api/` is GENERATED and untracked. What is on disk is whoever last
built it locally; mine had 4 module pages for 124 modules. So the failure
said nothing about the published site, and a test that fails on every
checkout is a test that gets deleted rather than read.

Build the docs first, then run with SPACR_DOCS_BUILT=1. That is also the
right moment to do instruction 63's read-through, since it needs a build
for the same reason.

WHAT IS STILL OPEN HERE: the text sweep itself -- the shape, the length,
the units and defaults. The test covers the links; it says nothing about
whether a tooltip is any good.

--------------------------------------------------------------------------------
2026-08-08 - RUN AGAINST A REAL BUILD. THE LINKS ARE CLEAN.
--------------------------------------------------------------------------------

Built the docs (`sphinx-build -E -b html --keep-going docs/source <out>`,
~8 minutes, 125 module pages) and ran the check against the output rather
than against the stale tree:

    links checked : 1151
    dead targets  : 0

So the API links are FINE, and the "dozens of dead links" from an hour
earlier were entirely an artefact of a local `docs/api/` holding 4 pages
for 124 modules. Recorded because the wrong version of this note would
have sent someone hunting a bug that does not exist.

This also answers part of instruction 63 for free: the generated tree has
a page per module -- 125 of them -- so the API site is not missing content.
Whatever 63 finds will be about presentation and docstring quality, not
absence.
