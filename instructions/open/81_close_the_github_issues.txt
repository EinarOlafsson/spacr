2026-08-12 - #72 (ANNOTATE SEGFAULT ON RESIZE): NOT REPRODUCED, NOT CLOSED
--------------------------------------------------------------------------------

Investigated, not fixed, and deliberately NOT marked solved. What is known:

RULED OUT BY INSPECTION, each recorded so it is not re-audited:

  1. A widget painting from a freed numpy buffer. Every `QImage(...)` built
     from an array in `spacr/qt/**` calls `.copy()` before the array can be
     collected -- checked all nine sites (space.py:1002, iconset.py:450,
     live_preview.py:517, model_compare.py:872, model_zoo.py:948,
     measure_preview.py:988, animation_zoom.py:484, make_masks.py:221,
     umap_explorer.py:813). This is the classic cause and it is absent.

  2. A stale slot index walking off `_thumbs` after a rebuild.
     `_set_slot_image` and `_repaint_slot` both bounds-check against the
     CURRENT list, and `_rebuild_grid` resizes `_thumb_pixmaps` and
     `_raw_thumb_images` with it.

  3. A worker handler running on the worker thread -- the failure mode this
     project has hit before. `JobRunner.submit` relays `worker.finished`
     through a Signal whose receiver is a bound method of a GUI-thread
     object, and the module says so at the connection.

  4. Re-entrant resize (stack exhaustion presents as SIGSEGV).
     `_compute_grid_dims` only READS viewport geometry and writes to the
     settings dataclass; it mutates no widget, so `resizeEvent` cannot
     recurse through it. `_rebuild_grid` is reached from the 150 ms debounce
     timer, not from inside the resize event.

NOT REPRODUCED. `tests/qt/test_annotate_resize_crash.py` drives the real
AnnotateScreen against a real source and hammers it: a 21-step resize drag, a
rebuild started while a page load is in flight, a close landing on a pending
reload. Six tests, all pass, no crash. Run under QT_QPA_PLATFORM=offscreen,
which is the limit of what this machine can do -- there is no X server and no
xvfb here, so the real windowing and compositing path is NOT exercised, and
that is where a windowed segfault would live.

The tests are kept regardless: they pin the ordering invariants whose
violation would produce exactly this class of crash -- the debounce
collapsing a drag into at most two reloads, the three slot arrays staying the
same length as the grid, and `_hover_slot` being dropped when its widget is.

TO CLOSE THIS, one of: a stack trace from the reporter's crash, or a run on a
machine with a real display. Guessing a fix for a native crash that four
inspections and one measurement say is not in the Python paths would be a
change with no evidence behind it.

2026-08-12 (later) - #15 HAS A FIX, AND THE FIRST EXPLANATION OF IT WAS WRONG
--------------------------------------------------------------------------------

Candidate 2 from the diagnostic comment ("the measurement writer does not go
through database_concurrency.connect") IS ALREADY DONE:
`_append_to_measurements_db` calls `connect(db_path, timeout=DB_WRITE_TIMEOUT)`
at utils.py:2943. Nothing to do there.

Candidate 1 -- WAL where the filesystem allows it -- is now implemented, and
working out WHY it helps corrected the diagnostic comment's own reasoning.

THE COMMENT SAID, and I repeated it: "under WAL a reader does not block a
writer, which is most of this problem", with the failing has_table probe as a
READ that was being blocked by writers. The test written to prove that
measured 0.000 s and refuted it. In rollback-journal mode a writer holding
RESERVED does NOT block readers; only its brief EXCLUSIVE commit does.

THE DIRECTION IS THE OTHER WAY, and it is worse for this workload. A reader
holds SHARED for the length of its statement, and a writer cannot COMMIT
until every SHARED lock is gone. Measure runs one worker per field, and
to_sql issues has_table (a read) before every append -- so each worker
alternates read, write, read, write, someone is always reading, and the
committing worker waits out its busy timeout. Measured, a commit attempted
while one reader holds an open SELECT:

    journal_mode=delete    writer waited 1.037 s
    journal_mode=wal       writer waited 0.002 s

That is writer starvation by a stream of readers, and "database is locked"
surfaces on whichever has_table loses the race -- which is exactly the
statement in the reporter's traceback.

WHAT SHIPPED: `database_concurrency.enable_wal_where_safe`, called once per
source folder from `measure_crop` before any worker starts. The safety bar is
a POSITIVELY IDENTIFIED local filesystem -- `WAL_SAFE_FILESYSTEMS` is an
allowlist, not the complement of `NETWORK_FILESYSTEMS`, because "not a type I
recognise as networked" is a weaker claim than "local" and the gap between
them is a corrupted database on a cluster. Network types, unrecognised types,
and platforms where `filesystem_type` cannot tell (it reads /proc/mounts, so
macOS and Windows always answer None) all keep the shipped DELETE behaviour.
Never raises.

NOT CLOSED, AND NOT YET COMMENTED ON, for two reasons:

  1. It is unpushed, so it is not real for the reporter yet.
  2. It fixes the reader-blocks-writer half. It does NOT make two writers
     concurrent -- SQLite still serialises those -- and the reporter's path
     (`/home/jkellerm/.conda/...`) may well be a network filesystem, in which
     case this changes NOTHING for them and the `df -T` the diagnostic asked
     for is still the next thing needed.

So the honest state is: a measured improvement for local-disk runs, which is
most runs, and an open question for theirs. Say that in the comment rather
than "fixed", and ask for `df -T` again.
