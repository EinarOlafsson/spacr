  * NOT the old cluster-montage grid at the end.
  * NOT the default spaCR figure-generation slider. This module gets its own

    backgrounds; clicking one loads it into the container.

--------------------------------------------------------------------------------
WHAT TO TAKE FROM starplast, AND WHAT NOT TO
--------------------------------------------------------------------------------

`/mnt/firecuda2/Claude/repo/starplast` is the reference, and the parts worth
copying are named rather than "make it like starplast":

    starplast/gpu.py          `available()`, `enabled()`, `describe()`,
                              `worth_it()`, `umap_class()`. It already ranks
                              three backends, carries the MEASURED size
                              threshold below which the copy to the device
                              costs more than it saves, and states that a
                              cuML map is a DIFFERENT MAP of the same data
                              rather than the same map faster.
    starplast/embedding.py    `EmbeddingSpec` -- the whole recipe as one
                              frozen record that round-trips, so a table row
                              IS a spec and clicking it can rebuild exactly
                              that map.
    starplast/tuning.py       the walk.
    starplast/clustering.py   HDBSCAN on the embedding.

spaCR already has `spacr/gpu_reduce.py`, written for instruction 86 and never
used. It should become the spaCR half of starplast's gpu.py rather than a
second answer.

--------------------------------------------------------------------------------
THE GPU BUTTON, AND THE PART THAT NEEDS CARE
--------------------------------------------------------------------------------

Pressing GPU when cuML is absent should CHECK THE INTERPRETER FIRST and then
either install or explain:

    3.11 / 3.12   install `spacr[rapids]` and say what it will pull -- it is
                  gigabytes of CUDA libraries, not a small wheel, and a
                  progress-free multi-gigabyte download reads as a hang.
    anything else say exactly what is needed: cuML declares 3.11-3.12 ONLY,
                  so on 3.10 or 3.13 the answer is "make a 3.11 environment",
                  not a resolver error the user cannot read.

INSTALLING INTO THE RUNNING INTERPRETER FROM A GUI BUTTON IS THE RISK. pip can
upgrade numpy/scipy under a process that has already imported them, and the
session then behaves unpredictably until it is restarted. So: install, then
tell the user to restart spaCR, and do not pretend the new backend is live in
the current process.

AND SAY IT IS A DIFFERENT MAP. cuML's UMAP is not umap-learn's. A row computed
on the GPU and a row computed on the CPU are not comparable, so the table must
record WHICH backend produced each row -- otherwise a walk whose rows came
from both is comparing the two libraries rather than the settings.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A search fills a table; clicking a row draws that row's 2D or 3D UMAP in the
container beside it; that map can be clustered; one button shows every map in
the table on black and clicking one loads it; the clustering walk runs during
the UMAP search or after a map is chosen; the GPU button either turns cuML on,
installs it and says to restart, or says precisely what interpreter is needed;
and every table row records which backend drew it.
