--------------------------------------------------------------------------------
WHAT IS ASKED FOR, IN TWO PARTS OF DIFFERENT SIZE
--------------------------------------------------------------------------------

THE REQUIREMENT: the download buttons move to the TOP of Input Tables, above
`paired_data`. "in any cas the input tables sould start with download buttons
not end wit them" -- that sentence is the acceptance criterion and it is
satisfied by reordering alone.

THE PREFERENCE: each download button sits above the column it fills, in a
second table whose column widths are locked to the paired-data table below,
with each button centred in its cell. "if you can allign each button to their
respective columns below in the table that would be perfect."

DO THE REQUIREMENT FIRST AND SHIP IT. The preference is worth doing and is
strictly harder; a reorder that lands tonight is better than an alignment that
lands next week, and the two are independent.

--------------------------------------------------------------------------------
WHY THE ALIGNMENT IS THE HARD HALF
--------------------------------------------------------------------------------

Two widgets whose columns must agree are two layouts that must be kept in
step, and this repository already knows what that costs -- "One source of
truth. Two editors of the same setting drift; the `_ClusterSettingsDialog`
docstring records what it cost last time."

So do NOT build a second table with its own column model and try to keep the
widths equal by setting both. Either

  * put the buttons in the SAME table as a header row or a first row, so
    there is one column model and alignment is free; or
  * have the button strip READ the paired-data table's column geometry
    (`sectionSize`/`sectionPosition`) and follow it, one direction only,
    re-reading on `sectionResized`.

The first is simpler and cannot drift. Prefer it unless the table's model
makes a widget row impossible.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* The Input Tables category is defined in
  `spacr/qt/screens/settings_model.py` under `_APP_CATEGORY_SPECS["regression"]`
  and currently reads `("Input Tables", ("paired_data", "metadata_files",
  "count_grna_column", "count_value_column", "independent_variable_layout",
  "wide_predictor_columns", "src"))`. A reorder is an edit THERE, not in the
  screen, and it moves the whole row rather than only the buttons -- check
  which of those keys the download buttons actually belong to before moving
  anything.
* A column that is hidden or reordered by the user must not orphan a button
  above it. If the table allows either, the strip has to follow.
* 347 is changing what a settings row renders (the API dot and the animation
  square). Both items touch the same rows; whoever does the second should read
  the first's commit rather than re-deriving the layout.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* Input Tables renders the download buttons above `paired_data`, asserted on
  widget order, not by eye.
* If the alignment is done: each button's horizontal centre is within a pixel
  or two of its column's centre, asserted after a resize as well as before.

--------------------------------------------------------------------------------
2026-09-02 — THE REQUIREMENT IS DONE. THE PREFERENCE IS NOT.
--------------------------------------------------------------------------------

`Section.add_prose_row` learned `at_top`, using the same `insertRow(0, ...)`
that `add_prose` already had, and `_install_example_data_button` passes it.

Input Tables now reads, top to bottom:

    row 0   Load test data…        (the whole-screen button, unchanged)
    row 1   Download   [Score] [Count] [Measurements (.db)] [Image crops]
    row 2   Paired data
    row 3   Metadata files
    row 4   Count gRNA column
    row 5   Count value column
    ...

Read out of the built screen rather than off the source: the row order above
is what `QFormLayout` actually holds after `AppScreen(app_key="regression")`.

WHY THE WHOLE-SCREEN BUTTON STAYS ABOVE THE DOWNLOAD ROW. Both insert at 0 and
the button inserts last, so it wins the top slot. That is the right order
anyway -- it fills BOTH slots at once, so it is the broader action, and the
row below it is the narrower per-table one. Broadest first.

VERIFIED against a HEAD baseline on the same selection: 10 failed before, 10
after, no regressions. (Those 10 are the 345/346 order-dependent family.)

THE PREFERENCE -- each button aligned over the column it fills -- IS NOT DONE
and is deliberately left. Nothing above changes when it is: the row is in the
right place now, and the alignment is a change to what that row CONTAINS.
Read the WATCH section before starting it; the "one column model" point is the
whole of it.
