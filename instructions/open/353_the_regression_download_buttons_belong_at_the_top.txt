--------------------------------------------------------------------------------
WHAT IS ASKED FOR, IN TWO PARTS OF DIFFERENT SIZE
--------------------------------------------------------------------------------

THE REQUIREMENT: the download buttons move to the TOP of Input Tables, above
`paired_data`. "in any cas the input tables sould start with download buttons
not end wit them" -- that sentence is the acceptance criterion and it is
satisfied by reordering alone.

THE PREFERENCE: each download button sits above the column it fills, in a
second table whose column widths are locked to the paired-data table below,
with each button centred in its cell. "if you can allign each button to their
respective columns below in the table that would be perfect."

DO THE REQUIREMENT FIRST AND SHIP IT. The preference is worth doing and is
strictly harder; a reorder that lands tonight is better than an alignment that
lands next week, and the two are independent.

--------------------------------------------------------------------------------
WHY THE ALIGNMENT IS THE HARD HALF
--------------------------------------------------------------------------------

Two widgets whose columns must agree are two layouts that must be kept in
step, and this repository already knows what that costs -- "One source of
truth. Two editors of the same setting drift; the `_ClusterSettingsDialog`
docstring records what it cost last time."

So do NOT build a second table with its own column model and try to keep the
widths equal by setting both. Either

  * put the buttons in the SAME table as a header row or a first row, so
    there is one column model and alignment is free; or
  * have the button strip READ the paired-data table's column geometry
    (`sectionSize`/`sectionPosition`) and follow it, one direction only,
    re-reading on `sectionResized`.

The first is simpler and cannot drift. Prefer it unless the table's model
makes a widget row impossible.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* The Input Tables category is defined in
  `spacr/qt/screens/settings_model.py` under `_APP_CATEGORY_SPECS["regression"]`
  and currently reads `("Input Tables", ("paired_data", "metadata_files",
  "count_grna_column", "count_value_column", "independent_variable_layout",
  "wide_predictor_columns", "src"))`. A reorder is an edit THERE, not in the
  screen, and it moves the whole row rather than only the buttons -- check
  which of those keys the download buttons actually belong to before moving
  anything.
* A column that is hidden or reordered by the user must not orphan a button
  above it. If the table allows either, the strip has to follow.
* 347 is changing what a settings row renders (the API dot and the animation
  square). Both items touch the same rows; whoever does the second should read
  the first's commit rather than re-deriving the layout.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* Input Tables renders the download buttons above `paired_data`, asserted on
  widget order, not by eye.
* If the alignment is done: each button's horizontal centre is within a pixel
  or two of its column's centre, asserted after a resize as well as before.

2026-09-02 — THE PREFERENCE IS DONE TOO. EACH BUTTON IS OVER ITS COLUMN.
--------------------------------------------------------------------------------

WHAT WAS MISALIGNED, MEASURED BEFORE TOUCHING ANY LAYOUT CODE. An `AppScreen(
app_key="regression")` shown offscreen at 1400x900, Input Tables expanded, the
table left at its default 100 px columns. Button centres and column centres,
both in the screen's own coordinates:

    button                  centre    its column          centre    out by
    Score                    240.0    1 Score CSV          351.0   -111.0 px
    Count                    326.0    2 Count CSV          451.0   -125.0 px
    Measurements (.db)       435.5    3 Measurements DB    551.0   -115.5 px
    Image crops              547.5    -- fills `src` --        --        --

Every one of them was left of the column it fills, because the row was a plain
QHBoxLayout starting at the strip's left edge -- which is also the TABLE's left
edge, so the buttons were spread across "Plate / proposal" and the two columns
after it. The button that fills the score column sat over the plate column.

AFTER, same screen, same widths: -0.0, -0.0, -0.0 px. After dragging column 1
to 180 px and column 3 to 160 px: -0.0, -0.0, -0.5 px (the half pixel is a
column whose width and its button's differ by an odd number, split by integer
division). After shrinking the screen to 1000 px: unchanged. Hiding a column
moves its button out of the aligned run rather than leaving it stacked on its
neighbour, and showing the column again brings it back.

HOW, AND WHY IT IS NOT THE SECOND TABLE THE REQUEST OFFERED. New
`spacr/qt/widgets/column_aligned_row.py`: a QLayout that asks a QHeaderView
where each section is, every time it lays out, and writes nothing back. There
is one column model -- the paired table's -- and the strip follows it in one
direction, so there is nothing to keep in step and nothing to drift. It
re-lays-out on `sectionResized`, `sectionMoved` and `geometriesChanged`, and
on the header viewport moving or resizing under it.

WHO INSTALLS IT, AND WHY IT IS THE TABLE. The strip is built by the generic
`AppScreen._install_example_data_button`, which knows nothing about these
columns -- every module's example-data row is built by the same method. The
paired table is the only widget in the form that is Regression's alone and the
only object that knows what the columns are, so `PairedFileTableWidget` grew
`align_download_buttons()` and calls it from its own `showEvent`. It finds the
buttons by the ATTRIBUTES the screen keeps them on
(`_example_scores_button`, `_example_counts_button`, `_screen_feature_button`,
`_screen_crops_button`), never by the text on them: a download in progress
renames a button to "Fetching…", and a strip identified by caption would lose
its buttons in the middle of the download the user is watching. The columns
come from the table's own `SIDE_COLUMNS`, which is the same mapping the drop
router files a dropped file into -- one statement of which column is which.

IMAGE CROPS HAS NO COLUMN and is not pretended to have one. It fills `src`, a
setting row of the same form, so it trails the aligned run instead of being
centred over "Plate rule", which it has nothing to do with.

A BUTTON IS CLAMPED TO ITS COLUMN'S WIDTH. "Measurements (.db)" wants 127 px
and the column is 100 px, so at its natural width it would reach 3.5 px into
the Count button -- two download buttons drawn overlapping, which is the
confusion the alignment exists to remove. It is given its column and no more,
which is also what "lock the width ... to the width of the paired data column
counterparts below" asks for.

WHAT THAT COSTS, AND THE ONE THING LEFT. At the default 100 px the clamped
caption is clipped to "surements (". The table's OWN headers are clipped the
same way at that width and were before any of this -- "Plate / proposal" draws
as "late / propos", "Measurements DB" as "asurements" -- so this is the paired
table's default column widths being too narrow for their own labels, not
something the alignment introduced. Widening them is a change to the TABLE and
must stay one: sizing a column from the button above it would be the strip
writing back into the column model, which is the drift this design exists to
avoid. Left for whoever takes that on.
