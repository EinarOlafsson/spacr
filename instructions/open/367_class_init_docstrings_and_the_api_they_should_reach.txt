CLASSES DOCUMENT THEMSELVES BUT NOT THEIR __init__, WHERE THE PARAMETERS ARE
================================================================================

Status:    measured 2026-09-02, implementation started.
Requested: 2026-09-02 -- "i noticed for classes in spacr many have a short
           docstring and nothing for the __init__. the __init__ is where the
           settings imports lie. so this section should have a docstring that
           explains the settings. these explanations should be available in
           the API. now users have to go to the source code to even see the

      PARAMETERS UNDOCUMENTED                        385   (72%)

  THE FIRST COUNT SAID 495 OF 554 (10% documented) AND WAS WRONG. It asked
  "does __init__ have a docstring", which is not the question. A class may
  document its constructor's parameters on the CLASS docstring with `:param:`
  fields, and `autoapi_python_class_content = 'both'` merges the two, so the
  reader sees them either way. 101 classes do exactly that -- it is the house
  pattern, `spacr.submodules.CellposeLazyDataset` is the worked example, and
  counting them as undocumented would have sent this work to rewrite pages
  that are already correct.

  The right question is whether EVERY PARAMETER IS NAMED in a `:param:` field
  anywhere the API will show. Asked that way the answer is 385 classes, and
  those are the ones to fix. Where the class docstring is the natural home,
  put it there; do not move existing prose onto `__init__` for uniformity.

--------------------------------------------------------------------------------
THE GOOD NEWS: THE API MACHINERY ALREADY DOES THIS
--------------------------------------------------------------------------------

`docs/source/conf.py` already sets

    autoapi_python_class_content = 'both'   # class docstring + __init__ docstring

so an `__init__` docstring is CONCATENATED onto its class's API page today.
Nothing needs configuring, nothing needs a template change, and there is no
"API overhaul" to do in the build -- the pipeline works and is waiting for
content. Writing the docstring is the whole of the work, and it appears in
the API the moment it exists.

  VERIFY THIS ON A REAL BUILD BEFORE WRITING 495 DOCSTRINGS. Document one
  constructor, build the docs, and confirm the parameter list appears on the
  class page. If `autoapi_options` lacking `special-members` turns out to
  suppress it after all, that is a one-line config change -- and much better
  discovered now than after the writing.

--------------------------------------------------------------------------------
WHAT A CONSTRUCTOR DOCSTRING HAS TO SAY
--------------------------------------------------------------------------------

The repo already uses reST field lists and has a test that parses them
(`tests/test_docstring_field_lists_are_parsed.py`), so the form is settled:

    :param settings: ...
    :param parent: ...
    :raises ValueError: ...

EVERY PARAMETER, and for a `settings` mapping that means the KEYS it reads,
not the sentence "a settings dictionary". The complaint is that users "have
to go to the source code to even see the settings", and a docstring saying
"settings: the settings" leaves them exactly where they were.

  WHERE THE KEY DESCRIPTIONS ALREADY EXIST, LINK RATHER THAN COPY.
  `spacr/settings.py` carries tooltips for settings keys. A constructor
  docstring that restates one is a second copy that goes stale -- the same
  fault instruction 362 removed from the README grid and the model zoo table.
  Name the keys and point at the settings reference; copy prose only where
  none exists.

  DO NOT DESCRIBE `self`, and do not write `:param parent: the parent` for a
  Qt widget's parent. A docstring that documents the obvious to reach 100%
  makes the page longer without making it more useful, and buries the
  parameters that matter.

--------------------------------------------------------------------------------
TRAPS
--------------------------------------------------------------------------------

* A NEW DOCSTRING IS NEW SOURCE TEXT FOR THE TRANSLATION CATALOGS. Every
  docstring added here stales `docs/i18n/reviewed/api/**` records pinned to
  the old text and adds rows to the translation backlog. One two-word default
  change staled two reviewed records this week; 495 docstrings will not be
  free. Coordinate with 306 and 316, and expect the API catalog job to go red
  until the catalogs are rebuilt.
* `tests/test_docstring_correctness.py` and
  `tests/test_user_facing_docstrings.py` already fail at HEAD (6 failures).
  Read them before writing, so 495 docstrings are not written in a shape
  those tests reject.
* Do not let the count become the goal. 10% -> 100% is not the objective;
  a caller being able to use the class without opening the source is.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* The 8 settings constructors document every key they read.
* A built API page for a documented class shows its parameters.
* A test fails when a PUBLIC class's `__init__` takes parameters and
  documents none of them -- ratcheted, so the number cannot go back up.
* No constructor docstring restates a settings tooltip verbatim.
