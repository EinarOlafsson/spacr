THE GOOD NEWS: THE API MACHINERY ALREADY DOES THIS
--------------------------------------------------------------------------------

`docs/source/conf.py` already sets

    autoapi_python_class_content = 'both'   # class docstring + __init__ docstring

so an `__init__` docstring is CONCATENATED onto its class's API page today.
Nothing needs configuring, nothing needs a template change, and there is no
"API overhaul" to do in the build -- the pipeline works and is waiting for
content. Writing the docstring is the whole of the work, and it appears in
the API the moment it exists.

  VERIFY THIS ON A REAL BUILD BEFORE WRITING 495 DOCSTRINGS. Document one
  constructor, build the docs, and confirm the parameter list appears on the
  class page. If `autoapi_options` lacking `special-members` turns out to
  suppress it after all, that is a one-line config change -- and much better
  discovered now than after the writing.

--------------------------------------------------------------------------------
WHAT A CONSTRUCTOR DOCSTRING HAS TO SAY
--------------------------------------------------------------------------------

The repo already uses reST field lists and has a test that parses them
(`tests/test_docstring_field_lists_are_parsed.py`), so the form is settled:

    :param settings: ...
    :param parent: ...
    :raises ValueError: ...

EVERY PARAMETER, and for a `settings` mapping that means the KEYS it reads,
not the sentence "a settings dictionary". The complaint is that users "have
to go to the source code to even see the settings", and a docstring saying
"settings: the settings" leaves them exactly where they were.

  WHERE THE KEY DESCRIPTIONS ALREADY EXIST, LINK RATHER THAN COPY.
  `spacr/settings.py` carries tooltips for settings keys. A constructor
  docstring that restates one is a second copy that goes stale -- the same
  fault instruction 362 removed from the README grid and the model zoo table.
  Name the keys and point at the settings reference; copy prose only where
  none exists.

  DO NOT DESCRIBE `self`, and do not write `:param parent: the parent` for a
  Qt widget's parent. A docstring that documents the obvious to reach 100%
  makes the page longer without making it more useful, and buries the
  parameters that matter.

  until the catalogs are rebuilt.

  `tests/test_user_facing_docstrings.py` already fail at HEAD (6 failures).
  Read them before writing, so 495 docstrings are not written in a shape
  those tests reject.
* Do not let the count become the goal. 10% -> 100% is not the objective;

WHAT A RATCHET FOR THIS SHOULD CHECK, now that the backlog is gone. A
parameter counts as documented if it is named in ANY of: `:param x:` in the
class docstring, a NumPy `Parameters` block, or either style on the
`__init__` docstring. The parameter list must come from `args` PLUS

keyword-only parameter as a GHOST.

FOUR WAYS THE WRITING ITSELF WENT WRONG, all caught by verification and worth
knowing before anyone automates more of this:

  1. `#: :param x:` is a Sphinx ATTRIBUTE comment. It renders beside whatever
     follows and documents no parameter at all, so it counts as work done
     while `__doc__` stays empty. Written twice.
  2. A docstring that opens on one line and closes on the next is not a
     one-liner. Treating it as one ate three characters off the closing line
     and turned `:class:` into `"""ass:`.
  3. A class nested inside a function needs deeper indentation. Writing at a
     fixed four spaces left the module unparseable.
  4. A plausible reading of the NAME is not the meaning. `mode` was the crop
     source, not a png/array split; `removable` was "not the last one", not
     "not required"; `host` was where training is requested, not where output
     is published. Each was corrected by reading the call site.

THE OTHER HALF OF THIS ITEM -- whether the API pages these docstrings reach
render them correctly -- is untouched and is what remains.

The 06:55 note above measured the narrower question -- public classes
documenting NONE of their parameters -- and got it to zero. This is the

`:param:` field on either docstring. It was 168 short when this session

WHERE THE VALUE WAS, and it was not spread evenly. Three findings worth more
than the count:

  * `_Parser` (qt/widgets/formula.py) takes a `source` it stores and never
    reads. Documented as such rather than given an invented purpose -- it is
    there so an error can quote the offending span, which the parser does not
    yet do. A reader tracing that argument deserves to be told it stops at
    the assignment.
  * `_ReaderCache(max_open=1)` is silently raised to 2, and the reason is a
    bug that did not look like one: registration holds two readers at once,
    so a cache of one evicted a reader its own caller was still using and
    every tile fell back to its stage position. Not a refused stitch -- a
    plate that would not register.
  * `PCAPanel(source=...)` is the view's name on the linked-selection bus.
    Two panels sharing a link must not share it, which `str = "pca"` cannot
    say and a second panel built by copy-paste will not guess.

`parent` WAS A THIRD OF THE BACKLOG -- 56 of 163 at that point. This file
says not to write ":param parent: the parent", and that is right. What was
written instead says what the argument DOES: "ownership only", after
checking that all 56 hand it straight to the base constructor and never read
it again. Four looked like exceptions and were not; the scan had missed
`QObject.__init__(self, parent)` and `super().__init__(tr(text), parent)`.
An incomplete list cannot tell a reader whether a parameter was boring or
forgotten, and that is the whole value of the line.

ONE DOCSTRING WAS WRONG AND WAS CORRECTED BEFORE COMMIT. `_LabelIndex` was
described as silently mis-measuring a 3-D array. It does not: `np.nonzero`
returns three arrays and the two-name unpack raises. Checking cost one line.
"Fails loudly" and "fails quietly" send a reader in opposite directions.
