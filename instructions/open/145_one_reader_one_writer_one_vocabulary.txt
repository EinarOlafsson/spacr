--------------------------------------------------------------------------------

`spacr/schema.py` already holds the key names and is the right home.

    rowID     row, ROW, Row, rowid, row_id, row_name, rowName
    columnID  column, COLUMN, Column, col, columnid, column_id, column_name
    fieldID   field, FIELD, Field, fieldid, field_id, field_name

MATCHED CASE-INSENSITIVELY AND PUNCTUATION-INSENSITIVELY, so the table is
short and `Plate_ID` needs no entry of its own. Fold to lowercase, strip
non-alphanumerics, then look up.

DO NOT INVENT MEMBERS. `col` is real and in the existing map; `c` is not, and
a one-letter alias would capture a measurement column called `c` and rename a
real variable into a plate key. When in doubt leave it out -- a name that is
not normalised is visible; a measurement silently renamed to `columnID` is
not, and it corrupts a join.

--------------------------------------------------------------------------------
B. THE COLLISION RULE, EXACTLY AS ASKED
--------------------------------------------------------------------------------

Several columns can map to one key. What happens is decided by whether they
AGREE ROW-BY-ROW:

  THEY AGREE
      Keep one, drop the rest. Prefer the one already spelled canonically
      (`wellID`); if none is, choose one and rename it.
      PRINT what happened. No warning -- nothing is wrong.

  THEY DISAGREE
      Same action -- keep one, drop the rest -- but WARN, and the warning
      NAMES the columns and the choice:
      "well metadata columns well, wellID, well_name do not agree; wellID is
       being used".

COMPARE AS STRINGS, STRIPPED. `1` and `1.0` and ` 1 ` are the same well, and
a dtype difference is not a disagreement. This is where a naive `.equals()`
would warn on every file and teach the user to ignore the warning.

THE DISAGREEMENT WARNING IS THE VALUABLE ONE. It means the file carries two
different opinions about which well a row came from, and every join downstream
is picking one of them. Say how many rows differ, not just that they do.

--------------------------------------------------------------------------------
B. THE COLLISION RULE -- EXACTLY AS ASKED
--------------------------------------------------------------------------------

`schema.resolve_metadata_collisions(frame, report=, warn=)`.

  AGREE      keep one, drop the rest, PRINT. No warning; nothing is wrong.
             The canonical spelling wins if one is present; otherwise the
             leftmost, and it is renamed.
  DISAGREE   same action, and a WARNING that names the columns, the choice,
             and HOW MANY ROWS DIFFER:

             "wellID metadata columns well, wellID do not agree (2 of 4 rows
              differ); wellID is being used and the rest are dropped"

COMPARED AS STRIPPED STRINGS, through `comparable_key_value`. `1`, `1.0`,
`'01'` and `' 1 '` are the same well; missing (`None`/`NaN`/`''`) is its own
value, so two blanks agree. This is the half a naive `.equals()` gets wrong:
it would warn on every file that stored one copy of the well as text and the
other as a number, and a warning that fires every time is a warning the user
learns to ignore -- including the one that means the file carries two
different opinions about which well a row came from.

ONLY METADATA COLLAPSES. Two feature spellings keep both columns. A
measurement is data; dropping one to tidy a name is not the reader's call.

DUPLICATE LABELS ARE HANDLED POSITIONALLY, so a frame that already carries two
columns both literally named `rowID` -- which pandas allows and `to_sql`
refuses -- is repaired rather than raising.
