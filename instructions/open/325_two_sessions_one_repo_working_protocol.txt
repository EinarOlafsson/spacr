--------------------------------------------------------------------------------
3. COMMIT CADENCE — SMALL AND CONSTANT
--------------------------------------------------------------------------------

After EVERY finished item, without exception:

    git add -A
    git commit          (Einar's name only -- never Claude as author or
                         co-author, never a "Generated with" trailer)
    git pull --rebase
    git push

Not at the end of a session. Not when a group of things is done. Every
item. A conflict between two commits is a minute; a conflict between two
days is an afternoon, and the whole reason this section exists is that
conflicts compound while unpushed work sits.

If `git pull --rebase` reports a conflict:

  1. STOP. Do not resolve it by preference and carry on.
  2. Write what happened into section 5 of this file, in one commit of
     its own, and push that first if you can.
  3. If the conflicting hunk is in the other session's file, take THEIRS
     -- they know why it is that way. If it is in yours, take yours and
     tell them what you overwrote.
  4. If it is in a shared file, or you cannot tell, say so in section 5
     and move to the next item rather than guessing.

Never `--force` and never `--force-with-lease` on nightly. If you think
you need one, you have found something worth writing in section 5.

--------------------------------------------------------------------------------
4. REPORTING — A TABLE AFTER EVERY FINISHED TASK
--------------------------------------------------------------------------------

When you finish an item, print a table:

    item | summary (two sentences) | percent done | time left

If the item has numbered sub-items, ONE ROW PER NUMBER with its own
description -- not one row for the parent. "310: 40%" tells nobody which
six defects are left.

Percent is of the ITEM, not of your session. An item you cannot finish is
reported at its true percentage with the blocker named, not rounded up.

--------------------------------------------------------------------------------
5. HANDOFF — WRITE HERE, THE OTHER SESSION READS IT
--------------------------------------------------------------------------------

This is the channel. Append, never rewrite. Date every entry. Push it on
its own rather than bundling it with code, so the other session sees it
at their next pull rather than at their next conflict.

Use it for: a file you need that the other owns; a conflict you hit; a
premise of theirs you have invalidated; anything you changed outside your
lane and why; a measurement that changes their plan.

6. FOUR THINGS THAT COST AN HOUR EACH TODAY
--------------------------------------------------------------------------------

1. A TEST ASSERTING AN ABSENCE PROVES NOTHING UNTIL YOU HAVE WATCHED IT
   FAIL. Four separate cases today: a test that passed against a
   deliberately broken source; one that refused a path which had never
   existed; two that reached a different guard than the one they named.
   Always write the positive counterpart. Always mutate the source and
   confirm red.

   tests were written for the wrong half of a function today and would
   have been reported as three items closed having closed none.

   exclude_lines and partial_branches. Those markers are notes, not

   one line; the rest are genuinely impossible.

   were what settled three of them), and then pin the PREMISE the
   deletion rests on, so a change to that premise fails a test rather
   than silently making the removal wrong.

THE STANDING RULE: every new local full-suite, coverage, benchmark, training,
or other potentially long/high-memory command is launched through
``tools/run_memory_guarded.py``.  Its default hard stop is 115 GiB of total
system RAM in use (``total - available``), leaving about 10 GiB for VS Code,

when the host is already at the limit; if usage crosses the limit later, it
sends TERM to the guarded process tree, waits ten seconds, then sends KILL if
needed.  It never kills unrelated processes.

    python tools/run_memory_guarded.py -- \
        python -m pytest tests/qt -q -p no:randomly --timeout=180

Small focused tests need no wrapper.  A long command started without this
guard is a protocol violation, even if its own expected RSS looks small: the
failure being guarded is accumulation across descendants and tests.

2026-09-03 — `git commit` SWEEPS AN AGENT'S STAGED WORK. USE `-o`.
--------------------------------------------------------------------------------

Recorded because it happened and because the symptom is confusing rather
than loud.

`git commit` commits THE WHOLE INDEX, not the files you just added. With
several agents working in one clone, another agent's `git add` puts its work
in the same index — so a commit that names only your own files still carries
theirs, under your message. Tonight a 374 agent's nine files landed inside a
commit whose message is about instruction 371, and the agent noticed before I
did.

    git commit -o <paths> -F -        commits ONLY those paths
    git commit -F -                   commits everything staged, including
                                      whatever an agent staged a second ago

Nothing is lost when it happens -- the work is committed and correct -- but
the history says the wrong thing about who changed what and why, and that is
the whole value of these messages. `-o` costs nothing and is now the habit.

The other half of the same lesson: DO NOT `git stash` in a shared clone. It
takes every agent's uncommitted work with it, and `stash pop` after a test
run is a race with whatever they wrote meanwhile. Use a worktree for a
baseline instead — `git worktree add --detach <path> <commit>` — which is
what proved tonight that three preview tests were broken by a rename and a
fourth was not.

1. `pgrep -f "<pattern>"` MATCHES THE WAITER'S OWN COMMAND LINE.

       until ! pgrep -f "build_documentation_i18n.py --audit"; do sleep 30; done
