WHERE THE REDUNDANCY ACTUALLY IS
--------------------------------------------------------------------------------

78 of mask's 203 settings are the SAME 20 QUESTIONS asked once per object
type -- `cell_`, `nucleus_`, `pathogen_`, `organelle_`, `cytoplasm_`:

  CP_prob x4        FT x4              Signal_to_noise x3   area_multiplier x4
  background x3     channel x4         diameter x4          intensity_merge x4
  ... and 12 more shapes

This is the single biggest finding and it is NOT simply redundancy to
delete: a user genuinely may want a different diameter for a nucleus than
for a cell. But 20 shapes x N objects is a presentation problem being
solved by multiplying the vocabulary, and instruction 326 has already
established that the object count must be ARBITRARY -- so this multiplies
without bound as soon as 326 lands. The two items meet here.

  THE LIKELY SHAPE: one question per shape, answered per object in a small
  table or per-object tab, rather than N flat settings per shape. That is a
  presentation change with a settings-file migration behind it, not a
  rename. Propose it as such.

WHAT THE FIRST AUDIT FOUND (mask + measure, 2026-09-02)
--------------------------------------------------------------------------------

NOTHING IS DEAD. All 268 settings across the two modules are read somewhere.
An audit hunting for removable settings would have reported "nothing to do"
and missed every real problem. The axes that matter are REDUNDANCY and
NAMING.

THE ONE THAT IS A BUG, NOT UNTIDINESS: organelle carries BOTH
`_min_size`/`_max_size` and `_min_area`/`_max_area`. They mean the same
thing, and they are read by DIFFERENT code -- the `_size` pair by the batch
organelle mask writer, the `_area` pair by the shared filter the Qt live
preview uses. So tuning the preview and then running the batch applies a
different filter, silently. cell, nucleus and pathogen have only the `_area`
pair; organelle alone answers the question twice.

FOUR RENAMES PROPOSED, all where the tooltip must translate the name before
it can explain the setting: `_FT` -> `_flow_threshold`, `_CP_prob` ->
`_cellprob_threshold`, `_Signal_to_noise` -> `_signal_to_noise`, and
`_min_object_area` -> `_min_split_area` (that last one is not style: it is
the floor below which an object is never SPLIT, and its current name reads
as a variant of `_min_area`, which it is not).

AND A FINDING FROM OUTSIDE THIS ITEM: 59 of the 706 settings in the
generated `setting_api_targets.py` map point at a function that reads no
settings at all -- 30 of them at one guide-permutation CSV writer. That map
is what a setting's "where is this used" API link follows, and instruction
368 proposes building a settings-flow tree on it. It has to be right first.

--------------------------------------------------------------------------------
THE FOUR JUDGEMENTS, AND WHAT EVIDENCE EACH NEEDS
--------------------------------------------------------------------------------

UNNECESSARY -- propose removal. The evidence is not opinion:
  * nothing reads it (grep the package, not just the module);
  * it is read but every caller passes the default;
  * it exposes an implementation detail the user cannot reason about;
  * it duplicates something spaCR can measure or infer.
  A setting that only ever takes its default is a question with one answer.

REDUNDANT -- propose combining. Two settings are redundant when no
combination of their values is meaningful that one setting could not
express. Say which combinations become unreachable, because that is the
cost.

NOT INTUITIVE -- propose a rename. The test is whether the name says what
the user is deciding, in the user's vocabulary. `pathogen_Signal_to_noise`
mixes snake_case with a capitalised term of art; `FT` is an abbreviation of
something; `intensity_merge` does not say what merges with what. Check the
TOOLTIP against the NAME: where the tooltip has to explain what the word
means before it can explain the setting, the word is wrong.

  ONLY 14 TOOLTIPS ARE DEFINED against ~600 settings across all modules.
  Any rename proposal should note where there is no tooltip at all, because
  an unnamed, undocumented setting is the worst case and is invisible in a
  count of "settings that need work".

TRAPS
--------------------------------------------------------------------------------

* A REMOVED SETTING GOES IN `RETIRED_SETTINGS` in `spacr/validate.py`, so an
  old settings file loads with a message instead of an error. `corrected_manders`
  is the worked example.
* A RENAMED SETTING IS A REMOVAL PLUS AN ADDITION as far as every saved
  settings file, published tutorial, notebook and reviewed translation
  catalog is concerned. Each rename stales: the notebooks' generated setting
  documentation, `docs/i18n/reviewed/runtime/**` records pinned to the old
  tooltip text, and the tutorial JSON. Budget for that; instruction 337's
  two-word default change staled two reviewed records on its own.
* `settings.categories` MUST list every key, and a key added there without
  being registered in `KEYS_ADDED_BY_REGROUP` fails two tests. This has
  already caught one change this week.
* Do not confuse "unused by the GUI" with "unused". Several settings exist
  for the headless `spacr-run` path and notebooks only.

DECIDED AND DONE, 2026-09-02
--------------------------------------------------------------------------------

RETIRED, as approved: `organelle_min_size` and `organelle_max_size`. Both are
in `RETIRED_SETTINGS` mapped to their `_area` counterpart, so an old settings
file loads with a message rather than an error. The batch mask writer now
reads the `_area` pair the Qt live preview already used, so tuning the
preview and pressing run finally apply the SAME filter. Mask went 203 -> 201.

  THE DEFAULT CARRIED OVER, NOT RESET. `organelle_min_area` is now 10 -- the
  value the batch run actually used through the retired `_size` setting --
  rather than the 0 the preview had. Real runs are unchanged; it is the
  preview that stops disagreeing with them.

  AND A SECOND COPY WAS FOUND WHILE DOING IT. The mask factory hand-wrote
  `organelle_min_area`/`organelle_max_area` as 0 beside
  `_set_organelle_defaults`, which owns them per organelle type and sets 10.
  That shadowing is what made the preview read 0 while the batch read 10, so
  it is the other half of the same bug and is removed.

RENAMED, all four approved: 90 settings across 26 organelle slots.

    <object>_FT               -> <object>_flow_threshold
    <object>_CP_prob          -> <object>_cellprob_threshold
    <object>_Signal_to_noise  -> <object>_signal_to_noise
    <object>_min_object_area  -> <object>_min_split_area

  Done as a SUFFIX substitution rather than 90 literal renames, because the
  organelle slots are generated and a literal list would miss the next one.
  497 occurrences across 60 files, plus 94 more for the retirement.

  THE TOOLTIPS NOW STATE THE REAL PER-APP DEFAULTS. The surviving
  `organelle_min_area` tooltip said "Default 0 (disabled)" while Mask's
  default is 10 -- a claim that was already wrong and would have stayed wrong
  silently. It now names both, which also removed two entries from the
  tooltip-drift ledger: a variant the tooltip itself explains is not drift.

THE PER-OBJECT TABLE'S MODEL IS BUILT: `spacr/object_settings_table.py`.
`to_table(settings)` reads a flat settings dict as {question: {object:
value}} and `from_table` writes it back. Mask's 113 per-object keys become 55
questions.

  AND THERE IS NO SETTINGS-FILE MIGRATION AFTER ALL, which is the important
  part. This file assumed one; there is none, because the table is a
  PRESENTATION and the stored keys do not change. `from_table(to_table(s), s)
  == s` for both Mask and Measure, so no saved settings file, notebook,
  tutorial or headless `spacr-run` has to move. Storing a nested structure
  instead would have been a file-format change -- the presentation was what
  was wrong, so only the presentation changes.

  `widen(table, 'organellec')` is the operation 326 needs: one call, one new
  column, and the number of QUESTIONS does not move. It starts the new
  organelle where the first one is rather than at a global default nobody
  chose. In the flat vocabulary the same act is twenty new settings that
  every consumer, tooltip and translation catalog has to learn.

  TWO THINGS THE MODEL GETS RIGHT THAT A GUI WOULD OTHERWISE GET WRONG.
  Object prefixes are matched LONGEST FIRST, or `organelleb_min_area` files
  under `organelle` and twenty-six slots collapse into one column -- which no
  assertion about totals would catch. And a question an object does not ask
  is ABSENT from its row rather than present as None: cytoplasm is derived,
  so it has no channel and no diameter, and that is a different fact from a
  diameter nobody has chosen yet.

STILL TO BUILD: the GUI that renders it, and the same treatment for the
remaining modules in this file's order.

2026-09-02: THE TABLE IS BUILT -- MODEL AND VIEW
--------------------------------------------------------------------------------

`spacr/object_settings_table.py` was the model and drew nothing; the view is
now `spacr/qt/widgets/object_settings_grid.py`. One row per question, one
column per object, and the button that widens it.

WHAT IT COSTS THE SETTINGS FILE: nothing, and that is the whole design.
`to_table` reads a flat dict and `from_table` writes it back, so the stored
keys are unchanged and no settings file, notebook, tutorial or `spacr-run`
invocation migrates. `test_showing_a_settings_dict_changes_nothing_in_it`
round-trips Mask's own 201 defaults and checks the TYPE of every value as
well as its value.

TWO THINGS THE VIEW HAD TO GET RIGHT, both of which corrupt a settings file
rather than merely look wrong, and both now pinned:

  * A VALUE KEEPS ITS TYPE. A table hands back strings. `cell_background` is
    an int and `organelle_cellprob_threshold` is a float -- the SAME question
    with two types, which is exactly the case a single "cast to the row's
    type" rule gets wrong. Where the cell being replaced is None there is no
    type to copy, so the same question asked about another object is used
    instead: a diameter is a diameter whether it is a cell's or a nucleus's.
  * A QUESTION AN OBJECT DOES NOT ASK STAYS ABSENT. `cytoplasm` is derived --
    cell minus the rest -- so it has no channel, no diameter and no detection
    method. Those cells are not editable, because a value typed there invents
    a settings key nothing reads. They read as blank rather than as `auto`,
    which is a different claim: `auto` means "work it out" and is what an
    unset diameter says.

WHERE IT MEETS 326. Adding an organelle is `widen()` -- one column, seeded
from the first organelle's answers rather than from a global default nobody
chose. The question count does not move. In the flat vocabulary the same
operation was twenty new settings that every consumer, tooltip table and
translation catalog had to learn, which is why 326's ceiling could not be
raised before this existed. The column headers are NUMBERED ("Organelle 2"),
never lettered, per the maintainer on the same day.

The ceiling is refused out loud rather than hit silently: at 26 the button
says the slots are lettered and the alphabet is what runs out.

STILL TO DO: mounting the grid on Mask's own settings form in place of the
78 flat rows. The widget is finished and tested against Mask's real defaults
(`tests/qt/test_the_per_object_settings_are_one_table.py`, 13 tests), and
the mount is NOT a small edit. Read before starting it, because the seam
looks like a two-line change and is not:

  * THE SEAM IS `_split_rows_by_object` (settings_model.py:2219) and its one
    caller at 8312, which turns a family's rows into one sub-section per
    object. Replacing those children with a single grid section is the
    obvious move.
  * WHAT MAKES IT NOT OBVIOUS is what a "row" is by the time the screen has
    it. `AppScreen` reads each row as `(label, widget)` and then: derives the
    setting key from the widget (`_key_of_field`); decides from that key
    whether the run has an object for it and DEFERS the caption if not;
    hands the key list to `SettingsWidgets.remember_section_rows`; lets the
    settings search index the row by key; and `tests/qt/test_all_module_
    smoke.py` reads every entry as a labelled setting row. A QTableView
    holding 78 keys satisfies none of those five contracts.
  * SO THE REAL WORK is teaching the row machinery about a SPANNING
    COMPOSITE row that owns many keys -- what its key list is, how the
    search reaches a cell, what "hidden because the run has no organelle 3"
    means when the slot is a column rather than a row. That is a design
    change to the most-used screen in the application, and it is worth doing
    deliberately rather than in the same afternoon as the widget.
  * THE WIDGETS THEMSELVES SHOULD SURVIVE THE MOUNT. `collect()` reads
    `self._widgets`, and with it every coercion, canonicalisation and the
    organelle-slot rule in `_organelle_slots_worth_keeping`. The cheap and
    safe shape is therefore a grid that EDITS THE EXISTING WIDGETS and a
    flat row that is hidden rather than deleted -- not a grid that owns the
    values and a widget dict that has lost them.
