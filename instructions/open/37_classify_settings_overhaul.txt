--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Two themes run through the whole list.

FIRST, settings that do not say what they mean. `png_type` is a path
substring. `file_type` and `png_list` appear to be the same thing. `size` and
`image_size` both exist. `custom_model` is a boolean next to a path that
already answers the same question. Each one is a place where a user has to
know a convention rather than read a label, and each is a place where two
settings can disagree and one silently wins.

SECOND, the class definition is doing too little. A user who has annotated one
class has to reach for a "write random annotation column" button to get the
other; a user who annotated across two columns cannot express it at all; and a
metadata-based model needs location/positive/negative control settings that
say the same thing the classes already say. A Classes dict that names the
value AND the column it came from replaces all of that.

WHAT TO DO
--------------------------------------------------------------------------------

CLASSES

 1. Classes becomes a DICT, populated from the chosen column(s): set the
    column, the keys appear, the user names them. Each entry names the VALUE
    and the COLUMN that value came from, so more than one annotation column
    can define classes at once.
 2. `annotation_column` therefore becomes plural and is the same setting as
    `location_column` -- one setting, one name.
 3. Remove "write random annotation column". When only one label is present,
    the second class is a random selection of the NON-annotated images, and
    the Classes dict is what says so.
 4. In the metadata basis the same dict offers the metadata columns (plate,
    row, column, field, well) instead of user-defined annotation columns, and
    replaces `location_column`, `positive_control` and `negative_control`
    entirely.
 5. Downstream compatibility is the hard half, exactly as it was for the
    training basis: spacr/io.py reads annotation_columns/annotation_values
    today. Old settings CSVs must keep working -- translate the old keys into
    the dict in one place (the normalize_settings pattern), never in each
    reader.

RENAMES AND DUPLICATES

 6. `png_type` -> "path string": a substring that must appear in each image's
    path.
 7. `file_type` -> a dropdown of image file types, and its LOGIC becomes a
    file-extension filter. It and `png_list` currently look identical; decide
    which survives and retire the other with an alias.
 8. `size` and `image_size` are the same thing twice. Keep `image_size`.
 9. `save_to_db` -> "Save Results to DB", and it does not get a category of
    its own.

CROP SOURCE

10. `crop_source` dropdown: PRE-GENERATED CROPS / ON-DEMAND CROPS / GENERATE
    CROPS.

HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * A settings CSV written BEFORE this trains on the same objects afterwards.
    The test asserts the resulting dataset, not that the keys translated --
    the failure mode is a silently different training set, which a key-level
    test would pass straight through.
  * Setting one annotation column populates the Classes dict with that
    column's values; setting a second adds its values alongside, each
    remembering which column it came from.
  * Annotating one class and leaving the rest blank yields a second class of
    randomly chosen non-annotated images, with no separate button pressed.
  * Choosing the metadata basis offers plate/row/column/field/well in the same
    dict, and location column / positive control / negative control are gone
    rather than ignored.
  * Choosing ON-DEMAND crops and running training produces actual crops on
    disk from `merged` -- checked end to end, because "the crops are actually
    generated" is the requirement and a unit test on the settings cannot see
    it. Same for the database-coordinate source, where only bounding-box crops
    are offered.
  * Selecting pre-generated crops greys the on-demand settings and vice versa;
    every greyed control keeps its value (INVARIANTS 6).
  * A custom model path that loads is the model used, with no boolean set, and
    `model_type` is visibly superseded rather than silently ignored.
  * Clicking a model reports whether it is compatible with the chosen class
    structure, including for a class structure the model cannot serve.
  * `size`, `png_type` and the duplicate of `file_type`/`png_list` no longer
    appear anywhere in the UI, and an old CSV containing them still runs.
  * The category list is shorter than it is today, and every name says what is
    in it.

A NOTE ON EDITING settings_model.py's CATEGORY_TOOLTIPS
--------------------------------------------------------------------------------

Do NOT remove entries with a regex. The values are implicitly-concatenated
multi-line strings, and a pattern that matches the key line leaves the
continuation lines behind as bare strings inside a dict literal -- a
SyntaxError several hundred lines away from the edit. It happened three times
in this session. Match the exact block, or delete by line range after locating
the next key.

THE EDITOR, concretely:

    Column(s):  [ column picker, multi-select ]

    Class: [____]   Value: [____]   [ Add ]

    then a list of the rows added, each removable.

So the user says "class `infected` is value `1`" and "class `uninfected`
is value `0`", and that is the whole interaction. No dict to populate, no
keys appearing when a column is chosen.

THE COMBINATION RULE is the part with real logic in it. When SEVERAL
columns are given and the same value appears in more than one -- which the
maintainer says is common -- a combination column is generated, giving each
distinct COMBINATION of labels its own unique class. Decide and write down:

  * what the generated label looks like (``colA=1|colB=2``, or the class
    names joined, or an index), because it ends up in the database and in
    figures;
  * whether combinations the user never named become a class, are dropped,
    or are an error. Dropping silently would lose objects with no trace,
    which is the failure mode this module already has elsewhere;
  * where the generated column is written, and whether it persists or is
    recomputed -- a column that appears in measurements.db after a classify
    run is a schema change and needs to be deliberate.

2026-08-10 - THE `classes` ROUND-TRIP, MEASURED. IT IS NOT A DATA-LOSS BUG.
--------------------------------------------------------------------------------

`tests/qt/test_settings_list_editor.py::test_every_default_round_trips_
untouched[classify]` has been failing since commit 30500970 turned `classes`
from `['nc','pc']` into a dict of name -> {column, value}. The triage called
it "migrate the product default, not the test". Measured before doing that,
and the picture is more constrained than it looked:

  normalize_settings(['nc','pc'])                  -> class_names ['nc','pc']
  normalize_settings({'nc': {...}, 'pc': {...}})   -> class_names ['nc','pc']

`class_names` is what `deep_spacr` and the evaluation code actually read, and
it is IDENTICAL either way. So merely opening the Classify screen and saving
does not change what gets trained. The failing assertion is about the stored
SHAPE, not about behaviour.

THREE CONSTRAINTS THAT RULE OUT THE OBVIOUS FIX:

  1. The Tk GUI expects a LIST. `gui_elements.py:5879` does
     `str(defaults.get('classes', ['nc','pc']))` and `:6183` parses it back
     with `_parse_list_literal`. spaCR ships both front ends, so changing the
     default to a dict breaks the Tk path.
  2. `normalize_settings` translates only `if not isinstance(raw, Mapping)`.
     A dict default -- including `{}` -- SKIPS the legacy translation, so a
     default of `{}` would silently mean "no classes" rather than "not set".
  3. The migration fills `column='?'`, a deliberate "you must fill this in"
     marker. Shipping that as a default puts a non-column in every fresh
     settings CSV.

SO THE HONEST FIX IS NOT THE DEFAULT. It is that the panel should not
REWRITE a setting the user never touched: `collect()` should return the value
it was given when nothing was edited. That keeps the Tk GUI working, keeps
the legacy translation reachable, and satisfies the invariant the test is
actually defending -- opening a screen and saving must not rewrite your
settings file.

That is a change to the collect path, not a one-line default swap, which is
why it is still here rather than done. It belongs in this instruction rather
than 47: 47's scope was "make the suite finish", and this is the classify
settings design.

NOT A BLOCKER FOR ANYTHING. The test is red, the behaviour is correct, and
the reason is now written down.

  The chip/bubble editor that `class_metadata` already uses, but with TWO
  fields side by side: CLASS then VALUE. Entering a class name emits a TEAL
  bubble; entering its value emits a GREEN bubble. Same widget, same gesture,
  in BOTH training bases -- metadata mode and annotation mode -- so a user
  learns it once.

  The dict is not the point and was never the requirement: "i dont care about
  the dict i just thought it was a good idea to consolidate the information
  into one object." So the storage shape is free to be whatever serves the
  two-field editor. Do not preserve the current
  `{name: {column, value, random_complement}}` shape out of loyalty to it --
  preserve only what the pipeline actually reads.

WHAT THIS SETTLES, and it reverses a recommendation recorded above. The entry
dated earlier today argued against migrating the `classes` default BECAUSE
`gui_elements.py:5879` parses it as a list and changing it would break the Tk
GUI. That reasoning is now void:

    "in the future if there is something that is a change that will break the
     Tk legacy application, then implement the fix anyway and change the
     legacy code to accomodate the new code."

So: make the change, then update every Tk reader in the same commit.
`gui_elements.py:5879` (the entry's initial value) and `:6183`
(`_parse_list_literal` on the way back) are the two known ones; grep the
`gui_*` modules for `classes` before assuming they are the only ones.

WHAT MUST STILL HOLD

  * `class_names` is what `deep_spacr` and the evaluation code read. Whatever
    the editor stores, that list must come out the same, in order.
  * `normalize_settings` translates the legacy list ONCE and only when the
    value is not a Mapping -- so if the new shape is a Mapping, the legacy
    path must be reached some other way or old settings files stop loading.
    This is the trap that makes a default of `{}` mean "no classes" rather
    than "not set".
  * `test_every_default_round_trips_untouched[classify]` is currently RED
    because opening the screen rewrites the setting. Whatever shape is
    chosen, the default must round-trip through the panel unchanged -- that
    invariant is what stops opening a screen and saving from rewriting a
    user's settings file.
  * The random-complement row ("everything not claimed, chosen at random")
    is a real feature of the current editor. Keep it or replace it
    deliberately; do not lose it in the simplification.

COLOURS: teal and green must come from the palette, not literals, or they
will not survive a theme change -- and the contrast rules in `theme.py` apply
to bubble text as much as to anything else.
