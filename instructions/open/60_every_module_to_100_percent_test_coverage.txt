--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The coverage push that produced the two numbers above also produced 29 real
bug fixes. That is the argument: writing a test for an uncovered branch is
how the bugs in it get found, and at 55% the majority of this codebase has
never had that done to it.

It matters more here than in most projects because the failure mode is
quiet. A segmentation pipeline that takes a wrong branch does not crash --
it writes plausible-looking masks, and the error is discovered, if ever,
in the analysis of a screen that took a week to run.

WHAT TO DO
--------------------------------------------------------------------------------

1. Get the real per-module numbers first and record them here, so progress
   is measurable rather than felt:
       pytest --cov=spacr --cov-report=term-missing
   (with the sitecustomize workaround above).
2. Work module by module, worst-first among the modules that RUN things --

3. TEST THE DEFENSIVE BRANCHES FOR REAL. No `# pragma: no cover` to reach

5. Fix what the new tests find, rather than writing a test that documents

2026-08-10 - UNBLOCKED, AND A MEASUREMENT TRAP TO AVOID
--------------------------------------------------------------------------------

THIS TASK WAS BLOCKED ON INSTRUCTION 47 and is not any more. The qt suite now

THE TRAP, hit while scoping this and worth writing down because the number it
produces looks authoritative: COVERAGE FROM A PARTIAL RUN IS MEANINGLESS.
Running three test files with `--cov=spacr.utils` reported

    spacr/utils.py   4598 statements   16%

against the 99% this file records for the same module. Nothing regressed --
the 99% came from the WHOLE suite, and utils is exercised by hundreds of
files. A per-module coverage number is only comparable to another number
taken over the same test set, and the honest way to state one is
"<module> at <percent> over <which tests>".

THE COMMAND, with the two settings that make it work here:

    QT_QPA_PLATFORM=offscreen PYTHONPATH=<dir with sitecustomize.py> \
    OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
    pytest tests -q -p no:randomly -n 4 --timeout=600 \
      --cov=spacr --cov-report=term:skip-covered --cov-report=json:cov.json

  * the `sitecustomize.py` is one line, `import torch`, and exists because
    coverage's tracer plus torch's lazy `_has_torch_function` import crash
    together otherwise. It has to be on PYTHONPATH, not in the repo.
  * the thread caps matter: `-n 4` does NOT bound the run to 4 cores, because
    torch and numpy spawn threads per worker. Without them load reached 20+
    on this machine during the qt run.
  * `--timeout=600` rather than 300: coverage slows every test, and the
    heavier integration tests do exceed 300 s under the tracer.

WHAT TO DO WITH THE RESULT: rank by UNCOVERED STATEMENTS, not by percentage.
A 4,598-statement module at 90% has more untested code than a 200-statement
module at 40%, and this repo's biggest modules are exactly the ones whose
percentage looks respectable.

SIX REAL BUGS, WHICH IS THE POINT OF THE EXERCISE
--------------------------------------------------------------------------------

Every one was reproduced before it was fixed, and each has a test that fails
without the fix.

1. THE CLUSTER BUTTON HAS NEVER WORKED, IN TWO SEPARATE WAYS.
   `GateCanvas.active_gate` is a PROPERTY and `GateTree.active_gate` is a
   METHOD; `run_cluster` called the canvas one as a method, so every cluster
   that got past the parameter dialog died on `TypeError: 'NoneType' object
   is not callable`. And the clusters it would have produced were added to
   `self.canvas.gates`, a DIFFERENT GateSet from `self._gates` until
   something calls `set_gates` -- which nothing does on a fresh session -- so
   they never reached the gate list, were never saved, were not counted, and
   were deleted by the next hand-drawn gate.

50))` and `anim.save(..., writer='pillow', fps=2, dpi=80)`, so every frame is
50 x 80 = 4000 px on a side -- 64 MB of RGBA before compression, for a mask
that is usually a few hundred pixels across. It is written whenever `save` is
true on any of the three tracking backends
(`_visualize_and_save_timelapse_stack_with_tracks`), and a real timelapse is
tens to hundreds of frames. `spacr.plot`'s interactive viewer beside it uses
the same `figsize=(50, 50)`. Measured, not guessed:

    plt.subplots(figsize=(50, 50)) canvas   5000 x 5000 at default dpi
    the frame the writer emits              4000 x 4000 at dpi=80
    uncompressed                            64 MB per frame

This is why the three `if plot or save:` call sites at timelapse.py 699, 976
and 1234 have no test that lets them run: a test that writes one real movie
costs seconds and hundreds of megabytes. Sizing the figure from the mask
(with a sane dpi) would make those three lines cheap to cover AND make the
output usable -- which is the order to do it in.

AND ONE MORE, ALSO QUEUED RATHER THAN FIXED: A PLATE FOLDER WHOSE NAME HOLDS
AN UNDERSCORE STILL CANNOT BE MEASURED. `spacr.io` composes the stack name as
`f'{plate}_{well}_{field}_{timeID}.tif'` with the plate taken straight from
the regex group or from `os.path.basename(src)` -- a folder name, which very
often holds one. `exp_1` therefore produces `exp_1_A01_1_1.npy`, five
components, and the reader cannot tell the plate from the well:

    _map_wells('exp_1_A01_1_1.npy')  ->  ('error',) * 5

That is not new and this pass did not make it worse -- before `09a4a75d` the
same name parsed as plate `exp`, well `1`, field `A01` -> `f1`, which is
worse, because it is wrong quietly. It is now wrong loudly. The fix already
exists and is simply not called: `schema.escape_field_stem_plate` writes
`exp%5F1_A01_1_1`, which `parse_field_stem` reads back as plate `exp_1`
exactly. It belongs at the two places that build the name --
`io._rename_and_organize_image_files` (`output_filename = ...`) and
`io._move_to_chan_folder` (`newname = ...`) -- and it changes names on disk,
so the mask folders and any resume manifest have to move with it. That is the
whole of why it is queued here rather than done at the end of a coverage
pass.
