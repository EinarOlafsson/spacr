--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The coverage push that produced the two numbers above also produced 29 real
bug fixes. That is the argument: writing a test for an uncovered branch is
how the bugs in it get found, and at 55% the majority of this codebase has
never had that done to it.

It matters more here than in most projects because the failure mode is
quiet. A segmentation pipeline that takes a wrong branch does not crash --
it writes plausible-looking masks, and the error is discovered, if ever,
in the analysis of a screen that took a week to run.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Get the real per-module numbers first and record them here, so progress
   is measurable rather than felt:
       pytest --cov=spacr --cov-report=term-missing
   (with the sitecustomize workaround above).
2. Work module by module, worst-first among the modules that RUN things --
   a pipeline module at 30% is a worse risk than a plotting helper at 30%.
3. TEST THE DEFENSIVE BRANCHES FOR REAL. No `# pragma: no cover` to reach
   the number. The except-branch that has never run is exactly where the
   bugs are, and covering it by exclusion is covering it by pretending.
4. When a test and the code disagree, find out which one is describing
   reality before changing either. Several tests in this repository have
   been wrong since the commit that introduced them; several others were
   right and the code had regressed. Both happened again today.
5. Fix what the new tests find, rather than writing a test that documents
   a bug. A test that asserts current-wrong-behaviour makes the bug
   permanent.

2026-08-10 - UNBLOCKED, AND A MEASUREMENT TRAP TO AVOID
--------------------------------------------------------------------------------

THIS TASK WAS BLOCKED ON INSTRUCTION 47 and is not any more. The qt suite now
reaches its summary line (41 minutes at `-n 8`), so a whole-suite coverage
run is possible for the first time. A full run is in flight as this is
written.

THE TRAP, hit while scoping this and worth writing down because the number it
produces looks authoritative: COVERAGE FROM A PARTIAL RUN IS MEANINGLESS.
Running three test files with `--cov=spacr.utils` reported

    spacr/utils.py   4598 statements   16%

against the 99% this file records for the same module. Nothing regressed --
the 99% came from the WHOLE suite, and utils is exercised by hundreds of
files. A per-module coverage number is only comparable to another number
taken over the same test set, and the honest way to state one is
"<module> at <percent> over <which tests>".

THE COMMAND, with the two settings that make it work here:

    QT_QPA_PLATFORM=offscreen PYTHONPATH=<dir with sitecustomize.py> \
    OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
    pytest tests -q -p no:randomly -n 4 --timeout=600 \
      --cov=spacr --cov-report=term:skip-covered --cov-report=json:cov.json

  * the `sitecustomize.py` is one line, `import torch`, and exists because
    coverage's tracer plus torch's lazy `_has_torch_function` import crash
    together otherwise. It has to be on PYTHONPATH, not in the repo.
  * the thread caps matter: `-n 4` does NOT bound the run to 4 cores, because
    torch and numpy spawn threads per worker. Without them load reached 20+
    on this machine during the qt run.
  * `--timeout=600` rather than 300: coverage slows every test, and the
    heavier integration tests do exceed 300 s under the tracer.

WHAT TO DO WITH THE RESULT: rank by UNCOVERED STATEMENTS, not by percentage.
A 4,598-statement module at 90% has more untested code than a 200-statement
module at 40%, and this repo's biggest modules are exactly the ones whose
percentage looks respectable.
