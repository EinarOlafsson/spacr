WHAT IS ACTUALLY MISSING: COVERAGE
--------------------------------------------------------------------------------

Measured on one Mask screen, in English, counting distinct label and
button strings against the catalogue:

    catalogue entries                 267
    distinct strings on ONE screen    230
    of those, in the catalogue         10   (4%)

Untranslated samples: "Adjust cells", "Anisotropy", and every setting
label on the screen.

So choosing Swedish today translates the chrome -- menus, buttons like Run
and Settings -- and leaves the module screens in English. That is why a
Swedish session still shows 223 English labels.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A half-translated interface is arguably worse than an untranslated one: the
user is told the program speaks their language, and then the part they
actually work in does not.

The setting labels are also the hardest part to translate well -- they are
domain terms, and a wrong translation of "Anisotropy" or "Flow threshold"
is worse than the English word a microscopist already knows.

It matters more for this tool than for most: spaCR's users are labs, and
the ones least served by an English-only interface are exactly the ones
least likely to file an issue about it in English.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. DONE ALREADY -- the selector exists and the choice loads at startup.
   Nothing to build for the request as clarified.
2. DECIDE HOW FAR TRANSLATION SHOULD GO, which is the real question this
   task turned out to be. Three defensible answers:
     (a) chrome only, as today -- and then say so, rather than implying a
         fully localised program;
     (b) chrome plus setting LABELS, leaving the tooltips English;
     (c) everything, including the 700 tooltips of instruction 61.
   (c) is a translation project, not a feature. (b) is roughly 230 strings
   per screen and is where the value is. Someone who reads the languages
   has to make this call -- a machine translation of "Anisotropy" shipped
   to a microscopist is worse than the English.
3. THE CHOICE IS WHAT LOADS AT STARTUP. Clarified by the maintainer:
   "default" means the translation loaded first on startup, not a fallback
   for missing strings. So the persisted `prefs/language` value must be
   applied during application start, before the first window is built --
   otherwise the user picks Swedish, restarts, and gets English until they
   touch the setting again.

   Following the SYSTEM locale on a first-ever launch is NOT part of this
   request and should not be bundled into it. Noted only so the next reader
   does not re-derive it: it would be a separate, arguable behaviour change,
   and the ask here is simply that the user's own choice is what loads.
4. Persist through the installer question if instruction 45's account /
   options screens land first: asking the language at install time and then
   again on first launch would be asking twice.
5. Check that a language with a non-Latin script (zh_CN, hi, ko) actually
   renders in the bundled fonts, and that the layout survives longer German
   strings. A picker that produces boxes-instead-of-glyphs is worse than
   no picker.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Open Preferences, choose Svenska, and the running window re-labels without
a restart. Reopen the app and it is still Swedish. On a fresh profile with
a Swedish system locale, it starts Swedish without being asked.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Not started. Note the scope trap: this task is a combo box and a default
policy, NOT a translation effort. The translations exist. If they turn out
to be thin or stale, that is a separate task with a separate cost, and it
should be measured -- count the translated strings per language -- before
anyone promises a language is supported.
