================================================================================
THE DOCK: HELP GETS ITS OWN SECTION, THE ICONS GROW, AND THE NAMES MOVE OFF IT
================================================================================

Status:    not started, filed 2026-09-02.
Requested: 2026-09-02, verbatim, in two messages --
           "the dock module nested modules works great! but there are some
           modules that have been mooved to help that are still in the dock
           under core for example . these should be under the category Help,
           which comes lowest on the dock."
           "also in the dock enlarge the icons and add a magnification effect
           so the dock functions like the osx dock and remove the text that
           can be moved to the category tooltip location upon hover."
Owner:     spacr/qt/app.py (the dock) and its icon path.
Follows:   330, which put the folded modules in the dock and is DONE. This is
           the next thing asked for on the same surface, and the praise for
           330 is recorded above because it is the only report so far that
           the nested rows work.

--------------------------------------------------------------------------------
THREE THINGS
--------------------------------------------------------------------------------

1. HELP IS A SECTION, AND IT IS LAST.
   Modules that moved to Help are still listed under Core. The section list
   and its order live with `APPS` / `SECTION_ORDER` in `spacr/qt/app.py`;
   Help must exist as a section and sort last.

   FIND WHICH MODULES ACTUALLY MOVED before editing the table. "moved to help"
   is a statement about the module's category, and this repository has twice
   had two copies of a section map disagree -- 330's own note records it. One
   mapping, and the dock, the menu bar and the fold strips all read it.

2. THE ICONS GROW AND MAGNIFY.
   Bigger icons, with an OS X-style magnification under the pointer.

   THE COST IS THE WHOLE RISK HERE, and there is a measured precedent to
   respect: instruction 315 found that an application-wide event filter
   watching mouse events cost 13,646 Python calls per second while a module
   opened, and put 130 ms back onto a GUI-thread block that had just been
   removed. A magnification effect is a per-mouse-move geometry update on up
   to sixty rows. Do it with ONE handler on the dock that computes from the
   pointer position, not a filter per row, and measure the module-open block
   before and after -- 315's numbers are the baseline.

3. THE NAMES COME OFF THE DOCK.
   With icons doing the work, the text moves to the same place a category's
   help text appears on hover -- which is the bottom-of-screen strip that
   instruction 347 is making the single home for category help. THE TWO ITEMS
   SHARE THAT SURFACE: do not build a second strip.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* A DOCK WITH NO TEXT IS UNUSABLE IF THE STRIP IS EMPTY. The name must be in
  the strip before the label is removed from the row, not after.
* Accessibility: the row still needs an accessible name for a screen reader
  even when it renders no visible text. `setAccessibleName`, and a test.
* The dock already collapses sections and expands hosts (330). Bigger rows
  make the collapsed default matter more, not less -- 33 folded children plus
  Help must still fit.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* Every module whose category is Help appears under Help, and Help is the
  last section. Counted from the one mapping, not from a hand-written list.
* Hovering a dock row puts its name in the strip; the row itself renders no
  text and still reports an accessible name.
* The pointer magnifies the row under it and its neighbours, and the
  module-open GUI-thread block is no worse than 315's recorded baseline --
  measured, both numbers written here.

2026-09-02 — PART 1 DONE: HELP IS A DOCK HEADING, AND IT IS NOT A SECTION
--------------------------------------------------------------------------------

The eight Help-menu modules -- queue, batch, distributed_jobs, db_browser,
run_history, report, data_manager, pipeline_graph -- now draw under a Help
heading at the BOTTOM of the dock. They were filed under Data, so the dock
drew them beside the modules that get data IN, which is not what any of them
does. (The report said "under core"; measured, they were all under Data. The
three tileless rows under Core -- train_compare, profiler, investigate_hit --
are folded children reached from a button in their host, not from Help, and
were correctly left alone.)

MAKING HELP A REAL SECTION WAS TRIED FIRST AND REVERTED. Recorded because it
looks like the obvious implementation and costs an hour to discover otherwise.

Adding `SECTION_HELP` to `SECTION_ORDER` broke THIRTEEN tests across six
files, and they were right to break. A section in this codebase is HOME's
categorisation: `home_categories`, `home_bands` and `section_members` all mean
"a tab and the tiles on it", and `test_no_section_is_empty` defends the
invariant by name. Every Help module is TILELESS by construction, so Help can
never satisfy it. Patching `_refresh_sections` to count only tiled apps made
it worse -- it broke the separate invariant that `SECTIONS` is the set of
sections `APPS` uses, which `test_no_section_is_used_that_was_never_declared`
holds.

THE FIX IS A DOCK-ONLY VIEW. `app.dock_rows()` returns APPS with the
Help-menu modules re-labelled and stably re-sorted, and the dock walks that
instead of `APPS`. Home never sees it, `SECTION_ORDER` stays at four, and the
thirteen tests go back to green untouched.

DRIVEN BY `_HELP_MODULES`, not by a second list -- that table already says
which modules the Help menu opens, and a hand-written copy is the shape that
has caused two bugs on this surface.

TWO TESTS WERE UPDATED, and both were asserting the same wrong thing: that the
sidebar's headings equal Home's. `test_sidebar_draws_exactly_one_heading_per_
section_in_order` compared against `home_bands()` and
`test_a_registered_app_is_drawn_on_home_and_in_the_sidebar` against
`SECTIONS`. Both now compare against `dock_rows()` and additionally assert
that the dock's list is Home's plus Help, so the relationship is pinned rather
than the equality dropped.

VERIFIED AGAINST A HEAD BASELINE, same 1,249-test selection, twice:

    HEAD    21 failed
    part 1  21 failed        regressions: none, fixes: none

THE 21 ARE PRE-EXISTING and are the 345/346 family again -- several pass in
isolation. One of them, `test_the_sidebar_re_inks_its_icons_when_the_theme_
changes`, was chased here and cleared: it fails at HEAD in isolation too, and
the sidebar's 33 null-icon rows are byte-identical before and after this
change.

STILL OPEN IN THIS ITEM: part 2 (bigger icons and the magnifier) and part 3
(row text moves to the strip). The menu bar was NOT given a Help submenu --
only the dock was asked for, and the Help menu already lists these modules,
so a Help submenu inside the Help menu would say it twice.

THE COST, which is the risk 348 named. 315's rejected filter was 13,646 Python
calls a second while a module opened, for 130 ms back on the GUI-thread block.

    one second of a pointer sweep, 101 positions, 10 visible rows
        1.25 ms of GUI thread, 4,905 Python calls
    the same second with every section forced open, 37 visible rows
        2.09 ms, 9,470 calls
    module-open GUI-thread block, three runs each side
        HEAD    mask 2098-2585 ms   measure 904-914 ms   annotate 115-124 ms
        after   mask 1994-2060 ms   measure 902-929 ms   annotate 115-116 ms

The magnifier costs NOTHING while a module opens, because it is one handler
installed on the dock's own rows and on nothing else -- it is handed no event
unless the pointer is over the dock. The first cut cost 11.02 ms and 9,640
calls for that same second; `scaled_px` reads QSettings through
`get_font_scale` and `magnify_from` was asking for three of them per pointer
position. `Sidebar.magnifier_metrics()` caches them and is dropped by
`_forget_row_positions`, which the preferences path already reaches.

THE ROW HEIGHT IS FIXED AT 48 px AND MAGNIFYING NEVER MOVES IT. This is the
one place the effect departs from the OS X dock. Growing the rows themselves,
the way OS X does, was reasoned through and rejected BEFORE it was written:
a row that grows pushes every row below it down, so the row under a STATIONARY
pointer stops being the row under the pointer, and the next mouse move
computes from geometry the last one moved. This dock has already been reported flickering once for a hover
that moved geometry ("the dock on linux is acting up, flickering when mouse is
hovered", 2026-09-01). 48 px = the largest icon plus 4 px above and below, so
a magnified icon is never clipped by its own row.
`test_magnifying_never_changes_a_row_height` holds the heights AND the tops.

THE NAME IS STILL SET ON THE ROW; ONLY THE PAINTING DROPS IT, and that is the
decision in this change most likely to look wrong later. `setText("")` is the
obvious implementation and was rejected before it was written, because three
pieces of code read a dock row's name and none of them is about pixels:
`tutorial.scripts._sidebar_button` falls back to a label match ("Mask") when a
script names a row by its display name; `clipped_items()` -- which
`test_no_shipping_sidebar_label_is_clipped` and
`test_sidebar_caps_its_width_and_elides_a_pathological_name` both read -- can
only answer about text the row still holds; and `fitting_width()` sizes the
column from the widest NAME. All three fail silently on a blank string, and
two of them live in files this session was not allowed to edit. `_DockRow`
paints the QSS plate and the icon and clears `opt.text`, so the name stays as
data and leaves the screen. The test that says so RENDERS the row and looks
for ink, with an ordinary button carrying the same text as a control -- a
"no ink" verdict from a probe that cannot see ink at all would pass forever.

THE STRIP WAS ALREADY CARRYING THE NAME BEFORE THE LABEL CAME OFF, which is
what 348's WATCH demanded and it is checked rather than assumed:
`test_hovering_a_dock_row_puts_its_name_in_the_status_strip` PASSES AT HEAD
as well as after. `spacr.qt.module_hints` reads `moduleNameSource` /
`moduleSummarySource`, which `_make_item` has always stamped, and routes them
to the bottom-of-window status bar -- 347's surface. No second strip was
built. `setAccessibleName` / `setAccessibleDescription` / `navKey` / the
tooltip are all untouched: 71 rows carry all four before and after.

THE 34 FOLDED CHILDREN HAD NO ICON AT ALL and would have become 34 blank
strips. They were identified purely by three indented words. Measured before
wiring anything: 31 of the 34 resolve to a DISTINCT icon and only
`import_images`, `regression_diagnostics` and `explain_cv` fall through to the
shared puzzle piece -- so giving them icons is worth doing, where a fallback
that gave them all one picture would have been no better than blank.
`test_no_dock_row_is_blank` fails at HEAD with all 34 and passes now.

330's THREE LEADING SPACES were the only mark of a child row, and with no
label to indent they moved into the icon: a child is drawn at x=30 instead of
x=12 and at 19 px instead of 26 px.

VERIFIED, `tests/qt/test_the_dock_behaves_like_a_dock.py`, 12 tests:

    against HEAD's app.py    8 failed, 3 passed
    working tree            12 passed

The 3 that pass on both sides are the preservation guards -- accessible names,
tooltips and the status strip -- and they are MEANT to pass on both sides:

coordinate mapping into the scrolled row host are all covered; the rest would
pass over a magnifier nothing ever calls.

WHAT WAS DELIBERATELY NOT DONE

* THE DOCK WAS NOT NARROWED. It is 220 px before and after, which is
  `Sidebar.WIDTH_MIN` and not the width of any name -- measured,
  `fitting_width()` returns the floor in both versions, so the hidden names
  cost nothing. An icon-only column 220 px wide is arguably too wide, but
  narrowing it was not asked for, it would change where every section heading
  sits, and `test_sidebar_caps_its_width_and_elides_a_pathological_name`
  pins the current bounds. Left for whoever the maintainer tells.
* `spacr/qt/theme.py` AND `spacr/qt/iconset.py` WERE NOT TOUCHED. Nothing in
  this change is a colour or a stylesheet rule: the row height, the icon
  sizes, the indent and the falloff are all layout decisions the dock makes
  in Python and the magnifier has to read back. One number does duplicate the
  sheet -- `Sidebar.ICON_LEFT_PX = 12` matches `SPACING["md"]` in the
  `QPushButton#SidebarItem` padding -- and is commented as such on both
  counts.
* NO MENU-BAR CHANGE, as in part 1: only the dock was asked for.
