Status:    filed 2026-08-18.

  "dosnt look like there is an option to change the exis color for the colcano
   plot"

  "in white mode lots of graphs still have white text and axes color"

Related: 150 is the SAVED figure (dark mode writes white ink onto paper). This

--------------------------------------------------------------------------------
A. THE WHITE-TEXT-IN-LIGHT-MODE BUG. FOUND, AND IT IS EXACT.
--------------------------------------------------------------------------------

`preferences.get_figure_colors()` is written correctly. It stores the TOKEN
"auto" and resolves it against the live theme at read time:

    auto_fg = "#ffffff" if dark else "#000000"

So on a light theme "auto" gives black text, and the reported bug should be
impossible. IT IS NOT, because the token gets overwritten with its own
resolution:

    figure_queue.py:1884   self._bg, self._fg = get_figure_colors()
                           ^ the RESOLVED pair -- "#ffffff" on a dark theme,
                             never the word "auto"

    figure_queue.py:2019   set_figure_colors(self._bg, self._fg)
                           ^ writes that resolution back as an EXPLICIT value

THE DIALOG DOES NOT NEED TO BE CHANGED FOR THIS TO FIRE. Open the figure style
dialog once while on a dark theme, press OK, alter nothing -- and "auto" is
gone for good, replaced by a hard "#ffffff". Every figure is then white-on-
whatever for the rest of time, and switching to a light theme leaves white
text on a white page. That is the second report, exactly.

VERIFIED ON THE MAINTAINER'S OWN SETTINGS, 2026-08-18:

    stored fig bg : 'none'        <- the resolved TRANSPARENT_FIGURE_BG
    stored fig fg : '#ffffff'     <- the resolved dark-theme foreground
    theme         : dark
    resolved      : ('none', '#ffffff')

Both are explicit, so the "auto" branch never runs. It already happened.

THE FIX IS TO STORE THE TOKEN, NOT ITS ANSWER. A dialog seeded from a resolved
value cannot tell "the user chose white" apart from "the theme is dark", and
once it writes back, nothing can. So:

  * the dialog seeds from the STORED tokens and shows what "auto" currently
    resolves to as a preview, labelled as automatic rather than as a choice;
  * it writes "auto" back unless the user actually picked a colour;
  * there is an explicit way BACK to automatic -- "Follow the theme" -- because
    a user who has been bitten by this has no other route to it;
  * and this is a general rule worth stating once: NEVER PERSIST A RESOLVED
    DEFAULT. It converts a preference that tracks into a preference that
    freezes, and the damage outlives the session that caused it.

MIGRATING WHAT IS ALREADY BROKEN. Per the standing rule, correct the format
going forward AND convert the old content: a stored value that exactly equals
what "auto" would have resolved to on some theme is indistinguishable from the
bug and should be migrated back to "auto" once, with a line saying so. A user
who genuinely chose #ffffff on a dark theme loses nothing they cannot re-pick,
and every user who never chose anything gets their theme back.

--------------------------------------------------------------------------------
B. THERE IS NO AXIS-COLOUR CONTROL, AND "FONT COLOUR" IS NOT IT
--------------------------------------------------------------------------------

The menu offers "Font colour…" (`_ask_font_colour` -> `set_font_colour`), which
is the TEXT. The axes themselves -- the spines, the ticks, the tick labels --
take `_foreground` at construction and there is no control that changes them
afterwards. So the first report is correct: there is no option.

DECIDED BY THE MAINTAINER 2026-08-18, and it replaces the three-control
proposal this file carried until now:

  "I want one color option when picking color for the graph elements. called
   line color which should cahnge the color of all lines including axis lines
   and ticks. and then a font color theat controlls the color of all font in
   the graph."

SO THERE ARE EXACTLY TWO COLOUR CONTROLS, and they divide the figure by what a
mark IS rather than by which part of the code draws it:

    Line colour     EVERY line. The data's own lines, the reference and
                    threshold lines, the Q-Q diagonal, the trend lines, AND
                    the axis spines and the tick marks.

    Font colour     EVERY piece of text. Title, axis labels, TICK LABELS,
                    legend text, annotations, the p=0.05 caption.

TICK MARKS ARE LINES AND TICK LABELS ARE TEXT. That split is the one place the
two controls meet and it is the one a reader could take either way, so it is
written down: the little dash beside the axis follows Line colour, the number
printed next to it follows Font colour. Anything else would make "all font in
the graph" untrue.

WHY THIS IS MORE THAN A RENAME. Today these are two unrelated mechanisms:

    set_line_style()   sets a QPen on each item in line_items()
    _foreground        a pyqtgraph axis/foreground setting, applied at
                       construction, with no control after

and `line_items()` DELIBERATELY EXCLUDES anything that is not a plot item, so
no existing call reaches the axis at all. One control covering both means
`set_line_style` must also drive the axis pen and the tick pen, and the
existing exclusions have to be re-read: the selection ring stays excluded (it
is a cursor, not a mark), and the scatters stay excluded (they are points, and
they have their own control).

THE DASH PATTERNS STILL SURVIVE, for the reason set_line_style already gives:
each pen is copied and only the colour is replaced, so a threshold line stays
dashed. Extending the reach must not lose that.

151 SPLITS "Line colour and width…" INTO TWO ENTRIES. The "Line colour…" half
it creates is this control; there is not a third one.

AND "FOLLOW THE THEME" STAYS. Two colours plus a way back to automatic, which
is what section A is about -- a user who has set a colour needs a route to
un-set it, or the freeze this instruction exists to fix simply happens by hand
instead of by accident.

THE SAME CONTROL MUST REACH THE MATPLOTLIB FIGURES. `figures/style.py` and
`figure_queue._style_figure_colors` read the same preference, so an axis colour
set in one place is the axis colour everywhere -- that shared source is the
good half of the present design and this must not break it.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Switch to the light theme with no explicit colour set: every figure's text
  AND axes are dark. Checked by sampling pixels on a rendered figure, both a
  pyqtgraph one and a matplotlib one.
* Open the figure style dialog, press OK without touching anything, switch
  theme: the figures still follow. This is the regression test for A and it
  fails today.
* A settings store already holding '#ffffff' is migrated back to 'auto' once,
  and the migration says so in the console.
* The volcano's menu has an axis colour entry, it changes the spines and ticks
  and not the title, and "Follow the theme" undoes both.

WHAT SHIPPED

`spacr/qt/preferences.py` -- the store keeps TOKENS and nothing else:

    AUTO_FIGURE_COLOR         the token "auto". Not a colour.
    figure_color_is_auto()    is this token the theme, or a choice?
    auto_figure_colors()      what "auto" resolves to RIGHT NOW, for display
    get_figure_color_tokens() the stored pair, UNRESOLVED  <- seed from this
    get_figure_colors()       the stored pair, RESOLVED    <- draw from this
    set_figure_colors()       writes tokens; also marks the store migrated
    set_figure_colors_auto()  the way back

The rule is stated at the head of that section, where the next person will be
standing when they are about to break it: NEVER PERSIST A RESOLVED DEFAULT.
The same reasoning was already written one screen up for `get_figure_style`,
which stores {} rather than today's defaults; the two now point at each other.

`figure_queue._FigureSettingsDialog` seeds from the tokens, shows the
automatic answer as a labelled preview ("Automatic (#ffffff)", "Automatic
(transparent)"), and writes back what it was given. A new "Follow the theme"
button un-sets both, and is greyed when both already follow (106). Propagate
sends the TOKENS, so a saved run does not freeze the colour in a second store.

THE MIGRATION. `_migrate_frozen_figure_colors` runs once per store, on the
first read or write of a figure colour, and turns a stored value that "auto"
resolves to on SOME theme back into "auto", saying so in the console. The
value sets are `{none, #000000, #ffffff}` for the background and
`{#000000, #ffffff}` for the text -- both HISTORIC resolutions as well as
current, because "auto" resolved to opaque black/white before 2026-08-06 and
those stores are frozen too. Both halves migrate together on purpose: freeing
the text but keeping a frozen white background gives white-on-white again the
moment the theme goes dark.

MEASURED, NOT ASSUMED. Ink luminance of the opaque pixels of a rendered
figure, light theme, nothing chosen -- 0.0 is black ink, 1.0 is white:

    matplotlib (render_figure_to_png)   before OK 0.00   after OK+theme switch
                                        was 1.00, now 0.00
    pyqtgraph  (FastPlot.export)        frozen store 1.000, migrated 0.000
                                        over the same 1316 opaque pixels

The 1.00 IS the report -- "in white mode lots of graphs still have white text
and axes color" -- and it is what the regression test asserts against.

The migration was also run against a COPY of the maintainer's real
~/.config/spacr/qt.conf (bg 'none', fg '#ffffff'): it migrates to auto/auto,
resolves to #000000 on light and #ffffff on dark, and does not fire twice. The
live file was NOT touched -- it migrates itself the next time the app reads a
figure colour.

TESTS  tests/qt/test_figure_colour_tokens.py, 17 tests. Five of them fail if
the dialog is put back to seeding from `get_figure_colors()`, verified by
doing exactly that and re-running:

    test_the_dialog_seeds_from_the_token
    test_ok_without_touching_anything_leaves_auto_alone       <- the regression
    test_the_button_says_when_a_colour_is_automatic
    test_picking_a_colour_stores_it_explicitly
    test_pressing_ok_then_going_light_still_renders_dark_ink  <- 1.0 vs 0.0

WHAT REMAINS -- section B, all of it, and none of it in this territory:
one "Line colour" reaching the axis spines and tick MARKS, one "Font colour"
reaching every text including tick LABELS, and `set_line_style` extended to
the axis pen without losing the per-pen dash patterns. `figures/style.py` and
`figure_queue._style_figure_colors` already share the preference, so whatever
B stores must be a token too or this bug returns by the other door.

WHAT SHIPPED, in spacr/qt/widgets/fast_plots.py only.

EXACTLY TWO COLOUR CONTROLS, on every plot's Appearance group:

    "Line colour…"   -> set_line_colour()  -> set_line_style(colour=...)
    "Font colour…"   -> set_font_colour()  -> apply_text_style()

LINE COLOUR NOW REACHES THE AXES, which is what the first report asked for
and what nothing could do before. `set_line_style` walks `line_items()` as it
always did AND the new `axis_items()`, setting both `setPen` (the spine) and
`setTickPen` (the tick MARKS).

  THE TICK PEN IS A SEPARATE CALL AND IT IS NOT OPTIONAL. pyqtgraph falls
  back to the spine's pen for the ticks only while no tick pen has ever been
  set, so an axis that has been given one keeps drawing its ticks in the old
  ink unless setTickPen is called too.

FONT COLOUR NOW REACHES THE CAPTIONS AND THE LEGEND. `apply_text_style` was
already doing the axis text pen, the axis labels and the title; it now also
does every `InfiniteLine.label` and every legend LabelItem.

THE p=0.05 CAPTION CHANGED SIDES, and this file is why. It used to be
recoloured by `set_line_style`, with a comment arguing that a red word beside
a green line is wrong. The maintainer's decision is the other way -- "a font
color that controls the color of all font in the graph" -- so the caption is
TEXT. `set_line_style` no longer touches labels at all, and `add_line` gives
a new caption the font colour from the moment it is drawn.
`test_the_threshold_caption_is_text_and_follows_the_font_control` records the
reversal so nobody re-argues it from the old comment.

THE WIDTH DOES NOT REACH THE AXES. Colour does, width does not: a spine three
pixels thick is not what "line width" was asked for, and the axes have no
dash pattern to preserve. Written down because it is the one asymmetry.

GATING SPLIT IN TWO, because the two controls now have different answers:

    line_reason()          -> "this plot has no lines on it"  (WIDTH)
    line_colour_reason()   -> "" on any drawn plot            (COLOUR)

A plot with axes and no data lines can be recoloured and cannot be widened.

"FOLLOW THE THEME (COLOURS)" is `follow_the_theme()`: both controls back to
automatic. Every line's ORIGINAL colour is remembered on first restyle
(`item._spacr_base_colour`) so the way back restores what the line was drawn
with rather than inventing one -- which would be the same class of mistake as
section A's "never persist a resolved default", performed by hand.

THE DASHES SURVIVE the extended reach; there is a test for it.
THE SELECTION RING AND THE SCATTERS STAY EXCLUDED; there is a test for that.

WHAT IS NOT MINE AND WAS NOT TOUCHED

  * Section A -- the resolved-colour-over-"auto" freeze, the dialog seeding,
    and the migration -- is preferences.py / figure_queue.py, the other agent
    in this wave. This side only READS the preference, through the existing
    `_figure_colors()` -> `preferences.get_figure_colors()`, and
    "Follow the theme" returns to it.
  * The controls here are PER PLOT, which is what `set_font_colour` already
    documented ("the user overriding it for one figure"). A colour for EVERY
    figure is the preferences dialog, i.e. the other half.
