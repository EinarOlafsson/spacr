PART 0 -- THE ASSAYS SECTION ALREADY HAS FOUR, AND TWO OF THEM OVERLAP THIS
--------------------------------------------------------------------------------

Before designing anything, what is already shipped:

    analyze_plaques   Plaque Assay        beta    plaque measurements
    recruitment       Recruitment          -      host protein at the vacuole
    invasion          Invasion Assay      alpha   attached vs invaded parasites
    replication       Replication Assay   beta    parasites per vacuole

INVASION AND REPLICATION ARE BOTH INFECTION MEASUREMENTS. Invasion already
computes an efficiency from two-colour differential staining -- the
`attached` / `invaded` classes and the thresholding hazards around them are
worked out in `submodules.py` and carry real notes about how weak staining
inflates the invaded fraction. Replication already buckets vacuoles by
parasites-per-vacuole and distributes them per well.

SO THE FIRST QUESTION IS NOT "WHAT CAN WE MEASURE". It is whether an Infection
module is:

  (a) a FIFTH assay beside those four, measuring the thing neither covers --
      what fraction of host cells carry any parasite at all; or
  (b) a PARENT that invasion and replication become views of, since both are
      infection measured at a different stage; or
  (c) a REPORT rather than a pipeline -- infection metrics assembled from
      measurements Measure already writes, with no new image processing.

(c) is the cheapest and may be most of the value. `measure.py` already
carries `uninfected`, `_exclude_objects(..., uninfected=...)` and the
per-object masks; `io.py` already computes `pathogen_prcfo_count` per host
cell. Infection rate is a groupby away from data that already exists. This
should be measured before anything is built: count how many of the metrics in
PART 1 are already derivable from a finished Measure run.

THE REQUEST SAYS "it can come up with things it could measure", so the list
below is offered as a proposal to choose from, NOT as a scope to implement.
Building all of it would be a worse module than building six of them well.

PART 0-A -- HOW MUCH OF PART 1 ALREADY EXISTS: 13 OF 16
--------------------------------------------------------------------------------

PART 0 says: "This should be measured before anything is built: count how
many of the metrics in PART 1 are already derivable from a finished Measure
run." Counted, by reading what Measure writes rather than by estimating.

WHAT A MEASURE RUN LEAVES BEHIND. Four per-object tables -- `cell`,
`cytoplasm`, `nucleus`, `pathogen` (`filters.OBJECT_TABLES`) -- each written
from the FULL label mask by `_morphological_measurements`, so the `cell`
table holds one row per segmented cell whether or not it is infected. That is
the denominator, and it already exists.

Each row carries `label`, `area`, `area_filled`, `area_bbox`, `convex_area`,
`major_axis_length`, `minor_axis_length`, `eccentricity`, `solidity`,
`extent`, `perimeter`, `euler_number`, `equivalent_diameter_area`,
`feret_diameter_max`, centroids, per-channel intensity, and the spatial
columns `nearest_neighbor_distance` and `touching_neighbors`.

AND THE LINK IS ALREADY THERE. `io.py:4883` computes
`pathogens['pathogen_prcfo_count']` by grouping the pathogen table on its
host's `prcfo` key -- plate/row/column/field plus `cell_id`. Parasites per
host cell is not something to be built; it is a column.

    DERIVABLE FROM AN EXISTING RUN                         13
      infection rate              cell table as denominator, pathogen table
                                  grouped by cell_id as numerator
      infection index             the same join, mean instead of fraction
      parasites per infected      `pathogen_prcfo_count` IS this
      multiplicity distribution   the histogram of that column
      perinuclear localisation    vacuole and nucleus centroids are both
                                  measured; the distance is arithmetic
      vacuole eccentricity        `eccentricity`, already measured
      host cell size / shape      cell table, split by the join
      host nucleus morphology     nucleus table, split by the join
      host marker intensity       per-channel intensity, split by the join
      uninfected control rate     infection rate, grouped by well
      per-field variance          the `prcf` key carries the field
      cell count per well         a count on the cell table
      edge-object exclusion       already implemented -- and see the warning

    NEEDS SOMETHING NEW                                     3
      intracellular fraction      needs the invasion module's two-colour call
                                  or a containment test; not in Measure
      vacuoles per cell           needs vacuoles distinguished from parasites,
                                  which is a segmentation question
      distance to host boundary   centroids are measured, the boundary is not

SO THE EVIDENCE FAVOURS (c) -- A REPORT, NOT A PIPELINE. Thirteen of sixteen
are a groupby away, and the three that are not are each a separate piece of
image processing that belongs to invasion or to segmentation rather than to
an infection report.

THE DENOMINATOR WARNING IN PART 2 IS REAL AND I CAN NAME THE MECHANISM.
`io.py:4879` does `pathogens.dropna(subset=['cell_id'])` -- a parasite not
assigned to a host cell disappears -- and `pathogen_limit` then filters rows
by `pathogen_prcfo_count`. Neither filter touches the `cell` table. So a
numerator built from the filtered pathogen table over a denominator built
from the unfiltered cell table counts different populations, and the ratio is
wrong in a way that looks entirely plausible. Whatever is built must apply
the same exclusions to both sides and SAY SO in its output.

WHAT I DID NOT VERIFY: none of this was run against a real measurements.db,
because this session has none. The columns and the join are read from the
source. A single real run would confirm the join produces what these names
say, and should happen before any of it is trusted.

PART 0-B -- BUILT, AND WHAT IT REFUSES TO DO
--------------------------------------------------------------------------------

`spacr/infection.py`, answering 357's 377-A: "(c) A report, not a pipeline".

    parasites_per_cell         every host cell with its parasite count,
                               INCLUDING THE ZEROES
    infection_report           rate, index, parasites-per-infected, and the
                               three counts behind them
    multiplicity_distribution  the histogram the means hide
    host_contrast              one host measurement, infected against
                               uninfected, within the same well

EVERY ROW CARRIES ITS OWN DENOMINATOR, which is PART 2's requirement and the
reason this module exists in the shape it does. `infection_rate` is over
"segmented host cells" and `parasites_per_infected` is over "infected host
cells"; both the phrase and the count travel with the value, so a reader who
disagrees with a number can see which half they disagree with.

THE ZEROES ARE THE WHOLE TRICK. The cell-to-parasite relationship is stored on
the PARASITE, and `measure.get_components` explodes each cell's child list and
drops the empty ones -- so a cell with no parasites appears nowhere in the
pathogen table. A report that counts rows there counts INFECTED cells and
calls the result a cell count, turning a 40 % infection rate into 100 %,
silently, on every plate. The denominator is taken from the `cell` table,
which holds every segmented cell. There is a test named for exactly this.

NO FIFTH VOCABULARY. `pathogen_count` is the name already used in `io.py` and
`merge_tables.py`, and it is reused rather than joined by a synonym.

WHAT IT DOES NOT DO, per the answer's own limits:
  * No new image processing. The three metrics PART 0-A found were not
    derivable -- intracellular fraction, vacuoles per cell, distance to the
    host boundary -- are absent, not approximated. They belong to the invasion
    module and to segmentation.
  * No GUI surface and no `spacr-run` name yet. It is a library with tests.
    Whether it becomes a button, a Report section, or something Measure emits
    on its way past is a separate decision.

WHAT IT OWES: a real `measurements.db`. The fixture is synthetic, with ten
cells whose answers -- 0.4, 0.7, 1.75 -- were chosen rather than computed. That
proves the arithmetic and the denominators; it says nothing about whether the
column spellings in a real database match. One real run settles it.

PART 1 -- CANDIDATE MEASUREMENTS, GROUPED BY WHAT THEY ANSWER
--------------------------------------------------------------------------------

HOW MUCH INFECTION IS THERE
  infection rate             fraction of host cells with >= 1 parasite
  infection index            mean parasites per host cell, all cells
  parasites per infected     mean parasites per host cell, infected only
  multiplicity distribution  the histogram behind those two means, which is
                             the number that actually distinguishes "a few
                             heavily infected cells" from "many lightly
                             infected ones" -- two conditions with the same
                             infection index and different biology
  vacuoles per cell          distinct from parasites per cell once replication
                             has started; replication assay already buckets it

WHERE THE PARASITES ARE
  intracellular fraction     needs the invasion module's two-colour call, or
                             a cytoplasm/nucleus containment test
  perinuclear localisation   distance from vacuole centroid to host nucleus
  vacuole eccentricity       and its distance to the host cell boundary

WHAT INFECTION DOES TO THE HOST
  host cell size / shape     infected vs uninfected in the same well, which is
                             the comparison that controls for well effects
  host nucleus morphology    area, eccentricity, intensity -- host nuclear
                             changes are an early infection phenotype
  host marker intensity      any measured channel, split by infection status

QUALITY AND CONTROLS -- the ones that stop a number being believed too easily
  uninfected control rate    infection rate in wells that should have none;
                             a non-zero value here invalidates the plate
  edge-object exclusion      already implemented for measurement; the infection
                             denominator has to use the same rule or the rate
                             is computed against a different cell count than
                             the numerator
  per-field variance         infection rate by field within a well, because a
                             well mean hides a settling gradient
  cell count per well        a denominator small enough to make the rate noise

--------------------------------------------------------------------------------
PART 2 -- WHAT MUST BE TRUE BEFORE THIS IS BUILT
--------------------------------------------------------------------------------

THE DENOMINATOR IS THE WHOLE PROBLEM. Every metric above is a ratio, and
almost every way of getting one wrong is a denominator that does not match
its numerator: cells excluded at the image edge, cells excluded for size,
cells with no nucleus, cells whose parasite was excluded but which still
count as infected. `merge_tables.py:352` already records one of these -- an
area summed over two objects while the count says three. Whatever is built
must state its denominator in the output, per metric, rather than leaving the
reader to infer it.

IT MUST NOT BE A FIFTH VOCABULARY. 364 found the cost of two tables of the
same words drifting. `uninfected`, `pathogen_count`, `parasite_count` and
`pathogen_prcfo_count` already exist across `measure.py`, `io.py` and
`timelapse.py`; an infection module that invents `infected_flag` beside them
is how the fifth spelling starts.

AND IT NEEDS A REAL DATASET TO BE BELIEVED. The plaque assay has one on the
NAS; this needs its equivalent before any threshold in it is defensible.
