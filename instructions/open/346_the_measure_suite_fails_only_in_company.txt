`tests/test_cov_11_measure.py` is the poisoner, on its own.

THE MECHANISM, and nothing in it looks wrong at the site:

`spacr.measure._ZERNIKE_AVAILABLE` is a module-level cache of "is Mahotas
importable", filled on first use. The file's `stub_mahotas` fixture puts a
FAKE Mahotas into `sys.modules`; a measurement taken while it is there fills
that cache with **True**. `monkeypatch` then removes the fake -- it restores
what it was asked to restore -- but THE CACHE IS NOT SOMETHING IT WAS ASKED
ABOUT, so True survives into a process where Mahotas does not exist.

Measured directly, with a probe test appended after that file:

    after test_cov_11_measure.py:   _ZERNIKE_AVAILABLE is True
                                    "mahotas" in sys.modules is False
    on its own:                     _ZERNIKE_AVAILABLE is None

Every later test that measures morphology then believes Zernike is available,
asks for it, and gets a frame with different columns. That is the whole of the
`test_measure_hooks.py` family.

THE FIX is an autouse fixture in the offending file that puts the cache back
after every test. File-local and autouse on purpose: the leak happens whenever
the cache is FILLED, which any test there can do -- including one added later
by someone who does not think it is about Zernike.

A SECOND, UNRELATED BUG WAS FIXED IN PASSING and it was a real one.
`test_region_filter_removes_exactly_the_excluded_objects` also failed ALONE,
on `cell_second_neighbor_distance`. Its claim was that the survivors are
"measured exactly as they were" -- true of per-object measurements and false
of neighbourhood ones, which are computed over the objects PRESENT. Excluding
cells 2 and 4 changes cell 1's second-nearest neighbour, and it SHOULD: a
region filter exists to say those objects are not part of the analysis, so
counting an excluded object as a neighbour would report a density the user
filtered out. The assertion is now split in both directions -- per-object
columns identical, neighbourhood columns required to MOVE -- because asserting
only the first half would pass against a build that stopped computing
neighbours at all.

name starts with `spacr.measure` from `sys.modules` so the capability probe
runs again -- which is a legitimate thing for it to test. The next import then

`tests/test_measure_hooks.py` then registers its hooks through one copy and
runs a measurement that imports the other, which has no hooks registered at
all. Every hook test fails, and nothing fails where the mistake is.

THE FIX is an autouse fixture that restores the ORIGINAL module objects
afterwards, rather than forbidding the reload -- the reload is the point of
that file and the probe genuinely has to run twice.

with the dot -- while the deletion used the dotless prefix. So it put the
module back and left `spacr.measure_hooks` rebuilt: the exact state that

2026-09-02 — THE LAST TWO, DIAGNOSED EXACTLY. THE ERROR NAMES ITS OWN CAUSE.
--------------------------------------------------------------------------------

Run the trio and the failure says what is wrong in one line:

    PicklingError: Can't pickle <function _measure_crop_core at 0x79da7d4e7100>:
    it's not the same object as spacr.measure._measure_crop_core

TWO LIVE COPIES OF ONE FUNCTION, and multiprocessing is what makes it visible:
a Pool pickles a function BY QUALIFIED NAME and the far side checks identity,
so a stale copy raises here instead of failing silently the way an ordinary
call would. Both survivors go through the pool -- one measures with a region
filter, the other checks the start method before starting it -- which is why
these two and no others.

WHAT DOES NOT FIX IT, tried and reverted so nobody repeats it: widening the
fixture's restore from `spacr.measure*` to the WHOLE `spacr.` namespace. Same
two failures. THE STALE REFERENCE IS NOT IN `sys.modules`. Restoring modules
cannot reach a function object already captured somewhere else -- a default
argument, a registry entry, a partial, a Pool initializer -- and one of those
is holding the copy from the rebuilt module.

THE NARROWER FIXTURE IS KEPT because it is what took ten failures to two; it
is not the whole answer and the file now says so beside it.

WHERE TO GO NEXT, in order of how much it would prove:

  1. FIND THE HOLDER. `gc.get_referrers` on the function object from the
     rebuilt module, run right after `_reimport_measure()`, will name what is
     keeping it. That is one probe and it ends the guessing.
  2. IF IT CANNOT BE RELEASED, MOVE THE RELOAD OUT OF THE PROCESS. The file's
     purpose is to re-run a module-level capability probe, which a subprocess
     can do without leaving anything behind:
     `subprocess.run([sys.executable, "-c", ...])` returning the probe's
     answer. That trades a little speed for an isolation the in-process
     reload cannot give, and it is the standard remedy for exactly this.
  3. Only then consider making `_measure_crop_core` resolvable by name at
     call time rather than captured at import time. That would be a
     PRODUCTION change to satisfy a test, which is the wrong order unless the
     same hazard is reachable from a real run -- and whether it is should be
     established first, because a user who reloads spaCR modules in a notebook
     would hit it too.

2026-09-02 — THE THIRD POISONER IS FOUND. IT IS NOT IN `sys.modules` BECAUSE
IT IS THE PARENT PACKAGE'S ATTRIBUTE.
--------------------------------------------------------------------------------

The handoff above said "THE STALE REFERENCE IS NOT IN `sys.modules`" and
guessed at a default argument, a registry entry, a partial or a Pool
initializer. It is none of those, and it is simpler than all of them.

IMPORTING A SUBMODULE BINDS IT IN TWO PLACES. `import spacr.measure` writes
`sys.modules["spacr.measure"]` AND sets `measure` as an attribute on the
`spacr` MODULE OBJECT. `_reimport_measure()` deletes only the first; the
re-import then rewrites both, pointing them at the rebuilt copy. The fixture
put the first one back. Nothing put the second one back, so the process ran
on with:

    sys.modules["spacr.measure"]  ->  the ORIGINAL   (what `import` finds)
    spacr.measure                 ->  the REBUILT    (what getattr finds)

MEASURED, not argued -- a probe test appended after the file:

    PROBE sys.modules entry is package attribute: False
    PROBE resolve("spacr.measure") is sys.modules entry: False

WHY THAT BREAKS THE TWO SURVIVORS, and why it looked like multiprocessing.
`_pytest.monkeypatch.resolve` walks a dotted target BY GETATTR from the top
package down, so `monkeypatch.setattr("spacr.measure.measure_crop", fake)`
patched the REBUILT copy, while `from .measure import measure_crop` inside
the pipeline went through `sys.modules` and got the ORIGINAL. The stand-in
was installed on a module nobody called. The pool made the same split
visible more loudly, because pickling a worker function by qualified name
checks identity on the far side:

    PicklingError: Can't pickle <function _measure_crop_core ...>:
    it's not the same object as spacr.measure._measure_crop_core

Same one cause, two symptoms. Multiprocessing was the messenger.

THE FIX, in the same fixture: rebind the parent package's attribute to
whatever is being restored into `sys.modules`, and delete the attribute for a
module that was not imported before this file ran, so the next import builds
ONE copy and binds it in both places.

AND THE GUARD HAS TO BE UNCONDITIONAL, which the first attempt at this got
wrong too. Recording the attribute only when it already AGREED with
`sys.modules` at fixture setup repairs nothing from the second test onward:
by then the two are already split, which is precisely the case the fixture
exists for.

WHAT IT CLOSED. Both survivors named in the handoff --
`test_region_filter_is_applied_before_features_are_computed` and
`test_measure_crop_checks_the_start_method_before_it_starts_the_pool` -- pass
in the trio that reproduced them
(`test_cov_r6_tracking_and_measurement.py + probes + measure_hooks`: 2 failed
-> 65 passed). So did two order-dependent failures in
`test_cov_w2_1_external_masks.py` that instruction 337's stricter size

A FOURTH, FOUND WHILE VERIFYING, AND IT IS THE FIRST CAUSE FROM THE OTHER
SIDE. `test_measure_optional_zernike.py::test_automatic_morphology_skips_
zernike_when_extra_is_missing` fails after `test_measure_3d.py`.
`_zernike_is_available` answers once per process and PRINTS ITS NOTICE WITH
THE FIRST ANSWER; `test_measure_3d.py` measures morphology and so spends both.
Blocking the import afterwards proves nothing -- the probe never runs and the
test reads an empty capsys. Its `_block_mahotas` now clears
`_ZERNIKE_AVAILABLE` through `monkeypatch`, which is what
`tests/test_cov_11_measure.py`'s namesake already did. THE SAME CACHE, CAUGHT
FROM THE READING SIDE INSTEAD OF THE WRITING SIDE.

THE LESSON, now stated once for all four: A NAME HAS MORE THAN ONE BINDING.
An import lives in `sys.modules` AND on its parent package. A capability
lives in the import AND in the cache of it AND in the notice printed with it.
Restoring one binding is not restoring the name.
