2026-09-02 — THE MECHANISM IS FOUND, NAMED, AND FIVE OF THE 21 ARE CLOSED
--------------------------------------------------------------------------------

Bisected rather than reasoned about, exactly as step 1 above asks. 112
candidate files, halved four times:

    test_cov_14_settings_model.py ALONE    0

`tests/test_cov_11_measure.py` is the poisoner, on its own.

THE MECHANISM, and nothing in it looks wrong at the site:

`spacr.measure._ZERNIKE_AVAILABLE` is a module-level cache of "is Mahotas
importable", filled on first use. The file's `stub_mahotas` fixture puts a
FAKE Mahotas into `sys.modules`; a measurement taken while it is there fills
that cache with **True**. `monkeypatch` then removes the fake -- it restores
what it was asked to restore -- but THE CACHE IS NOT SOMETHING IT WAS ASKED
ABOUT, so True survives into a process where Mahotas does not exist.

Measured directly, with a probe test appended after that file:

    after test_cov_11_measure.py:   _ZERNIKE_AVAILABLE is True
                                    "mahotas" in sys.modules is False
    on its own:                     _ZERNIKE_AVAILABLE is None

Every later test that measures morphology then believes Zernike is available,
asks for it, and gets a frame with different columns. That is the whole of the
`test_measure_hooks.py` family.

THE FIX is an autouse fixture in the offending file that puts the cache back
after every test. File-local and autouse on purpose: the leak happens whenever
the cache is FILLED, which any test there can do -- including one added later
by someone who does not think it is about Zernike.

    113 files:   21 failed  ->  16 failed, 3,098 passed

A SECOND, UNRELATED BUG WAS FIXED IN PASSING and it was a real one.
`test_region_filter_removes_exactly_the_excluded_objects` also failed ALONE,
on `cell_second_neighbor_distance`. Its claim was that the survivors are
"measured exactly as they were" -- true of per-object measurements and false
of neighbourhood ones, which are computed over the objects PRESENT. Excluding
cells 2 and 4 changes cell 1's second-nearest neighbour, and it SHOULD: a
region filter exists to say those objects are not part of the analysis, so
counting an excluded object as a neighbour would report a density the user
filtered out. The assertion is now split in both directions -- per-object
columns identical, neighbourhood columns required to MOVE -- because asserting
only the first half would pass against a build that stopped computing
neighbours at all.

WHAT IS LEFT: 16, and they are not one family.
`test_measure_spawn.py` (3), `test_measure_3d.py` (4),
`test_measure_hooks.py` (still some), and one each from intermittent,
join_contracts, manager_guard and optional_zernike. Bisect them the same way;
the method above took about fifteen minutes for the first one.

THE GENERAL LESSON, worth more than the five tests: A MONKEYPATCHED IMPORT AND
A CACHE OF THAT IMPORT ARE TWO PIECES OF STATE, and restoring one does not
restore the other. Anywhere spaCR caches "is X installed", a test that fakes X
has to put the cache back too. `_ZERNIKE_AVAILABLE` is not the only such
cache.

2026-09-02 — THE SECOND POISONER, AND 21 IS NOW 4
--------------------------------------------------------------------------------

With the Zernike cache fixed, `test_measure_3d.py`'s four went and
`test_measure_hooks.py`'s ten remained -- a SECOND cause. Bisected the same
way, 112 files to one:

    first 27 files before measure_hooks    0 failures
    first 28                              10
    tests/test_cov_r8_measure_probes.py ALONE   10

THE MECHANISM. That file's `_reimport_measure()` deletes every module whose
name starts with `spacr.measure` from `sys.modules` so the capability probe
runs again -- which is a legitimate thing for it to test. The next import then
builds a NEW module object, and anything still holding the old one is talking
to a module the pipeline does not use.

`startswith("spacr.measure")` HAS NO DOT, so it also removes
`spacr.measure_hooks` -- WHICH IS WHERE THE HOOK REGISTRY LIVES.
`tests/test_measure_hooks.py` then registers its hooks through one copy and
runs a measurement that imports the other, which has no hooks registered at
all. Every hook test fails, and nothing fails where the mistake is.

THE FIX is an autouse fixture that restores the ORIGINAL module objects
afterwards, rather than forbidding the reload -- the reload is the point of
that file and the probe genuinely has to run twice.

AND THE FIRST VERSION OF THAT FIXTURE DID NOT WORK, which is worth recording
because it looked right. It restored `spacr.measure` and `spacr.measure.*` --
with the dot -- while the deletion used the dotless prefix. So it put the
module back and left `spacr.measure_hooks` rebuilt: the exact state that
caused the bug. THE RESTORE MUST USE THE SAME PREDICATE AS THE DELETION, and
the fixture now says so in a comment beside the function it mirrors.

BOTH CAUSES ARE THE SAME SHAPE, and it is worth stating once: A TEST THAT
FAKES AN IMPORT LEAVES TWO PIECES OF STATE BEHIND -- the import itself, which
`monkeypatch` restores, and everything DERIVED from it, which it does not. A
cached boolean in one case, a whole module object in the other. Anywhere
spaCR caches an import or reloads a module, the test that does it owns
putting both back.

2026-09-02 — THE THIRD WAS NOT AN ORDER PROBLEM AT ALL. 21 IS NOW 3.
--------------------------------------------------------------------------------

`test_direct_insert_matches_pandas_arrow_timedelta_encoding` failed ALONE,
which took it out of this item's own category and made it the cheapest of the
four to settle.

It is an UPSTREAM DEPRECATION surfacing as a failure because `pytest.ini`
turns warnings into errors. numpy 2.5 deprecates the generic timedelta unit;
pandas' `ArrowExtensionArray.to_numpy` builds its NA sentinel with one on the
way. spaCR is not the cause and does not have a fix available: `_insert_frame`
already asks for an explicit `dtype='timedelta64[ns]'`.

THE EVIDENCE THAT IT IS UPSTREAM is in the traceback rather than in an
argument: the same DeprecationWarning is raised by the test's own
`pd.Series([...], dtype='duration[us][pyarrow]')`, before any spaCR code runs.

A filter scoped to that one test, naming the cause and saying when to remove
it. Not a code change, because there is no spaCR behaviour to correct.

    test_measure_crop_checks_the_start_method_before_it_starts_the_pool

THE HYPOTHESIS WORTH TESTING FIRST, from the second name: multiprocessing. A
reloaded `spacr.measure` re-runs whatever module-level work sets up the pool
or records the start method, while an earlier import of the same module left a
Pool, a start-method decision or a registered initializer behind. Both
surviving failures are about the pool and about work done BEFORE features are
computed, which is the same phase.

WHAT NOT TO DO: do not widen the fixture's restore further without a
measurement saying what else is stale. The first version of it was widened by
guess -- the dot in the prefix -- and put the module back while leaving
`spacr.measure_hooks` rebuilt, which is the bug it was written to fix.

HOW TO FIND IT: the technique changes from bisecting FILES to bisecting STATE.
Add a probe test after the pair, as was done for `_ZERNIKE_AVAILABLE`, and
print the module-level names those two tests read -- the start method, any
pool handle, the hook registries, and the identity of every `spacr.measure*`
module. Compare the values with and without the earlier file. The Zernike
cause was found in one such probe.
