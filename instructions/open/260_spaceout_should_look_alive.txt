0. FLYING THROUGH FRACTAL SPACE            <-- THIS REPLACES THE BUDDING
--------------------------------------------------------------------------------

"i want it to look like the user is continuously mooving through fractal
space", with a video as the reference.

THE VIDEO WAS NOT WATCHED. Whoever builds this should say so too rather
than pretend otherwise. What is written here is the shape the words
describe, and the maintainer is the one who says whether it is right --
so BUILD A SHORT RECORDING AND SHOW IT rather than describing what was
done. The gap between "continuous movement through fractal space" and any
particular rendering of it is exactly the kind of thing that costs a
round trip.

WHAT THE WORDS DESCRIBE, as a starting point:

  * CONTINUOUS FORWARD TRAVEL. The camera never arrives and never stops.
    Structure appears small ahead, grows as it is approached, and passes
    the viewer. That is the whole effect: it is a JOURNEY, not an object
    being watched;
  * IT NEVER VISIBLY REPEATS. A fractal is self-similar at every scale,
    which is what makes endless travel possible -- each scale reveals the
    next. If a watcher can see the loop point, the illusion is gone;
  * THE STRUCTURE IS THE THING, not a shape sitting in the middle of the
    screen. What was drawn before was a form with a backdrop; this is the
    inside of something the viewer is passing through;
  * a slow drift or roll of the camera is usual and helps, so long as
    the forward motion stays the dominant sense.

WHAT THIS RETIRES from the previous pass:

  * THE BUDS GO. Bubbles budding off a central form is a thing being
    watched, which is the opposite of travelling through;
  * THE BEAT GOES, or becomes very much quieter. A pulse says "this is an
    organism in front of you"; steady motion says "you are moving";
  * THE VORTEX STAYS IN SPIRIT and changes in kind: it was a 3-D effect
    INSIDE a form on the screen, and what is wanted is the viewer being
    inside it.

WHAT IS KEPT from everything below: the higher resolution, the buffer
matching the screen, the drifting palette, the more-rainbow text, the
oscillating cursor accent, the preferences page, and every rule about the
contrast check and the performance guard. Those were not the complaint.

--------------------------------------------------------------------------------
0b. THE FRACTAL RUNS ON THE GPU, AND YIELDS IT
--------------------------------------------------------------------------------

WHY THE GPU AT ALL. The backdrop currently renders into a 256-pixel buffer
in Python and scales it up, which is exactly why it looks coarse and why
"higher resolution" is expensive. A fragment shader renders at the display's
own resolution for almost nothing, and a raymarched distance field is what
makes a flythrough possible at all.

MEASURED BEFORE COMMITTING TO IT, so the known traps are not rediscovered:

  * PySide6 here is 6.11.2. In Qt 6 `ShaderEffect.fragmentShader` takes a
    URL to a PRE-COMPILED `.qsb`, not inline GLSL. `pyside6-qsb` is
    installed, so the pipeline exists. Inline GLSL source FAILS SILENTLY --
    loading such a QML reports `Status.Ready` with no errors and simply
    never draws, which is the worst failure mode available;
  * `QQuickWidget` renders NOTHING under `QT_QPA_PLATFORM=offscreen`.
    Measured: the framebuffer comes back null. spaCR's whole suite runs
    offscreen, so anything that only exists on the GPU path cannot be
    tested the way everything else here is tested;
  * QQuickWidget is a near-native surface and does not always compose well
    UNDER other widgets. The backdrop sits behind the entire application.
    Check that early rather than discovering it late.

SO: BOTH ENGINES, NOT ONE.

    GPU shader   where a working context exists -- native resolution, a
                 real raymarched flythrough, no Python in the frame loop
    CPU engine   headless, remote X, a VM, no GPU -- and it is what the
                 tests drive

The quality page from section 1 chooses between them, so a machine that
cannot afford the shader turns it off rather than enduring it.

--------------------------------------------------------------------------------
0c. A RUN TAKES THE GPU BACK, AND NOTHING SNAPS
--------------------------------------------------------------------------------

"when the user hits run ... the fractal background either gracefully auto
switches to the CPU version or turns the fractals off (this should be a
setting). and the fractal shouldnt just die abruptly it should wind down and
wind up the cpu version or not wind up at all."

THE RUN COMES FIRST, ALWAYS. Segmentation and classification are what the
GPU is for; a backdrop holding VRAM and shader cycles while Cellpose loads
is the animation competing with the work. The house rule already says the
GPU drives the display and must not be taken wholesale -- this is the same
rule pointed at spaCR's own animation.

WHAT HAPPENS WHEN RUN IS PRESSED, as a setting:

    hand over    the GPU shader winds DOWN, and the CPU engine winds UP in
                 its place. The backdrop keeps going, quieter and cheaper.
    stand down   the GPU shader winds down and nothing replaces it. The
                 backdrop is simply absent until the run ends.

NEITHER OF THEM CUTS. "Wind down" means the motion slows and the image
fades over a visible interval rather than vanishing between two frames --
a backdrop that disappears mid-stride reads as a crash, which is the exact
impression to avoid at the moment a long run begins. Winding up is the same
in reverse, so the CPU engine arrives rather than appearing.

AND IT COMES BACK. When the run finishes -- or fails, or is cancelled -- the
backdrop returns the way it left: the CPU engine winds down, the shader
winds up. A run that ends badly must not leave the application permanently
plain, and a run cancelled two seconds in must not leave two engines
running at once.

THINGS THAT WILL GO WRONG IF NOT DESIGNED FOR:
  * two runs in a row, or a run started while the previous wind-up is still
    in progress. The transition must be interruptible and must not stack;
  * a run that crashes the worker -- the backdrop still has to come back;
  * the wind-down must not itself block the GUI thread at the very moment
    the run is starting, or the fix costs the thing it was protecting.

--------------------------------------------------------------------------------
1. HIGHER RESOLUTION
--------------------------------------------------------------------------------

The backdrop renders into a buffer capped by `BUFFER_MAX_EDGE = 256` in
`ambient.py`, then scales up -- which is where the coarseness comes from.
`BUFFER_EDGE_CEILING` is 2048 and `BUFFER_MAX_PIXELS` is 1920x1080, so
there is room above the cap without touching the ceilings.

RAISE IT FOR THIS ENGINE ONLY. The blob engine's cap is tuned for what the
blobs need; a fractal carries detail at every scale and is the one thing
that shows the buffer's edge. Whatever number is chosen, the existing
PERFORMANCE GUARD still decides -- see below.

THE BUFFER'S CEILING IS THE SCREEN. `BUFFER_MAX_PIXELS` is written as
`1920 * 1080` -- a guess at a monitor rather than a measurement of one. It
should be THE ACTUAL SCREEN'S resolution, read from Qt, so the backdrop is
never rendered coarser than the display can show and never finer than it
can use.

Two things that follows from, both of which have to be handled rather than
discovered later: a 4K display asks for four times the pixels of the guess,
and a multi-monitor setup has no single answer -- take the screen the window
is actually on, and cope with it moving to another one.

AND IF THAT IS TOO MUCH FOR SOME MACHINES, SAY SO IN PREFERENCES. The
maintainer: "if this is computationally intense in this mode there should be
a special preferences page for the themes settings for users that have worse
hardware than i."

The knobs already exist and are already stored -- `get_ambient_resolution`,
`get_ambient_blur`, `get_ambient_speed`, `get_ambient_density` in
`spacr/qt/preferences.py`, each a multiplier on what the theme does. What is
missing is a PAGE that offers them, so a slower machine can turn the
backdrop down instead of enduring it.

THIS DOES NOT REOPEN THE SPACEOUT RULE. What must never appear in
Preferences is the MODE -- no entry that puts an ordinary `spacr` start into
the fractal theme. Quality knobs for the backdrop are a different thing and
belong there: they apply to the blobs as much as to the fractals, and a user
who cannot afford the animation needs them whichever one is drawing.

--------------------------------------------------------------------------------
2. BUDDING, AND MORE THAN ONE THING ON SCREEN
--------------------------------------------------------------------------------

  * BUBBLE FRACTALS BUD OFF the main form -- they separate from it rather
    than fading in somewhere else;
  * SOMETIMES there is more happening than the thing in the middle. Not
    always: the point is variation, so a screen with one form and a screen
    with several are both states it passes through;
  * a bud is the same kind of thing as its parent, at its own scale, with
    its own life -- it drifts, it turns, and it goes.

--------------------------------------------------------------------------------
3. A VORTEX INSIDE EACH FORM
--------------------------------------------------------------------------------

"inside of the elements on screen (the main and budded) there should be a
3D effect so it looks like you are looking into a vortex of turning
fractalls."

So each form is not a flat shape: looking at one is looking INTO it, down a
turning tunnel. The buds have it too, not only the main form.

--------------------------------------------------------------------------------
4. IT BEATS, AND IT IS NOT ALWAYS THE SAME
--------------------------------------------------------------------------------

"a beating living pattern generator ... sometimes deep 3D vortex and
somtimes not."

THIS IS THE HEART OF THE REQUEST and the easiest part to get wrong. A loop
that always does the same thing at the same rate does not read as alive; it
reads as a screensaver. What is wanted is a thing with STATES it moves
between -- deep and flat, busy and quiet, fast and slow -- on its own,
without repeating on a period a watcher can learn.

  * a beat: the whole form pulses rather than drifting evenly;
  * transitions between states are gradual, not cuts;
  * the sequence is not a fixed cycle. Randomness that never repeats the
    same order is what separates living from looping.

--------------------------------------------------------------------------------
5. THE PALETTE DRIFTS
--------------------------------------------------------------------------------

"its color pellet should gradually shift and change randomly as well."

The whole palette moves through hue space over time, gradually and without
a fixed loop -- and the TEXT goes further towards rainbow than it does now
("pretty good but could be more rainbow like").

THE CONTRAST RULE IS NOT SUSPENDED FOR THIS. A palette that drifts must
pass the same readability check at every point on its drift, not only where
it started. That check already exists -- the colourblind work used it -- and
a drifting palette makes it a per-frame property rather than a one-off. If
holding the check costs some saturation, hold the check: a trippy theme
that cannot be read is a broken theme.

--------------------------------------------------------------------------------
6. THE THING THAT FOLLOWS THE CURSOR OSCILLATES
--------------------------------------------------------------------------------

"the little blue window thing that follows the mouse should also osilate in
color under this special theme."

Identify it first -- the accent that tracks the cursor is aimed by
`_aim_at_the_cursor` in `spacr/qt/widgets/setup_card.py`, which reads the
GLOBAL cursor position rather than receiving events, so it follows the mouse
even outside the window. Confirm that is the thing the maintainer means
before changing it; if there is a second cursor-following mark elsewhere,
say which one you changed.

Under spaceout its colour oscillates. Under an ordinary start it does not
change at all.

--------------------------------------------------------------------------------
STILL ONLY THROUGH spaceout
--------------------------------------------------------------------------------

Every one of these is dressing on the same application, reachable only by
starting it with `spaceout`. Nothing in Preferences offers any of it, no
stored value can put an ordinary `spacr` start into it, and the theme
contract -- `resolve_effective_theme`, light and dark -- is untouched.

THE PERFORMANCE GUARD STILL DECIDES. Higher resolution, buds, a vortex and
a drifting palette are all more work per frame. The ambient animation
already answers to a guard; this answers to the same one, and where the
machine cannot afford the full thing it degrades -- fewer buds, a smaller
buffer -- rather than stuttering. A launcher that makes the application
stutter is worse than no launcher.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * the buffer edge for this engine is larger than the blob engine's, and
    the guard still caps it on a machine that cannot afford it;
  * over a run of frames, the number of forms on screen CHANGES -- a
    measurement that finds exactly one every time has not got budding;
  * a bud's pixels are traceable back to the parent it left;
  * sampling the same form's centre over time shows it turning, not static;
  * over a long run the state sequence does not repeat on a fixed period;
  * the palette's hue at frame N differs from frame 1, and EVERY sampled
    frame passes the contrast check;
  * the cursor accent's colour differs between two frames under spaceout
    and is constant under an ordinary start;
  * nothing in Preferences offers any of it.


================================================================================
SECTION 0B -- THE SCRIPT THE MAINTAINER SUPPLIED, 2026-08-27
================================================================================

Supersedes the budding-and-beating direction entirely. The maintainer handed
over `fractal_travel.py` v2.1.0 and asked for it, or the code from it, to be
what spaceout draws.

WHAT IT IS. Two renderers, not one engine with a switch:

  * GPU -- VisPy/gloo with a GLSL fragment shader, four spatial samples per
    physical pixel (2x2 SSAA), detail loop adapting between 5 and 9 octaves
    from sampled GPU time against the frame period.
  * CPU -- a cheaper orbit-fold fractal in Numba (`njit(parallel=True)`),
    rendered at animation rate with a FOUR-POSITION TEMPORAL 2x2 jitter and a
    rolling four-frame accumulation. No keyframes and no crossfades. Capped
    at 30 FPS because every displayed frame is newly evaluated, and the
    internal pixel count adapts to hold about 78% of the frame period.

WHAT MUST CHANGE FROM THE SCRIPT AS GIVEN:

  * IT IS PyQt6 AND SPACR IS PySide6. Signal/Slot, the enum spellings, and
    `vispy.app.use_app('pyside6')` all move. A stray PyQt6 import inside the
    Qt application is two Qt bindings in one process, which segfaults.
  * `numba` is present (0.67.0). `vispy` is NOT INSTALLED in the shipped
    environment, so the GPU path must degrade to CPU rather than raise --
    which `backend='auto'` already does -- and the GPU path must be written
    so it starts working the day vispy is installed, with nothing else
    changed.

REQUIREMENTS THE SCRIPT DOES NOT ALREADY MEET:

  * WIND DOWN WHEN A RUN STARTS, gracefully. A background eating cores while
    a segmentation runs is the opposite of what it is for. The render thread
    stops and the last frame stays on screen; it resumes when the run ends.
  * PREFERENCES, and ONLY IN SPACEOUT. scale, speed, quality, dream,
    backend, and a VARIABLE SPEED option. The rows must not appear in an
    ordinary launch.
  * OFF THE MAIN THREAD wherever possible. The CPU renderer already owns a
    QThread; the GUI thread must never evaluate a fractal.

DEFAULTS, exactly as given:

    gpu:  --backend gpu --quality auto              --speed 4.0 --dream 1.5
    cpu:  --backend cpu --quality balanced --scale 1.0 --speed 4.0 --dream 1.5

Prefer the GPU renderer when it works.

HOW TO KNOW IT WORKED:

  * spaceout draws the supplied fractal, and an ordinary launch does not;
  * with vispy absent the CPU renderer runs and says which backend it is on;
  * starting a run stops the rendering and the interface stays answerable;
    ending one resumes it;
  * the six settings exist in Preferences under spaceout and change the
    picture; they are absent otherwise;
  * no PyQt6 symbol is imported anywhere in the shipped package.
