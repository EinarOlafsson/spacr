================================================================================
A TOOLTIP APPEARS OVER THE SETTING, NOT OVER ITS FIELD
================================================================================

Status:    DONE 2026-08-15, 155 -> 0. The DIAGNOSIS in WHY IT HAPPENS is
           WRONG and is kept only as a record; THE REAL SCOPE and RESULT at
           the end are what happened.
Requested: 2026-08-15 - "add to instructions, tooltips should only appear whe
           the mouse is hovered over the setting not the field for the
           setting."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Hovering the input for a setting -- the spin box, the combo, the text field --
pops the setting's help. It should pop only over the setting's NAME.

This is not an undecided question. `install_api_tooltips` already says so in
its own docstring:

    "Descriptive help belongs to the label, not the editable field; a compact
     teal dot immediately beside that label opens the API page."

So the intent is already written down and the code does something else. That
makes this a defect, not a design change.

WHY IT MATTERS beyond taste: a tooltip over the field covers the field. The
user is hovering there because they are about to type in it, and the help
they have already read pops up over the thing they are aiming at. Help
belongs where you go to ASK, not where you go to ANSWER.

--------------------------------------------------------------------------------
WHY IT HAPPENS
--------------------------------------------------------------------------------

`spacr/qt/screens/settings_model.py`, in `install_api_tooltips`:

    html = attach_api_tooltip(widget, app_key, key, ...)   # the FIELD
    label = _setting_label_for_field(owner, widget)
    ...
    label.setToolTip(html)                                  # the LABEL

`attach_api_tooltip` is called on the field because that is what computes the
html and stamps the `settingKey` / `apiTooltipHtml` / `settingsAppKey`
properties other code reads. But it ends with

    widget.setToolTip(html)
    widget.setToolTipDuration(-1)

so the field keeps a tooltip as a side effect of being the thing that carries
the metadata. Then the label gets the same html, and both hover.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. WHEN A LABEL IS FOUND, CLEAR THE FIELD'S TOOLTIP. Keep every property on
   the field -- `settingKey`, `apiTooltipHtml`, `apiTooltipDescriptionSource`
   and the rest are read by the tooltip refresh pass, the i18n retranslation
   sweep and the API-dot builder, and stripping them would break all three.
   It is only `setToolTip("")` on the field, after the label has taken it.

   Do NOT do this by not calling `attach_api_tooltip` on the field. That
   function is where the html and the properties come from.

2. DO NOT TOUCH THE ONE-WIDGET ROW. A Toggle or QCheckBox carries its own
   visible text and has no separate label -- `_setting_label_for_field`
   returns None and the code deliberately installs hover on the widget
   itself. For those, the widget IS the setting name, so hovering it is
   correct and must keep working. The rule is "hover the name", not "never
   hover a control".

3. THE API DOT IS UNAFFECTED. It sits beside the label and opens the API
   page; it is not a tooltip target and should keep behaving as it does.

4. CHECK THE OTHER SETTERS IN THAT FILE. There are several `setToolTip` calls
   around lines 3048-3156 -- the disabled-reason note, the caption path.
   Establish which of those land on a field, because a rule that holds only
   in `install_api_tooltips` will be re-broken by whichever one was missed.
   The disabled-reason note in particular ("this setting does nothing
   because...") may be the one case where the FIELD is the right target,
   since it explains why that control is greyed -- if so, say that here
   rather than making it an exception someone later deletes as an
   inconsistency.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Hovering a setting's NAME shows its help.
* Hovering that setting's spin box / combo / line edit shows NOTHING.
* A Toggle or checkbox that carries its own text still shows help on hover,
  because there its text is the name.
* The teal API dot still opens the API page.
* The i18n retranslation sweep and `refresh_api_tooltips` still find every
  setting -- i.e. the properties are intact and only the tooltip string was
  cleared. The existing tooltip tests (`test_tooltip_length_and_shape.py`,
  `test_tooltip_api_links_resolve.py`) still pass.
* A test asserts the field's `toolTip()` is empty while its label's is not,
  so this cannot regress silently the next time the decoration pass changes.

================================================================================
THE REAL SCOPE: THE GENERIC PATH IS ALREADY CORRECT
================================================================================

`install_api_tooltips` does NOT leave a tooltip on the field. It already ends:

    # The editor itself remains quiet on hover. Keep its metadata so tests,
    # integrations and a later re-parenting pass can still identify it.
    widget.setProperty("apiTooltipDisplayRole", "metadata")
    widget.setToolTip("")

and has since a3a1d56f (2026-07-30). The "clear the field's tooltip" fix this
file proposed is already in the tree. Anything hovering a field is NOT coming
from there.

WHERE IT IS ACTUALLY COMING FROM: hand-built screens that call `setToolTip`
on their own fields, never having gone through the generic decorator. There
are 510 `setToolTip` calls across `spacr/qt/screens` and `spacr/qt/widgets`.
Most are legitimate -- buttons, API dots, links, elided labels, and toggles
that carry their own text. A minority are on editable fields that have a
separate label, and those are this instruction.

Confirmed offenders so far:

    hyperparam.py:777        edit.setToolTip(lab.toolTip())
                             -- copies the LABEL's help onto the field, which
                                is this defect performed deliberately
    hyperparam.py:1061       plot_label.setToolTip(self._max_panels.toolTip())
                             -- reads a field's tooltip to build a label's
    distributed_jobs.py      ~8 fields given tooltips directly
    distributed_jobs.py:292  help_text = field.toolTip() or ...
                             -- reads the field as the carrier

That last pattern matters: two screens READ `field.toolTip()` to populate a
label. Clearing fields without fixing those readers turns their labels blank.
They must read `widget.property("apiTooltipHtml")` first, which is the
canonical carrier and survives the field's tooltip being cleared.

THE ONE DEFENSIBLE EXCEPTION, and it should stay:

    gate_settings.py:805  appends "NOT YET IN EFFECT: the 3D volume is not
                          built (instruction 52)" to the FIELD's tooltip.

That is a disabled-reason, not descriptive help. It explains why THAT CONTROL
does nothing, so the control is the right place for it -- the same argument
instruction 106 (inapplicable settings are greyed out and say why) is built
on. Keep it, and keep it distinguishable from help so a later sweep does not
delete it as an inconsistency.

--------------------------------------------------------------------------------
HOW TO DO IT WITHOUT AUDITING 510 CALL SITES BY EYE
--------------------------------------------------------------------------------

Write the detector first, then fix what it finds. Build each settings screen
and dialog, walk its form rows, and for every row that has BOTH a label and
an editable field, assert the field's `toolTip()` is empty. That is the whole
rule, it is mechanical, and it is the only version of this that does not rot:
a hand-built screen added next month will fail the guard rather than
reintroducing the defect silently.

Exempt, in the detector and for stated reasons:
  * a control that IS its own label (Toggle, QCheckBox with text) -- hovering
    it is hovering the name;
  * a field whose tooltip is a disabled-reason (see gate_settings above),
    which needs a property to mark it as such rather than a filename
    allowlist.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED (REVISED)
--------------------------------------------------------------------------------

* The detector runs over every settings screen and dialog and reports zero
  editable-field-with-a-separate-label carrying a tooltip.
* Hovering a setting's name still shows its help everywhere.
* The two screens that read `field.toolTip()` to build a label still show
  their labels' help -- i.e. they were moved onto `apiTooltipHtml` before the
  fields were cleared, not after.
* The gate-settings "NOT YET IN EFFECT" note still appears on its control.

--------------------------------------------------------------------------------
RESULT (2026-08-15) -- 155 -> 0
--------------------------------------------------------------------------------

MEASURED FIRST, because "audit 510 setToolTip calls by eye" was never going to
finish. A detector builds every screen that constructs with no arguments (64
of them) and counts editors that carry a tooltip AND have a label naming them:

    before   155 offenders across 28 screen classes
    after      0

`settings_model.retarget_field_tooltips(root)` is the mechanism: one post-pass
called at the end of a hand-built screen's ``__init__``, rather than 155 edits
and a convention every future row has to remember. It moves the tooltip onto
the sibling label (positionally identified -- these screens use form layouts,
grids and plain rows interchangeably, but they all put the name to the left of
the editor) and clears the field.

Three things it leaves alone, each for a stated reason:

  * a field with NO sibling label -- the editor is the setting's only visible
    identity there, so its tooltip is the only help that exists;
  * a label that already has its own tooltip -- decorated properly already,
    and overwriting would lose the richer text;
  * a tooltip marked `DISABLED_REASON_TOOLTIP` -- "this control does nothing
    because ..." explains THAT control, so it belongs on it. This is the
    gate_settings "NOT YET IN EFFECT" case, now expressible as a property
    rather than as a filename exception.

QCheckBox and Toggle are not editors for this purpose: they carry their own
text, so they ARE the name and hovering them is correct.

tests/test_tooltips_are_on_the_setting_not_the_field.py is a SWEEP guard, not
an example: it re-runs the detector over every screen and fails naming the
offending class, so a screen added next month cannot reintroduce this
quietly. It also asserts it built more than 40 screens, because a green sweep
that covered nothing would prove nothing.
