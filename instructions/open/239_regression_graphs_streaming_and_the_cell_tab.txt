1. GRAPH TYPE, ON THE RIGHT-CLICK MENU OF EVERY PLOT      <-- ASKED MANY TIMES
--------------------------------------------------------------------------------

Verbatim: "in regression, i have asked many times at this point for an
option when i right click on a graph, called graph type that would allow
the user to switch between graph types. but still you have not implemented
this... please this time implement this, and i want this for all graphs in
the core modules, really for all matplotlib graphs in the software."

SCOPE IS EVERY PLOT, not the regression panel alone. A right-click menu
entry named "Graph type" with the alternatives that make sense for the data
on that axis -- bar/box/violin/strip for a per-group distribution,
line/scatter for a series, and so on -- switching in place.

Note before starting: spaCR's figures do NOT all come from matplotlib.
`spacr/ml.py` draws through pyqtgraph (see `_draw_*_in_pyqtgraph`) and the
rest write through `figures.scene`. So "all matplotlib graphs" means every
plot the user sees, and the menu has to be installed at the ONE seam both
back ends pass through, or it will be added to half of them again.

3. ONE CROP, WHATEVER CUT IT                              <-- ASKED BEFORE
--------------------------------------------------------------------------------

"with the streaming you need to make sure that all methods generate the
same single crop images. so the coordinate table (which also must use the
cell_id or object_number to name the png it generates), object id in array
method and png crop during measure_crop should all generate the exact same
files named with the same object number."

Three producers, one result required:
  a. `measure_crop`'s PNG export,
  b. the ARRAY method (label plane scanned for the object),
  c. the COLUMN/coordinate method (bbox read from the database).

Same pixels AND same filename, and the filename carries the object number.
The coordinate method is the one named as wrong today: it must name its PNG
from `cell_id` / the object number like the other two.

Already verified on 2026-08-23: (a) and (b) are byte-identical on plate1.
(c) is NOT yet compared, and its naming is the open defect.

4. JOINING THE MEASUREMENTS TABLE HANGS SPACR
--------------------------------------------------------------------------------

"pressing join the measurements table in the cell tab in the regression
module makes spacr unresponsive"

A join on a real screen is long work on the GUI thread. It belongs on a
worker with progress and a cancel, like every other long run.

5. THE JOIN WARNS ABOUT 60,095 OF 60,816 OBJECTS
--------------------------------------------------------------------------------

    the same column arrived from two tables with different values for the
    same object:
      'object_label': 60095 of 60816 objects disagree between cell and
      pathogen (e.g. prcfo 0, 1, 2, 3, 4)

This is not a corruption: a cell's object_label and a pathogen's
object_label are DIFFERENT OBJECTS' labels and there is no reason they
should agree. The warning is comparing two columns that were never the same
quantity, so it fires on every healthy screen and says something alarming.
Either exclude the object key from the disagreement check (it is the join
key, not a measurement) or say what it really means.
