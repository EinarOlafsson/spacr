================================================================================
AN UNAVAILABLE OPTION OFFERS TO MAKE ITSELF AVAILABLE
================================================================================

Status:    filed 2026-08-18.
Requested: 2026-08-18 --

  "I want all of these to be options, just add some text in the tooltip about
   each: install spacr with python 3.11 or 12 then pip install cuML or whatever
   the user needs to do. If it is not available it should be greyed out, if it
   is available it should [be] clickable. Even better would be if when the user
   clicks unavailable options that need cuML they get prompted to install cuML
   in the conda environment spacr is on, can that be made? If so I want that
   for image UMAP as well. As for the other problematic packages, include them
   but include an instruction in the api for how to make them available.
   Including the one that needs R."

Related: 141 is the backend inventory. 106 is the greying rule. 95/109 are the
         Image UMAP. `spacr/gpu_reduce.py` already decided cuML is an EXTRA.

READING NOTE: the request says "if it is available it should not be clickable",
which is a slip for the obvious opposite -- available means CHOOSABLE. Recorded
so nobody builds the sentence rather than the intent.

--------------------------------------------------------------------------------
A. CAN IT BE MADE? YES, AND spaCR ALREADY HAS THE PARTS.
--------------------------------------------------------------------------------

Nothing new has to be invented:

  * `spacr/updater.py` ALREADY installs into spaCR's own environment --
    `find_uv()`, `upgrade_command()`, `run_pip_upgrade()` -- and already
    handles the case its docstring names: an install where `python -m pip`
    fails because pip was never seeded, which is why `uv` is looked for first.
  * `spacr/doctor.py` already reports the interpreter and `sys.prefix`, so the
    environment a prompt would install INTO is already known and already shown.
  * `spacr/gpu_reduce.py` already has the availability pattern: importable AND
    a device present, with the CPU path staying the answer otherwise.

So the work is a shared "offer to install this" flow, not an installer.

--------------------------------------------------------------------------------
B. THE CASE THAT MUST NOT OFFER TO INSTALL, AND IT IS cuML's
--------------------------------------------------------------------------------

THIS IS THE PART THAT WOULD BE WRONG IF BUILT NAIVELY. Measured 2026-08-18:

    cuml-cu12 26.8.0   requires_python >= 3.11, and the recent wheels are
                       cp311 ONLY: 25.10/25.12/26.2 shipped cp310-cp313,
                       26.4/26.6/26.8 ship cp311 alone. The window is
                       NARROWING.
    also wants         numpy>=2.0,<3.0, numba<0.65, scipy>=1.14, sklearn>=1.6

    in the default `spacr` env (python 3.10, numpy 1.26.4):
        CANNOT BE INSTALLED AT ALL at 26.x. Resolving anyway drags numpy
        1.26.4 -> 2.2.6 and downgrades numba and llvmlite.
    in `spacr12` (python 3.12, numpy 2.4.6): numpy is untouched, but it still
        downgrades numba 0.66 -> 0.64, llvmlite 0.48 -> 0.46,
        cuda-bindings 13.3.1 -> 12.9.7, cuda-toolkit 13.0.3 -> 12.9.2,
        and moves pandas 2.3.3 -> 3.0.3.

SO ON THE INTERPRETER spaCR IS USUALLY RUN ON, "pip install cuml" IS NOT THE
REMEDY AND MUST NOT BE OFFERED AS ONE. The remedy is a different environment.
A prompt that runs pip here either fails, or succeeds at breaking the install
-- and the second is worse, because the user asked for a faster lasso and got
a numpy major upgrade under an image-analysis stack.

THE PROMPT THEREFORE HAS THREE ANSWERS, NOT TWO:

  1. INSTALLABLE HERE -- offer it, name the exact command, say what it will
     change (the dry-run report already computes this), and install on
     confirmation.
  2. NOT INSTALLABLE HERE, BUT POSSIBLE ELSEWHERE -- say what environment
     would take it and how to make one, and do NOT run anything:
     "cuML needs Python 3.11; this spaCR is on 3.10. Create an environment
     with `conda create -n spacr311 python=3.11`, install spaCR there, then
     `pip install cuml-cu12`."
  3. NOT POSSIBLE -- say so, with the reason. pymer4 is this: see D.

AND ALWAYS SHOW THE DRY-RUN BEFORE INSTALLING. `pip install --dry-run
--report` is what caught cuML, and a user is entitled to see "this will move
numpy 1.26.4 -> 2.2.6" BEFORE agreeing rather than after. An install that
changes a package spaCR already depends on is REFUSED by default and needs a
second, explicit confirmation naming what moves.

--------------------------------------------------------------------------------
C. WHERE IT APPEARS, AND IT IS MORE THAN THE BACKENDS
--------------------------------------------------------------------------------

"If so I want that for image UMAP as well."

So this is ONE shared control, not a backend feature: a greyed option that
knows why it is greyed, what would ungrey it, and whether it can do that here.
The two callers today are the regression backend picker (141) and the Image
UMAP's GPU acceleration (`gpu_reduce`, which already offers cuML for UMAP,
t-SNE, PCA, DBSCAN and KMeans and already decided it is an EXTRA). Build it
once, in a place neither owns, and let both ask.

EVERY ENTRY IS PRESENT, ALWAYS. Per the request and per instruction 106:
nothing is hidden because it is unavailable -- a missing option cannot explain
itself, and a user cannot ask for what they cannot see. Greyed, with the
reason ON the entry.

--------------------------------------------------------------------------------
D. THE ONES THAT CANNOT SIMPLY BE INSTALLED, WRITTEN INTO THE API DOCS
--------------------------------------------------------------------------------

"include them but include an instruction in the api for how to make them
available. Including the one that needs R."

  * pymer4 / lme4 -- NEEDS R. Measured 2026-08-18: the 0.9.2 wheel declares NO
    dependencies at all, which is why a dry-run reported one additive package;
    installed, it fails at `pymer4/io.py: import polars`, and every module
    under `pymer4/models/` opens with `from rpy2.robjects.packages import
    importr`. 141 said otherwise and 141 was wrong.
    THE API PAGE STATES THE REAL RECIPE: an R installation, `lme4` and
    `lmerTest` inside it, `rpy2`, then `pymer4` -- and says plainly that this
    is a heavier ask than the other backends, so a reader can decide before
    starting rather than halfway through.
  * cuML -- the environment recipe from B.2, plus the CUDA 12 pin and the
    pandas 3 jump it brings in `spacr12`.
  * numpyro / gpytorch -- installable, and they return a DIFFERENT ANSWER
    (posteriors, not point estimates plus standard errors). The docs say that
    first, because a user installing them to go faster has misunderstood what
    they are for.

--------------------------------------------------------------------------------
E. AND SAY WHAT IT COSTS TO USE, NOT ONLY TO INSTALL
--------------------------------------------------------------------------------

A backend that is installed and choosable still has to keep 141 D: it agrees
with statsmodels to a stated tolerance, or the box says what differs. cuML's
penalised path is the live example -- two coordinate-descent implementations
at the same alpha can SELECT DIFFERENT VARIABLES, which is a different answer
and not a tolerance. `gpu_reduce` already says the same of cuML's UMAP not
being bit-identical. Neither may become available quietly without that
sentence travelling with it.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Every backend and every GPU accelerator is VISIBLE in its control, greyed
  when unavailable, with the reason and the remedy on the entry.
* Clicking a greyed entry that CAN be satisfied here offers the install, shows
  what the install will change first, and installs on confirmation.
* Clicking one that cannot -- cuML on Python 3.10 -- explains the environment
  it needs and runs NOTHING.
* An install that would move numpy, torch, pandas or scikit-learn is refused
  by default and needs a second confirmation naming what moves.
* The same control serves the regression backends and the Image UMAP.
* The API docs carry a working recipe for pymer4-with-R, for cuML, and for
  numpyro/gpytorch, each saying what it costs and what differs.
