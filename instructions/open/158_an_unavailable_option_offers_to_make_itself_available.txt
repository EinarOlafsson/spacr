AN UNAVAILABLE OPTION OFFERS TO MAKE ITSELF AVAILABLE
================================================================================

Status:    filed 2026-08-18.
Requested: 2026-08-18 --

  "I want all of these to be options, just add some text in the tooltip about
   each: install spacr with python 3.11 or 12 then pip install cuML or whatever
   the user needs to do. If it is not available it should be greyed out, if it
   is available it should [be] clickable. Even better would be if when the user
   clicks unavailable options that need cuML they get prompted to install cuML
   in the conda environment spacr is on, can that be made? If so I want that
   for image UMAP as well. As for the other problematic packages, include them
   but include an instruction in the api for how to make them available.
   Including the one that needs R."

Related: 141 is the backend inventory. 106 is the greying rule. 95/109 are the
         Image UMAP. `spacr/gpu_reduce.py` already decided cuML is an EXTRA.

DECIDED 2026-08-18, after two rounds of clarification. THIS SUPERSEDES the
custom-delegate options this file carried before; do not build those.

  "if it is NOT available it should not be clickable, only the install"
  "instead could we put the install in the tooltip? so the field is grayed out
   when it is not available. and in the tooltip everything is explained and the
   API is linked to and to the right of the API link there is an install which
   prompts the install, is this possible?"

YES, WITH ONE SUBSTITUTION, and it is a better design than the delegate routes
because the greyed entry stays HONESTLY dead -- unselectable, unpressable -- and
everything interactive moves to the hover panel where it can be interactive.

MEASURED 2026-08-18, PySide6, three probes:

  1. A DISABLED COMBO ITEM KEEPS ITS TOOLTIP.
         row 1: enabled=False  tooltip='tooltip for cuML (GPU)'
     So hovering an unavailable backend can show something. This is the half
     the whole design rests on and it works.

  2. A REAL QToolTip CANNOT CARRY A CLICKABLE LINK.
         QToolTip has a linkActivated signal:  False
         QToolTip is a QWidget:                False
     `QToolTip` is a STATIC PAINTER, not a widget. It renders rich text, and
     nothing in it can be clicked, hovered or focused. So "an install link in
     the tooltip" cannot be `QToolTip` -- and a naive attempt renders a link
     that LOOKS pressable and is not, which is instruction 106's inert control
     yet again.

  3. THE ROUTE THAT DOES WORK.
         QLabel.linkActivated exists:            True
         a link can be routed to an action:      ['install']
     A frameless, tooltip-styled QLabel with `Qt.TextBrowserInteraction`,
     shown on hover and kept alive while the pointer is over IT rather than
     over the row. Its `linkActivated` carries the href, so "api" opens the
     documentation and "install" opens the offer.

SO THE CONTROL IS:

    the combo row        DISABLED -- greyed, not selectable, not pressable,
                         and it can never become the chosen value (see below)
    the hover panel      the explanation, then the API link, then INSTALL to
                         the right of it, exactly as asked

BUILD IT AS ONE REUSABLE HOVER PANEL, not as a backend feature: the Image UMAP
needs the same thing (section C), and a second implementation of an interactive
tooltip is a second set of hover, focus and dismissal bugs.

THREE THINGS THE HOVER PANEL MUST GET RIGHT, all of them the reason people
avoid interactive tooltips:
  * IT MUST NOT VANISH WHEN THE POINTER MOVES TOWARD IT. The pointer has to
    cross the gap between the row and the panel; a plain leave-event dismissal
    closes it mid-journey and the Install link can never be reached.
  * IT MUST BE DISMISSABLE -- Escape, clicking away, and moving well clear --
    or it is a panel the user cannot get rid of.
  * IT MUST BE REACHABLE BY KEYBOARD. A control that only a mouse can operate
    is not an option for everyone, and the row itself is disabled, so the
    keyboard route has to be explicit rather than inherited.

AND THE INVARIANT, WHICHEVER WAY IT IS BUILT: an unavailable entry may never
become the selected value, not briefly and not by keyboard. NOTE, measured
above: `QStandardItem.setEnabled(False)` leaves `ItemIsSelectable` set in the
flags -- Qt will not ACTIVATE a disabled row, but a model-level selection can
still land on it. Clear the selectable flag too rather than relying on the
enabled state alone. `_require_backend` already refuses a settings CSV naming
an unavailable backend; this must not open a second door to the same state.

--------------------------------------------------------------------------------
A. CAN IT BE MADE? YES, AND spaCR ALREADY HAS THE PARTS.
--------------------------------------------------------------------------------

Nothing new has to be invented:

  * `spacr/updater.py` ALREADY installs into spaCR's own environment --
    `find_uv()`, `upgrade_command()`, `run_pip_upgrade()` -- and already
    handles the case its docstring names: an install where `python -m pip`
    fails because pip was never seeded, which is why `uv` is looked for first.
  * `spacr/doctor.py` already reports the interpreter and `sys.prefix`, so the
    environment a prompt would install INTO is already known and already shown.
  * `spacr/gpu_reduce.py` already has the availability pattern: importable AND
    a device present, with the CPU path staying the answer otherwise.

So the work is a shared "offer to install this" flow, not an installer.

--------------------------------------------------------------------------------
B. THE CASE THAT MUST NOT OFFER TO INSTALL, AND IT IS cuML's
--------------------------------------------------------------------------------

THIS IS THE PART THAT WOULD BE WRONG IF BUILT NAIVELY. Measured 2026-08-18:

    cuml-cu12 26.8.0   requires_python >= 3.11, and the recent wheels are
                       cp311 ONLY: 25.10/25.12/26.2 shipped cp310-cp313,
                       26.4/26.6/26.8 ship cp311 alone. The window is
                       NARROWING.
    also wants         numpy>=2.0,<3.0, numba<0.65, scipy>=1.14, sklearn>=1.6

    in the default `spacr` env (python 3.10, numpy 1.26.4):
        CANNOT BE INSTALLED AT ALL at 26.x. Resolving anyway drags numpy
        1.26.4 -> 2.2.6 and downgrades numba and llvmlite.
    in `spacr12` (python 3.12, numpy 2.4.6): numpy is untouched, but it still
        downgrades numba 0.66 -> 0.64, llvmlite 0.48 -> 0.46,
        cuda-bindings 13.3.1 -> 12.9.7, cuda-toolkit 13.0.3 -> 12.9.2,
        and moves pandas 2.3.3 -> 3.0.3.

SO ON THE INTERPRETER spaCR IS USUALLY RUN ON, "pip install cuml" IS NOT THE
REMEDY AND MUST NOT BE OFFERED AS ONE. The remedy is a different environment.
A prompt that runs pip here either fails, or succeeds at breaking the install
-- and the second is worse, because the user asked for a faster lasso and got
a numpy major upgrade under an image-analysis stack.

THE PROMPT THEREFORE HAS THREE ANSWERS, NOT TWO:

  1. INSTALLABLE HERE -- offer it, name the exact command, say what it will
     change (the dry-run report already computes this), and install on
     confirmation.
  2. NOT INSTALLABLE HERE, BUT POSSIBLE ELSEWHERE -- say what environment
     would take it and how to make one, and do NOT run anything:
     "cuML needs Python 3.11; this spaCR is on 3.10. Create an environment
     with `conda create -n spacr311 python=3.11`, install spaCR there, then
     `pip install cuml-cu12`."
  3. NOT POSSIBLE -- say so, with the reason. pymer4 is this: see D.

AND ALWAYS SHOW THE DRY-RUN BEFORE INSTALLING. `pip install --dry-run
--report` is what caught cuML, and a user is entitled to see "this will move
numpy 1.26.4 -> 2.2.6" BEFORE agreeing rather than after. An install that
changes a package spaCR already depends on is REFUSED by default and needs a
second, explicit confirmation naming what moves.

C. WHERE IT APPEARS, AND IT IS MORE THAN THE BACKENDS
--------------------------------------------------------------------------------

"If so I want that for image UMAP as well."

So this is ONE shared control, not a backend feature: a greyed option that
knows why it is greyed, what would ungrey it, and whether it can do that here.
The two callers today are the regression backend picker (141) and the Image
UMAP's GPU acceleration (`gpu_reduce`, which already offers cuML for UMAP,
t-SNE, PCA, DBSCAN and KMeans and already decided it is an EXTRA). Build it
once, in a place neither owns, and let both ask.

EVERY ENTRY IS PRESENT, ALWAYS. Per the request and per instruction 106:
nothing is hidden because it is unavailable -- a missing option cannot explain
itself, and a user cannot ask for what they cannot see. Greyed, with the
reason ON the entry.

--------------------------------------------------------------------------------
D. THE ONES THAT CANNOT SIMPLY BE INSTALLED, WRITTEN INTO THE API DOCS
--------------------------------------------------------------------------------

"include them but include an instruction in the api for how to make them
available. Including the one that needs R."

  * pymer4 / lme4 -- NEEDS R. Measured 2026-08-18: the 0.9.2 wheel declares NO
    dependencies at all, which is why a dry-run reported one additive package;
    installed, it fails at `pymer4/io.py: import polars`, and every module
    under `pymer4/models/` opens with `from rpy2.robjects.packages import
    importr`. 141 said otherwise and 141 was wrong.
    THE API PAGE STATES THE REAL RECIPE: an R installation, `lme4` and
    `lmerTest` inside it, `rpy2`, then `pymer4` -- and says plainly that this
    is a heavier ask than the other backends, so a reader can decide before
    starting rather than halfway through.
  * cuML -- the environment recipe from B.2, plus the CUDA 12 pin and the
    pandas 3 jump it brings in `spacr12`.
  * numpyro / gpytorch -- installable, and they return a DIFFERENT ANSWER
    (posteriors, not point estimates plus standard errors). The docs say that
    first, because a user installing them to go faster has misunderstood what
    they are for.

--------------------------------------------------------------------------------
E. AND SAY WHAT IT COSTS TO USE, NOT ONLY TO INSTALL
--------------------------------------------------------------------------------

A backend that is installed and choosable still has to keep 141 D: it agrees
with statsmodels to a stated tolerance, or the box says what differs. cuML's
penalised path is the live example -- two coordinate-descent implementations
at the same alpha can SELECT DIFFERENT VARIABLES, which is a different answer
and not a tolerance. `gpu_reduce` already says the same of cuML's UMAP not
being bit-identical. Neither may become available quietly without that
sentence travelling with it.

HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Every backend and every GPU accelerator is VISIBLE in its control, greyed
  when unavailable, with the reason and the remedy on the entry.
* Clicking a greyed entry that CAN be satisfied here offers the install, shows
  what the install will change first, and installs on confirmation.
* Clicking one that cannot -- cuML on Python 3.10 -- explains the environment
  it needs and runs NOTHING.
* An install that would move numpy, torch, pandas or scikit-learn is refused
  by default and needs a second confirmation naming what moves.
* The same control serves the regression backends and the Image UMAP.
* The API docs carry a working recipe for pymer4-with-R, for cuML, and for
  numpyro/gpytorch, each saying what it costs and what differs.

THREE MEASUREMENTS, TWO OF THEM CONFIRMING THIS FILE AND ONE CORRECTING A BUG
IT WOULD HAVE CAUSED.

  1. CONFIRMED. `QStandardItem.setEnabled(False)` leaves `ItemIsSelectable`
     SET; clearing it works; the tooltip survives both. Kept as
     `test_setEnabled_alone_leaves_the_row_selectable`, so nobody discovers
     the hole a third time. Also measured and worth having: Qt's own keyboard
     navigation SKIPS the disabled row (Down from 0 lands on 2), so the
     remaining door was the model-level one this file named.

  2. CONFIRMED, on the real resolver. `pip install --dry-run --report -
     cuml-cu12` in the default env reports exactly what section B says:
     numpy 1.26.4 -> 2.2.6, numba 0.62.1 -> 0.61.2, llvmlite 0.45.1 -> 0.44.0,
     eight nvidia-cu12 runtime libraries moved, 24 packages added. The
     protected-package refusal fires on it.

  3. FOUND AND FIXED WHILE MEASURING IT. `--report -` writes the JSON to
     STDOUT with pip's own progress BEFORE it and a "Would install ..." line
     AFTER it. `json.loads` on the stream therefore raises on trailing data,
     and the first implementation reported "the packaging tool produced no
     readable plan" for a resolve that had SUCCEEDED -- which routes to the
     refusal branch, so every install would have been unreachable and the
     reason would have looked like a network problem. `json.JSONDecoder.
     raw_decode` at the first `{` is the fix;
     `test_the_pip_report_is_found_between_pips_own_chatter` is the guard.

DESIGN CHOICES MADE HERE, one line each.

  * THE POPUP IS CLOSED WHEN THE POINTER LEAVES IT. A `QComboBox` popup is a
    `Qt.Popup` with an active mouse grab; with it still open the first press
    on the panel is eaten by the grab, so Install would need two clicks and
    the first would look inert. Leaving the popup viewport while the panel is
    up calls `hidePopup()`, and the panel keeps the pointer.
  * THE KEYBOARD ROUTE IS Shift+F1 ON THE COMBO -- Qt's own "explain this
    control" chord, on the widget that IS focusable, since the rows are not.
    It opens the panel pinned and focused; Up/Down cycle the unavailable
    entries; Escape closes and hands focus back. A pinned panel ignores the
    hover timer, because a reader who is not holding the mouse must not have
    it taken away.
  * THE GAP IS A CORRIDOR. The hide is a timer, cancelled on entry, and while
    it is pending the cursor is tested against the union of the anchor's
    rectangle and the panel's -- so travelling through the gap re-arms the
    timer. Bounded by `CORRIDOR_GRACE_MS`, so a pointer parked in the corridor
    still lets it go.
  * THE ENVIRONMENT IS ASKED BEFORE spaCR's OWN WIRING. "cuML needs Python
    3.11 and this is 3.10" is something a user can act on; "spaCR routes no
    fit through it yet" is not, and saying that instead would hide the half
    they could have acted on.
  * THE RESOLVER IS NOT HANDED THE PROSE. `REGRESSION_BACKENDS['pymer4']
    ['pip']` reads "pip install pymer4  (plus R, rpy2, lme4)", which is four
    requirements and a syntax error to pip. `BACKEND_REQUIREMENTS` is the
    machine-readable copy.
  * THE DRY RUN RUNS OFF THE GUI THREAD behind a cancellable progress dialog.
    Against cuml-cu12 it took minutes here, and a frozen window during "I
    pressed Install" is indistinguishable from a crash. Cancelling returns a
    DryRun that did not answer, which `install_decision` refuses.
  * SECTION D IS IN THE MODULE DOCSTRING as well as in `INSTALL_RECIPES`,
    because `docs/source/api` is built by sphinx-autoapi, which publishes a
    module docstring verbatim and renders a dict as a truncated repr -- a
    recipe living only in the dict would be in the GUI and not in the docs.
    `test_the_module_docstring_carries_every_command_the_gui_shows` is what
    stops the two copies drifting.
