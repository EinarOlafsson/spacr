================================================================================
THE HF E2E MASK STAGE PRODUCES NO CELL MASKS, IN BOTH ITS MODES
================================================================================

Status:    STILL OPEN, and THREE proposed causes have now been disproven --
           including one I was confident enough about to file a separate
           instruction for. Read THE THREE WRONG ANSWERS at the very end
           before proposing a fourth.
Requested: not asked for. Found while attributing a failure in a regression
           sweep for instruction 100, and filed because a bug found in
           passing gets queued rather than narrated.

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

    tests/test_hf_e2e_integration.py::test_hf_e2e_mask_stage
    AssertionError: mask stage produced no cell_mask output files
    assert []

The manifest IS written, so the run completes and `open_run` is satisfied.
What is missing is the output: the test globs the dataset for any path whose
name contains "cell_mask", and gets nothing -- not even the
`cell_mask_stack/` DIRECTORY that `spacr/core.py:337` writes into, whose own
name would match.

It also prints, on the way past:

    WARNING: could not write the relationships table ...
    FilterError: this database has no object table to build relationships from

which is consistent: no masks, so no objects, so no object table.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The stage can report completion and publish a manifest while omitting its
principal output. Downstream relationship and measurement work then fails
later, obscuring the actual segmentation failure.

WHY IT IS INVISIBLE. The test is `@pytest.mark.slow` + `@pytest.mark.network`.
The fast leg excludes both, so this never runs there, and it did not surface
in the CI Slow leg either. It only appeared under an ad-hoc `-k` sweep that
ignored markers.

--------------------------------------------------------------------------------
IT IS NOT THE CELLPOSE channels= REMOVAL
--------------------------------------------------------------------------------

Stated because that change landed the same day, in the same files, and is the
obvious suspect. Two independent checks say no:

1. cellpose 4.0.7's `CellposeModel.eval` mentions `channels` exactly once as
   anything other than a docstring or a signature default:

       if channels is not None:
           models_logger.warning("channels deprecated in v4.0.1+. ...")

   The value is read for a truthiness test and discarded. It cannot change a
   mask.

2. The test fails IDENTICALLY at 8c4db209 -- the commit before any code
   change of that pass -- run in a clean worktree. Same assertion, same empty
   list.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

FIRST, ESTABLISH WHICH BUG THIS IS. There are two candidates and they need
different fixes, so do not start until it is known which:

  (a) The STUB dataset does not segment. `SPACR_HF_E2E_STUB=1` substitutes a
      synthetic dataset, and cpsam finds nothing in simple synthetic blobs --
      confirmed separately: a 128x128 image of five clean Gaussian blobs
      returns zero objects from `CellposeModel.eval`. If the stub images are
      that shape, the test asserts something the fixture cannot deliver, and
      the fix is the FIXTURE: stub data that a real model actually segments,
      or a stubbed model that returns known masks.

  (b) The mask stage genuinely drops its cell output. The network run in the
      same sweep reported real segmentation happening but failing QC --
      "Segmentation QC (cell): FAIL - 2 of 8 fields failed (25%)",
      "(pathogen): FAIL - 4 of 8 (50%)" -- so on real data masks ARE made.
      Whether the cell stack is then written, and where, is the question.

  The cheap discriminator: run the stub mode and look for ANY mask output
  under the workspace, for any object type. Nuclei present and cell absent is
  (b). Nothing at all present is (a).

THEN. If (a), fix the fixture -- an e2e test whose stub cannot pass is worse
than no e2e test, because it trains everyone to ignore a red mark. If (b),
fix the writer, and add the assertion to a suite that actually runs.

EITHER WAY. This test is currently unrunnable-green and outside every CI leg
that executes. Whatever the outcome, it needs to land somewhere the release
gate can see it, or the next person will rediscover it the same accidental
way.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

`SPACR_HF_E2E_STUB=1 pytest tests/test_hf_e2e_integration.py` passes, in
under a minute, with no network. And the same file passes in its network mode
on a machine that has the dataset -- including the QC stage, which currently
reports a quarter of the cell fields and half the pathogen fields as failed.

================================================================================
WHAT IT ACTUALLY IS: INTERMITTENT. BOTH HYPOTHESES ABOVE ARE WRONG.
================================================================================

The discriminator this file asks for was run, and it ruled out both branches.

(a) IS WRONG -- THE STUB SEGMENTS FINE. A stub run prints

        Found 12.5 cell/FOV. average size: 79.400 px2
        Found 8.5 cell/FOV. average size: 83.756 px2
        Segmentation QC (cell): 4 fields, 2 ok / 2 warn / 0 fail

    and `data/plate1/masks/cell_mask_stack` exists on disk afterwards, whose
    own directory name matches the test's glob. So the fixture is not the
    problem and the masks are not missing.

(b) IS WRONG TOO -- OR AT LEAST IS NOT THE WHOLE STORY. The output IS
    written, at the path the test looks in.

WHAT IS ACTUALLY HAPPENING: the test does not fail every time.

    run 1  passed          a later batch:  6 consecutive passes
    run 2  FAILED                          then 1 failure in the next pair

Same commit, same stub, same machine, no code change between runs. Roughly
one failure in eight. That is why it "failed at HEAD and also failed at
8c4db209" when this was first filed -- both of those were single runs of an
intermittent test, and a single run of a flaky test proves nothing about the
commit it was run on. The pre-existing claim still holds (it fails on old
commits too), but the attribution reasoning in this file was luckier than it
was sound.

WHY THAT IS WORSE THAN EITHER ORIGINAL HYPOTHESIS. A deterministic failure is
a bug with an address. An intermittent one in the MASK STAGE means the
segmentation pipeline is nondeterministic somewhere -- and this test only
asserts that *some* cell_mask output exists, which is the weakest possible
assertion about it. Whatever varies could equally be varying in a run that
writes masks nobody checks.

WHAT TO DO INSTEAD OF THE SECTION ABOVE

1. FIND THE VARIANCE, do not re-run until green. Candidates, in the order
   they are cheap to eliminate: cellpose on CPU with thread counts left free;
   an unseeded RNG in the stub or in segmentation; a temp-directory or
   filesystem race between the write and the glob; and pytest's own tmp_path
   numbering interacting with a leftover workspace.

2. MAKE THE ASSERTION SAY SOMETHING. "at least one file named *cell_mask*"
   passes when segmentation finds one cell in one field. If the stub is
   deterministic it should assert the object COUNT, not the existence of a
   path -- otherwise the test cannot distinguish "worked" from "barely
   worked", which is exactly the gap a flaky pass hides in.

3. ONLY THEN decide whether it belongs in a CI leg. Marking a flaky test
   `slow`+`network` and never running it is how it got to be a year old
   without anyone noticing; putting it in a leg while it is flaky would make
   the leg untrustworthy instead. Fix the variance, strengthen the assertion,
   then run it somewhere.

================================================================================
THE CAUSE: THE MASK PIPELINE IS UNSEEDED, AND CELLPOSE HAS NO SEED OF ITS OWN
================================================================================

The stub images are seeded (`np.random.default_rng(0)`), so the INPUT was
never the variance. The variance is downstream, and this repository had
already written down exactly why -- `spacr.runctx.SEED_CAVEATS["cellpose"]`:

    "Cellpose has no seed of its own; it draws from NumPy and Torch, so it
     follows this call on CPU."

"This call" is `seed_everything`. Nothing in the mask path calls it. Searching
the package, only `deep_spacr.py` does. So every segmentation run draws from
whatever state the global NumPy and Torch streams happen to be in, and the
masks vary run to run -- occasionally finding no cells at all, which is the
one-in-eight failure.

The test's assertion made it worse rather than causing it: "at least one file
named cell_mask exists" is weak enough to pass whenever segmentation finds
anything, so the nondeterminism was invisible except at its extreme.

FIXED IN THE TEST. `_prepared_workspace` now calls `seed_everything(0)`.
Verified 8 consecutive passes where the previous rate was about one failure in
eight.

--------------------------------------------------------------------------------
THE LARGER FINDING, WHICH IS NOT FIXED AND IS NOT THIS INSTRUCTION'S TO FIX
--------------------------------------------------------------------------------

SPACR'S SEGMENTATION IS NOT REPRODUCIBLE. Running Mask twice on the same
plate with the same settings can produce different masks, because nothing in
`core.preprocess_generate_masks` or `object.py` seeds the streams cellpose
draws from. `seed_everything` exists, is documented, knows about this exact
caveat -- and the pipeline does not call it.

That matters more than a flaky test:

  * every downstream number is computed from those masks, so a run is not
    reproducible either;
  * the provenance manifest records inputs and settings, which implies a run
    can be repeated, and it currently cannot be;
  * two people comparing the "same" analysis are not necessarily comparing
    the same segmentation.

WHAT IT NEEDS, and why it is not done here: seeding a pipeline is a product
decision with a compatibility edge -- it changes what today's runs produce,
and the seed has to be recorded in the manifest to be worth anything. That is
a new instruction and the maintainer's call, not a side effect of fixing a
test. The GPU path additionally is not bit-reproducible even seeded, per
SEED_CAVEATS["cuda"], so "seeded" would need to mean something precise.

WHAT IS STILL WORTH DOING TO THE TEST ITSELF, from the section above:
strengthen the assertion from "a cell_mask path exists" to an object COUNT.
With the run now deterministic that is a stable number, and it is the
difference between "worked" and "barely worked" -- which is the gap a flaky
pass hid in.

================================================================================
THE THREE WRONG ANSWERS (2026-08-15) -- READ BEFORE PROPOSING A FOURTH
================================================================================

This file has now proposed three causes and disproven all three. Recording
them so the next attempt does not re-derive them.

WRONG 1 -- "the stub dataset does not segment."
    It does. A stub run prints "Found 12.5 cell/FOV", the QC reports
    "4 fields, 2 ok / 2 warn / 0 fail", and `masks/cell_mask_stack` exists on
    disk afterwards.

WRONG 2 -- "the mask stage drops its cell output."
    It does not. The output is written, at the path the test's glob looks in.

WRONG 3 -- "the mask pipeline is unseeded, so cellpose varies."
    THIS ONE WAS FILED AS ITS OWN INSTRUCTION (114) AND IS FALSE. The claim
    rested on `grep -rl seed_everything spacr/*.py` returning only
    `deep_spacr.py`. That grep was the mistake: the mask path does not call
    `seed_everything` DIRECTLY, it enters `runctx.run_context`, which calls it
    for every run. `core.py:209` wraps `preprocess_generate_masks` in exactly
    that, and its comment says so -- "one seed reaching numpy / random / torch
    / cellpose". `resolve_seed` defaults to `DEFAULT_SEED = 42`, and the run
    log line confirms it: "run ... module=mask seed=42".

    So the pipeline IS seeded, 114 was withdrawn, and the "fix" that followed
    from it -- seeding the test fixture -- was reverted.

THE MEASUREMENT THAT SETTLED IT, and the reason to trust it over the earlier
reasoning: sixteen runs with the fixture seed and sixteen without.

    with the seed     16 passed, 0 failed
    without the seed  16 passed, 0 failed

Identical. The seed changes nothing, and 8 consecutive passes -- which is what
the "fix" was originally declared on -- has probability (7/8)^8 = 0.34 at the
observed failure rate. That was not evidence.

WHAT IS ACTUALLY KNOWN

* The test HAS failed, twice, reproducibly enough to notice: once during a
  full `-k "cellpose or mask"` sweep and once in a two-run loop.
* It has since passed 32 consecutive times in isolation.
* Both observed failures happened while the machine was running other test
  work in parallel; every clean run since has been on an idle machine.

That makes LOAD the leading remaining hypothesis -- a timeout, a resource
limit, or a race that only opens when the box is busy -- and it is the one
thing none of the three disproven answers looked at. It is also consistent
with the assertion being about a FILE existing: a stage that is starved or
cut short writes nothing, and "no cell_mask output" is what that looks like.

HOW TO TEST THE FOURTH ANSWER, rather than reasoning about it: run the test
repeatedly WHILE the machine is loaded -- `-n 8` on the rest of the suite in
another shell -- and see whether the failure rate returns. If it does, the
question is which resource, and the fix is in the test or its timeouts rather
than in segmentation.

AND STILL WORTH DOING EITHER WAY: strengthen the assertion from "a cell_mask
path exists" to an object COUNT. It is the weakest possible assertion about a
segmentation stage, it is why the failure looked like "no masks at all"
instead of "fewer masks than expected", and it would tell a future
investigator which of those two they are looking at.
