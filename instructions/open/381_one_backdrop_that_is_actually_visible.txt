================================================================================
ONE BACKDROP, AND THE PANELS ABOVE IT LET IT THROUGH
================================================================================

Status:    OPEN, filed 2026-09-07. AFTER THE RELEASE, at the maintainer's
           instruction: "file the backdrop thing somwhere in instructions for
           later and ill get to it after the next relese."
Owner:     spacr/qt/app.py (`_drop_a_redundant_screen_backdrop`),
           spacr/qt/widgets/home.py, spacr/qt/screens/app_screen.py,
           spacr/qt/theme.py (the QSS that makes containers opaque).
Costs, until it is done: idle GUI-thread CPU ~16% of a core instead of
           ~10%, and four times worse at 4K than at 1080p, because the cost
           is counted in pixels.

--------------------------------------------------------------------------------
WHAT HAPPENED, BECAUSE THE MISTAKE IS THE USEFUL PART
--------------------------------------------------------------------------------

Commit 7508d8dfb (2026-09-05) removed a second animated backdrop. Every
number in it was real:

    two full-size fields shaded and blitted at 12.5 fps
    950 paints/s, 393 Mpx/s with nobody touching the machine
    the lower layer covered over 87% of its area
    idle GUI-thread CPU ~16% of a core -> ~10%

And the conclusion drawn from those numbers was wrong. The commit message
said the lower layer was "a picture nobody could see". THE 13 % THAT WAS NOT
COVERED IS THE THEME. Retiring the screen's own backdrop leaves the window's,
which sits behind the stack -- and HomePage's plain `QWidget` containers paint
`bg` over it. On the dark theme `bg` is `#000000`.

The maintainer's report, two days later: "i get a black background when the
blobs theme is active ... what did you break?"

MEASURED FROM X, which is the only way this can be measured:

    1.5.0.1, the last desktop install    38.9 % chromatic, no pure black
    f9fa45319, the parent commit         29.6 % chromatic, no pure black
    7508d8dfb, the commit                 2.5 % chromatic, 31.7 % pure black
    with the dedup off (ded192cc4)       25.2 % chromatic, no pure black

  DO NOT MEASURE THIS WITH `QWidget.grab()`. It does not capture the
  GL-backed `AmbientWidget`, so it renders a WORKING backdrop as black. An
  A/B across two trees came out byte-identical for an hour because of it, and
  that hour was spent concluding the bug was not there. Use
  `QScreen.grabWindow`, which reads composited pixels from the X server.

  AND `test_home_shows_exactly_one_backdrop` PASSED THROUGHOUT. Counting
  widgets cannot see that the widget being counted is covered up. A test that
  asserts a structural property will not notice the product going black.

--------------------------------------------------------------------------------
WHAT TO ACTUALLY BUILD
--------------------------------------------------------------------------------

The dedup is right and the way it was landed was wrong. One backdrop IS
enough -- but only once the things above it stop painting an opaque
background. So:

1. FIND WHAT IS OPAQUE. Sampled at the black pixels and asked
   `MainWindow.childAt` who owned them, the answer was plain `QWidget`
   containers:

       860  QWidget < QWidget < QWidget
       708  QWidget < HomePage < QStackedWidget
       232  QWidget < QWidget < QScrollArea
       108  QTabWidget < QWidget < HomePage

   Generic containers, not spaCR classes -- which points at an
   application-wide QSS rule giving `QWidget` a background, rather than at
   any one widget. Confirm that before changing anything.

2. MAKE THEM TRANSPARENT WITHOUT MAKING EVERYTHING TRANSPARENT. The panels
   are supposed to be translucent-over-the-animation, and `pane_opacity`
   (default 60) already expresses that. What must not happen is a blanket
   `background: transparent` that takes the panels with it -- the cards have
   to keep reading as cards.

3. THEN TURN THE DEDUP BACK ON, in `_drop_a_redundant_screen_backdrop`,
   which currently returns immediately with the reasoning written at the top
   of it.

4. AND GATE IT ON A PIXEL MEASUREMENT, not on a widget count. The assertion
   that would have caught this is "the home screen is more than N% chromatic
   with an animated theme on", taken from `QScreen.grabWindow`. Both
   assertions in `tests/qt/test_one_backdrop_for_the_window.py` were replaced
   with a weaker "there is a visible backdrop at all" precisely because the
   strong one is only safe next to a visibility measurement. Restore the
   exact-one assertion together with that measurement, not before it.

--------------------------------------------------------------------------------
THE TRANSFERABLE RULE
--------------------------------------------------------------------------------

A PERFORMANCE FIX THAT REMOVES SOMETHING VISIBLE MUST BE MEASURED ON SCREEN
BEFORE IT SHIPS. CPU went down, the test stayed green, and the product went
black. Instruction 380's sweep will produce more changes of exactly this
shape, and this is the one to read first.

Related: 327 (the backdrop camera), 380 (the performance sweep).

--------------------------------------------------------------------------------
2026-09-09 -- STEP 1 CONFIRMED, AND THE FIX ALREADY SHIPS FOR ANOTHER THEME
--------------------------------------------------------------------------------

The file asks that the opaque-container theory be CONFIRMED before anything
is changed. It is confirmed, and it is exactly what the pixel sample said:
a blanket application-wide rule, not any one widget.

`spacr/qt/theme.py`, `_window_block`, line 3002. For every theme that is
not an image theme:

    QWidget { background-color: bg; ... }
    QMainWindow, QDialog { background-color: bg; }

That is the rule those 860 plain-`QWidget` black pixels were obeying. On
the dark theme `bg` is `#000000`, which is why the failure was pure black
rather than merely flat.

AND STEP 2 IS ALREADY SOLVED IN THIS FILE, for a different theme family.
The other branch of the same function -- the one taken for IMAGE_THEMES --
is the shape the animated themes need, and its docstring states the recipe
in three parts:

    "An image theme needs three things the opaque themes do not: a
     background image on the window, QWidget transparent so the image is
     not covered by every child, and each top-level window type explicitly
     re-opaqued so a stray plain QWidget window does not render as a hole."

It ships that as:

    QWidget { background-color: transparent; ... }
    QMainWindow, QDialog { <the picture> }
    QMenu, QToolTip, QMessageBox, QComboBox QAbstractItemView {
        background-color: surface_alt; }

The third rule is the one that answers this file's "what must not happen is
a blanket `background: transparent`". Popups are separate top-level windows
and are re-opaqued by name; the panels keep their own `background-color`
rules and go on reading as cards.

SO THE CHANGE IS NOT A NEW MECHANISM. It is: when an ambient backdrop is
enabled, take the image-theme branch's window block instead of the opaque
one, with the window painting the theme's own ground rather than a picture.

WHY IT IS STILL NOT DONE HERE. This session has no display, and this file's
own transferable rule is that a change of this shape must be measured on
screen before it ships -- `QWidget.grab()` cannot see the backdrop and
renders a working one as black, so the only honest verification is
`QScreen.grabWindow` under X. Landing the QSS change blind would be the
same mistake as 7508d8dfb with the sign reversed: a change that is right in
principle, green in the suite, and unseen.

WHAT THE NEXT SESSION WITH A DISPLAY SHOULD DO, in order:
  1. Switch `_window_block` to the transparent branch when
     `get_ambient_enabled()` is true, keeping the popup re-opaque rule.
  2. Grab the home screen with `QScreen.grabWindow` and check the
     chromatic fraction against the numbers already in this file --
     29.6 % at f9fa45319 is the target, 2.5 % is the failure.
  3. Only then re-enable `_drop_a_redundant_screen_backdrop`, and restore
     the exact-one assertion in
     `tests/qt/test_one_backdrop_for_the_window.py` alongside the pixel
     assertion, never before it.

--------------------------------------------------------------------------------
2026-09-11 -- THE PROBE WAS THE BUG, AND WITH IT FIXED STEPS 0, 1 AND 2 ARE
DONE WITH NUMBERS
--------------------------------------------------------------------------------

THIS SECTION FIRST SAID THE SESSION WAS LOCKED. It was not, and the
correction matters more than the claim did.

Written here on 2026-09-11: `tools/can_this_display_be_measured.py` painted
a marker colour, grabbed its own window and got back 0.0% marker and 73%
rgb~(16,16,16), and I concluded the maintainer's session was locked and
`QScreen.grabWindow` was returning the locker's pixels. The home session
checked the live session -- LockedHint=no, DPMS on with all timeouts 0,
"Monitor is On", idle 0 ms -- reproduced the same near-black, and found the
probe wrong in two ways:

  * IT NEVER RAISED ITS WINDOW. grabWindow returns what is in FRONT of the
    rectangle, so an unraised probe measures whatever is stacked above it.
  * `for _ in range(40): app.processEvents()` IS NOT A WAIT. Forty calls
    take microseconds; a compositing window manager needs milliseconds to
    map and composite. The grab fired before the window was on screen.

  SO THE TOOL WRITTEN TO ESCAPE THIS FILE'S `QWidget.grab()` TRAP HAD THE
  SAME TRAP ONE LAYER OUT, and returned exactly what a real bug returns.
  Fixed in ef0896f7a with `raise_()`, `WindowStaysOnTopHint` and a real
  1.5 s spin on a `QElapsedTimer`: 100.0% marker, USABLE. Step 0 stands and
  is worth keeping -- it is what turns "the picture is black" into "the
  picture is black AND the instrument is honest".

--------------------------------------------------------------------------------
STEP 2 FIRST, WHICH IS THIS FILE'S OWN RULE: PROVE THE MEASUREMENT CATCHES
THE DEFECT BEFORE TRUSTING IT ABOUT THE FIX
--------------------------------------------------------------------------------

Home screen, the maintainer's display, 1600x1000, grabbed through
`QScreen.grabWindow` on a raised window after a real settle. "Chromatic"
here is max(r,g,b) - min(r,g,b) >= 12, which is NOT the definition behind
this file's earlier 29.6%/2.5% figures -- so compare within this table
only, never across.

    theme   dedup OFF (today)      dedup ON, no QSS change
    dark    58.8% chromatic        3.0% chromatic
            0.0% pure black        20.4% pure black
    cell    93.5% / 0.3%           93.5% / 0.2%
    glass   61.7% / 0.0%           67.3% / 0.0%

THE MIDDLE COLUMN IS THIS FILE'S FAILURE SIGNATURE -- recorded here as
"2.5% chromatic, 31.7% pure black" -- reproduced on demand. And it is
DARK-THEME-ONLY: cell and glass are `IMAGE_THEMES` and already take the
transparent window block, so they were never affected. That is new: the
2026-09-07 report named the blobs theme, and the measurement says the
opaque themes are the ones that break.

--------------------------------------------------------------------------------
STEP 1, AND IT WORKS
--------------------------------------------------------------------------------

`_window_block` now takes the transparent shape for an opaque theme when an
animated backdrop is running -- `QWidget` transparent so the animation is
not covered, the window itself opaque so a compositor-less desktop does not
show through, popups re-opaqued by name, and the window painting THE
THEME'S OWN GROUND rather than a picture, so nothing depends on a cached
master existing. Exactly the recipe the 2026-09-09 note worked out.

    theme   dedup ON + this change
    dark    60.1% chromatic, 0.0% pure black
    cell    95.7% / 0.1%
    glass   72.8% / 0.0%

Dark comes back BETTER than it is today with the dedup off (60.1% against
58.8%), and no theme has any pure black. The `get_ambient_enabled()` read
is guarded: a build without preferences -- a test composing a sheet, a docs
run -- gets the opaque block it had before.

--------------------------------------------------------------------------------
STEP 3 IS DONE. THE DEDUP IS BACK ON AND THE EXACT-ONE ASSERTION WITH IT
--------------------------------------------------------------------------------

`_drop_a_redundant_screen_backdrop` was a bare `return` from 2026-09-07.
The condition it was waiting for -- "until the window's backdrop is actually
visible through the screens" -- is met, so it runs again, and the whole of
the measurement it cost is back: one full-size animated field per window
instead of two, which was 950 paints/s and 393 Mpx/s of picture nobody
could see, and ~16 % of a core at idle instead of ~10 %.

MEASURED WITH IT ON, from X, after the window block change:

    theme   chromatic          pure black
    dark    46.9 - 65.2 %      0.0 % in every one of five runs
    cell    93.7 %             0.3 %
    glass   67.4 %             0.0 %

against 3.0 % chromatic and 20.4 % pure black for the same configuration
with the old opaque window block.

`tests/qt/test_one_backdrop_for_the_window.py` now carries BOTH halves, in
the order this file demanded and never the other way round:

  * `test_home_still_has_a_backdrop_the_user_can_see` asserts EXACTLY ONE
    visible backdrop again, which is the assertion that was withdrawn on
    2026-09-07 because counting widgets shipped a black window;
  * `test_the_home_screen_is_not_black_on_a_real_display` reads the pixels
    from the X server and is marked `gui`, so it runs only where it can
    tell the truth. The suite runs `-m "not gui"` and therefore never
    pretends to have checked.

  THE THRESHOLDS COME FROM THE FIVE RUNS ABOVE, not from taste: black under
  5 % (measured 0.0, regression 20.4) and chromatic over 25 % (measured
  46.9-65.2, regression 3.0). The backdrop is ANIMATED, so the chromatic
  figure moves with whichever frame the grab catches, which is why the
  floor sits well under the lowest reading rather than near it.

CALIBRATED AGAINST THE DEFECT, which is this file's own rule and the one
7508d8dfb skipped. With the window block forced back to opaque, the pixel
test reports "35.5% of the home screen is pure black" and fails. With the
fix it passes. It can tell the two apart, which is the only thing that
makes it worth having.

507 offscreen tests pass across the backdrop, black-page, panel-slab,
ambient and home files with the dedup on.

WHAT IS LEFT OF THIS ITEM: nothing. The remaining backdrop question --
whether fullscreen is choppy and why -- is 327's, and 327 now has the GPU
numbers saying the shaders are not the cause.
