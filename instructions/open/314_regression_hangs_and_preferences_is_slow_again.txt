A CONFOUND THAT MUST BE RULED OUT FIRST, AND WHICH IS PROBABLY THE ANSWER.

is part stale and part unsaved is a plausible cause of a hang all by itself,
and no timing measured against it describes the shipped product.

REPRODUCE ON A CLEAN TREE BEFORE DIAGNOSING ANYTHING. If the hang does not
reproduce from a clean checkout of HEAD, the defect is the working tree and
not the code, and this instruction closes with that finding recorded.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A hang is the worst failure shape spaCR has: there is no traceback, no error
dialog, and no way for the user to tell a wedged process from a slow one. The
maintainer's own report -- "it took less time before" -- is the only signal,
and it arrives only because the same person used the older build. A user who
meets this on their first run concludes the application is broken.

It also silently invalidates 284's badge. An instruction that closed on a
green ratchet, whose behaviour has since regressed without the ratchet firing,
means the ratchet is not running on the path the user actually takes.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. RULE OUT THE TREE. Create a clean worktree at HEAD, install it, and drive
   the real app there. If regression opens normally, stop and record that.

2. MEASURE, DO NOT GUESS. ``tools/spacr_startup_benchmark.py`` already drives
   the real entry point through every live Qt app, presses every sidebar
   button, and fails on a 500 ms event-loop stall inside any measured
   interval. Run it with ``--record-only`` and compare against 284's table
   above. It needs the machine to itself; a timing number taken beside a test
   run is not evidence.

3. FIND THE STALL, NOT THE SLOWNESS. If regression wedges rather than
   finishes, attach ``faulthandler.dump_traceback_later(30, repeat=True)`` and
   take the stack while it is hung. Instruction 160 was diagnosed exactly this
   way, and its cause -- ``plt.show()`` entering a Qt event loop off the GUI
   thread -- was one no amount of reading would have found.

4. PREFERENCES. Time the dialog's construction separately from the screen
   behind it. 118 gave Preferences per-graph-type sections and 290 gave it a
   tooltip strip; either can be built eagerly for every setting spaCR has
   rather than for the page being shown.

5. EXTEND THE RATCHET TO WHAT BROKE. Whatever is found, the benchmark must
   fail on it next time. A hang needs a wall-clock ceiling that fails the run,
   not a budget that is only checked once the operation returns.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * ``xvfb-run -a python tools/spacr_startup_benchmark.py`` exits zero on a
    quiet machine, with every module inside its budget and Home inside the
    enforced 5.0 s budget;
  * regression opens on ten consecutive cold starts with no hang -- the report
    is of two hangs, so a single successful open proves nothing;
  * Preferences opens within a stated budget, and that budget is in the
    benchmark rather than in this file;
  * the stall that caused the hang has a test that fails without its fix.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

  * 284 is NOT reopened. It closed on evidence that was true; reopening it
    would overwrite that record with a later, different failure.
  * No optimisation is attempted before the tree confound is ruled out.
    Tuning code against a measurement taken on a half-stale checkout is how
    an afternoon gets spent making the wrong thing faster.

The maintainer's own session, measured while it was running:

Zero offscreen against 96.6% on a display is not a small difference, and the

default, and the backdrop and the GL path it can take are exactly what the

The GPU confirms it. During that same session:

    NVIDIA GeForce RTX 3090   55% utilisation
    compute processes: NONE

Fifty-five percent of a 3090 with no compute client is a GRAPHICS workload:
the backdrop is running on GL, and still costs about one CPU core to feed.

WHY THIS MAKES EVERYTHING ELSE FEEL BROKEN, including a module that "hangs":
a main thread already at 54% is one that has to finish painting a frame before
it can service a click. Every interaction queues behind the animation. That is
the shape of the report -- not one broken screen, but Preferences AND
regression AND "it took less time before", all at once.

WHAT LIKELY CHANGED, and it is recent: instructions 298, 301 and 303 added the
space theme, the Mandelbrot deep-zoom theme and its real controls, across
about twenty commits since 2026-08-20. A deep-zoom dive is far more expensive
per frame than the blob backdrop that preceded it.

NOT YET PROVEN, and it must be before anything is changed: that the backdrop
is the CAUSE rather than a large bystander. The measurement that settles it is
one launch with the backdrop off and one with it on, on the same display, both
sampled the way the table above was. Run it before touching a line.

3. TWO REAL COSTS IN THE START PATH, from a 40-second py-spy profile of a cold
   start on clean HEAD (824 samples, 50 Hz):

   * ICON RE-INKING IS 22% OF STARTUP. ``iconset.themed_pixmap`` ->
     ``themed_array`` -> ``themed_qimage`` is 22.1% cumulative, and under it
     sits PIL: ``Image.resize`` 4.6%, ``ImageFile.load`` 4.6%,
     ``_encode_tile`` 3.3%, ``reink`` 2.9%. ``app_icon`` alone is 19.2%.
     There IS a disk cache (``icon_cache_dir``, ``ICON_CACHE_VERSION``) and an
     ``lru_cache``, so this is a cache MISS, not an absent cache. The key is
     ``_file_stamp(path)`` = (path, mtime, size) -- and in an editable install
     whose files are rewritten all day, that stamp changes constantly, so a
     developer pays a cold icon cache on every single launch. Worth checking
     whether a released install keeps its cache; if it does, this cost is
     ours and not the user's.

   * ``apply_preferences_to_app`` IS 13.5% OF SELF TIME, at preferences.py:3910
     -- which is ``app.setStyleSheet(stylesheet(...))``. A stylesheet set on
     the QApplication re-polishes every widget in the process. This is the
     direct measured answer to "triggering the preferences took a very long
     time", and it is a cost paid on every preference change, not only at
     startup.

2026-08-30 -- THE EDITABLE ICON-CACHE MISS IS FIXED; ITEM REMAINS OPEN
--------------------------------------------------------------------------------

The persistent icon key now uses the SHA-256 digest of the compressed source
artwork rather than its absolute path and mtime. The in-process key still
carries mtime and size, so an edit is noticed immediately; the disk key then
distinguishes the actual bytes. Consequently a checkout, reinstall or archive
extraction that rewrites timestamps but not artwork reuses the finished PNG,
while even a same-size content change gets a new entry.

Measured over all 75 bundled PNGs on this machine, with module-import time
excluded in all three arms:

    cold decode + resize + re-ink       2.7814 s
    persistent cache, unchanged mtime   0.0514 s
    persistent cache, all mtimes moved  0.0508 s

The mtime-only rewrite created no new cache files and never entered the source
decode path. The two new invalidation tests plus the complete adjacent icon
and Space-theme suite are 64/64 green. Implementation commit: ``493aef85``.

The item remains OPEN for the quiet-machine real-display backdrop on/off pair,
the resulting frame-budget decision, and ten cold Regression starts through
the wall-clock-guarded benchmark.

2026-08-30 -- THE REAL-DISPLAY CAUSE IS PROVEN AND ITS FRAME BUDGET IS FIXED
--------------------------------------------------------------------------------

The required on/off comparison drove the ACTUAL ``spacr.qt.run(["--no-setup"])``
entry point on Xorg display ``:0`` at 3840x2160, with a clean temporary HOME
for every series.  The process tree was sampled with psutil and the arms were
interleaved so background machine load could not line up with one condition.
Hardware/software: Ryzen 9 5950X (32 logical CPUs), RTX 3090, Python 3.12.4,
PySide6 6.11.2.  All launches returned zero and had empty stderr.

Before the change, two disabled/backdrop/backdrop/disabled arms measured:

    condition      process CPU mean   median   maximum   final RSS
    disabled #1          0.167%        0.0%      1.0%     296.6 MB
    backdrop #1         25.033%       25.1%     26.0%     296.6 MB
    backdrop #2         24.483%       24.3%     25.1%     296.7 MB
    disabled #2          0.000%        0.0%      0.0%     296.0 MB

This is causal rather than a profile inference: toggling only the backdrop
repeatedly adds one quarter of a CPU core while RSS is unchanged.  System CPU
varied between roughly 19 and 26 percent across the arms, while spaCR's own
disabled process stayed at zero.

The shared production installer now gives this slow diffuse animation a
12-fps idle budget instead of repainting at the direct widget's full 24 fps.
The public ``AmbientWidget`` default and an explicit caller's requested rate
remain unchanged.  Repeating the same interleaved real-display experiment:

    condition      process CPU mean   median   maximum   final RSS
    disabled #1          0.000%        0.0%      0.0%     296.7 MB
    backdrop #1         12.480%       12.6%     13.6%     296.8 MB
    backdrop #2         12.080%       11.6%     13.0%     296.9 MB
    disabled #2          0.000%        0.0%      0.0%     295.8 MB

The repeated enabled-arm mean fell from 24.758 to 12.280 percent, a 50.4
percent reduction, with no memory tradeoff.  This is the requested frame
budget rather than an off switch.

The same audit found a separate exit-time failure in spaceout's CPU fallback.
Closing the real app during its first Numba compilation destroyed a live
QThread and Qt aborted the process (exit 134).  Renderer shutdown now joins at
explicit shutdown, widget destruction AND QApplication ``aboutToQuit``; if a
finite render exceeds the five-second soft deadline, shutdown waits rather
than entering Qt's process-fatal detached state.  The identical one-second
real-display reproducer now exits zero with no critical log.  Direct and
adjacent verification is 175 ambient tests, 94 fractal tests and 23 movement/
budget tests, all passing.  Implementation commit: ``b369d911``.

Preferences' measured whole-dialog construction is 0.823 seconds against its
3.0-second benchmark budget.  Unchanged preference applications now skip the
global QApplication stylesheet re-polish which the profile attributed 13.5
percent of self time to (``05f0d0ca``).  The startup ratchet now measures
Preferences as a real post-paint state and has a wall-clock backstop which can
fail a blocked GUI thread even when its QTimer cannot run (``fb43b70d``).
The two re-polish budget tests and 22 startup/readiness driver tests pass.

The item remains OPEN only for ten consecutive cold Regression starts through
that wall-clock-guarded benchmark on a machine no longer occupied by the CI
partition replays.  Timing them beside those jobs would not be valid evidence.

2026-08-30 -- THE FIVE-PASS STYLESHEET FINDING RECONCILED WITH THE FINAL TREE
--------------------------------------------------------------------------------

An independent coverage lane, based before the integrated late-QSS change,
measured five global stylesheet compositions during a cold launch: the initial
preference application plus four import-time widget-QSS registrations.  Its
first fix batched those registrations and reduced five passes to two.

The canonical integration tree already contains the stronger resolution in
``a3c18f77``: late widget QSS is installed on the newly created screen root,
not by re-polishing the entire ``QApplication``.  Consequently cold launch
applies preferences once when setup has no new answers, while still installing
late blocks before their screen's first paint.  The final merge deliberately
kept that one-pass scoped-overlay design rather than reintroducing a second
global pass.  ``test_the_theme_is_resolved_once_when_nobody_was_asked_anything``
and the late-screen QSS cohorts ratchet both halves of that contract.

The lane's warm measurement put one ``apply_preferences_to_app`` call at a
median 5 ms (min 5, max 6, n=7).  Removing redundant passes is real work, but
it is not presented as the multi-second hang; the causal real-display backdrop
and frame-budget evidence above remains the explanation for that report.
