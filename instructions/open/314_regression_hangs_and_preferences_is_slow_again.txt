Two measurements taken at filing time, on the live tree:

  * The cost must therefore be in what the SCREEN does when it is built --
    the first real work behind the click -- not in module loading.

A CONFOUND THAT MUST BE RULED OUT FIRST, AND WHICH IS PROBABLY THE ANSWER.
The working tree at ``/mnt/firecuda2/codex/repo/spacr`` was found on
2026-08-29 to be simultaneously (a) BEHIND origin/nightly -- 36 files present
in HEAD are absent from disk, including the whole ``spacr/flowview/`` package
committed that afternoon -- and (b) carrying 199 modified files whose content
is in no commit in the repository's history. ``pip -e`` points at this tree
(HANDOFF 3f), so ``spacr`` on PATH launches exactly this mixture. A tree that
is part stale and part unsaved is a plausible cause of a hang all by itself,
and no timing measured against it describes the shipped product.

REPRODUCE ON A CLEAN TREE BEFORE DIAGNOSING ANYTHING. If the hang does not
reproduce from a clean checkout of HEAD, the defect is the working tree and
not the code, and this instruction closes with that finding recorded.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A hang is the worst failure shape spaCR has: there is no traceback, no error
dialog, and no way for the user to tell a wedged process from a slow one. The
maintainer's own report -- "it took less time before" -- is the only signal,
and it arrives only because the same person used the older build. A user who
meets this on their first run concludes the application is broken.

It also silently invalidates 284's badge. An instruction that closed on a
green ratchet, whose behaviour has since regressed without the ratchet firing,
means the ratchet is not running on the path the user actually takes.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. RULE OUT THE TREE. Create a clean worktree at HEAD, install it, and drive
   the real app there. If regression opens normally, stop and record that.

2. MEASURE, DO NOT GUESS. ``tools/spacr_startup_benchmark.py`` already drives
   the real entry point through every live Qt app, presses every sidebar
   button, and fails on a 500 ms event-loop stall inside any measured
   interval. Run it with ``--record-only`` and compare against 284's table
   above. It needs the machine to itself; a timing number taken beside a test
   run is not evidence.

3. FIND THE STALL, NOT THE SLOWNESS. If regression wedges rather than
   finishes, attach ``faulthandler.dump_traceback_later(30, repeat=True)`` and
   take the stack while it is hung. Instruction 160 was diagnosed exactly this
   way, and its cause -- ``plt.show()`` entering a Qt event loop off the GUI
   thread -- was one no amount of reading would have found.

4. PREFERENCES. Time the dialog's construction separately from the screen
   behind it. 118 gave Preferences per-graph-type sections and 290 gave it a
   tooltip strip; either can be built eagerly for every setting spaCR has
   rather than for the page being shown.

5. EXTEND THE RATCHET TO WHAT BROKE. Whatever is found, the benchmark must
   fail on it next time. A hang needs a wall-clock ceiling that fails the run,
   not a budget that is only checked once the operation returns.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * ``xvfb-run -a python tools/spacr_startup_benchmark.py`` exits zero on a
    quiet machine, with every module inside its budget and Home inside 2.0 s;
  * regression opens on ten consecutive cold starts with no hang -- the report
    is of two hangs, so a single successful open proves nothing;
  * Preferences opens within a stated budget, and that budget is in the
    benchmark rather than in this file;
  * the stall that caused the hang has a test that fails without its fix.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

  * 284 is NOT reopened. It closed on evidence that was true; reopening it
    would overwrite that record with a later, different failure.
  * No optimisation is attempted before the tree confound is ruled out.
    Tuning code against a measurement taken on a half-stale checkout is how
    an afternoon gets spent making the wrong thing faster.

WHAT LIKELY CHANGED, and it is recent: instructions 298, 301 and 303 added the

NOT YET PROVEN, and it must be before anything is changed: that the backdrop
is the CAUSE rather than a large bystander. The measurement that settles it is
one launch with the backdrop off and one with it on, on the same display, both
sampled the way the table above was. Run it before touching a line.

3. TWO REAL COSTS IN THE START PATH, from a 40-second py-spy profile of a cold
   start on clean HEAD (824 samples, 50 Hz):

   * ICON RE-INKING IS 22% OF STARTUP. ``iconset.themed_pixmap`` ->
     ``themed_array`` -> ``themed_qimage`` is 22.1% cumulative, and under it
     sits PIL: ``Image.resize`` 4.6%, ``ImageFile.load`` 4.6%,
     ``_encode_tile`` 3.3%, ``reink`` 2.9%. ``app_icon`` alone is 19.2%.
     There IS a disk cache (``icon_cache_dir``, ``ICON_CACHE_VERSION``) and an
     ``lru_cache``, so this is a cache MISS, not an absent cache. The key is
     ``_file_stamp(path)`` = (path, mtime, size) -- and in an editable install
     whose files are rewritten all day, that stamp changes constantly, so a
     developer pays a cold icon cache on every single launch. Worth checking
     whether a released install keeps its cache; if it does, this cost is
     ours and not the user's.

   * ``apply_preferences_to_app`` IS 13.5% OF SELF TIME, at preferences.py:3910
     -- which is ``app.setStyleSheet(stylesheet(...))``. A stylesheet set on
     the QApplication re-polishes every widget in the process. This is the
     direct measured answer to "triggering the preferences took a very long
     time", and it is a cost paid on every preference change, not only at
     startup.

--------------------------------------------------------------------------------

MEASURED: A COLD LAUNCH COMPOSED THE STYLESHEET FIVE TIMES
----------------------------------------------------------
Found while working the failing-test list, not by looking for it.

`register_widget_qss` re-applied the whole application stylesheet the moment
a block was registered. That is right for one screen module arriving on its
own long after startup -- it must be styled before it can paint -- and it is
quadratic for a run of them. Building MainWindow imports four such modules,
so `launch` composed the sheet five times where one is owed:

    1  app.py:4608          launch, before the window
    2  shortcuts.py         imported by MainWindow.__init__
    3  settings_search.py   imported by shortcuts.install
    4  recipes.py           imported by shortcuts.install
    5  screens/map_barcodes.py  imported by shortcuts.install

Four of the five were thrown away by the next one.

Fixed with `theme.batched_widget_qss()`, a reentrant scope that collects the
names and restyles once on the way out. `launch` opens it around the
MainWindow construction, which is safe because the window has not been shown
yet, so the single flush still lands before first paint. Cold launch: 5 -> 2.
The two that remain are both owed -- one before the window so its widgets are
built against the right palette and font metrics, one after to fold in the
blocks its modules brought.

HONESTLY, THOUGH: THIS IS NOT THE HANG.
`apply_preferences_to_app` measures at a median of 5 ms (min 5, max 6, n=7,
warm, all registrars loaded). Removing three of them is worth about 16 ms.
That is worth having and it is three orders of magnitude short of the
multi-second delay reported here. Recorded so that nobody reads the 5 -> 2 as
the explanation and stops looking. The cause of the reported hang is still
open; what this closes is a real inefficiency found on the way past, and a
guard against it coming back.

The guard is tests/qt/test_the_window_comes_before_the_dialog_filters.py
::test_the_theme_is_resolved_twice_and_not_once_per_screen_module. It counts
the blocks registered while the window is built ALONGSIDE the restyles,
because a restyle per registering module and one restyle for all of them are
indistinguishable if you only count restyles.

2026-08-31 — A RECOVERED LEAD: 323,014 IMPORT STATEMENTS PER REGRESSION BUILD
--------------------------------------------------------------------------------

Found as an UNCOMMITTED edit in the duplicate checkout at
/media/carruthers/mnt3/claude/repo/spacr, which had zero unique commits and was
deleted on the maintainer's instruction once this was preserved. It is recorded
here rather than applied because spacr/qt/widgets/ is held by a concurrent
session.

`feature_dictionary._still_alive` does `from shiboken6 import isValid` INSIDE
the function. `FeatureHelpFilter` is installed on the QApplication and must
check liveness before it may touch `event.type()`, so `_still_alive` runs twice
for every event in the application -- 323,014 times while ONE Regression screen
is built. That is 323,014 executions of an import statement.

    import inside the function   625 ms per Regression screen build
    resolved once at module level 33 ms

Measured, not assumed. The patch hoists the import to a module-level
`_SHIBOKEN_IS_VALID`, keeping the fallback as a module-level `None` so the
"cannot ask the question" branch behaves exactly as before.

    instructions/data/314_feature_dictionary_shiboken_import.patch

WHY IT MATTERS TO THIS ITEM. 592 ms on a Regression build is not the
multi-second hang either, and must not be reported as its cause -- this file
has already recorded one inefficiency being mistaken for the explanation. But
Regression is the screen the maintainer named, and this is the largest single
measured cost found in its build so far. Apply it, re-measure the build, and
see what is left.

NOT APPLIED HERE. Whoever holds spacr/qt/widgets/ should apply it, add a guard
that fails if the import returns inside the function, and re-run the cold
Regression gate.

ADDENDUM 2026-08-31 — NOT REPRODUCED HERE, AND WHAT WAS RULED OUT
--------------------------------------------------------------------------------

MEASURED on the Linux machine, offscreen, warm cache:

    start -> usable Home     0.88 s
    click -> regression      1.34 s
    click -> mask            0.47 s
    click -> measure         0.23 s
    build Preferences        0.42 s   (0.07 s on a second build)

Neither symptom appears. That is not evidence the report is wrong -- it
is a different machine, and the report is from an interactive session on
a Mac.

THE TWO PATHS THAT COULD BLOCK THE GUI THREAD ARE ALREADY GUARDED, so
whoever picks this up does not spend the afternoon finding that out:

  * `AppScreen._install_ambient` checks `_heavy_lock_is_free()` and
    defers on a 120 ms timer rather than waiting. The comment there
    records the original measurement -- 83% of a 3148 ms block was the
    backdrop constructor waiting for a lock the startup preloader held.
  * `fractal_travel` acquires the same lock with a TIMEOUT and raises
    `_HeavyImportInProgress` rather than blocking.
  * The preloader itself runs on a WORKER thread. It holds the lock
    through each import, which is what the two guards above exist for.

So the freeze this instruction describes has a known mechanism and that
mechanism is handled. What is reported now is either a different one or a
regression in those guards.

A GUARD NOW EXISTS FOR THE SHAPE ITSELF:
`tests/qt/test_opening_things_does_not_hang.py`. Instruction 314's own
observation is that 284's ratchet fails a module at ten seconds and a
hang has no number, so the ceilings there are deliberately generous --
20 s for a module, 10 s for a Preferences build, against measured costs
of 1.34 s and 0.42 s. It is watching for stuck, not for slow. It also
pins that `_install_ambient` still checks the lock and still retries,
because that check is what a refactor would quietly remove.

WHAT IS STILL NEEDED, and it can only come from the machine that saw it:

  1. WHICH MACHINE, and whether it was the first launch after an install
     -- the preloader's imports are slowest with a cold disk cache, and
     that is when the lock is held longest.
  2. WHETHER THE WINDOW WAS RESPONSIVE during the hang. A frozen window
     is the GUI thread blocked; a responsive window with nothing
     appearing is a worker that never finished, and they have different
     causes.
  3. `~/.spacr/logs/spacr.log` from that session. The timing spans are
     logged, so the slow step names itself.
  4. Whether Preferences was slow ONLY the first time. It builds in
     0.42 s cold and 0.07 s warm here; "slow every time" and "slow once"
     are different faults.

2026-09-01 — MEASURED ON A CLEAN TREE. THE CONFOUND IS RULED OUT AND THE
CAUSE IS NAMED.
--------------------------------------------------------------------------------

STEP 1, THE TREE, IS CLEAR. `pip -e` now resolves to
/mnt/firecuda2/Claude/repo/spacr, which is at origin/nightly with a clean
status, and the codex tree that was part-stale and part-unsaved reports 0
modified files at a real commit. The mixture this instruction suspected no
longer exists, so what follows describes the code.

STEP 2, THE MEASUREMENT. tools/spacr_startup_benchmark.py, one cold run,
offscreen, nothing else on the machine:

    start -> usable Home      3.00 s   budget  5.00   OK
    click -> regression       6.49 s   budget 10.00   OK
    click -> mask             3.66 s   budget 10.00   OK
    click -> classify_merged  3.16 s   budget 10.00   OK

EVERY MODULE IS INSIDE ITS BUDGET. Not one of the 46 measured intervals
misses. The 44 violations the run reports are ALL event-loop stalls, and
that is the finding:

    module            worst single stall   total build
    regression              6,132 ms          6.49 s
    mask                    3,448 ms          3.66 s
    classify_merged         2,881 ms          3.16 s
    umap                    2,367 ms          2.51 s
    measure                 2,124 ms          2.29 s
    Preferences             1,371 ms          1.39 s

    14 of 46 exceed the 500 ms ceiling.

WHAT THIS MEANS, and why the existing ratchet did not catch it. Regression
spends 6,132 of its 6,491 ms -- 94% -- in ONE uninterrupted block of the
GUI thread. The window cannot repaint, cannot show a cursor change and
cannot accept a click for that whole time. That is what the maintainer
met: it is not a wedge, because it does finish, but it is
indistinguishable from one while it lasts, and on a slower machine the
same block is proportionally longer.

Preferences is the same shape at 1,371 ms, which is exactly the second
half of the report -- "triggering the preferences took a verry long time".

SO THE INSTRUCTION'S OWN FRAMING WAS RIGHT: "a hang is not a slow budget
miss". The budget ratchet measures how long an operation TAKES and passes
everything; the thing that hurts is how long the GUI thread is held
WITHOUT YIELDING, and 284's table could never have shown it.

WHAT IS LEFT: the fix. The screen build has to yield -- either in chunks
the event loop can interleave, or off the GUI thread entirely. The
measurement above is the before; the same command is the after.

2026-09-01 (later) — WHAT THE 6.1 SECONDS IS NOT
--------------------------------------------------------------------------------

Six candidates measured and rejected, so the next attempt does not repeat
them. All numbers from this machine, offscreen, nothing else running.

  IMPORTS. A genuinely cold build of the regression screen -- fresh
  interpreter, imports included -- settles in 1.96 s, of which 1.3 s is
  import machinery. Not five seconds.

  CONSTRUCTION. AppScreen("regression") warm is 0.58 s. Through the real
  MainWindow, `_build_screen("regression")` is also 0.58 s.

  THE NAVIGATION HANDLER. `_on_nav_selected("regression")` on a real
  MainWindow is 1.22 s, and the screen settles 0.18 s after.

  RETRANSLATION. `retranslate_widget_tree` over the built regression
  screen -- 1,320 widgets -- is 0.036 s. It runs on every navigation and
  is not the cost.

  ACCUMULATION. Opening the benchmark's own first six modules in order
  leaves 4,599 live widgets, and regression still opens in 0.77 s.

  THE BACKDROP. Re-run with SPACR_NO_BACKDROP=1: regression 6,305 ms
  against 6,101 ms with it on. No difference. The CPU renderer competing
  for cores was the best hypothesis and it is wrong.

  THE PRELOADER. Off by default since instruction 282
  (`get_preload_policy() != "eager"` drops it), so it is not running to
  contend for the GIL.

WHAT IS LEFT. The stall reproduces ONLY under
tools/spacr_startup_benchmark.py, which drives the real entry point and
presses actual sidebar buttons; every harness that calls the same
handler directly gets 0.77-1.22 s. Two marks in the benchmark's own log
narrow it further: "navigation requested" for regression is emitted at
14.84 s and AGAIN at 20.65 s, with NOTHING in between and the screen
interactive 0.66 s after the second. So either the GUI thread is blocked
for 5.8 s with no event processed, or the benchmark re-issues a request
it believes was lost. Distinguishing those two is the next step, and it
is a question about the benchmark as much as about the app.

A FALSE COMMENT FOUND ON THE WAY, and it is worth fixing whatever the
cause turns out to be. `_on_nav_selected` says "The build already yields
to the event loop on a 25 ms deadline, so this card animates while the
widgets are made." There is no such mechanism on that path:
`_show_preparing` calls `processEvents` exactly ONCE before the build,
and `_build_screen` then runs to completion without yielding. Anyone
reading that comment while chasing this would rule out the build for a
reason that is not true.
