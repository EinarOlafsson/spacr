WHY THE THIRD ONE MATTERS MORE THAN THE OTHER TWO
--------------------------------------------------------------------------------

An order-dependent failure in `tests/qt` has a known mechanism in this
repository and it should be checked against that mechanism BEFORE it is
assumed to be leaked global state. Instruction 288 records it: a widget built
by a fixture with no parent and returned without teardown is destroyed at a
moment nobody chose, and the same pairing can produce EITHER a segfault OR an
ordinary failure -- `test_the_issue_preview_can_diagnose.py` plus
`test_track_previews.py` failed the track test without dying.

So the first question is not "what global did the earlier test leave behind".
It is "which fixture built a widget that outlived its test". The fix shape is
already written down there and is per-fixture: stop the timer, then `close()`,
`setParent(None)`, `deleteLater()`, `processEvents()` -- stopping the timer
FIRST is load-bearing.

DO NOT add a between-tests `gc.collect()` fixture. 288 records it as measured
not to work and as forbidden by
`tests/qt/test_retained_widget_tree.py::
test_no_boundary_fixture_forces_python_collection_over_live_qt_wrappers`.

LEAK ONE: A SINGLE-SHOT TIMER THAT BELONGS TO NOTHING
................................................................................

BISECTED TO A PAIR OF FILES, three files apart in the run (console_can_be_copied, console, engine_v2, keyboard):

    test_annotate_console_can_be_copied_and_reported.py
      + test_annotate_keyboard.py            102 passed, 1 ERROR
    test_annotate_keyboard.py alone          all passed
    test_annotate_console...  alone          7 passed

THE ERROR NAMED ITS OWN CAUSE once the traceback was read rather than the
summary line:

    File "spacr/qt/screens/annotate.py", line 2989, in <lambda>
      lambda: self._btn_copy_console.setText(tr("Copy console"))
    RuntimeError: libshiboken: Internal C++ object
    (PySide6.QtWidgets.QPushButton) already deleted.

`AnnotateScreen._on_copy_console` flipped the caption to "Copied" and set
`QTimer.singleShot(1200, functor)` to put it back. THE TWO-ARGUMENT FORM HAS
NO OWNER: it fires 1.2 seconds later no matter what has been destroyed in the
meantime. `test_annotate_console_can_be_copied_and_reported.py` presses that
button twice; qtbot tears its screens down at the end of those two tests; the
two strays then landed in whichever test was spinning an event loop 1.2
seconds later -- `test_auto_advance_skips_already_labelled_crops`, which
touches neither a console nor a button. pytest-qt reports an exception caught
in the Qt event loop against the test that was running, which is why the
failure kept changing name every time anything upstream of it got faster or
slower.

THE FIX IS PRODUCTION, NOT TEST. `QTimer.singleShot(1200, button, functor)`
-- the button is the context object, so Qt cancels the pending call when the
button is destroyed. A user who copies the Annotate console and leaves the
screen inside 1.2 seconds was getting that RuntimeError too; it is not a test
artefact. Verified in this PySide6 build before relying on it: a functor
given a context object that is `deleteLater`d does not fire.

    the pair:   102 passed + 1 error  ->  103 passed

LEAK TWO: THE SESSION-WIDE STYLESHEET, AND THE REAL DEFECT IT UNCOVERS
................................................................................

`test_it_opens_at_the_size_it_always_did[annotate._SettingsDialog]` fails
after ANY test that has used `tests/qt/conftest.py::qt_theme_applied`. That
fixture is session-scoped and has no teardown by design -- it puts a 68,364
character stylesheet and the dark palette on the shared QApplication and
they stay there for the rest of the process. Measured with a probe run twice:

    probe alone                         app.styleSheet() is 0 chars
    probe after one keyboard test       app.styleSheet() is 68,364 chars

So the smallest reproducer is one line, not a file pair: any earlier test
that asks for the theme.

THE TEST'S OWN DOCSTRING BLAMES THE WRONG THING. It says the 1,183-against-
1,191 it saw was font-metric warm-up and builds the dialog up to six times
until two agree. It is not warm-up: eight consecutive builds give exactly
1,191 with the filter off and exactly 1,183 with it on, every time. The
warm-up loop is measuring a stable difference and calling it noise.

WHAT THE DIFFERENCE ACTUALLY IS. `dialogs._DetachEveryDialog` reads a
dialog's floor on its Polish event, stores it, lowers the floor into a scroll
area, and restores the stored size on Show. An event FILTER runs before the
widget's own Polish handler, so at that instant nothing in the dialog has had
the stylesheet applied yet. Spying on `dialogs.window_floor`:

    floor read at Polish      480 x 1183
    floor once on screen      512 x 1191

Diffing all 165 children across that boundary named the culprit exactly: 16
of them change, and they are the EIGHT QComboBoxes plus their popup frames.
Unstyled each reports a 29 px minimum in "Sans Serif 9"; styled, 30 px in
"Open Sans". Eight rows, eight pixels. `ExecutionProfileDialog`'s 615-vs-616
is the same arithmetic with one combo box.

So the dialog opened eight pixels short of its own content, with a scroll bar
already showing on a form that fits -- IN THE REAL APPLICATION, which always
has the stylesheet. The unstyled 1,003-both-ways that makes the test pass on
its own is the case no user ever sees.

THE FIX, in `_SettingsDialog.__init__`: polish the children before the dialog
is ever shown, so the floor the filter reads is the floor the dialog has.

    for child in self.findChildren(QWidget):
        child.ensurePolished()

`self.ensurePolished()` DOES NOT WORK and was measured, not assumed: it sends
the dialog's own Polish event, which is the very event the filter measures
on, so it moves the short measurement earlier instead of correcting it --
480x1183 either way. Qt polishes a parent before its children, which is the
whole mechanism.

    with the filter on:  1183 -> 1191, which is what it opens at without it
