THE CONTRACT
--------------------------------------------------------------------------------

1. GITHUB ISSUES

Read every open issue against the current code. Close an issue only when its
acceptance criteria are implemented and verified, or when the issue is a
demonstrable duplicate/obsolete report with that evidence recorded. Do not
roll back a later implementation to match an older issue. An issue that needs
external information remains explicitly open rather than being declared fixed.

2. ONE GREEN COMMIT

Every required GitHub workflow and every job in those workflows must complete
successfully on the same final commit. A cancelled, skipped-by-error, stale-
branch or superseded run is not a passing badge. Local tests are diagnostics;
the GitHub run is the release evidence.

3. 100% FOR EACH MODULE

Measure statement and branch coverage per source module on a frozen worktree.
Every module reaches 100%; one heavily tested module cannot average away an
untested one. Tests exercise observable behavior and contain meaningful
assertions. Do not use ``# pragma: no cover``, omit files from configuration,
or delete reachable code merely to alter the denominator. Truly dead code may
be removed only after proving it is unreachable and unneeded.

The renewed request says "the library", so the denominator is every shipped
Python module in the distributions, not only ``spacr/`` files that happen to
be imported by the default test command. Package discovery, the coverage
inventory and the wheel/sdist contents must agree. A shipped module missing
from the inventory is a failure, not zero work hidden outside the report.

4. KEEP THE RESULT RATCHETED

CI fails when a new module lacks a coverage row, when any existing module
drops below 100%, or when a prohibited coverage exclusion appears. The report
artifact identifies uncovered lines and branches by module.

A FULL DISK IS THE OTHER WAY A COVERAGE RUN LIES (2026-08-30)
--------------------------------------------------------------
Caught with 405 MB left on `/` while the second batched run was writing into
it. The consumer was /tmp/pytest-of-olafsson: 19 GB across 101 abandoned
per-run temp directories, from this session's runs and the other lane's
together.

pytest keeps the last three runs' `tmp_path` trees on purpose, so a developer
can look at what a failing test wrote. It keeps them PER RUN, and a suite that
is run a hundred times in a night is a hundred trees. Nothing removes them.

Two things worth remembering.

  * `fuser -m <dir>` does not answer "is this directory in use". The -m means
    "the filesystem this path is on", so it reported all 101 as busy and the
    first cleanup removed nothing. Matching on the run counter -- keep the
    newest 25, drop the rest -- is what worked.

  * A coverage run that dies on ENOSPC mid-batch loses that batch's data the
    same way a lost xdist worker does, and reports a lower number without
    saying why. The disk is therefore part of the measurement, not part of
    the environment.

Freed 19 GB; `/` went from 405 MB to 21 GB and the run continued. Worth a
line in whatever ends up being the standing instruction for these runs: check
the disk before starting one, and clear /tmp/pytest-of-olafsson down to the
newest handful.

DO NOT UNION TWO COVERAGE RUNS TAKEN ON DIFFERENT COMMITS (2026-08-30)
------------------------------------------------------------------------
Tempting arithmetic, tried and discarded. Two batched runs exist, one of them
missing a batch, so the obvious move is to take the better of the two per
module and call the result a floor. It reads 98.68%, and it is wrong.

The reason is section 7's trap wearing a different hat. An arc is a PAIR OF
LINE NUMBERS. Between the two measured commits, 22 source files changed, so
run 1's arcs for those files name lines that are now something else -- and
counting them as covered credits the newer file for whatever the older one
executed. The 0.74 points that separated the union from the measured figure
were almost entirely that.

Restricted to files IDENTICAL in both measured revisions, the union is 98.06%
of 248,695 arcs, and the two runs differ by:

    arcs run 1 had and run 2 did not     46
    arcs run 2 had and run 1 did not     66

112 arcs out of 248,695 -- 0.045%. THE MEASUREMENT IS REPRODUCIBLE. Two runs
of the same suite on the same source agree to within a twentieth of a percent,
which is worth knowing in both directions: a coverage change smaller than
about 0.05% is noise, and a change larger than that is real and has a cause
worth naming.

So the rule is: quote one run, on one commit, and say which. Combine runs only
across files whose bytes are identical, and say that is what you did.

A MECHANISM FOR THE SEGFAULT, FOUND AND REPRODUCED (2026-09-01)
--------------------------------------------------------------------------------

A test that leaves a PARENTLESS Qt object owning a RUNNING TIMER for the
garbage collector to free will crash a LATER test's event loop.

REPRODUCED, both directions, in about a minute:

    pytest tests/qt/test_the_console_keeps_the_ai_error_analysis.py \
           tests/qt/test_track_previews.py::test_completion_handler_runs_on_the_gui_thread
    -> Fatal Python error: Segmentation fault
       Current thread ... qt_compat.py:160 in exec
                          wait_signal.py:58 in wait
                          test_track_previews.py:584

Each file passes ALONE. The faulting frame is inside `qapp.exec()` in the
SECOND file, which is why "every file was run on its own and none segfaulted"
came back clean and told us nothing: the guilty file is not the one that dies.

WHY. A `ConsolePanel` built in a test has no parent, so nothing owns it and
Python frees it whenever the collector next runs -- which can be in the middle
of another test's event dispatch. It owns `_WorkingDots`, a QTimer that is
still RUNNING. Destroying a Qt object with a live timer from inside event
dispatch is the crash. This is the same defect `spacr/qt/gc_policy.py` was
written for on the application side, one layer out: an object destroyed at a
moment nobody chose. THE SUITE DOES NOT INSTALL THAT POLICY, so tests remain
exposed to it.

THE FIX IS PER-FIXTURE AND CHEAP: stop the timer, then `close()`,
`setParent(None)`, `deleteLater()`, `processEvents()`. Stopping the timer
FIRST is load-bearing -- `deleteLater` has not run by the time the fixture
returns. Applied to `test_the_console_keeps_the_ai_error_analysis.py` and
`test_the_issue_preview_can_diagnose.py`; both crashes went away.

WHAT TO DO NEXT, in order:

1. Audit every `tests/qt` fixture that constructs a widget with no parent and
   returns it without teardown. `grep -l "= ConsolePanel()\|Panel(\|Dialog("
   tests/qt` is the starting set. Each is a candidate for the same crash.

2. DO NOT add a between-tests `gc.collect()` fixture. It was tried on
   2026-09-01 and it is the wrong answer twice over:

   * MEASURED NOT TO WORK. With the per-fixture teardown reverted and the
     collect fixture in place, the pair still dumped core. Raising it from
     `gc.collect(1)` to a full `gc.collect()` turned the crash into a plain
     failure but did not remove it. Whatever retains the panel is not a cycle
     the collector frees at that point.
   * AGAINST A DELIBERATE INVARIANT ALREADY WRITTEN DOWN HERE.
     `tests/qt/test_retained_widget_tree.py::
     test_no_boundary_fixture_forces_python_collection_over_live_qt_wrappers`
     exists to forbid exactly this, and calls itself "the CI segfault guard:
     ownership cleanup must stay on Qt's side". Its AST check inspects two
     named fixtures by name, so a third one slipped past it -- which is worth
     fixing on its own: the guard should check every autouse fixture in both
     conftests, or it only forbids what it happens to have been pointed at.

   The per-fixture teardown is therefore the fix, not a stopgap for it.

3. Only then re-measure whether the full-suite segfault is gone. Do NOT
   conclude it is fixed from a single clean run: the position moved between
   runs before, so absence on one run is not evidence.

NOTE the second symptom of the same cause: the same pairing can produce a
FAILURE rather than a crash (`test_the_issue_preview_can_diagnose.py` +
`test_track_previews.py` failed the track test without dying). So an
order-dependent FAILURE in `tests/qt` is worth checking against this mechanism
before it is assumed to be leaked global state.

2026-09-03. WHERE THE tests/qt SEGFAULT ACTUALLY IS, which matters because it

from `pytest_runtest_setup` -- that is, BETWEEN tests, while draining the

something it was connected to still has a queued event, most likely a
`QTimer` or a `deleteLater` that outlives its test.

2026-09-09 -- A TEST-ISOLATION LEAK THAT ONLY SHOWS WHEN TWO FILES SHARE A
                     PROCESS, AND WHY CI COULD NOT SEE IT
--------------------------------------------------------------------------------

Found while running the fractal suites together for 327. Three tests in
`tests/qt/test_the_spaceout_fractal.py` fail -- but only when
`tests/qt/test_cov_r8_fractal_travel_tails.py` has run first in the same
process:

    test_a_fractal_that_cannot_be_built_leaves_the_old_backdrop
    test_the_backdrop_uses_the_stored_settings
    test_the_chosen_pattern_reaches_the_backdrop

Each fails as a monkeypatch that did not take: `install_the_spaceout_fractal`
returns True where the patched builder should have raised, and a spy dict
comes back empty.

THE CAUSE IS THAT ONE NAME MEANT TWO MODULES. `TestImportingWithoutNumba`
re-imports `spacr.qt.widgets.fractal_travel` in a scratch namespace and
undoes it with `monkeypatch.delitem(sys.modules, ...)`. That restores the
`sys.modules` DICT and nothing else -- and an import also writes the module
as an ATTRIBUTE of its package. So after teardown:

    spacr.qt.widgets.fractal_travel            the scratch module
    sys.modules["spacr.qt.widgets.fractal_travel"]   the real one

and the two import forms follow different ones:

    from spacr.qt.widgets import fractal_travel     -> the attribute
    from .widgets.fractal_travel import ...         -> sys.modules

The later test patched the first and the code under test read the second.

FIXED by recording the package attribute under monkeypatch before the
re-import, so undoing puts the real module back in both places. A test in
the same class now asserts the two agree after an undo -- asserted there
rather than in a teardown check, because the failure it prevents lands in
another file and arrives as three unrelated-looking assertion errors.

WHY CI NEVER SAW IT, and this is the transferable part: the suite runs
under xdist, which distributes by FILE. Two files that only conflict when
they share a process are exactly what a per-file distribution hides, and
they stay hidden until someone runs a related group by hand. A green CI
does not mean the files are independent -- it means they were not asked to
be.

2026-09-10 -- SEQUENCING RULE: REBUILD THE CATALOGS ONCE, AT THE END OF A BATCH
OF CODE WORK, NEVER AFTER EACH CHANGE
--------------------------------------------------------------------------------

Demonstrated on myself tonight, which is the only reason it is worth writing
down. The API catalogs had just reached EXIT=0 at 10,283 symbols. Two new
public docstrings were then added by an unrelated performance fix --
`i18n.ui_language_resolved_once` and `PreferencesDialog` -- and the very next

    is: 2 API prose blocks remain exact English
        (spacr.qt.i18n.ui_language_resolved_once#1,
         spacr.qt.preferences.PreferencesDialog#1)
    wrote English API manifest: symbols=10284

TWO DOCSTRINGS, NINE LANGUAGES, AND A GREEN AUDIT TURNED RED. This file
already records that "a public docstring in any lane silently stales all
nine catalogs". What it did not say is what follows from it for scheduling:

  * A rebuild takes tens of minutes per language on this GPU. Doing it
    after each change multiplies that by the number of changes, and every
    intermediate result is thrown away by the next one.
  * The work does not shrink by being spread out. Ten docstrings translated

source that has already moved is neither.

of `PreferencesDialog.__new__`, does not appear in the manifest at all; the
public wrapper's docstring does. Where a helper does not need to be public,
not making it public is a translation cost avoided rather than deferred.

2026-09-10 -- DO NOT TOUCH GIT'S WORKING TREE WHILE A REBUILD IS RUNNING
--------------------------------------------------------------------------------

Nearly cost four locales for the second time in two days, and the near-miss
is worth more than the rule.

The builder reads the ENGLISH MANIFEST off the working tree at the start of
each language, and writes that language's catalog at the end. A
`git stash push` of the catalog paths -- to make room for a rebase -- reverts
`en.json` to HEAD for as long as the stash is out. Any language that STARTS
in that window reads the old manifest and produces a catalog against a
source that no longer exists, and nothing anywhere reports it: the file is
written, the audit passes for that language in isolation, and the symbol
counts disagree only when all nine are compared.

The window here was about fifteen seconds and `pt` started inside it, so it
is being re-run. Nothing was lost. The rules that follow:

  * NO `git stash`, `git checkout`, `git rebase` or `git pull` while a
    rebuild is running. Not on the catalog paths, not on anything --
    a rebase rewrites the whole tree, and the builder also reads
    `spacr/**` to extract the manifest in the first place.
  * COMMITS ARE FINE. They move HEAD and leave the working tree alone.
  * AND THE CHECK THAT CATCHES IT is the symbol count across all nine plus
    English, which must be one number:

        python -c "import json,pathlib
        for l in ('en','sv','de','es','zh_CN','pt','hi','ko','is','fr'):
            d=json.loads(pathlib.Path(
                f'docs/source/_static/i18n/api/{l}.json').read_text())
            print(l, len(d['symbols']))"

    Ten identical numbers, or one of them was built against a different
    tree. Run it before committing the catalogs, every time.

TWO THINGS FOLLOW AND THEY PULL IN OPPOSITE DIRECTIONS.

  * CI PROBABLY DOES NOT REACH THE DEADLOCK. Two file shards times four
    xdist workers is eight processes over ~1,034 files, so a worker sees a
    couple of hundred tests rather than 2,400. The leak accumulates per
    PROCESS, and no process gets far enough. `setup.py`'s dev extra says
    this out loud: xdist is "the accepted way to keep the Qt suite's
    process-global state from accumulating over thousands of tests".
  * SO THE GREEN CI THIS ITEM WANTS MAY ALREADY BE REACHABLE, and the local
    single-process hang is not the gate it looked like an hour ago. What it
    IS is the reason nobody can get a clean whole-suite signal on one
    machine -- which is what 325 recorded and what makes every "the suite
    passes" claim in this repository shard-shaped.

THE PER-TEST TIMEOUT IS A CONTAINMENT, NOT A FIX, and its own comment says
so: it "turns a lost job into one named failure". Naming the failure is
better than losing the job and it is not the same as not leaking the thread.
The per-test leak counter added above is the complement: the timeout tells
you WHICH TEST WAS RUNNING when the process gave up; the counter tells you
which tests LEFT A THREAD BEHIND, which is a different and usually earlier
list.

WHAT TO DO WITH THAT, in order:
  1. Get the per-test list from a run that completes -- the suite in
     quarters, or the CI shards' own output.
  2. Fix the leakers. Each one is a `shutdown()` a test did not call.
  3. THEN try the single process again. If it completes, every future
     "the suite passes" means the whole suite in one process, which is a
     stronger claim than eight shards agreeing separately.

    assert by_stage["alpha"] == ALPHA_MODULES

to start by reproducing, and the first attempt FAILED TO: running the
chunk's first nine files in file order gave 255 passed. The reason is that
the naming run did not pass `-p no:randomly`, so `pytest-randomly` had
shuffled the order and "the files before it" was not a fixed set.

    A BISECT THAT CANNOT REPRODUCE IS MEASURING THE WRONG THING, and the
    seed is part of the reproduction. Record it.

    before   2 failed, 1154 passed

`tests/qt/test_the_count_controls_the_categories.py::

A BISECT BY HALVES DID NOT REPRODUCE IT, and the reason is this file's own

THE GUESS. `SettingsWidgets._set_row_visible` has an early return -- "NOT

2026-09-11, LATER -- FOUR MECHANISMS PROPOSED, FOUR MEASURED FALSE, AND WHAT
IS ACTUALLY KNOWN
--------------------------------------------------------------------------------

Recorded at this length because the NEGATIVE results are the useful part:
each one is a plausible story somebody else would otherwise spend the same
hours on.

  1. A parentless early return in `_set_row_visible` silently leaves a row
     visible. FALSE: it fires 1,442 times in the passing run and 6,228 in
     the failing one. Ordinary, and not a discriminator.

  2. The panel is built from a different settings shape.  FALSE:
     `resolve_default_settings("mask")` returns the identical 193-key dict
     in both, with `has_registered_defaults` False both times. Verified
     that it is a FRESH dict each call and that mutating one does not
     reach the next.

  3. `CHANNELLED_OBJECTS` or `object_of_setting` has been mutated, so the
     rule cannot recognise a nucleus key. FALSE: at the moment of a wrong
     show it reads `('cell', 'nucleus', 'pathogen')` and resolves
     `nucleus_background` to `'nucleus'` correctly.

  4. The role's switch is not on the panel when the rule runs, so
     `if not switches: continue` skips it -- which the rule does on purpose,
     "hiding a row whose switch lives on another screen would leave the
     user a control they cannot bring back". FALSE for the mask panel:
     `channel_on_panel=True`, `switches_on_panel=['nucleus_channel']`.

AND THE OBSERVATION THAT LOOKED LIKE A SMOKING GUN IS CONTAMINATED, which
is the part most worth writing down. A probe on `_set_row_visible` reported
27 nucleus rows SHOWN while `nucleus_channel` read None, zero such in the
passing run -- a perfect discriminator. IT IS NOT EVIDENCE: the probe
re-reads `_object_visibility_settings()` at show time, which is not the
snapshot the rule decided on. A channel that read `'1'` when the rule ran
and `None` a moment later produces exactly that reading, and the rule was
right both times.

    MEASURING THE INPUT AT THE WRONG MOMENT IS THE SAME CLASS OF MISTAKE AS
    MEASURING THE WRONG TREE, and it produced a cleaner-looking signal than
    any of the four wrong mechanisms did. A discriminator that separates
    pass from fail perfectly is still worthless if the quantity was sampled
    after the decision it claims to explain.

WHAT IS SOLIDLY KNOWN, and it is all a next session should rely on:

  * it reproduces every time at chunk_020 of the 40-file split, seed 288;
  * 6/6 green alone and 17/17 green as a whole file;
  * it pre-dates the 2026-09-11 Qt work -- present at `ae8bdb417`;
  * the failure is three nucleus rows visible that the rule should have
    hidden, `nucleus_background` and `nucleus_min_area` among them;
  * every wrong show goes through `refresh_object_visibility` itself. No
    foreign caller shows those rows.

  THE NEXT PROBE TO WRITE wraps `keys_hidden_by_their_object` and records
  the `settings` mapping it was HANDED together with the set it RETURNED.
  That is the only pair that cannot be contaminated by a later re-read, and
  it answers in one run whether the rule decided wrongly or was decided
  wrongly for.

2026-09-11, LATER STILL -- IT IS A STALE PASS, NOT A WRONG ONE. THE RULE IS
NEVER ASKED AGAIN AFTER THE CHANNEL EMPTIES
--------------------------------------------------------------------------------

The probe above was written and run, and then one more that reads the
FAILING TEST'S OWN PANEL through `item.funcargs` rather than any aggregate.
Together they settle it.

  `keys_hidden_by_their_object`, asked 279 times in the failing run:

      wrong answers: 0
      ('None', 19 gated, 0 still shown) x50
      ('1',    19 gated, 19 still shown) x25
      ('2',    19 gated, 19 still shown) x8

  THE RULE IS NEVER WRONG. With no channel it hides all nineteen, every
  time. With a channel it shows all nineteen, correctly.

  Every hide it orders also LANDS. Watching each hide attempt through to
  the widget, in the failing run: 437 through a form row and 190 through
  the parentless path, and in all 627 the widget is hidden afterwards.
  So mechanism 1 above is dead twice over.

  AND THE TEST'S OWN PANEL SAYS WHY:

      the test's panel id=... nucleus_channel=True
      shown_now=['nucleus_background', 'nucleus_intensity_merge',
                 'nucleus_min_area']
      decisions recorded for THIS panel: 266
      last decision for each shown row: [(...,True), (...,True), (...,True)]

  THE LAST DECISION FOR ALL THREE WAS *SHOW*. Not a missed hide, not a
  dropped hide -- a deliberate show, ordered by a pass that ran while the
  channel HELD A VALUE, and never revisited after it emptied.

SO THE DEFECT IS A STALE PASS. The object rule is correct, is applied, and
is simply not asked again between the channel being cleared and the panel
being read. `refresh_object_visibility` early-returns while
`_applying_settings` is set -- deliberately, because a half-poured settings
file would narrow a slot to the wrong morphology and then narrow it again --
and relies on `_refresh_setting_dependencies` running at the end of the bulk
apply to catch up. A bulk apply that ends without that call, or leaves the
flag set, leaves exactly this: nineteen rows decided against a channel that
no longer has a value.

  WHERE TO LOOK, and it is a small target now: every path that clears an
  object's channel, and whether `_applying_settings` is still True when it
  does. Not the rule, not `_set_row_visible`, not the defaults, and not the
  ordering except as the thing that changes which path runs.

  WHY THE ORDERING MATTERS AT ALL: the three rows that survive are the ones
  whose last pass happened to be a channel-set one. Under a different
  ordering the last pass is a channel-empty one and the test passes, which
  is why this looks like order-dependence and is really a missing refresh.
