THE CONTRACT
--------------------------------------------------------------------------------

1. GITHUB ISSUES

Read every open issue against the current code. Close an issue only when its
acceptance criteria are implemented and verified, or when the issue is a
demonstrable duplicate/obsolete report with that evidence recorded. Do not
roll back a later implementation to match an older issue. An issue that needs
external information remains explicitly open rather than being declared fixed.

2. ONE GREEN COMMIT

Every required GitHub workflow and every job in those workflows must complete
successfully on the same final commit. A cancelled, skipped-by-error, stale-
branch or superseded run is not a passing badge. Local tests are diagnostics;
the GitHub run is the release evidence.

3. 100% FOR EACH MODULE

Measure statement and branch coverage per source module on a frozen worktree.
Every module reaches 100%; one heavily tested module cannot average away an
untested one. Tests exercise observable behavior and contain meaningful
assertions. Do not use ``# pragma: no cover``, omit files from configuration,
or delete reachable code merely to alter the denominator. Truly dead code may
be removed only after proving it is unreachable and unneeded.

The renewed request says "the library", so the denominator is every shipped
Python module in the distributions, not only ``spacr/`` files that happen to
be imported by the default test command. Package discovery, the coverage
inventory and the wheel/sdist contents must agree. A shipped module missing
from the inventory is a failure, not zero work hidden outside the report.

4. KEEP THE RESULT RATCHETED

CI fails when a new module lacks a coverage row, when any existing module
drops below 100%, or when a prohibited coverage exclusion appears. The report
artifact identifies uncovered lines and branches by module.

A FULL DISK IS THE OTHER WAY A COVERAGE RUN LIES (2026-08-30)
--------------------------------------------------------------
Caught with 405 MB left on `/` while the second batched run was writing into
it. The consumer was /tmp/pytest-of-olafsson: 19 GB across 101 abandoned
per-run temp directories, from this session's runs and the other lane's
together.

pytest keeps the last three runs' `tmp_path` trees on purpose, so a developer
can look at what a failing test wrote. It keeps them PER RUN, and a suite that
is run a hundred times in a night is a hundred trees. Nothing removes them.

Two things worth remembering.

  * `fuser -m <dir>` does not answer "is this directory in use". The -m means
    "the filesystem this path is on", so it reported all 101 as busy and the
    first cleanup removed nothing. Matching on the run counter -- keep the
    newest 25, drop the rest -- is what worked.

  * A coverage run that dies on ENOSPC mid-batch loses that batch's data the
    same way a lost xdist worker does, and reports a lower number without
    saying why. The disk is therefore part of the measurement, not part of
    the environment.

Freed 19 GB; `/` went from 405 MB to 21 GB and the run continued. Worth a
line in whatever ends up being the standing instruction for these runs: check
the disk before starting one, and clear /tmp/pytest-of-olafsson down to the
newest handful.

DO NOT UNION TWO COVERAGE RUNS TAKEN ON DIFFERENT COMMITS (2026-08-30)
------------------------------------------------------------------------
Tempting arithmetic, tried and discarded. Two batched runs exist, one of them
missing a batch, so the obvious move is to take the better of the two per
module and call the result a floor. It reads 98.68%, and it is wrong.

The reason is section 7's trap wearing a different hat. An arc is a PAIR OF
LINE NUMBERS. Between the two measured commits, 22 source files changed, so
run 1's arcs for those files name lines that are now something else -- and
counting them as covered credits the newer file for whatever the older one
executed. The 0.74 points that separated the union from the measured figure
were almost entirely that.

Restricted to files IDENTICAL in both measured revisions, the union is 98.06%
of 248,695 arcs, and the two runs differ by:

    arcs run 1 had and run 2 did not     46
    arcs run 2 had and run 1 did not     66

112 arcs out of 248,695 -- 0.045%. THE MEASUREMENT IS REPRODUCIBLE. Two runs
of the same suite on the same source agree to within a twentieth of a percent,
which is worth knowing in both directions: a coverage change smaller than
about 0.05% is noise, and a change larger than that is real and has a cause
worth naming.

So the rule is: quote one run, on one commit, and say which. Combine runs only
across files whose bytes are identical, and say that is what you did.

A MECHANISM FOR THE SEGFAULT, FOUND AND REPRODUCED (2026-09-01)
--------------------------------------------------------------------------------

A test that leaves a PARENTLESS Qt object owning a RUNNING TIMER for the
garbage collector to free will crash a LATER test's event loop.

REPRODUCED, both directions, in about a minute:

    pytest tests/qt/test_the_console_keeps_the_ai_error_analysis.py \
           tests/qt/test_track_previews.py::test_completion_handler_runs_on_the_gui_thread
    -> Fatal Python error: Segmentation fault
       Current thread ... qt_compat.py:160 in exec
                          wait_signal.py:58 in wait
                          test_track_previews.py:584

Each file passes ALONE. The faulting frame is inside `qapp.exec()` in the
SECOND file, which is why "every file was run on its own and none segfaulted"
came back clean and told us nothing: the guilty file is not the one that dies.

WHY. A `ConsolePanel` built in a test has no parent, so nothing owns it and
Python frees it whenever the collector next runs -- which can be in the middle
of another test's event dispatch. It owns `_WorkingDots`, a QTimer that is
still RUNNING. Destroying a Qt object with a live timer from inside event
dispatch is the crash. This is the same defect `spacr/qt/gc_policy.py` was
written for on the application side, one layer out: an object destroyed at a
moment nobody chose. THE SUITE DOES NOT INSTALL THAT POLICY, so tests remain
exposed to it.

THE FIX IS PER-FIXTURE AND CHEAP: stop the timer, then `close()`,
`setParent(None)`, `deleteLater()`, `processEvents()`. Stopping the timer
FIRST is load-bearing -- `deleteLater` has not run by the time the fixture
returns. Applied to `test_the_console_keeps_the_ai_error_analysis.py` and
`test_the_issue_preview_can_diagnose.py`; both crashes went away.

WHAT TO DO NEXT, in order:

1. Audit every `tests/qt` fixture that constructs a widget with no parent and
   returns it without teardown. `grep -l "= ConsolePanel()\|Panel(\|Dialog("
   tests/qt` is the starting set. Each is a candidate for the same crash.

2. DO NOT add a between-tests `gc.collect()` fixture. It was tried on
   2026-09-01 and it is the wrong answer twice over:

   * MEASURED NOT TO WORK. With the per-fixture teardown reverted and the
     collect fixture in place, the pair still dumped core. Raising it from
     `gc.collect(1)` to a full `gc.collect()` turned the crash into a plain
     failure but did not remove it. Whatever retains the panel is not a cycle
     the collector frees at that point.
   * AGAINST A DELIBERATE INVARIANT ALREADY WRITTEN DOWN HERE.
     `tests/qt/test_retained_widget_tree.py::
     test_no_boundary_fixture_forces_python_collection_over_live_qt_wrappers`
     exists to forbid exactly this, and calls itself "the CI segfault guard:
     ownership cleanup must stay on Qt's side". Its AST check inspects two
     named fixtures by name, so a third one slipped past it -- which is worth
     fixing on its own: the guard should check every autouse fixture in both
     conftests, or it only forbids what it happens to have been pointed at.

   The per-fixture teardown is therefore the fix, not a stopgap for it.

3. Only then re-measure whether the full-suite segfault is gone. Do NOT
   conclude it is fixed from a single clean run: the position moved between
   runs before, so absence on one run is not evidence.

NOTE the second symptom of the same cause: the same pairing can produce a
FAILURE rather than a crash (`test_the_issue_preview_can_diagnose.py` +
`test_track_previews.py` failed the track test without dying). So an
order-dependent FAILURE in `tests/qt` is worth checking against this mechanism
before it is assumed to be leaked global state.
