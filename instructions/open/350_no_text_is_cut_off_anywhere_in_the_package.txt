--------------------------------------------------------------------------------
THE KNOWN INSTANCE, WHICH IS THE PLACE TO START
--------------------------------------------------------------------------------

Annotate's "Load test data" tooltips overflow their popup. That is a concrete,
reproducible case and it should be fixed and TURNED INTO THE MEASUREMENT the
rest of the sweep uses -- one instance fixed by hand teaches nothing; one
instance fixed with a check that then runs over every widget finds the others.

--------------------------------------------------------------------------------
WHY A SWEEP AND NOT A LIST
--------------------------------------------------------------------------------

Text is cut off for four different reasons and they need four different fixes,
so an audit that only records "this one is clipped" produces a list nobody can
act on:

  * the string is too long for a fixed-width control  -> the string, or a
    wrapping/eliding policy;
  * the control has a fixed size that a longer TRANSLATION overflows -> the
    layout, and it will only reproduce in one of the nine locales;
  * a font scale other than 1.0 -> instruction 04 records that the tests
    measured a font scale no user has, so a check that runs at one scale
    proves nothing about the others;
  * the container does not grow -> a layout stretch or size policy.

THE TRANSLATION CASE IS THE ONE MOST LIKELY TO BE MISSED and the most likely
to be wrong in the shipped product: German and Portuguese run materially
longer than English for the same caption, and nobody reads those screens.
Any sweep that runs only in English is a partial sweep and should say so.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Write the check first, against the Annotate instance, so it is known to
   catch a real failure before it is trusted on anything else. For a rendered
   widget, `QFontMetrics.boundingRect` of the text against the widget's
   contents rect answers this without a screenshot.
2. Run it over every screen and dialog, at more than one font scale, in
   English AND in the longest locale.
3. Fix by category, not one control at a time, and record which of the four
   causes each fix addressed.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* ELIDING IS NOT ALWAYS THE FIX. A tooltip that elides has lost the sentence
  it existed to say. Prefer wrapping or a wider container for prose; elide
  only identifiers and paths, where the head or tail is enough.
* A control that grows can push its neighbour off the screen. Assert the
  CONTAINER still fits too, or the sweep trades one clipped string for
  another.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* The Annotate "Load test data" tooltip fits, asserted rather than eyeballed.
* A committed check walks every screen and dialog and reports zero clipped
  strings, at the default font scale and at the largest one preferences
  offers, in English and in the longest-rendering locale.
* Each fix names which of the four causes it was.

2026-09-02 — THE ANNOTATE INSTANCE, DIAGNOSED. IT IS A HARD-CODED HEIGHT.
--------------------------------------------------------------------------------

`spacr/qt/widgets/test_data_chooser.py`. The dialog has a description pane
under the route buttons that fills in as you hover, and it is built with

    self._description.setMinimumHeight(110)

with this comment above it:

    # A FIXED HEIGHT, so the dialog does not resize under the pointer as
    # the text changes length -- the buttons would move away from the
    # cursor that is hovering them.

THE INTENT IS RIGHT AND THE IMPLEMENTATION IS A GUESS. 110 is a number, not a
measurement: it was presumably enough for the descriptions that existed when
it was written. A longer route description -- or the same one at a larger font
scale, or in German -- needs more, and the pane does not grow because growing
is precisely what the comment set out to prevent.

THE FIX THAT SATISFIES BOTH GOALS is to size the pane to the LONGEST text it
can ever hold, rather than to a constant: walk `ROUTES`, take
`QFontMetrics.boundingRect` of each description wrapped to the pane's width,
and use the tallest. The dialog is then stable under the pointer AND cannot
clip, and it stays correct when a route is added or a caption is translated,
which a constant cannot.

`RESTING_TEXT` must be in that measurement too -- it is what the pane shows
before anything is hovered.

THIS IS THE MEASUREMENT THE REST OF THE SWEEP WANTS. The same
"boundingRect against the contents rect" comparison is what item 1 of WHAT TO
DO asks for, so fixing this one correctly produces the tool for the others
rather than just one fixed dialog.

AND IT IS AN INSTANCE OF CAUSE 2 AND CAUSE 3 AT ONCE, from the four listed
above: a fixed size that a longer string overflows, and a size that only holds
at one font scale. Worth noting because it means the sweep cannot be a single
pass at 1.0 in English -- the very first case found needs two of the four
dimensions to reproduce reliably.

2026-09-02 — CORRECTION. THE NOTE ABOVE IS WRONG. I MEASURED BEFORE THE LAYOUT
             SETTLED, AND GERMAN IS THE CLEANEST LOCALE, NOT THE WORST.
--------------------------------------------------------------------------------

The previous note's headline -- "3 clipped in English, 38 in German, 33 in
Portuguese" -- IS AN ARTEFACT AND MUST NOT BE PLANNED AGAINST. Retracted in
full, including the five named captions and the claim that cause 2 dominates
by an order of magnitude.

WHAT WENT WRONG. The probe called `app.processEvents()` ONCE after `show()`
and then read `widget.width()`. That is too early: Qt had not finished the
layout pass, so most widgets still carried a pre-layout default width and
every caption looked too big for its control. Measured directly on one
button, in German:

    after  1 processEvents:  width=111   sizeHint=171   text=156   -> "clipped"
    after  5 processEvents:  width=171   sizeHint=171   text=156   -> fits
    after 20 processEvents:  width=171   sizeHint=171   text=156   -> fits

Every "clipped" button in that list was a 111 measured against a 156 that
would have been a 171. The button row was never even close to overflowing --
715 px of buttons in an 845 px row in German -- and checking THAT is what
exposed the contradiction. Two measurements disagreeing is what caught this;
one measurement on its own looked entirely plausible.

THE REAL NUMBERS, same screens, same 1100x800 window, layout allowed to
settle over twelve event-loop turns:

    en   2 clipped        de   0 clipped        pt   3 clipped

German is the CLEANEST of the three. The opposite of what I reported.

AND THE REAL LIST IS ONE WIDGET CLASS:

    en  mask, measure         AiToggleLabel  'Time'                  +7 px
    pt  mask, measure         AiToggleLabel  'Tempo'                 +19 px
    pt  regression            AiToggleLabel  'Varredura de parâmetros' +40 px

`AiToggleLabel` is the only control that clips anywhere in four screens and
three languages, and it clips in ENGLISH too -- so this is not a translation
problem at all, it is one control whose width does not follow its caption.
That is a small, sharp fix and it is the whole of what this sweep found.

WHAT SURVIVES FROM THE RETRACTED NOTE:

  * the `_WrappedLabel` false-positive warning -- a wrapping label measured
    with `horizontalAdvance` still asks for its width on one line;
  * the observation that a plain script building screens ends in the
    `QThread: Destroyed while thread is still running` core dump, with no
    pytest involved (288/345/346);
  * that a larger font scale is still untested.

THE LESSON FOR THE SWEEP ITSELF, and it belongs in the method above: PUMP THE
EVENT LOOP UNTIL THE GEOMETRY STOPS CHANGING BEFORE MEASURING ANYTHING. A
clipping check that reads a width too early does not report a few extra
findings -- it reports a completely different package, confidently.

2026-09-02 — SECOND CORRECTION. THE FIVE SURVIVORS WERE DELIBERATE ELISION.
--------------------------------------------------------------------------------

The corrected note above named `AiToggleLabel` as "the only control that clips
anywhere" and called it a small sharp fix. IT IS NOT A DEFECT EITHER.

`AiToggleLabel` elides ON PURPOSE. `ELIDE_ABOVE_PX = 120` caps its
`minimumSizeHint` so a long secondary caption cannot force the whole row
wider -- the comment cites INVARIANTS 10, "a secondary control must not be
able to starve the primary one" -- and `sizeHint` still asks for the full text
so a roomy layout shows all of it. The behaviour is designed, documented and
correct.

AND THE CLASS OFFERS THE ANSWER MY CHECK SHOULD HAVE ASKED FOR:

    text()            the full logical caption
    displayed_text()  what it is actually painting, elided or not

with a docstring saying tests need both "to tell 'the toggle says X' from
'the toggle currently fits this much of X'". I compared `text()` against the
width, which for an eliding widget reports clipping BY CONSTRUCTION.

THE SWEEP'S ACTUAL RESULT, with the layout settled AND the check asking for
painted text:

    en 2      de 0      pt 2

and the survivors are wrapped labels, i.e. the `_WrappedLabel` false-positive
class already recorded above and still unaddressed. So the honest finding is
that FOUR SCREENS IN THREE LANGUAGES SHOW NO PROVEN CLIPPING AT ALL, and the
check is not yet sharp enough to say more than that.

`painted_text()` is now in `tests/qt/test_no_caption_is_clipped.py` so the
next use of this measurement starts with the rule rather than rediscovering
it.

THREE FALSE-POSITIVE CLASSES ARE NOW KNOWN, and any sweep must handle all
three before its numbers mean anything:

    1. measuring before the layout settles      (pump the event loop)
    2. a wrapping label measured on one line    (use the wrap-aware path)
    3. a control that elides by design          (ask for painted text)

TWO WRONG HEADLINES IN ONE NIGHT, on the same item, both confident and both
retracted within the hour. That is the honest character of this work: a
clipping check is easy to write and hard to make true, and every number it
produces should be doubted until a second, differently-shaped measurement
agrees with it. The button-row width check is what caught the first; reading
the widget's own class is what caught the second.

MEASURE'S ACTION ROW: TRIED, REVERTED, AND WHAT IT ACTUALLY NEEDS
--------------------------------------------------------------------------------

`FlowLayout` looked like the answer and is not, quite. It exists for exactly
this failure -- its own module docstring says "Qt's answer to a box it cannot
satisfy is to let the children overlap" -- and swapping the action row's
QHBoxLayout for it took one line.

IT FAILED IMMEDIATELY, on `AttributeError: 'FlowLayout' object has no
attribute 'addStretch'`, and the error is the useful part: THE ACTION ROW IS
NOT A ROW OF BUTTONS. It is eight buttons, then a stretch, then the progress

interactive and AI switches. The stretch is load-bearing: it is what holds
the switches against the right edge while the buttons stay left.

So the fix is not a layout swap but a SPLIT: the buttons into their own
wrapping container, and that container plus the stretch, the progress bar and
the switches in the horizontal row they are in now. That is a structural
change to the busiest screen in the application, in a file six test files
reach into by attribute, and it is worth doing deliberately rather than in
the same pass as the measurement.

The revert is complete -- the sweep is green at its recorded counts -- and

`KNOWN_OFFENDERS` IS NOW EMPTY. All twenty-five combinations of the sweep are

FIRST, THE CORRECTION, because the numbers this item has been planning against
were not what they looked like. The sweep read every screen after a flat
`qtbot.wait(30)`, and `QTest.qWait` ENDS ITS LOOP WITH A SLEEP, not with a pass
of `processEvents`: it processes events, sleeps 10 ms, checks the clock, and
breaks when the time is up. Whatever was posted during that last sleep is still
in the queue when the call returns, and on a module screen the thing sitting
there is the layout request raised by the language pass -- which runs a turn
after the screen is built. So the row was read carrying GERMAN captions inside
buttons still sized for the ENGLISH ones they had been constructed with, and
every one of them looked clipped. In one test, in one run:

    after qtbot.wait(30):  6 clipped, `_btn_run` 60 px wide, hint 103
    after one more wait(1): 0 clipped, `_btn_run` 103 px wide, hint 103

Nothing changed in that millisecond except that Qt was finally allowed to
deliver an event it had been holding. That is the FOURTH confident wrong
headline on this item and the second of the "measure before the layout settles"
family -- rule 1 was written down after the first one and then implemented as a
constant, which is not an implementation of it. `settle()` in the sweep is now a
loop with a stopping CONDITION: two readings of every measured widget's
geometry, 10 ms apart, that agree.

THE FIX IS THE SPLIT THE PREVIOUS NOTE ASKED FOR, WITH ONE CHANGE OF SHAPE.
`_WrappingButtonStrip` in `spacr/qt/screens/app_screen.py` is a `FlowLayout`
subclass used as a SUB-LAYOUT of the row's `QHBoxLayout`, not as a `FlowHost`
widget inside it. That distinction is the whole reason this was safe to do:

  * a widget added to a sub-layout is parented to the widget that owns the
    TOP-level layout, so every button is still a Qt child of `_actions_row`.
    `test_chaining_gui.py` asserts `screen._btn_run.parent() is
    screen._actions_row`; `_clear_page_surfaces` still has ONE widget to tag,
    so no new opaque strip appears over the backdrop; `findChildren` from the
    screen still reaches every button. A nested `FlowHost` breaks the first,
    complicates the second and was rejected on that.
  * `FlowLayout`'s own `sizeHint` is its `minimumSize` -- the widest single
    chip -- which is right for a chip strip in a column and wrong in a
    horizontal box, where a 192 px hint would let the stretch swallow the rest
    and wrap eight buttons onto five lines in a row with room for one. The
    subclass overrides `sizeHint` to ask for the whole line. THAT IS THE ONLY

2026-09-09 -- THE LAST DEFECT IS CLOSED. IT WAS A MATTER OF ORDER.
--------------------------------------------------------------------------------

    test_no_caption_is_cut_off[regression-pt-2.0]
    QPushButton 'Contagem': 144 px wide, wants 151

FOUND BY LOOKING, WHICH IS WHAT THE PREVIOUS NOTE ASKED FOR. Four fixes had
been tried and measured away and the note said to start by finding the
widget rather than by reading `file_list.py`. Doing that took one
instrumented run of the failing case:

    QPushButton 'Contagem'  w=144  hint=151
      ^1 QWidget  layout=ColumnAlignedRow
      ^2 SectionBody (QFormLayout)  ...
      header sections [209, 138, 144, 269, 133]
      items: 'Score' col 1 hint 94 span (210,138)
             'Contagem' col 2 hint 151 span (348,144)
             'Medições (.db)' col 3 hint 203 span (492,269)

So it IS the Download row, it IS `PairedFileTableWidget`, and the earlier
note's "`_example_counts_button` is None on the regression screen" was
wrong -- the alignment demonstrably ran and put three buttons over three
columns. That claim came from a probe on a screen built differently.

THE CAUSE IS THE ORDER OF TWO EVENTS, AND NEITHER IS WRONG ON ITS OWN.

    1. the row is built with its ENGLISH captions
    2. `_widen_columns_for` fits each column to its button -- ONCE
    3. the language pass replaces the captions

"Count" is 100 px. "Contagem" is 151. Column 2 was 144 -- from
`_fit_columns_to_their_headers`, fitting the HEADING -- so English fitted
and Portuguese did not, and the once-only guard meant the column was never
looked at again. Measured directly:

    ENGLISH  text='Count'     hint=100   sections [209,138,144,269,133]
    PT       text='Contagem'  hint=151   sections [209,138,144,269,133]

THE FIX IS IN TWO PARTS, and the second is what makes the first safe.

  * `ColumnAlignedRow.invalidate` now passes the event on. Qt already
    reports it -- `setText` calls `updateGeometry`, which invalidates the
    parent layout -- and the row cannot act on it itself: the header is
    read and never written there, and a layout writing back to the
    geometry it reads would re-enter itself on the resize it caused. So it
    calls a callback the header's OWNER supplied.
  * `_widen_columns_for` stopped being once-only and started REMEMBERING.
    A flag answers "have we ever done this" when the question is "has the
    user moved it since". The width this widget set is recorded, a column
    that already fits records its width as a baseline, and a column found
    at any other width is the USER'S -- permanently, not until the next
    caption grows.

    THE BASELINE IS THE HALF THAT IS EASY TO MISS. Without it, "we have
    never touched this one" and "the user has not touched it either" are
    the same state, so a column dragged narrow before any caption grew
    would be dragged back the moment one did. It failed exactly that way
    once before the sentinel was added.

    AND THE ONE-WAY DOOR IS THE OTHER HALF. Recording the width on every
    pass looks equivalent and is not: the refit triggered BY the user's own
    drag records the dragged width as ours, and the next pass then widens
    it back. Also failed exactly that way, once.

MEASURED AFTER: column 2 goes 144 -> 151 when the caption is translated,
the button is no longer clipped, and the four-locale sweep at both font
scales passes -- 208 cases, no offenders anywhere.

THREE TESTS HOLD IT, in `test_the_download_buttons_sit_over_their_columns`:
a caption that grows after the fit takes its column with it; a column the
user narrowed is not widened back; and the two rules meeting, where the
user wins. The first is written against the MECHANISM rather than against
Portuguese -- any caption that changes after the fit must re-fit, and a
test keyed on one locale would go green the day that string changed.

  THE SWEEP IS NOW GREEN IN EVERY COMBINATION IT RUNS: 4 locales x 2 font
  scales x 26 screens, and `KNOWN_OFFENDERS` is still empty.

AND THE FIX COSTS NOTHING ON THE HOT PATH, measured rather than assumed --
`invalidate` runs on every layout change, so adding work there could have
bought a readable caption with a choppy resize. 2,000 calls on the
Regression screen: 5.3 microseconds per refit and 5.5 per invalidate, which
is 0.03 % of a 60 Hz frame. Instruction 380's rule cuts both ways: a change
that makes something better by making something else slower has to say so,
and this one does not.

    built once, standalone            survives

    QApplication.sendPostedEvents(None, QEvent.DeferredDelete)

THE MECHANISM, AND IT IS AN OWNERSHIP BUG IN THE HARNESS RATHER THAN THE

function returned nothing held a Python reference to the panel: it was
collected, its C++ half destroyed its children including the dialog, and the
`DeferredDelete` already queued for that dialog was then delivered to an
object that no longer existed.

    A PARENT MUST OUTLIVE THE CHILD IT OWNS, and a test harness that
    registers the child and not the parent has inverted that. `_build_with`
    now registers every QWidget it supplied as an argument, so pytest-qt
    keeps the parent alive and tears the pair down in one place.

WHY THIS IS NOT FILED AS A PRODUCT DEFECT: in the application the panel is
owned by a screen and outlives every dialog opened over it, which is the
ordering the code is written for -- `closeEvent` returning the widgets to
`self._panel` only makes sense if the panel is still there. The crash needs
a caller that lets the panel go first, and only the sweep did that.

  IT IS STILL WORTH THE PARAGRAPH. A segfault delivered one test LATER than
  its cause, in a fixture that is doing exactly what it says, is the hardest
  shape of failure to read in this repository -- and the next person to add
  a parented dialog to any sweep will hit it. 165 pass.

AND THE LAST ONE IN FOUND A DEFECT. `RecipeDialog` in German, at both font
scales:

    QPushButton 'Aktuelle Einstellungen speichern…'  399 px wide, wants 440

Five buttons in a `QHBoxLayout` want more width than the dialog's own
`scaled_px(520)` floor once the captions are German, and Qt's answer to a
box it cannot satisfy is to shrink every child BELOW its hint rather than
to wrap. The caption goes, silently. NOT the device-pixel class this file
found seven of -- that minimum was already scaled.

FIXED THE WAY THIS PACKAGE ALREADY FIXES IT. `app_screen._WrappingButtonStrip`
records the identical defect on the module action row, with its own numbers
(a single box made that row's minimum 1,092 px in German against 908 in
English), and the remedy is that buttons wrap instead of squeezing. The
recipes row is a `FlowLayout` now.

WHAT IT COST, stated because a fix that quietly changes a layout is worse
than one that says so: the `addStretch(1)` between {Save, Import} and
{Share, Delete, Apply} is gone -- a flow layout has no notion of it. That
grouping was a nicety; a caption nobody can read is not.

VERIFIED THAT ENGLISH DID NOT MOVE, which is the half a wrap fix can break:
after the change all five buttons sit on ONE row at exactly their size
hints -- 163, 78, 72, 66 and 60 px, none squeezed. 173 dialog cases pass.
