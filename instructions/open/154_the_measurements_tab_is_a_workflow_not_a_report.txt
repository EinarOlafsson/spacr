A. THE FREEZE. FOUND, AND IT IS THE WHOLE OF IT.
--------------------------------------------------------------------------------

`measurement_scan_panel.py:992::merge` calls `merge_across_databases(...)`
DIRECTLY, on the GUI thread. Counted in that file:

    JobRunner / QThread / start_job occurrences:  0

So the entire merge -- four databases, 226,467 cell rows before any join, three
joined tables, and an aggregation over ~85 defaulted columns per table -- runs
inside the button's own click handler. Qt cannot paint, cannot show a spinner
and cannot accept a cancel until it returns. THE APPLICATION IS NOT HUNG; it is
working, and there is no way for it to say so. That is exactly the report.

EVERY OTHER LONG JOB IN THIS APPLICATION ALREADY HAS THE ANSWER: `JobRunner`,
which this panel is the one that does not use. So this is not new machinery,
it is an omission -- and instruction 140 asks for the same thing on the
regression fit, so both should land on one idiom rather than two.

WHAT IT MUST DO: run off the GUI thread, say what stage it is on (reading
plate3, joining pathogen, aggregating 85 columns), show rows processed against
rows expected -- the plan ALREADY KNOWS the total, it prints it -- and be
cancellable, leaving nothing half-written.

B. THE PREVIEW IS TRUE AND UNREADABLE
--------------------------------------------------------------------------------

The plan text is correct and nobody can use it. It prints EIGHTY-FIVE column
names inline for `nucleus`, then EIGHTY-FIVE more for `pathogen` -- a hundred
and seventy names in a 190-pixel-tall read-only box -- so the three lines that
matter (what joins how, how many rows, what the anchor is) are buried in
`nucleus_channel_2_channel_3_M2_correlation_85` and its brothers.

    "85 columns match no aggregation rule and would take the default (mean)"
    is the SENTENCE. The list is the EVIDENCE, and evidence goes behind a
    disclosure, not in front of the summary.

Collapse it: the count, the kinds it breaks into, and a "show them" that opens
the full list. The house already has this idiom -- a foldable section -- and
instruction 110 is about exactly this failure elsewhere.

--------------------------------------------------------------------------------
C. `file_name` AND `path_name` CANNOT TAKE A MEAN, AND THE PANEL SAYS THEY WILL
--------------------------------------------------------------------------------

This is the one to fix first, because it is a correctness claim rather than a
presentation one. Both defaulted lists BEGIN with

    file_name, path_name

which are TEXT. "Would take the default (mean)" is not merely unhelpful for a
string, it is impossible, and a user reading it has been told something about
their data that cannot happen. Either the aggregation silently drops them (so
the sentence is wrong), or it attempts a mean (so the merge is wrong).
FIND OUT WHICH AND SAY THE TRUE THING -- and per instruction 79 they should be
classified rather than defaulted: an identifier column is carried through as
`first` when it is constant within the group and REFUSED when it is not,
because a file name that differs across the cells being combined is a genuine
ambiguity and picking one silently invents provenance.

THE DEEPER POINT: a "no rule matched" bucket that mixes 83 numeric texture
features with 2 filesystem paths is not one bucket. Classify by dtype before
reporting, and the 85 becomes "83 numeric measurements -> mean" and "2 text
identifiers -> first, or refused". That is a sentence a user can approve.

--------------------------------------------------------------------------------
D. THE PLATE IDS READ `pplate1`
--------------------------------------------------------------------------------

    plate1: 60,816 rows, plates pplate1

The label is `plate1` and the id beside it is `pplate1`. spaCR's well key is
`p<plate>_<row>_<column>` (submodules.py:826 builds it), so a plate already
named `plate1` becomes `pplate1` when the prefix is applied to a name rather
than to a number. Establish which is stored and which is displayed, and show
the user the plate as the plate is called. A doubled prefix in a preview is
small; the same doubling in a JOIN KEY is not, and instruction 145 (one key
vocabulary) is where that risk lives. CHECK WHETHER THE KEY ITSELF IS AFFECTED
before deciding this is cosmetic.

--------------------------------------------------------------------------------
E. "Nothing to scan. Load a run whose wells carry both the gene assignment and
   the measurement"
--------------------------------------------------------------------------------

`measurement_scan_panel.py:1202`. The maintainer got this WHILE having four
measurement databases loaded, which means either the sentence is wrong about
what is missing, or it is right and cannot say what to DO about it. It names
two things a well must carry and no way to give it them.

Say which half is absent -- there is no gene assignment, or there is no
measurement, or the two exist and do not join -- and if they do not join, name
the key that failed and show one example from each side. "Nothing to scan" with
a generic remedy is the same defect as 153's "opened from disk": a message
asserting a cause it has not checked.

--------------------------------------------------------------------------------
F. THE WORKFLOW THE TAB IS FOR, AS FOUR STEPS
--------------------------------------------------------------------------------

The request states the purpose plainly: "the point of the measurements tab is
to merge measurements so that regression can be run on any column in the
databases." The tab should therefore READ as those steps, in order, with the
state of each visible:

    1. LOAD the measurement databases            (109's working set -- built)
    2. MERGE THE TABLES within each database     (cell/nucleus/pathogen/cyto)
    3. MERGE THE DATABASES into one frame        (plates side by side)
    4. PICK A COLUMN and regress on it

Today steps 2 and 3 are one button and one wall of text, and step 4 is not on
this tab at all, so the tab ends without reaching its own purpose. A user who
has merged has no idea what to do next, which is most of "i dont understand how
this is all set up".

  * 4b. A SELECTION OF COLUMNS, EACH ITS OWN RUN. "do regression on a selection
    of columns each gets saved as a run that i can evaluate." So the column
    picker is multi-select, each column produces ONE run with its own folder
    and its own row in the Runs tab, and they are comparable afterwards -- which
    is what the Runs tab exists for. A queue of N fits is a long job: it gets
    140's progress and cancellation, and a fit that fails does not take the
    other N-1 with it.
  * THE MERGED FRAME MUST SURVIVE THE TAB. Regression on "any column in the
    databases" means the merge is an artefact, not a preview: written once,
    named, reusable, and not recomputed for every fit.

--------------------------------------------------------------------------------
G. A RUN THAT JUST RAN SHOULD BE THE RUN THAT IS LOADED
--------------------------------------------------------------------------------

"the cell table just says that no regression results are loaded. but i just ran
a regression so that should be loaded automatically" -- `cell_montage_view.py:873`.

    * A run that finishes BECOMES the loaded run. No step in between.
    * ONE run in the folder means that run is loaded. There is nothing to
      choose between.
    * SEVERAL runs means the Runs tab carries the choice -- one control saying
      which is loaded, per the request -- and the choice is visible from the
      views that depend on it, not only from the tab that sets it.
    * AND A RUN CAN BE LOADED DELIBERATELY, including one from an earlier
      session on disk. That is 153's other half: a run on disk is a first-class
      run, not a degraded one.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Merging four databases keeps the window responsive, names the stage it is
  on, counts rows against the total it already printed, and can be cancelled.
* The plan's summary fits in the box; the 170 column names are one click away.
* No column is reported as taking a mean unless a mean is what it will take;
  text identifiers are named as identifiers and are carried or refused.
* A plate called `plate1` is shown as `plate1`, and the join key is verified
  to be unaffected either way.
* "Nothing to scan" names which half is missing, or which key failed to join.
* From a fresh start: load 4 databases, merge, pick 3 columns, get 3 runs, and
  evaluate them against each other in the Runs tab, without leaving the app.
* A finished run is the loaded run, with no further action.

2026-08-18 - A, B, C, D AND E SHIPPED. F AND G ARE NOT STARTED.

A. THE FREEZE IS GONE, AND IT WAS THE WHOLE OF IT.

`DatabaseMergePanel` now holds a `JobRunner` (the idiom the other twenty-odd
screens already use) and the Merge button is wired to `start_merge`, never to
`merge`. `merge` is still there and still blocks -- it is the synchronous
entry point for a headless caller and for a test that wants the frame on the
next line -- and both go through the same `_prepare_merge` / `_merge_worker` /
`_finish_merge` triple, so the two paths cannot diverge.

MEASURED IN THE REAL WIDGET, not in a test. Four databases, 160,000 cells,
480,000 rows read across cell+pathogen, driven by clicking the actual button:

    merge took 6.2s; the GUI kept running for 100 event-loop passes
    the progress label changed 16 times while it ran
    plan box: 10 lines (it used to be the same 10 plus 170 column names)

The stages name the table AND the database ("reading cell from plate3"), and
the row count is against the plan's OWN total -- `describe_merge` is now run
for every chosen table BEFORE the first read, so the denominator exists before
the first row does. That also moved a missing table's failure to before the
expensive anchor read rather than after it.

Cancellation: `threading.Event`, checked between sources and between stages.
`read_merged` raises the new `MergeCancelled`, which is deliberately NOT a
`MergeRefused` -- a refusal is an answer about the data and a cancel is the
user changing their mind, and wording them the same puts "Refused" in front of
somebody who pressed Stop. Nothing is written until the merge RETURNS, so a
stopped merge leaves the previous frame exactly where it was; there is a test
that asserts `panel.frame is` the earlier object.

C. WHAT ACTUALLY HAPPENED TO `file_name` AND `path_name` -- MEASURED.

    NEITHER. They were not dropped and no mean was attempted.

`roll_up` calls `aggregation_plan`, which asks `is_numeric_dtype` FIRST, so a
text column takes `TEXT_AGGREGATION` = `first` whatever its name. They reached
the merged frame as `pathogen_file_name` / `pathogen_path_name` carrying the
first child's value.

SO THE MERGE WAS RIGHT AND THE SENTENCE WAS WRONG -- but only the PRE-merge
sentence. `merge_report` filtered on the actual plan and was already correct;
`_table_notes` (the plan) walked column NAMES against AGGREGATION_RULES and
never looked at a dtype, which is why the false claim appeared only before the
merge and vanished after it. Reproduced before the fix:

    pathogen: 3 column(s) match no aggregation rule and would take the
    default (mean) - file_name, path_name, texture_thing_85

The bucket is now split by dtype before it is counted, from
`multi_database.column_kinds` (one PRAGMA, no rows read), into
numeric -> mean / text identifier / no declared type. The third bucket is
named rather than folded into either: a column SQLite was given no type for
cannot be promised either treatment.

AND THERE WAS A REAL CORRECTNESS GAP UNDERNEATH THE SENTENCE. The `first` was
silent even where the identifier was NOT constant within the group. Per
instruction 79 item 2 that is a genuine ambiguity: such a column is now LEFT
OUT and named with an example from the offending group, in BOTH merges (the
panel's `merge_across_databases` and the headless
`plate_measurements.merge_plate_databases`), under one shared helper
`ambiguous_identifiers`. `on_ambiguous_identifier='first'` restores the old
pick for a caller who asks for it in writing. Only TEXT columns are examined:
`object_label` also takes `first`, by the identity rule, and it is SUPPOSED to
differ across three pathogens -- refusing it would delete the column the rules
carry verbatim so a row can be traced back.

B. The plan and the report each split into a COUNT (in the box) and the NAMES
(behind a collapsed `Section`, the house foldable). `plan_text()` and
`merge_report()` still return the whole statement for a headless caller, and
`panel.statement()` is what a test reads when it wants to know whether the
panel said something at all. One existing assertion moved from
`report.toPlainText()` to `statement()`; the requirement it guards is
unchanged.

D. THE PLATE ID IS NOT COSMETIC, AND THE PANEL WAS NOT THE ONE DOUBLING IT.

Measured: a database whose `plateID` holds `plate1` shows `plate1`; one that
holds `pplate1` shows `pplate1`. Nothing in the panel, in `describe_merge` or
in `read_merged` adds a prefix. **The doubling is in the data.** So:

  * every join INSIDE the merge is unaffected -- both sides read the same
    stored value out of the same file;
  * the join to the REGRESSION side is affected, because
    `utils.correct_metadata` already rewrites `^pp` -> `p` in `plateID`,
    `prc` and `prcfo` on the score and count CSVs and nothing did it for a
    measurements database. That is the recorded zero-row join that died two
    hundred lines later in a plot with `KeyError: 0`, arrived at from the
    other direction.

The plate is now DISPLAYED as it is called, via the new
`multi_database.canonical_plate_id`, and the stored id is named beside it with
the join risk spelled out. `canonical_plate_id` is pinned by test to give the
same answer as `correct_metadata` for every input, so the one rule stays one
rule (instruction 145).

E. "Nothing to scan" now names which half is missing and checks it:
`why_nothing_to_scan` distinguishes no provider wired / no run loaded / a run
whose table has no rows, and in every case says what IS attached and whether
it has been merged. When a scan is REFUSED and both halves exist,
`what_is_available` runs `describe_key_overlap`, which names the key
(`prc`, or plateID_rowID_columnID) and shows one example from each side -- and
recognises the case where the two sides name the same wells and differ only by
the `pp` doubling, which is section D seen from here.

WHAT SHIPPED, in `sweep_runs.py` (the Runs tab) and `cell_montage_view.py`

* A `loaded` COLUMN, first in `PREFERRED_COLUMNS`. One row carries the mark
  and the rest are blank. A COLUMN AND NOT A CHECKBOX, and the reason is worth
  recording: the table is the shared `ResultsTable`, which draws text items,
  and a second table implementation to carry one tick box is a second set of
  bugs. It reads the same way and it sorts, filters and copies with the row.

* A RUN THAT FINISHES BECOMES THE LOADED RUN. `update_run(handle,
  status="ok")` moves the mark. A run still going does not take it -- a row
  claiming to be loaded is a click that opens nothing -- and neither does one
  that failed.

* ONE RUN IS THE LOADED RUN. `_settle_the_loaded_run` runs inside every
  rebuild: if the marked run is gone the key is cleared, and if exactly one
  row is loadable it takes the mark. Several with no choice made says so out
  loud -- "No run is loaded — pick one to show it everywhere else" -- rather
  than leaving an empty column that looks like a broken feature.

* THE CHOICE REACHES THE VIEWS. `set_loaded_run` and picking a row both emit
  `trial_activated`, which is what `app_screen._show_trial` already listens to,
  so the results panel, the Summary tab and the figure grid follow. Verified
  by driving a real `AppScreen`: the panel's path, the summary text and
  `CellMontageView.loaded_run_name()` all move to the chosen run.

* A RUN ON DISK IS FIRST-CLASS. A "Load run…" button beside Reload:
  `load_run_from_disk(folder)` resolves the folder (a parent works), gives it
  a row with `source = "on disk"`, reads its settings back through
  `refit.settings_of_run` so it is described by the SAME columns as a session
  run, marks it loaded and shows it. Opening the same folder twice is one row.
  A folder with no results table names the files it looked for and where.

* THE CELLS TAB STOPS TELLING ONE STORY FOR TWO SITUATIONS. `reason()` split
  "No regression results are loaded" into `NO_RUN_LOADED` (nothing at all --
  and it names the Runs tab and Load run… as the way out) and
  `RESULTS_WITHOUT_A_FOLDER` (a coefficient table on screen with no run folder
  behind it, where the old sentence contradicted what the user was looking
  at). When it is ready it names the run it would build from.
