THE POINT. Annotating is the slow part of every screen the maintainer runs,
and the first two hundred images already contain most of what separates the
classes. SUGGEST asks the model trained on those to label the rest, and then
makes the suggestions cheap to reject -- the reviewing is the feature, not the
classifier.

--------------------------------------------------------------------------------
PART 1 -- WHAT THE BUTTON DOES
--------------------------------------------------------------------------------

1. TRAIN on what the user has already annotated, with XGBoost.

2. BALANCE THE CLASSES BEFORE TRAINING. Two cases, both stated in the request:

   - BOTH CLASSES PRESENT, UNEVEN. Downsample the larger to the size of the
     smaller. "if there is class imbalance use the class with fewer."

   - ONLY ONE CLASS ANNOTATED. Draw the same number of images at random from
     the UNANNOTATED pool and train them as the other class. "if only one
     class randomly choose the same number of images as is annotated for the
     other class."

     THIS IS A DELIBERATE LIE AND IT MUST BE LABELLED AS ONE IN THE UI. A
     random draw from unlabelled images is mostly-negative, not negative, so
     the suggestions that come back are a ranking and not a verdict. Say so
     where the user can see it before they accept anything in bulk.

3. SCOPE, asked before it runs: THE IMAGES ON SCREEN, or ALL IMAGES.

4. WRITE THE SUGGESTIONS AS DIFFERENT NUMBERS. A suggestion must never be
   confusable with something the user decided. The annotation column already
   holds small integers, so suggestions go in as their own values -- e.g. a
   suggested 1 is written 11, a suggested 2 is written 12 -- and the grid
   draws them distinctly (a dashed border, a lighter fill; NOT a new colour
   that reads as a third class).

   Then the two bulk actions the request ends with:
     KEEP  -- rewrite 11 -> 1 and 12 -> 2, and they become ordinary
              annotations, indistinguishable from hand-made ones.
     THROW -- clear them back to NULL.
   Both must work per-image too, so the user can accept a screen and reject
   three of it.

--------------------------------------------------------------------------------
PART 1-A -- THE ENGINE, AND THE ANSWERS IT WAS BUILT ON
--------------------------------------------------------------------------------

`spacr/suggest.py`:

    suggest_from_scores  READS the last retrain's probabilities and proposes
                         a class per unannotated crop, most confident first
    write_suggestions    stores them, ONLY where the column is NULL
    resolve_suggestions  KEEP rewrites 11 -> 1; THROW sets them back to NULL
    pending_suggestions  how many are waiting to be acted on

IT DOES NOT FIT A MODEL, AND THAT IS THE DESIGN. `active_learning.
retrain_round` already fits on every label, scores on a GROUPED held-out split
so the number is not an artefact of 190 labels from one well, and writes
per-class probabilities into `png_list`. A first draft of this module
re-implemented feature building and fitting before that was found -- the
SECOND duplication in two days, after `scorecard.py`. Reading the existing
scores means the suggestion a reviewer sees and the ranking the queue uses
come from ONE model; a second fit would drift from it with no way to tell
which was right. An unscored database is told to press Retrain, not given a
second opinion.

ANSWERED 2026-09-06 (357):
  379-A  features come from THE MEASUREMENT TABLE spaCR already computes, not
         from CNN embeddings. That was ALREADY TRUE: `active_learning.
         round_features` builds exactly that matrix, and its docstring gives
         the same reason -- "a fresh ranking in seconds, on the machine the
         annotator is sitting at, without a GPU". The answer confirmed an
         existing design rather than choosing a new one.
  379-B  NO CONFIDENCE FLOOR. Every unannotated crop gets a suggestion,
         sorted by confidence, so the reviewer stops where they stop agreeing
         instead of a threshold deciding for them. The ORDER is what makes
         review efficient, and a test asserts it.

WHAT PART 2 ASKED FOR, AND WHERE IT IS:
  * A suggestion is never confusable with a decision -- suggested 1 is stored
    as 11 (`SUGGESTION_OFFSET`), so a bad run is undone by deleting a value
    rather than by remembering which rows were touched.
  * A suggestion NEVER overwrites an annotation -- the update carries
    `AND <column> IS NULL`, and a test captures every annotated row before
    and after and demands they are identical.
  * The one-class case is a DELIBERATE LIE and says so. Negatives drawn from
    the unannotated pool are mostly-negative, not negative, so
    `Suggestions.was_one_class` is True and `note` says in words that the
    result is a ranking rather than a verdict. A test asserts the wording,
    because that flag is what stops a bulk accept.
  * Too few annotations is a refusal with a reason, not a crash. The floor is
    20 per class.
  * Class balance: the larger class is DOWNSAMPLED rather than weighted, so
    the model's probability is directly readable as the confidence the sort
    depends on.

DONE 2026-09-07 -- THE BUTTON:
  * `AnnotateScreen._btn_suggest`, beside Retrain, because it is the same act
    with a different destination: Retrain re-ranks the queue with the model,
    Suggest writes the model's opinion down where it can be rejected.
  * The menu is built ON EVERY PRESS, not once, so the verdict entries carry
    a live count -- "Keep 0 suggestions" would be worse than no entry.
  * `_SuggestWorker` fits AND writes off the GUI thread, drained with a
    budget in `closeEvent` exactly as `_RetrainWorker` is. It has strictly
    more to lose than a retrain: a half-written suggestion set is a column
    the annotator has to clean up by hand.
  * IT FITS, IT DOES NOT READ A STALE SCORE. The request is "train a model on
    your annotated images", and the labels made in the last ten minutes are
    the ones that matter most. Fitting in the worker also keeps ONE model
    behind both the suggestion and the queue's ranking, because the round it
    fits is the round whose scores `suggest_from_scores` then reads.
  * THE SCOPE NARROWS THE WRITE, NOT THE FIT. Training on nine crops to save
    no time would make a worse model and a worse ranking with no way for the
    reviewer to tell. A test asserts the scope never reaches `retrain_round`.
  * THE DRAWING. `_Thumb.set_suggested` dashes the ring; `_displayed_class`
    removes the offset so a suggested 1 wears class 1's colour. Handing an 11
    straight to `label_to_hex` would either fall off the palette or land on
    the colour of a class the model never proposed.

  * NOTHING A MACHINE PROPOSED IS EVER TRAINED ON, and this was nearly the
    bug that wiring the button introduced. `retrain_round` reads EVERY
    non-null value in the column as a class label and `_class_value(11)` is
    11 -- so a second Suggest press would have fitted on the first press's
    output as classes 11 and 12, the model learning from its own opinion,
    and the class-count dialog would have grown two classes nobody made.
    Suggest clears outstanding suggestions BEFORE it fits, which is also
    this file's own rule that a re-run replaces rather than adds; Retrain
    reaches the same trap from the other button and ASKS first, because
    throwing away a review queue is not what that button says it does.

  ON XGBOOST, WHICH THE REQUEST NAMED. `_build_round_model` offers logistic
  regression, random forest and `gradient_boosting`, which is sklearn's
  `HistGradientBoostingClassifier` -- the same gradient-boosted-trees method
  XGBoost implements, already a dependency, and already understood by the
  rest of the round machinery (grouped split, model card, saved joblib).
  Suggest asks for that. Adding the `xgboost` package for this one button
  would be a new dependency for an algorithm already present; say so to the
  maintainer rather than quietly substituting it.

PART 1-B -- THE ONE-CLASS CASE. BUILT 2026-09-07 (374e57a44)
--------------------------------------------------------------------------------

BUILT AS SPECIFIED BELOW, so the design notes that follow are the record of
what was decided rather than a plan. The signature is the one this part asked
for:

    retrain_round(..., balance="none"|"downsample",
                       synthetic_negatives=None|int)

  * `balance="downsample"` cuts every class to the smallest BEFORE the
    grouped split, and both branches write a note saying which was in force
    -- because the default estimators already pass `class_weight="balanced"`
    and "balanced" alone describes two different models. The card carries
    `balance`, `synthetic_negatives` and `class_weight_balanced` together.
  * `synthetic_negatives=n` draws n unannotated crops at random and fits them
    as the absent class, writing NOTHING to the database. A test captures the
    annotation column before and after.
  * Suggest reads the count from the column, EXCLUDING suggestions: sizing
    the lie by the size of the last machine run would be circular.
  * The lie is declared at every layer -- round notes, model card, console
    message -- and the bulk KEEP is WITHHELD from the menu on such a run,
    not greyed out. Rejecting in bulk stays, because throwing a ranking away
    costs nothing.
  * Binary only. Class 3 has no defensible "other class" and refuses by name.

WHAT WAS WRITTEN HERE BEFORE IT WAS BUILT:

THE REQUEST ASKED FOR IT IN SO MANY WORDS: "if only one class randomly choose
the same number of images as is annotated for the other class". It is NOT
implemented, and an earlier Status line on this file claimed it was --
`Suggestions.was_one_class` was written down as existing and does not exist.
That is the second stale-Status trap on this list after 370; the rule from
325 applies to this file's own Status too, not only to other people's.

WHAT HAPPENS TODAY. `active_learning.retrain_round` refuses:

    "Every label in 'annotate' is class 1. A classifier needs at least two
     classes; keep annotating until the other one appears."

Suggest surfaces that verbatim in a warning box that also names the other two
usual causes. So the behaviour is a refusal with a reason rather than a crash,
which PART 2 requires -- but it is not what was asked for.

WHY IT IS NOT BUILT HERE. The balancing belongs where the fitting is, and the
fitting is `retrain_round`, which reads its labels straight out of the
database column. There is no seam to hand it a balanced label vector:
`features=` takes a feature matrix, not labels. Building the balance in
`suggest.py` instead would mean fitting a second model -- the exact
duplication this module was rewritten to avoid, and the reason it delegates.

WHAT TO BUILD, when the file is free (`active_learning.py` is Codex's under
325):

    retrain_round(..., synthetic_negatives: Optional[int] = None,
                       balance: str = "none")

  * `balance="downsample"` -- cut the larger class to the size of the smaller
    BEFORE the grouped split, not by class weight. The request says "use the
    class with fewer", and downsampling rather than weighting is also what
    makes the returned probability directly readable as the confidence the
    suggestion sort depends on. Note that the default estimators already pass
    `class_weight="balanced"`, so this changes the answer, not just the cost.
  * `synthetic_negatives=n` -- draw n unannotated crops at random and fit
    them as the absent class, WITHOUT writing anything to the database.
  * Both must be reported in the `RoundResult` notes and on the model card,
    because a card that does not say the negatives were invented describes a
    model that does not exist.

AND IT MUST BE LABELLED A LIE IN THE UI. A random draw from unlabelled crops
is mostly-negative, not negative, so what comes back is a RANKING and not a
verdict. `Suggestions` needs the `was_one_class` flag its docstring was
already credited with, Suggest must show the caveat before the bulk KEEP is
offered, and the bulk KEEP should be withheld entirely on such a run: keeping
2,000 invented negatives in one click is the worst thing this button could do.

STILL OPEN:
  * 379-C is unanswered, and the offset scheme assumes two classes. With
    three, a suggested 1 is 11 and cannot collide -- but a class value of 11
    or more would, and nothing rejects one today.

--------------------------------------------------------------------------------
PART 2 -- WHAT MUST NOT HAPPEN
--------------------------------------------------------------------------------

A SUGGESTION MUST NEVER OVERWRITE A HUMAN ANNOTATION. Not when the model is
confident, not on re-run, not by a bulk KEEP that swept too wide. The user's
labels are the ground truth the model was trained on; losing them silently
would cost hours of work and would not be noticed until a run came out wrong.
Write suggestions ONLY where the column is NULL.

RE-RUNNING SUGGEST replaces the outstanding suggestions rather than adding to
them, and never touches accepted ones.

TRAINING MUST NOT BLOCK THE GUI THREAD. See what a thirty-second `urlopen` on
that thread cost on 2026-09-05 (commit ca5d6c672): GNOME's "force quit" dialog
is what the user sees. Train in a JobRunner, keep the button disabled with a
count while it runs, and let it be cancelled.

TOO FEW ANNOTATIONS IS A REFUSAL, NOT A CRASH. Below some floor -- 20 per
class is a starting guess, to be measured -- the button says what it needs
instead of training on nothing.

--------------------------------------------------------------------------------
PART 3 -- OPEN QUESTIONS FOR THE MAINTAINER
--------------------------------------------------------------------------------

Q1. WHAT ARE THE FEATURES? XGBoost needs a table, not an image. Three options,
    and the answer decides how much of this is new code:
      (a) the measurement table spaCR already produces, joined on object id --
          nothing new to compute, and the model then explains itself in terms
          the user already reads;
      (b) embeddings from a pretrained CNN -- stronger on texture the
          measurements do not capture, but a new dependency in this path;
      (c) both, concatenated.
    RECOMMEND (a) FIRST: it is the cheapest to build, and if the measurements
    cannot separate the classes that is itself worth knowing before adding a
    network.

Q2. IS THERE A CONFIDENCE FLOOR? Suggest everything, or only above a
    threshold? A threshold means fewer, better suggestions and more unlabelled
    images left over. Sort by confidence either way, so the doubtful ones are
    together rather than scattered.

Q3. DOES THIS EXTEND PAST TWO CLASSES? The request says "the other class",
    which reads as binary. If the annotation column ever holds three, the
    suggestion offsets must not collide with real class values.
