--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Measured on one Mask screen, in English, counting distinct label and button
strings against the catalogue:

    catalogue entries                 267
    distinct strings on ONE screen    230
    of those, in the catalogue         10   (4%)

Ten languages are bundled and every one carries all 267 strings. So
choosing Swedish today translates menus and buttons -- Run, Settings -- and
leaves every setting label on every module screen in English.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A half-translated interface is arguably worse than an untranslated one: the
user is told the program speaks their language, and then the part they work
in does not. It is also the part where a bad translation costs most --
"Anisotropy" and "Flow threshold" are domain terms, and a wrong rendering
is worse than the English word a microscopist already knows.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. DECIDE HOW FAR, which is the real content of this task:
     (a) chrome only, as today -- and say so, rather than implying a fully
         localised program;
     (b) chrome plus setting LABELS -- roughly 230 strings per screen, and
         where the value is;
     (c) everything, including the ~700 tooltips of instruction 61.
   (c) is a translation project rather than a feature.
2. Whoever decides needs to read the languages. Machine-translating domain
   terms and shipping them is the failure mode to avoid.
3. Count translated strings per language before claiming any language is
   supported. Today all ten are complete against a 267-entry catalogue,
   which is a different claim from "spaCR is available in ten languages".
4. Check non-Latin scripts (zh_CN, hi, ko) render in the bundled fonts, and
   that longer German strings do not break layouts.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Choose Swedish, open Mask, and the settings column is in Swedish -- not
just the buttons around it. The per-language counts are recorded somewhere
a reader can check before trusting a language.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Not started, and deliberately not begun by machine translation. The
decision at step 1 comes first; translating 230 strings into ten languages
before deciding whether that is the right scope would waste most of it.

--------------------------------------------------------------------------------
2026-08-09 - THE ANSWER TO "HOW FAR": EVERYTHING, AND THE API TOO
--------------------------------------------------------------------------------

  "for each translation, as much as possible should be translated including
   tooltips and settings names and the API should be translated as well. fo
   the api the translated docstrings canot live in the functions themselcves.
   needs to be somwhere else, otherwise it gets to cluttered."

That settles step 1: option (c). Scope is chrome + setting NAMES + the ~700
tooltips + the API documentation.

THE ARCHITECTURAL CONSTRAINT IS THE USEFUL PART, and it is right: a
docstring carrying ten languages is unreadable as source, and source is
read far more often than the rendered page. So translated docstrings live
OUTSIDE the functions.

That means a catalogue keyed by qualified symbol name --
`spacr.core.preprocess_generate_masks` -> {language: text} -- in the shape
`spacr/qt/i18n.py` already uses for UI strings, and a docs build that
substitutes them. Two things to settle before building it:

  * WHAT IS THE KEY. A qualified name is stable until someone renames or
    moves a function, at which point the translation silently detaches. A
    test that every catalogue key still resolves to a real symbol is the
    cheap defence, and it is the same shape as the tooltip link test.
  * WHO BUILDS WHICH LANGUAGE. Sphinx builds one language per run, so this
    is N builds and N output trees, and the API link in every tooltip has
    to point at the reader's language rather than at English.

SIZE, measured so nobody starts blind: 267 catalogue entries today, ~700
tooltips, and the API surface is 125 module pages. Translating the
tooltips alone is roughly 7000 strings across ten languages. This is a
project with a budget, not a task -- and the domain-term warning above
stands: "Anisotropy" translated badly is worse than the English.
