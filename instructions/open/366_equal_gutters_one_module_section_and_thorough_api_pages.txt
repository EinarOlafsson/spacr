PART 1 -- THE VERTICAL GUTTER MUST MATCH THE HORIZONTAL ONE
--------------------------------------------------------------------------------

362 made every tile identical and six to a row. The HORIZONTAL gutter is
solved and solved deliberately: each tile is `TILE_SIZE` centred in a
`BUTTON_SIZE` canvas with `TILE_PADDING` transparent margin, rows are joined
with RST's zero-width `\ ` separator, so two margins meet between
neighbours and the gap is exactly `2 * TILE_PADDING`.

THE VERTICAL GUTTER IS NOT CONTROLLED AT ALL. Each row is its own RST
paragraph, so the space between rows is the browser's paragraph margin plus
the line box -- a number nothing in this repository sets, and one that has
no reason to equal `2 * TILE_PADDING`.

  DO NOT GUESS AT IT. Measure the rendered gap on the real GitHub page
  before and after. GitHub's own stylesheet is what decides this, a local
  docutils render will not show it, and 362's part 1 was preceded by two
  confidently wrong measurements taken against a page that had not settled.

  THREE APPROACHES, in the order they should be tried:

  a. ONE PARAGRAPH, NO BLANK LINES between rows. All 21 substitutions in a
     single flowing run, wrapping naturally at six because 6 x 16% = 96% and
     a seventh does not fit. Vertical spacing then comes from the line box
     rather than paragraph margins. RISK: the wrap is the browser's decision,
     not ours, so a narrow viewport or a different font size can produce five
     or seven per row. The 6-per-row requirement and this approach may be in
     direct conflict -- establish which the maintainer wants more before
     building it.

  b. AN RST TABLE, one tile per cell. Puts both gutters under the same
     mechanism. RISK: GitHub styles table cells with borders and padding of
     its own, which may be worse than the problem.

  c. BAKE THE VERTICAL MARGIN INTO THE CANVAS. If the residual paragraph
     margin proves to be a constant, reduce `TILE_PADDING` and add the
     difference to the canvas height so the drawn gaps come out equal. Ugly,
     exact, and the only one that does not depend on GitHub's CSS staying
     put. Record the measurement if this is chosen, because the number is
     otherwise unexplainable.

PART 2 -- MAKE MASKS KEEPS ITS SECTION; NO OTHER MODULE GETS ONE
--------------------------------------------------------------------------------

The README currently has a "Make Masks" subsection listing its nine tools
(Brush, Erase, Erase object, Wand +, Wand -, Draw, Divide, Zoom, Recrop) and
what three of them do. It is the only module with prose of its own, and the
maintainer wants that kept -- Make Masks is a manual tool whose vocabulary a
reader needs before they open it -- while every other module's explanation
lives behind its tile in the API.

  SO THE WORK IS SUBTRACTIVE IN THE README AND ADDITIVE IN THE API. Check
  what other per-module prose has accumulated: the "Core workflow" section
  currently describes all six pipeline modules in a bulleted list. That list
  IS per-module explanation, and by this instruction it belongs in the API.
  Confirm with the maintainer whether the six-line summary goes too, or only
  longer sections -- the request says "no other moduals" get a section, and
  a bulleted list is arguably not a section.

  THE TEST `test_readme_keeps_the_feature_catalog_curated_and_points_to_detail`
  asserts "The primary workflow comprises six modules" is present. If that
  list goes, that assertion goes with it, and the editorial word ceiling in
  the same test should come DOWN to lock in the reduction rather than leave
  the freed budget available for new sprawl.

PART 3 -- "A THOROUGH EXPLANATION IN THE API" FOR EVERY MODULE
--------------------------------------------------------------------------------

This is the largest part and the one that makes parts 1 and 2 safe: text is
only being REMOVED from the README on the promise that it is better said in
the API, so the API has to actually say it first. Do part 3 BEFORE part 2.

Every tile in the grid links to an API page. Those links already exist and
`test_every_workflow_button_tracks_the_home_screen_registry_and_api` pins
them, so the destinations are right; the question is whether what is THERE
is worth arriving at.

  MEASURE IT FIRST, per module, and write the numbers down: does the landing
  page open with prose a user can read, or with an autoapi member list? Does
  it say what the module is for, what it needs as input, what it produces,
  and which settings matter -- or only what its functions are called?

  WHAT "THOROUGH" SHOULD MEAN, judged from the reader's side: someone who
  clicked the tile because they do not know what the module does can, after
  reading, say what it is for, what it needs, what it produces, and what to
  do next. That is the bar, not a word count.

  The existing docstrings in `spacr/qt/screens/foreign.py` are the house
  standard: what the screen is for, an ASCII layout, and design notes saying
  WHY each decision was made. Modules already written to that standard need
  their prose surfaced on the landing page, not rewritten.
