================================================================================

--------------------------------------------------------------------------------
WHAT HAPPENS
--------------------------------------------------------------------------------

Help -> Check for updates offers the upgrade, the user says yes, and it
fails with exit code 1 and a message naming a terminal that a desktop
entry (Terminal=false) never opened.

--------------------------------------------------------------------------------
WHY
--------------------------------------------------------------------------------

The installers build their environment with `uv venv`, which does NOT seed
pip. Confirmed on a real install:

    $ ~/.local/share/spacr/venv/bin/python -m pip --version
    No module named pip

The updater in an old build runs `sys.executable -m pip install --upgrade
spacr`, so it fails before it starts.

`spacr/updater.py` already handles this. `find_uv()` looks for

    <install root>/bootstrap/uv        <- the tool the installer used
    <install root>/venv/               <- sys.prefix

and `upgrade_command()` prefers it. On the machine this was diagnosed on,
that file exists at exactly that path. The code is simply newer than the
installed build:

    $ ~/.local/share/spacr/venv/bin/python -c \
        "import spacr.updater as u; print(hasattr(u, 'find_uv'))"
    False

So the fix cannot arrive by the route it fixes. That is the whole problem:
it is a bootstrap trap, not a bug that will drain away as people update.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Ship a build containing `find_uv` / `upgrade_command` through a channel
   that is NOT the in-app updater. The installers are that channel:
   packaging/build_debian.sh, build_macos.sh, build_windows.ps1.

2. Tell existing users the manual escape. One line, no sudo, no reinstall:

     ~/.local/share/spacr/bootstrap/uv pip install --upgrade \
       --python ~/.local/share/spacr/venv/bin/python spacr

   On macOS and Windows the two paths differ; derive them the way
   `find_uv` does -- `sys.prefix` for the venv, its parent + /bootstrap/uv
   for the tool.

3. Consider making a failed upgrade say this itself. The dialog already
   shows the tail of pip's output rather than pointing at a terminal (that
   part is fixed). A missing-pip failure is recognisable -- "No module
   named pip" in the output -- and is the one case where the app knows the
   exact command that would work.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

From an installed build, not from a checkout:

    <venv>/bin/python -c "from spacr.updater import upgrade_command; \
                          print(upgrade_command())"

It must print the uv form, `[.../bootstrap/uv, 'pip', 'install', ...]`,
and NOT `[<python>, '-m', 'pip', ...]`. If it prints the pip form on a
machine whose venv has no pip, the upgrade will fail again.

--------------------------------------------------------------------------------
WHAT WAS ALREADY DONE
--------------------------------------------------------------------------------

Nothing in this file is a code change; the code is right. The only reason
this is unfinished is distribution.

--------------------------------------------------------------------------------
2026-08-29 — RE-AUDIT: TWO OF THREE PLATFORMS SHIPPED; WINDOWS DID NOT
--------------------------------------------------------------------------------

The public PyPI wheel and three GitHub installer assets for 1.5.0.4 were
published on 2026-08-10. That release contains ``find_uv`` and
``upgrade_command``, so running the 1.5.0.4 installer is an external escape
for affected Linux and macOS installations.

The published 1.5.0.4 wheel is not a complete Windows fix. Its ``find_uv``
checks only ``<root>/bootstrap/uv``, while the published Windows bootstrap
writes ``<root>/bootstrap/uv.exe`` and does not put that private directory on
``PATH``. Commit ``8eefc701`` added ``uv.exe`` discovery after the release;
that source fix therefore still has to ship in 1.5.0.5.

The manual, no-sudo escape commands for Linux, macOS and Windows now live in
``docs/source/installer_guide.rst``. They name the original broken installers'
actual default roots, including macOS's historical ``SpaCR`` capitalization.

The native online-installer workflow already imports ``upgrade_command`` from
each installed private environment and requires the uv form on Linux, Windows
and macOS. It now also asserts that ``pip`` is genuinely absent in each of
those environments, so the acceptance test proves the reported bootstrap
boundary instead of merely proving that uv is preferred when pip happens to
be available.

REMAINS: publish the tested 1.5.0.5 wheel and all three native installers, then
verify their installed acceptance jobs. Publishing PyPI/GitHub/Zenodo assets
is public and irreversible and therefore requires the maintainer confirmation
recorded by the release instructions; source tests cannot close this item.
