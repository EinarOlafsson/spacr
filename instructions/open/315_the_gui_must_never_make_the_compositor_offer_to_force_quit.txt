1. WHAT ACTUALLY CAUSED EACH SYMPTOM
------------------------------------

Every one of these was measured, not guessed, and four of the five were
NOT what they looked like.

1a. THE 60-SECOND START WAS VERBOSE LOGGING. `logging_util` installs a
    profile hook with `threading.setprofile_all_threads`, so every call
    on every thread went through Python. Startup 60 s -> 2.4 s with it
    off. No code changed. The feature is still shipped and still does
    this: it is a diagnostic that costs an order of magnitude, and the
    user is right that a switch which makes the application unusable is
    broken rather than expensive.

1b. THE WINDOW WOULD NOT DRAG because nothing implemented it. The
    frameless window carried a comment saying the menu bar is what you
    drag it by, and no code anywhere honoured it. `startSystemMove()` on
    the window handle is the only mechanism the compositor accepts; a
    press on a menu still opens the menu, only the bare strip drags.

1c. THE MISSING BACKDROP AND THE BLACK CORNERS WERE THE SESSION TYPE.
    A native Wayland session gives Qt an OpenGL ES context; vispy
    compiles the fractal shaders as desktop GLSL 120 and ES answers
    "unsupported version 120", so the backdrop never drew a frame. The
    same compositor rounds an opaque surface, which is where the black
    corners outside the rounded edges came from. Both are gone under
    `xcb`. NOTHING IN SPACR CHANGED -- and four separate "fixes" were
    attempted against the wrong cause before anyone asked what the
    session was. Two of them (an eager shader link, a CPU fallback) took
    the application down or ate twenty cores.

1d. THE "NOT RESPONDING" ON OPENING A MODULE WAS THE BACKDROP WAITING
    FOR A LOCK. `_PipelinePreloader` holds HEAVY_IMPORT_LOCK for a whole
    module import; a screen build takes the same lock to construct its
    GL backdrop. Clicking a module while the preloader was still running
    cost a 3148 ms block of the GUI thread, of which 83% was the
    backdrop's constructor waiting. The backdrop is decoration and the
    module is not, so the decoration is what waits now: the install
    peeks at the lock without blocking and comes back on a timer.
    Longest block 3062-4054 ms -> 1380-1424 ms; the backdrop arrives
    0.27 s after the screen instead of holding it up.

1e. THE HOME REFRESH WAS 30,832 STAT CALLS. `recent_runs` and
    `journal_totals` between them made four `iterdir()` passes with an
    `is_dir()` on every entry, over a journal that had grown to 10,192
    run folders. One `os.scandir` gives the same answers for 173 stat
    calls: 23.8 ms and 9.1 ms, byte-identical results. `journal_totals`
    was ALREADY incremental -- that cache saved the manifest reads, and
    never saved the directory walk that found them.


2. THERE ARE THREE SPACR INSTALLS ON THIS MACHINE
-------------------------------------------------

This wasted an hour and produced a flat contradiction with the user,
who was right:

    spacr      -> ~/.local/share/spacr/venv/.../site-packages/spacr
    spaceout   -> whichever env is active; the `spacr` env points at
                  /mnt/firecuda2/codex/repo/spacr
    anaconda3/bin/spaceout -> a STALE script that still imports
                  `spacr.gui:gui_app`, the removed tkinter GUI

A fix committed to the repo does not reach `spacr`, because `spacr` does
not run the repo. ALWAYS resolve what the command actually imports --
`python -c "import spacr; print(spacr.__file__)"` with THAT
interpreter -- before claiming a GUI fix is in the user's hands.

The platform preference therefore lives in `spacr.qt` and is called from
`run()`, `run_without_setup()` and spaceout's `main()`, so no entry point
can be missed again. An explicit QT_QPA_PLATFORM always wins, including
the `offscreen` the test suite sets.


3. STILL OPEN
-------------

3a. THE DOCK AND THE HEADER FLICKER -- FIXED, and the first diagnosis
    in this file was WRONG. It said "it is not the backdrop", on the
    strength of a test that paused the backdrop and saw the repaints
    stay. That test was broken: `pause()` sets a flag the draw path
    checks, it does not stop the timer, so the canvas kept ticking and
    nothing was actually paused. `set_animating(False)` stops it, and
    with the animation genuinely still the burst goes from 238 painted
    widgets to 5 for a menu, and 90 to 0 for a tooltip.

    A popup composited over the native GL child makes the widgets around
    it repaint once. That burst is harmless over a STILL surface -- it
    redraws identical pixels -- and visible over a moving one. So the
    backdrop holds still while a popup is up.

    HOW IT ASKS MATTERS AS MUCH AS THAT IT ASKS. The first
    implementation was an application-wide event filter watching Show
    and Hide. It worked, and it was thrown away: measured at 13,646
    Python calls per second while a module opens, and it put 130 ms back
    onto the GUI-thread block that 1d had just removed (1380-1424 ms
    became 1473-1606). It also broke a timing-sensitive fractal test by
    leaking across tests in one worker, since a filter on the
    application outlives the window that installed it.

    `spacr/qt/widgets/popup_state.py` replaces it with two C++ calls
    asked once per animation frame -- 120 a second against thirteen
    thousand. Both halves are needed: a menu is an `activePopupWidget`,
    a tooltip is NOT (it is its own Qt::ToolTip window) and only
    `QToolTip.isVisible()` reports it. Asking only the first would have
    left the tooltip flicker, which was reported alongside the menu.
    The module is at 100% branch coverage.

    Still worth knowing: the user also describes 'the bar on top of the
    window with maximize, minimize, close'. The main window is frameless
    by design, so that bar is probably a dialog rather than the main
    window; establish which before changing anything there.

3b. THE BLACK BOX IN REGRESSION WAS THE AI-PROVIDER CHEVRON. A sentinel

    pure-black component: 368 of its 525 pixels were black. It now uses the

3c. VERBOSE LOGGING no longer installs the interpreter-wide profile hook.

4. HOW TO MEASURE THIS CLASS OF BUG
-----------------------------------

The lesson of the evening is that wall-clock on a module open told us
almost nothing -- the same open measured 0.47 s and 22.59 s. What the
compositor actually reacts to is the LONGEST UNINTERRUPTED BLOCK of the
GUI thread, so measure that directly:

* a QTimer heartbeat at 20 ms; the largest gap between two ticks is how
  long the thread went without answering anything;
* a sampling thread reading `sys._current_frames()[main]` every 5 ms,
  correlated to that gap, to say what it sat in.

That pair found 1d in one run after several hours of wall-clock timings
had pointed at four different innocent subsystems. cProfile is NOT
usable here: on a tree of several thousand widgets it distorts the thing
it is measuring, exactly as the verbose-logging hook in 1a does.

Never measure while a `git cherry` over 4,000 commits is running in
another terminal. Several "findings" this evening were that.


1f. THE ONE THAT WAS LEFT: `spaceout` FROZE WHERE `spacr` DID NOT
-----------------------------------------------------------------

Reported 2026-08-31: "spaceout still has a wait-for-quit popup when I
open regression, spacr does not."

THE ASYMMETRY IS THE DIAGNOSIS, and it is the fastest one in this file
because the maintainer handed over both halves of a controlled
experiment. Same machine, same module, same click. The only difference
between the two launchers is `enable_spaceout()`, and the only thing that
turns on which touches a lock is the fractal backdrop.

1d fixed `AppScreen._install_ambient` -- it peeks at HEAVY_IMPORT_LOCK and
comes back on a timer rather than installing into a held lock. What it did
not fix is what happens AFTER the peek says yes:

    GpuFractalWidget.__init__:      with lock:  self._canvas = _Canvas()

A plain blocking acquire, on the GUI thread, against a lock the preloader
holds for a whole module import. A priority inversion: a background task
with no deadline holding up the one thread that has one.

The peek cannot close it. It is a check, not a reservation -- its own
docstring says so -- and `_PipelinePreloader._work` releases the lock
between two imports and takes it again immediately. A click landing in
that gap is not the unlucky case, it is the ordinary case for the first
few seconds of a session.

`spacr` never froze because `AmbientWidget` has no GL context and takes no
lock. The freeze needed BOTH halves: the fractal to want the lock, and the
preloader to be holding it.

MEASURED, xvfb + llvmpipe, against a 2,000 ms hold:

    before   2,130 ms blocked GUI thread, backdrop built
    after      142 ms, refused; the retry builds it in 43 ms

FIXED 2026-08-31. The acquire is bounded at 100 ms and a refusal raises
`HeavyImportInProgress`, which is deliberately not a `GpuBackendError`:
`create_fractal_widget` answers those with the CPU renderer -- 1c's
twenty-core fallback -- so a busy lock falling through there would trade a
third of a second for that renderer on every module opened during startup.

"Not yet" is not "never", so all three callers come back: AppScreen
forgets the attempt it had already recorded in `_ambient_applied`, Home
gains the peek and the retry it never had (and it is built at startup,
which is when the preloader runs), and the screens that are not
AppScreens get the backdrop install split out of `_theme_screen` so a
retry does not re-apply the stylesheet to the whole tree every 120 ms.

THE SHAPE, which is the reusable part: a bounded wait plus a retry is the
only honest way for the GUI thread to take a lock a background task can
hold for seconds. Peeking first is worth keeping -- it stops the retry
timer paying the bound on every tick during a long import -- but a peek
alone is a check-then-act race and cannot be the whole answer.

Guard: tests/qt/test_the_backdrop_never_waits_out_a_heavy_import.py, 19
tests. The three that carry the argument were mutation-checked.

3d, MEASURED 2026-08-31 ON A REAL DISPLAY: IT IS NOT DIFFUSE
--------------------------------------------------------------------------------

3d said "diffuse -- imports, settings_search.install, widget construction --
with no single offender". That verdict does not survive a profile that
separates cold from warm. 3840x2160 display, quiet machine, seven consecutive
warm builds of the Regression screen:

    cold (first open in the process)   2,068 ms
    warm (every open after)            1,263 ms   median, min 1,246, max 1,288

So ~800 ms of the "1.4 s" is once-per-process import cost and is NOT what a
user pays when opening a module. The 1,263 ms warm build is, and it has three
named owners rather than none:

    _build_runtime_panel                673 ms   53%
    _build_settings_panel               314 ms   25%
      of which 11 pyqtgraph plots       199 ms   16%

1. THE STYLE CASCADE IS 65.6% OF EVERY EVENT DISPATCHED.
   109,410 events reach each application-wide filter during ONE build:

       PaletteChange   27,995   25.6%
       FontChange      27,832   25.4%
       StyleChange     16,027   14.6%

   Those 71,854 events come from FIFTY-FOUR setStyleSheet/setFont/setPalette
   calls -- about 1,330 descendant events each, because Qt sends them to the
   whole subtree. Setting style on a parent AFTER its children are attached is
   therefore quadratic in the subtree, and the call sites are all in
   spacr/qt/screens/. `theme.batched_widget_qss()` already solves exactly this
   shape at window level; the same trick per-screen is the fix. NOT DONE HERE:
   screens/ belongs to the concurrent session.

2. field_fade's FILTER DOES ZERO WORK DURING A BUILD.
   It is dispatched 109,410 times and acts on Paint only -- and there are
   ZERO Paint events in the whole 1,263 ms. Its first line is already a single
   enum compare, so the ~89 ms is pure C++ -> Python dispatch that cannot be
   optimised from inside the filter. Removing it needs either a per-widget
   install or a suspend scope entered by the builder, which is in screens/.

3. THE OBVIOUS REORDER IN button_roles IS WRONG. RECORDED SO IT IS NOT RETRIED.
   That filter asks `isinstance(watched, QPushButton)` on all 109,410 events to
   act on 155 (0.14%), which looks like an obvious win: test `event.type()`
   first and reject 95.8% before the isinstance. Implemented and measured:

       original ordering    1,282 ms median
       "optimised" ordering 1,352 ms median      <- 5% SLOWER

   `event.type()` is a PySide call that crosses into C++ and builds an enum
   object; `isinstance` against a shiboken type is a C-level check. The
   original ordering pays type() only for the 4,576 QPushButton events. The
   change was reverted. The general point: in PySide the cheap-looking test is
   not always the cheap one, and a filter this hot must be A/B measured rather
   than reasoned about.

NEXT, AND IT IS IN widgets/ RATHER THAN screens/: RegressionResultsPanel builds
ten pyqtgraph plots eagerly at 199 ms and puts each straight into a QTabWidget
tab, of which the user sees one. Deferring construction to first tab activation
is worth ~199 ms of the 1,263. It is not a two-line change: the tabs set their
tooltips through `self.tabs.indexOf(self.effect_rank)`, and the plots are also
fed directly by attribute (`self.qq.set_p_values(...)`) from the results
loader, so laziness has to survive both an indexOf during construction and an
attribute touch before the tab is ever shown. A `__getattr__` that materialises
on first touch covers both; it was scoped but deliberately not shipped
half-tested.

2026-09-02 — BEFORE ANYONE STARTS 3d: THE FUNCTION THIS FILE NAMES DOES NOT EXIST
--------------------------------------------------------------------------------

The 3d note above says "`theme.batched_widget_qss()` already solves exactly
this shape at window level; the same trick per-screen is the fix." There is no
`batched_widget_qss` anywhere in the package:

    grep -rn "batched_widget_qss" --include=*.py spacr/     ->  no matches

What DOES exist in `spacr/qt/theme.py` is the widget-QSS REGISTRY, which is
the same idea under a different name -- one composed sheet instead of N
`setStyleSheet` calls:

    register_widget_qss(name, fn)          3265
    unregister_widget_qss(name)            3318
    widget_qss_names()                     3323
    load_widget_qss_registrars()           3228
    set_widget_qss_context(app, theme, font_scale, ...)   3344

So the fix shape is real and the name is not. Reuse the registry rather than
writing a new batching helper, and do not spend time looking for the function
this file invented.

WHERE THE CALLS ACTUALLY ARE, counted rather than estimated. The 54 the note
attributes to `screens/` are not evenly spread:

    app_screen.py      11        annotate.py         6
    train_compare.py    3        plate_view.py       3
    model_compare.py    3        hyperparam.py       3

`app_screen.py` is the one every module screen is built from, so it is where
