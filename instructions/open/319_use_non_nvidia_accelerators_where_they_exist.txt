319 — USE NON-NVIDIA ACCELERATORS WHERE THEY EXIST, AND SAY SO IN SETUP
======================================================================

ASKED FOR (2026-08-31, verbatim)
--------------------------------
"for the CUDA accelerated tasks in spacr. if these have radeon/ intel
counterparts that can be implemented in the cases of other graphics cards
being detected or neural network acceleration chips being detected that can
be used please implement code that allows these non NVIDIA massive parallel
processing hardware components to be used by spacr if possible. in spacr
setup try to detect these other acelerators. and state if they are
detected."

TWO DELIVERABLES, AND THEY ARE NOT THE SAME SIZE
------------------------------------------------
1. DETECT AND REPORT, in the setup screen. Small, self-contained, and
   useful on its own: the first setup slide already draws a CUDA line in
   green or red (item from 2026-08-30). Whatever else is present should be
   named on that same line rather than silently reading "no GPU" on a
   machine with a perfectly good one.

2. ACTUALLY RUN ON THEM. Large, and gated on what each backend really
   supports. Do not let (1) imply (2): a setup screen that announces an
   accelerator spaCR will never dispatch to is worse than one that says
   nothing, because the user then blames their hardware for the speed.
   Report DETECTED and USABLE as two separate facts.

THE BACKENDS THAT ARE REAL
--------------------------
* Apple Silicon — `torch.backends.mps.is_available()`. The most valuable
  one: every M-series Mac has it, spaCR already runs on those machines,
  and torch supports it directly with `device="mps"`. Caveats that must be
  handled rather than discovered by a user: float64 is unsupported, and
  some ops silently fall back to CPU unless
  `PYTORCH_ENABLE_MPS_FALLBACK=1`.
* AMD Radeon — ROCm. `torch.version.hip` is not None, and ROCm builds
  still report `torch.cuda.is_available()` True with `device="cuda"`. So
  the CUDA path may already work; what is missing is saying "ROCm"
  instead of "CUDA" and not claiming an NVIDIA card that is not there.
  Linux only in practice.
* Intel Arc / Xe — `torch.xpu.is_available()` on a torch built with XPU,
  else the `intel_extension_for_pytorch` path. `device="xpu"`.
* DirectML (Windows, any vendor) — `torch_directml`. Widest reach on
  Windows, thinnest op coverage.
* NPUs — treat as detect-and-report only for now. There is no portable
  torch device for the Apple Neural Engine (CoreML only), Intel AI Boost
  (OpenVINO only), or Qualcomm Hexagon. Naming one as a spaCR compute
  device would be a promise nothing behind it can keep.

WHERE THE WORK LANDS
--------------------
The CUDA checks are NOT in one place, which is the main cost of this item.
Find them all before writing anything -- `torch.cuda.is_available()`,
`.cuda()`, `device="cuda"`, `torch.device("cuda")` and `cuda:` strings
appear across `deep_spacr`, `ml`, `core`, `measure`, `utils`, the cellpose
call sites and the Qt setup slide. The right shape is ONE resolver
("what device should this run on, and what is it called") that every site
asks, not a second vendor branch at each site -- a per-site branch is how
the third backend costs as much as the second.

Cellpose has its own device handling and its own `gpu=` argument; it must
be routed through the same resolver or the two will disagree on the same
machine.

DONE MEANS
----------
* One resolver, with a test per backend that FAKES the backend's probe
  and asserts the device string -- these cannot be tested on this machine
  for real, so the fake is the test, and it must fail when the branch is
  removed.
* The setup slide names what was found, and distinguishes "found" from
  "spaCR will use it".
* An unknown or broken accelerator falls back to CPU without an
  exception. A machine with a half-installed ROCm must still start.
* No behaviour change on an NVIDIA machine -- assert that explicitly,
  because that is the configuration every current user has.


ADDENDUM 2026-08-31 — THE README AND THE API MUST SAY SO TOO
================================================================================

Asked for: "the readme should reflect that spacr can be run with a NVIDIA,
RADEON, etcetera card. all this should be reflected in the readme and API".

DOCUMENTATION IS PART OF THIS ITEM, not a follow-up. A user chooses
hardware from the README. If it says CUDA and nothing else, somebody buys
an NVIDIA card they did not need, or concludes spaCR will not run on the
machine they have.

WHAT IS THERE NOW, and both lines become wrong the moment the resolver
lands:

  README.rst:75   "CUDA is used automatically where a ..."
  README.rst:292  "Linux is recommended for CUDA workflows; macOS and ..."

WRITE IT WHEN THE CODE LANDS, NOT BEFORE. This addendum was filed at the
moment it was asked for, and the README was deliberately NOT edited then,
because `spacr/accelerator.py` did not exist yet. A README that advertises
ROCm before anything dispatches to ROCm is worse than one that says
nothing: the first sends somebody to buy a card, and the second only
fails to mention an option.

So the sequencing is: resolver, then dispatch, then the two surfaces
below -- and the wording comes from what the resolver actually does, not
from this list.

  README: the hardware sentence names every backend that DISPATCHES, and
  says what happens on a machine with none (CPU, correct results,
  slower). Keep the DETECTED-versus-USABLE split from the body of this
  instruction: if a backend is recognised but not dispatched to, the
  README must not imply otherwise. And say which platform each backend
  is available on -- ROCm is Linux in practice, MPS is Apple Silicon,
  DirectML is Windows -- because "supported" without a platform is the
  half-answer that wastes an afternoon.

  API: `spacr/accelerator.py` gets a page like any other module, and the
  resolver is the documented entry point for "which device will this
  use". Anything scripting spaCR against a GPU needs to be able to ask
  that question without reading the dispatch sites.

  spacr-doctor: already in this instruction's file list, and it is the
  third surface -- the one a user reaches when the other two have not
  answered them. Its line must name what was found and whether spaCR
  will use it.

DONE MEANS, additionally: no sentence in README.rst, the nine translated
READMEs, or the API index names CUDA as the only way to get a GPU; and
the README's claims are checked against the resolver's own list rather
than typed, in the way the module grid now is -- see instruction 321.

2026-08-31 — IMPLEMENTED. ONE RESOLVER, AND THE MAC'S AMD CARD NOW RUNS
==============================================================================

MEASURED ON: Intel iMac, Core i5-10500, macOS 26.5.2, AMD Radeon Pro 5300
(4 GB, Metal 3), conda env `spacr`, Python 3.12.11, PySide6 6.11.2,
torch 2.2.2 / shiboken6 6.11.2. Quote the env with the version; see 320 for
why that matters on this host.

THE INSTRUCTION'S BACKEND TABLE WAS WRONG ABOUT THIS MACHINE, in the one way
that mattered. It files MPS under "Apple Silicon" and AMD under ROCm. Both
are wrong here:

  * ROCm HAS NO macOS BUILD AT ALL. On a Mac it is not "Linux only in
    practice", it is unavailable in principle.
  * MPS IS METAL, NOT AN APPLE-SILICON FEATURE. `torch.backends.mps` drives
    the AMD Radeon in this Intel Mac. Metal is the ONLY route to an AMD card
    on macOS, and the instruction does not mention the combination.

So the leading question -- "which PySide/torch version" -- was not the axis.
The axis was that ~45 sites asked `torch.cuda.is_available()` and about a
dozen of them meant "is there a GPU".

WHAT WAS MEASURED, all on the machine above, CPU vs the same machine's card:

    conv2d stack 512x512, inference     139.5 ms  ->    8.5 ms   (16x)
    conv+BN+Adam step, 16x3x224x224      1022 ms  ->   380 ms   (2.7x)
    cellpose cpsam, one 256x256 image   444.5 s   ->    3.2 s    (139x)

The cellpose number is the headline and it is not a typo: 7.4 minutes to
3.2 seconds for one small image, because cpsam is a SAM encoder and that is
what a CPU does with one.

WHAT IT TOOK, because "point it at mps" is not the fix and each of these
was a separate failure with its own symptom:

  1. `gpu=` AND `device=` TOGETHER. Cellpose branches on `gpu` BEFORE it
     looks at `device`, so passing a device without the flag still runs on
     the CPU. spaCR passed `gpu=torch.cuda.is_available()`, which is False
     here -- so spaCR was actively overriding a cellpose that already
     resolves Metal correctly on its own (`assign_device(gpu=True)` answers
     `mps`). The capability was installed and being switched off.
  2. `use_bfloat16=False`. cpsam loads its weights in bfloat16 and Metal on
     torch 2.2 has none: `TypeError: BFloat16 is not supported on MPS` at
     construction. PROBED, not hardcoded -- Metal gained bfloat16 after 2.2
     and 2.2.2 is the last x86-64 macOS wheel, so the same backend answers
     differently on an Intel Mac and an Apple Silicon one.
  3. `PYTORCH_ENABLE_MPS_FALLBACK=1` SET BEFORE `import torch`. Metal is
     missing operators; the network died at `aten::upsample_linear1d` after
     the model had loaded. Torch reads this variable when the MPS backend
     REGISTERS, which is at import. Measured: identical code fails when it
     is set after the import and succeeds when set before. It is therefore
     in `spacr/__init__.py` and NOT in the resolver, which runs far too late
     to matter. This is the one that would be silently reintroduced by
     anyone "tidying" it into the module it belongs to.
  4. A NARROW SHIM keeping cellpose's flow-error pass on the CPU.
     `cellpose.dynamics.masks_to_flows_gpu` indexes one past the end on MPS
     (`IndexError: index 256 is out of bounds for axis 1 with size 256`),
     reproduced on ordinary round blobs, not a pathological input. Only
     `remove_bad_flow_masks` moves back -- it is post-processing, it is
     cheap, and its own signature already defaults to the CPU. The encoder,
     which is all of the runtime, stays on Metal. Removal condition is in
     the docstring.

THE SHAPE, as the instruction asked: ONE resolver, `spacr/accelerator.py`,
that every site asks. It answers three questions the old idiom conflated:

    is_gpu()   "is there an accelerator"   <- what a dozen sites meant
    is_cuda()  "is it NVIDIA"              <- what they asked
    capabilities / float64 / bfloat16 / autocast   "what can it NOT do"

The third is not decoration. float64 raises on Metal, `autocast(device_type=
"mps")` raises, and cellpose needs the dtype answer -- so a resolver that
returned only a device string would hand those to a training run.

DETECTED AND USABLE STAY SEPARATE, in the setup slide and in the doctor,
and the doctor was the worse offender: its FIRST branch is "No NVIDIA
driver and a CPU-only torch: segmentation and training will be very slow",
which is what every Mac got. Wrong by two orders of magnitude about the
card in the machine, and it ended in `nvidia-smi`. It now reads:

    PASS  AMD Radeon Pro 5300 (Apple Metal) — spaCR will use it.
          device: mps
          still on the CPU: UMAP / t-SNE / clustering
          float64 is unsupported on this backend, so anything needing
          double precision runs on the CPU

That cuML line is deliberate. RAPIDS ships for CUDA only -- no AMD, no
Intel, no macOS build -- so those reductions are honestly red on every
machine here except NVIDIA, and one green tick for all five tasks would be
a lie about that one.

A SECOND BUG FOUND WHILE LOOKING, unrelated to torch: the spaceout fractal
ran its CPU renderer on EVERY Mac. `platform_can_do_opengl` required
`DISPLAY` or `WAYLAND_DISPLAY` when `QT_QPA_PLATFORM` is empty, which is the
normal state on macOS, where neither variable exists. VisPy opens a context
on this machine reporting GL_RENDERER "AMD Radeon Pro 5300 OpenGL Engine",
so the card was there the whole time and the environment heuristic was what
said otherwise. The offscreen refusal -- which exists because a GL canvas
there DUMPS CORE rather than raising -- is unchanged and asserted.

NEURAL ENGINES: detect and report only, as instructed. The ANE is reachable
through CoreML alone, Intel AI Boost through OpenVINO; naming either as a
compute device would be a promise nothing behind it can keep. They appear
on the slide as "detected, not used by spaCR".

TESTS. One per backend, each FAKING that backend's probe and asserting the
device string, because no machine has five of them and this one has one --
the fake is the test. `test_the_accelerator_resolver.py` (19) and
`test_the_doctor_names_a_non_nvidia_accelerator.py` (5). The first
assertion in each file is that NVIDIA is unchanged, which is the whole risk
of this change.

NOT DONE, AND WHY
-----------------
* UMAP / t-SNE / DBSCAN on a non-NVIDIA GPU. cuML is CUDA-only and there is
  no port; this is "write it", not "enable it". PCA and KMeans are
  reachable in torch on Metal but sklearn's PCA is 71 ms on 20k x 256 here,
  so the transfer would cost more than the compute.
* Mixed-effects regression on Metal. It wants float64 and MPS raises on it.
  Blocked at the backend, not by spaCR.
* torch 2.2.2 IS A CEILING on this machine: PyTorch stopped publishing
  x86-64 macOS wheels after it. Apple Silicon is not capped this way and
  should pick up bfloat16 and the missing operators automatically, because
  the capability flags are probed rather than declared.
