--------------------------------------------------------------------------------
BOTH REPORTS REPRODUCE, AND THEY ARE DIFFERENT FAULTS
--------------------------------------------------------------------------------

    api_docs_url("mask", "src")
      -> .../api/spacr/annotation_dataset/index.html
             #spacr.annotation_dataset.generate_annotation_dataset

    api_docs_url("mask", "magnification")
      -> .../api/spacr/utils/index.html

The first is WRONG, not merely unbuilt. `spacr.annotation_dataset` is a
rendered module, so the 404 is a published site older than the module; the
next docs deploy will turn it into a page. What the deploy will NOT fix is
that a reader pressing API on `src` in the Mask panel is sent to the
annotation-dataset generator. `src` in a Mask run is read by
`core.preprocess_generate_masks`.

The second is a page with no mention of the setting, exactly as reported.
`utils` is where `magnification` is read, so the module is right and there is
no anchor to offer, because the only consumer is a private function. Landing
on a 4,000-line module page is honest and useless in the same gesture.

MEASURED, SO THE SIZE OF IT IS NOT A GUESS
--------------------------------------------------------------------------------

Across every app/setting pair that shows a help link:

    801   pairs with a link
    195   land on a module page with NO anchor        (magnification's class)
      4   land on an anchor naming a symbol that is

The dead four are all `spacr.measure._morphological_measurements`, a private

--------------------------------------------------------------------------------
THE ROOT CAUSE IS THAT THE MAP IS KEYED ON THE SETTING ALONE
--------------------------------------------------------------------------------

`settings_model._mapped_api_target(key)` takes a setting name and nothing
else. The app the reader is looking at is not an input, so a setting shown in
several modules gets ONE answer for all of them:

    596   distinct settings shown in a panel
     99   shown in more than one app
     96   of those have a key-only target, so one answer serves every app

    src         in 41 apps  -> annotation_dataset
    verbose     in 10 apps  -> core
    n_jobs      in  6 apps  -> core
    plot        in  5 apps  -> core
    normalize   in  5 apps  -> core

`src` is the report, and it is the worst case in the package: forty-one
panels, one destination, and the destination is the right answer for at most
one of them. This is not a bad ranking that a better `_rank` would fix. The
function cannot express the answer, because it is not told which app is
asking.

WHY IT LOOKS RIGHT IN THE TESTS. `tests/test_tooltip_api_links_resolve.py`
asks whether every link RESOLVES -- that the page is a canonical public
module, that no link goes to the index. All 801 pass that. "Resolves" and
"is the right page for this reader" are different claims and only the first
is currently made.

--------------------------------------------------------------------------------
WHAT GOOD LOOKS LIKE
--------------------------------------------------------------------------------

1.  The target is chosen from (app_key, setting), not setting alone. The
    consumer map already records every site that reads a setting -- see
    `tools/build_setting_consumer_map.py` -- so the data is there; what is
    missing is a per-app column and a rule for picking among the readers
    reachable from THIS app's entry point.

2.  A setting whose only reader is private gets an anchor a reader can use,
    or the link says plainly that the page is the module. 195 pairs land on
    a module page today with nothing to say why.

3.  The four dead fragments stop being emitted. A fragment naming a private
    symbol is worse than no fragment: the browser silently ignores it and
    the reader believes they are looking at the right place.

    DONE 2026-09-08, and it was a one-line asymmetry. `resolve_targets` has
    two branches that can name a symbol. The private-consumer branch already
    dropped the anchor and says why; the CLOSURE branch aimed at the
    enclosing function without asking whether that function is public, so a
    closure inside `_morphological_measurements` was given an anchor to
    `_morphological_measurements`. Same failure, arrived at by the other
    route. The closure branch now drops the symbol when the ancestor is
    private, and the measured count of dead anchors is 0.

4.  A test that asserts LANDING, not resolving -- for a sample of settings,
    the target page or anchor actually mentions the setting.

--------------------------------------------------------------------------------
NOT A RELEASE BLOCKER, AND WHY IT IS FILED ANYWAY
--------------------------------------------------------------------------------

Nothing here breaks a run. But the API word is the one affordance in the
settings help that promises more than the tooltip already says, and on the
most-shared setting in the package it has been pointing at an unrelated
module in forty-one panels. A reader who follows it twice and finds the
wrong page both times stops following it, which costs the whole documentation
surface rather than these two settings.

    before   551 API anchor    0 flow page   245 module page only
    after    551 API anchor  185 flow page    60 module page only

The settings-flow page from 368 already names every setting, carries its help

The remaining 60 have no flow section either, because nothing static analysis

ITEM 4, the landing test. `test_an_anchorless_link_goes_to_the_setting`

Two more hold the mechanism together: the generated index must equal the set
of sections actually written into the page -- an anchor the page does not

ONE TEST HAD TO CHANGE AND THE REASON IS WORTH RECORDING.
`test_the_link_prefers_the_asking_apps_own_module` asserted on the URL, so
moving anchorless links to the flow page read as 185 regressions. The rule it
means is about which MODULE was chosen, and the flow fallback does not change
that -- it changes how the answer is shown when the chosen module has no
anchor. It now asserts on `_mapped_api_target`, so a presentation change
cannot look like a misdirection again.

STILL OPEN: item 2's second half. The 60 residue links say nothing about why
they land on a module page. A reader who follows one still cannot tell
whether they arrived somewhere useless or somewhere incomplete.

2026-09-08 -- THE RESIDUE WAS NOT UNUSED SETTINGS. IT WAS THREE ANALYSER BUGS.
--------------------------------------------------------------------------------

The 60 links still landing on a bare module page looked like the honest
residue: settings nothing reads, so no page mentions them and there is none to
link to. That reading was wrong, and it was wrong in a way worth recording,
because the evidence for it was an ABSENCE and an absence is what a broken
detector produces.

Grepping one of them settled it in a minute:

    hit_bootstrap    spacr/hit_investigation.py:324
                     n_bootstrap=int(configured["hit_bootstrap"])

Read, plainly, in the app's own module. Three separate faults hid it.

1.  `settings or {}` WAS NOT SEEN THROUGH. Both analysers accept an alias
    bound by `dict(settings)`, but the defensive idiom is
    `configured = dict(settings or {})`, and the argument is a BoolOp rather
    than a Name. Everything read through that alias was invisible. One
    function, `hit_investigation_default_settings`, gates 17 `hit_*` settings.

2.  THE CONSUMER MAP DID NOT KNOW THEY WERE SETTINGS. `setting_keys()` read
    `tooltips` and `expected_types` at MODULE scope in `settings.py` only, and
    `hit_investigation` declares its own `tips` dict inside a function body.
    A setting the map has never heard of cannot have a read, so no amount of
    fixing (1) alone would have helped. It now also reads the EN catalog's
    `SETTING_TOOLTIPS`, which is the list of settings the GUI actually shows
    -- generated from the resolved runtime tables, so a setting a user can
    see is in it wherever its tooltip was declared.

3.  `_APP_API_MODULE` IS BUILT LAZILY and the generator read it half-filled.
    Importing `settings_model` gives 41 of 65 apps; importing `spacr.qt.app`
    gives all 65. The 24 missing apps silently lost every per-module row, so
    `verbose` in Investigate Hit pointed at `core.preprocess_generate_masks`.
    The generator printed "41 app module(s)" the whole time, which is a count
    that looks like a fact.

    per-module rows   653 over 492 settings, 41 modules   (before)
                      762 over 598 settings, 56 modules   (after)

2026-09-09 -- THE 43 WERE AUDITED. AT LEAST 32 OF THEM ARE READ IN PLAIN SIGHT,

--------------------------------------------------------------------------------

The closing note above said the 43 "have no flow section because nothing
static analysis can see reads them ... That is the honest floor unless the
analyser learns to see more", and warned that they were unexplained rather
than settled. The warning was right. The floor is not 43.

    15   curated -- batch, evaluation, umap search. Unchanged, correct,
         and not reopened.
    43   the residue, one pair each, 43 distinct settings
    --
    20   read through an ALIAS the analyser does not recognise
    12   read through a key that is never a literal

So 32 of the 43 are read, in the app's own code, by a `.get()` or a subscript
a person can see at a glance. This is the THIRD time this instruction has read
an absence as a fact about the package.

BLIND SPOT A -- AN ALIAS BOUND BY A HELPER, 20 settings.

`_alias_targets` (tools/settings_flow.py:91) accepts four bindings:
`x = settings`, `x = settings.copy()`, `x = dict(settings)` and
`x = deepcopy(settings)`, and since fault 1 it sees through `settings or {}`
inside them. It does NOT accept a settings mapping RETURNED BY A HELPER, and
three helpers account for every one of the 20:

    power_default_settings          spacr/qt/screens/power.py:1528
        filled = power_default_settings(settings)
        -> all 15 power_* settings, read as filled["power_n_genes"] etc
           at power.py:1530-1544

    default_settings                spacr/convert.py:2165
        resolved = default_settings(settings)
        -> layout, plate_naming, z_handling; same shape again at
           foreign.py:3584 and external_masks.py:551

    hit_investigation_default_settings   spacr/hit_investigation.py:298
        configured = hit_investigation_default_settings(settings)
        -> guide_fractions_file, hit_phenotype

THE THIRD ONE IS THE INTERESTING ONE, because hit_investigation.py binds
`configured` TWICE. Line 266 is `dict(settings or {})`, which fault 1 taught
the analyser to see, and that is why 17 hit_* settings came back. Line 298 is
the helper, which it still cannot see, and that is why exactly two did not.
The same file, the same alias name, one visible binding and one invisible one
-- which is why fixing fault 1 looked complete and was not.

BLIND SPOT B -- THE KEY IS NEVER A LITERAL, 12 settings, and this one is
different in kind.

    spacr/seg_qc.py:282
        SETTING_KEYS: Dict[str, str] = {
            f"seg_qc_{name}": name for name in QC_DEFAULTS
        }

    spacr/seg_qc.py:387
        for key, name in SETTING_KEYS.items():
            number = _as_number((settings or {}).get(key))

The eleven `seg_qc_*` setting names DO NOT EXIST as string literals anywhere
in the package. They are synthesised by an f-string inside a dict
comprehension over `QC_DEFAULTS`, and then read in a loop through a variable.
The twelfth, `seg_qc` itself, is a literal but is bound to a constant --
`MODE_SETTING = "seg_qc"` at :287, read as
`(settings or {}).get(MODE_SETTING, "report")` at :406 -- so it is not a
literal AT THE CALL SITE either.

NO AMOUNT OF ALIAS TRACKING FINDS THESE. Blind spot A is a missing case in a
list of four and can be closed by adding a fifth. B is a category the current
design cannot express: a pass that looks for a setting name at a subscript or
a `.get()` will never see a name that is computed. Closing B needs either
constant folding over module-level tables, or a declaration the module makes
about itself. Recorded as a limit with a shape, not as a bug with a fix.
