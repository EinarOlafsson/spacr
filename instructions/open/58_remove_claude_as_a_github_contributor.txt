WHAT THE STATE IS

Measured on `nightly`, last 400 commits:

    NO commit is authored or committed by Claude.

    38 commits carry a `Co-Authored-By: Claude ...` TRAILER.

That trailer is the whole cause. GitHub reads `Co-Authored-By` and credits
the named account in the contributors list and in per-commit attribution,
exactly as if it were a second author.

Going forward this is already prevented: the standing rule for this repo is
that no commit carries a Co-Authored-By trailer and the maintainer is sole
author. The 38 are historical, from before that rule.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The contributors list is what a visitor reads as "who wrote this". For an
academic tool, authorship is not decoration -- it is the thing citation and
credit attach to, and a tool that appears to have a corporate co-author
invites questions the maintainer should not have to answer.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

There is no way to remove a contributor through the GitHub UI. Attribution
is computed from commits, so it changes only when the commits do.

OPTION A -- rewrite history. The only fix that removes the existing 38.

    git filter-repo --message-callback \\
        'return re.sub(rb"\\n*Co-[Aa]uthored-[Bb]y: Claude[^\\n]*", b"", message)'

    then force-push every affected branch, and re-push tags.

    THIS IS DESTRUCTIVE AND PUBLIC. Every commit hash after the earliest
    rewritten commit changes, which means:
      * open pull requests against the old hashes break;
      * anyone with a clone or fork must re-clone or hard-reset;
      * a Codex session is working in this repo concurrently and would be
        rebasing onto history that no longer exists.
    DO NOT RUN IT without the maintainer saying so, and coordinate the
    timing with whoever else has the repo checked out.

The rewrite is authorised. The ordering is part of the instruction, not a
preference, and the reason is mechanical rather than cautious:

REWRITING CHANGES EVERY COMMIT HASH AFTER THE EARLIEST REWRITTEN COMMIT.

committed after it is built on the new history. Doing it in the middle
means every remaining task is done twice -- once on the old hashes, once
after a forced reset -- and anyone else in the repository has to re-clone
in the middle of their own work.
