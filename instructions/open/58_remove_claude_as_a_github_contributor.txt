That trailer is the whole cause. GitHub reads `Co-Authored-By` and credits
the named account in the contributors list and in per-commit attribution,
exactly as if it were a second author.

Going forward this is already prevented: the standing rule for this repo is
that no commit carries a Co-Authored-By trailer and the maintainer is sole
author. The 38 are historical, from before that rule.

THAT RULE IS NOT SELF-ENFORCING, and 2026-09-10 proved it. The three commits
merging nightly into main were each written with a `Co-Authored-By: Claude
Opus 5` trailer, because the agent writing them is instructed by its own
HARNESS to add one -- an instruction that arrives from outside the
repository, where no hook, test or instruction file can reach it. They were
caught before the push and stripped, and the branch is back to zero.

    COUNT IT WITH THE PATTERN ANCHORED, or the number is wrong:

        git log --format=%B <ref> | grep -cE "^[ \t]*Co-Authored-By:[ \t]*Claude"

academic tool, authorship is not decoration -- it is the thing citation and
credit attach to, and a tool that appears to have a corporate co-author
invites questions the maintainer should not have to answer.

2026-08-08 - APPROVED, AND WHY IT GOES LAST
--------------------------------------------------------------------------------

The rewrite is authorised. The ordering is part of the instruction, not a
preference, and the reason is mechanical rather than cautious:

REWRITING CHANGES EVERY COMMIT HASH AFTER THE EARLIEST REWRITTEN COMMIT.
Any work committed before the rewrite is rewritten with it; any work
committed after it is built on the new history. Doing it in the middle
means every remaining task is done twice -- once on the old hashes, once
after a forced reset -- and anyone else in the repository has to re-clone
in the middle of their own work.

So it is the last thing that happens to this repository, and NOTHING should
be committed after it until the maintainer has re-cloned.

BEFORE RUNNING IT, in this order:

  1. Every other instruction in `open/` is finished or explicitly closed.
     That includes 48, the tutorials task, which belongs to a CONCURRENT
     CODEX SESSION -- its work has to be landed and pushed first, or the
     rewrite discards it or strands that session on dead hashes.
  2. Confirm the count on the DEFAULT branch, not just nightly. GitHub
     computes contributors from the default branch, so the number that
     matters may not be the 38 measured here:
         git log --grep='Co-Authored-By: Claude' -i --oneline | wc -l
  3. Full backup: `git clone --mirror` to somewhere off this disk. The
     rewrite is not reversible from the working copy.
  4. Confirm no open pull requests, or that their authors know.
  5. Rewrite, force-push every branch AND tags.
  6. Verify the count is 0 on the default branch, then check the
     contributors page. GitHub caches it; a stale entry can need a support
     request, so a page that still shows Claude an hour later is not a
     failed rewrite.

WHAT COULD STILL STOP IT. If, when the time comes, there are open PRs or
another session is mid-work, say so and ask rather than proceeding -- the
approval is for the rewrite, not for doing it at a moment that costs
somebody else their work.
