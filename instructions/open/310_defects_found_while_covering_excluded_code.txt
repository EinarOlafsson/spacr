2. A BARE VEuPATHDB ACCESSION IS CLASSIFIED AS A GUIDE  (lane: spacr/hits.py)
--------------------------------------------------------------------------------

``guide_of("fraction[TGGT1_231640]")`` returns ``"TGGT1_231640"`` -- a guide --
because the shape rule ``_\d+$`` matches the accession's own numeric tail.
Only the explicit spelling protects it:
``guide_of("gene_fraction:gene[TGGT1_231640]") is None``.

Consequence: an unlabelled gene term lands in the *grna* testing family rather
than the gene family, which changes which multiple-testing family a term is
corrected within. Every table spaCR writes today carries the label, so this
reaches only legacy or hand-built formulas -- but it is a scientific
classification error, not a cosmetic one, which is why it is filed rather than
patched in passing.

A fix must change BOTH ``guide_of`` and ``family_labels``: family_labels
computes ``suffix_guide`` independently and its docstring promises it agrees
with guide_of, so changing one alone makes the docstring false. The candidate
rule is ``_gene_id_of(token) != token``.

Current behaviour is pinned by
tests/test_hits_uncovered_paths.py::test_only_an_explicit_label_protects_a_bare_veupathdb_accession,
so that test must be UPDATED, not deleted, when the behaviour changes.

FIXED 2026-08-29. ``guide_of`` and the vectorized ``family_labels`` path now
share one ``_is_guide_token`` predicate: a token is a guide only when
normalizing it to a gene id removes a suffix. Thus ``TGGT1_231640`` remains a
gene while ``TGGT1_231640_3`` remains a guide, and the updated regression test
asserts both public functions agree on all three explicit/bare spellings.

2b. TWO LATENT DEFECTS IN DEAD ATTRIBUTION CODE  (lane: spacr/guide_attribution.py)
--------------------------------------------------------------------------------

Both are unreachable today -- proved by exhaustive and random fuzzing -- so
neither is a live bug. They are recorded because each would be SILENT
corruption of a scientific result if the guard above it ever did fire, and
because the obvious "fix" at each site does not actually recover.

  * L487 ``if columns.size != n:`` then ``columns[:n]``. Slicing does not
    recover: ``linear_sum_assignment`` on an (n x m) matrix with m < n matches
    only m rows, so ``assigned`` would be shorter than the cell count -- cells
    dropped from the attribution without a word -- and ``order =
    np.empty(n)`` would carry UNINITIALISED memory into ``best`` and then into
    ``degeneracy``. Verified against scipy directly.
  * L675 ``density[dead, :] = weights`` in ``posterior_multivariate``. Copied
    from ``posterior``, where it is live and correct. Here it sets ``density =
    prior`` and the following ``r = density * weights`` applies the prior a
    SECOND time, so a dead row would start from prior-squared, not the prior
    the comment promises.

If either guard is ever made reachable, the body must be rewritten, not
uncommented.

5. THE WORKING TREE ITSELF WAS THE FIRST DEFECT  (2026-08-29, later session)
--------------------------------------------------------------------------------

Before any coverage could be measured, the tree it would have been measured on
turned out to be in two contradictory states at once. This is recorded here
because a coverage number taken from it would have been fiction, and because
the same shape will recur whenever work is committed from a side worktree.

/mnt/firecuda2/codex/repo/spacr was found to be SIMULTANEOUSLY:

  * BEHIND origin/nightly. 36 files present in HEAD were absent from disk,
    including the entire spacr/flowview/ package and its tests, committed that
    same afternoon between 17:28 and 19:38. The reflog shows why: repeated
    ``commit`` -> ``reset: moving to origin/nightly`` cycles. Those commits
    were made in OTHER worktrees (codex/pushwt, codex/covwt3) and pushed, and
    this tree received a MIXED reset, which moves the pointer and never
    touches a file. It therefore never got them.
  * AHEAD in unsaved work. 199 modified files whose exact content appears in
    NO commit in the repository's entire history -- checked against all 47,765
    blobs reachable from every ref, not merely recent ones -- plus 62
    untracked files.

Both halves matter and they are easy to confuse. ``git status`` alone reads as
"someone has edits"; it does not distinguish an edit from a file this checkout
never received, and ``git pull`` or ``git restore`` on that state would have
destroyed the 199.

THE CHECK THAT SEPARATES THEM, since it is not obvious:

    h=$(git hash-object "$f")
    git rev-list --objects --all | awk 'NF>1{print $1}' | grep -qx "$h" \
      && echo "committed somewhere (tree is merely behind)" \
      || echo "content exists only here"

A second, cheaper discriminator for a file that IS unique: count deletions in
``git diff HEAD -- "$f"``. Zero deletions means the working copy is HEAD plus
additions and is safe to commit; deletions mean the copy lacks something HEAD
has, and committing it would silently revert that.

Of 146 modified test files, only 21 were pure additions. The other 125 each
carried deletions against HEAD and were left alone.

WHAT WAS RECOVERED: 54 test files (34 new, 20 pure-addition edits) and
spacr/resource_log.py, all run before committing -- 970 passed, 4 skipped.

TWO FILES DELIBERATELY NOT RECOVERED, each checked against a CLEAN worktree at
HEAD rather than assumed:

  * tests/qt/test_registration_seams.py fails three tests in the working tree
    and THE SAME THREE on clean HEAD -- test_nothing_registered_is_byte_-
    identical_to_no_seam_at_all, test_none_opacity_reaches_the_callback_as_none
    and test_two_widgets_cannot_quietly_claim_one_name. Pre-existing, and red
    on HEAD right now, which item 288's "one green commit" cannot tolerate.
    Lane: Qt.
  * tests/qt/test_external_i18n_catalogs.py fails TWO in the working tree and
    a DIFFERENT FOUR on clean HEAD. A file that fails differently on two trees
    is reporting catalog state, not code. Lane: i18n.

THE RULE THIS ADDS to HANDOFF 0c ("git commit without paths commits the
index") and 3f ("pip -e pointed at the wrong checkout"): BEFORE MEASURING
ANYTHING, ASSERT THE TREE IS WHAT YOU THINK IT IS. A stale checkout does not
announce itself, and neither does a checkout carrying a day of unsaved work.

    git status --short | wc -l          # both halves, undifferentiated
    git diff HEAD --stat | tail -1      # how far apart they are

Coverage is now measured on a frozen worktree at /mnt/firecuda2/codex/covclean

6. A CRASH FOUND BY WRITING A TEST FOR A BRANCH  (lane: spacr/annotation.py)
--------------------------------------------------------------------------------

FIXED 2026-08-29. ``spacr.annotation.annotate`` raised

    KeyError: "['gene_nr'] not found in axis"

on any table whose gene column is literally named ``gene_nr``.

The cause: the join did ``out.merge(right[["gene_nr"] + new], left_on=
"_gene_nr", right_on="gene_nr")`` and then ``out.drop(columns=["gene_nr"])``.
When the caller's own frame already carries ``gene_nr``, pandas suffixes both
sides into ``gene_nr_x`` and ``gene_nr_y``, so the drop finds no ``gene_nr``
and raises.

THIS IS NOT AN EXOTIC INPUT. ``gene_nr`` is the FIRST name ``_key_column``
looks for, ahead of ``gene``, ``gene_id``, ``grna`` and ``feature`` -- so it is
the canonical spelling, and it is what spaCR's own annotated output is keyed
on. Re-annotating a table that this very function had already written crashed.
It went unnoticed because every fixture in the suite keyed on ``grna`` or
``gene``, which is also why the "already annotated, stay quiet" branch below
it had never run: nothing had ever reached a second pass.

Fixed by renaming the right-hand key to a private ``_JOIN_KEY`` before the
merge, so the two sides cannot collide and the drop names a column that is
certainly there. Regression: 622 annotation/toxo tests pass, and a table keyed
on ``gene_nr`` now survives two passes.

The branch that started this is tests/test_the_last_branch_in_five_readers.py::
test_a_second_annotation_pass_says_nothing_when_asked_to_be_quiet.

  * spacr/model_zoo.py:481 -- ``return f"{n:.1f} GB"`` after the loop in
    ``_human_bytes``. A THIRD instance of the pattern already recorded for
    spacr/data_manager.py:333: ``for unit in ("B", ..., "GB"): if n < 1024 or
    unit == "GB": return ...``. On the final iteration the ``unit == "GB"``
    disjunct is unconditionally true, so the loop cannot complete. Verified by
    brute force over 0.5, 1, 1023, 1024, 1024**2, 1024**3, 1024**4, 1024**8,
    1e300 and inf -- every one returns from inside the loop, including inf,
    which yields "inf GB".

    Three copies of one helper, all with the same unreachable tail. This is
    the deduplication candidate that spacr/fit_resources.py ``readable`` and
    spacr/mixed_gpu.py ``_readable`` were already noted for in section 4; the

7. THE COVERAGE REPORT'S LINE NUMBERS ARE NOT THE WORKING TREE'S
--------------------------------------------------------------------------------

A coverage report is taken on a FROZEN worktree and read on the SHARED one, and
those two disagree wherever the shared tree has uncommitted edits. spacr/crops.py
is the case that surfaced it: its working copy carries eight extra comment lines,
so the report's "missing lines 3619, 3621, 3622" pointed at comment text when
read in the shared tree, which is impossible and is what gave it away.

Checked across every module targeted in this session's sweep: crops.py was the
only one affected, so nothing else needs revisiting. But the trap is general and
it fails QUIETLY in the other direction -- a report line that lands on a
different STATEMENT rather than on a comment gives a test aimed at the wrong
branch, which then passes.

THE CHECK: compare the file, not the commit. ``git diff eb4af2ef HEAD -- <file>``
was EMPTY for crops.py and still the two files differed, because the difference
was never committed at all.

    md5sum <frozen-worktree>/spacr/x.py <shared-tree>/spacr/x.py

THE HABIT THAT AVOIDS IT: verify by ARC, not by line number. Every closure in
this sweep was confirmed by re-running under coverage with the exclude list
emptied and checking ``executed_branches`` for the specific arc -- so a
misread line number shows up as a test that does not close what it claimed,
rather than as a green test measuring the wrong thing. That check caught three
tests in this session that exercised nothing.

  * The dead ``dirname(abspath(...))`` guard has TWELVE independent copies:
    roi.py:451, figures/headless.py:111, plate_qc.py:1014 (write_layout_csv),
    style_base.py:182 (write), counting.py:401 (to_csv), tabular.py:231
    (write_table), tabular.py:420 (write_database), illumination.py:386
    (IlluminationModel.save), convert.py:2041 (populate_db_from_map),
    curation.py:315 (CurationLog.write), curation.py:967 (save) and
    report.py's own walk helper. Same proof each time: '', '.', '/', 'out.csv' and 'a/b.csv'
    all yield a non-empty directory, so ``if parent:`` is unconditionally true
    and its false side can never be taken.

    TWELVE copies is not twelve slips, it is one idiom nobody has written down. The
    fix is a shared helper -- ``_ensure_parent(path)`` doing the abspath and
    the makedirs together and returning the absolute path -- which removes twelve
    uncoverable arcs and the twelve chances for a later edit to drop the abspath
    and make the guard load-bearing again. NOT REMOVED HERE, deliberately, and item 288's own wording is why: "Truly

``SPACR_ALLOW_GITHUB_WRITES=1`` was intended to let offline tests exercise the

a mock. Test permission must be coupled to the substituted capability itself,
and a test-session prohibition must outlive every individual test phase and

The coverage runner installs Torch but has no NVIDIA driver, so Home's NVML
probe returns no device. ``SystemPanel.gpu_util`` and ``gpu_vram`` then each
fell back to importing Torch just to print ``no CUDA`` or process-allocated
VRAM. Merely opening spaCR therefore loaded the model runtime on precisely the
CPU-only and laptop installations where the fallback was most likely. Two
fresh-process memory contracts caught it in CI: startup and ordinary module
navigation both found ``torch`` already in ``sys.modules``.

Fixed by keeping Home on the lightweight NVML boundary. When that probe cannot
measure a device, both cells honestly report ``n/a``; choosing an operation
that needs Torch remains the boundary that may import it. The former fallback
test now blocks every Torch import and drives both dashboard readings, while
the existing real-NVML tests retain exact utilisation and used/total VRAM
coverage.

THE GENERAL RULE. A status card may report what an already-lightweight probe
knows. It must not initialise the resource-heavy subsystem it is supposed to
describe, because observation would then change both startup memory and GPU
state.

23. COVERAGE SHARDS EXPOSED SIX TESTS OF ACCIDENTAL ENVIRONMENT STATE
--------------------------------------------------------------------------------

The full CI matrix exercised paths that isolated developer runs did not. Six
contracts were measuring the runner instead of the behaviour they named:

* a regression-only announcement test required an otherwise unrelated console
  to be empty, although startup diagnostics may already own its current block;
* a tooltip transparency test sampled two fixed pixels, one of which can fall
  on a glyph when CI substitutes a font with different bearings;
* two organelle tests still encoded the pre-instruction-300 rule that a missing
  cell channel hides the reference-cell controls;
* a cold-process model test used one developer machine's absolute checkout;
* a harmless-unsubscribe test made no observation at all; and
* parameter-sweep tests accidentally admitted or refused work according to the
  current host's free memory, while two UI tests inspected a deliberately lazy
  panel before asking it to build.

Fixed each contract at its ownership boundary. The announcement test compares
the console before and after the helper; tooltip transparency uses the modal
colour of each complete container; cell controls follow the current reference-
object rule; the child process derives its repository from the test file; the
unsubscribe test proves the callback registry is unchanged; sweep unit tests
state their synthetic memory capacity; and UI tests explicitly take the same
switch transition a user takes before inspecting the realised panel.

THE GENERAL RULE. A deterministic test supplies every environmental input that
can change its decision and observes only the state owned by the operation.
Cold-process tests derive their checkout, rendering tests tolerate legitimate
font metrics, and lazy UI tests exercise the public transition that constructs
the object they inspect.

25. THE LINE-NUMBER TRAP AGAIN, THIS TIME SELF-INFLICTED (see also section 7)
    -------------------------------------------------------------------------
    Section 7 recorded that a coverage report's line numbers stop matching the
    working tree when the tree has edits the measured copy did not. Here is the
    same trap arriving by a route worth naming separately: MY OWN EDIT, EARLIER
    IN THE SAME SESSION.

    Removing the dead `if parent:` guard from counting.py deleted one line at
    401. Every line after it shifted up by one, so the batched run's

        spacr/counting.py arc 450->449

    became arc 449->448 in the tree. Checking the old numbers reported MISSING
    for an arc the new test had just covered, and the obvious next move -- write
    another test -- would have been chasing a number, not a gap.

    THE RULE THAT SURVIVES THIS. A coverage artifact is only valid against the

    re-derive the line from the code rather than from the report. The check

    handed; reading the three lines around the arc costs seconds and settles it.

    Eleven files were edited in the guard removal, so eleven files' arcs in the
    2026-08-30 batched artifact are off by one or two after the edit point. The
    artifact is still correct for the commit it names.

29. THE COLOUR CHOOSER ADDED A DUPLICATE ROW EVERY TIME IT WAS USED

33. A PALETTE EVENT RESOLVED THE PAGE BEFORE ITS BACKDROP EXISTED
--------------------------------------------------------------------------------

Importing the full Qt application changes when palette events are delivered
while a module screen is being built. One can arrive from the settings
builder's explicit event processing before the constructor has decided
whether to install an ambient backdrop. ``changeEvent`` nevertheless called
``_sync_page_palette`` immediately. It saw ``_ambient is None`` as "no

Home-import order is green with branch coverage: 103 tutorial and module-build
contracts pass under PySide6/Qt 6.11.2.

34. A FOURTH TEST THAT ASSERTED NOTHING, AND WHAT THE FOUR HAVE IN COMMON
--------------------------------------------------------------------------------
    `_check_app_specific(settings, app)` returns an empty list for an app it
    has no rules for. A test written as

        problems = V._check_app_specific({...}, "explain_cv_model")
        assert "surrogate_model" not in _keys(problems)

    passes whatever the validator does, because the app key is "explain_cv"
    and the whole block was skipped. `not in []` is True.

    THE SHAPE, NOW SEEN FOUR TIMES (sections 5, 7, 16, this):

      * the runctx factory test        -- built the wrong object
      * a `to_crop_settings` stub      -- made `dict()` fail, so {} came back
      * the control_names retry        -- an input that could not reach the arc
      * this                           -- an identifier the function ignores

    Every one of them ASSERTS AN ABSENCE, and an absence is what a function
    returns when it did nothing. Every one of them passed. The arc check
    caught all four and nothing else would have.

    TWO HABITS FOLLOW.

    First: run the arc check on every test written for a named branch, before
    committing. That is already the practice here and it is the only thing
    that has ever caught this.

    Second, and cheaper: when a test asserts that something is ABSENT, assert
    in the same test that the machinery is live -- drive one input that
    produces the thing, so "no complaint" is the code agreeing rather than the
    code never having run. Both new tests here do that now, and it makes them
    fail on a mistyped app key without needing coverage at all.

35. THE ARC CHECKER COULD NOT READ AN EXIT ARC
--------------------------------------------------------------------------------
    coverage.py writes a return or fall-off-the-end as a NEGATIVE target:

        [617, -610]   "line 617 exits the function that starts at 610"

    `check_arcs.py` split each target on "-" and int()'d both halves, so
    `617--610` produced an empty second field and the script died with

        ValueError: invalid literal for int() with base 10: ''

    -- in the middle of verifying a commit. Every early return in the package
    is an arc of that shape, so the one tool this work depends on could not
    check the single most common branch there is. It was worked around by
    hand twice before being fixed, which is twice too many.

    Fixed: split on the first separator after position 0, so a leading minus
    stays with the head and the tail keeps its own sign.

    Worth noting for what it says about the artifact rather than the script.
    A tool that silently could not answer a whole CLASS of question is the
    same failure as a coverage run that silently loses a worker: the number
    it gives is right, and it is not the number you asked for.

36. SAVING A GENE-MEASUREMENT COMPARISON LEAKED ITS PRIVATE FIGURE
--------------------------------------------------------------------------------
    ``gene_measurement_compare.save`` builds a pyplot figure, writes its PDF
    and PNG paths, and returns only those paths.  It never closed the figure.
    No caller could take ownership of an object it was never given, so every
    save left one more figure registered in a long-lived GUI or batch process.

    The minimum-dependency coverage order exposed the leak through a later
    panel test.  That test had its own defect: it required the process-wide
    Matplotlib registry to be empty, even though the caller may legitimately
    own unrelated open figures.  Earlier comparison tests also created
    caller-owned figures without closing them, making the order dependence
    deterministic.

    ``save`` now closes only the private figure in a ``finally`` block.  The
    tests close the figures they own, and the panel contracts keep a sentinel
    caller figure while checking that ``available`` neither leaks a new one
    nor closes somebody else's.  The exact two-file order is green (30 tests),
    as is the original 32-file minimum-dependency batch (248 tests), without
    the more-than-20-figures warning.
