2. A BARE VEuPATHDB ACCESSION IS CLASSIFIED AS A GUIDE  (lane: spacr/hits.py)
--------------------------------------------------------------------------------

``guide_of("fraction[TGGT1_231640]")`` returns ``"TGGT1_231640"`` -- a guide --
because the shape rule ``_\d+$`` matches the accession's own numeric tail.
Only the explicit spelling protects it:
``guide_of("gene_fraction:gene[TGGT1_231640]") is None``.

Consequence: an unlabelled gene term lands in the *grna* testing family rather
than the gene family, which changes which multiple-testing family a term is
corrected within. Every table spaCR writes today carries the label, so this
reaches only legacy or hand-built formulas -- but it is a scientific
classification error, not a cosmetic one, which is why it is filed rather than
patched in passing.

A fix must change BOTH ``guide_of`` and ``family_labels``: family_labels
computes ``suffix_guide`` independently and its docstring promises it agrees
with guide_of, so changing one alone makes the docstring false. The candidate
rule is ``_gene_id_of(token) != token``.

Current behaviour is pinned by
tests/test_hits_uncovered_paths.py::test_only_an_explicit_label_protects_a_bare_veupathdb_accession,
so that test must be UPDATED, not deleted, when the behaviour changes.

FIXED 2026-08-29. ``guide_of`` and the vectorized ``family_labels`` path now
share one ``_is_guide_token`` predicate: a token is a guide only when
normalizing it to a gene id removes a suffix. Thus ``TGGT1_231640`` remains a
gene while ``TGGT1_231640_3`` remains a guide, and the updated regression test
asserts both public functions agree on all three explicit/bare spellings.

2b. TWO LATENT DEFECTS IN DEAD ATTRIBUTION CODE  (lane: spacr/guide_attribution.py)
--------------------------------------------------------------------------------

Both are unreachable today -- proved by exhaustive and random fuzzing -- so
neither is a live bug. They are recorded because each would be SILENT
corruption of a scientific result if the guard above it ever did fire, and
because the obvious "fix" at each site does not actually recover.

  * L487 ``if columns.size != n:`` then ``columns[:n]``. Slicing does not
    recover: ``linear_sum_assignment`` on an (n x m) matrix with m < n matches
    only m rows, so ``assigned`` would be shorter than the cell count -- cells
    dropped from the attribution without a word -- and ``order =
    np.empty(n)`` would carry UNINITIALISED memory into ``best`` and then into
    ``degeneracy``. Verified against scipy directly.
  * L675 ``density[dead, :] = weights`` in ``posterior_multivariate``. Copied
    from ``posterior``, where it is live and correct. Here it sets ``density =
    prior`` and the following ``r = density * weights`` applies the prior a
    SECOND time, so a dead row would start from prior-squared, not the prior
    the comment promises.

If either guard is ever made reachable, the body must be rewritten, not
uncommented.

5. THE WORKING TREE ITSELF WAS THE FIRST DEFECT  (2026-08-29, later session)
--------------------------------------------------------------------------------

Before any coverage could be measured, the tree it would have been measured on
turned out to be in two contradictory states at once. This is recorded here
because a coverage number taken from it would have been fiction, and because
the same shape will recur whenever work is committed from a side worktree.

/mnt/firecuda2/codex/repo/spacr was found to be SIMULTANEOUSLY:

  * BEHIND origin/nightly. 36 files present in HEAD were absent from disk,
    including the entire spacr/flowview/ package and its tests, committed that
    same afternoon between 17:28 and 19:38. The reflog shows why: repeated
    ``commit`` -> ``reset: moving to origin/nightly`` cycles. Those commits
    were made in OTHER worktrees (codex/pushwt, codex/covwt3) and pushed, and
    this tree received a MIXED reset, which moves the pointer and never
    touches a file. It therefore never got them.
  * AHEAD in unsaved work. 199 modified files whose exact content appears in
    NO commit in the repository's entire history -- checked against all 47,765
    blobs reachable from every ref, not merely recent ones -- plus 62
    untracked files.

Both halves matter and they are easy to confuse. ``git status`` alone reads as
"someone has edits"; it does not distinguish an edit from a file this checkout
never received, and ``git pull`` or ``git restore`` on that state would have
destroyed the 199.

THE CHECK THAT SEPARATES THEM, since it is not obvious:

    h=$(git hash-object "$f")
    git rev-list --objects --all | awk 'NF>1{print $1}' | grep -qx "$h" \
      && echo "committed somewhere (tree is merely behind)" \
      || echo "content exists only here"

A second, cheaper discriminator for a file that IS unique: count deletions in
``git diff HEAD -- "$f"``. Zero deletions means the working copy is HEAD plus
additions and is safe to commit; deletions mean the copy lacks something HEAD
has, and committing it would silently revert that.

Of 146 modified test files, only 21 were pure additions. The other 125 each
carried deletions against HEAD and were left alone.

WHAT WAS RECOVERED: 54 test files (34 new, 20 pure-addition edits) and
spacr/resource_log.py, all run before committing -- 970 passed, 4 skipped.

TWO FILES DELIBERATELY NOT RECOVERED, each checked against a CLEAN worktree at
HEAD rather than assumed:

  * tests/qt/test_registration_seams.py fails three tests in the working tree
    and THE SAME THREE on clean HEAD -- test_nothing_registered_is_byte_-
    identical_to_no_seam_at_all, test_none_opacity_reaches_the_callback_as_none
    and test_two_widgets_cannot_quietly_claim_one_name. Pre-existing, and red
    on HEAD right now, which item 288's "one green commit" cannot tolerate.
    Lane: Qt.
  * tests/qt/test_external_i18n_catalogs.py fails TWO in the working tree and
    a DIFFERENT FOUR on clean HEAD. A file that fails differently on two trees
    is reporting catalog state, not code. Lane: i18n.

THE RULE THIS ADDS to HANDOFF 0c ("git commit without paths commits the
index") and 3f ("pip -e pointed at the wrong checkout"): BEFORE MEASURING
ANYTHING, ASSERT THE TREE IS WHAT YOU THINK IT IS. A stale checkout does not
announce itself, and neither does a checkout carrying a day of unsaved work.

    git status --short | wc -l          # both halves, undifferentiated
    git diff HEAD --stat | tail -1      # how far apart they are

Coverage is now measured on a frozen worktree at /mnt/firecuda2/codex/covclean
created with ``git worktree add --detach``, never on the shared tree.

6. A CRASH FOUND BY WRITING A TEST FOR A BRANCH  (lane: spacr/annotation.py)
--------------------------------------------------------------------------------

FIXED 2026-08-29. ``spacr.annotation.annotate`` raised

    KeyError: "['gene_nr'] not found in axis"

on any table whose gene column is literally named ``gene_nr``.

The cause: the join did ``out.merge(right[["gene_nr"] + new], left_on=
"_gene_nr", right_on="gene_nr")`` and then ``out.drop(columns=["gene_nr"])``.
When the caller's own frame already carries ``gene_nr``, pandas suffixes both
sides into ``gene_nr_x`` and ``gene_nr_y``, so the drop finds no ``gene_nr``
and raises.

THIS IS NOT AN EXOTIC INPUT. ``gene_nr`` is the FIRST name ``_key_column``
looks for, ahead of ``gene``, ``gene_id``, ``grna`` and ``feature`` -- so it is
the canonical spelling, and it is what spaCR's own annotated output is keyed
on. Re-annotating a table that this very function had already written crashed.
It went unnoticed because every fixture in the suite keyed on ``grna`` or
``gene``, which is also why the "already annotated, stay quiet" branch below
it had never run: nothing had ever reached a second pass.

Fixed by renaming the right-hand key to a private ``_JOIN_KEY`` before the
merge, so the two sides cannot collide and the drop names a column that is
certainly there. Regression: 622 annotation/toxo tests pass, and a table keyed
on ``gene_nr`` now survives two passes.

The branch that started this is tests/test_the_last_branch_in_five_readers.py::
test_a_second_annotation_pass_says_nothing_when_asked_to_be_quiet.

  * spacr/model_zoo.py:481 -- ``return f"{n:.1f} GB"`` after the loop in
    ``_human_bytes``. A THIRD instance of the pattern already recorded for
    spacr/data_manager.py:333: ``for unit in ("B", ..., "GB"): if n < 1024 or
    unit == "GB": return ...``. On the final iteration the ``unit == "GB"``
    disjunct is unconditionally true, so the loop cannot complete. Verified by
    brute force over 0.5, 1, 1023, 1024, 1024**2, 1024**3, 1024**4, 1024**8,
    1e300 and inf -- every one returns from inside the loop, including inf,
    which yields "inf GB".

    Three copies of one helper, all with the same unreachable tail. This is
    the deduplication candidate that spacr/fit_resources.py ``readable`` and
    spacr/mixed_gpu.py ``_readable`` were already noted for in section 4; the

--------------------------------------------------------------------------------

A coverage report is taken on a FROZEN worktree and read on the SHARED one, and
those two disagree wherever the shared tree has uncommitted edits. spacr/crops.py
is the case that surfaced it: its working copy carries eight extra comment lines,

it fails QUIETLY in the other direction -- a report line that lands on a

THE CHECK: compare the file, not the commit. ``git diff 4eccf7b8 HEAD -- <file>``
was EMPTY for crops.py and still the two files differed, because the difference

THE HABIT THAT AVOIDS IT: verify by ARC, not by line number. Every closure in
this sweep was confirmed by re-running under coverage with the exclude list
emptied and checking ``executed_branches`` for the specific arc -- so a
misread line number shows up as a test that does not close what it claimed,
rather than as a green test measuring the wrong thing. That check caught three
tests in this session that exercised nothing.

  * The dead ``dirname(abspath(...))`` guard has TWELVE independent copies:
    roi.py:451, figures/headless.py:111, plate_qc.py:1014 (write_layout_csv),
    style_base.py:182 (write), counting.py:401 (to_csv), tabular.py:231

8. A CONSENSUS THAT IS SAFE ONLY BECAUSE ITS CALLERS PAD  (lane: spacr/sequencing.py)
--------------------------------------------------------------------------------

``create_consensus`` (spacr/sequencing.py:283-287) loops over ``len(seq1)`` and
indexes ``seq2`` and ``qual2`` at the same offset. A shorter second sequence
raises IndexError; nothing in the function checks, and the docstring does not
say the two must be equal.

It is safe today because all three callers --
``paired_find_sequence_in_chunk_reads``, its reverse-complement retry, and
``single_find_sequence_in_chunk_reads`` -- pad both reads to ``expected_end``
before calling. The padding is four lines above each call and reads as
cosmetic.

WHY THAT MATTERS BEYOND TIDINESS: this runs inside a chunk worker over a whole
FASTQ, so the failure mode of removing or reordering that padding is an
IndexError in a subprocess partway through a sequencing run.

THE ASYMMETRY IS WORSE THAN THE RAISE. A shorter seq2 raises. A LONGER seq2 is
silently ignored past ``len(seq1)``, so the second read simply stops
contributing -- no error, a consensus built from one read, and a count that
lands in the wrong well rather than being discarded.

CONSEQUENCE FOR ITEM 288, and this is why it is filed rather than fixed: the
padding makes ``len(consensus_seq)`` exactly ``expected_end``, so the three
``if len(consensus_seq) >= expected_end:`` guards at :436, :461 and :521 are
unconditionally true. Their false arcs -- 436->407, 461->467 and 521->497 --
are UNREACHABLE and cannot be covered without deleting the padding. Verified by
fuzzing create_consensus over 3,000 equal-length pairs: the consensus is
exactly ``len(seq1)`` every time.

The invariant is now pinned by tests/test_the_consensus_depends_on_its_callers_padding.py,
so a change that stops padding fails a test instead of a run. A fix would give
create_consensus its own length check; that is a decision for the sequencing

13. THE MEASUREMENT ITSELF IS NOT YET TRUSTWORTHY  (lane: item 288)
--------------------------------------------------------------------------------

Two complete full-suite runs now exist and their whole-library figures DISAGREE
in the wrong direction:

    2026-08-29, commit 4eccf7b8   95.00%   494 modules, 167 at 100%
                                  46,918 passed / 453 failed / 1:49:41
                                  2 'node down' events

    2026-08-30, commit 955faa4e   88.99%   508 modules, 132 at 100%
                                  47,673 passed / 421 failed / 2:05:00
                                  3 'node down' events

The second run has 755 MORE passing tests, 32 FEWER failures, and 99 new test
files -- and reports six points LESS coverage. That is not a regression, and
the tests prove it is not: 186 modules read materially lower and only 17 read
higher, which is a systematic loss rather than 186 separate ones.

THE CAUSE IS THE LOST WORKERS. Each 'node down' takes an xdist worker's
coverage data with it. The tests it had already run still count toward the
pass/fail summary -- the master reassigns them or the run continues -- but the
lines they executed are gone from the report.

PROOF, on a module whose gap this session closed: spacr/figure_font.py measures
51/51 units when its own test file is run alone, 38/51 in this full run, and
31/51 in the previous one. The module did not change between the last two
numbers; the worker that ran its tests did.

CONSEQUENCE FOR ITEM 288. Its contract wants "a clean frozen-worktree coverage
run [that] reports 100% statements and branches for every spaCR module". A run
that silently loses a worker's data cannot demonstrate that -- it will report
modules as short when they are complete, and no amount of test-writing will
close a gap that is an artifact of the harness.

WHAT WOULD FIX IT, in preference order:

  1. ``-p xdist --dist loadfile`` with ``--max-worker-restart`` set, so a
     worker that dies is replaced and its FILES are re-run rather than lost.
     This also restarts the interpreter periodically, which addresses the
     six-fold deceleration HANDOFF 3d records.
  2. Batched runs in fresh processes, combining ``.coverage.*`` at the end --
     the design already written at
     covscratch/run_coverage.sh. Slower, but every batch's data is on disk
     before the next begins, so one death costs one batch.
  3. A single-process run (no -n). Trustworthy and far too slow for 48,000
     tests, but it is the reference a batched run should be checked against
     once.

Until one of those is done, every whole-library percentage in this instruction
is a FLOOR, and the per-module rows are only trustworthy where they read 100%.
Individual closures in this sweep were each verified by re-running the module's
own tests under coverage and checking ``executed_branches`` for the specific
arc, which is why they are reliable while the aggregate is not.

27. TWO MEASUREMENT DEFECTS THAT SILENTLY INVALIDATE A COVERAGE RUN
==============================================================================

Both cost real time, both produce a number that looks fine, and neither
announces itself. Recorded because the failure mode is indistinguishable
from success until something else contradicts it.

27a. MEASURING A DIFFERENT TREE THAN THE AGENTS TEST

  I measured coverage in a clean git worktree checked out at HEAD, for
  reproducibility. The agents closing arcs ran pytest in the ordinary
  working tree. The two differed by 247 modified files, because a second
  lane had uncommitted work in flight.

  Nothing errors. Both runs pass. But an arc is a pair of line numbers,
  so every target in a dirty file named a line in a file the agent never
  saw. 1,662 arcs -- 38% of everything left -- looked "blocked by
  uncommitted work" when they were only blocked by my measuring the
  wrong tree.

  The fix is not to commit the other lane's work to make HEAD match. It
  is to measure what the agents actually import: rsync the working tree
  into the measurement worktree and measure the snapshot. That also buys
  immunity to a second race (27b), because a snapshot cannot be rewritten
  underneath a running measurement.

  Rule: the measured tree and the tested tree must be the same tree.
  Verify it, do not assume it -- `diff -rq` between them should print
  nothing before a run is trusted.

27b. A FULL-SUITE RUN CANNOT SHARE A CHECKOUT WITH AGENTS WRITING TESTS

  A whole-suite xdist run in the live repo aborted at collection:

    Different tests were collected between gw5 and gw0

  A coverage agent had rewritten tests/qt/test_cov_r3_qt_app_1.py while
  the workers were collecting, so two workers enumerated two different
  versions of the same file and xdist refused to schedule. The run died
  after 50 seconds having measured nothing.

  This is not xdist being fragile. It is a genuine race, and xdist
  detecting it is the good outcome -- the bad outcome is 27a, where the
  same race produces a plausible number instead of an error.

  Rule: any measurement that takes longer than an agent takes to write a
  file must run against a snapshot, never the live checkout.

27c. THE COROLLARY FOR `--cov-append`

  Both defects share a root: coverage data is only meaningful relative to
  the exact source that produced it. Appending across runs, unioning two
  JSON artifacts, or reusing yesterday's target list all assume a tree
  that has not moved. When the tree has moved, every one of those
  operations produces a number that is wrong in the optimistic direction.
  An earlier union of two runs across commits read 98.68%; restricted to
  the files that were byte-identical between them it read 98.06%.

29. THE GPU BACKDROP STORMED BECAUSE ITS FALLBACK GUARDED THE WRONG MOMENT
==============================================================================

Reported from a real session, not found by coverage: running `spaceout`
on Wayland printed

    ERROR: Invoking ... _Canvas.on_draw ... for DrawEvent
    ERROR: Invoking ... repeat 2, 4, 8, 16, 32, 64, 128, 256 ...

forever, over a window that never drew a frame.

WHY THE EXISTING FALLBACK DID NOT FIRE

`create_fractal_widget` already wraps `_make_gpu_widget` in `except
Exception` and falls back to the CPU renderer, with a warning that was
itself added after an earlier bug where GPU failures were swallowed
silently. It did not fire here, and the reason is worth generalising:

    the guard was around CONSTRUCTION, and the failure was at FIRST USE.

vispy links a shader program lazily, on its first draw. Construction
therefore succeeds on a context that cannot run the shaders at all. The
first draw happens inside a DrawEvent, and vispy's dispatcher catches
what a handler raises, logs it, and RETRIES with a doubling counter --
so the one condition the fallback existed for arrived in the one place
the fallback could not see, and the retry turned a single failure into
an unbounded log.

The fix is to make the failure happen where the guard already is: link
the program in `_Canvas.__init__`, inside the try the caller already
has. `on_draw` is also guarded now, and checks `_dead` on entry, because
a context can be lost after a successful link and one lost context must
not become a storm either.

THE UNDERLYING INCOMPATIBILITY

On Wayland, Qt gives vispy a GLES context. vispy prepends `#version 120`
-- desktop GLSL -- to shaders that carry no version directive of their
own, and the driver answers

    on line 2: error C0201: unsupported version 120
    on line 3: error C7532: global type vec2 requires "#version 100" or later

The "requires #version 100 or later" phrasing is GLSL ES, which is what
identifies the context as ES rather than desktop. The identical session
under QT_QPA_PLATFORM=xcb gets a GLX context and runs on the GPU with no
errors at all, so this is a property of the Qt platform plugin, not of
the machine, the driver, or the card.

Not fixed: making the shaders compile on a GLES context. That needs them
written to a version GLES accepts, and the fragment shaders are the
substantial ones. Until then Wayland gets the CPU renderer.

THE GENERAL SHAPE, WHICH IS THE PART WORTH KEEPING

A `try` around construction only covers what construction actually does.
Any resource acquired lazily -- a shader program, a database handle, a
model weight file, a compiled kernel -- moves its failure out of that try
and into the first call that touches it. Where the caller's recovery is
attached to construction, laziness silently disables the recovery. Force
the acquisition inside the guard, or move the guard to where the
acquisition happens.

THE TESTS, AND WHY THEY DO NOT USE A REAL CONTEXT

Both contracts are driven through an injected program that refuses to
link, not through a GL context a test would have to hope is broken. The
offscreen platform the suite runs on compiles these shaders fine, so a
test that waited for a real failure would skip everywhere it mattered.
The first version of the file did exactly that and the suite's own
hygiene guard rejected it, correctly: `except Exception: pytest.skip(...)`
would have reported a genuine break in the factory as a skip. It now
skips only on `GpuBackendError`, which is precisely "no usable GL
context here".

27c, CONTINUED: THE INSTANCE THAT HAPPENED AN HOUR AFTER 27c WAS WRITTEN
------------------------------------------------------------------------------

Recorded because the abstract rule did not prevent the concrete mistake,
which is the most useful thing to know about a rule.

Round 3's first three files were measured against a baseline of the 34
pre-existing test files for spacr.io and spacr.regression_annotation, and
the marginal figure -- coverage those files add that the baseline does
not already have -- came out as 939 lines+arcs. That number went into the
commit message of 9295a875.

Re-running the identical comparison later gave 1533, itemised as io.py
715 and regression_annotation.py 818. Nothing about the test files had
changed. What changed was `base.json`: it had been overwritten between
the two computations, so the second run subtracted a different baseline
from the same measurement.

The commit message therefore states a number that cannot be reproduced.
It does not change what was decided -- the files close real coverage
either way, and the later keep-or-revert decision between the committed
and the agent-revised versions (1533 vs 1549) was computed inside a
single script against one baseline, so that comparison is sound.

Two things follow, and the second is the point:

  - A baseline artifact must be frozen before it is used. Copy it to a
    timestamped path and `chmod 444`. A baseline that can be rewritten is
    not a baseline; it is a variable that happens to be in a file.

  - Comparisons whose operands were produced at different times are worth
    less than comparisons computed together, even when both look equally
    like arithmetic. Prefer to load both operands and print the answer in
    one script, and prefer to re-derive a number over quoting an earlier
    one -- a figure copied forward carries none of the context that would
    reveal it had gone stale.

The general defect in 27 is that coverage data is meaningless once its
source has moved. This instance shows the same thing one level up: it is
just as meaningless once its BASELINE has moved, and the baseline is the
half nobody thinks to pin.

31. `--cov=<DOTTED PATH TO A Qt MODULE>` DUMPS CORE BEFORE ANY TEST RUNS
==============================================================================

Four agents on round 4 hit this independently and each spent real time on
it, so it is worth stating exactly. Measuring a Qt module by its dotted
module path kills the process:

    pytest <any test file> --cov=spacr.qt.widgets.annotation_strategy_panel
    -> "timeout: the monitored command dumped core"

No traceback, no pytest output, no coverage data. It reproduces with a
trivial one-line test file, so it is nothing to do with the tests being
measured. One agent traced the death to tests/conftest.py's
`from PySide6.QtCore import QSettings` inside `pytest_configure`.

WHAT DOES AND DOES NOT CRASH -- measured, not assumed:

    --cov=spacr                                        works
    --cov=spacr.qt.widgets            (package)        works
    --cov=spacr.utils                 (non-Qt module)  works
    --cov=spacr.qt.widgets.<any Qt widget module>      DUMPS CORE

It is not the import on its own. Importing that module in a bare
interpreter with no QApplication succeeds, and constructing
`coverage.Coverage(source=['spacr.qt.widgets.annotation_strategy_panel'])`
outside pytest succeeds too. It needs both: coverage resolving a `source=`
entry by importing it WHILE conftest is bringing PySide6 up in
`pytest_configure`. An ordering interaction, not a plain import failure.

THE PRACTICAL RULE

Measure with a package spec and filter afterwards:

    pytest <files> --cov=spacr --cov-branch --cov-report=json:out.json
    # then select the module out of out.json["files"]

`tools/coverage/batched_coverage.sh` already uses `--cov=spacr`, so the
whole-library measurement is not affected by this. What IS affected is
every ad-hoc per-module check, which is exactly what a coverage agent
reaches for first.

WHY IT MATTERS BEYOND THE INCONVENIENCE

A crashed process writes no coverage data, but the tests it was running
still ran. Anyone who takes the surviving data as the module's coverage
reads a module that has been measured as far less covered than it is --
which is one of the ways a target list comes to name arcs that are
already closed. See 32.

32. A STALE TARGET LIST SENDS AGENTS TO ALREADY-COVERED CODE
==============================================================================

Round 4 was scoped from a coverage artifact measured at 06:11, filtered
for modules whose source had not changed since. That filter was not
enough, and five agents reported the same thing from different modules:

  setup_slides      226 of the chunk's 229 arcs already closed
  annotation_umap_tab   every listed line and arc already closed; the
                        module was already at 100%/100%
  figure_settings   all 13 targets already closed
  model_zoo (screen)  7 of 12 arcs already closed
  memory_budget     18 of 21 already closed, by a commit landed that day
  mask              chunk said 59.8%; the pre-existing tests give 77%

Three separate causes, and they need separating because the fixes differ:

  1. DATA LOST AT MEASUREMENT TIME. A batch whose worker died contributes
     nothing while its tests still count as passed, so real coverage is
     recorded as missing. 31 is one way that happens.

  2. THE ARTIFACT PREDATES RECENT WORK. Round 3 landed between the
     artifact and round 4, so round 4's biggest targets were precisely
     what round 3 had just finished. Excluding round 3's six modules by
     hand caught most but not all of it -- memory_budget was closed by a
     commit that same morning.

  3. LINE NUMBERS DRIFT FROM COMMITS, NOT JUST FROM UNCOMMITTED EDITS.
     One agent proved its chunk was measured at commit 80a1a4b6 by
     re-parsing every revision of the file and finding exactly one with
     zero invalid statements and zero invalid arcs; HEAD's copy had been
     rewritten by 84b3bff2, so 51 of 58 arcs named positions that are not
     statements any more. Another found model_zoo's numbers uniformly off
     by +2. Both worked around it by building a difflib line map from the
     measured revision to HEAD, which is the right move and should be the
     documented one.

THE RULE THAT FOLLOWS

A target list is only valid against the exact tree it was measured on.
Before dispatching a round, either re-measure at HEAD, or record the
commit the artifact was measured at and remap through difflib -- and in
both cases drop any module that has acquired a test file since. An
mtime filter against the artifact catches uncommitted edits only; it
does not catch a commit, and it does not catch coverage that was closed
by someone else's test file.

The cheapest available check is the strongest: a module that already has
a `test_cov_*` file naming it is a module whose chunk should be
re-derived before anyone is sent to it.

33. live_preview's MIP TOOLTIP READS THE FIELD ID AS A TIME AXIS
==============================================================================

Reported by a coverage agent, verified here, NOT fixed -- the fix is a
design decision rather than a correction.

spacr/qt/widgets/live_preview.py:2019, in `_refresh_mip_toggle`:

    timed = any(len(s.key) > 2 and s.key[2] for s in sets) and planes > 1

`s` is an `ImageSet`, and its key is declared at preview_controls.py:400
as

    key: Tuple[str, str, str]     # (plate, well, field)

which `ImageSet.label()` unpacks eight lines later as
`_plate, well, fieldid = self.key`. So `s.key[2]` is the FIELD ID, not a
timepoint. It is non-empty for every ordinary acquisition, so `timed` is
true for essentially every z-stack, and the tooltip gains

    "Projects within a timepoint only; the time axis is left alone."

on data that has no time axis at all.

WHY THIS IS NOT A ONE-LINE FIX

There is no time signal available to correct it with. `ImageSet` carries
exactly four fields -- key, directory, channels, planes -- and none of
them is a timepoint or a time count. The word "timelapse" does not appear
anywhere in live_preview.py except inside the docstring of this very
method, which says the 4-D axis order "is never inferred here; that is
`t_axis_order`'s job in the pipeline, and it deliberately has no default
because (T,Z,Y,X) and (Z,T,Y,X) cannot be told apart."

So the method's own documentation says this widget cannot know, and the
line beneath it guesses anyway from a field that means something else.

The three ways out are a product decision, not a correction:

  1. Drop the sentence. The tooltip then describes the z-projection only,
     which is all this widget can honestly claim.
  2. Plumb the timelapse flag in from the settings the run was configured
     with, and say it only when that flag is set.
  3. Give `ImageSet` a real time field at discovery time, which is the
     largest change and the only one that would let the preview show
     anything else time-aware later.

Left alone deliberately. Whoever owns the preview should pick; pinning
the current behaviour in a test would only make the wrong sentence
harder to remove.

CONTRAST WITH THE custom_model DEFECT FIXED IN 387b47b5

That one was also found by reading rather than by a failing test, and it
was fixed the same afternoon -- because the correct behaviour was not in
question. The description, the validator and every consumer agreed
`custom_model` is a path; only the type table disagreed, and the repo
already had a precedent for exactly that fix. Where the intended
behaviour is unambiguous, fix it. Where the fix requires choosing what
the software should do, report it and stop. The difference is not how
sure you are that the code is wrong; it is whether "right" has one
answer.
