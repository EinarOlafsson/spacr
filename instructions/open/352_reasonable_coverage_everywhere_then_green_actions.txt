THE FIRST NUMBER IS THE TRAP THIS ITEM WARNS ABOUT, from the other side. A
module measured against "its own" tests looks twenty-five items worse than it
is, and twenty-five tests written against that reading would duplicate cover
that already exists in `test_option_c_reads_every_measurement`,
`test_a_guide_and_a_probability_for_every_cell` and a dozen others. The unit
of measurement is the SUITE, not the file whose name matches.

THE TWO THAT ARE LEFT ARE BOTH UNREACHABLE DEFENSIVE GUARDS, and neither
should be driven:

  * `attributable`, line 343, `if total <= 0: return False, 0.0`. Three
    things must hold together for it: `p < 1` (or the function has already
    returned `(True, 1.0)`), every competitor filtered out, and the fallback
    competitor's weight `1 - p` also zero -- which contradicts the first. The
    one way it used to happen is named in the comment above it: a weight
    whose conversion is not pure could pass the positivity filter as one
    number and be stored as another. READING IT ONCE CLOSED THAT, and
    `test_a_weight_is_read_once_in_attributable.py` keeps it closed.

  * `posterior_multivariate`, line 761, the `dead` row fallback. The line
    above it re-centres each row on its own maximum, so at least one entry
    is exactly zero, `exp` gives that column 1.0, and the row sum is never
    zero. An all-NaN row does not reach it either -- `NaN <= 0` is False.

WHAT WAS WRITTEN INSTEAD OF TWO TESTS THAT REACH THEM. Two classes that
assert the INVARIANT making each guard unnecessary, and say so in their
docstrings -- including the three inputs most likely to break the second
one (a zero measurement, whose log is -inf; a negative one; NaN), all three
measured and all three finite. Reaching either arm would mean weakening the
invariant to make the guard reachable, which is the wrong way round, and is
exactly the shape of the four tests 288 records as "passing while exercising
nothing".

SO guide_attribution IS DONE for this item at 98.83 %, and the two remaining
statements are recorded here as deliberate rather than left to look like
debt. THE LIST ABOVE IS STALE IN BOTH DIRECTIONS -- it says 8 -- and the

2026-09-10 -- regression_annotation: 7 ITEMS ON THE LIST, 99.06 % -> 99.57 %
--------------------------------------------------------------------------------

Second module, same method, and it went the other way from the first --
three of the four remaining statements WERE behaviours and now have tests:

  * `Strategy.describe()` when a strategy is declared and not built. Every
    shipped strategy is implemented, so the sentence has never been produced
    by the real menu -- but the field exists so a strategy can be OFFERED
    for discussion before it is built, and a menu entry that reads like a
    working feature is the failure it prevents.
  * `strategy()` handed an entry where a key is expected. The caller that
    matters passes a resolved entry through a second layer, and looking it
    up again would fail for a strategy that is not on the menu at all --
    which is exactly the case a caller holding the object is in.
  * `LeakageReport.summary()` when the INCLUSIVE fit is itself at chance.
    Survival is the fraction of that fit's lift retained after removing the
    score's own inputs; with no lift there is nothing to retain, so the
    report says so in words instead of printing a ratio nobody can read.

THE FOURTH IS AN UNREACHABLE GUARD, and it is left alone.
`_run_self_training` raises `NotEnoughLabels` when `best is None`, and the
loop is `range(max(1, int(request.rounds)))` -- it runs at least once
whatever the request asks for, and the first pass assigns `best`. Reaching
it would mean removing that floor, which trades an unreachable line for a
real way to get no fit at all.

TWO MODULES IN, THE PATTERN IS THE SAME BOTH TIMES: the stale list's number
is wrong, the per-file measurement is wrong in the pessimistic direction,
and what is left at the end is defensive guards over invariants asserted
