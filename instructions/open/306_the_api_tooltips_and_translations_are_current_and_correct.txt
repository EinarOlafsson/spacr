--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The tooltip is often the only explanation beside a scientific setting. A
wrong default, unit, option or API link can yield plausible but incorrect
analysis. The same defect in a translated catalog reaches only one locale and
can escape an English-only test run. API documentation is a public contract
and must describe the code that ships.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. INVENTORY THE WHOLE SURFACE FROM SOURCE

Generate one canonical inventory of every public module, class, function,
method and parameter; every registered setting tooltip; and every supported
locale. Compare that inventory with the built package, documentation pages,
runtime catalogs and API catalogs. Missing, duplicated, orphaned or stale
entries are failures, not fallback successes.

``tools/audit_i18n_coverage.py`` must compare catalogs to this live inventory,
not to another generated manifest which can be stale in the same direction.

2. CHECK THE ENGLISH CONTRACT AGAINST THE CODE

Verify signatures, parameter names, return/error behavior, defaults, choices,
units and cross-references against their implementations. Every setting has a
useful tooltip in the established house shape, declares its type and actual
default, names a unit when one applies, explains conditional applicability,
and links only to a real canonical API page in a fresh documentation build.

Rewrite only prose with a concrete defect. Keep user-facing text directed at
the user, concise enough to scan, specific enough to choose a value, and free
of private development history or instruction references.

Define the public class-member boundary explicitly before measuring it. Once
defined, parameter documentation is checked in both directions: no ghost
``:param:`` names and no undocumented required public parameters.

3. CHECK EVERY TRANSLATION FOR COMPLETENESS AND MEANING

For every supported language, require source-current entries for the API and
tooltips. Check placeholder and markup parity, protected scientific/database
identifiers, URLs, option literals and the spaCR wordmark mechanically. Treat
text identical to English as untranslated unless it is on a reviewed
reasoned allowlist. Review domain terms and context-sensitive words in their
actual rendered sentence; a dictionary-valid but scientifically wrong word
is a defect.

Translations remain in external locale files, not inside Python docstrings.
Unsafe or low-confidence scientific prose must fall back explicitly and be
reported, rather than being counted as translated.

4. DRIVE THE RENDERED EXPERIENCE

Build the documentation from an empty output directory with warnings treated
as errors. Exercise the language selector and runtime language switching on
representative settings-heavy modules, then verify that tooltip text, API
navigation, formatting, links and fallbacks are readable in the actual UI and
rendered pages. Record which content was reviewed by a person or language
model, the sampling method, and the exact remainder; do not call an unnamed
sample an exhaustive sweep.

5. KEEP THE RESULT RATCHETED

Run the inventory, freshness, signature/default, placeholder, protected-term,
untranslated-entry, link-resolution and documentation-build checks in required
CI. A new public symbol, setting or locale entry must fail until its English
contract and all required catalogs are current.

The documentation workflow must honor the warning-as-error Sphinx exit code;
the existence of a partially built ``index.html`` cannot convert a red build
to green. The real catalogs, not two-symbol synthetic fixtures alone, must be
driven through the runtime and browser language selectors.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * source, package, documentation, tooltip and locale inventories agree, with
    zero missing, duplicate, orphaned or stale required entries;
  * every public signature/default/cross-reference check passes against the
    implementation, and a clean warning-as-error documentation build succeeds;
  * every tooltip has the correct type and default, a unit where applicable,
    accurate applicability text and a link that resolves in that fresh build;
  * every former ``KNOWN_THIN`` exception has been verified and either fixed
    or replaced by a narrowly reasoned invariant rather than a blanket waiver;
  * every supported API and tooltip catalog has current source hashes, matching
    placeholders/markup and protected identifiers, with zero unexplained
    English-identical or low-confidence entries;
  * runtime language switching and the documentation language selector show
    the translated text and safe fallbacks in the rendered UI/pages;
  * a written review report names the languages and exact proportion reviewed,
    lists every explicit fallback or allowlisted untranslated term, and records
    the disposition of every defect found;
  * all mechanical guarantees run in required CI and fail when a synthetic
    stale docstring, missing tooltip translation or broken API link is added.
