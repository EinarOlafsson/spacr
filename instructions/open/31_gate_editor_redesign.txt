--------------------------------------------------------------------------------
ONE THING TO CONFIRM BEFORE WRITING CODE
--------------------------------------------------------------------------------

"a clustering tool using DB browse" almost certainly means **DBSCAN** -
density-based clustering, which is the standard way to turn a dense blob on
a scatter into a gate. It is NOT the spaCR Database Browser, which browses
tables and has nothing to do with clustering. ASK. Building the wrong one is
a week.

  * axis transforms and cutoffs;
  * granularity, cmap, highlight mode;

  * more than two axes;

  * generating UMAP / PCA / t-SNE in the module.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Gating is how a screen becomes a population, and every downstream number
depends on the population being the one the user meant. A gate you cannot
adjust after drawing is a gate you redraw from scratch, and a scatter you
cannot transform is one where the interesting structure sits in the bottom
2% of a linear axis.

--------------------------------------------------------------------------------
WHAT TO DO - PHASES, IN THIS ORDER
--------------------------------------------------------------------------------

Do NOT attempt this as one change. Each phase below is independently
useful and independently shippable, and the ordering is by
(value / risk), not by the order the request lists them.

PHASE 1 - make the existing gates editable and legible
  1. Move a gate: click inside, drag. Resize: grab a handle.
     RectGate is easy; PolygonGate needs per-vertex handles. Both already
     serialise, so persistence is free.
  2. Highlight mode: shade the AREA or recolour the POINTS, user's choice.
  3. Consolidate the left panel - "filter" and "columns" into one section,
     and fix the overlap. Check the layout for a missing stretch or a fixed
     height; overlapping widgets are usually one of those two.

PHASE 2 - make the plot readable
  4. Right-click an axis -> context menu: cutoffs (min/max), log / symlog /
     sqrt / none. Store the transform WITH the axis, and make gates
     transform-aware: a gate drawn on a log axis and re-read on a linear one
     must select the same objects, or gates silently change meaning. That is
     the trap in this phase and it is worth a test of its own.
  5. Granularity: subsample for drawing only. NEVER let the drawn sample
     decide the gate's contents - the gate must always be evaluated against
     the full frame, or the population depends on the zoom level.
  6. cmap picker. Reuse the existing figure/cmap settings rather than adding
     a second colour system.

PHASE 3 - selection tools
  7. Magic wand: pick a point, grow to a density/percentile threshold. Show
     the threshold and let it be adjusted - a wand whose sensitivity is
     hidden is a wand nobody trusts.
  8. DBSCAN (confirm first, see above): eps + min_samples in a "cluster
     settings" dialog, a "Cluster" button, clusters become gates or labels.

PHASE 4 - dimensionality reduction in-module
  9. UMAP / PCA / t-SNE on selected columns or a condition subset, feeding
     the same canvas. spacr.core.generate_image_umap and the Image UMAP
     module already do UMAP - call them; do not write a second embedding
     path that can drift.

PHASE 5 - more than two axes
  10. The honest options are a scatter-plot MATRIX (all pairs, gate on any
      panel) or a parallel-coordinates view. A 3-D scatter is the obvious
      idea and the worst one: gating in a rotated 3-D projection is
      imprecise and hard to reproduce. Recommend the matrix.

CROSS-CUTTING - saving labels
  11. "Saveable to any database table in a new column specified by the
      user." Generalise the write that annotate/UMAP already do: pick table,
      pick/create column, write. It must go through ONE writer -
      measurements.db has a documented concurrency hazard - and it must
      refuse to overwrite an existing column without saying so.

--------------------------------------------------------------------------------
OTHER IDEAS, SINCE THEY WERE ASKED FOR
--------------------------------------------------------------------------------

  * Show n and % at every gate, of parent and of total. GateStats already
    computes exactly this and nothing displays it. 90% of a parent that is
    2% of the plate is 1.8% of the objects, and that is the number people
    get wrong.
  * Back-gating: show where a gated population falls on the OTHER axes.
    This is the single most useful thing in flow software and it is cheap
    once gates are transform-aware.
  * A gate is already a DataFilter clause - so a gate should be usable as a
    Classify training basis (dataset_mode 'measurement') without export.
    That closes a loop the merged Classify module opened.
  * Quadrant gates: one click, four populations. Common and trivial.
  * Show the gate's definition as text, and let it be edited as text. A gate
    that can only be drawn cannot be reproduced in a methods section.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Per phase. Phase 1: draw a rectangle, drag it, and the population count
changes; reload the saved gates and it is where you left it. Phase 2: switch
an axis to log and the SAME objects stay selected. Phase 3: DBSCAN on a
known two-blob synthetic finds two clusters. Phase 5: gate on one panel of
the matrix and the others show the selection.

GATE CREATION IS BROKEN. Everything built so far -- DBSCAN clustering, the
move model, the canvas drag handler -- operates on gates that exist, so none
of it is reachable. FIX THIS BEFORE ANYTHING ELSE. Specifically:

  * POLYGON: clicking the FIRST point a second time must close the gate.
    Today closing is a separate "Close polygon" button, which is not what
    anyone tries.
  * DRAG: a click-and-drag must draw a RECTANGLE by default, with no tool
    selection needed.
  * Once closed, a gate is draggable. That part is written and tested; it
    simply has nothing to act on.

SHAPES beyond the rectangle: ovals, circles, and others, chosen by the user.

DATA DISPLAY
  * cmap choice for the scatter.
  * RESOLUTION: from every individual point through to binned density, so a
    million-row table is not a million artists. This is the same idea as the
    "granularity" already in phase 2 -- one setting, and the gate is ALWAYS
    evaluated against the full frame however coarsely it is drawn.

CLUSTERING
  * A clustering algorithm option with a hyperparameter search, including a
    WALK -- the same directional search described for Image UMAP in
    instruction 34, and it must carry the SAME NAME in both modules.

LAYOUT, as reported
  * The middle section (the one with "delete gate" at the bottom) OVERLAPS
    the filter section. The filter section itself "looks fine, and adding
    new filters does work live".
  * Filter sets and values should be SAVEABLE, exactly as gates already are.
  * The console and the AI chat box belong at the BOTTOM of that section.
  * Filter and Hyperparameter-search become TABS, the active one blue like
    the app's buttons, sitting above the console.
  * Graph, filter and search containers all resizable in width and height.

DIMENSIONALITY - the largest piece
  * Three exclusive modes, as buttons where the two axis pickers are now:
      2D  - two axis fields (today's behaviour)
      3D  - three axis fields, and the gate becomes a 3D voxel gate
      xD  - two axis fields by default, each fed by a dimensionality
            reduction over a list of columns
  * xD reduction methods: PCA, UMAP, t-SNE, and others. Each with its own
    hyperparameters, and a search/Walk toggle. Irrelevant parameters are
    GREYED when another method is chosen -- the same rule the merged
    Classify module already follows (INVARIANTS 6: greyed, not removed).

SETTINGS PANEL - three tabs
    1. General   - data resolution, cmap, which tables, what to merge on.
    2. 3D        - greyed unless 3D is active.
    3. xD        - greyed unless xD is active: how many axes (2 or 3), the
                   reduction method dropdown, its hyperparameters, and the
                   search/Walk toggle which reveals the search region.

TABLE MERGING
  * Combine cell, cytoplasm, nucleus, pathogen, organelle, png_list and any
    other table the user names.
  * DEFAULT merge key: the plate/row/column/field/object label (the cell
    object). That is what nearly every real case wants, so it is the
    default rather than a choice the user has to make first -- but it stays
    editable in the settings panel.
  * spacr.io._read_and_join_tables already does exactly this join and knows
    the traps (cell_id anchoring, the timelapse key mismatch). CALL IT.

3D WORKSPACE
  * Click and drag spins the plot on both axes.
  * The spin SNAPS to axis-aligned views: it rotates along the axes, not
    between them, and settles with two axes facing the user, one vertical
    and one horizontal.
  * With a face toward the user, the gate is edited on that face. A 3D gate
    therefore starts as a 2D shape and is then extruded along the third
    axis.
  * Shapes in 3D: polygons, cylinders, cubes, and so on -- the extrusions of
    the 2D shapes above.
