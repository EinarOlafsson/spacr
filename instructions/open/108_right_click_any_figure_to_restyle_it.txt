================================================================================
RIGHT-CLICK ANY FIGURE AND CHANGE HOW IT LOOKS, WITHOUT RE-RUNNING ANYTHING
================================================================================

Status:    not started — one worked example exists, the general mechanism does not
Requested: 2026-08-15 — "i want to be able to right click on each graph and have
           access to as many settings for the graph as possible: ledgend on/off,
           grid on/off, colors, symbols, line width, line color, font size, logx,
           logy, etc. so depending on the graph as many as many settings as
           possible"
Owner:     unassigned

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

A spaCR figure is drawn once, by whichever module produced it, from settings
fixed before the run started. Changing a legend, an axis scale or a marker
colour means editing the settings and re-running the analysis -- minutes to an
hour for a regression -- or opening the PDF in Illustrator.

ONE figure already works the way this asks for. The Volcano Explorer
(`spacr/qt/widgets/volcano_explorer.py`, screen at `qt/screens/volcano.py`)
exposes 55 controls over a live plot: axis scales and log, inversion, split
axis, four threshold rules with multipliers, 15 marker shapes, 29 colormaps,
colour-by and shape-by from any column, line width/colour/style, font
family/size/weight, titles, grid, legend, figure size, dpi -- plus click-a-
point-for-its-record and vector export. It is the worked example this
instruction generalises.

What makes it work is worth stating, because it is the whole design:

  * `spacr/volcano_style.py` holds the appearance as DATA -- a dataclass of
    ~60 fields, serialisable to JSON, with `render_volcano(results, style)` a
    pure function of the two. The headless pipeline and the live canvas call
    the SAME renderer, so they cannot drift.
  * The widget writes into the style object and asks for a redraw. Export
    re-renders from the same object at print size rather than screenshotting.

Nothing else in spaCR has this. Every other figure is a `savefig` at the end
of a plotting function, with its styling inline.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The immediate cost is that a figure the user cannot read is a figure they
cannot fix. The volcano's legend was 27 double-spaced entries at the axis font
size, running taller than the plot and squeezing the data into a strip. That
was a two-line change in `toxo.py` -- but from the GUI it was unfixable, and
the user's report was simply "I can't really see the results".

The larger cost is that every figure spaCR produces is a take-it-or-leave-it
render. A screen produces a dozen figures; the ones destined for a paper get
re-made by hand in Illustrator, which breaks the link between the figure and
the analysis that produced it. That is precisely how a published volcano came
to show a P = 0.05 line while its Methods claimed BH q < 0.05.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. A SHARED STYLE BASE. Generalise `volcano_style.VolcanoStyle` into
   `spacr/figure_style.py`: a base dataclass carrying what every figure has
   (axes labels and scales, log flags, limits, grid, legend on/off and
   position, fonts, line width/colour/style, figure size, dpi, background)
   and per-figure subclasses adding what only they have (a volcano's
   thresholds, a heatmap's colormap and normalisation, a jitter-bar's point
   size and jitter width). JSON round-trip and forwards-compatible loading
   come from the base, as `VolcanoStyle.from_dict` already does.

2. A RENDERER CONTRACT. Each plot type gets `render(data, style, figure=None,
   save_path=None)`. Existing plotting functions become thin callers of it,
   so the pipeline's saved figure and the interactive one are the same code.
   Do this per figure type, starting with the ones a screen actually
   produces: volcano (done), jitter-bar, plate heatmap, histogram.

3. THE CONTEXT MENU. A mixin for the Qt canvas that adds a right-click menu
   built FROM THE STYLE OBJECT'S FIELDS rather than from a hand-written list
   per figure: a bool renders a checkbox, a bounded float a spin box, a field
   with a declared choice set a submenu. Then "as many settings as possible,
   depending on the graph" is automatic -- a style gains a field, the menu
   gains an entry, and the two cannot fall out of step.

4. FIGURES MUST STAY LIVE. The menu can only exist where the GUI holds a
   matplotlib Figure. Where a screen currently shows a saved image, it must
   hold the figure instead. This is the actual prerequisite -- see
   DELIBERATELY NOT DONE on why it is not about PDF.

5. SAVE AND REUSE A STYLE. `Save style` / `Load style` as the Volcano
   Explorer already has, plus a per-project default so a lab's house style is
   applied to every figure of that type without re-setting it each time.

6. CLOSE THE PREFERENCE LEAK while in here. `spacr.plot.save_figure` honours
   the "Figure format" and "Resolution" preferences, but TWENTY-ONE
   `savefig` calls across the package bypass it (`classifier_evaluation.py`,
   `illumination.py`, `spacrops.py`, `regression_qc.py`, `sequencing.py`,
   `sim.py`, `spacr_cellpose.py` and others), several hard-coding a format.
   Those figures ignore the preference entirely. Route them through
   `save_figure` unless they have a documented reason not to.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * Right-clicking a jitter-bar, a plate heatmap and a volcano each opens a
    menu whose entries match that figure's style fields -- asserted by
    comparing the menu's actions against `dataclasses.fields(style)`, so a
    new field cannot be silently missing from the menu.
  * Toggling `legend` off and back on returns the figure to its original
    state (the style is the single source of truth; nothing is lost).
  * A style saved from one figure and loaded into another of the same type
    reproduces it exactly.
  * Export after restyling produces a file matching what is on screen,
    verified by rendering both and comparing, not by eye.
  * `grep -rn "\.savefig(" spacr/*.py | grep -v save_figure` returns only
    calls with a comment saying why they bypass the preference.
  * `pytest tests/qt/test_all_module_smoke.py -q` still passes 60/60.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Not making this depend on PDF. The request says "this will only be possible
if the graphs are PDFs and not PNGs", and that is not the constraint. Neither
format is editable once written -- a PDF is vector, so it scales and its text
stays selectable in Illustrator, but nothing in a saved PDF can be changed by
spaCR either. What makes restyling possible is the GUI holding a live
matplotlib Figure and a style object, which is point 4. Format matters for
export quality and for Illustrator, and PDF should stay the default for
publication figures -- it is simply a separate concern from interactivity.

Not a general-purpose plot editor. The menu is generated from declared style
fields, so it offers exactly what that figure type supports. An editor that
lets any property of any artist be changed produces figures the analysis
cannot reproduce, which is the problem this is meant to remove.

Not rewriting all sixty-odd plotting functions at once. Point 2 is per figure
type, in the order a screen actually produces them.

2026-08-18 -- GITHUB ISSUE #108's SECOND BUG: THE FONT SIZE. THREE CAUSES.
--------------------------------------------------------------------------------

The issue's TITLE names a FileNotFoundError (fixed in ac22ac03). Its PROSE
reports something else the reporter hit first, and that half was still live:

  "the font size in the figure previews does not work as expected. Font size
   is by default to large to be visible. Adjusting font size using the
   'Figure settings...' button from 10 to 2, does not reduce the font size,
   in fact increases it, and when returning to the 'Figure settings...'
   button menu the font size has been returned to 10."

REPRODUCED FIRST, all three symptoms, on this tree. Each had its own cause.

  1  "BY DEFAULT TOO LARGE".  `_FigureSettingsDialog` seeded its spin box
     from `get_figure_text_size() or 10` and `_apply_and_accept` wrote the
     SHOWN number back. The store's 0 means "leave every figure the sizes it
     was drawn with"; 10 is only what the box displays while that is true.
     So pressing OK once -- to change a colour, or by accident -- froze 10
     into every figure that user would ever draw. Measured: store 0 in, OK
     with nothing touched, store 10 out.

     THIS IS INSTRUCTION 152 SECTION A, IN THE SIZE KEY. The colours were
     fixed by seeding from the TOKEN; the size has no token, so it took a
     `_size_touched` flag connected AFTER `setValue` instead. A comparison
     would not have done: a store of 0 and a box showing 10 are different
     states and only one of them may be written.

  2  "10 -> 2 INCREASES IT".  `_style_figure_colors`, the pass EVERY render
     goes through, built its own list of text objects and that list missed
     an ANNOTATION, the SUPTITLE and a legend's TITLE. Measured on a
     volcano-shaped figure with the preference at 2:

         EAF1, TSG101   22.0 -> 22.0     <- the gene labels, and the LARGEST
         a run          12.0 -> 12.0        text on the plot
         everything else 10.0 -> 2.0

     Shrinking "all text" shrank everything EXCEPT the biggest thing on the
     figure, which then dominated it. That reads exactly as "it got bigger",
     and on a volcano it is the common case rather than a corner one.

     `figure_settings._every_text` had already been fixed for the DIALOG and
     the render pass kept its own copy, which is the drift itself. There is
     now ONE list, `figure_queue.figure_text_items`, Qt-free because
     `render_figure_to_png` runs on a worker thread, and `_every_text` IS
     that function. A test compares the two by identity.

     THE COLOUR RODE THE SAME LIST, so this also fixes a dark theme leaving
     a black suptitle on a black page and a black gene label on top of it.
     Exactly one artist in the package colours an annotation deliberately
     (`gate_editor.py:1165`), and it draws into its own canvas rather than
     through this pass.

  3  "RETURNED TO 10".  The dialog's "All text size" set the sizes on the
     artists and NOWHERE ELSE, so the next full render re-applied the global
     preference over the top -- and the control reads its opening value off
     the figure, so it then showed the preference back. Both halves, one
     cause.

     A size is now remembered ON THE FIGURE
     (`figure_queue.set_figure_text_size_override`) and beats the global
     default in `render_figure_to_png`. An ATTRIBUTE rather than a side
     table, because an evicted figure is PICKLED to the temp directory and
     read back, and a per-figure choice that vanished when the figure left
     RAM would be worse than none. There is a test that pickles it.

     NOT written to the preference, for the same reason the colour buttons
     on that tab are not: this dialog restyles the figure in front of the
     user, and the setting for EVERY figure is the other dialog. That one
     clears the override when it is used, so the figure being looked at
     cannot become the one figure that ignores what was just asked for.

PREVIEW OR THE FILE? BOTH, and the instruction asked because the answer
distinguishes display scaling from a preference. `render_figure_to_png`
calls `set_fontsize` on the Figure's OWN artists, so whatever it decides is
what the sibling vector page written in the same call gets, and what a later
"Save figure as..." writes. Measured on the rendered PNG, ink composited
onto white so a transparent page cannot be counted as text:

    at the figure's own sizes      36,920 dark px in 1144x972
    after asking for 2pt           17,536 dark px in 1058x906
    the kept file, save_figure_as   19,470 dark px in 1058x906

It is a preference that never reached all of the text. Nothing here is
display scaling.

TESTS  tests/qt/test_the_font_size_survives_the_next_render.py, 20 of them.
17 of the 20 fail on the previous commit; the 3 that pass are the ones about
what must NOT change. `test_reopening_the_dialog_shows_what_the_user_set`
drives the reporter's own sentence: set 2, redraw, open the dialog again.
