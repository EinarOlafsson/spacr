--------------------------------------------------------------------------------
THE POINT
--------------------------------------------------------------------------------

TRAINING SHOULD BE POSSIBLE ON AS MANY COMBINATIONS OF THE DATA AS POSSIBLE.
Today the crops have to exist on disk before a model can see them, so every
combination of objects, channels and bounding-box choice is a separate
export somebody has to remember to make. Streaming makes the combination a
setting rather than a directory.

--------------------------------------------------------------------------------
A. THE SETTINGS, RENAMED AND MERGED
--------------------------------------------------------------------------------

  * CROP SOURCE becomes IMAGE SOURCE, and becomes a dropdown of
    "load images" and "stream images". Everything in C below is gated on
    this.
  * TABLES defaults to cell, nucleus, pathogen, cytoplasm -- the four
    objects spaCR measures, which is what the default should have been.
  * FILE METADATA, PATH_STRING and FILE_TYPE merge into ONE setting,
    LOAD PATH REGEX. Three settings that between them describe one pattern
    is three chances to describe it inconsistently.
  * EXTRACT CHANNELS is removed and replaced by TRAIN CHANNELS. The channels
    that matter are the ones the model sees.
  * OBJECT ARRAY becomes a dropdown of the possible objects, GREYED OUT
    unless "stream images" is chosen.
  * COORDINATE COLUMN is DERIVED FROM OBJECT ARRAY, not asked for. It is
    always the same for a given object, so asking is asking the user to
    restate something spaCR knows -- and gives them a way to get it wrong.

--------------------------------------------------------------------------------
B. THE STREAM METHOD, AND WHAT EACH ONE NEEDS
--------------------------------------------------------------------------------

A new setting, STREAM METHOD, with two values. THE SETTINGS EACH ONE NEEDS
ARE DIFFERENT, and the ones the chosen method does not use must not be on
screen asking to be filled in:

  * "column" -- coordinates come from a column in a table.
    Needs: OBJECT ARRAY, CHANNEL ARRAYS (new).

  * "array" -- object numbers come from a mask array.
    Needs: MASK ARRAY (new), CHANNEL ARRAYS (new), BOUNDING BOX.
    BOUNDING BOX is what chooses between streaming the box around the object
    and streaming ONLY THE PIXELS THAT OVERLAP THE MASK. Both are wanted;
    they are different training sets.

--------------------------------------------------------------------------------
C. THE STREAMING ITSELF
--------------------------------------------------------------------------------

BORROW FROM `measure_crop`, do not re-derive. It already solves cropping,
channel assembly and the bounding-box/mask choice, and a second
implementation would drift from it. THE NAMING CONVENTION MUST BE THE SAME
as measure_crop's -- a streamed crop and an exported crop of the same object
should be the same filename, or nothing downstream can treat them alike.

THE TABLE COMES FIRST, AND IT IS SAVED. Streaming does not begin by walking
images. It begins by deciding WHICH objects are to be streamed and writing
that decision down:

  1. Build the table from the OBJECT NUMBER in the object table.
  2. IF THE OBJECT TABLE DOES NOT EXIST, fall back: read every .npy in the
     merged folder and record the object numbers present in the chosen mask
     array.
  3. The table carries a SELECTION ANNOTATION saying what goes to TRAINING
     and what goes to TESTING.
  4. Save it. Then, and only then, stream to generate the datasets on disk.

THE SAVED TABLE IS THE REPRODUCIBILITY. A training set that was decided at
run time and never written down cannot be re-made, compared against, or
audited when a model turns out to have learned something it should not have.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* The panel says Image source, with the two options, and the streaming
  settings are inert until "stream images" is chosen.
* Choosing a stream method shows only that method's settings.
* Coordinate column is not a setting; a test asserts it is derived from
  object array and matches what the old setting would have held.
* The three merged settings are one, and an old settings CSV naming the
  three still loads.
* A streamed crop and a `measure_crop` export of the same object have the
  SAME FILENAME -- asserted against each other, not against a fixture.
* The selection table is written before any image is, holds the
  train/test annotation, and re-running with it produces the same dataset.
* The .npy fallback is exercised by a test with NO object table present.
* Bounding box off streams only mask-overlapping pixels, and a test
  measures that the corners are background rather than trusting the flag.

--------------------------------------------------------------------------------
A AND B, DONE 2026-08-21
--------------------------------------------------------------------------------

Every rename, merge and derivation, with the old spellings accepted because
every settings CSV in existence carries one:

  * `crop_source` -> `image_source`, values `load_images` / `stream_images`.
    An unrecognised value resolves to loading rather than raising: a file
    naming a source spaCR never had should still OPEN the module.
  * `file_metadata` + `path_string` + `file_type` -> `load_path_regex`.
  * `extract_channels` -> `train_channels`, and the migration runs BEFORE
    any default lands. `train_channels` already existed with a default of
    its own, so a later `setdefault` would have silently outvoted the value
    an old file actually meant -- which is what the first attempt did.
  * `tables` defaults to the four objects spaCR measures. `None` meant "work
    it out", and what it worked out was frequently nothing.
  * `coordinate_columns` is DERIVED from `object_array` and is no longer a
    control. It comes back as a LIST because that is how it has always been
    declared -- returning the bare string made every run fail its own
    settings validation.

B. `stream_method`, and `METHOD_SETTINGS` is the single source for what each
one reads -- a list living in the GUI would drift from what the streamer
reads, and the symptom would be a control that changes nothing. An unknown
method RAISES rather than returning an empty tuple, which would grey every
setting and look like a UI bug.

--------------------------------------------------------------------------------
C: THE TABLE, DONE
--------------------------------------------------------------------------------

`spacr/stream_dataset.py`. THE TABLE IS WRITTEN BEFORE ANY IMAGE IS, and the
split is SEEDED -- a shuffle nobody can reproduce turns the saved table into
a record of one run rather than a recipe, which is the opposite of why it is
saved.

THE OBJECT TABLE FIRST, THE .npy FALLBACK SECOND, in the instruction's own
order. The fallback is not a worse answer; it is the answer for a screen
that was masked but never measured. Both refuse rather than return an empty
table: a selection with no rows would stream nothing and report success.

BACKGROUND IS NOT AN OBJECT, and each row records which file it came from.

THE NAMING IS `measure_crop`'s OWN. `crop_name` calls
`spacr.utils._generate_names`, the same function, and the test asserts the
two agree by calling both -- a second naming rule would drift, and the drift
would only show up as two folders that cannot be pooled.

THE CUTTER IS THE SHARED ONE. `cut` delegates to
`crop_source.crop_object`, which already solves the plane check, the bounds
and the mask-out; this only translates instruction 230's vocabulary into
that function's, where `bounding_box=False` is `shape='object'`. A test
asserts the delegation, because a second cutter is the thing worth
preventing rather than the thing worth writing.

--------------------------------------------------------------------------------
WHAT IS LEFT
--------------------------------------------------------------------------------

THE LOOP THAT WALKS THE SAVED TABLE AND WRITES THE DATASET. Every piece it
needs is built and tested -- the table, the naming, the cutter, the settings
that choose between them -- and what remains is the pass that reads the
merged stack per field, cuts each selected object and writes it under its
`crop_name` into the train/test folders the table annotates.

Deliberately last, and deliberately separate: it is the only part that
cannot be tested without writing a dataset to disk, and everything it
depends on can be.
