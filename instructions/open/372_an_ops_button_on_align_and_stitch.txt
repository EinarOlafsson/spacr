  * `get_preprocess_ops_settings({})` returns 63 keys.
  * `stitch_cycle_wells` runs end to end: organises the plate into per-well
    folders, computes ORB features with a disk cache, scores every candidate

  * THE GEOMETRY IS EXACT. 12 of 12 pair offsets recovered to within 0.3 px

  A WARNING FOR WHOEVER TESTS THIS NEXT, because it cost an hour: at the

WHAT IS BROKEN:

  1. FIXED. `write_mosaic` was inverted: `if settings["write_mosaic"]:
     mosaic_out = None`. Asking for a mosaic set the output path to nothing.

  2. FIXED. `mosaic` defaulted to False and is a SEPARATE key from
     `write_mosaic`, so `stitch_cycle_wells` never built one -- while its own
     docstring promises "single- or multi-channel mosaics". To get a mosaic
     before this you had to set `mosaic=True` AND leave `write_mosaic=False`,
     which is the opposite of what both names say.

  3. FIXED. `mosaic_allc` wrote ONE channel from two. `tifffile` records the
     leading axis of a plainly stacked array as `Q` -- unspecified -- so a
     genuine (2, Y, X) tile arrives as axes `QYX`.
     `_get_channel_count_tif` filtered the axes down to `TCZYX`, found no `C`,
     returned 1, and NEVER REACHED the shape-based guess below it, which gets
     (2, Y, X) right. The channel plan is `range(min(counts))`, so one
     mis-counted tile silently flattened the whole mosaic.
     The fix falls through to the shape guess only when an axis was
     unrecognised: a file that DOES declare `ZYX` still counts as one channel,
     because z-planes are not channels. Verified (2,Y,X)->2, (4,Y,X)->4,
     (Y,X)->1, declared ZYX->1.

  4. FIXED, AND IT WAS LOSING DATA. `_pairs_by_site_window` built
     `idx_by_site[s] = i`, one index per site -- but a site holds one file PER
     CHANNEL. Ordered c1_S1, c2_S1, c1_S2, c2_S2, ... the map became
     {1:1, 2:3, 3:5, 4:7}: every candidate partner was a channel-2 file, so
     two tiles of the SAME channel were never compared and the c1/c2 rows of
     the pairs CSV were one comparison written twice. It also orphaned
     `10X_c1_A1_Site-4.tif` outright -- index 6, whose only candidate was
     index 5, which fails `j > i` -- so it was in no pair, got no features and
     reached no mosaic: a corner with no channel-1 data and no warning.
     Keeping every index at a site fixes both. Pairs 12 -> 24, all 24 offsets
     still exact, manifest 7 -> 8 of 8 tiles, mosaic (1,1314,1313) ->
     (2,1061,1061) on CYX input.

  Defects 3 and 4 are exactly what PART 0 predicted of code that "nothing
  imports, no test and no user" -- and both are the silent kind. A GUI button
  shipped over them would have returned a one-channel mosaic with a hole in
  the corner and said nothing.

PART 1 -- WHAT OPS NEEDS THAT spaCR DOES NOT HAVE
--------------------------------------------------------------------------------

Optical pooled screening reads the barcode OUT OF THE IMAGES, across several
in-situ sequencing cycles. spaCR's existing barcode module does something
else entirely, and the two must not be confused:

    spacr/sequencing.py     "Decode pooled-screen FASTQ reads into per-well
                            guide counts" -- NGS. Reads gzipped FASTQ, finds
                            row/column/guide barcodes, counts guides by well.
    OPS                     no FASTQ at all. Four channels per cycle, one
                            base per cycle per spot, read off the pixels.

So Map Barcodes is NOT the back half of this and must not be pointed at it.

WHAT EXISTS (the front half):        stitching, cycle alignment, phenotype
                                     alignment, FOV cropping -- spacrops.py
WHAT DOES NOT EXIST (the back half): spot detection over the cycle stack,
                                     per-cycle base calling, assembling a
                                     barcode from one spot's bases, mapping
                                     reads to a guide library, assigning a
                                     read to a segmented cell

The back half is the work. The front half is the wiring.

PART 1-A -- THE DECODE CHAIN IS BUILT, IN `spacr/ops_sbs.py`
--------------------------------------------------------------------------------

Five of the six things PART 1 lists as "the back half" now exist, written from
brieflow's source (PART 2-A) rather than from its stage names:

    estimate_read_locations   SD across CYCLES, mean across channels
    find_peaks                local maxima, window-suppressed
    extract_bases             per-cycle per-channel intensity at each peak
    compensate_crosstalk      linear unmixing fitted from the data itself
    call_reads                argmax after unmixing, with a per-read quality
    correct_to_library        unique-closest-match only; ties are DROPPED
    assign_reads_to_cells     a cell takes the barcode its reads AGREE on

`spacr/ops_merge.py` is the other half -- matching cells across
magnifications by triangle-hashing their arrangement, since the pixels do not
correspond between a 10x and a 20x acquisition:

    triangle_descriptors      Delaunay + a scale/rotation-invariant shape
    align_by_triangles        the transform, by consensus over shape matches
    match_cells               mutual nearest neighbour, 1:1, ties DROPPED

VALIDATED AGAINST PLANTED TRUTH, which is the only way to know a decoder
works: an in-situ decoder that is wrong still finds spots, still emits
barcodes of the right length, and still matches the library by chance often
enough to look healthy. `tests/test_in_situ_barcodes_are_decoded.py` builds a
320 px field with 120 reads whose barcodes IT CHOSE, and demands them back.

The field is built to punish the three specific mistakes:

  * 15 pieces of CONSTANT-BRIGHT DEBRIS, brighter than any read, in every
    channel and every cycle. A decoder that looks for bright things finds
    these; one that looks for CHANGE does not.
  * CROSS-TALK through a mixing matrix, so the raw argmax is the wrong answer.
  * AN UNEQUAL BASE COMPOSITION -- one base at a third the rate of the others
    -- which is the case a median-based unmixing fit gets wrong and a
    percentile-based one survives.

WHAT THE CROSS-TALK STEP IS WORTH, measured on a field where a dim dye leaks
harder into its neighbour's channel than into its own (0.75 against 0.55,
which mis-calls that base EVERYWHERE and is not noise):

    with compensation     400/400 barcodes,  2400/2400 bases
    raw argmax             85/400 barcodes,  1805/2400 bases

WHAT IS NOT DONE, and should not be claimed:

  * MERGE. Triangle-hashing cell centroids across magnifications (PART 2-A)
    is not written. It is the other genuinely new surface and spaCR has
    nothing equivalent -- `align_image_to_stitch` aligns IMAGES by ORB
    features, which is a different thing for a different purpose.
  * The chain has never seen real data. Synthetic truth proves the method is
    implemented correctly; it does not prove the parameters suit a real
    plate. Peak spacing, the peak threshold and the unmixing percentile all
    want fitting against one real acquisition before anyone trusts a number
    that comes out.
  * THE BUTTON (PART 3). Nothing here is reachable from the GUI or from
    `spacr-run`, and the ~40 OPS settings still have no category, type or
    tooltip. That is the remaining work, and it is now the ONLY thing between
    this and a user.

  * Assignment is written (`assign_reads_to_cells`) but has only ever seen a
    synthetic label image. It wants Mask's real output before it is trusted.

PART 2 -- WHAT TO TAKE FROM BRIEFLOW, AND WHAT NOT TO
--------------------------------------------------------------------------------

Brieflow (Cheeseman lab, Nat Commun 2026, s41467-026-73643-7;
github.com/cheeseman-lab/brieflow) is a Snakemake pipeline with SIX named
stages, and the naming is worth stealing because it separates concerns spaCR
currently mixes:

    preprocess   ND2 to tiled TIFF, plus metadata (cycle, tile, well)
    sbs          find and decode the in-situ barcodes
    phenotype    per-cell morphology and intensity features
    merge        match phenotype features to decoded barcodes
    aggregate    collapse single cells by perturbation or barcode
    cluster      unsupervised structure across perturbations

  MAP THAT ONTO WHAT spaCR ALREADY HAS RATHER THAN ADDING SIX MODULES.
  `phenotype` is Measure. `aggregate` and `cluster` are Regression and Image
  UMAP. `preprocess` is Import plus `stitch_cycle_wells`. So the genuinely
  new surface is **sbs** and **merge**, which is the same conclusion Part 1
  reaches from the other direction -- and two agreeing derivations is the
  reason to trust it.

  DO NOT COPY THE SNAKEMAKE ARCHITECTURE. spaCR runs from a GUI button and a
  `spacr-run` name, and a workflow engine underneath one is a second way to
  describe a pipeline that has to be kept in step with the first.

  I DID NOT READ THE ALGORITHMS. The README and the readthedocs landing page
  describe the stages and not the steps inside `sbs` -- no spot detection, no
  peak calling, no base-calling detail. Read the source before implementing,
  and record here what it actually does; a plausible reconstruction of a
  method from its stage name is exactly the kind of thing that produces a
  pipeline that runs and is wrong. The paper is the other half of that
  reading.

--------------------------------------------------------------------------------
PART 2-A -- WHAT BRIEFLOW'S `sbs` AND `merge` ACTUALLY DO, FROM THE SOURCE
--------------------------------------------------------------------------------

PART 2 says: "I DID NOT READ THE ALGORITHMS ... Read the source before
implementing, and record here what it actually does; a plausible
reconstruction of a method from its stage name is exactly the kind of thing
that produces a pipeline that runs and is wrong."

Read on 2026-09-05 from a shallow clone of github.com/cheeseman-lab/brieflow.
LICENCE: MIT (Copyright 2025, Massachusetts Institute of Technology). spaCR is
BSD-3-Clause. MIT code may be incorporated with its notice retained, so the
question here is engineering, not permission -- but the attribution is not
optional and belongs in whatever file borrows.

THE `sbs` STAGE IS ELEVEN RULES, in this order (workflow/rules/sbs.smk):

   1. align_sbs                 rigid alignment, WITHIN a cycle (channel to
                                channel) and BETWEEN cycles. Both, separately:
                                `align_within_cycle` and `align_between_cycles`.
   2. log_filter                Laplacian-of-Gaussian, to sharpen spots.
   3. compute_standard_deviation  THE READ-LOCATION ESTIMATE, and it is
                                cleverer than "find bright things": standard
                                deviation ACROSS CYCLES, then mean across
                                channels. A spot that is bright in every cycle
                                is not a read; a spot whose base CHANGES from
                                cycle to cycle is. With one cycle it falls back
                                to SD across channels.
   4. find_peaks                local maxima, each labelled by its difference
                                to the next-highest neighbouring pixel -- so
                                the label is a measure of how isolated the peak
                                is, which is what the later threshold uses.
                                An alternative path uses Spotiflow, a deep
                                learning spot detector.
   5. max_filter                maximum filter in a window, so a peak's
                                intensity can be read without sub-pixel
                                registration being perfect.
   6. apply_ic_field_sbs        illumination correction.
   7. segment_sbs               cell and nucleus segmentation.
   8. extract_bases             intensity from the max-filtered stack at every
                                peak above threshold -> a long DataFrame of
                                (cycle, channel, intensity) per spot.
   9. call_reads                CHANNEL CROSS-TALK IS COMPENSATED FIRST, and
                                this is the step a naive implementation gets
                                wrong. The four dyes bleed into each other, so
                                the raw argmax is not the base. Brieflow fits a
                                linear transform from the data itself -- either
                                `transform_medians` (median of the maximum
                                points along each dimension) or
                                `transform_percentiles` (points above the 95th
                                percentile in each dimension define new axes) --
                                applies it, and THEN takes the highest
                                corrected intensity per cycle. Quality per
                                cycle comes out alongside.
  10. call_cells                assign reads to segmented cells, with error
                                correction AGAINST THE GUIDE LIBRARY: a read is
                                corrected only when there is a UNIQUE closest
                                reference barcode within `max_distance`.
                                Ambiguity is dropped, not guessed. Also handles
                                multi-barcode protocols, UMIs, count-vs-peak
                                sorting and recombination detection.
  11. eval_mapping             QC on the mapping rate.

THE `merge` STAGE MATCHES TWO MAGNIFICATIONS BY GEOMETRY, NOT BY IMAGE:

   * hash_cell_locations       Delaunay-triangulate the cell centroids and hash
                               the triangles. The shape of a local triangle of
                               cells is invariant to magnification, rotation
                               and translation, so it survives the thing that
                               defeats pixel correlation between a 10x and a
                               20x acquisition.
   * merge_triangle_hash       match the two hashed sets to get a coarse
                               rotation and translation.
   * merge_sbs_phenotype       fine alignment of one matched (tile, site).
   * match_cells               MUTUAL nearest neighbour with a distance
                               threshold, enforcing 1:1. A cell is matched only
                               when each is the other's nearest, and ambiguous
                               cells are DROPPED rather than assigned. That is
                               the right default for a screen: a wrongly
                               assigned barcode is worse than a missing one.
   * refine_local_warp         local non-rigid warp for residual within-tile
                               distortion a single affine cannot capture --
                               explicitly for the case of two differently
                               configured microscopes.

WHAT THIS CHANGES ABOUT THE PLAN.

  * spaCR's existing stitching is NOT what `merge` does, and the two must not
    be confused. `spacrops.align_image_to_stitch` aligns IMAGES by ORB
    features. `merge` aligns CELL COORDINATE SETS by triangle hashing, because
    across magnifications the pixels do not correspond but the cells do. For
    matching phenotype to genotype, brieflow's approach is the sounder one and
    spaCR does not have it.
  * Three steps carry most of the correctness risk and none of them is
    guessable: the SD-across-cycles read estimate (3), the cross-talk
    compensation (9), and unique-match-only error correction (10). Implement
    those from the source, not from the stage name.
  * Steps 6 and 7 are already spaCR: illumination correction exists, and
    segmentation is Mask. Do not build them twice.

THE HOST IS RUNNING A DIFFERENT STITCHER
----------------------------------------
PART 3 says the fold goes on Align and Stitch. Worth knowing before designing it:
`spacr/qt/screens/align.py` (815 lines) imports `from ... import align as align_mod`
at spacr/qt/screens/align.py:51 and does not import `spacr.spacrops` at all. The
Align screen's engine is `spacr/align.py` -- another 2,608 lines, with its own
`Tile`, `PairResult`, `Placement`, `AlignPlan`, `CanvasSpec`, `AlignResult`. So

a second engine behind the same host: the screen's plan-before-write contract

enables) is implemented in `spacr/align.py` and `spacrops.py` has no equivalent.

biggest design question in 372.

modules and the only stitching-related key is `align`. There is no `ops`.

NOT DONE, AND IT IS A PRODUCT DECISION RATHER THAN A LINE OF CODE:
WHAT SHOULD `mosaic` DEFAULT TO?

`stitch` and `mosaic` are set to False, which is what the read sites already
fell back to, so no run changes. ROT #1 argues they should be True -- with
`mosaic` off the alignment half has nothing to align to, so
`align_image_to_stitch` returns `{}` and the pipeline succeeds having

I TRIED TRUE AND IT IS NOT FREE.
`tests/test_cov_r4_spacrops.py::test_the_post_stitch_move_never_finds_a_tile_
already_at_its_target` goes from passing to

    RuntimeError: mosaic_all_channels_from_csv: CSV has no usable rows

So the choice is not "silence versus correctness". It is SILENCE VERSUS A
CRASH on input that cannot be mosaicked, and both are wrong answers to
different questions:

    mosaic=False   a default run finishes and produces nothing, quietly
    mosaic=True    a default run over unmosaickable input stops with a
                   RuntimeError from a function three layers down

mosaics should SAY SO rather than return `{}`, and an unmosaickable well
should be reported and skipped rather than raising. Then True is safe. That
is a change to the error handling in `spacrops.py`, it is more than a
default, and it wants the maintainer's view on what an OPS run is for --
whether a well that cannot be stitched is a failure of the run or a fact
about the plate.

--------------------------------------------------------------------------------
2026-09-04 -- THE MAINTAINER'S ANSWER, AND IT REFUSES THE QUESTION AS ASKED
--------------------------------------------------------------------------------

Asked whether a well that cannot be stitched is a failure of the run or a fact
about the plate, he answered, verbatim:

    "it can be a failure of the run or it can be an image that is genuanly
     not stitchable."

BOTH. The question above was a false binary and the answer is that the two
cases are DIFFERENT EVENTS THAT LOOK THE SAME AT THE POINT OF FAILURE, which
is exactly why the current code cannot handle either well: it has one outcome
for two situations, and whichever outcome is chosen is wrong half the time.

    mosaic=False   silence. A genuinely unstitchable plate looks identical to
                   a broken run, and both produce nothing.
    mosaic=True    a crash. A broken run and an acquisition that was never a
                   mosaic both stop the whole thing three layers down.

SO NEITHER DEFAULT IS THE FIX, and the choice recorded above -- "then True is
safe" -- is not what to build. WHAT TO BUILD IS A REASON.

THE SHAPE THAT FOLLOWS FROM THE ANSWER

Every well that does not produce a mosaic must carry WHY, and the why decides
what happens to the run:

  NOT STITCHABLE -- a fact about the plate. There is one tile, or the tiles
    do not overlap, or the acquisition was never a mosaic. Report it, skip the
    well, CONTINUE. The run is doing its job; this plate is simply not that
    kind of plate. It belongs in the run summary as a count with the wells
    named, not as an error.

  FAILED TO STITCH -- a failure of the run. The tiles are there and should
    have gone together: a tile is missing from a cycle, a file will not read,
    the feature match found too few inliers, RANSAC did not converge. Report
    it AS A FAILURE, name the well and the reason, and do not let the run
    claim success. Whether it stops or carries on to the other wells is a
    second question, and the answer is carry on and fail at the end with the
    list -- one bad well should not cost the other ninety-five.

  The distinction is not always cleanly decidable, and where it is not, SAY
  SO rather than guessing a category. "3 wells not stitchable, 1 failed, 2
  undetermined -- see the log" is a true summary; "6 wells skipped" is not.

WHAT THIS UNBLOCKS AND WHAT IT DOES NOT

It unblocks the error-handling design that PART 0's last section was waiting
on. It does NOT make that the next thing to build.

PART 0'S FIRST JOB STILL COMES FIRST: 3,891 lines that nothing imports, with
no test reaching the entry points and no user for an unknown length of time.
Changing the error handling of code whose current behaviour nobody has
measured would be building on an assumption, and this repository has a
standing lesson about exactly that. The order is:

  1. Find out what of `spacrops.py` still runs. Drive `ops_preprocess`,
     `stitch_cycle_wells` and `align_image_to_stitch` on real input and
     record what happens -- including which of the two cases above each
     failure actually is, since that classification is now the design.
  2. Then implement the reason, with `align_image_to_stitch` saying it found
     no mosaics rather than returning `{}`.
  3. Then the default, which stops being a coin-flip once a reason exists.

NOTE FOR WHOEVER TAKES STEP 1: `tests/test_cov_r4_spacrops.py::test_the_post_
stitch_move_never_finds_a_tile_already_at_its_target` is the test that turns
red under `mosaic=True` with "CSV has no usable rows". Under the design above
that input is the NOT STITCHABLE case, so the test should end up asserting a
reported skip rather than either a crash or a silent pass.
