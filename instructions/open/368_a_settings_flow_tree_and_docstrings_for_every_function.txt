MEASURED FIRST, 2026-09-02 -- these numbers decide what is possible
--------------------------------------------------------------------------------

DOCSTRING COVERAGE
    module-level functions   7036   documented 6541  (92%)
    methods                  8794   documented 5915  (67%)
    nested "sub" functions    742   documented  241  (32%)

  The maintainer's observation is confirmed and located: the gap is METHODS
  and NESTED FUNCTIONS, not module-level functions. 2879 undocumented
  methods and 501 undocumented nested functions.

SETTINGS READS
    literal-string key reads  4251   (95%)
    dynamic key reads          233   (5%)
    distinct keys read          954

  The 5% is not scattered noise. It is dominated by ONE pattern --
  f'{object_type}_intensity_merge', f'{object_type}_min_area' and siblings --
  which is the per-object family instruction 364 measured from the other
  side. Expanding `object_type` over the known object vocabulary resolves
  most of it, so effective coverage is well above 95%.

THE SETTINGS-PROPAGATING CALL GRAPH -- the part the tree actually needs
    functions receiving a settings-shaped argument   562
    settings-propagating call sites                  698
      resolved by a bare-name + import-table pass    481   (68%)
      unresolved: method / attribute / dynamic       217   (31%)

  THIS IS THE FINDING THAT MAKES THE FEATURE FEASIBLE. The tree does not
  need the whole call graph -- 156,371 call sites, of which a naive
  name-match resolves 18%. It needs only the subgraph along which settings
  travel, and that is 698 edges over 562 functions. A tractable object.

  The unresolved 31% are `self.method(settings)` and `obj.method(settings)`.
  Those are resolvable, but by class-attribute analysis, which is phase 2
  work rather than a reason to abandon the design.

--------------------------------------------------------------------------------
THE ANSWER ON SPHINX: KEEP IT
--------------------------------------------------------------------------------

Changing the API compiler would cost everything and buy nothing, because no
compiler -- Sphinx, mkdocs, pdoc, Doxygen -- does settings-flow analysis.
None of them knows what a "setting" is. The tree has to be built by a
purpose-written static analyser whatever renders the result.

Sphinx is also already carrying work that would have to be rebuilt: nine
translated API catalogs with source-hash pinning, `autoapi_python_class_content
= 'both'`, the reviewed-translation gates, and the tests that pin every
module tile to its API destination.

  SO: a new tool emits the trees as data, and Sphinx renders them. The
  analyser is the deliverable; the renderer is a detail.

--------------------------------------------------------------------------------
WHAT WILL BE BUILT
--------------------------------------------------------------------------------

PHASE 1 -- THE ANALYSER (`tools/settings_flow.py`)
  Walks the package with `ast` and emits one JSON artifact:
    * every settings key read, and by which qualified function;
    * for each function, which settings-shaped parameters it receives;
    * the propagation edges (caller -> callee, with the argument passed);
    * a confidence marker per edge: RESOLVED, AMBIGUOUS or UNRESOLVED.
  No import of spaCR at build time -- pure `ast`, so it cannot be defeated
  by an import failure and needs no GPU, no Qt and no torch.

PHASE 2 -- THE TREE, per setting
  For a key K: root at each module entry point that owns K, walk the
  propagation edges, mark nodes that READ K, and PRUNE branches that reach
  no reader. Pruning is what makes it a usable tree rather than a call-graph
  dump. Cycles get cut with a "(recurses)" marker.

PHASE 3 -- THE PAGE
  One page per setting, listing the tree with every node a link to its
  existing API page. Cross-linked from the settings reference so clicking
  `cell_channel` lands on its tree. Nodes whose edge is UNRESOLVED are shown
  AS UNRESOLVED rather than omitted -- a tree that silently drops what it
  could not resolve is worse than one that admits the gap.

PHASE 4 -- THE DOCSTRINGS
  2879 methods and 501 nested functions, worked in the order of instruction
  367: the settings-carrying ones first, then the core pipeline, then the
  rest. Nested functions are the maintainer's explicit ask and are today the
  worst covered at 32%.

  NOTE: AutoAPI does not emit nested functions at all -- they are not module
  members. Making them "visible in parent functions" therefore needs the
  parent's page to carry them, which the analyser can supply since it has
  already parsed them. This is why phase 4 comes after phase 1.

--------------------------------------------------------------------------------
WHAT THIS WILL NOT DO, STATED UP FRONT
--------------------------------------------------------------------------------

* Static analysis cannot follow a call through `getattr`, a dispatch dict, a
  Qt signal, or a callback passed as a value. Those edges will be marked
  UNRESOLVED, not guessed.
* A settings dict rebuilt or filtered mid-flow (`sub = {k: settings[k] ...}`)
  breaks the chain. The analyser should DETECT and report these rather than
  follow them wrongly.
* "Every branch below" is bounded by these limits. The tree is a strong
  guide, not a proof of reachability, and the page must say so once.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* A known key -- `cell_channel` -- produces a tree whose readers match a
  hand-audited list. Build the hand list FIRST; it is the specification.
* Every node in a rendered tree links to a page that exists.
* The analyser runs in CI and fails when an edge that used to resolve stops
  resolving, so refactors cannot silently empty the trees.
* Coverage ratchets for methods and nested functions, so the numbers above
  cannot go back up.


--------------------------------------------------------------------------------
PHASES 1 AND 2 ARE BUILT, 2026-09-02
--------------------------------------------------------------------------------

`tools/settings_flow.py`. Pure `ast`, imports no spaCR -- so a broken import
cannot empty the trees, and building the docs needs no torch, no Qt and no
GPU. A test asserts that.

    settings read           1058
    functions taking them    617
    propagation edges        776   (524 resolved, 252 unresolved)

THE DESIGN ASSUMPTION HELD. The package has ~156,000 call sites and a naive
name match resolves 18%; the settings-carrying subgraph is 776 edges, two
orders of magnitude smaller, and two thirds of it resolves. A test fails if
that ratio collapses, because a tree that is mostly holes is not usable.

`--key cell_channel` prints the worked example from this file:

    cell_channel
      spacr.core.preprocess_generate_masks_timelapse
          spacr.core.preprocess_generate_masks  <-- reads it
              spacr.io.preprocess_img_data
                  spacr.io.concatenate_and_normalize
                      spacr.io._normalize_img_batch  <-- reads it
              spacr.object.generate_cellpose_masks_sam  <-- reads it
              spacr.object.generate_organelle_masks_sam
                  spacr.object._segment_cellpose_sam  <-- reads it
              spacr.validate.run_preflight
                  spacr.validate.describe_plan
                      spacr.validate._describe_objects  <-- reads it

  PRUNED TO BRANCHES THAT REACH A READER, which is what makes it a tree
  rather than a call-graph dump. `generate_organelle_masks_sam` does not read
  the setting and is still shown, because the function BELOW it does.

  THE F-STRING EXPANSION IS WHAT MAKES IT WORK. `cell_channel` is never
  written literally in most of its readers -- it is built as
  `f'{object_type}_channel'` -- so a literal-only matcher reports it as read
  by nothing. Expanding the five object roles turns most of the dynamic 5%
  into concrete keys.

  ONE EDGE PER (caller, callee). The raw edge list records call SITES, so a
  function calling another three times produced the whole subtree three
  times. Correct as a record and useless as a tree.

  UNRESOLVED EDGES ARE KEPT AND MARKED, never dropped -- 252 of them. A tree
  that silently omits what it could not follow looks complete, and the reader
  has no way to tell which they are looking at.

PHASE 3 IS BUILT. `python tools/settings_flow.py --rst` writes
`docs/source/_generated/settings_flow.rst`: one section per setting that is
read anywhere, an anchor per section so a tooltip can land on it, and every
node a `:py:func:` link to its API page.

  A LINE BLOCK, NOT A LITERAL BLOCK, and that is the whole of the difficulty.
  `::` is the obvious way to draw a tree and renders it as preformatted text
  in which NOTHING IS CLICKABLE -- and "all branches should be clickable" is
  the request. A line block keeps one source line per output line and still
  interprets roles. RST then discards ordinary leading whitespace inside one,
  so the depth is drawn with non-breaking spaces; without them every node
  appears at the same level and the tree says nothing.

  A PRIVATE READER IS NAMED BUT NOT LINKED. AutoAPI publishes no page for an
  underscore function, so a link to one is a Sphinx warning and a broken link
  for the reader. `_normalize_img_batch` appears as plain text, which still
  says where the value is used.

  ONE PAGE, NOT 1058. A page per setting is a file per setting and a toctree
  nobody can scan. The anchors give a reader arriving from a tooltip the same
  landing while keeping the rest browsable.

tree once the Sphinx build is next run. The map those links resolve against was fixed
