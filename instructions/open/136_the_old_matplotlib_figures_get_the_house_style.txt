THE STYLE ALREADY EXISTS. ALMOST NOTHING USES IT.
--------------------------------------------------------------------------------

`spacr/figures/style.py` implements the visual system in
`.claude/skills/apicomplexan-figures`, derived by direct inspection of
Waldman et al. Cell 2020 and Giuliano et al. Nature Microbiology 2024. It has
the palette, the type scale, the frame, `figure_style()` as a CONTEXT MANAGER
(never a global rcParams write), `panel_letter`, `descriptor`,
`reference_line`, `text_legend` and `theme_target()`.

MEASURED 2026-08-18, by counting `plt.subplots(` / `plt.figure(` against uses
of `figures.style` per file:

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

THE ONE RULE THAT MATTERS MOST, from the skill, restated because every panel
has to obey it: **everything is grey except what the sentence is about.**
Grey is the default ink for data; colour is an argument. If half the marks
are coloured, the figure has no claim. A rainbow of 27 categories is the
failure this rule exists to prevent -- `spacr/localisation.py` already
records that a 27-colour volcano cost 40 ms of a 49 ms redraw AND said
nothing.

1. `with figure_style(theme_target()):` AROUND THE BUILD, never an rcParams
   write. A global write in a long-running GUI styles every later figure in
   the session, in every other module, until the process exits. Five
   functions were doing exactly that and it cost this repository a day --
   `figures/style.py` says so at the top. That failure must not be
   reintroduced at 133 new sites.

2. `theme_target()`, not a hard-coded 'print'. The published palette is near
   black on white; on spaCR's dark theme that is invisible axes on a
   transparent page.

3. EVERY SAVE GOES THROUGH `spacr.plot.save_figure`, which honours the user's
   figure-format preference. A literal '.pdf' in a savefig call is a
   complaint this project has already had twice.

4. ORDER OF WORK, by what a user actually sees:
     a. spacr/plot.py                45 figures, the shared plotting surface
     b. spacr/submodules.py          12
     c. spacr/toxo.py                 6, and they are the screen's own figures
     d. spacr/ml.py                   5
     e. spacr/timelapse.py           11
     f. the long tail

5. DO NOT CHANGE WHAT A FIGURE MEANS. This is a restyle. If a panel is wrong
   -- wrong statistic, wrong axis, a claim the data does not support -- that
   is a separate finding: FIX IT or file it, but say which you did. A
   restyle that silently changes a number is the worst outcome available
   here.

6. A FIGURE WITH FEWER THAN TEN REPLICATES PER GROUP may move its published
   numbers when the statistics engine behind it changed; that release note is
   already owed. Do not let a restyle be blamed for it -- if a number moves
   under your hands, say so.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* A count of `plt.subplots(` / `plt.figure(` against `figure_style` uses is
  no longer 133 to 4.
* No module writes rcParams globally; there is already a test asserting the
  headless import graph, and this needs its own.
* Every figure still saves in the user's chosen format, via save_figure.
* Opening a run's figures shows one visual system, not twelve.

--------------------------------------------------------------------------------
2026-08-20 -- THE COUNT HAS FLIPPED, AND BOTH CHECKS THIS FILE ASKS FOR EXIST.
--------------------------------------------------------------------------------

"A count of `plt.subplots(` / `plt.figure(` against `figure_style` uses is no
longer 133 to 4." It is 145 raw against 209 style uses -- the other way round,
and the second number more than fifty times what it was.

THE RATCHET holds the direction, for the same reason 145's does: a partial
conversion silently un-converts itself as new code is written, and a figure
drawn outside the house style does not FAIL, it just looks like a different
application. A new raw figure now has to go through `figure_style` or lower
the ceiling deliberately.

"No module writes rcParams globally; there is already a test asserting the
headless import graph, and this needs its own." IT HAS ONE, AND IT FOUND A
LEAK: `utils.setup_plot` wrote the GUI theme's colours straight into
`plt.rcParams`, which is PROCESS-WIDE -- so every figure created afterwards in
the same process inherited them, including one being SAVED FOR PAPER. That is
instruction 150's failure reached by a different route, and it had been there
the whole time.

It uses `matplotlib.rc_context` now. The figure keeps its look because
`_style_plot_axes` sets the same colours on the artists directly; what stops
is the leak.

`spacr.figure_style` is the one module allowed to write rcParams globally,
because applying the house style process-wide is what `apply()` MEANS.

AND THE TEST THAT WAS GUARDING THE LEAK. `test_setup_plot_applies_theme`
asserted `plt.rcParams["figure.facecolor"]` AFTER the call -- so it was
asserting the leak rather than the theming, and it passed for
`black_background=False` only because white is already matplotlib's default.
It asserts the figure and the axes now.

6 tests in tests/test_one_visual_system_not_twelve.py.

STILL OPEN: the 145 remaining raw call sites, 45 of them in plot.py. Each is
mechanical and the ratchet stops the number growing while they are worked
through.
