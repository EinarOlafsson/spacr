================================================================================

Status:    not started
Requested: 2026-08-08 - "Add to the installation an opt in to save and send
           logs to spacr@gmail.com for developmental purposes. You would
           have to setup an automatic mechanism that sends user logs to this
           email if the user opts in. And if the user has a GitHub, clause,
           GPT account id like for them to be able to log in during the

           auto issue feature to GitHub should also be asked about during

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Three separate features that share one screen. Build them separately.

Already exists and must be REUSED, not reinvented:
  * The GitHub auto-issue feature. `AppScreen` has "File as issue" and an
    opt-in already lives in AI Settings ("Report errors as GitHub issues").
    This task only moves the ASK to install time; the mechanism is built.
  * AI provider sign-in. The AI menu already has a provider picker and an
    install/login dialog. Same: move the ask, reuse the mechanism.
  * `spacr.qt.preferences` for anything persisted, and the run logs are
    already written per run -- `spacr.runctx.read_run_log(run_id)`, and
    `spacr/run_journal.py` writes a manifest beside them.

Nothing exists for sending logs anywhere.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Most spaCR faults are reported as a sentence and a screenshot. The run log
and the manifest answer nearly all of them and nobody has them. A user who
opted in once is a user whose next crash arrives already diagnosable.

The sign-in ask matters for a smaller reason: a user who has to find AI
Settings after their first crash usually does not.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

Read the CONSTRAINTS section below BEFORE designing the transport. It is
the part that is easy to get wrong and expensive to get wrong.

1. THE ASK. One installer page, three checkboxes, all defaulting to OFF:
   share logs / report errors as GitHub issues / sign in now. Each says
   in one sentence what it does and what leaves the machine. Every one is
   revocable later in Preferences, and the page says so -- an install-time
   choice that cannot be changed is a choice people decline.

2. LOG SHARING. Store the preference; do the sending from the APP, not the
   installer. An installer that mails something has no user to ask when it
   fails. Send on a real event -- a crash, or the user pressing "send" --
   never on a timer.

3. REDACT BEFORE SENDING, and show the user what will go. Run logs carry
   absolute paths, which carry usernames, and often the names of unpublished
   experiments. A preview with a "send" button is both the consent and the
   check.

4. ACCOUNTS. Reuse the existing provider login. Store tokens in the OS
   keyring (`keyring` is the standard; check whether it is already a
   dependency) and NEVER in QSettings, the settings CSV, or a run manifest
   -- the manifest is designed to be shared, which is exactly the problem.

5. THE ISSUE TOGGLE is the smallest of the three: it is one existing
   preference, asked earlier.

--------------------------------------------------------------------------------
CONSTRAINTS THAT DECIDE THE DESIGN
--------------------------------------------------------------------------------

DO NOT EMBED SMTP CREDENTIALS. Mailing spacr@gmail.com directly from the
client means shipping a password or an app token in the installer, where it
is readable by every user and revocable only by changing it for everyone.
It is also the kind of thing that gets an address rate-limited or closed.

Three transports that do not have that problem, in order of preference:

  a. THE GITHUB ISSUE PATH THAT ALREADY EXISTS. It is authenticated as the
     USER, it is already opt-in, and the report lands somewhere with a
     history. The log becomes an attachment or a fenced block. This is the
     cheapest correct answer and probably the right one.
  b. A COLLECTION ENDPOINT you control, posted to over HTTPS. Costs a
     service to run, but keeps the credential server-side.
  c. `mailto:` with the log attached, opened in the user's own mail client.
     No credential at all, and the user sees exactly what is sent before
     it goes -- at the price of them having to press send.

If the address in the request is a hard requirement, (c) reaches it without
shipping a secret and (b) can forward to it.

Also: whatever is chosen must fail QUIETLY and never block a run. Sending a
log is decoration in the sense of INVARIANTS 10 -- a failure to report a
crash must not become a second crash.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A fresh install shows the page with all three off. Opting in to logs and
then triggering a deliberate failure produces a preview naming the exact
file that would be sent, with paths redacted, and nothing leaves the
machine until the user presses send. Declining everything installs and runs
identically to today.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Nothing yet. Recorded here rather than in the code: the transport decision
above is the one to bring back to the maintainer before building, because
"send to this address" and "do not ship a password" pull in different
directions and only they can say which matters more.

--------------------------------------------------------------------------------
2026-08-08 - THE ACCOUNT LIST IS FOUR, AND GEMINI WAS MISSING
--------------------------------------------------------------------------------

Restated: "make sure to add the CPU/GPU ask and GIThub, claude, gemeni,
gpt, asks during installation".

So the sign-in step offers all four:

    GitHub    - also what the auto-issue feature needs (instruction 55)
    Claude    - the AI console's provider
    Gemini    - NEW; was not in the original list and is now asked for
    GPT       - the AI console's provider

Each is independent and each is skippable. An installer that cannot be
completed without signing into four services is an installer people
abandon; every one of these is a convenience, and the product has to run
with none of them.

Sign-in during INSTALL only saves a step if the credential survives to
first launch, so whatever is captured has to land where the running app
looks for it. Check that before designing the screens -- if the app reads
its keys from somewhere the installer cannot write, this is four screens
that achieve nothing.
