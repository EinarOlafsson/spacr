--------------------------------------------------------------------------------
THE THING THAT DECIDES HOW THIS IS DONE
--------------------------------------------------------------------------------

GITHUB READS COMMUNITY HEALTH FILES FROM THE DEFAULT BRANCH ONLY, AND THE
DEFAULT BRANCH IS `main`. All development happens on `nightly`, and `main`
advances only at a release. So writing these five files on `nightly` and
pushing does NOT turn a single row green; the checklist will keep reporting
42% until the files exist on `main`.

That is a decision for the maintainer and is recorded rather than assumed:

  ROUTE A -- land them on `nightly` and let the next release carry them to
    `main`. Nothing extra to approve; the rows stay red until 1.5.0.5 ships,
    which is itself gated on 288, 05, 304 and 316.

  ROUTE B -- land them on `nightly` AND put the same five files on `main` in
    their own commit. The rows go green immediately. Pushing to `main` is
    safe from an accidental release: `release.yml` triggers on a push to
    `main` ONLY when `setup.py` changes, and none of these files is
    `setup.py`. It is still a push to the release branch and wants saying
    out loud before it happens.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The checklist is the first thing a prospective user or reviewer reads about
whether a scientific tool is maintained. For a package that is cited, that is
part of the citation's credibility -- and a journal or institution auditing
the software's provenance reads exactly this page. 42% is a number that
invites the question.

It also has practical value beyond the badge. The tracker already receives
AUTO-FILED issues from inside the application, which carry a traceback
fingerprint and redacted paths. HANDOFF section 6 records the two things
those reports do that cost time: the title names the CRASH while the body
reports a DIFFERENT problem the user hit first, and paths arrive as `<PATH>`.
An issue form can ask for the missing half up front instead.
