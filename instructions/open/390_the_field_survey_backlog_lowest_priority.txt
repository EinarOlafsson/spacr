--------------------------------------------------------------------------------
PART A -- THE PROFILING VOCABULARY: mAP, PERCENT-REPLICATING, SPHERING
--------------------------------------------------------------------------------

WHAT IS MISSING. spaCR has `spacr/batch_correction.py` and can correct across
plates. What it cannot do is answer the question the image-profiling field
asks FIRST of any screen: *did this screen work at all?* That field has a
settled vocabulary for it -- mean average precision over replicate pairs,
percent-replicating, and sphering/whitening as the standard normalisation --
and spaCR reports none of it.

WHY IT MATTERS. These are not extra statistics, they are the gate. A screen
whose replicates do not retrieve each other has no hits worth calling, and
every downstream number in it is noise wearing a p-value. spaCR will happily
run regression on such a screen today. The vocabulary is also how a reviewer
or a collaborator judges a screen, so a spaCR result currently cannot be
compared to a JUMP-style one without the user computing it by hand.

WHERE IT LIVES: the pycytominer / copairs stack, which is CLI-only. There is
no GUI anywhere for it.

WHAT TO DO. A `spacr/profiling_stats.py` beside `batch_correction.py`:
replicate-retrieval mAP with its null, percent-replicating, and sphering as a
normalisation option. Surface it in the Report module (`spacr/report.py`) as
a screen-level verdict, next to the QC verdict that is already there. It
consumes the measurement table and needs no new I/O.

--------------------------------------------------------------------------------
PART B -- GATING AND EXPLORATION OVER THE FEATURE SPACE
--------------------------------------------------------------------------------

WHAT EXISTS ALREADY, and this is completion rather than construction:
`spacr/gate_library.py`, the `db_browser` module (read-only table preview,
column search, filtered CSV export), `plate_view` (per-well heatmaps and the
edge-artefact test), `umap` (image-glyph UMAP) and `annotate` (crop grids).

WHAT IS MISSING is the loop that joins them: draw a gate on a scatter or a
UMAP, see the objects inside it as crops, name the gate, save it, and use it
as a class or a filter downstream. CellProfiler Analyst 3.0 is the comparator
and is explicitly built around that loop.

WHY IT MATTERS. It is the shortest path from "the screen found something" to
"I can see what it found", and it is the step that currently leaves spaCR --
a user exports CSV and opens something else. It also feeds PART A: gating is
how a subpopulation gets defined once mAP says the screen is real.

WHAT TO DO. Selection on the existing UMAP and plate views -> a gate saved
through `gate_library.py` -> the gated objects rendered as crops through the
machinery `annotate` already has -> the gate available as a filter or a class
to `classify_merged` and `regression`. No new statistics.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

PART A: take a screen already known to be good and one already known to be
bad. Percent-replicating must separate them, and the bad one must fail
VISIBLY in the Report rather than producing a slightly worse number. The null
matters more than the statistic: an mAP with no null distribution beside it
is a number nobody can act on. Sphering is verified by the same measure
improving, not by inspection of the transformed matrix.

PART B: a gate drawn on the UMAP, saved, reopened in a new session, and used
as a class in `classify_merged` -- with the object count identical at every
step. The failure this must not have is a gate that means something different
after a reload, which is the bug that makes saved gates worse than none.
