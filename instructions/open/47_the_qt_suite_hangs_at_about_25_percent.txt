2026-08-09 - pytest-xdist INSTALLED, AND IT WORKS ON THE QT SUITE

Step 2 of WHAT TO DO, done. `pip install pytest-xdist` (3.8.0, with
execnet 2.1.2). Measured on a five-file qt subset, same machine, same load:

    serial      44 s
    -n 4        17 s        2.6x, 0 failures

THE QUESTION THIS ANSWERS is not the speed -- it is whether the fixtures
survive being distributed. This file worried that the session-scoped
`qt_theme_applied` fixture would fight xdist. It does not: xdist gives each
worker its OWN session, so a session-scoped fixture runs once per worker
rather than once, which is exactly what a per-process QApplication needs.
That is the property that makes a Qt suite parallelisable at all, and it is
why `-n` works here when it often does not for suites sharing a database.

Used `--dist load` (the default), so tests are handed out as workers free
up. If an order-dependent failure appears under `-n` that does not appear
serially, `--dist loadfile` keeps each FILE on one worker and is the first
thing to try -- that distinction matters here because instructions 03 and 46
are about order-dependent failures, and xdist changes the order.

`--timeout=300` so a single hung test names itself instead of stopping the
run at a wall clock. That run is the actual success criterion for this task
-- "one run reaches its summary line" -- and its result belongs in the next
entry here.

Note the machine is NOT idle (load ~18 from the concurrent tutorials
session), so `-n 4` rather than `-n 8`: the standing constraint is 16 cores

2026-08-10 - THE SWEEP AUDITED ITSELF, AND THAT IS WHERE THE VALUE WAS
--------------------------------------------------------------------------------

The stale/ordering sweep took its eleven suites from 48 failures to 3, but
the useful output was its SELF-AUDIT: every agent's work was checked by a
second agent that ran mutation tests against the new assertions. It found
several of its own edits had produced tests that could no longer fail.

TWO DEAD ASSERTIONS, both now repaired and both mutation-proven in each
direction:

  `assert not bar.clipped_items()` (twice in test_cov_qt_app) could NEVER
  fail. `clipped_items()` reads `_elided`, which is only ever set in
  `resizeEvent`, so a widget that was never shown reports nothing clipped
  however narrow it is. Proven by mutation: a sidebar column 52 px too narrow
  for its own text passed all six sidebar tests. One of the two was
  pre-existing -- the sweep had merely copied it into a second parametrised
  test. Both now lay the widget out first, and a WIDTH_MAX of 150 makes them
  fail as they should.

  `test_the_classes_setting_gets_the_class_editor` asserted shape with
  `all(isinstance(rule, dict) for rule in value.values())`, which is
  VACUOUSLY TRUE over an empty dict -- an editor that dropped every class
  passed. It now pins the two default class names.

AND A REAL PRODUCT BUG, found by an agent following the "if the change looks
accidental the test is right" rule rather than editing the assertion:

  A settings CSV stores `repr(value)`, so `classes` comes back as the TEXT
  `"['nc', 'pc']"`. `ClassEditorWidget.set_value` handled Mapping and list
  and nothing else, so the string matched neither arm, fell through to an
  empty table, and REPORTED SUCCESS: `apply_settings_dict` returned
  `applied=1` while `collect()['classes']` was `{}`. Because `{}` is a
  Mapping, `classify_classes.normalize_settings` then skipped its own
  legacy-translation branch, so nothing downstream recovered them.

  Every other list-shaped key survived that round trip. This was the one that
  decides WHAT GETS TRAINED, and losing it was silent. Fixed, with the
  corrupt-string case tolerated rather than raising out of an import.

THE LESSON, which is why the audit stage is worth its cost: a sweep that
updates failing assertions will, left unchecked, produce a green suite that
tests less than the red one did. Three of the weakenings here were
introduced by the very pass that fixed the failures, and none would have been
visible in a summary line. Mutation testing -- change the product, confirm
the test screams -- is the only check that catches it.

TWO MORE FINDINGS RECORDED, NOT FIXED:

  `verbose_logger.apply_console_levels()` mutates a process-global forwarder
  and has NO counterpart that restores or removes the filter. Fine for a GUI
  that launches once; it means the console gate is unrestorable by design,
  and the test fixture now has to reach into `_handler.filters` to undo it.
  A small restore/reset API would let the fixture stop touching privates.

  A flake, not reproducible on demand: constructing `AppScreen` leaves a
  QThread alive ("QThread: Destroyed while thread '' is still running"), and
  one run in ~5 segfaulted with a background PipelineWorker importing
  matplotlib concurrently with pytest-qt's GC on the main thread.

A TRAP THAT NEARLY INVALIDATED THE CONTROLS, and the reason to write this
entry at all. spaCR is installed EDITABLE, via a setuptools MetaPathFinder

the obvious control --

    cd /tmp/pristine && pytest tests/qt/...

-- runs the pristine TESTS against the CURRENT product code, silently, and

    CONTROL spacr resolved to: /tmp/pristine_gear/spacr/__init__.py

Any future "it is pre-existing" claim made from a worktree in this repo is
worthless without that check. Corroborate with a `diff` of the implicated

THE HANGING FILE IS tests/qt/test_make_masks_canvas.py -- six tests, and the
cause is one line of product code doing exactly what it should:

    make_masks.py:750   _warn()  ->  QMessageBox.warning(self, title, text)

`_warn` opens a modal only when `is_headless()` says a display is attached.
Under `xcb` a display IS attached, so the branch is correct and the box

    test_warn_falls_back_to_status_line_when_headless
      -> make_masks.py:750 _warn -> QMessageBox.warning

THE GUARD HAD A HOLE, one level down from the 2026-08-08 one. That entry
found that QMessageBox OVERRIDES `QDialog.exec`, and patched both. But the
STATIC convenience calls -- `QMessageBox.warning/question/information/
critical/about`, `QFileDialog.getExistingDirectory/getOpenFileName/...`,
`QInputDialog.getText/getInt/...`, `QColorDialog.getColor`,
`QFontDialog.getFont` -- build the dialog and run its event loop entirely
inside C++. A Python-level `exec` override is never consulted, so every one
of them sails past the guard exactly as `box.exec()` used to.

`_no_unguarded_modals` now replaces those statics as well. With the guard
extended and NOTHING else changed, the same file went from six hangs that
killed their worker to seven fast failures in 9.07 s -- which is the whole
argument for the fixture, and how all six offenders were enumerated in one
run instead of one per multi-hour run.

SEVENTEEN test files carry a private copy of that same list as a per-file
`no_modals` fixture. `test_make_masks_canvas` -- the file that actually hung
-- is not one of them. The files that remember to write the guard are not
the files that need it.
