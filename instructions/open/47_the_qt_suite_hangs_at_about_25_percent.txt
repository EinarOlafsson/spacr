2026-08-08 - THE HANG IS FIXED. NOW IT SEGFAULTS, SLIGHTLY FURTHER ON.
--------------------------------------------------------------------------------

THE HANG: found with pytest's own faulthandler, no extra package needed --
`-o faulthandler_timeout=180`, which is what I should have used instead of
SIGABRT the first time.

    test_stop_survives_a_thread_that_refuses_to_be_interrupted
      -> app_screen.py:2680 _on_stop
      -> shutdown.py:89 ask_how_to_quit

`_on_stop` asks how to quit before stopping anything, the test predates
that feature, and it opened a real QMessageBox with nobody to click it. The
`no_modals` guard had a genuine hole: it patched `QDialog.exec`, and
QMessageBox OVERRIDES exec, so an instance-level `box.exec()` went straight
past it. Both `exec` and `exec_` are patched now, and the guard immediately
caught a second test, which is the evidence the hole was real. Fixed in
commit 59a2d1a1; test_cov_app_screen.py is 149/149.

THE SEGFAULT, which is now what stops the suite finishing:

    Fatal Python error: Segmentation fault, at 28%
      File "spacr/qt/screens/app_screen.py", line 2987 in _sample_usage
      File "spacr/qt/screens/app_screen.py", line 2930 in <lambda>
      File "spacr/qt/job_runner.py", line 60 in _capture
      File "spacr/qt/job_runner.py", line 143 in <lambda>
      File "spacr/qt/bridge.py", line 1018 in run

So it dies inside the RESOURCE USAGE SAMPLER, running on a job-runner
thread. Two candidates, both worth checking before changing anything:

  * `_sample_usage` touching a QWidget from a non-GUI thread. Qt widgets
    are not thread-safe and this is the classic way to earn a segfault
    rather than an exception.
  * the GPU/NVML query. `pynvml` is already warning it is deprecated in
    this environment, and it is a C extension -- a bad call there crashes
    the process rather than raising.

Read `_sample_usage` and ask which objects it touches and which thread owns
them. INVARIANTS 4 is the neighbouring rule and the same family: the last
crash of this kind here was an object with two owners, measured at 3
crashes in 8 runs.

HOW TO KNOW IT WORKED is unchanged: the full `pytest tests/qt` run reaches
its summary line unattended. It now gets to 28%, up from wedging at 25%.

--------------------------------------------------------------------------------
2026-08-08, THIRD FIND - AND THE REASON THIS KEPT HAPPENING
--------------------------------------------------------------------------------

The suite wedged AGAIN, at 35%, past both previous points. Same cause,
third location -- pytest's faulthandler named it after five minutes:

    dnd_handlers.py:730  _open_regex_editor   ->  dlg.exec()
    dnd_handlers.py:573  _render_mask_report
    dnd_handlers.py:420  <lambda>

A QDialog modal, in a drag-and-drop path, in a test file with no modal
guard. Order-dependent: `tests/qt/test_dnd.py` alone passes in 2.58 s, so
some earlier test leaves the state that makes the regex editor open.

THE PATTERN, which is the actual finding. Three hangs, three locations,
one cause:

    25%   _on_stop       -> shutdown.ask_how_to_quit   QMessageBox
    28%   (segfault, different -- the usage sampler)
    35%   drag-and-drop  -> dnd_handlers:730           QDialog

Each was fixed by adding a guard to ONE test file, and each fix cost a
multi-hour run to discover the next. Per-file guards do not scale: the next
`.exec()` anyone writes hangs the suite again, and finding it costs another
afternoon.

SO THE GUARD IS GLOBAL NOW. An autouse fixture in `tests/qt/conftest.py`
makes `QDialog.exec`, `QMessageBox.exec` and their `exec_` spellings RAISE,
with a message naming the fix. A test that genuinely drives a dialog
patches it itself, and because monkeypatch in the test body runs after the
fixture, that patch wins.

Verified: 5 dialog-heavy suites, 0 failures -- test_cov_app_screen,
test_issue_report_url, test_gates, test_hyperparam_screen,
test_layout_drops. test_dnd.py passes in 2.58 s.

STILL UNCONFIRMED, and it is the whole point of this instruction: a full
`pytest tests/qt` run reaching its summary line. It has now been stopped
three times by three different causes and has never finished. Run it early;
