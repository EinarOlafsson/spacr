2026-08-08 - THE HANG IS FIXED. NOW IT SEGFAULTS, SLIGHTLY FURTHER ON.
--------------------------------------------------------------------------------

THE HANG: found with pytest's own faulthandler, no extra package needed --
`-o faulthandler_timeout=180`, which is what I should have used instead of
SIGABRT the first time.

    test_stop_survives_a_thread_that_refuses_to_be_interrupted
      -> app_screen.py:2680 _on_stop
      -> shutdown.py:89 ask_how_to_quit

`_on_stop` asks how to quit before stopping anything, the test predates
that feature, and it opened a real QMessageBox with nobody to click it. The
`no_modals` guard had a genuine hole: it patched `QDialog.exec`, and
QMessageBox OVERRIDES exec, so an instance-level `box.exec()` went straight
past it. Both `exec` and `exec_` are patched now, and the guard immediately
caught a second test, which is the evidence the hole was real. Fixed in
commit 59a2d1a1; test_cov_app_screen.py is 149/149.

So it dies inside the RESOURCE USAGE SAMPLER, running on a job-runner
thread. Two candidates, both worth checking before changing anything:

  * `_sample_usage` touching a QWidget from a non-GUI thread. Qt widgets

    25%   _on_stop       -> shutdown.ask_how_to_quit   QMessageBox

Each was fixed by adding a guard to ONE test file, and each fix cost a

makes `QDialog.exec`, `QMessageBox.exec` and their `exec_` spellings RAISE,
with a message naming the fix. A test that genuinely drives a dialog
patches it itself, and because monkeypatch in the test body runs after the
fixture, that patch wins.

Verified: 5 dialog-heavy suites, 0 failures -- test_cov_app_screen,
test_issue_report_url, test_gates, test_hyperparam_screen,

2026-08-08 - THE A/B, AND DELETING MY OWN FIX
--------------------------------------------------------------------------------

Five stopping points had been found and four "fixed", and the suite still
would not finish. Two of those crashes were in `_drain_job_runners`, the
fixture I wrote to fix the first one. So rather than guard it a third time,
I ran the experiment:

    WITH the fixture     segfault at 28% (dead widgets)
                         segfault at 33% (event loop pumped at teardown)
                         segfault at 35%
    WITHOUT it           66%, ZERO crashes, ZERO failures -- and it stopped
                         only because my own 5.5-hour timeout expired

So it is deleted, and the reasoning is left in `tests/qt/conftest.py` where
the next person will look.

THREE BUGS CAME OUT OF ONE FIXTURE: a 3000ms-per-runner shutdown budget
that turned "crashes at 28%" into "still going at 35% after 80 minutes";
a crash on widgets whose C++ side was already gone; and a crash on LIVE
ones, because `shutdown()` pumps the event loop, which runs pending
deleteLater calls on widgets pytest-qt was about to close itself.

THE SHAPE WAS THE PROBLEM, not the details. A teardown fixture that reaches
across every widget in the application, during Qt teardown, cannot be made
safe by guarding -- each guard I added revealed the next crash. That is the
lesson worth keeping.

WHAT SURVIVES, and should: the GLOBAL MODAL GUARD. `QDialog.exec` and
`QMessageBox.exec` raise in tests unless a test patches them itself. Three
separate hangs were modals with nobody to answer them, and per-file guards
had already failed to scale -- each new `.exec()` cost another multi-hour
run to find.

STILL UNCONFIRMED: a full run reaching its summary line. Best so far is
66%. The suite is slow enough under load that this needs a quiet machine
and a longer budget than 5.5 hours, or `-p xdist` if that can be made to
work with the Qt fixtures.

2026-08-09 - pytest-xdist INSTALLED, AND IT WORKS ON THE QT SUITE
--------------------------------------------------------------------------------

Step 2 of WHAT TO DO, done. `pip install pytest-xdist` (3.8.0, with
execnet 2.1.2). Measured on a five-file qt subset, same machine, same load:

    serial      44 s
    -n 4        17 s        2.6x, 0 failures

THE QUESTION THIS ANSWERS is not the speed -- it is whether the fixtures
survive being distributed. This file worried that the session-scoped
`qt_theme_applied` fixture would fight xdist. It does not: xdist gives each
worker its OWN session, so a session-scoped fixture runs once per worker
rather than once, which is exactly what a per-process QApplication needs.
That is the property that makes a Qt suite parallelisable at all, and it is
why `-n` works here when it often does not for suites sharing a database.

Used `--dist load` (the default), so tests are handed out as workers free
up. If an order-dependent failure appears under `-n` that does not appear
serially, `--dist loadfile` keeps each FILE on one worker and is the first
thing to try -- that distinction matters here because instructions 03 and 46
are about order-dependent failures, and xdist changes the order.

A FULL `tests/qt` RUN AT `-n 4` IS IN FLIGHT as this is written, with
`--timeout=300` so a single hung test names itself instead of stopping the
run at a wall clock. That run is the actual success criterion for this task
-- "one run reaches its summary line" -- and its result belongs in the next
entry here.

Note the machine is NOT idle (load ~18 from the concurrent tutorials
session), so `-n 4` rather than `-n 8`: the standing constraint is 16 cores
for this session, and oversubscribing would make the timing meaningless in
the same way the load-33 measurement was.
