--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

94 GIFs in `spacr/resources/setting_animations/gifs/`, described by
`manifest.json` (94 entries) and loaded through
`spacr/setting_animations.py`. `validate_setting_animation_assets()`
already exists and checks that the FILES are present and hashed -- it says
nothing about whether they show the right thing.

ONE KNOWN INACCURACY, reported by the maintainer:

    the "remove edge objects" animation removes one edge object AND one
    object that is not on the edge.

The border-object family is four files, so the fault may be in all of them:

    cell_remove_border_objects.gif
    nucleus_remove_border_objects.gif
    organelle_remove_border_objects.gif
    pathogen_remove_border_objects.gif

The stated cause is "animation misalignment during animation generation" --
i.e. the before and after frames came from runs that do not correspond, so
the difference between them is not the difference the setting makes.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

An animation is a stronger claim than a sentence. A user who reads "removes
objects touching the image border" and sees a non-border object vanish will
believe the picture, and will then either avoid a setting they needed or
distrust the ones next to it.

It is also the hardest kind of documentation error to notice: it looks
finished. Nothing fails, the asset validator passes, and the only way to
find it is for someone to watch 94 short loops and think about each one --
which is what this task is.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Find the GENERATOR. These were produced by a script, and if the cause is
   misalignment then the fix belongs there rather than in the GIFs -- a
   hand-patched asset regenerates wrong the next time.
2. Fix the border-object family first, since it is reported and specific.
   The correct animation shows exactly the objects touching the border
   disappearing, and nothing else changing between the frames.
3. Then audit all 94. For each: does the visible difference between the
   before and after frames equal the difference the setting makes, and
   nothing more? Record the verdict per animation here so a second pass
   does not start from zero.
4. Where before/after frames are generated separately, make them share a
   SEED and an input image. Misalignment of exactly this kind is what
   happens when two runs are allowed to differ in more than the one
   variable being illustrated.
5. Consider whether the validator can grow a real check. It cannot judge
   meaning, but it can assert that a before/after pair differs in only the
   region the setting is documented to affect -- which would have caught
   this one.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

The four border-object animations each show only border-touching objects
being removed. Every one of the 94 has a recorded verdict, and the ones
found wrong have been regenerated from a fixed generator rather than
edited.

2026-08-08 - CONFIRMED, MEASURED, AND THE CHECK IS REPEATABLE
--------------------------------------------------------------------------------

THE METHOD, which is the reusable part. Comparing the FIRST and LAST frames
proves nothing -- the GIFs loop, so those are identical (measured: 0 pixels
different). The "after" state is the frame MOST DIFFERENT from frame 0.
From there:

    diff  = |after - before| summed over RGB, thresholded at 30
    label = connected components of the changed mask
    a component is legitimate if it TOUCHES the image border

Results for the four border-object animations, components >= 60 px:

    cell        border: 1    interior: 3
    nucleus     border: 1    interior: 4
    organelle   border: 1    interior: 18
    pathogen    border: 1    interior: 6

Every one shows exactly ONE border-touching change -- the object being
removed, which is correct -- and interior changes as well. That corroborates
the report: something that is not on the edge changes when "remove edge
objects" is illustrated.

A CAVEAT WORTH KEEPING, because pixel diffs cannot tell an object from a
caption: some interior components are probably chrome. Across all four
files there is a component near (row 50-65, col 245-265), which is
consistent enough to look like a fixed label rather than an object. The
larger mid-image components -- cell's 5284 px at rows 148-211, cols 101-240
-- are the suspicious ones.

A rendered before | after | overlay strip was produced and sent to the
maintainer for visual confirmation, with border-touching changes in GREEN
and interior ones in RED. Regenerate it with the snippet above.

WHAT THIS CHANGES ABOUT THE TASK: step 5 of WHAT TO DO -- "consider whether
the validator can grow a real check" -- is now clearly worth doing, because
the check exists and is four lines of numpy. Asserting "no interior
component larger than N pixels changes" would have caught this at
generation time, and would catch it again for the other 90 animations.

Do that BEFORE regenerating anything, so the fix can be verified rather
than assumed.

2026-08-09 - ALL 94 AUDITED. TWO LISTS, AND ONE CORRECTION.
--------------------------------------------------------------------------------

Ran the border-object method over every animation. Results in
`anim_audit.json` (regenerate with the script quoted in the previous
section; ~2 minutes for all 94).

CORRECTION TO THE PREVIOUS ENTRY'S FRAMING. 89 of 94 animations change
something in the image INTERIOR, and for almost all of them that is
CORRECT: `cytoplasm`, `pathogen_intensity_split`, `dialate_pngs` and the
rest are settings whose whole job is to change objects away from the edge.
Interior change is only a defect where the setting's semantics say
"edge only" -- which is the four border-object files, already confirmed.
So "interior change" is not by itself a bug signal, and a validator built
on it alone would flag 89 files and be ignored.

DEFECT LIST 1 -- ANIMATIONS THAT SHOW ALMOST NOTHING. 27 of 94 change less
than 1% of the frame between before and after. At the bottom:

     0.0%   pathogen_diameter        <- changes nothing measurable at all
     0.1%   nucleus_diameter
     0.1%   organelle_diameter
     0.1%   remove_cluster_noise
     0.2%   cell_diameter
     0.2%   nucleus_min_intensity_percentile
     0.2%   organelle_fill_holes
     0.2%   plot_by_cluster
     0.2%   plot_points
     0.3%   fill_in
     0.3%   min_dist
     0.5%   cell_min_intensity_percentile

An animation whose before and after differ by a fifth of one percent is
not teaching anyone what the setting does -- and the *_diameter family
being at the bottom is suspicious as a group, since diameter should be one
of the most visible settings there is. Worth checking whether those were
generated with two values too close together to see.

DEFECT LIST 2 -- the four border-object files, confirmed in the previous
entry and unchanged: each removes exactly one border-touching object
(correct) AND changes interior objects (wrong for this setting).

SO THE VALIDATOR CHECK, revised from step 5: assert a MINIMUM visible
change -- say 1% of the frame -- which catches list 1 across all 94 and
would have caught `pathogen_diameter` at generation time. The "interior
change" assertion applies ONLY to settings documented as edge-only, and
must be opt-in per animation rather than global.

2026-08-09 - STEP 5 IS DONE: THE CHECK EXISTS
--------------------------------------------------------------------------------

`spacr/setting_animations.py` gains two functions:

    measure_visible_change(path)          -> fraction of the frame changed
    validate_animations_show_something()  -> {slug: fraction} below threshold

with `MIN_VISIBLE_CHANGE = 0.01`. It reproduces the audit exactly: 27
animations below 1%, `pathogen_diameter` at 0.01%.

THREE DECISIONS IN IT, each of which was a bug in an earlier attempt:

  The "after" frame is the one MOST DIFFERENT from the first, not the last.
  These GIFs loop, so first-vs-last is zero for every animation ever made.
  A test pins this, because it is the mistake anyone writing this check
  makes once.

  An unreadable file measures 0.0 rather than raising. The caller wants
  "this one shows nothing" in its report beside the others, not a
  traceback that hides the other 93.

  It RETURNS the failures instead of raising on the first. Raising would
  make fixing 27 animations a 27-round loop.

Deliberately SEPARATE from `validate_setting_animation_assets`, which
checks the files are intact. A GIF can have the right size and the right
digest and still show nothing -- it passes that check and fails this one,
which is the whole point.
