--------------------------------------------------------------------------------
1. FULLSCREEN IS CHOPPY AND THE BACKDROP IS NOT
--------------------------------------------------------------------------------
Same renderer, same machine, different frame rate -- so the difference is
in what changes between the two, not in the shader. Measure BEFORE
changing anything, and measure the RIGHT thing: frames actually painted,
not the timer interval. `AmbientWidget` already counts `frames_painted`
for exactly this reason.

Candidates, in the order they are cheap to rule out:

  * AREA. Fullscreen is several times the pixels of a backdrop panel at
    the same supersampling. If the cost is quadratic in the long edge,
    this is the whole answer and the fix is to scale resolution or
    supersampling with area rather than hold it constant.
  * SUPERSAMPLING. `FractalSupersampling` squares its cost. A value fine
    for a panel is four or nine times the work fullscreen.
  * WHAT ELSE IS ON SCREEN. The backdrop draws behind a settled window;
    fullscreen may be compositing over more, or without the same
    occlusion.
  * THE REFERENCE ORBIT. `fractal_mandelbrot.py` rebuilds it on the CPU
    when the camera moves far enough; if fullscreen moves the camera
    faster, it rebuilds more often, and that cost is not in the shader
    at all.

State which one it was, with numbers, before writing a fix.

--------------------------------------------------------------------------------
2. THE CAMERA MUST NOT JUMP
--------------------------------------------------------------------------------
Two separate jumps, and they need different fixes.

SPEED CHANGES MUST NOT MOVE THE CAMERA. Scrolling changes how fast the
trajectory is travelled; it must not change WHERE on the trajectory the
camera is. If speed is applied by scaling a time value that also
positions the camera, a change of speed teleports it. Keep a phase that
only ever advances, and let speed change the RATE that phase advances --
never the phase itself.

ARRIVING SOMEWHERE NEW MUST BE A MOVE, NOT A CUT. Interpolate position
and zoom, and interpolate zoom in LOG SPACE: a linear ramp through a
magnification of 1e6 spends almost all its time at one end and arrives
as a jump anyway. Ease in and out; a constant-velocity move still reads
as mechanical.

"WITHOUT PIXELING OUT FOR AS LONG AS POSSIBLE" is a real constraint and
it has a hard floor: `fractal_mandelbrot.py:31` records that the
REFERENCE ORBIT's precision sets the end of the zoom. Do not fight that
-- detect the approach and turn the camera before the detail dissolves,
so the limit is never reached in view.

--------------------------------------------------------------------------------
3. TWENTY PLACES WORTH LOOKING AT
--------------------------------------------------------------------------------
The Mandelbrot set is deterministic, so the interesting coordinates can
be found ONCE and written down rather than searched at runtime.

FIND THEM WITH A SCRIPT, KEEP THE SCRIPT. `tools/` already holds
`draw_volcano_explorer_icon.py` on the same principle: the artefact is
generated, the generator is committed, and the values are reproducible
rather than mysterious. A candidate is a point where the escape-time
gradient is high over a range of zooms -- that is what a spiral or a
filament is, numerically -- and not a point that dissolves into uniform
colour two zoom levels in.

Store them as data, with a name and the zoom range each is good at, so a
reader can tell why a coordinate is in the list. Twenty is the number
asked for; the structure should not care how many there are.

DRIFT IS OFF THE MOMENT THE USER TAKES THE CAMERA. Dragging is a
statement about where they want to be, and a tour that resumes over it is
the application arguing. Restart the tour on Ctrl+R, as asked, and say so
somewhere a user can find it.

--------------------------------------------------------------------------------
4. THE POINTER SHOULD BEND THE PICTURE, NOT TOW THE CAMERA
--------------------------------------------------------------------------------
THIS IS THE ONE THAT CHANGES A DESIGN DECISION, so it is worth being
explicit. `fractal_travel.py:87` says today's behaviour outright: "The
pointer pulls the pattern toward it, and a click shoves it away."
Moving the CAMERA is what produces the reported snap-back -- the camera
is pulled off its path, the pull cannot continue past the widget edge,
and it returns.

What is wanted instead is a LOCAL DISTORTION centred on the pointer,
with the camera left alone:

  * the feature under the pointer is what moves, not the viewport;
  * in space mode, stars near the pointer are drawn toward it, and get
    faster as they get closer -- an inverse-square falloff, which is what
    makes it read as gravity rather than as a magnet;
  * nothing snaps back, because nothing was displaced from a path.

The CPU orbit fold ALREADY DOES THIS and the user likes it: "the orbit
fold cpu effect is like a magnigying glass, which looks cool". Read that
implementation first -- it is the reference for what is wanted, and it is
the one renderer excluded from the complaint.

--------------------------------------------------------------------------------
5. ORBIT FOLD ON THE GPU
--------------------------------------------------------------------------------
Port the CPU orbit fold to the GPU list. "Orbit fold" is taken, so it
needs its own name -- the user suggested "Orbit fold 2"; something
descriptive would be better if one fits.

With the pointer behaviour from section 4: the SPIRAL under the pointer,
rather than the camera being dragged and snapping back.

--------------------------------------------------------------------------------
DONE MEANS
--------------------------------------------------------------------------------
* Fullscreen and windowed frame rates measured and reported, the cause
  named, and fullscreen no longer choppy on the machine that reported it.
* Changing speed does not move the camera -- asserted by sampling the
  camera position across a speed change, not by eye.
* Transitions are interpolated, zoom in log space, with no discontinuity
  at either end.
* The interesting coordinates are generated by a committed script, stored
  as named data, and each has a zoom range.
* User drag disables the tour; Ctrl+R restarts it; both tested.
* The pointer distorts locally and moves no camera, on every GPU pattern
  and every CPU one except the orbit fold, which already behaves.
* Orbit fold is available on the GPU under a new name.
* NO REGRESSION IN THE BACKDROP. It is described as "super smoothe"
  today, and it is on screen behind every module -- a change that makes
  fullscreen better and the backdrop worse is a bad trade. Measure both.

WATCH
-----
`fractal_travel.py` and the fractal modules are large and shared with the
backdrop that every screen draws. A frame-rate regression here is felt
everywhere, and `spacr/qt/widgets/fractal_travel.py` already carries a
heavy-import lock whose contention caused a two-second freeze once. Do
not hold it longer, and do not move work into the paint path.

2026-09-05 — THE MEASUREMENT SESSION, AND ONE THING THE AUDIT MISSED
--------------------------------------------------------------------------------

MEASURED ON THE MACHINE THAT REPORTED IT (32 logical CPUs, 19 render
threads, an RTX 3090 on a 4.6 GLX context), with
`tools/measure_the_backdrop.py`, which is committed so these numbers can
be re-run rather than believed.

1. FULLSCREEN AGAINST WINDOWED. THE CAUSE IS THE AREA, AND IT IS THE CPU
   RENDERER THAT FEELS IT.

   Pixels first. At render scale 1.0 a 2560x1440 fullscreen shades 6.83x
   a 900x600 backdrop panel, and a 4K one 15.36x. Cost is LINEAR in that,
   not quadratic in the long edge:

     the CPU orbit fold, median shader time, 19 threads, 33.3 ms budget
       backdrop panel 900x600      540,000 px    4.77 ms   210 fps
       windowed 1600x1000        1,600,000 px   14.22 ms    70 fps
       fullscreen 2560x1440      3,686,400 px   32.41 ms    31 fps
       fullscreen 3840x2160      8,294,400 px   74.63 ms    13 fps

   And the whole pipeline -- FRAMES ACTUALLY DELIVERED by the real
   widget over eight seconds, worker thread and QImage conversion and
   paint included, which is what "choppy" is about:

       backdrop panel 900x600    29.0 fps, 900x600,     5.7 ms a frame
       fullscreen 2560x1440      23.4 fps, 2560x1440,  37.4 ms a frame

   That is the report: the panel sits at its 30 fps cap and fullscreen
   cannot reach it, because one frame costs more than the budget.

   AFTER (1) RECONNECTED THE ADAPTIVE LOOP, same run, same machine:

       backdrop panel 900x600    29.2 fps, 900x600,     5.6 ms a frame
       fullscreen 2560x1440      28.1 fps, 2100x1180,  25.3 ms a frame

   Fullscreen sheds resolution and keeps the frame rate; the backdrop is
   untouched, which is the trade this file said not to get wrong. NO
   REGRESSION IN THE BACKDROP: 29.0 -> 29.2 fps is the same number twice.

   THE GPU IS NOT WHERE THE CHOPPINESS WAS, on this machine. Every GPU
   pattern, drawn into an offscreen framebuffer at fullscreen 2560x1440:
   orbit_gpu 1.29 ms, cascade 0.69 ms, space 2.44 ms, the shared orbit
   shader 0.73 ms; the Mandelbrot 2.08 ms at the surface and 5.37 ms
   twelve decades down. All of them fit a 60 fps budget several times
   over even at 4K.

   STILL OPEN, and not part of (1): the GPU path has NO adaptive
   resolution at all. `target_render_size` and the user's `scale` are
   read only by the CPU widget; the GPU canvas shades native pixels and
   adapts `_detail` instead -- and for `orbit_gpu` and `space`,
   `base_detail == detail_floor`, so that loop cannot turn anything down
   either. On this GPU there is a 12x margin at 1440p and it does not
   matter. On a weak integrated GPU fullscreen there is nothing to shed.
   The comment in `_make_gpu_widget` that says "resolution is what gives
   way instead, through the adaptive render scale" describes the CPU
   path, not this one.

2. THE SPEED CHANGE STILL TELEPORTED FOUR PATTERNS OUT OF FIVE.

   (2) built `DepthPhase` and gave it to the Mandelbrot's depth. It was
   never asked anything by the renderers: the CPU widget CONSTRUCTED a
   DepthPhase in `__init__` and then sent the worker `t = the sim clock,
   speed = the control`, and the GPU canvas fed the shaders `u_time =
   elapsed, u_speed = the control`. Every pattern but the Mandelbrot
   positions itself with `t * speed` -- the cascade's and the flight's
   depth, the orbit fold's radial phase -- so the picture still moved the
   whole elapsed time in one frame when the speed changed.

   Measured with the CPU kernels at t=57.3s, as mean absolute change per
   pixel over a frame, a scroll from speed 1 to 2 against ordinary travel:

       orbit    26.8, where one frame moves  4.97  -- ~1.0s at once
       cascade  25.2, where one frame moves  3.49  -- ~2s at once
       space     8.4, where one frame moves  0.14  -- more than 30s

   And with `variable_speed` on, which changes the speed EVERY FRAME:
   1,066 of 3,000 frames ran BACKWARDS over 100 seconds, the worst single
   step being 29 frames' worth of travel. The "how gradually" sweep was
   not a change of pace at all; it was a permanent stutter.

   FIXED by handing the renderers the phase as their clock and a speed of
   1.0: the rate is in the clock, so a speed change is continuous by
   construction and applying it twice is impossible. At speed 1 the phase
   and the wall clock are the same number, so nothing about the default
   backdrop changes. Measured after, through the real widget's own
   request stream: the frame a scroll lands on differs from the one
   before it by 7.47 levels per pixel, against 7.43 for an ordinary frame
   at the new speed -- indistinguishable, where the same scroll used to
   arrive as a second of travel.

   `state_at_seconds` was also still handed the wall clock for the drift,
   rotation and stretch while the depth used the phase, so one camera was
   moving at two rates; it takes the phase now too.

   Covered by `tests/qt/test_a_speed_change_does_not_teleport_the_camera.py`,
   which fails in three places with the fix reverted.

STILL OPEN AFTER THIS SESSION
  * The GPU path cannot shed work (above). It needs the same treatment as
    the CPU path -- shade into a smaller framebuffer and blit up -- before
    a machine with a weak GPU is asked to draw this fullscreen.
  * (3)'s `RegionTour` is built and tested and NOTHING CALLS IT. Nothing
    in `spacr/` imports it or `fractal_regions.REGIONS`, so the twenty
    places worth looking at are not on screen and the camera never floats

2026-09-10 -- (3) IS WIRED. THE CAMERA ACTUALLY TOURS THE TWENTY REGIONS NOW.
--------------------------------------------------------------------------------

The closing note above said "(3)'s `RegionTour` is built and tested and
NOTHING CALLS IT... The pieces are there; the wire is not." The wire exists.

A THIRD PATH, beside "fixed" and "guided". `path = "tour"` in the fractal
settings, offered in Preferences as **Tour the mapped regions**, next to
Straight down and Search as it goes.

ONE LEG OF THE TOUR IS ONE DIVE, and that is the whole design decision.
`tour_leg_seconds(seconds_per_decade, max_depth, travel)` sizes the dwell as
"the dive, less the move", so the camera holds one region for the entire
descent and moves to the next in the seconds around a restart. At the
shipped numbers -- 24 s a decade, 23 decades, a 9 s move -- that is 543 s on
a region, 9 s in flight, and 3.07 hours for a full circuit of the twenty.

WHY IT HAS TO BE AT THE SURFACE. Thirty decades down the view is narrower
than the gap between two regions by thirty orders of magnitude. Travelling
that gap there is a white flash, which is precisely the jump the request was
about: "it ruins the immersion when it jumps."

THE OFFSET IS RECOMPUTED, NEVER INTEGRATED. `u_center_offset` is measured
from the reference orbit, and `_refine_the_reference` MOVES that orbit onto
the boundary as the dive descends, zeroing the camera's offset when it
lands. A tour that remembered its own offset would be thrown off the region
every time that happened. `tour_offset(tour, seconds, orbit_centre)` asks
where the region is relative to wherever the reference is NOW, which is
immune to it -- and there is a test that drives the same instant of the tour
against two different references and asserts they point at one place.

DRAGGING ENDS IT, Ctrl+R HANDS IT BACK. `RegionTour` documented that
contract and nothing honoured it; the drag branch now calls `take_over()`
and the restart-token branch calls `restart()`.

THE DECIDING IS OUT OF THE CANVAS, which is this file's own rule and the
reason `SteeringCamera` exists. `tour_leg_seconds` and `tour_offset` are
module-level and have no Qt in them, so they are driven frame by frame in
tests rather than reasoned about; `_tour_centre` is only the settings read
and the clock.

Eight new tests in `tests/qt/test_the_camera_tours_the_places_worth_seeing.py`
(20 in the file now), including the two that would have caught the original
gap: that the Preferences dropdown offers the mode, and that the renderer's
steering actually branches on it.

NOT THE DEFAULT. `path` stays "fixed". Making a mode that changes what every
user sees the default is the maintainer's call, not a side effect of wiring
it up -- and it is worth asking, because "the camera will automatically
smoothely float towards" the regions reads like it was meant to be on.
ASK BEFORE THE NEXT RELEASE.

STILL OPEN, unchanged: the GPU path cannot shed work. `target_render_size`
and the user's `scale` are read only by the CPU widget.
