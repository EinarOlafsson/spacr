WHAT THE STATE IS
--------------------------------------------------------------------------------

Instruction 48's Gate Editor section turned out to be right about a "product
mismatch": five GateEditorSettings fields were saved, reloaded and read by
nothing, and the algorithm picker offered k-means while the code ran DBSCAN
regardless. Those are fixed (48, 52). The question this file answers is how
much MORE of that there is.

A five-lens sweep of the shipped package, each finding adversarially checked
by two independent skeptics told to default to "refuted" when unsure. 26
verdicts, 25 survived. Three were then confirmed by hand -- the discarded
Levene test, the sorted-vs-unsorted Cellpose filenames, and the outlier
trimming that moves p-values -- and all three were real, which is the reason
to trust the rest enough to work the list rather than re-derive it.

ONE IS ALREADY FIXED: plot.py's discarded Levene test (commit 4dbb2a37).
It is left in the list below, marked, because it is the worked example of
what the rest look like.

ONE OF THE 24 DID NOT SURVIVE, and the list below does not say so, so it is
said here. Finding 4 -- `remove_outliers` trimming the data the p-values are
computed on, plot.py:4344 -- was refuted on REACHABILITY, not on mechanism.
The mechanism is exactly as described: `create_plot` assigns
`self.df = self.remove_outliers_from_plot()` and only then runs the
normality, variance, test and post-hoc passes, all of which read `self.df`.
But `self.remove_outliers` is False in every shipped path. None of the five
in-repo constructions of `spacrGraph` pass the kwarg, the three QC callers
in ml.py hardcode False, the key is absent from the GUI categories, and
`plot_data_from_csv` does its own trimming upstream and then builds the
object without the flag. The only construction that sets it True anywhere is
a test.

So it is LATENT, not live: `spacrGraph` is public documented API, so a user
scripting the class directly hits it. Worth fixing, worth not counting as a
number anyone has been given. Treat this file as 23 live defects and one
loaded gun.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A wrong number that looks plausible is more dangerous than a control that
does nothing: the latter is noticed, while the former can be reported as a
biological result. Phantom settings also promise behavior the program does
not provide and make legacy compatibility impossible to reason about.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

Severity order, not file order. A wrong number that looks right is worse
than a control that does nothing, because the second is noticed.

For a PHANTOM SETTING the standing rule is to delete it -- but instruction
48 set the precedent that overrides it: where the setting names a feature
someone actually asked for, implement it instead. Walk was implemented for
exactly that reason. Check the instruction list before deleting.

Every fix needs a test that FAILS without it. The reason this list exists is
that all 24 passed CI.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Each surviving finding has a focused regression test that fails on the old
behavior and passes after the fix, the relevant broader test group remains
green, and settings that are removed or implemented no longer appear as
unread inert configuration.

 1. spacr/plot.py:5560
    level='plate' silently falls through to object-level pooling in plot_proportion_stacked_bars

    WHAT IS WRONG:
      `plot_proportion_stacked_bars` branches on `if level in ['well', 
      'plateID']`, but the setting it is fed only ever holds 'object', 'well' 
      or 'plate' — never the string 'plateID'. Every caller passes 
      `level=settings['level']` verbatim (spacr/submodules.py:2150, :3268, 
      :4823) and each one explicitly prepares a plate key for it first 
      (`prc_column = 'plateID' if settings['level'] == 'plate' else 'prc'`, 
      submodules.py:3259 and :4808; `'plate'` at :2138). So 'plate' misses 
      the aggregation branch entirely and drops into the `else:` branch that 
      pools every object. The prepared `prc_column` is then never read. The 
      settings tooltip (spacr/settings.py:3159) promises "'plate' does the 
      same across plates", i.e. averaged per-plate proportions with SD 
      whiskers.

    FAILS LIKE THIS:
      Run analyze_replication / analyze_invasion / analyze_endodyogeny with 
      settings['level'] = 'plate' on a 3-plate screen. The user expects a bar 
      per condition whose height is the mean of the 3 per-plate proportions 
      with an SD whisker across plates. What is drawn is `group_counts / 
      group_totals` over every parasite pooled — identical to level='object', 
      with no whiskers at all — so a condition whose effect exists on one 
      plate only and is driven by that plate's higher object count is 
      rendered as a clean condition-level proportion, and the plate-to-plate 
      spread the option exists to expose is never shown.


 2. spacr/timelapse.py:1811
    peaks_per_cell divides by a cell count that collides across fields of the same well

    WHAT IS WRONG:
      `summarize_per_well` counts cells per well as 
      `nunique('object_number')` grouped on `well_ID`, where `well_ID = rowID 
      + '_' + columnID` (line 1794) and `object_number` is the per-field 
      object label (`cell_df['object_number'] = cell_df['object_label']`, 
      timelapse.py ~1976). Object labels restart at 1 in every field, so two 
      fields of the same well that both contain objects 1..N contribute 
      nunique = N, not 2N. The denominator is therefore the number of 
      distinct object *labels* in the well, not the number of cells. The same 
      function already has a field-aware count one line above — 
      `unique_IDs_with_amplitude=('ID', 'nunique')` on the full 
      `plate_row_column_field_object` key — so the correct denominator is 
      available and is not the one used. Identical bug at line 1854 in 
      `summarize_per_well_inf_non_inf`.

    FAILS LIKE THIS:
      A calcium-oscillation run with 4 fields per well, ~60 cells per field: 
      the well truly holds ~240 cells and produces, say, 480 peaks. 
      `cells_per_well` comes back as ~60 (the label range), so the CSV 
      reports `peaks_per_cell = 480/60 = 8.0` instead of 2.0 — a 4x 
      overstatement that scales with the number of fields imaged, so a well 
      imaged at 6 fields looks more oscillatory than the same biology imaged 
      at 2.


 3. spacr/plot.py:4129
    spacrGraph reports n_object and n_well from the same aggregated frame, so one of the two is always wrong

    WHAT IS WRONG:
      In `spacrGraph.perform_statistical_tests`, both `n_object` and `n_well` 
      are counted off `self.df`. But `__init__` (plot.py:3840-3841) keeps the 
      un-aggregated frame in `self.raw_df` and replaces `self.df` with 
      `preprocess_data()`, which collapses to one row per well when 
      `representation='well'` and one per plate when 
      `representation='plate'`. So at well/plate representation `n_object` 
      counts wells (or plates), and at object representation `n_well` counts 
      objects. The two columns are numerically identical in every run. 
      `perform_posthoc_tests` on the same object does use `self.raw_df` for 
      its `n_object` (plot.py:4165-4166, 4194-4195), so the single stats CSV 
      mixes the two meanings under one column name.

    FAILS LIKE THIS:
      Build a spacrGraph with representation='well' on a plate of 12 wells 
      and 4,382 cells and save the stats. The T-test row reports n_object = 
      12 and n_well = 12; the Tukey/Dunn post-hoc rows in the same CSV report 
      n_object = 4,382 for the same comparison. A reader quoting n_object as 
      the sample size gets 12 from one row and 4,382 from the next, and the 
      object count the t-test row claims is the well count.


 4. spacr/plot.py:4344
    remove_outliers, documented as plot-only, trims the data the p-values are computed on

    WHAT IS WRONG:
      `create_plot` reassigns `self.df = self.remove_outliers_from_plot()` 
      and only then runs the normality test, Levene, the group test and the 
      post-hoc — all of which read `self.df`. The method's own docstring says 
      "Remove outliers from the plot but keep them in the data" and the class 
      docstring says "Drop 1.5*IQR outliers per group before plotting", so 
      the option presents as cosmetic. Nothing in `results_df` records that 
      trimming happened or how many rows went. The post-hoc block compounds 
      it: its `n_object` is taken from the untrimmed `self.raw_df` while the 
      Tukey/Dunn p-value beside it was computed on the trimmed `self.df`.

    FAILS LIKE THIS:
      A user re-renders the same comparison with remove_outliers=True purely 
      to tidy the figure. Every row of the saved test_results CSV changes: 
      with a right-skewed recruitment ratio, dropping the per-group 
      >Q3+1.5*IQR tail shrinks both variance and the group difference, so a 
      Mann-Whitney/T-test p of 0.03 can move either side of 0.05 with no 
      record in the output that a different sample was tested — and the 
      post-hoc rows still advertise the full, untrimmed n.


 5. spacr/plot.py:4349
    spacrGraph computes Levene's equal-variance test and discards it, then runs equal-variance t-test/ANOVA anyway

    WHAT IS WRONG:
      `create_plot` calls `perform_levene_test` and binds the result to 
      `levene_stat, levene_p`, which are never read again — the next line 
      builds `results_df` from `normality_results + test_results + 
      posthoc_results` only, and grep confirms 'levene' appears nowhere else 
      in the file outside the import, the method and this call. The 
      parametric branch is then selected on normality alone and runs 
      `ttest_ind(grouped_data[0], grouped_data[1])` (scipy default 
      `equal_var=True`, i.e. Student's, not Welch's) and `f_oneway`, neither 
      of which tolerates heteroscedasticity. The variance check the code 
      performs is the one thing that would have flagged that, and it is 
      thrown away.

    FAILS LIKE THIS:
      Compare a low-variance control group (n=30) against a high-variance 
      treated group (n=8) on a normally-distributed feature. Levene's p comes 
      back at 0.001 — the assumption is violated and n is unbalanced in the 
      anticonservative direction — but the value is dropped, Student's t-test 
      runs on the pooled variance and reports p = 0.02 where Welch's gives p 
      = 0.11. The user sees a significant result and no equal-variance row 
      anywhere in the saved stats CSV to contradict it.

    WHAT IS WRONG:

      `image_files` order in the loops below (and unreadable files are

      incidental.

      folder holding a.tif, b.tif, c.tif. spacr_cellpose.py:169 
      `random.shuffle(all_image_files)` makes image_files e.g. 
      ['c.tif','a.tif','b.tif']; `images` loads in that order, but 
      `image_names` comes back as ['a.tif','b.tif','c.tif']. At 
      spacr_cellpose.py:245 `output_filename = os.path.join(dst, 
      image_names[file_index])` writes c.tif's mask to masks/a.tif, a.tif's 
      mask to masks/b.tif and b.tif's mask to masks/c.tif. Every mask in

      spacr_cellpose.py:296, write at spacr_cellpose.py:352), which is what 
      `check_cellpose_models` calls. Switching normalize to True makes the

 7. spacr/plot.py:1467
    plot_merged indexes filter_min_max by compacted mask position, so one object type's size filter is applied to another

    WHAT IS WRONG:
      `mask_dims` is a COMPACTED list — Nones are dropped at plot.py:1726 — 
      but `filter_min_max` is documented (settings.py:3225) as "one 
      [min_area, max_area] pair in pixels per mask dimension, in the order 
      cell, nucleus, pathogen", i.e. a fixed 3-slot list. 
      `_filter_objects_in_plot` pairs them with `enumerate(mask_dims)` -> 
      `filter_min_max[i]`, so as soon as any of the three mask dims is None 
      the two sequences go out of step and each remaining mask is filtered 
      with the range belonging to an earlier object type. The sibling list 
      `mask_names` on the very next line (1727) is compacted the same way as 
      `mask_dims` and is therefore correct, which shows the pairing is 
      positional by intent — `filter_min_max` simply was never compacted with 
      it.

    FAILS LIKE THIS:
      Call plot_merged with cell_mask_dim=4, nucleus_mask_dim=None, 
      pathogen_mask_dim=6 and 
      filter_min_max=[[500,50000],[100,5000],[10,2000]] (the documented 
      cell/nucleus/pathogen order). mask_dims becomes [4, 6]. i=0 filters the 
      cell mask with [500,50000] (correct); i=1 filters the PATHOGEN mask 
      with [100,5000] — the nucleus range — so every pathogen under 100 px is 
      erased from the overlay and the pathogen's own [10,2000] range is never 
      applied at all. The user sees an overlay with real parasites missing 
      and oversized ones kept, with no warning. The same shift happens with 
      cell_mask_dim=None (cell range applied to nuclei, nucleus range applied 
      to pathogens).

 9. spacr/io.py:7472
    prepare_cellpose_dataset zips image pairs against a mis-sized augmentation list, so the "balanced" training split is not balanced

    WHAT IS WRONG:
      The augmentation loop is meant to add exactly `needed = target_size - 
      dataset_len` pairs. Instead each of the `full_loops = needed // 
      len(aug_methods)` iterations emits `min(dataset_len, len(aug_methods) * 
      (dataset_len // len(aug_methods)))` pairs, because `zip` truncates 
      `pairs` against `aug_methods * (dataset_len // len(aug_methods))`. That 
      count only equals `len(aug_methods)` when `dataset_len` is an exact 
      multiple of 5; otherwise the dataset is over-augmented, and when 
      `dataset_len < len(aug_methods)` the multiplier is 0, the list is empty 
      and zip yields nothing at all. The docstring states the function 
      "balances datasets to a common size (with augmentations if requested)".

    FAILS LIKE THIS:
      Run prepare_cellpose_dataset(input_root, augment_data=True) over three 
      dataset folders holding 12, 20 and 29 image/mask pairs. target_size = 
      29 and get_augmentations() returns 5 names. For the 12-pair folder: 
      needed=17, full_loops=3, extra=2; each loop zips 12 pairs against 
      aug_methods*(12//5=2) = 10 entries, so 10 pairs per loop -> 30, plus 2 
      from the extra branch -> the folder contributes 12+32 = 44 pairs 
      against a target of 29. A folder with 4 pairs gets aug_methods*(4//5=0) 
      == [], zip yields nothing, and it contributes 4. The resulting 
      train/test split therefore holds 44 / 29 / 4 pairs from the three 
      sources instead of 29 each, so the Cellpose model is trained with the 
      sample weighting inverted relative to what augment_data=True promised, 
      and nothing reports it.

13. spacr/plot.py:5551
    The chi-squared p-value is computed over objects while the `level` setting documents the well as the unit of replication

    WHAT IS WRONG:
      `plot_proportion_stacked_bars` builds `raw_counts` by pooling every 
      OBJECT (`groupby([group_column, bin_column]).size()`) and feeds that to 
      `chi2_contingency` and `chi_pairwise` before the `level` branch is ever 
      reached. `level` only chooses whether the bars are per-well means or 
      pooled object counts; it never touches the statistics. The published 
      contract for the setting says the opposite in so many words. The 
      resulting p-value is a pseudo-replicated test whose n is the number of 
      cells rather than the number of wells, and it is what gets written to 
      class_chi_squared_results.csv and class_frequency_test.csv.

    FAILS LIKE THIS:
      analyze_class_proportion with its default `level='well'`, 3 wells per 
      condition and ~20 000 classified cells per condition, where the class-1 
      fraction is 0.50 in nc and 0.52 in pc and the well-to-well spread is 
      +/-0.06. The bars are drawn as well means with SD whiskers (so the 
      reader sees 3 replicates), but class_chi_squared_results.csv reports 
      chi2 on 40 000 objects and p ~ 1e-8. The correct well-level test on n=3 
      vs n=3 gives p ~ 0.4. A 2-percentage-point difference is published as 
      overwhelmingly significant.

FIXED. `plot_proportion_stacked_bars` checked `level in ['well', 'plateID']`

by `prc` -- the WELL column -- so a plate-level request averaged wells and

parametrized 'plateID' alongside 'well' and passed for that reason; the

The second half is false. The chi-squared is computed at the top of the

    level='well'     chi2 = 0.5794   p = 4.4655e-01

    level='plateID'  chi2 = 0.5794   p = 4.4655e-01

Byte-identical. The statistic does not follow the level and never has.

2026-08-11 - THE INNER JOIN: THE LOSS IS NOW REPORTED. THE JOIN TYPE IS YOURS.

`_read_and_merge_data` merges every grouped object table through one closure,

five joins go through it: cytoplasm, nucleus, pathogen, png_list numeric and

THE DISCONTINUITY, measured against real synthetic databases:

    usable crops =   0  ->  merged rows = 100   (cells in db = 100)
    usable crops =   1  ->  merged rows =   1
    usable crops =  50  ->  merged rows =  50
    usable crops = 100  ->  merged rows = 100

With NO usable crop, png_list drops out before the join and every cell
survives. With exactly ONE, the merge keeps that one and deletes the other
99. Nothing printed either way, and every shipped caller passes
verbose=False. `analyze_class_proportion` force-appends 'png_list' on top of
its default tables, so it is on that path by construction.

    the two callers that append it automatically.

  * pathogen -- the case for 'inner' is real. `analyze_recruitment` on an
    infection screen genuinely wants cells that HAVE a pathogen, and an outer
    join would fill the measurement columns with NaN that later means zero.

  * nucleus / cytoplasm -- in between, and probably follows whether the
    analysis treats the compartment as required.

So the question is not "which how" but "which how PER TABLE, and does the
caller get to say". Until that is answered the report is the honest
behaviour: the numbers are unchanged and the loss is no longer silent.

2026-08-11 (late) - THE LIVE PREVIEWS: DIAGNOSED, NOT YET FIXED
--------------------------------------------------------------------------------

`AppScreen._build_runtime_panel` builds the four screen-owned previews (mask,
timelapse, motility, measure) and wires ONLY the push direction --
`set_propagate_callback`. The pull direction exists and is used elsewhere:
`_PreviewHost.prime()` calls `panel.apply_settings(model.collect())` when a
card is first shown, and `_on_hyperparam_switch` does the same for the
Hyperparameter card. But `install()` returns early for these four
(`if spec is None or spec.owned_by_screen: return None`), and the screen's
own `_on_preview_switch` does nothing but `card.setVisible(on)`.

So a user opens Mask, sets `cell_FT`, opens Live preview to CHECK THE
SEGMENTATION, and the preview runs Cellpose at its own hardcoded
`flow_threshold=0.4` and its own diameter. The preview is consulted to make a
decision, which is the worst place for it to disagree with the run.

THE FIX IS NOT A ONE-LINER, and the trap is worth writing down because it
would look fixed:

    NAME TRANSLATION. Mask declares `cell_FT`, `cell_diameter`,
    `cell_CP_prob`; `LivePreviewPanel.apply_settings` reads
    `flow_threshold`, `diameter`, `CP_prob`. A seed written without the
    rename map silently drops exactly the settings this item is about --
    while `cell_channel` and `nucleus_channel` DO land, so the preview
    visibly changes and looks seeded.

Any patch must be verified against `_build_request()`, which is what turns
the panel's state into the Cellpose call, not merely against
`apply_settings` accepting the dict.

Seed on FIRST SHOW rather than at construction, mirroring what
`_PreviewHost.prime` already documents, so a preview nobody opens stays free.
