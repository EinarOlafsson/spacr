--------------------------------------------------------------------------------
WHAT THIS UNLOCKS
--------------------------------------------------------------------------------

Two screens sharing a guide library share their independent variable. Their
measurement tables share most of their columns. So the two can be stacked and
ANY measurement regressed against the guides -- across both screens, with
twice the wells and the screen itself available as a blocking factor.

That is a different and larger thing than running the same analysis twice and
comparing the outputs by eye. It is one model over one frame.

--------------------------------------------------------------------------------
1. screenID -- AND WHY IT IS NOT plateID QUALIFICATION
--------------------------------------------------------------------------------

Both screens have plate1..plate4. Their keys collide, and merging without
fixing that computes every per-well number over two experiments at once.

SPACR ALREADY REFUSES THAT COLLISION. `spacr/multi_database.py` (instruction
109) detects a plate id present in more than one database and either refuses
the merge or QUALIFIES it -- rewriting `plate1` to `runA-plate1` using the
reversible key escape.

QUALIFICATION IS THE WRONG ANSWER HERE, and the maintainer has named the
right one. Qualifying hides the screen inside the plate id: it makes the keys
unique, which is all it was built to do, but it leaves the screen
un-analysable. You cannot block on it, you cannot test for a screen effect,
you cannot colour by it without parsing a string back apart.

`screenID` is a FIRST-CLASS METADATA COLUMN, alongside plateID / rowID /
columnID / fieldID:

  * the key stays `plate1`, unchanged, so nothing already on disk moves;
  * the identity becomes (screenID, plateID, rowID, columnID, ...);
  * and it is a DIMENSION -- available as a fixed effect, a blocking factor,
    a colour, a facet.

WHAT IT TOUCHES, and this is the expensive part of the instruction:
`spacr/schema.py` owns the key vocabulary (`PLATE_KEY`, `FIELD_KEY_COLUMNS`,
`WELL_KEY_COLUMNS`, `compose_prc`/`parse_prcf`). Adding a dimension above
plate is not a column rename -- decide DELIBERATELY whether `prc` grows a
component or whether screenID rides alongside as a separate column, and write
the decision here.

    RECOMMENDED, to be confirmed: screenID rides ALONGSIDE and the `prc`
    grammar is untouched. Every existing database, every stored key and every
    parser keeps working, and a single-screen project simply has one value.
    Growing `prc` would re-key every measurement ever written -- and
    instruction 100 has already shown what one change to that grammar costs.

A row with no screenID is a single-screen project. Default it rather than
demanding it, or every existing project stops opening.

--------------------------------------------------------------------------------
2. READING AND MERGING THE TABLES
--------------------------------------------------------------------------------

Most of this exists. `spacr/multi_database.py` already does:

    describe_merge(paths, table)   what the merge would cost, before it runs
    read_merged(paths, table, ...) one frame, with SOURCE_COLUMN provenance

WHAT IT NEEDS FOR THIS:

  * `screen=` / a screen label per source, written into `screenID` rather
    than into the plate id. That replaces `on_collision='qualify'` as the
    recommended answer -- keep qualify for callers who genuinely want it, but
    the screen-aware path should be the one the GUI offers.
  * A COLLISION THAT IS NOT A COLLISION: once screenID exists, two screens
    both having plate1 is NORMAL and must stop being reported as a clash.
    The check becomes "duplicate identity WITHIN a screen", which is still a
    real error.
  * The measurement tables are wide and differ between versions. `'common'`
    is the safe default here, and the user must be told which measurements
    were dropped -- that set IS the analysis they are about to run.

--------------------------------------------------------------------------------
3. THE MEASUREMENT SEARCH -- AND THE TRAP IN IT
--------------------------------------------------------------------------------

"instead of a paramiter search a serch for which measurement has genes with
clear effect sizes".

So: hold the model fixed, sweep the DEPENDENT VARIABLE, and report which
measurements show gene effects. Structurally it reuses the parameter sweep --
the same runs tab (instruction 116), the same containment and memory
discipline (114), the same results surface (119). What changes is what varies.

THE TRAP, and it is the whole statistical content of this instruction:

    A MEASUREMENT SCAN IS A MULTIPLE-TESTING PROBLEM ACROSS MEASUREMENTS.

spaCR measures hundreds of features per object. Scan 500 of them for "genes
with a clear effect" and some will look clear by chance alone -- and they
will look exactly as convincing as the real ones, because the per-measurement
FDR was computed WITHIN each measurement and knows nothing about the other
499.

So the search must correct ACROSS THE SCAN, not only within each run, and the
report must show both numbers. A measurement that survives within-run FDR and
fails across-scan correction is the single most important thing this feature
can tell a user, and the easiest for it to hide.

Related and not the same: the measurements are heavily CORRELATED (area,
perimeter, and equivalent-diameter are one thing measured three ways). So the
effective number of independent tests is far below the column count, and a
naive Bonferroni across 500 correlated columns is too harsh in the other
direction. Say which correction is used and why; report the effective number
of tests if it can be estimated.

RANK BY EFFECT SIZE, NOT BY P-VALUE. The maintainer asked for "clear effect
sizes", and with two screens' worth of wells a trivial effect will be
significant. The result table's primary sort is the effect.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Two screens, each with plate1..plate4, load into one frame with no
  collision reported and screenID distinguishing them.
* A per-screen row count after the merge equals the count before it, for each
  screen -- the anti-pooling test instruction 109 already uses.
* screenID is available as a blocking factor / fixed effect in the
  regression, not merely as a label.
* A single-screen project opens and runs exactly as before, with no screenID
  anywhere in its settings.
* The measurement search returns a table ranked by EFFECT SIZE, carrying both
  the within-run FDR and the across-scan correction, and says how many
  measurements were scanned.
* A scan over pure noise returns nothing that survives the across-scan
  correction -- the test that proves the correction is real. Build it with a
  permuted guide assignment, so the data are real and only the labels are
  wrong.

1. THE DECISION: CONFIRMED. screenID rides ALONGSIDE; prc is untouched.
--------------------------------------------------------------------------------

The RECOMMENDED answer above holds, and there is a third reason for it that is
stronger than the two the instruction gives.

  (a) `prcf` is a STORED COLUMN, not a derived one. It is in
      `schema.OBJECT_TABLE_REQUIRED_COLUMNS`, so every object row spaCR has
      ever written carries it, and `validate_object_table_frame` asserts it
      matches the component key columns exactly ("prcf must exactly match the
      component key columns", schema.py). Growing the grammar re-keys every
      measurement on disk AND breaks the writer's own validator.

  (b) IT COULD NOT BE PARSED BACK. This is the decisive one, and it is not in
      the instruction. `schema.parse_prcf` and `ml._split_prc` both parse RIGHT
      TO LEFT precisely because the LEFTMOST component is the one allowed to
      contain the separator -- extra leading components are absorbed INTO THE
      PLATE, deliberately, so that a plate named `exp1_plate1` works. A screen
      component in front of the plate is therefore textually identical to a
      plate named `screenA_plate1`:

          screenA_plate1_r1_c1_f1     screen 'screenA', plate 'plate1'
          screenA_plate1_r1_c1_f1     plate 'screenA_plate1'

      The guard that tells a genuine underscored plate from a key one level
      too deep (`is_row_column_pair`) inspects the TRAILING pair, so it cannot
      help here: both readings have the same trailing pair. There is no rule
      that separates them, so growing `prc` would not merely be expensive, it
      would be ambiguous.

  (c) A qualified plate id is not a dimension. Unchanged from the instruction.

WHAT WAS ADDED TO schema.py (additive only; no existing constant changed):

    SCREEN_KEY = 'screenID'
    DEFAULT_SCREEN = 'screen1'
    SCREENED_WELL_KEY_COLUMNS  = ('screenID','plateID','rowID','columnID')
    SCREENED_FIELD_KEY_COLUMNS = (+ 'fieldID')
    screen_id(value)          -> defaults absence, never raises on it
    add_screen_column(frame, screen=None, overwrite=False)
    'screen' / 'screen_id' / 'screen_name' / any case of 'screenID' now
        canonicalise to screenID

FIELD_KEY_COLUMNS and WELL_KEY_COLUMNS are UNCHANGED -- the screened forms are
separate tuples. 42 call sites join, group and resume-delete on the narrow
ones, and silently widening them would change what every one of them means.

A row with no screenID is a single-screen project and is DEFAULTED, not
demanded. Pinned by
`test_a_single_screen_project_opens_with_no_screen_id_anywhere`: no screens=
argument, no screenID column in the database, merge works, and the column
comes out present with exactly one value so downstream code never branches.

3. THE MEASUREMENT SCAN -- spacr/measurement_scan.py (NEW)
--------------------------------------------------------------------------------

Pure logic, no GUI. No spacr.ml import; no pandas, scipy or torch at module
scope. 230 statements, 100% line coverage.

    scan_measurements(frame, *, measurements=None, gene_column='gene',
                      block_columns=(schema.SCREEN_KEY,), control_genes=(),
                      within_run_method='fdr_bh',
                      across_scan_method='fdr_bh', alpha=0.05) -> ScanResult

One OLS per measurement over one shared design (intercept + block dummies +
gene dummies), fitted as a single factorisation per missing-data pattern
rather than one statsmodels call per column.

THE TRAP, handled: every row carries BOTH numbers. `within_run_q` is what a
single-measurement analysis would have reported across that measurement's own
genes; `across_scan_q` corrects across the scan. The across-scan stage is fed
Simes' global-null P per measurement -- the minimum BH-adjusted P over its
genes -- because the raw minimum of 23 gene tests is not a P value and would
smuggle the within-measurement multiplicity past the second correction.

WHICH CORRECTION AND WHY: Benjamini-Hochberg across measurements. Measurement
columns are positively dependent, which is the condition BH is valid under and
is not made absurd by; Bonferroni over 500 correlated columns is too harsh in
the other direction. The Li & Ji (2005) effective number of tests is reported
beside the column count (ScanResult.effective_n_tests) and is available as the
divisor via across_scan_method='bonferroni_effective'. Every correction comes
from spacr.multiple_testing -- there is no second implementation, pinned by
test_there_is_not_a_second_correction_implementation.

RANKED BY EFFECT SIZE, as asked. effect_size is the gene's coefficient in
units of the RESIDUAL standard deviation (a Cohen's d). Residual and not
total, because a blocking factor's whole job is to remove a nuisance source of
spread and dividing by the total would make blocking on screenID look
pointless -- which is exactly the property
test_the_screen_is_blocked_on_by_default checks.

THE PROOF TEST, built with a permuted guide assignment as demanded:
test_a_scan_over_permuted_guides_finds_nothing. Paired with
test_a_planted_effect_survives_both_corrections so it cannot pass by returning
nothing ever.

MEASURED, over 200 independent permuted scans of 40 pure-noise measurements:

    across-scan correction fires on   5.0%  of scans   (the alpha promised)
    within-run correction fires on   83.5%  of the SAME scans

So a scan reporting only the within-run number would have shown the user a
convincing measurement in five runs out of six over data with no signal in it
at all. That gap is the feature. A 60-trial version is pinned as
test_over_many_permutations_the_across_scan_rate_is_the_one_promised (marked
slow).

BUGS FOUND AND FIXED WHILE BUILDING THIS
--------------------------------------------------------------------------------

  1. describe_merge reported two spellings of one column (`row` / `rowID`) as
     two partial columns, i.e. as a measurement about to be dropped, while
     read_merged correctly canonicalised them into one. The plan and the read
     disagreed about what the merge would cost. Fixed: the plan now computes
     its column sets through the same canonical_rename_plan the read applies.

  2. (in new code, caught by the coverage tests) A measurement that the design
     explains exactly -- a per-well aggregate that turns out to BE the guide
     assignment -- left a floating-point residual of ~1e-15 and produced an
     effect size of 4.5e8 that sat at the top of the table permanently. Now
     judged relative to the response's own spread and reported as
     'no estimable gene effect' in ScanResult.skipped.

  3. (in new code) effective_number_of_tests dropped a column if any OTHER
     column's correlations were undefined, because it tested whole rows of the
     correlation matrix instead of the diagonal. One constant column therefore
     discarded the entire family. Now a column is judged on its own diagonal.
