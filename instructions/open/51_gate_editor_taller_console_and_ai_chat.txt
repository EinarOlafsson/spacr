--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A console showing three lines is a console the user has to scroll to read
a traceback in, which is exactly when they least want to. Same for a chat
reply longer than its box.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Find who sets the heights -- a splitter size, a minimumHeight, or a
   stretch factor.
2. Give both more room. If it is a splitter, this is an initial-sizes
   change and the user can still drag it; that is the better fix than a
   larger fixed minimum, which takes the choice away.
3. Beware the neighbouring failure mode just fixed in instruction 46: a
   minimum height that cannot be shrunk starves whatever shares the axis
   with it. Prefer stretch and initial sizes over hard minimums.

--------------------------------------------------------------------------------

appreciably more lines than now without the graph losing usable area, and
both panes can still be dragged.

2026-08-08 - FOUND BOTH. THEY ARE NOT THE SAME KIND OF PROBLEM.
--------------------------------------------------------------------------------

`spacr/qt/widgets/gate_console.py` -- "A console and a chat box beside the
gating surface" -- holds both:

    self.log    QTextEdit,  added with stretch 1   <- the console transcript
    self.input  QLineEdit                          <- the command entry
    self.chat   QLineEdit                          <- the AI chat box

THE CHAT BOX IS A QLineEdit. A single-line control. It cannot be made
"taller" by resizing -- it is one line by construction, and giving it a
larger fixed height just puts one line of text in a tall box. Making it
taller means making it MULTI-LINE (QTextEdit / QPlainTextEdit), which is a
behaviour change and brings a question with it: what does Enter do?
Today Enter sends. In a multi-line box, Enter usually inserts a newline and
Ctrl+Enter (or Shift+Enter) sends -- and changing that on someone who has
built the habit of pressing Enter is worse than a short box.

THE CONSOLE is different: `self.log` already has stretch 1, so it grows
with its panel. If it looks short, the constraint is the PANEL, not the
widget. And the panel is in a HORIZONTAL splitter in
`spacr/qt/screens/gate_editor.py`:

    body = QSplitter(Qt.Horizontal, self)
    body.addWidget(self.console)
    body.setSizes([700, 260, 0])          <- console starts at width 0

So the console is collapsed by DEFAULT, with the comment "it is a thing you
reach for, not a thing you look past". Since the splitter is horizontal,
that 0 is a WIDTH, and the console already has the full height available.

THE QUESTION TO ASK, and the reason this was not just changed: "taller"
does not fit either widget as found. Either
  (a) the chat box should become multi-line -- then decide the Enter key;
  (b) the console panel should not start collapsed, and "taller" meant
      "give it room without me dragging for it"; or
  (c) this is about a different console -- the AppScreen one that every
      module has, rather than the gate editor's own.
Ask before changing, rather than pick one and ship a UI the maintainer did
not describe. The measurement above is what makes the question answerable
in one sentence.

--------------------------------------------------------------------------------
2026-08-08 - DONE. THE QUESTION ABOVE WAS DECIDED RATHER THAN ASKED.
--------------------------------------------------------------------------------

THE CHAT BOX is now multi-line. It was a QLineEdit, which cannot be made
taller -- one line is what a QLineEdit is -- so "taller" necessarily meant
changing the widget. It is a `_ChatInput`, a QPlainTextEdit three lines
tall, and it went from one line to 63px.

ENTER STILL SENDS. That was the open question and it is decided: the habit
is already built, and taking Enter away to gain a newline is a bad trade.
The newline is on Shift+Enter, where a chat box usually keeps it, and the
placeholder says so -- "ask in words - Shift+Enter for a new line" --
because an invisible keybinding is one nobody uses.

THE HEIGHT IS IN LINES, NOT PIXELS. `CHAT_VISIBLE_LINES = 3`, multiplied by
the font metrics at construction. A pixel height picked at one zoom level
is the wrong height at every other one, and this project's default font
scale is 1.5 while its tests pin 1.0 (INVARIANTS 9), so a literal would
have been wrong somewhere immediately.

THE TRANSCRIPT gets `CONSOLE_MIN_HEIGHT = 180` -- about ten lines, enough
to read a traceback without scrolling, which is the moment scrolling is
least welcome. It already stretched, but nothing stopped the entry rows
below squeezing it.

NOT CHANGED, deliberately: the console panel still starts collapsed in the
body splitter. That collapse is documented as a decision -- "it is a thing
you reach for, not a thing you look past" -- and it is a WIDTH in a
horizontal splitter, so it was never what "taller" referred to. The
expression input is also still a QLineEdit, because an expression is one
line.

11 tests. 66 pass across the console and gates suites.
