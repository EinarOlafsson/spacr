================================================================================

Status:    the end state is FIXED and PDFs are reachable (2026-08-09).
           The reopen was right; my design was the bug. The Gate Editor inherits the

Requested: 2026-08-07 - "when evaluating hyperparameters, show each graph as soon as it is generated on a grid defined by the width and height of the container, which is dynamic. whether to show each as a png (which takes less compute) or as a pdf (editable but takes more compute) is defined by the spacr preference figure format and PNG resolution." Also, for the Gate Editor: "the figures should map onto a grid where each figure is a pdf or png defined by the general settings in preferences, and the grid should map onto the hyperparameter search space."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not started. The pieces exist: FigureQueue already adopts a pre-rendered PNG
from the worker thread, render_figure_to_png already honours
get_figure_png_dpi() and get_figure_format(), and figures already stream
from the bridge as they are produced.

What does not exist is a GRID view -- FigureQueue is a one-at-a-time gallery.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A search that shows nothing until it finishes is a search the user cannot
steer. Seeing the first few settings land is what tells them the range is
wrong before the other fifty run.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. A grid view that appends a figure as each arrives, reflowing to the
   container's width and height. Shared by Image UMAP and the Gate Editor --
   write it once.
2. Format and resolution come from the EXISTING preferences
   (get_figure_format, get_figure_png_dpi). Do not add a second setting.
3. The grid's axes should map onto the search space (instruction 34), so a
   cell's position says which parameter values produced it.
4. Rendering stays on the worker thread (bridge already does this). A grid
   of fifty PDFs rendered on the GUI thread would freeze it, which is the
   one thing the GUI must never do.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Start a search: figures appear one by one, the grid reflows when the panel
is resized, and switching the preference between png and pdf changes what
is produced without touching the module.

2026-08-08 - WIRED. FIGURES ARRIVE DURING THE SEARCH NOW.
--------------------------------------------------------------------------------

The rendering happens on the WORKER, which was the whole design constraint
and the reason this sat unwired.

`_SearchWorker.run` passes `run_search_for_app` a bound method rather than
a lambda now. That method draws the trial's embedding, writes a PNG, and
only THEN emits -- so every matplotlib call is on the search thread and the
GUI thread does nothing but load a finished image. The `on_trial` callback
was always invoked from inside the fit loop, so this needed no new thread.

    trial_ready = Signal(object, int, int, str)     # + the png path

`render_trial_figure` is module-level and touches no Qt, which is what
makes it safe to call from there. It returns False rather than raising when
a trial has no embedding -- a classifier sweep has none, and a failed UMAP
trial has none either, and neither is an error.

THE PANE HOLDS BOTH VIEWS, stacked. The grid fills a cell at a time while
the search runs; `build_panel_figure`'s summary replaces it at the end.
Live steering and the deliverable are different jobs and neither replaces
the other. The grid KEEPS its figures when the summary takes over -- the
user was watching those.

`set_parameters(space.params)` is called when the search STARTS, before the
first figure lands, so the grid does not rearrange itself as results
arrive.

A figure that fails to render or place is swallowed with a debug log. A
search is hours of real work and a plot is decoration; losing the second
must never lose the first (INVARIANTS 10).

10 new tests; 103 pass across the hyperparameter screen, the axes dialog
and the grid.

STILL OPEN, and it is instruction 49's: the Gate Editor's clustering Walk
uses the same `HyperparamPanel`, so it inherits this the moment 49 wires

2026-08-09 - THE REOPEN WAS RIGHT, AND I HAD BUILT THE COMPLAINT
--------------------------------------------------------------------------------

Traced the real path rather than the tests. The worker was innocent: a real
`_SearchWorker` run emitted 4 trials, all 4 with a rendered PNG path and an
embedding. `keep_embeddings` defaults True and `run_search_for_app` never
overrides it, so the hypothesis at the top of this section was wrong.

THE BUG WAS THE END STATE, and it was mine.
`_show_summary_instead_of_grid` HID the grid and showed the single summary
figure when the search finished. So the per-trial figures did stream during
the run, and were then replaced -- and the end state is the only state a
user who steps away ever sees. That is precisely "not all at the end in one
large grid and as a large PNG": I had implemented the thing being
complained about, at the last moment of the run.

Both are shown now. The grid stays because it is what the user asked to
look at; the summary keeps its place below because it carries the ranking
and the noise band that individual panels cannot.

A test asserted the old behaviour -- `test_the_grid_hides_when_the_summary_
takes_over` -- so it was PINNING the bug. Inverted, with the reason
recorded in it.

THE PDF HALF. `render_figure_to_png` already writes a sibling `.pdf` per
trial when the preference is PDF; measured, PDF mode produces trial.pdf and
trial.png. What was missing is that nothing surfaced it: the figures live
in a temp directory, the grid necessarily DISPLAYS the PNG (a PDF cannot be
painted into a label), and there was no way to reach the vector file.

`SearchFigureGrid.figure_path(index)` now hands back the PDF when one
exists, and clicking a cell opens it. Measured: preference png -> trial.png,
preference pdf -> trial.pdf.

98 pass across the grid, streaming and screen suites.

STILL OPEN: the per-trial figures are written to a TEMPORARY directory, so
they vanish with the process. Clicking opens them while the app runs, and
nothing saves them with the run. If the figures are meant to be kept they
should go to the run folder -- that is a decision about where a search's
output belongs, not a bug, and it is what remains here.
