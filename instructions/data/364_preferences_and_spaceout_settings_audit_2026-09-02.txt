spaCR Preferences (`PreferencesDialog`)          111 setting rows
             behind them, in spacr/qt/preferences.py   70 QSettings keys
             + the Figures tab's graph-style panel     23 general rows
             + its per-graph pages                     37 rows, 27 keys
spaceout Preferences (the Fractal tab)            12 rows
             behind them                               29 `spaceout/*` keys

The dialog builds 128 labelled rows with the Fractal tab forced on (counted
by walking the finished dialog, the way
`tests/qt/test_every_preference_says_what_it_is.py` does): 12 Fractal, 5
action buttons that are not settings (Memory, GPU memory, Threads, Disk,
Application), and 111 settings. Five of those 111 -- the log levels -- carry
two switches each, so the surface asks 116 questions on 111 rows.

The same three questions the five previous audits asked, in the same order,
against the same standard of evidence: every claim below is either a
quotation from the setting's own tooltip or a line of code that reads it, or
does not.

THESE TWO SURFACES ARE NOT LIKE THE SIX MODULES. A module setting is a key in
a dict that a pipeline function reads. A preference is a QSettings key with a
typed getter, and the getter is the only way in -- so "is it read" is a
question about FUNCTION CALLERS, not about `settings['<key>']`. The scan used
here is: for every `def get_*` and `def set_*` in `spacr/qt/preferences.py`,
count references outside that file and inside it, then read every call site.
It found what the module scans could not: eight public functions with no
caller anywhere in `spacr/`, and a whole vocabulary of 37 figure settings
that is stored, shown, translated, and cannot reach a figure.

AND THE GOOD NEWS FIRST, because it is a real result. Every one of the 128
rows is explained. `tests/qt/test_every_preference_says_what_it_is.py` walks
the finished dialog -- with `spaceout_enabled` forced True, so the Fractal
tab is covered -- and asserts that every label writes a sentence into the
hint strip, that no tooltip is left on a field, that no explanation merely
repeats its label, and that `PREFERENCE_TIPS` carries no key for a row that
is not there. All four pass. This surface has the equivalent of
`test_every_setting_a_module_offers_has_a_category`, and it works. What it
cannot check is whether the sentence is TRUE, and that is where Findings 3, 6
and 11 live.

--------------------------------------------------------------------------------
FINDING 0 -- WHAT THE SURFACE HAS INSTEAD OF `categories` AND `expected_types`
--------------------------------------------------------------------------------

Recorded first because the open instruction asks it directly and the answer
is different in kind from the module answer.

There is NO `settings.categories` entry and NO `settings.expected_types`
entry for any preference, and there should not be: a preference is not a key
in a module's settings dict. Its category is its TAB (General, Appearance,
Performance, Modules, Figures, Logging, and Fractal under spaceout) and its
type is enforced by its own getter, each of which validates on read against a
declared tuple -- `VALID_THEMES`, `VALID_CB_MODES`, `PERFORMANCE_LEVELS`,
`FRACTAL_QUALITIES` and so on -- and falls back to a named default rather
than propagating a bad value. `_as_bool` (preferences.py:3786) exists for
exactly the reason the Annotate audit found `edge_image` shipping the STRING
'False': an INI hands every value back as a string and `bool("false")` is
True. So the defect that let a checkbox ship a truthy string CANNOT happen
here; each getter coerces.

  THE HOLE IS THE OTHER DIRECTION. Nothing checks that every STORED key has a
  row, or that every row's value is READ. `test_every_preference_says_what_it
  _is.py` walks rows and asks whether they are explained; no test walks the
  99 `_KEY_*` constants and asks whether anything consumes them. That is what
  lets Findings 2, 4 and 5 sit unnoticed, and it is the one test this surface
  is missing.

FINDING 1 -- THE FIGURES TAB'S 37 PER-GRAPH ROWS CANNOT REACH A FIGURE
--------------------------------------------------------------------------------

PROPOSE: THIS IS THE ITEM TO LOOK AT FIRST. It is the largest block of
settings on either surface, it is the only one that costs a user their work
rather than their patience, and the code that proves it is a comment the
package already wrote about itself.

35 of the 37 per-graph rows, and 2 of the 23 general rows, are stored, shown,
tooltipped, translated -- and cannot change any figure spaCR draws.

  THE ONE ROUTE FROM THE STORE TO A FIGURE, and there is only one:

      spacr/figures/style.py:327    params.update(user_overrides(kind))
      spacr/figures/style.py:229    chosen = resolve(kind, general, per_graph)
      spacr/figures/style.py:231    after, before = rc_params(chosen),
                                                    rc_params(untouched)
      spacr/figures/style.py:232-233    return {key: value for key, value in
                                        after.items() if before.get(key) != value}

  `user_overrides` turns the user's style deltas into MATPLOTLIB rcParams and
  returns only the rcParams that MOVED. A style key that `rc_params` does not
  emit therefore reaches nothing. `spacr/figure_style.py` says so itself, in
  the comment beside the palette:

      # THE PALETTE IS AN rcParam TOO, and it has to be one here rather than
      # only inside `apply`. `spacr.figures.style.rc` -- the only supported
      # way a figure gets this style -- builds its overrides by DIFFING two
      # `rc_params` dicts, so a setting this function does not emit cannot
      # reach a drawn figure at all: a user who picked a palette in
      # Preferences got the Matplotlib default cycle back.
      (spacr/figure_style.py:386-392)

  That paragraph was written to fix ONE key. It is true of twenty-seven.

MEASURED, not inferred. For each style key: take the resolved style, change
that key, and diff `rc_params` before and after.

    INERT GENERAL (2 of 23):    format   mark_colouring

    INERT PER-GRAPH (25 of 27): annotate  annotate_cells  aspect  bar_alpha
    bins  centred  colormap  edge_colour  edge_width  error_bars  fill_colour
    jitter_width  label_top_n  legend  log_y  per_row  point_alpha
    reference_colour  reference_style  split_axis  threshold_colour
    threshold_style  threshold_width  trend_colour  trend_line

    LIVE PER-GRAPH (2 of 27):   grid -> axes.grid
                                marker_size -> lines.markersize

  So of the 37 per-graph ROWS the panel builds -- five for jitter_bar, three
  for residuals, five for scatter, six for histogram, five for plate_heatmap,
  nine for volcano, four for line -- 35 do nothing. A user who opens
  Preferences, picks the volcano page, sets "Label top n" to 25, turns
  "Split axis" on and chooses a threshold colour, and presses OK, has changed
  three JSON entries and no figure.

THE API THAT WAS MEANT TO DELIVER THEM EXISTS AND HAS NO CALLER.
`spacr/figure_style.py:401 apply()` returns the FULL resolved style,
"including settings that have no Matplotlib rcParam equivalent". Its only
caller is `spacr/qt/preferences.py:949 apply_figure_style`, whose docstring
reads:

    """Push the user's style for ``kind`` into matplotlib. Returns it.

    The one call a plotting function needs: it reads the preferences, layers
    them over the defaults and this graph kind's own, and applies the result.
    """

  `apply_figure_style` HAS NO CALLERS ANYWHERE UNDER `spacr/`. "The one call
  a plotting function needs" is a call no plotting function makes.

  AND THE TESTS DESCRIBE THE CALLER THAT DOES NOT EXIST:

      `apply` still has to return the resolved style -- the caller reads
      per-graph settings such as ``label_top_n`` out of it that have no
      rcParam at all
      (tests/test_figure_style_uncovered_paths.py:122-124)

      the settings matplotlib has no rcParam for -- how many volcano labels
      to write -- are read off the return value and the plot cannot be drawn
      without them
      (tests/test_figure_style.py:129-131)

  Both are true statements about a design. Neither is a statement about this
  package: no plot reads them off anything.

  THE PACKAGE ALREADY KNOWS `label_top_n` IS NOT AN rcParam, and says so
  three lines from where it stores the panel's values:

      #: Merging the two vocabularies would put `label_top_n` into
      #: `rcParams.update`, which raises rather than being ignored.
      (spacr/qt/preferences.py:817-818)

  -- and the panel offers `label_top_n` anyway.

  PROPOSAL, and it needs the maintainer because there are two honest
  answers. EITHER make `rc()` hand the resolved style to the plot (which
  means every plotting function that draws a volcano, a histogram or a plate
  heatmap has to read it, and that is the design the tests already describe);
  OR cut `GRAPH_DEFAULTS` down to the keys `rc_params` emits and stop
  offering the other twenty-five. What must not stand is the third state,
  which is what ships: thirty-five controls with tooltips explaining what
  they would do.

  THE LIVE CONTROLS FOR THE SAME QUESTIONS ALREADY EXIST ELSEWHERE, which is
  why nobody noticed. `spacr/volcano_style.py` has its own `split_axis`,
  `colormap` and `show_colorbar` on a `VolcanoStyle` dataclass driven by the
  Volcano explorer, stored under the SEPARATE key `figures/style_defaults`
  (preferences.py:819) -- and that one works. Two vocabularies, one live.

      (spacr/qt/widgets/fractal_cascade.py:15-16)

      // TRUE SPATIAL 2x2, four samples of ONE instant. The CPU path jitters
      (spacr/qt/widgets/fractal_orbit_gpu.py:139)

      """Two samples a side on a small frame, one on a large one.
      (spacr/qt/widgets/fractal_space.py:472-476)

  Two samples a side, always, whatever the field says.

AND THE CONSTANT THAT DOCUMENTS THE DEFAULT DOCUMENTS NOTHING.
`fractal_defaults.py:44-57` carries five lines of reasoning for

      def test_preferences_reads_these_and_not_a_second_copy():

FINDING 3 -- QUALITY: FOUR LEVELS, THREE ACCEPTED, AND A PRESET NEVER APPLIED
--------------------------------------------------------------------------------

PROPOSE: this is three defects on one row, and the third is the one the
module documents having already fixed elsewhere.

(a) `apply_quality_preset` HAS NO CALLER. `QUALITY_PRESETS`
    (preferences.py:2365-2390) maps each level to four numbers, and
    `apply_quality_preset` (preferences.py:2394-2409) writes them. Nothing
    under `spacr/` calls it -- only four tests. The dialog's save writes only
    the STRING (`quality=fractal_quality.currentData()`,
    preferences.py:6023). So the row's own tooltip is false:

        "A level is a set of numbers, not an adjective: choosing one fills
        in supersampling, render scale, the iteration budget and the scale
        below."
        (preferences.py:5444-5451)

    It fills in none of them.

(b) `ultra` IS SILENTLY RESET TO `auto`. Two copies of the level list, and
    they disagree:

        spacr/qt/preferences.py:2358
            FRACTAL_QUALITIES = ("auto", "balanced", "high", "ultra")
        spacr/qt/widgets/fractal_travel.py:53
            QUALITIES: Final[tuple[str, ...]] = ("auto", "balanced", "high")

    `Settings.validated()` (fractal_travel.py:257) does
    `quality=self.quality if self.quality in QUALITIES else DEFAULT_QUALITY`,
    and `create_fractal_widget` calls it on every build
    (fractal_travel.py:2427). Measured:

        panel picks ultra -> validated auto -> gpu resolves balanced
        panel picks high  -> validated high -> gpu resolves high

    So on the GPU -- the default backend wherever vispy is installed --
    choosing ULTRA gives you BALANCED, which is strictly less than High. On
    the CPU it lands on `high` only if the machine has 16 or more cores, and
    on `balanced` otherwise. Ultra is never more than High and is usually
    less.

  THIS IS THE DEFECT `fractal_defaults.py` RECORDS HAVING FIXED FOR PATTERNS:

      #: There used to be a second copy in `preferences.FRACTAL_PATTERNS`,
      #: and adding a pattern to one and not the other meant the new pattern
      #: was selectable in code and absent from the Preferences combo --
      #: which is how it was found.
      (spacr/qt/fractal_defaults.py:33-36)

    `FRACTAL_PATTERNS` is now imported from `fractal_defaults`
    (preferences.py:2355). `FRACTAL_QUALITIES` is still a second copy, and
    it grew a fourth entry the renderer never learned.

(c) THE TOOLTIP DESCRIBES TWO LEVELS AND THE COMBO OFFERS FOUR.

        "Quality": "How much detail the fractal is asked for. Balanced costs
        less per frame; high adds an iteration to the fractal and raises the
        internal resolution. Automatic chooses from the number of cores on
        the CPU renderer and uses balanced on the GPU."
        (preferences.py:4216)

    Ultra is not mentioned. "raises the internal resolution" is not true
    either -- see Finding 4.

  PROPOSAL: import `FRACTAL_QUALITIES` from `fractal_defaults` the way
  `FRACTAL_PATTERNS` already is, so one list decides both; then either call
  `apply_quality_preset` from the combo or delete `QUALITY_PRESETS` and the
  sentence that promises it.

FINDING 4 -- `scale` AND `render_scale` ARE ONE QUESTION, SHIPPED DISAGREEING
--------------------------------------------------------------------------------

PROPOSE: COMBINE. This is the `organelle_min_size`/`_min_area` shape from the
Mask audit -- two keys for one question, read by different code -- with one
extra turn: at a fresh install the two hold different values, so the shipped
default does not happen.

    scale         the row on the Fractal tab. Default 0.5.
    render_scale  derived from it on save (`SCALE_GROUP`,
                  preferences.py:384-388; `scale_group_values`, :406-418).
                  Default 1.0, from `fractal_mandelbrot.DEFAULTS`.

Measured in a clean store:

    scale: 0.5   render_scale: 1.0   DEFAULT_SCALE: 0.5

  `DEFAULT_SCALE`'s own comment (fractal_defaults.py:59-62) says: "Render
  scale, asked for on 2026-09-01. Half resolution: the backdrop is behind the
  interface and a full-resolution one buys sharpness nobody reads at the cost
  of frames everybody feels." The backdrop renders at FULL resolution until
  somebody opens Preferences and presses OK, because that is the only thing
  that runs the derivation.

AND `scale`'S OWN CONTRIBUTION IS THROWN AWAY. On the CPU path:

    spacr/qt/widgets/fractal_travel.py:785
        base_pixels *= settings.scale * settings.scale

    spacr/qt/widgets/fractal_travel.py:1307-1328
        requested = float(base_pixels) * adaptive_scale ** 2
        ...
        if render_scale > 0.0:
            requested = native * render_scale * render_scale * adaptive_scale ** 2

  `base_pixels` -- and with it `settings.scale` AND the per-pattern budget
  AND the balanced/high distinction -- is overwritten whenever
  `render_scale > 0`, which the same comment says is always: "since
  `render_scale` defaults above zero, that was every launch"
  (fractal_travel.py:1311-1312). `_number` floors `render_scale` at 0.05
  (FRACTAL_LIMITS, preferences.py:335), so it can never be zero.

  ON THE GPU PATH NEITHER IS READ. `_render_scale()` has exactly one caller,
  `CpuFractalWidget._target_size` (fractal_travel.py:961), and
  `_make_gpu_widget` (fractal_travel.py:1542-2266) sizes from
  `self.physical_size` and never mentions `render_scale` or `settings.scale`.
  `_render_scale`'s docstring says "MODULE LEVEL, because both builders need
  it" (fractal_travel.py:2373); one builder needs it.

  SO THE TOOLTIP IS HALF RIGHT AND HALF WRONG:

      "Scale": "A resource multiplier for the CPU renderer's internal
      resolution, applied before it adapts. Below 1.0 draws fewer pixels and
      scales them up; above 1.0 draws more. It does not change what the
      fractal looks like, only how finely it is sampled. The GPU renderer
      ignores it."
      (preferences.py:4217)

  "The GPU renderer ignores it" is honest and correct. "above 1.0 draws more"
  is not: `target_render_size` caps at `min(native, requested)`
  (fractal_travel.py:1330), so above 1.0 draws exactly native, and
  `Settings.validated()` clamps scale to 2.0 first (fractal_travel.py:258).
  Measured: `target_render_size(1920,1080,1.0,render_scale=1.75,...)` returns
  (1920, 1080), the same as 1.0.

  PROPOSAL: one key. Keep `render_scale` -- it is the one the renderer reads
  and the one whose name says what it is -- retire `scale` into
  RETIRED_SETTINGS, and let the row write `render_scale` directly. Then
  `DEFAULT_SCALE = 0.5` becomes true on first launch instead of after the
  first Save.

FINDING 5 -- THE FRACTAL FIELDS PROMISE TO BE UNCAPPED AND ARE CAPPED IN USE
--------------------------------------------------------------------------------

PROPOSE: fix the promise or fix the clamp. The design is written out twice
and contradicted once, silently.

    """A NUMBER FIELD, not a capped slider.

    A spin box whose maximum is 2 turns a typed 40 into 2 without

        scale=clamp(float(self.scale), 0.25, 2.0),
        (spacr/qt/widgets/fractal_travel.py:258, in `Settings.validated`)

    Measured: `Settings(scale=40.0).validated().scale == 2.0`. And

  AND THE HONEST NUMBERS ARE WRITTEN AT THE CALL SITE AND DISCARDED.

      fractal_scale = _tenths("FractalScale", ..., 0.25, 2.0)   (:5490)
      fractal_speed = _tenths("FractalSpeed", ..., 0.15,
                              MAX_FRACTAL_SPEED)                    (:5493)
      fractal_dream = _tenths("FractalDream", ..., 0.0, 1.5)    (:5496)

  `0.25, 2.0` at :5490 is EXACTLY the clamp `validated()` applies. The number
  that would have made the field honest is typed into the call and thrown
  away.

  THE FUNCTION NEXT DOOR HAS THE ARGUMENT ALREADY WRITTEN OUT:

      # NO `suffix` PARAMETER. It had one, defaulting to "", and the single
      # caller below never passed it -- so the `setSuffix` it guarded could
      # not run ... A parameter with no caller is not extensibility, it is a
      # branch that cannot be tested and a reader wondering what uses it.
      (spacr/qt/preferences.py:5475-5480, `_whole`)

  The same defect survives in `_tenths` twenty lines above, with five
  callers instead of none.

  `MAX_FRACTAL_SPEED` IS A CASUALTY OF IT. `MAX_FRACTAL_SPEED: float =
  1_000_000.0` (preferences.py:448) occurs exactly twice in the package: its
  definition, and :5495 where it is passed to the parameter that is ignored.
  A module-level constant with a five-line provenance that decides nothing.

  PROPOSAL: either delete `low`/`high` from `_tenths` and `MAX_FRACTAL_SPEED`
  with them, or give `scale` a ceiling in `FRACTAL_LIMITS` so
  `explain_a_fractal_number` says what `validated()` is about to do.

FINDING 6 -- LAPTOP MODE: A SETTER AND A GETTER THAT DISAGREE, AND A ROW THAT
             REVERTS EVERY LAUNCH
--------------------------------------------------------------------------------

PROPOSE: the second item for the maintainer's attention, because unlike
Finding 1 it changes what the application looks like on every start and there
is nothing on the surface that explains it.

(a) THE GETTER NO LONGER READS THE KEY THE SETTER WRITES.

        def get_laptop_mode() -> str:
            """...
            DERIVED, NOT STORED. ... There is no ``"automatic"`` any more
            """
            return "on" if get_performance_level() == "laptop" else "off"
        (preferences.py:2746-2762)

        def set_laptop_mode(choice: str) -> None:
            ...
            if choice not in LAPTOP_MODE_CHOICES:   # ("automatic","on","off")
                raise ValueError(...)
            _settings().setValue(_KEY_LAPTOP_MODE, choice)
        (preferences.py:2764-2783)

    `prefs/laptop_mode` is read in exactly one other place -- the one-shot
    migration inside `get_performance_level` (preferences.py:2894) -- and
    that migration is idempotent: "once a level is stored the old values are
    never consulted again" (:2882). So on any installed spaCR,
    `set_laptop_mode("on")` writes a key nothing will read, and
    `get_laptop_mode()` answers "off" straight afterwards unless the
    performance level happens to be Laptop. The setter still accepts
    "automatic", a value the getter documents as gone.

    NEITHER HAS A CALLER. `get_laptop_mode`, `set_laptop_mode` and
    `laptop_mode_note` (preferences.py:2785) are called nowhere under
    `spacr/` -- only from tests -- and `LAPTOP_MODE_LABELS`
    (preferences.py:2334) is referenced nowhere at all. There is no Laptop
    row in the dialog; the level selector replaced it.

(b) AND THE MODE STILL ACTS, BEHIND THE PREFERENCE THAT REPLACED IT.

        def apply(on: Optional[bool] = None) -> Dict[str, object]:
            if on is None:
                on, why = wanted()
            ...
            if on:
                if preferences.get_ambient_enabled():
                    preferences.set_ambient_enabled(False)
        (spacr/qt/laptop_mode.py:143-166)

    called unconditionally at launch (`spacr/qt/app.py:5819-5821`), and
    `wanted()` decides from the MACHINE -- fewer than 4 usable cores or less
    than 8 GiB (laptop_mode.py:21-25, :104-111) -- not from the performance
    level the user chose. So on a small machine, or in a container pinned to
    three CPUs, every launch PERSISTS `ambient_enabled = False` and never
    restores it, whatever the user picked on the Performance row.

    THE ANIMATION ROW THEN LIES, WHICH IS THE STATE THE DESIGN WAS WRITTEN TO
    PREVENT. `set_ambient_enabled` does not touch `ambient_theme`, so the
    Preferences Animation combo still reads "Blobs" while nothing is painted.
    The module docstring:

        ``ambient_enabled``: ... The user-facing control is the ``None``
        entry in the Animation list rather than a second switch: one row, one
        meaning. Choosing an animation turns it back on.
        (preferences.py:94-99)

    Saving Preferences does turn it back on (`set_ambient_animation` ->
    `set_ambient_enabled(True)`, preferences.py:1789), and the next launch
    turns it off again. A row that cannot be made to stick, with no control
