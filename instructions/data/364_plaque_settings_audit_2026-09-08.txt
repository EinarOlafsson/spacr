`analyze_plaques` (get_analyze_plaque_settings)
22 settings

Same three questions as mask, measure, regression, classify, annotate, map
barcodes and motility: is it needed, is it a duplicate, is its name honest.
Same standard: every claim below is either the setting's own tooltip or the
line of code that reads it.

--------------------------------------------------------------------------------
FINDING 0 -- THE MODULE CANNOT RUN FROM ITS OWN DECLARED SETTINGS
--------------------------------------------------------------------------------

This is not a naming question and it is the reason this audit is filed ahead
of the smaller modules that were meant to come first.

`analyze_plaques` calls `spacr.spacr_cellpose.identify_masks_finetune`, which
reads 24 keys out of the settings dict. `get_analyze_plaque_settings` declares
22 keys, and SEVEN of the reads are not among them and are not added by
`analyze_plaques` either:

    channels   grayscale   invert   model_name
    normalize  percentiles  remove_background

`analyze_plaques` adds exactly two before the call -- `custom_model` and
`dst` -- and neither is one of these.

REACHED, NOT MERELY PRESENT. `settings['normalize']` is read at
`spacr_cellpose.py:237`, inside the per-batch loop, with no branch above it:

    if len(all_image_files) == 0:
        ...
        return
    time_ls = []
    for i in range(0, len(all_image_files), settings['batch_size']):
        ...
        if settings['normalize']:          <- line 237

So `analyze_plaques` with `masks=True` -- WHICH IS THE DEFAULT -- raises
`KeyError: 'normalize'` as soon as it finds one image. `model_name` is read
too, but only on the branch where `custom_model` is None, and
`analyze_plaques` always sets it; that one is unreachable from this module and
is listed for completeness rather than as a defect.

  NOT FULLY EXECUTED, AND SAYING SO. Driving it to the KeyError needs a real
  Cellpose checkpoint, which this audit did not download. What WAS executed:
  with a fake checkpoint the run reaches the model-loading step and fails
  there, which is strictly before the loop -- so the control-flow argument
  above is what carries the claim, not a traceback.

  THE FUNCTION HAS THIS EXACT HISTORY, three lines above the loop, in its own
  comment:

      # NB: use the local ``dst`` -- there is no settings['dst'] key, so
      # the old settings['dst'] raised KeyError on this no-images path.

  One instance of this bug was already found and fixed in place. Seven more
  were left.

WHY NO TEST CAUGHT IT. `tests/test_submodules_plaque_well_integration.py`
::test_analyze_plaques_hands_detected_well_crops_to_the_analysis is the only
test that drives `analyze_plaques`, and it passes `"masks": False`, which is
the branch that SKIPS `identify_masks_finetune` entirely. The default is
`True`. So the covered path is the one the user does not take.

WHAT TO DO, and the choice is the maintainer's:
  (a) declare the seven in `get_analyze_plaque_settings` with the defaults the
      plaque path wants -- which also makes them visible and editable in the
      GUI, since the settings panel is built from this factory; or
  (b) have `analyze_plaques` set them explicitly before the call, the way it
      already sets `custom_model` and `dst`, if they are implementation
      details the user should not see.
  (a) is the honest one if any of them changes results -- `normalize`,
  `percentiles`, `invert` and `remove_background` all do.
  EITHER WAY, the integration test should be repeated with `masks=True`.

--------------------------------------------------------------------------------
FINDING 1 -- NOTHING IS DEAD
--------------------------------------------------------------------------------

All 22 declared settings are read. The five that looked dead on a consumer
count were each checked against the line that reads them:

    fill_in            spacr_cellpose.py:277
    plaque_model       submodules.py, resolved to a checkpoint path
    well_confidence    the YOLO well detector's confidence floor
    well_diameter_mm   the physical scale used to convert plaque areas
    well_pad           the crop margin around a detected well

Four of those five exist only to serve `well_detection`, which is the newest
feature in this module. That is a shape worth naming rather than a defect --
see FINDING 3.

--------------------------------------------------------------------------------
FINDING 2 -- TWO NAMES THAT DO NOT MATCH THE HOUSE STYLE
--------------------------------------------------------------------------------

  `Signal_to_noise` is the only setting in this module -- and one of very few
  in spaCR -- that is not lower_snake_case. It is read as
  `settings.get('Signal_to_noise', 10)` in `io.py:1745` and 1769. PROPOSE
  `signal_to_noise`, with the old spelling accepted through the usual
  migration, because a settings file in the wild carries the capital.

  `CP_prob` is an abbreviation of an abbreviation. Cellpose itself calls this
  `cellprob_threshold`, and `spacr_cellpose.py:265` passes it straight through
  as `cellprob_threshold=settings['CP_prob']`. PROPOSE `cellprob_threshold`,
  matching the library the user will read the documentation of.

  Both are renames and therefore need `RETIRED_SETTINGS` handling and the
  maintainer's approval; neither is proposed as a silent change.

--------------------------------------------------------------------------------
FINDING 3 -- FIVE SETTINGS THAT ONLY MEAN ANYTHING TOGETHER
--------------------------------------------------------------------------------

`well_detection` is a switch, and `well_confidence`, `well_diameter_mm`,
`well_pad` and `plate_format` are all inert while it is False -- which is the
default. Four of the module's 22 settings therefore do nothing for a user who
has not turned on well detection, and nothing in the form says so.

This is the same shape the mask and classify audits recorded, and the same
remedy applies: the four belong in a section that is disabled, or hidden,
while the switch is off. NOT proposed as a removal -- they are all live.

--------------------------------------------------------------------------------
FINDING 4 -- `resize` IS IMPLIED BY THE TWO SETTINGS BESIDE IT
--------------------------------------------------------------------------------

`resize` (bool, default True) gates `target_height` and `target_width`
(default 1120 each) at `spacr_cellpose.py:255`, 280 and 292. Three settings
express one decision, and the boolean can disagree with the pair: `resize`
False with a target size set reads as "resize to 1120x1120, but do not".

PROPOSE folding it: a target size of `None` means "do not resize". One
setting fewer, no state that contradicts itself. LOWER CONFIDENCE than the
findings above -- `resize` is also read on the mask-writing path at 280 and
292 to undo the resize, and whether "was it resized" needs to survive
independently of "what size was asked for" should be checked before acting.
