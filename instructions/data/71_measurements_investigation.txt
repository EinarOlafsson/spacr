### 1. Measurements you are missing

Prerequisites that apply to every new column, because two of them delete the feature silently: a name containing the substring `label` is swallowed by `utils._check_integrity` (folded into `label_list`, dropped, no warning — and if it sorts before the real label column it *becomes* `object_label` and corrupts the merge key); `utils.filter_dataframe_features` does `df.dropna(axis=1)`, so one NaN anywhere (e.g. a partially re-measured plate, or one flat object producing NaN skew) deletes the column from every model matrix; every `<object>_`-prefixed numeric column auto-enrols in every classifier/UMAP/timelapse feature matrix via `schema._model_feature_role` with nobody opting in; and each feature needs a `KNOWN_PROPERTIES` + `FEATURE_SCOPE` entry in feature_dict or it reports as family `unknown` with a null description. Each new setting is four edits in settings.py (setdefault, expected_types, tooltip stating the default, category) gated by five tests.

CHEAP, ranked:

1. **GLCM properties beyond homogeneity.** The co-occurrence matrix is already built and thrown away after one of skimage's ten properties is read. Add contrast, dissimilarity, correlation, energy/ASM, entropy — chromatin condensation, vacuole granularity, cytoskeletal linear structure, general disorder. Cost at the mandated default (`glcm_levels=256`, back-compat): today's matrix 0.62 ms + homogeneity 0.75 ms = 1.32 ms per object/channel/distance; six properties = 5.2 ms, i.e. ~4x. At `glcm_levels=64` six properties cost 0.50 ms total — 2.6x *faster* than today — but homogeneity changes scale completely (0.0350 → 0.1313 on the same patch), so reduced-level features must be written under distinct column names. `graycoprops` re-normalises the whole P array per call, so cost is O(levels²·distances·angles) per property. Also: only angle 0 is used, an 8.1% spread across the four angles, i.e. the current homogeneity is rotation-dependent; pooling four angles into one matrix before reading properties costs 0.68 ms at 64 levels. Free fix in the same edit: hoist `rescale_intensity` out of the per-distance loop (0.105 ms per object/channel wasted at 3 distances).
2. **Radial distribution: MeanFrac.** The bin loop stores only the shell mean. `MeanFrac = (vals.sum()/cell_total) / (vals.size/cell_pixels)` is normalised for both exposure and shell area and is free from the already-extracted vector (~20 µs against ~615 µs per bin). This is the recruitment/translocation statistic. Do not ship a pixel-wise `std/mean` as "RadialCV" — CellProfiler's RadialCV is across angular slices and needs an extra `arctan2` pass. Caveat already documented in feature_dict: shell width is per-object, so bins are not comparable between objects of different size. Real cost is not the arithmetic — `_create_dataframe` writes each value with a scalar `df.loc[...]`, so tripling the statistics adds ~4.2 s per object type at 400 objects × 4 channels. Vectorise that function in the same commit.
3. **Colocalization: Spearman + Manders overlap coefficient.** Both are reductions on vectors the function already extracted. Spearman is monotone-robust — Pearson flips on a single saturated punctum; MOC needs no threshold. Cost: Spearman 0.33 ms at n=500 up to 1.47 ms at n=5000, against 0.43–0.61 ms for the six percentile calls already made; MOC 0.018 ms. Two caveats: MOC is scale- but not offset-invariant, so a background pedestal drives it toward 1 (it trades a threshold for a background-subtraction assumption); and the name collides with feature_dict's existing (wrong) description of M1/M2 as "overlap coefficient" — call it `Manders_overlap_correlation` and fix that text. Add a constant-vector guard while you are there: `pearsonr` on an all-zero channel returns NaN today with a `ConstantInputWarning`, and that NaN either deletes the column (default `filter_by='channel_0'` → `dropna(axis=1)`) or is imputed as the column mean, giving an uninfected cell the average colocalization of infected cells. M1/M2 correctly return 0 in the same case.
4. **Shape ratios: form_factor and roundness only.** `4πA/P²` and `4A/(π·major²)` — boundary roughness, which separates a smooth round cell from a ruffled/blebbing one of identical eccentricity. Five vectorised ratios over 5000 rows cost 0.67 ms. Do *not* add aspect_ratio or elongation: skimage's eccentricity is `sqrt(1-l2/l1)` and the axes are `4·sqrt(l)`, so both are exact monotone bijections of a column you already have. `compactness` as `P²/4πA` is exactly `1/form_factor` (CellProfiler's Compactness is a different, second-moment quantity and is not free). Perimeter-based convexity needs a per-object convex hull and is not free. `form_factor` is 2-D only — `perimeter` is in `PROPS_2D_ONLY`.
5. **Neighbours / local density — the largest genuine gap.** No spatial family exists in the taxonomy at all. Per cell: neighbour count within a radius, first/second nearest-neighbour distance, percent_touching. Cost is O(field) once, not O(objects × field): cKDTree build + k=6 query over 400 centroids is 0.437 ms, one field-level `find_boundaries` 14.1 ms. Local density is the dominant confounder in image screens — crowded cells are smaller, dimmer and cell-cycle-shifted — and there is no *per-object* column that lets a user regress it out (`object_counts` and `seg_qc.foreground_fraction` are per-field). It also gives per-object segmentation QC. Two mechanics: `binary_dilation` booleanises, so use `skimage.segmentation.expand_labels(labels, distance=1, spacing=...)` for identity-aware touching; and build the KDTree on spacing-scaled centroids or a 50-px radius means different physical lengths in 2-D vs 3-D runs.
6. **Cell periphery intensity.** The periphery/outside gate reads `if ls[j] in ('nucleus','pathogen','organelle')` — cell and cytoplasm are excluded, so there is no plasma-membrane profile for the compartment most often stained. Membrane recruitment, receptor internalisation, cortical-vs-cytosolic redistribution. Add `cell` to the *periphery* gate only (new `cell_periphery`, default True). Measured 340 ms per (mask, channel) at 400 objects on 1024², ≈35 min/plate at 4 channels × 1536 fields — but `find_boundaries` is recomputed inside the per-channel loop despite depending only on the mask; hoisting it cuts that to ~9 min and largely dissolves the default-True objection. New bias to document: cells touch the field edge far more often than nuclei, and `find_boundaries` does not mark the array edge, so clipped cells get a partial rim.

### 2. Opt-in high-compute additions

Ranked by value per second, all default False with the default stated in the tooltip:

- **True Manders M1/M2 at a single threshold** (~0.68 s/field via skimage, ~1.9 s at three thresholds; several times cheaper hand-rolled, since skimage's per-call validation dominates ~3600 calls). This is a correctness fix, not just a feature: the current `M1_correlation_85` is not Manders M1. Both channels are thresholded at their own within-object percentile and share one overlap mask, so M1 and M2 correlate at r=0.998; at t=95 M1 is structurally capped at the intensity fraction in the object's own top 5%; two pure-noise channels give M1=0.047. The tooltips at settings.py:2791 and :2669 (the activation-map path has the identical pattern, with `>=` instead of `>`) call them Manders' overlap coefficients, which names a third statistic again.
- **Costes auto-threshold** (`costes_threshold`, default False): ~21 ms per object per pair at 3000 px — the 100-step regression walk does not terminate early — so ~38 s/field, ~13x the whole existing coloc block. Buys a data-driven threshold instead of the user guessing percentiles, which matters because the shipped `manders_thresholds` default of 15 keeps ~85% of pixels and makes M1≈1 for nearly every object. `proposals/FEATURES_30.md:307` already proposes this; cite it.
- **Costes randomisation p-value: refuse at the per-object level.** 44–121 ms per object per pair → 83–112 s/field, 30–40x the coloc block. If a null is wanted, compute it once per plate on a subsample and say which pair and object type it covers (200 objects × 6 pairs × 5 types ≈ 370 s/plate).
- **Cell outside-ring intensity** (`cell_outside`, default False): 6.8 s per (mask, channel) at 400 objects, ~20x the periphery cost.
- **Full GLCM at 256 levels with pooled angles**, for users who will not rebase their homogeneity columns: ~4x today's texture cost.

Granularity remains absent and I have no measured cost for it; I would not add it on the strength of the current evidence.

### 3. GPU

Mostly no — and the reason is shape, not math. The expensive things in measure.py are not compute-bound; they are O(N_objects × H×W) full-field passes inside Python loops over objects. Fix them on the CPU with bounding boxes and they stop being bottlenecks:

- `_calculate_radial_distribution` runs a full-field EDT plus six full-field boolean passes per (cell, object) pair, three times per field. Measured 22.07 s/field on 1024², 196 pairs, 4 channels. Cropping to a bounding box and replacing the six boolean passes with one `np.bincount(bin_index, weights=intensity)` gives 0.254 s — **87x, bit-identical bins** (0/784 mismatches, max abs diff 8.7e-8). The crop must be `union(cell bbox, object bbox)` padded by 1: objects are selected by any overlap with the cell, so a cell sitting inside a large pathogen has no boundary pixel in its own bbox and every distance becomes `inf`.
- `_outside_intensity` has the same pattern (full-field `binary_dilation` per object): 3.04 s → 0.264 s with the bbox, and → ~0.041 s (**74x**) if the seven separate `np.percentile` calls per object are also collapsed into one vectorised call. The 3-D branch runs a full-field EDT instead and needs per-axis padding `ceil(ring_width/spacing[axis])`, not a flat 5.
- The colocalization pair loop re-runs `np.unique(mask)` and a full-array `mask == i` per channel *pair* — 30 decompositions per field at 4 channels, 140 at 8. Hoisting it out with `find_objects` bbox slices plus a vectorised `np.percentile(v, [15,85,95])`: 3.28 → 1.36 s/field, **2.41x, bit-identical** (roughly a quarter of that from the percentile change alone, which is a 3-line edit). Keep `np.unique(mask)[1:]` for label enumeration to preserve bit-identity. It also lacks the empty-mask guard the intensity loop has, so an unconfigured organelle mask still pays `np.unique` per pair.
- `_extended_regionprops_table` recomputes the whole-field p90/p10 inside the mask loop although it depends only on the channel — up to 5x redundant per channel.

Those four are ~25 s/field of pure waste and cost nothing but `find_objects` added to the existing scipy.ndimage import. They buy all the headroom section 1 needs.

What the GPU can actually take: only whole-field, batched, no-Python-loop work. I verified one exact port — iterating `torch.maximum(F.max_pool2d(x,(1,3),1,(0,1)), F.max_pool2d(x,(3,1),1,(1,0)))` five times is **bit-identical** to `scipy.ndimage.binary_dilation(mask, iterations=5)` (both are the L1 ball of radius 5, and max_pool's `-inf` padding coincides with scipy's `border_value=0`), verified across 200 randomised shapes including border-touching objects. Batching 196 crops as (196,1,33,33) and dilating runs in 11.7 ms with a 15 MiB peak — but that is only 2.3x the *fixed* CPU version, which does not repay a ~300 MiB CUDA context in a multiprocessing worker. Do not one-hot the whole field: 196×1024×1024 float32 peaked at 4964 MiB and was slower (88.6 ms).

Launch latency is real but not the blocker people assume: at realistic object sizes on this 3090, `scatter_add_` is 21.4 µs, `index_add_` 24.3 µs, `torch.bincount` 98.8 µs. 784 per-object ops is ~0.017 s — less than the fixed CPU version. The decisive obstacle for the radial family is different and stronger: **torch has no exact Euclidean distance transform**, in core or in `nn.functional`, and the EDT is the per-object cost. Moving it means writing one.

If anyone does port percentile-heavy code, one hard trap: `torch.quantile` raises `RuntimeError: quantile() input tensor is too large` above exactly 2²⁴ = 16,777,216 elements, **on CPU as well as CUDA** (so there is no fallback, but it is testable in CI). A 2048² 2-D field is 4.2M and fine; the 3-D path this module supports means a 40-plane 1024² stack is 42M and raises. `torch.sort` (0.021 s for 42M on the 3090) and `torch.kthvalue` have no cap, but both are nearest-rank while `np.percentile`/`torch.quantile` interpolate linearly — identical at 42M, but different at the per-object N<100 sizes elsewhere in the file, so a faithful swap needs the floor/ceil lerp.

cupy, cucim, cuml and pyclesperanto are not installed. Each is a new CUDA-version-coupled dependency, which matters given the conda-forge publication; I would not add one for measurements when the CPU fixes give 87x.

### 4. CNN / transformer feature layers

Yes, and most of it is already built. Today nothing embeds crops: `generate_image_umap` is 100% tabular (crops enter only as thumbnails pasted onto the scatter), the `resnet_features` branch raises `NotImplementedError` with a test pinning the raise, and the one helper, `utils.extract_features`, has no production caller and is unusable as written — no `.to(device)` (and its terminal `.squeeze().numpy()` would raise on a CUDA tensor), batch size 1, and ImageNet mean/std normalisation contradicting the mean=std=0.5 transform every spaCR classifier is trained and scored with. Rewrite it in place rather than adding a parallel path, and budget for two `load_image` tests that hard-code the ImageNet constants and the `(1,3,224,224)` shape.

**Which model:** the plate's own trained spaCR classifier, not a fresh ImageNet ResNet. Every classifier spaCR can build is a `TorchModel` (the only other branch, `model_type='custom'`, raises), and `torch_artifacts.build_model_from_configuration` rebuilds one on load, so this works for any saved checkpoint.

**Which layer:** `model._run_backbone(x)`. `TorchModel.forward` is literally `feats = self._run_backbone(x); (dropout); logits = self.spacr_classifier(feats)`, so this is the penultimate pooled vector with no hook, no surgery and no extra forward pass — and it is the honest choice, since the classifier's own decision is a linear function of exactly it. Assert `model.eval()` (dropout is applied after). If an intermediate conv layer is ever wanted, `GradCAMGenerator.hook_layers` and `attribution.resolve_layer` already resolve dotted layer names.

**Dimensionality** (measured through the repo's own `TorchModel` at 224 px, `num_ftrs` and `spacr_classifier.in_features` agreeing): maxvit_t **512**, resnet18 512, vit_b_16 768, convnext_tiny 768, densenet121 1024, efficientnet_b0 1280, resnet50 2048. maxvit_t — the shipped default — is 512 and not 2048 because `TorchModel` deliberately keeps all but the final Linear of maxvit's classifier, so it is the post-Tanh 512-d representation. Recommend 512.

**Where to capture:** one line inside `deep_spacr.apply_model_to_tar` (and identically `apply_model`) — replace `outputs = model(images)` with `feats = model._run_backbone(images)` followed by the existing head. Zero extra forward cost; it rides a pass the user already chose to run, keyed by the tar member name. Not `generate_activation_map` — it has no such line, its forward is inside the CAM generators and runs with gradients, its transform channel-masks the input and its loader may shuffle; it contributes only the proven DB-side-table plumbing. Throughput on an idle 3090, batch 64: maxvit_t 517 img/s fp32, 1071 fp16; resnet50 1486/2826. A real plate (58,751 cells, plate2) is 114 s fp32 / 55 s fp16 for maxvit_t.

**Where to store: a sidecar, not a wide SQL table — and that is a hard limit, not taste.** The sqlite in this env is compiled `MAX_COLUMN=2000`; 2000 columns create, 2001 fails with "too many columns", `ALTER TABLE ADD COLUMN` hits the same ceiling, and Python 3.10 has no `setlimit`. A 2048-d ResNet-50 vector therefore cannot be stored one-value-per-column in **any** table at **any** channel count. ≤1024-d does fit — today's tables measured through the real writer are cell 170 / nucleus 233 / pathogen 233 at 3 channels, 223/306/306 at the default 4, 283/386/386 at 5 — but the disk cost is bad: appending 512-d to cell gives a 682-column table at 8.08 KB/object versus 2.04 today (float32 is stored as 8-byte REAL), so a 384-well, 4-field, ~100-cell/field plate goes ~301 MB → ~1205 MB, a 4x blow-up per embedded object type, on top of a DB that is already 565 MB. And the writer widens one `ALTER TABLE ADD COLUMN` at a time whenever the table already exists.

Packing it into one column does not work either: `schema.validate_object_table_frame` rejects any non-numeric column in the object's own namespace — I ran text, `str(list)` and a float32 `.tobytes()` blob named `cell_*` through the real writer and all three raised `ObjectTableSchemaError('cell feature ... must be numeric, got object')`. An unprefixed column is accepted but is invisible to `model_feature_columns` and `is_provenance_column`. A separate `embeddings` table is a ~7-file change (schema.MEASUREMENT_TABLES / OWNED_TABLES / table_key_columns, resume.MEASURE_OWNED_TABLES, doctor, anndata_export, feature_dict, utils' table literals) and, if `resume.MEASURE_OWNED_TABLES` is missed, `clear_field_rows` silently skips it — every re-measure of a field appends a *second* embedding per object while the object tables are correctly replaced, with no test catching it.

**Recommended layout**, reusing the artifact kind that already exists (`ports.EMBEDDING`, already produced into `results/`, already labelled "embeddings" in the usage report, already in `DEFAULT_PRUNABLE_KINDS` — the project already classifies embeddings as a large regenerable intermediate):

- `<src>/results/embeddings/<model_stem>__penultimate.npy` — C-order float16 (N, D). 58,751 cells: 60 MB at 512-d, 240 MB at 2048-d. `np.load(mmap_mode='r')` memory-maps for free. float16 is safe because these are post-pool activations of order 0.1–10 and spaCR's own exporter upcasts to float32 anyway (`anndata_dtype` defaults to "float32"; anndata itself does not cast).
- Beside it, a key index in the same row order carrying `selection.OBJECT_KEY_COLUMNS` (plateID/rowID/columnID/fieldID/object_label) **plus the object type** — untyped keys collide when one sidecar covers cell and nucleus in the same field — plus the time column if timelapse. Key on the object key, not `png_path`: a path is not stable across machines, and `png_list` is the only table holding both.
- Beside that, a small JSON: model_path, model_name, layer, D, dtype, image_size, normalize_input, channels, crop_format.
- Prefer CSV or a small table over parquet unless you want the dependency: `to_parquet` needs pyarrow or fastparquet and neither is in setup.py's core deps (pyarrow 25.0.0 merely happens to be installed here). h5py 3.15.1 is installed too but HDF5 buys nothing over `.npy` + a key file.
- Declare the producer's own `Port(EMBEDDING, "features", "results/embeddings", "*.npy", shape=ShapeContract(ndim=2))` rather than leaning on the UMAP module's non-recursive `results/*` glob, so shape is actually validated and the bytes are attributed to the right module. And note the prune consequence: filing GPU-extracted features under the same kind as a few MB of UMAP scatter PDFs means a default `plan_prune` deletes both, one of which costs seconds to regenerate and one a full forward pass. Either widen the kind's docstring and separate by role, or accept it explicitly.

**Consumption for training is already written.** `build_anndata(db, embeddings={'cnn': df})` normalises the name to `X_cnn` and `_align_embedding` aligns a DataFrame carrying `OBJECT_KEY_COLUMNS` **by object key**, not positionally — tolerating untyped legacy keys, raising with the exact count and the first three unmatched objects otherwise. So one whole-plate embedding attaches to any filtered or selected export without silently shifting rows, and it round-trips to h5ad. Downstream that is `adata.obsm['X_cnn']` for scanpy, or a torch head trained straight off the memory-mapped `.npy`. Only gap: the settings-dict entry point `run_anndata_export` never passes `embeddings`, so the GUI/headless path needs one new setting (path to the sidecar), with a default and a tooltip. anndata is an optional extra, and scanpy is deliberately not declared — that is the user's own env.

**Do not concatenate embeddings into the tabular ML/UMAP feature table by default.** `generate_ml_scores` reports permutation and feature importances over the joined tables (821 and 1005 columns in two real databases), `preprocess_data`'s `log_data` branch computes `log(x + 1e-6)` on activations, and `remove_highly_correlated` would build a dense ~2850² correlation matrix. Worse, the naive concat silently does nothing under the shipped defaults: `filter_dataframe_features` drops every column not containing the channel string, and `filter_by` defaults to `'channel_0'` while `channel_of_interest` defaults to 3 — so `embedding_*` columns would be dropped before they ever reach a model. Make it a `feature_source` selector ('measurements' default, 'embeddings'), and retire `resnet_features` into it as an alias — it is already a typed, categorised, tooltipped bool that exists only to raise. Two mechanics: `training_basis.SETTING_ALIASES` only renames keys, it never maps values, so `resnet_features=True` would become `feature_source=True` — a value mapping has to be written; and `resnet_features` must *stay* in the settings category list, because `test_settings_categories` freezes it as add-only. Producer settings (`save_embeddings` default False, `embedding_layer` default 'penultimate', `embedding_dtype` default 'float16') belong in the module that runs the forward pass, and `tests/test_core_umap_validation.py:290` is the test to update rather than delete.

While you are in that filter: `channel_of_interest` deletes colocalization columns that were computed and stored. A coloc column contains two channel tokens, and the substring test hits it via the partner channel — at the UMAP default `filter_by='channel_0'` **zero** coloc columns survive; at `channel_of_interest`=1/2/3 exactly one pair survives and the rest are deleted, asymmetrically, purely because the hard-coded drop list starts at `channel_1`. Fix by special-casing `channel_<i>_channel_<j>_` to survive when either member matches. The data is already in measurements.db, so the fix is retroactive and needs no re-measurement.
