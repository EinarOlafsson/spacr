Short version: on this machine, almost nothing in spaCR is compute-bound in the way that makes cupy pay. The three things that actually make the software feel slow are (a) accidental O(objects x image) loops in `measure.py`, (b) a Qt paint path that re-composites the whole layer stack in numpy on the GUI thread, and (c) PNG inflate in annotate. None of those are GPU problems: (a) becomes 10-90x faster on one CPU core once it stops touching the whole field per object, (b) is fixed by QPainter, not CUDA, and (c) has no CUDA decoder available here at all. There is exactly one place where the GPU genuinely wins with a real number attached, and it needs no new dependency because torch 2.9.1+cu128 is already installed and already a core requirement (`setup.py:205`, `torch>=2.0,<3.0`).

The dependency question settles itself. torch is free — it is already there and already imported by `deep_spacr.py`/`hyperparam.py`. cupy is not installed: adding it means a ~100 MB wheel (~500 MB installed) pinned to the CUDA major version (`cupy-cuda12x` for this cu128 build), i.e. a CUDA-coupled variant matrix in the recipe. It does have a conda-forge feedstock so instruction 59 survives, but the recipe gains a cuda-version constraint and a GPU-only variant. cucim/cudf/cuml ship primarily from the rapidsai channel and would put a second channel into the install instructions. My recommendation is to add neither, because after the CPU fixes below there is nothing left for them to accelerate.

### Ranked by win / effort

1. **Batch the percentile calls in `_extended_regionprops_table`** (`/mnt/firecuda2/codex/repo/spacr/spacr/measure.py:1441-1446`, plus the IQR pair at 1420). It loops `for p in percentiles:` calling `np.percentile` once per percentile per object — 8 calls per object (6 + 2), 48,816 calls and 4.9 s in the profiled field. `np.percentile` accepts a sequence for `q`; one call is 7.3x faster and `np.array_equal` on the results is True. Effort: minutes. Caveat: hoist the *raw* masked array, not the NaN-filtered `intens` used by the stats loop at 1382 — reusing the filtered one silently changes output on any region containing NaN. While you are in there, `_field` at lines 1349-1356 (a whole-field ravel + two percentiles) is recomputed inside the 5-mask x n-channel double loop at 1199-1209 although it depends only on the channel; hoisting it turns 40 passes over a 42M-element 3-D volume into 8. No dependency, no GPU.

2. **Stream the annotate page and interrupt superseded loads** (`/mnt/firecuda2/codex/repo/spacr/spacr/qt/screens/annotate.py:300-310`, `:2609-2611`, `:2642-2653`). `_load_page` blanks every thumbnail, then one worker decodes the whole page and emits `done` once at the end. Measured per tile on the real crops in `/mnt/firecuda2/methods_paper/plate1`: 6.6-8.8 ms without outlines, 15.2 ms with them — so at the shipped 5x5 grid the grid is empty for ~220 ms, and for ~900 ms if outlines are on. Change `done` to `Signal(int, int, object)` and emit per tile (or per ~8); `_on_page_loaded` already discards results whose generation token is stale. Separately, `_queue_page_load` never calls `requestInterruption()` on the outgoing worker even though `run()` checks `isInterruptionRequested()` every iteration (line 304) — so held-down Next pays up to two full page decodes per step. One line. Both are pure GUI structure, zero compute, zero dependency, and they are the difference between "the grid blanks and repopulates" and "the grid fills as you look at it".

3. **Bounding-box the per-object morphology in `_outside_intensity` / `_periphery_intensity`** (`measure.py:1504` and `:1483`, called per (mask type, channel) from `:1217`/`:1222`, hardcoded on at the single call site `:2385`). `_outside_intensity` does `label_mask == region` and `binary_dilation(region_mask, iterations=5)` over the *entire field*, once per object, to sample a 5 px ring around an object that may be 8 px across. Measured with 196 objects at 1024^2: 3.04 s per (mask, channel). Cropping to `scipy.ndimage.find_objects` bboxes padded by `distance` and clipped at the edge gives bit-identical output in 0.021 s for the ring geometry — end-to-end the function drops to ~0.26 s, and to ~0.041 s (74x) if you also batch its seven separate `np.percentile` calls. Two caveats that must be in the patch: the 3-D branch at line 1533 is a full-volume `distance_transform_edt` per object and needs a per-axis pad of `ceil(ring_width / spacing[axis])`, not a flat 5; and the ring deliberately does not exclude neighbouring labels' pixels, so a "crop to background only" shortcut would silently change values. `find_objects` is not imported anywhere in the repo today, but `scipy.ndimage` already is (`measure.py:9`) — no new dependency.

4. **Bounding-box `_calculate_radial_distribution`** (`measure.py:1546`, `radial_dist=True` by default at `settings.py:994`, called three times per field at `:1247/:1252/:1257`). This is the single most expensive function in the module. Per (cell, child-object) pair it runs `find_boundaries` and `distance_transform_edt` over the whole field (lines 1627, 1631), then builds 6 more full-field booleans per channel. Cost scales with image area, not object size: 112-116 ms per pair at 1024^2, ~450 ms at 2048^2. Measured 22.1 s per call for 196 pairs at 1024^2, and roughly 360-490 s per field on a realistic 2048^2 CQ1/CV8000 field with ~800 pairs. The rewrite is exact, not approximate: the distance map is only ever read inside the parent cell, and `mode='outer'` boundaries lie at most 1 px outside the object, so computing on `union(bbox(cell), bbox(object))` padded by 2 gives bit-identical bins — I confirmed 0/784 mismatching entries. Measured 87x (22.07 s to 0.254 s). One trap: the crop must be the *union*, not the cell bbox — objects are selected by any overlap (line 1622-1624), so a cell inside a large pathogen would otherwise have no boundary pixel in its crop and every distance becomes `inf`. Medium effort, guarded by a before/after DataFrame equality test.

5. **Histogram LUT for `normalize_pil`** (`/mnt/firecuda2/codex/repo/spacr/spacr/qt/annotate_engine.py:113-141`, consumed at `screens/annotate.py:634`). It casts to float32 and runs `np.percentile` per channel per crop — 180 percentile calls per 60-tile page, 125-143 ms of a ~239 ms page, of which ~96 ms is the percentile. Every crop is already uint8 by then (`read_crop_png` ends in `narrow_to_uint8`, and a PIL RGB image is 8-bit by construction), so the percentiles are exact from a 256-bin histogram and the stretch is a 256-entry LUT through `PIL.Image.point()`. Measured 125 ms to 32 ms, worst single grey-level difference 2 out of 255 (nearest-rank vs numpy's linear interpolation; matchable exactly by interpolating between adjacent bins). Needs a guard for `p_lo == p_hi` on flat crops, which `rescale_intensity` currently handles for free. Pair it with a 4-worker decode pool: measured 239 ms serial to 87 ms at 4 workers, but it gets *worse* at 6 and 8, so the default is 4, not 6. If exposed as a setting it must go on `AnnotateSettings` (`annotate_engine.py:317-360`), not only in `set_annotate_default_settings` — nothing under `spacr/qt/` imports the latter, so a settings.py-only entry would be a no-op for the Qt screen.

6. **Replace the "one whole-image pass per label" idiom with segmented reductions.** Seven live sites: `measure.py:1655`, `:1093`, `:1013`, `:564-565`, `:1231`, `:1493`, `:1529` (`_analyze_cytoskeleton` at 678 has the same shape but is dead code — `feature_dict.py` says so three times and there is no call site). Per-label mean over 800 labels at 1024^2 is 237 ms as a `for k: img[lab == k].mean()` loop versus 9.5 ms as two `np.bincount` calls — 25x, numerically identical. `_summarize_organelles_per_parent` is the worst offender and is worse than it looks: `measure.py:2407/2412/2417/2422` call it up to four times per field with the *same* organelle mask and the *same* channel arrays, so the per-organelle x per-channel loop at 1089-1097 runs 4x redundantly (~3.2 s per field; the segmented version is 18.8 ms). Hoisting those shared intensities is a bigger and easier win than the bincount rewrite itself. Note that plain bincount is not enough wherever `np.percentile` appears on per-object pixel vectors (lines 1670-1671, 1498-1501, 1540-1543) — those need one `np.argsort` on the flattened label array plus `np.split`/`reduceat`, which is the fiddly part.

7. **Cache a QPixmap per layer instead of re-compositing in `paintEvent`** (`/mnt/firecuda2/codex/repo/spacr/spacr/qt/layer_viewer.py:390-409` calling `layers.py:2968` -> `:2949`; also `ortho_view.py:158`, three panes, and `comparison_grid.py:171` per linked pane). Every repaint re-renders every layer at widget resolution, synchronously, on the event loop: measured 115 ms at 800x600, 306 ms at 1200x900, 1061 ms at 2400x1300 with a 3-channel 1024^2 uint16 image plus a 256-object labels layer. That is a ~3 fps ceiling, and `wheelEvent` (418), pan (476-482) and the brush's `move` (`curation_tool.py:127`) all end in `self.update()`. Render each layer once at data resolution into a QPixmap on `LayerEvent`, then let `QPainter.drawPixmap(targetRect, pm, sourceRect)` do pan and zoom: measured 3.1 ms (fast transform) / 4.9 ms (SmoothPixmapTransform) for the two-layer repaint, flat in zoom — roughly 60-100x, inside one frame. This is the biggest perceived-smoothness item in the whole codebase and it is Qt-shaped, not CUDA-shaped. Large effort though, and three real caveats: `Blending.OPAQUE` binarises coverage so it is not plain SourceOver (bake the binarisation into the cached pixmap's alpha, and note smooth scaling re-softens the edge); MULTIPLY/MINIMUM only match numpy over an opaque backdrop, so paint onto an opaque black base; and `set_plane` (`layers.py:349`) and `set_depth` (`:358`) emit no LayerEvent at all, so a REPAINT-only invalidation shows a stale z-slice. Budget ARGB32, ~16.8 MB per 2048^2 layer. Brushing gets only a partial win — each dab still re-renders the labels layer at data resolution unless you blit the dab into the cached pixmap incrementally.

8. **Port trustworthiness/continuity to `torch.cdist` + `topk`** (`/mnt/firecuda2/codex/repo/spacr/spacr/hyperparam.py:1779`, `_umap_scores`). This is the one honest GPU win. sklearn's implementation (`sklearn/manifold/_t_sne.py:524-557`) is a full `pairwise_distances`, an n x n `argsort`, and an n x n int64 `inverted_index` — 24 bytes per n^2, all three live at once, and it is called twice per trial. Blocked `torch.cdist` + `topk` + `scatter_`, block 2048: n=1000 0.02 s vs 0.08 s, n=5000 0.04 s vs 2.17 s (60x), n=20000 0.35 s vs 44.3 s (127x), peak 1.39 GB on the 24 GB card, agreeing to ~1e-7 (float32 vs float64 — not bit-identical, so archived scores would move in the last digits). It also removes a hard memory wall the CPU version has: 9.6 GB at n=20000 and 60 GB at n=50000, reachable because the `row_limit` tooltip (`settings.py:2858`) explicitly invites "set to None to use every row". The honest caveat: `row_limit` defaults to 1000 (`settings.py:897`), and at n=1000 this saves ~0.06 s on an 0.08 s call. It is worth doing for users who raise `row_limit`, and it needs a new setting with a stated default (e.g. `search_scoring_device`, default `'cpu'` or `'auto'` above an n threshold), plus a tooltip noting the float32 divergence and that argsort tie-breaking differs on duplicate feature rows. Keep the sklearn path as the reference implementation and unit-test agreement.

9. **Write crops as 8-bit PNG going forward.** Real crops in `/mnt/firecuda2/methods_paper/plate1` are 224x224 with IHDR bit depth 16, colour type 2 (500/500 sampled), 60,816 files, 8.76 GB. PIL truncates to the high byte at load and `narrow_to_uint8` (`crops.py:1122`) does `//256` anyway, and the display target is a 200x200 8-bit tile — so the low byte is read, inflated and discarded. Resaving identical pixels at `compress_level=6` gives 53 KiB mean (3.4x smaller, ~2.6 GB/plate) and a *faster* warm decode (105 ms to 64 ms per 60 crops); the cold page goes 199 ms to 93 ms. Round-trip through `read_crop_png` is `np.array_equal` with the current output, and no sidecar/migration is needed because `read_crop_png` branches on `img.mode` at runtime, so old 16-bit folders keep reading unchanged (the future-first rule). Two things to get right: the new setting `png_bit_depth` (default 8) belongs in `get_measure_crop_settings` (`settings.py:956`), *not* in `set_default_settings_preprocess_generate_masks` — `settings.py:1067-1077` already documents a real bug from exactly that mistake; and do not implement it by passing `new_dtype='uint8'` to `normalize_to_dtype` (`utils.py:2180`), which changes only the rescale range and returns an array of the original dtype, giving you a 16-bit PNG with a zero high byte and black crops. Narrow with `crops.narrow_to_uint8` right before the write.

10. **LUT-fuse `ImageLayer._draw` and `LabelsLayer._draw`** (`layers.py:1896-1909`, `:2113-2119`, `:354-368`). One precomputed 65536-entry uint16 to RGB float32 LUT per channel replaces the float64 gather, the rescale and `Colormap.map`'s three `np.interp` calls; a label-id LUT replaces `label_colors`' `np.unique` + `np.searchsorted` over the whole canvas every frame. Bit-identical (I checked `np.array_equal` on the uint32 views, not just tolerance). But it is only ~1.3-1.5x on `render_uint8`, not the 2x it looks like — do it as insurance for off-screen rendering (export, report figures) after the QPixmap fix, not instead of it. Needs a `dtype in (uint8, uint16)` guard: a signed int plane would index the LUT from the end and return wrong colours with no error, and `ImageLayer` accepts whatever `np.asarray` gives it.

### Where the GPU is specifically the wrong lever, with the numbers

- **The EDT has no torch op.** `torch` and `torch.nn.functional` have only pairwise/point-set distances (`cdist`, `pdist`, `pairwise_distance`) — no image distance transform. So the single most expensive primitive in `measure.py` has no zero-dependency GPU route; the options are cupy/cucim (not installed, see above) or hand-writing a separable Felzenszwalb-Huttenlocher squared-EDT in torch, which is ~60 lines of nontrivial numerics that must also handle anisotropic `sampling` because all three call sites pass it. After the bbox crop the remaining per-pair work is 1-5 ms of CPU, well under a device round-trip, so this is moot.
- **Transfer cost, measured.** H2D for one float32 plane is 0.276 ms at 1024^2 and 0.918 ms at 2048^2; an int64 label plane is 0.511 ms. A GPU `scatter_add_` segmented reduction is ~6x faster than `np.bincount` including transfer (0.94 ms vs 5.71 ms at 1024^2) — real, but it turns 10 ms into 1 ms against multi-second per-field costs. Kernel launch floor is ~52 us, and at realistic object sizes `scatter_add_` is ~21 us and `index_add_` ~24 us, so per-object kernels are not as catastrophic as "launch latency dominates" suggests — they are simply pointless once the CPU version is 1-5 ms.
- **`torch.quantile` hard-fails above 2**24 elements**, on CPU as well as CUDA (`RuntimeError: quantile() input tensor is too large`; I bisected it — 16,777,216 passes, 16,777,217 raises). A 2048^2 field is 4.2M and fine, but `_extended_regionprops_table` explicitly supports 3-D and a 40-plane 1024^2 stack is 42M. Anyone porting the percentile work must use `torch.sort` (0.021 s at 42M) or `torch.kthvalue`, and must add a floor/ceil lerp if the helper is reused on small per-object arrays, where nearest-rank and numpy's linear interpolation genuinely differ.
- **Annotate does not want a CUDA context.** A batched torch normalize+resize of a whole page is 10 ms against 164 ms on CPU (16x), but decode and outline stay on the CPU, so the GPU floor for a page is ~160 ms — exactly where the free CPU fixes above already land (~87-124 ms). The price is 2.05 s `import torch` + 0.27 s context + 44 MiB VRAM held inside the GUI process, contending with Cellpose and classifier runs on the same card. `outline_image` (`annotate_engine.py:202-288`) is the only genuinely GPU-shaped stage and it defaults to off (`outline=None` in both `settings.py:3894` and `AnnotateSettings`); `binary_fill_holes` at line 268 has no torch equivalent (scipy implements it as iterative bounded dilation), and its `disk(thick)` dilation is only bit-identical to a cross `max_pool2d` at radius 1.
- **No CUDA PNG decode exists here.** torchvision 0.24.1+cu128 is installed but `decode_png` is CPU-only; only `decode_jpeg` takes `device=`. `nvimgcodec` is absent and would be a new CUDA-coupled dependency not on conda-forge. The only way to make decode cheaper is to decode fewer bytes, i.e. item 9.
- **Multiprocessing constrains any GPU path in measure, asymmetrically.** Under the Qt/Tk GUI the pool is already spawn (`gui_core.py:1765` and `gui.py:321` call `set_start_method('spawn', force=True)`, and CPython propagates that into the run process), so per-worker CUDA would actually work there — at 306 MiB of context per worker, measured. On the CLI/notebook path there is no such call, the pool forks, `n_jobs` defaults to `cpu_count()-2` = 30 here, and a forked child that touches CUDA after the parent has (which `preprocess_generate_masks` does, in-process) raises `Cannot re-initialize CUDA in forked subprocess`. Note `torch.cuda.is_available()` still returns True in that state — the correct test is `torch.cuda._is_in_bad_fork()`. Any GPU path in measure would have to branch on the start method. That is a good reason to keep measure CPU-only.

### Two things worth fixing that are neither GPU nor on the above list

`_cluster_structure` (`hyperparam.py:1872-1927`) is the dominant cost in `multi_objective` mode — 7 KMeans fits at `n_init=10` plus 7 silhouettes per repeat, 6.25 s per trial at n=1000 against 4.64 s of UMAP fitting. KMeans is 90% of that at the default `row_limit`, not silhouette, so the cheap fix is `n_init='auto'` and/or not recomputing the identical k-sweep for each of the 3 stability repeats. And trial counts are not where the win is: grid mode is 12 fits (36 with repeats), a Walk is up to 400 (1200), and `walk_search` already dedupes via a `seen` set of trial digests so an oscillating Walk never refits a configuration — the win has to come from per-trial cost.

Nothing above changes what spaCR measures. Every item is a same-output rewrite (bit-identical except where flagged: the torch trustworthiness port at ~1e-7, the histogram LUT at <=2 grey levels, and 8-bit crops which discard a low byte that is already discarded at read time). So the "as many measurements as possible without heavy compute" rule is not just preserved — items 3, 4 and 6 make the existing radial/periphery/outside features roughly two orders of magnitude cheaper, which is what would buy headroom if you ever did want to add texture back.
