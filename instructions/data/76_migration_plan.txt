### 2. THE NAMING DECISION

Recommend: **one slot string per organelle, used everywhere, digit-free and separator-free.**

    ORGANELLE_SLOTS = ("organelle", "organelleb", "organellec", "organelled")

That one string is the settings key prefix, the object type token, the table name, the feature-column prefix, the mask-stack folder name and the `png_list` id column stem. This extends the existing three-way identity at `schema.py:1661-1663` and `:1702-1704` (table name == object type == column prefix) to four rather than inventing a fifth namespace and a mapping between them. A mapping table would become the twelfth competing copy of the vocabulary, which is the disease being cured.

Human-readable names are metadata only: `organelleb_name = "lysosome"`, recorded in the settings table, used in GUI labels, plot titles and QC headings, never in a key, a column or a table name.

`organelle_1` / `organelle_2` cannot be the key token, and this is proven, not stylistic:

- `organelle_1` contains `KEY_SEPARATOR`. `compose_prcfo` yields `p1_r1_c1_f2_organelle_17`; `parse_prcfo` (`schema.py:1432-1444`) splits on `_`, pops `17`, and raises "is not a prcfo". `selection._split_key` (`selection.py:354-375`) rpartitions and finds an all-digit tail, so the key parses as an *untyped* object 17 in a field that does not exist — silently, in both halves.
- `organelle1` contains a digit. With longest-first matching (`schema.py:238`), `organelle141` reads back as type `organelle1` label `41`, so the round-trip proof in `object_id` (`schema.py:790-802`) refuses to key any plain organelle whose label starts with 1 — labels 1, 10-19, 100-199 become unwritable. The parametrised round-trip test `tests/test_schema.py:882-889` uses label 41, which passes for `organelle1`, so this edit goes green in CI and fails on the user's data.

Letter suffixes read badly. `organelleb_channel_0_mean_intensity` is ugly. Accept it: the alternative is either a two-namespace mapping or a per-run user-named vocabulary, and the latter makes `OWNED_TABLES` (`schema.py:1610`), `MEASURE_OWNED_TABLES` (`resume.py:258`) and `table_key_columns` (`schema.py:2066`) run-dependent — and the first two fail *silently* (see §5). Keep the vocabulary closed, hand-written and pin-tested; buy the ugliness.

Cost to an existing settings CSV: **zero.** Slot 1 keeps every key name it has. `organelle_channel`, `organelle_method`, all 58 keys stay typed (`settings.py:2344`), tooltipped (`:3034`), categorised (`:3330`, `:3351`), defaulted (`:467`, `:4415`) and read. No `DEAD_SETTINGS` entries, no tooltip rewrites, `KEYS_BEFORE_REGROUP` (`tests/test_settings_categories.py:397`) untouched. Renaming to `organelle_1_*` instead would cost ~55 `DEAD_SETTINGS` entries each needing a rewritten tooltip (`test_dead_settings.py:255`) and a parametrised validate test (`:291`) — and if you skip that, `utils.load_settings` passes the old key straight through, `organelle_1_channel` takes its `None` default, and the run produces no organelle masks and exits 0. `validate._check_unknown_keys` scores 0.944 on difflib, above the 0.85 cutoff, so it does say "did you mean" — as a WARNING, so `spacr-run` starts anyway.

Cost to an existing measurements.db: **zero.** New tables and new columns only. `CURRENT_SCHEMA_VERSION` stays 1 (`database_schema.py:52`), no `MIGRATIONS` entry (`:184`), no backfill, no `DatabaseSchemaTooNewError` (`:282`). The existing `organelle` table simply means slot 1. Every stored prcfo key composes byte-for-byte. `_rename_legacy_columns` (`database_schema.py:131`) walks `sqlite_master`, so new tables are canonicalised for free; `_widen_table_for` (`utils.py:2808`) already handles the widened summary tables.

One test changes deliberately either way: `tests/test_settings_categories.py:517` `test_exactly_one_organelle_category` asserts exactly one heading whose name contains "organelle". Any second heading breaks it. That is a real decision to take, not a test to route around.

### 3. THE DATABASE DECISION

**N tables for per-object measurements. Wide columns for per-parent summaries.** Not one table with an `organelle_index` column.

Per-object, N tables, because the index column breaks data that already exists:

- Two organelle masks are labelled from 1 independently. One table plus an index means mitochondrion 3 and lysosome 3 in the same field carry the identical `(plateID,rowID,columnID,fieldID,object_label)`. `selection.object_keys` (`selection.py:296`) knows nothing of an index, so they collapse to one key — the exact "two identities, one key" failure the type-in-key work at `selection.py:44-82` was done to end. `anndata_export._build_obs` (`anndata_export/__init__.py:859-873`) raises `DuplicateObjectKeys` on every export, and it only raises because that one guard exists; everywhere else the collapse is silent.
- `io._read_and_join_tables` (`io.py:2705-2712`) rolls children up by grouping on `['cell_id','prcf']` and *means every numeric column*. Suffixing (`:2735`) is per table, so it cannot separate them. Mitochondria and lysosomes would be averaged into one `organelle_area` per cell, silently.
- `png_list` has exactly one `organelle_id` text column (`utils.py:1137-1147`, `io.py:4036`).
- `schema.validate_object_table_frame` (`schema.py:2290-2301`) enforces one row per object key, making the design illegal the moment organelle enters `CANONICAL_OBJECT_TABLES`.
- Existing rows would need backfilling, forcing `CURRENT_SCHEMA_VERSION` 1→2, which makes every already-installed older spaCR refuse the file outright (`database_schema.py:282-288`). It is the only design that makes an existing database unopenable.

N tables costs breadth, not depth: ~20 literal lists become one derivation, and nothing on disk moves.

Per-parent summaries are the opposite case, because the summary row *is the parent*, not the organelle. Keep the four table names (`schema.py:1561`) and one row per parent; widen the columns: `organelle_summary_organelleb_count` alongside `organelle_summary_organelle_count`. This keeps `tests/test_db_contract.py:726` (one row per parent, `object_label` is the whole object key) passing untouched, keeps `OWNED_TABLES` a closed literal, keeps `resume` and `doctor` unchanged, and keeps slot 1's columns byte-identical so the legacy rewrite anchored on `^organelle_summary_organelle_ch<d>_` (`schema.py:316-325`) still fires. The alternative — 4×N table names — buys nothing and multiplies the owned-table problem.

Parameterisation point: the outer prefix `organelle_summary_` stays literal, only the inner token varies. `_parse_organelle_summary`'s gate (`feature_dict.py:2405`) is then unchanged; only the hardcoded `object_type="organelle"` at `:2425/:2433/:2437` becomes the parsed inner token, and the 15 curated keys at `feature_dict.py:1106-1240` become parameterised on `<org>`.

Do not emit slot-2+ summary columns in the pre-migration `ch<d>` spelling — the migration regex at `schema.py:316-325` will not match them and they will never be canonicalised.

### 4. THE ORDER OF WORK

Step 0 — no code. Produce the complete deduped file:line list (only 147 of ~450 exist today), and settle the `DEAD_SETTINGS` deadlock. `test_dead_settings.py:215` demands every declared-but-unreferenced key join the registry; `:232` forbids a key a defaults factory produces from joining; `:322` says the mask module's stock defaults must pre-flight clean. `_LiveTokens.visit_Constant` (`:149`) harvests identifiers only from literal string constants, so a reader written `settings[f'{slot}_min_size']` emits `organelle` and `_min_size`, never `organelleb_min_size`. No ordering of the work satisfies all three. This blocks the generated route and the hand-written route identically and must be answered before a single settings line is edited.

Step 1 — one role registry in `spacr/schema.py`. Collapse the eleven competing constants (`measure_hooks.py:142`, `feature_dict.py:98`, `schema.py:231`, `schema.py:1554`, `crops.py:146`, `io.py:4032`, `measure.py:2462`, `filters.py:49`, `merge_tables.py:96`, `diameter.py:129`, `validate.py:208`) onto one list; everything else derives. ### 5. WHAT WOULD SILENTLY GO WRONG

Ranked by how quietly it corrupts.

Plane-index drift. `merged/*.npy` has no header. A reader still holding `{organelle:7}` while the writer has moved on measures a different channel and writes a full, well-formed table of wrong numbers. No exception, no warning, no missing column. `crops.py:141`, `io.py:3177`, `measure.py:3893`, `io.py:4066`.

Resume row duplication. `MEASURE_OWNED_TABLES` (`resume.py:258-264`) is a hand-written frozenset of ten names; `discover_field_tables`' `owned_only` filter (`resume.py:1014`) drops anything absent from it, so `clear_field_rows` never clears the new organelle tables and a re-measured field *appends a second copy of every row*. `resume.py:253-257` documents this exact failure mode as the known cost of the allow-list. Same shape for `schema.OWNED_TABLES` (`schema.py:1610`) via `doctor.py:1715`, which reports the table as "not one of spaCR's tables".

Feature mis-attribution. `parse_column` breaks on the first `startswith(obj + "_")` at `feature_dict.py:2495`, so `organelle_2_channel_0_mean_intensity` today returns `object_type='organelle'`, `channel=None`, `family='unknown'` — it does not merely fail, it *claims* to be organelle 1, so panels and exports group slot 2's columns under slot 1. Verified against the installed package.

Scope lies. Even after the roster is widened and matching is longest-first, `parse_column(...).object_types` comes back from the literal tuples at `feature_dict.py:1868-1880` omitting the new slot. The parse succeeds; the metadata describing where the feature exists is wrong. `_RING_OBJECTS` (`:1872`), `_ZERNIKE_OBJECTS` (`:1875`).

The substring gate. `measure.py:2852` tests `"organelle" in settings['summarize_organelles_by']`, a character substring test on a `str` (`settings.py:2386` types it `str`). Any value containing the word enables the raw table; any slot token containing `organelle` as a substring makes it worse. `tests/test_settings.py:176` pins the current behaviour. This must become exact membership before slots exist. Note the live fork: `settings.py:1108-1110` and `schema.py:1613-1617` argue for keeping `'cell'` and str; `qt/synthetic.py:624-630` specifies widening to a list defaulting `['cell','organelle']`; and `external_masks.py:673-679` already builds the list form that `expected_types` forbids.

A renamed settings key. Covered in §2: unknown keys pass through `utils.load_settings`, the new key takes `None`, no masks are made, the run succeeds, and the only signal is a WARNING from `validate._check_unknown_keys` on a job that has already claimed a GPU-week.

Already-omitted joins, multiplied. `io.py:2590`, `io.py:3877` and `io.py:6011` list the tables to read back and *already* leave organelle out. Data is measured, written, and never read. N slots make it N times worse and step 3 exists to fix it first.

Cytoplasm absorbing organelles. `crops.py:542` subtracts only `('nucleus','pathogen','organelle')`. Miss one slot and lipid droplets are counted as cytoplasm, in a table that looks entirely normal.

No cull cascade. `utils._exclude_objects` (`utils.py:6092`) has no organelle argument, so culling a cell drops its nuclei, pathogens and cytoplasm but leaves its organelles as orphan rows. `measure_hooks.py:210` says this is intended for one organelle; with N it needs an explicit decision, not inheritance.

Inert generated settings. `postprocess_organelle_masks` today has a default, a type, a tooltip and a GUI widget, and does nothing — `generate_organelle_masks_sam` (`object.py:1416-1687`) never calls `merge_split_filter_masks`, as `settings.py:3105-3110` admits in prose. Generating that key for four slots produces four inert knobs. Decide whether it moves to the `None` bucket at `settings.py:2602-2605` before multiplying it.

Silent loss of the token guarantees. `object_type_prefix` (`schema.py:664-681`) checks emptiness and vocabulary membership only; the no-separator and no-digit rules its docstring promises (`:637`) have no code behind them and hold today only because the five hard-coded names happen to satisfy them. If the vocabulary ever opens, all three guarantees vanish at once with nothing raising. Add the checks at registration time in step 1 regardless of which naming scheme wins.
