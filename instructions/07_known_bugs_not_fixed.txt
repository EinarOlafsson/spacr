N. key_columns can return an object key with NO plate/well/field in it, and
   the guard downstream lets it through            [FIXED 2026-08-10]
--------------------------------------------------------------------------------

FIXED 2026-08-10. `filters.require_full_identity(keys, what)` now demands
every one of `IDENTITY_COLUMNS` plus `object_label`, and both write-back
sites call it (`export_gate`, `export_annotation`) in place of the
`if not keys or OBJECT_COLUMN not in keys` guard, which passed for
`['object_label']`. The refusal names the missing columns. `key_columns`
itself is unchanged -- it still reports what is there -- but its docstring
now says nothing merges on its result without going through the guard.

The reachability question below is ANSWERED, and the answer is "reachable":
the Qt gate editor loads a table through `filters.read_sampled`, which is a
raw `SELECT *`, so a database spelling its identity `plate`/`row`/`column`/
`field` reaches `export_annotation` with exactly the frame that yielded
`['object_label']`. It now raises a FilterError naming the four missing
columns instead of merging on the label. Tightening also refuses a genuinely
partial identity (e.g. no `fieldID`), which is intended: an object label
repeats in every field, so a merge without one is a wrong answer rather than
a reduced one. Regression tests: `tests/test_filters.py::
test_a_gate_needs_the_whole_identity_not_just_the_object_label` and the three
tests beside it.

The record of the defect, as found:
--------------------------------------------------------------------------------

Found 2026-08-10 while auditing new parameter documentation, and confirmed by
executing the real function rather than reading it.

    key_columns(DataFrame with plateID/rowID/columnID/fieldID/object_label)
        -> ['plateID', 'rowID', 'columnID', 'fieldID', 'object_label']

    key_columns(DataFrame with plate/row/column/field/object_label)
        -> ['object_label']

`spacr/filters.py` builds the identity from `IDENTITY_COLUMNS`, which carry
the canonical `*ID` spellings, and appends `OBJECT_COLUMN` unconditionally
when present. A frame using the LEGACY spellings therefore yields an
identity of `object_label` alone.

THE GUARD DOES NOT CATCH IT. Both call sites read

    if not keys or OBJECT_COLUMN not in keys:
        raise FilterError("this table has no object identity ...")

(`export_gate` around line 649, `export_annotation` around line 818.) For
`['object_label']` the first half is False and the second half is False, so
the guard PASSES and the merge proceeds on the label alone -- and
`object_label` is only unique WITHIN a field. Objects with the same label in
different plates, wells or fields would silently collide.

WHY IT IS LEFT: reachability is unproven. The legacy spellings do exist --
`utils.correct_metadata_column_names` exists precisely to rename them, and
`schema.py:251` records that they were two conventions -- but every path that
was checked normalises before reaching here (`ml.py:583`,
`sequencing.py:1060`). So this may be an unreachable hazard rather than a
live bug, and the honest fix depends on which:

  * if unreachable, the guard should still be tightened to require the full
    identity, as documentation of the invariant;
  * if reachable, it is a silent data-corruption path and the guard must
    reject, not warn.

Deciding needs someone who knows whether a user-supplied or hand-queried
frame can reach `export_gate`/`export_annotation` without passing through
`correct_metadata_column_names`. That is a question about how people use the
tool, not about the code.

A DOCSTRING WAS WRONG ABOUT THIS TOO, and is now corrected: it claimed such a
frame "yields an empty list here, which downstream reads as 'this table has
no object identity'". Both halves were false -- it yields `['object_label']`
and downstream accepts it. The docstring described a safe failure where the
code has an unsafe one, which is the most misleading kind.

N+1. SEVEN MORE, all found 2026-08-10 by documenting parameters and having a
     second agent EXECUTE each claim before accepting it
--------------------------------------------------------------------------------

Writing a parameter description forces someone to state what a value does,
and stating it forces a check. Every one below was reproduced, not read.

  make_validation_holdout(seed=...) IS DEAD. The seed is forwarded to
  make_cv_folds, which consumes its RNG only in the `groups is None` branch --
  but make_validation_holdout REQUIRES groups and raises without them, so the
  deterministic greedy path always runs. Verified: seed=0 and seed=12345 give
  byte-identical holdouts. A caller varying the seed to get a different
  validation set silently gets the same one.

  make_validation_holdout SILENTLY CLAMPS. `requested_folds = max(2, ...)`
  means any validation_fraction above 0.5 becomes a 2-way split:
  fraction=0.9 holds out 0.5, with no warning. The `min(requested_folds,
  distinct)` cap misses in the other direction -- 0.05 over 8 groups realises
  0.125. Both are silent divergences from an explicitly requested size.

  plot_single_array's panel title OVERSTATES THE OBJECT COUNT BY ONE. It
  prints `len(np.unique(array))` under a "(obj.)" label, and background 0 is
  one of those values -- a 3-object mask renders as "4 (obj.)". This one is
  on screen, in every mask panel.

  show_cam_on_image WRAPS INSTEAD OF CLIPPING. [FIXED 2026-08-10]
  `np.uint8(255 * mask)` on an
  un-normalised CAM sends anything above 1.0 to an arbitrary colormap
  position rather than saturating: measured, 1.1 -> 24 (cold end), 1.5 -> 126
  (mid), 2.0 -> 254. A `np.clip(mask, 0, 1)` before the cast is the fix.
  FIX: the mask is clipped to [0, 1] before the cast, so 1.5 now renders the
  same saturated red as 1.0 instead of mid-jet green, and a RuntimeWarning
  names the range it clipped so the missing normalisation is not hidden. The
  output cast is clipped too, so nothing wraps on the way out either.

  show_cam_on_image TURNS NaN INTO BLACK. [FIXED 2026-08-10]
  Its `else: cam.fill(0.0)` fallback
  cannot fire for the reason it looks like it should -- COLORMAP_JET maps 0 to
  BGR (128,0,0), so a zero input still has a positive peak. It is reachable
  only via NaN or a sufficiently negative img, and then returns a silent
  all-black image instead of surfacing the bad input.
  FIX: a non-finite `img` or `mask` raises ValueError, and the peak <= 0 case
  raises instead of filling black -- a black attribution map is
  indistinguishable from "the model looked nowhere", which is a claim the
  overlay must not make on the strength of bad input.

  invert_image WRAPS ON SIGNED DTYPES. [FIXED 2026-08-10]
  `max_value - image` on int8 with a
  pixel of -100 gives 227, which wraps to -29. Verified. The function neither
  checks signedness nor promotes.
  FIX: the pivot is now `iinfo.min + iinfo.max`, i.e. the dtype maximum when
  unsigned (uint8/uint16 are bit-for-bit unchanged) and -1 when signed, the
  convention `skimage.util.invert` uses. int8 -100 -> 99, in range, and
  inverting twice is the identity for every integer dtype. A non-integer
  dtype raises ValueError naming the dtype rather than numpy's "Invalid
  integer data type".

  MergedCropSource.get_many RAISES WHERE ITS TYPE SAYS IT SKIPS. It calls
  extract_crops without on_error, i.e. the default 'raise', so one row whose
  label is missing from its mask plane aborts the whole batch -- while the
  `List[Optional[np.ndarray]]` return type and the `if crop is not None`
  guard on the next line (which can never take the None branch) both say
  on_error='none' was intended, so a grid render survives one bad row.

LEFT UNFIXED WHEN WRITTEN, deliberately: the task was documentation, and each
of these changes behaviour. The docstrings describe what the code does TODAY,
so none of them is hidden. Three are worth prioritising because a user sees

N+2. An EMPTY GLCM returns plausible numbers instead of nothing, for most
     nuclei and pathogens
--------------------------------------------------------------------------------

Found 2026-08-10 while benchmarking the GLCM block, and measured rather than
reasoned about.

`graycomatrix` guards an empty co-occurrence matrix with
`glcm_sums[glcm_sums == 0] = 1`, and `graycoprops` then reads a matrix of
zeros. The result is not NaN and not an error: it is **0.0 for contrast,
dissimilarity, homogeneity, ASM, energy and entropy, and 1.0 for
correlation** (skimage guards std < 1e-15 by returning 1.0).

The matrix is empty whenever the object is smaller than the offset distance,
because no pixel pair at that separation lies inside it. Confirmed empty at
d=32 for any patch 32 px or less across -- WHICH IS MOST NUCLEI AND MOST
PATHOGENS at typical magnification.

So `homogeneity_distance_32` for a small nucleus is not missing data that a
model would drop; it is a confident 0.0, and `correlation_distance_32` is a
confident 1.0 -- a perfect correlation reported for an object that has no
pixel pairs at that distance at all. Both land in the feature table and
enrol automatically in every classifier and UMAP matrix.

WHY IT IS NOT FIXED HERE: the honest repair is to emit NaN (or omit the
column) when the matrix is empty, and `utils.filter_dataframe_features` does
`df.dropna(axis=1)` -- so a single small nucleus anywhere in the plate would
delete the whole column from every model matrix. Fixing this properly means
deciding what an absent texture measurement should DO downstream, which is a
question about the feature pipeline rather than about GLCM.

That decision belongs with instruction 71's texture work. Whoever takes it
should also know: at 32 grey levels a fully rotation-invariant seven-property
block costs LESS than today's single rotation-dependent property at 256
levels (1.108 ms vs 1.206 ms per region), so the correct statistic is
affordable -- it just renames every existing homogeneity column.

2026-08-11 - FOUND BY DOCUMENTING PARAMETERS. Each was REPRODUCED, not inferred.
--------------------------------------------------------------------------------

Writing `:param:` lines for 48 functions meant reading what each parameter
actually DOES. That surfaced eighteen dead parameters (now documented as such)
and the following defects, every one verified by calling the function.

WRONG OUTPUT

  utils.plot_images_by_cluster SILENTLY DROPS THE LAST CLUSTER. `colors` is
  bound by `zip(np.unique(labels), colors)` and the colour itself is never
  used -- only the zip LENGTH has an effect. Because np.unique counts the -1
  DBSCAN noise label, a palette sized to the real clusters is one short and
  the final cluster is plotted not at all. Verified: labels {-1,0,1} with a
  2-colour palette plots cluster 0 only; a 4-colour palette plots both.

  utils.plot_grid PAINTS ONE CLUSTER IN TWO DIFFERENT COLOURS. The panel
  border uses `colors[label]` (a direct integer index) while the side-legend
  swatch is positional. With cluster keys {0, 3} and a 4-colour palette,
  cluster 3's border is colors[3] and its swatch is colors[1]. Verified by
  reading the patch facecolors back off the figure. A reader matching
  swatches to panels matches them wrongly.

  utils.plot_activation_grid(overlay=False) DRAWS NO IMAGE AT ALL -- not the
  input, not the saliency or Grad-CAM map. The result is a grid of bare
  class-label boxes on empty axes (verified: len(ax.get_images()) == 0 for
  every panel). `normalize` is then dead too. An incomplete last row also
  renders as empty framed boxes, because ax.axis('off') runs only for i < N.

SILENT NO-OP DRESSED AS SUCCESS

  classifier_evaluation.cross_calibrate_probabilities DOES NOT VALIDATE
  y_true against the probability columns. A label of 7 against a 2-column
  matrix makes every fold's fit_temperature raise inside its try/except, each
  falls back to temperature 1.0, and the function returns UNCALIBRATED
  probabilities with only a printed warning. Verified: all four folds
  returned 1.0. A caller who does not watch stdout is told calibration ran.

  classifier_evaluation.calibration_table accepts an out-of-range label the
  same way: y_true=[5,5] against 2 columns matches no class, so every
  observed_frequency reads 0.0 and the reliability curve looks
  catastrophically miscalibrated rather than raising.

  calibration_table on EMPTY input returns a DataFrame of shape (0, 0) -- no
  rows AND no columns -- so downstream code indexing 'class_name' or 'bin'
  gets a KeyError instead of an empty column.

DISAGREEING TWINS

  The two plot_activation_grid implementations disagree on map shape. The
  saliency one transposes a leading 3 to channels-last, so (N,H,W) and
  (N,3,H,W) both work while (N,1,H,W) raises; the Grad-CAM one has no
  transpose, so (N,3,H,W) raises there instead. Same name, same signature,
  incompatible inputs.

  utils.remove_outliers_by_group's two methods disagree on tiny groups. A
  one-row group has std=NaN, so 'zscore' DELETES it while 'iqr' keeps it.
  Verified on a 6-row frame: 'iqr' keeps the singleton and drops the 50.0
  outlier; 'zscore' drops the singleton and KEEPS the 50.0, because the
  outlier inflates its own group's std. It also accepts a NEGATIVE threshold,
  which under 'iqr' inverts the band and deletes every row of every group
  with a nonzero IQR.

ALREADY CORRECTED IN THE DOCSTRING PASS: utils.filter_and_save_csv's summary
claimed it filters for "> upper and < lower". The code uses `|`: it is a
two-tailed selection that KEEPS the extremes, and passing upper < lower makes
the conditions cover the line so nothing is filtered at all.

WHY THESE ARE LISTED RATHER THAN FIXED HERE: each changes what a figure or a
table shows, and three of them are in the plotting layer where the right fix
is a judgement about what the user should see (should a short palette raise,
cycle, or extend?). They are ranked wrong-output first.

2026-08-11 - THE SECOND DOCUMENTATION SWEEP. Each verified by execution.
--------------------------------------------------------------------------------

SILENT WRONG OUTPUT

  align.window: AN OUT-OF-RANGE CHANNEL INDEX BEHAVES DIFFERENTLY PER STORAGE
  LAYOUT. A merged (H,W,C) .npy goes through crops.MergedField.read_window,
  which validates and raises CropError. Every other layout -- 2-D .npy,
  channel-first (C,H,W), TIFF, split channel files -- has NO validation and
  silently leaves that output plane ZERO. Same call, same-looking tile, error
  or silent zeros depending only on what is on disk.

  A NEGATIVE index diverges three ways in the same function: merged raises;
  a single-file memmap wraps Python-style, so channels=[-1] silently returns
  the LAST plane; split-channel tiles fail a `0 <= group` guard and return
  zeros.

  align.window's dtype cast is a bare astype with no rescale or clip, so
  narrowing WRAPS MODULO: a uint16 pixel of 300 read with dtype='uint8'
  comes back as 44.

  layers.Canvas.for_grid with depth=None pins every out-of-plane axis at
  world 0 rather than at that axis's own translate. For a 3-D layer with
  origin z=10.0 the canvas sits off the volume and EVERY LAYER RENDERS BLANK
  -- coverage 0.0, no error, no warning. Verified: LabelsLayer and ImageLayer
  both give coverage 0.0 by default and 12.0 with depth={'z': 10.0}.

  lineage.tree_for(typed=False) RESOLVES A COLLIDING KEY TO THE WRONG FAMILY.
  With nucleus 3 in cell 8 and pathogen 3 in cell 7, both collapse to
  'plate1_r1_c1_f1_3' and the call returns cell 7 -- the first root in
  field-then-label order -- whichever the caller meant.

SHAPE THAT BREAKS BATCHING

  crop_source.crop_at never calls _resize while crop_object does, so the same
  `size` setting means "guaranteed size x size" on one path and "at most this,
  unpadded" on the other. crop_at(a, 0, 0, size=6) on a 10x10 array returns
  (3,3,1) and crop_at(a, 9, 9, size=6) returns (4,4,1): crops near a border
  silently come out a different shape, which is what breaks naive batching.
  `half = max(1, int(size) // 2)` also makes the box side always even and
  never below 2, so size=5 cuts 4 px and size=0 or -4 cut 2 px.

RESOURCE LEAKS

  database_concurrency.run_concurrency_probe leaks its temporary directory
  when journal_mode is rejected: 'MEMORY' and 'TRUNCATE' raise
  DatabaseConfigurationError from connect() AFTER mkdtemp has run, and the
  cleanup is the last statement of the function. Reproduced twice.
  A stalled worker also leaks it, but that one is deliberate -- cleanup is
  guarded by `not alive` so a hung thread's database survives for inspection.
  An EXPLICIT path is never cleaned either, which is what makes the next run
  on that path fail with FileExistsError.

QUIET COERCION

  run_concurrency_probe int()-coerces its three counts before the >= 1 check,
  so writers=2.9 becomes 2 and writes_per_writer=3.7 becomes 3 with no
  warning; strings work too. journal_mode is typed `str` but None is accepted
  and means "do not set it", so the probe reports DELETE -- a quiet non-WAL
  run rather than an error.

WHY LISTED RATHER THAN FIXED: every one is a decision about intended
behaviour, not a repair. Should an out-of-range channel raise everywhere, or
zero-fill everywhere? Should crop_at pad like crop_object, or should the
setting be renamed on one of the two paths? Ranked silent-wrong-output first;
`layers.for_grid` and `lineage.tree_for` are the two that produce a confident
wrong answer rather than a crash.
