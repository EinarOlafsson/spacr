--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

94 GIFs in `spacr/resources/setting_animations/gifs/`, described by
`manifest.json` (94 entries) and loaded through
`spacr/setting_animations.py`. `validate_setting_animation_assets()`
already exists and checks that the FILES are present and hashed -- it says

ONE KNOWN INACCURACY, reported by the maintainer:

    the "remove edge objects" animation removes one edge object AND one
    object that is not on the edge.

The border-object family is four files, so the fault may be in all of them:

    cell_remove_border_objects.gif
    nucleus_remove_border_objects.gif
    organelle_remove_border_objects.gif
    pathogen_remove_border_objects.gif

The stated cause is "animation misalignment during animation generation" --
i.e. the before and after frames came from runs that do not correspond, so
the difference between them is not the difference the setting makes.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

An animation is a stronger claim than a sentence. A user who reads "removes
objects touching the image border" and sees a non-border object vanish will
believe the picture, and will then either avoid a setting they needed or
distrust the ones next to it.

It is also the hardest kind of documentation error to notice: it looks
finished. Nothing fails, the asset validator passes, and the only way to
find it is for someone to watch 94 short loops and think about each one --
which is what this task is.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Find the GENERATOR. These were produced by a script, and if the cause is
   misalignment then the fix belongs there rather than in the GIFs -- a
   hand-patched asset regenerates wrong the next time.
2. Fix the border-object family first, since it is reported and specific.
   The correct animation shows exactly the objects touching the border
   disappearing, and nothing else changing between the frames.
3. Then audit all 94. For each: does the visible difference between the
   before and after frames equal the difference the setting makes, and
   nothing more? Record the verdict per animation here so a second pass
   does not start from zero.
4. Where before/after frames are generated separately, make them share a
   SEED and an input image. Misalignment of exactly this kind is what
   happens when two runs are allowed to differ in more than the one
   variable being illustrated.
5. Consider whether the validator can grow a real check. It cannot judge
   meaning, but it can assert that a before/after pair differs in only the
   region the setting is documented to affect -- which would have caught
   this one.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

The four border-object animations each show only border-touching objects
being removed. Every one of the 94 has a recorded verdict, and the ones
found wrong have been regenerated from a fixed generator rather than
edited.

2026-08-09 - WHY THE *_diameter ANIMATIONS SHOW NOTHING. CAUSE FOUND.
--------------------------------------------------------------------------------

`tools/generate_setting_animations.py :: _diameter_scene`:

    radius = 64 if kind == "cell" else 40        # NEVER changes
    extent = radius * (0.35 + 0.65 * action)     # only the caliper moves

The object outline is drawn at a FIXED radius. The only thing that
animates is a measuring line of width 0.5 and two 10-pixel tick marks.
That is a few hundred pixels of a 360x360 frame, which is exactly the
0.0-0.2% the audit measured, and it explains why the whole *_diameter
family sits at the bottom of the list.

It is also the wrong illustration. `diameter` tells Cellpose what size an
object is expected to be; drawing a caliper that grows across an object
that never changes size shows the measurement, not the setting. A viewer
learns "diameter is a width" -- which they knew -- and nothing about what
changing it does.

THE FIX IS IN THE GENERATOR, and it is small: scale the outline with
`action` so the object grows as the setting grows, keeping the caliper as
the annotation rather than the subject. Something like

    scale = 0.55 + 0.45 * action
    _object_outline(painter, kind, center,
                    (radius * scale, radius * scale * 0.8), 1.0, 0.4)

NOT APPLIED HERE. Regenerating touches 94 GIF assets and every hash in
`manifest.json`, and the honest way to do that is one run of the generator
followed by `validate_animations_show_something()` over the result -- which
now exists and would confirm the whole family clears 1%. That is a
contained job for someone who can eyeball the output, and doing it blind
from a diff is how you ship 94 subtly wrong pictures.

The border-object family (the original report) still needs its own look:
that one removes a non-edge object, which is a different scene function.

2026-08-09 - THE BORDER-OBJECT FAMILY IS FIXED. THE ORIGINAL REPORT WAS RIGHT,
             AND EVERY EARLIER MEASUREMENT OF IT IN THIS FILE WAS WRONG.
--------------------------------------------------------------------------------

The maintainer said it removes one edge object AND one that is not. That is
exactly what it did. Both of the audits recorded above -- the "CONFIRMED,
MEASURED" entry and the all-94 sweep -- measured something else and got a
right answer for wrong reasons, so the METHOD is the part worth keeping.

TWO CAUSES, both geometry, neither visible to a pixel diff:

  1. The object at (278, 18) was flagged `touches=True` while sitting wholly
     INSIDE the well: it spans x[263,293] y[66.5,89.5], and the well edge is
     at 348. It was removed because a boolean said so. Only ONE of the four
     objects actually crossed the edge.

  2. The close camera was (205, 0, 360, 155), which does not contain the
     objects that are KEPT. At full zoom one interior object was entirely
     off-screen and, for `cell`, a second was cut in half. They leave the
     frame during the zoom, which a viewer cannot tell from removal. So the
     animation appeared to remove three objects, one of them interior.

WHY THE EARLIER MEASUREMENTS MISSED IT, which is the reusable warning:

  * "after = the frame most different from frame 0" is wrong for THIS scene.
    Frame 0 is fully zoomed OUT. The most-different frame is fully zoomed IN,
    so that diff is dominated by the CAMERA, and every object registers as
    changed. That is where "interior: 3 / 4 / 18 / 6" came from -- it is the
    zoom, not the setting. The scene needs two frames at the SAME zoom
    (render frames 13 and 21; `remove` goes 0 -> 1 while `zoom` stays 1.0).
  * Holding zoom constant and classifying by the scene's own `touches` flag
    ALSO passes -- it validates the generator against itself. It reported
    "ALL CORRECT" on the broken assets. The flag is the thing under test, so
    the check must use the drawn well rectangle instead.
  * GIF frame index != render index. Pillow drops consecutive identical
    frames and accumulates their duration, so these 28-frame renders are
    stored as 20 frames (and other animations as 7 to 18). Any check that
    maps a phase to a stored index is off by however many frames collapsed.

THE FIX, in the generator:

    close   = (228.0, 70.5, 378.0, 220.5)   # contains all four objects
    removed = (348, 40+Y_OFFSET), (350, 130+Y_OFFSET)   # straddle x=348
    kept    = (255, 45+Y_OFFSET), (262, 135+Y_OFFSET)   # clear of it

Now two objects visibly straddle the well edge and vanish while two visibly
inside it stay on screen and survive -- which is the setting.

AND A GATE, `_assert_border_layout`, run on every render: it refuses to draw
the scene if a flagged object does not cross the well edge, if a kept object
does cross it, or if any object is not contained in the close camera. It
rejects the layout that shipped, by name. That is step 5 of WHAT TO DO,
except on geometry rather than pixels -- pixels could not have caught this.

    visible change   cell 16.4%   nucleus 13.5%   organelle 13.5%   pathogen 21.1%
    asset validator  PASS (94 manifest entries, all_to_mip intact)
    tests            tests/test_border_animation_geometry.py, 15 tests

Regenerated with `--only`, per the warning above; 4 GIFs and the manifest
changed, nothing else.

2026-08-09 - TWO MORE SCENE FUNCTIONS FIXED. 27 -> 8 UNDER THRESHOLD.
--------------------------------------------------------------------------------

Grouping the under-threshold list BY SCENE FUNCTION is what made this cheap.
23 animations were 8 distinct scenes, and two of them held 15:

  _filter_scene   8 animations   min_area, min_intensity_percentile x4 kinds
  _umap_scene     7 animations   plot_points, min_dist, dot_size, ...

_filter_scene faded exactly ONE object. For `maximum`/`bright` that object
is the largest of four and measured 2.7-4.8%; for `minimum`/`dim` it is the
SMALLEST and measured 0.2-0.9%. Identical code -- the variants differ only
in which object they fade -- so the whole min family sat at the bottom for a
reason that had nothing to do with the settings. But the real fault is that
these are THRESHOLDS: everything past the threshold is discarded, not one
representative object. Now a threshold sweeps through the objects in order,
smallest-first or dimmest-first, and one always survives. 3-19% each.

_umap_scene drew three clusters of five dots at radius 1.5. That is about
106 px of a 129,600 px frame, so an animation changing EVERY point still
measured a fifth of a percent -- no per-animation fix could have worked, and
seven of them were under threshold for that single structural reason. Now 15
points per cluster on a deterministic golden-angle spiral (no RNG, so
regeneration is reproducible) at a shared DOT_RADIUS. It also just looks
like an embedding now instead of a diagram.

plot_by_cluster was additionally illustrating the WRONG THING: it grew one
thumbnail by two pixels. The setting chooses whether the overlaid thumbnails
are sampled per cluster or at random across the whole map -- so it now shows
that contrast, with a cluster left unrepresented when the setting is off.
Checking `settings.py` for what a setting MEANS before redrawing it caught
this; the spec title ("Sample images by cluster") was the clue.

A TEST THAT PINNED THE BUG. `test_the_known_offenders_are_caught` asserted
`remove_cluster_noise` was still broken, so fixing it failed the suite. Its
own docstring admitted the slug "has to be re-pointed whenever the named one
is fixed" -- a test that fails on success. Replaced with a RATCHET (the
count may fall, never rise) plus a per-family regression guard, which is the
shape this should have had.

    under 1%   27 -> 23 (diameter) -> 15 (filter) -> 8 (umap)

The last eight were one-offs rather than a family, and six shared a cause:
the subject was drawn too small to see. Nucleus objects at 14x11 in a 360px
frame (CP_prob), 16x12 (Signal_to_noise), organelles at 10x8

displayed small in a tooltip, where a 10px object is not visible at all.

Two needed redrawing rather than resizing:

  _fill_holes faded a hole-sized OUTLINE RING. That reads as a circle being
  rubbed out, not as a hole being filled. Now the background is punched
  through the mask and the fill closes over it, with three holes, since the
  setting fills all of them and real masks have more than one.

  timelapse_memory faded a single cell. The setting is how many CONSECUTIVE
  frames an object may go missing and still be linked, so it now shows a run
  of missed detections with the track surviving across the gap.

mask_within_cells needed both: enlarging the organelles pushed them outside
the cell, because every "inside" one had been sitting ON the cell boundary
and only looked contained at 10x8. The cell had to grow to visibly hold
them. Caught by looking at the render, which no measurement would have
flagged -- the pixel count went UP while the picture became wrong.
