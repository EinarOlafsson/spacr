WHY IT MATTERS
--------------------------------------------------------------------------------

A user on a cluster does not choose their Python. If 3.9 or 3.10 is broken
they cannot run spaCR at all, and the failure arrives as an import error
with no indication that the version is the problem.

"Optimal versions" is the other half and the subtler one. A floor that is
declared too low is worse than one declared too high: pip will happily
resolve to it, the install succeeds, and the failure comes later and
somewhere else -- exactly the cellpose case above, where the recorded API
and the minimum version disagree about what a function takes.

"OPTIMAL" IS DEFINED, AND BOTH READINGS KEEP THEIR JOB
--------------------------------------------------------------------------------

The two readings do imply opposite CI jobs, and both jobs stay -- because
they answer different questions and only one of them is a recommendation.

    WHAT A USER GETS is the NEWEST version in each declared range. `pip
    install spacr` resolves the top of every range, so the upper end is what
    spaCR is recommending. `Fast / Full suite control` installs with no
    constraints file at all and runs the suite against whatever pip picks
    that day.

    WHAT A USER IS PROMISED is the floor. A lower bound is for an environment
    pinned by something else -- a cluster module, a conda solve, another
    package's cap. It is not advice. `Minimum dependencies` installs
    .github/constraints/minimum-py39.txt on CPython 3.9 and runs the same
    selection there, which is what makes a declared floor a tested claim.

Written where the bounds are, not only here: setup.py carries the decision
under the heading WHAT "THE OPTIMAL DEPENDENCY VERSIONS" MEANS, each of the
two jobs says which end it is, and the constraints file states the rule it
executes. tests/test_optimal_dependency_versions.py holds the shape -- both
ends blocking, the floor end constrained, the newest end unconstrained, both
running one selection, and no pin above a floor without a recorded reason.

THREE FLOORS WERE NOT THE VERSION CI INSTALLS, which is the defect that rule
exists to catch. A pin quietly above its floor leaves the floor the one bound
in setup.py that nothing installs and nothing tests. Two are raised to the
version the minimum job runs:

    pyarrow        >=14      -> >=14.0.2
    pytest-xdist   >=3.6     -> >=3.6.1

The third is recorded rather than raised, and the reason is a real
cross-ecosystem disagreement rather than caution. `nvidia-ml-py` numbers its
PyPI releases after the NVIDIA driver, so `>=11.5` is a boundary and not a
release -- 11.450.51 is the first that satisfies it. The conda-forge recipe
declares the same dependency under its conda name `pynvml`, whose numbers
are NOT driver numbers: 11.5.0 is a real conda package there. Raising the
PyPI floor alone would put the two ecosystems on different versions, and
tests/test_conda_forge_recipe.py would refuse it. The gap is named in the
constraints file, which is what the rule allows.

The four pins that ARE above their floors for the ordinary reason stay,
because the floors cannot be installed together and the constraints file
names each one: torch and torchvision pull sympy up, umap-learn pulls
scikit-learn up, tensorboard pulls protobuf up.

WHY NOT A LOCKFILE, restated because it is the tempting answer: on Python 3.9
the newest resolvable IPython is 8.18.1 and on 3.11+ it is 9.16.1; matplotlib
is 3.9.4 versus 3.11.1. There is no single newest-that-works set across six
interpreters, so a file claiming one would be wrong on 3.9 the day it was
written.

    setup.py                                nvidia-ml-py>=11.5,<14

THE DECISION IS NOT A TRADE, which is why it can be made without the
ecosystem question being answered first. nvidia-ml-py names every release
after the NVIDIA driver it binds, so its published sequence runs 10.418.84,
11.450.51, 11.460.79, ..., 13.610.43 and the MIDDLE FIELD IS A DRIVER BRANCH.
`11.450.51` therefore sorts ABOVE a plausible-looking `11.5`, and nothing is
published between the two. Both spellings admit exactly the same 31 releases
in the `<14` band -- checked against PyPI metadata, not inferred -- so
declaring the exact release denies a user nothing at all.

What it buys is that the floor can be PINNED. A bound no release equals is a
bound the `Minimum dependencies` job cannot install, so it was the one lower
bound in setup.py that nothing ran the suite against, and the only reason
that was survivable is that pip resolves such a bound silently to the nearest
real release above it. That is the same failure mode as the cellpose floor,
in the one package whose numbering makes it look reasonable.

WRITTEN DOWN SO IT IS NOT "FIXED" BACK. The floor reads like a typo -- 450
where a minor version belongs -- and the obvious repair, to 11.5 or 11.45 or
11.4.50.51, restores a bound that can never be equalled. setup.py says so at
length beside the requirement, the constraints file says the pin is not an
exception any more, and tests/test_dependency_floors_name_a_published_release
.py holds it: the declared floor must be one of the recorded published
releases, the minimum profile must pin exactly that floor, and a
`network`-marked test asks PyPI the same question so the recorded list cannot
quietly go stale.

    conda-forge nvidia-ml-py   noarch, 11.450.51 ... 13.610.43 -- the SAME
                               driver-numbered releases as PyPI
    conda-forge pynvml         8.0.1 ... 13.0.1 -- the gpuopenanalytics
                               distribution, i.e. the deprecated
                               compatibility wrapper, which from 12.0.0 is a
                               shim that depends on `nvidia-ml-py >=12.0.0`

So `pynvml >=11.5,<14` in the recipe is not a differently-numbered spelling
of the same dependency. It is a DIFFERENT PACKAGE, and specifically the one
setup.py deliberately stopped declaring because importing it makes both spaCR
and torch.cuda print a FutureWarning at startup. Worse, `>=11.5,<14` lets
conda resolve pynvml 11.5.0 or 11.5.3, which predate the shim and do not
depend on nvidia-ml-py at all -- so a conda user gets the retired wrapper
implementation rather than NVIDIA's maintained bindings.

The repair is two lines and is NOT applied here, because neither file is in
this session's territory:

    conda-forge/recipe/recipe.yaml    - pynvml >=11.5,<14
                                  ->  - nvidia-ml-py >=11.450.51,<14
    tests/test_conda_forge_recipe.py  delete the `"nvidia-ml-py": "pynvml",`
                                      row from CONDA_NAMES; conda-forge uses
                                      the PyPI name, so no translation is
                                      needed

Until that lands, tests/test_conda_forge_recipe.py::
test_no_conda_recipe_floor_is_below_the_one_setup_py_declares is RED, and it
is red for the right reason: the recipe floor really is below the one
setup.py declares.
