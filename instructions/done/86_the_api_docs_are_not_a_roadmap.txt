--------------------------------------------------------------------------------
THE ANSWER TO THE QUESTION
--------------------------------------------------------------------------------

No, it is not a convention. API reference documents the public interface --
modules, classes, signatures, parameters, returns, raises -- so a reader can
call the thing. `docs/source/module_audit.rst` is an internal engineering
record from 2026-07-30 plus a set of recommendations addressed to the
maintainer, and it sits in `index.rst`'s toctree where users read it. A
reader meets "High-value additions" as a list of features spaCR does not
have, in the same document that is supposed to tell them what it does.

Its first half -- the cross-cutting guarantees and the module-by-module
execution map -- is genuinely useful and genuinely NOT API reference. It is
an architecture note. Moving it out of the published API rather than
deleting it outright preserves that, and this instruction says where.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Drop `module_audit` from `docs/source/index.rst`'s toctree so it stops
   being published as API documentation.
2. Keep the execution map and the cross-cutting guarantees as an internal
   architecture note, not in the API tree.
3. Delete the recommendation sections from the page entirely -- they are
   preserved below, which is where work belongs.

2026-08-13 - INSIGHT (e), THE BENCHMARK COMMAND, IS BUILT
--------------------------------------------------------------------------------

`spacr/benchmark.py`. `benchmark(work, items)` runs the real work over a few
representative units and records throughput, peak RSS and peak VRAM;
`recommend_workers(measurement)` turns that into a worker count;
`format_report` prints both as a few lines a user can paste into an issue.

WHY THIS IS WORTH HAVING, stated because the existing defaults look
reasonable. Every worker default in spaCR is arithmetic on the core count --
`cpu_count() - 4`, `cpu_count() // 2`, `-1`. Cores are the one thing that is
never the binding constraint on a measurement run: a field is hundreds of
megabytes decompressed, so eight workers on a 16-core laptop with 16 GB swap
long before they saturate the CPU. The number that decides is how much MEMORY
one worker needs for one field, which is a property of the plate and the
machine and cannot be derived from `cpu_count()`.

DECISIONS WORTH KEEPING:

  * IT MEASURES, IT DOES NOT TUNE. Nothing here writes a setting, and a test
    asserts that by scanning the module for `settings[`, `save_settings` and
    `os.environ[`. A benchmark that silently changed `n_jobs` would make a
    run's speed depend on when the benchmark last ran.
  * SERIAL ON PURPOSE. The question is what ONE worker needs; running them in
    parallel measures the sum and hides the per-worker figure the
    recommendation divides by.
  * A WARM-UP ITEM RUNS BUT IS NOT TIMED. The first field pays for imports,
    the CUDA context and page faults no later field pays again.
  * `MemAvailable`, NOT total, minus a 2 GiB reserve. Sizing workers against
    total memory is how a run is OOM-killed at field 900.
  * VRAM IS `None` WITHOUT CUDA, not 0. "Not measured" and "measured, and it
    used none" are different answers.
  * `ru_maxrss` IS KILOBYTES ON LINUX AND BYTES ON macOS. Getting that
    backwards is a factor of 1024 in a memory budget -- one worker on a large
    machine, or forty on a small one.
  * The recommendation carries its evidence (cores, available bytes, the
    measurement) and its reason, so a number a user disagrees with can be
    argued with rather than only overridden.

20 tests, Qt-free, registered in `_SUBMODULES`.

70's CONCLUSION (do not make it a dependency) holds. 70's stated REASON is

    cuml-cu12 26.8.0
      requires_python   >=3.11

      numpy             >=2.0

AS A HARD DEPENDENCY IT IS IMPOSSIBLE, and not marginally: it would drop
Python 3.9, 3.10, 3.13 and 3.14 -- four of the six interpreters spaCR
promises -- because cuML declares 3.11-3.12 only. It would also raise the
numpy floor to 2.0 (which has no cp39 wheels) and scipy to 1.14 (which needs

AS AN OPTIONAL EXTRA IT IS FINE, and this is the maintainer's point. An extra
does not constrain the base resolution: `pip install spacr` is untouched on
every interpreter, and `pip install spacr[rapids]` resolves only for someone
on 3.11/3.12 with CUDA 12 who asked for it. TORCH IS NOT A CONFLICT -- this
machine runs torch 2.9.1+cu128 and cuML wants cuda-toolkit 12.*, the same
major.

ONE NUMBER TO NOT MISREAD: the cuml-cu12 wheel is 6 MB. That is not the
footprint. It pulls libcuml-cu12, cudf-cu12, cupy-cuda12x and the CUDA
toolkit libraries, which is gigabytes -- so "12 MB" is not an argument for
making it a dependency either.

RECOMMENDATION, unchanged in substance from the earlier note but now with
the evidence: ship it as `spacr[rapids]`, keep the CPU path the tested and
default one, and gate the code on a runtime import that falls back silently.
The conda-forge recipe (59) must NOT list it, which an extra makes automatic.

2026-08-13 - EVERY EXTRA MUST BE REACHABLE FROM THE INSTALLERS
--------------------------------------------------------------------------------

Requested: 2026-08-13 - "by the way all the extra options need to be
           available via the installers as well add this to the instructions"

So an optional extra is not finished when `pip install spacr[rapids]` works.
The .exe, the .pkg and the .run are how most users arrive, and an extra only
a pip user can reach is an extra most users do not have.

WHAT THIS MEANS CONCRETELY, and it lands on instructions 44, 45 and 53:

  * The online installers already resolve dependencies at install time
    (`packaging/online/install_spacr_*.{ps1,sh}`), so they are the natural
    place: the extra becomes a CHOICE on the way through, not a second
    installation afterwards.
  * The choice must state its cost and its constraint. `rapids` pulls
    gigabytes of CUDA libraries and REQUIRES Python 3.11 or 3.12 -- an
    installer that offers it on 3.13 produces a resolver error the user
    cannot read. Offer it only where it can succeed, and say why when it
    cannot.
  * DEFAULT OFF, always. An extra that installs itself is a dependency
    wearing a different hat, and the whole reason `rapids` is an extra is
    that it must not reach anyone who did not ask.
  * The same applies to `attribution` (torchcam) and any extra added later,
    so this is a rule about the installer's shape rather than about rapids.

44 already covers the CPU-vs-GPU choice at install time; this is the same
dialog gaining a row per extra rather than a new mechanism.

(c) THE NOTE ABOVE SAYS "the settings are recorded, the INPUTS are not". THAT
IS FALSE, and it is the sixth instruction file this week to be wrong about
what already exists. `run_journal` hashes all of it:

    settings_sha256       full SHA-256 of settings.json
    input_hashes          per-file sha256 + size + mtime for every file under
                          every path-valued setting
    input_tree_sha256     a digest over that whole map
    output_hashes         only files whose (size, mtime) CHANGED during the
                          run, so an output is distinguished from an input
                          that happened to sit in the same folder
    output_tree_sha256
    model_hashes          checkpoints, already surfaced in the report
    input_hashing         "on" or "skipped", stated rather than implied

THE MISSING HALF WAS THE LAST MILE, and it is exactly the half the insight
named: "so REPORTS can prove which source state produced them". The manifest
had the digests; `spacr/report.py` -- the one artefact a collaborator
actually receives -- carried only the model hashes. Two runs of the same code
on two different plates produced byte-identical provenance sections.

BUILT: `report._fingerprints`, rendered into the provenance section.

THE DESIGN POINT WORTH KEEPING. There are THREE outcomes and they must not
look alike, because an absent fingerprint that reads as an absent difference
is a FALSE ASSURANCE -- worse than printing nothing:

    digests present        the report can be verified against the data
    input_hashing skipped  a CHOICE the run made; say so, and say that
                           re-running with it on is what makes the report
                           verifiable
    schema_version < 2     the field did not exist yet, so nothing was
                           declined and nothing is missing

That is this module's own "a missing section is stated, never omitted" rule
applied to a digest, where the cost of getting it wrong is highest.

PER RUN, NEVER MERGED, unlike the model hashes directly above it in the same
section. A tree digest identifies ONE run's view of the data; combining two
produces a number that matches neither and can be checked against nothing.

When hashing was skipped the tree digests are suppressed rather than printed
as stale -- printing them would assert a verification that did not happen.

report, report coverage and run_journal.

2026-08-13 - (a) THE DRY-RUN RESOURCE CARD IS BUILT
--------------------------------------------------------------------------------

`validate.describe_resources`, printed by `run_preflight` right after
`describe_plan`. Built ON the existing pre-flight as the note above required,
not beside it -- there is still one card.

WHY IT IS A SECOND FUNCTION AND NOT MORE ROWS IN describe_plan. The plan
answers "what would this do", and every number in it is a COUNT of something
that exists. The card answers "can this machine finish it", and every number
in it is a PROJECTION. Merged, a projection would be read with the confidence
of a count.

THE RULE, WHICH IS THE WHOLE DESIGN: a figure that cannot be derived is NAMED
AND LEFT OUT, never guessed. A fabricated ceiling that a run then sails past
is worse than no card at all, because the user stopped watching.

  MEASURED, off this machine        bytes on disk; the shape and dtype of one
                                    real .npy, read memory-mapped so the
                                    header is read and the pixels are not;
                                    MemAvailable; free space on the volume
                                    that would be written to
  DERIVED, AND SAID TO BE           memory is a FLOOR -- n_jobs workers each
                                    holding one field, before a single
                                    working copy. A floor is defensible and
                                    still catches the case that matters,
                                    which is eight workers holding a 900 MB
                                    field each on a 16 GB laptop. The card
                                    points at `spacr.benchmark` for the
                                    measured peak rather than inventing a
                                    multiplier for it
  REFUSED, AND NAMED                the PNG crop tree. It is objects x crop
                                    modes and the object count is what the
                                    run exists to discover, so a number there
                                    would be wrong by an order of magnitude
                                    in either direction

WHEN n_jobs DOES NOT FIT the card says so and names one that would, computed
from the per-field figure against MemAvailable less a 2 GiB reserve -- the
same reserve `benchmark` uses, and for the same reason.

THE TRAP IT STATES OUT LOUD: merged/ is uncompressed .npy, so it can be
LARGER than a compressed TIFF source rather than the same size. That is the
disk projection people get wrong.

TORCH IS READ OUT OF `sys.modules`, NEVER IMPORTED. This module's reason to
exist is that it stays light enough to run before anything heavy is loaded,
and `test_validate_does_not_import_torch_or_cellpose` enforces it -- a lazy
import inside the function would still be an import, and would still cost
seconds on a cluster node that only wanted its settings checked. So the card
reports the device when the process already has torch and says plainly that
it did not look when it does not, because SILENCE WOULD READ AS "no GPU",
which is a different answer. The GPU row appears for `mask` only; measure
loads no model and a VRAM figure there is noise.

The card is best-effort inside `run_preflight`: it stats the disk, and a
pre-flight that raises has denied the user the report it exists to give
them. The failure path is tested rather than pragma'd.

24 tests. Every line of the new code is covered; 103 pass in test_validate,
827 across the pre-flight-adjacent suites.

    spacr/checkpoint.py   CheckpointStore: one atomic JSON document per
                          workflow, written to a temporary sibling and
                          os.replace'd, with a `fingerprint` of the settings
                          and input identity that a resume is REFUSED against
                          when it differs. Standard library only, on purpose:
                          Mask and Measure consult resume state before loading
                          torch, so this must not make that import heavier.
    spacr/resume.py       the field-level half -- completed_fields_in_merged,
                          completed_fields_in_db, plan_measure_resume,
                          run_already_complete, SettingsComparison, and
                          clear_field_rows.

WIRED, all four of the five the insight names:

    Mask         core.py passes resume= into the mask writers; io.py:3286
                 reads completed_fields_in_merged
    Measure      measure.py:3410 calls plan_measure_resume, deliberately
                 BEFORE _save_settings_to_db, because that writes the settings
                 table with if_exists='replace' and would destroy the record
                 of the run being resumed -- which is what the comparison
                 reads
    UMAP search  hyperparam.py:665 opens a CheckpointStore
    Conversion   convert.py:1833 opens one

THE DELETE-BEFORE-INSERT THE NOTE WARNS ABOUT IS THERE. `clear_field_rows` is
called from `plan_measure_resume` (resume.py:2147). I first reported it as
called by nothing; that was a grep that excluded resume.py itself, and the
claim was wrong. It clears every table for a pending field inside one BEGIN
IMMEDIATE, keyed on the four identity columns rather than on a name prefix so
clearing f1 cannot touch f10, and refuses any table not on
MEASURE_OWNED_TABLES -- measurements.db is shared, and clearing a field out of
conversion_map would destroy the only record of how the project's files were
named.

REPORT GENERATION IS THE ONE WITHOUT A CHECKPOINT, AND SHOULD NOT HAVE ONE.
It reads a finished folder and writes one file; it is minutes at most and
re-running it overwrites cleanly. A checkpoint there would be machinery
guarding against a cost that does not exist, and every checkpoint is a second
thing that can disagree with the data.

176 tests already cover this across test_checkpoint, test_resume and
test_resume_owned_tables.
