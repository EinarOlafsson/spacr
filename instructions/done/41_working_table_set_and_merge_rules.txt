--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

The Gate Editor's table dropdown SWITCHES tables: picking nucleus replaces
cell. Only one table is ever in play, so a gate can never be drawn on a cell
measurement against a pathogen measurement.

The aggregation logic the user refers to already exists in spaCR -- the old
read-and-merge-tables functions in spacr/io.py (`_read_and_join_tables` and
around it) already aggregate child objects onto a parent. Whatever rules are
in there are the starting point and must not be reinvented: reimplementing
them slightly differently would give two answers to the same question
depending on which screen asked.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The aggregation rule has to follow the MEASUREMENT, not the column type. Four
pathogens in one cell:

  * area, integrated intensity, counts        -> SUM
  * minimum intensity                         -> MIN of the objects
  * maximum intensity                         -> MAX of the objects
  * mean, median                              -> the object mean / median

Averaging all of them, which is what a naive groupby-mean does, silently
answers a different question for every column: it turns four pathogens' total
area into an average area, and it turns a minimum into a mean of minima, which
is not a minimum of anything.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

THE WORKING SET

 1. The dropdown ADDS a table to the working set instead of switching to it.
 2. The first table (cell, or whichever the filters anchor logic picks) loads
    automatically and is itself a member of the set.
 3. Each member shows as a small blue rounded chip with an x to remove it,
    including the first.
 4. The COMBINATION of tables is what the module works on, so the axis
    pickers offer measurements from all of them.

MERGE SETTINGS

 5. A merge section in the settings window with, at least:
      - the PRIMARY object -- what everything else is aggregated onto;
      - how values are averaged / aggregated;
      - how N/A is handled.
    Dropdowns with several options, not booleans.
 6. Aggregation is chosen PER COLUMN by what the column measures, defaulting
    as above. Reuse the existing logic from the old read-and-merge-tables
    functions rather than writing a second set of rules.
 7. The rule applied to each column should be visible to the user and
    overridable -- a silent default that is right 95% of the time is a wrong
    answer nobody can find the other 5%.

--------------------------------------------------------------------------------
NOTES
--------------------------------------------------------------------------------

This depends on instruction 40: aggregating pathogens onto their cell needs
to know WHICH cell, which is what the relationships table is for. Do 40 first,
or this ends up carrying its own private join.

Ask the user where the old read-and-merge logic lives if it is not obvious --
they said "i have logic for this in my olf rad and merge tables functions",
and matching it exactly matters more than rederiving it.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * Opening a database loads cell automatically, shown as a removable chip.
  * Clicking nucleus in the dropdown ADDS it; both chips are present and the
    axis pickers offer measurements from both.
  * Removing a chip removes that table's measurements from the pickers, and
    any gate drawn on them says so rather than vanishing silently.
  * One cell with four pathogens: pathogen area sums, integrated intensity
    sums, min intensity is the minimum of the four, max is the maximum, mean
    is the mean. Verified against a hand-built table where all five answers
    differ.
  * The N/A policy and the primary object are settings, and changing them
    changes the merged table.
  * The rule chosen per column is visible and can be overridden.

--------------------------------------------------------------------------------
2026-08-26 -- RE-AUDIT: THE ARITHMETIC IS RIGHT; ONE GATE COST ALL THE OTHERS
--------------------------------------------------------------------------------

THE NUMBERS, hand-checked rather than trusted. One cell with four pathogens,
built so all five answers differ, through `merge_tables(db, ["cell",
"pathogen"])`:

    areas    1, 2, 4, 8        -> pathogen_area                    15  (sum)
    integ    5, 6, 7, 8        -> ..._integrated_intensity         26  (sum)
    inten    10, 20, 30, 100   -> ..._min_intensity                10  (min)
                               -> ..._max_intensity               100  (max)
                               -> ..._mean_intensity               40  (mean)

Every one as the criterion asks. `pathogen_count` and `pathogen_measured`
come along, which is what makes a childless parent distinguishable from one
with four.

WHAT WAS BROKEN: "Removing a chip removes that table's measurements from the
pickers, and any gate drawn on them says so rather than vanishing silently."

`GateTree._rebuild` called `GateSet.stats`, which is ALL-OR-NOTHING: it walks
every gate and the first one whose columns are absent raises, so the except
branch blanked the counts for EVERY gate. Dropping the nucleus table cost the
cell gates their numbers too -- the opposite of removing one table's
measurements -- and the gate that actually could not be answered said nothing
about why, since a blank cell reads as zero or as a slow redraw.

FIXED. `GateTree._gate_stats` falls back to evaluating gate by gate, so a
gate that cannot be answered loses only its own row, and that row now reads
`GateTree.UNAVAILABLE` in the count column with the missing measurement named
in its tooltip.

`tests/qt/test_a_gate_on_a_removed_table_says_so.py` -- three tests, two
confirmed RED before the fix.
`test_gates_that_do_not_fit_this_table_are_still_listed_without_counts`
pinned the blank cell; updated to the new text with the reason recorded in
it, its own property ("an uncomputable count was printed as a number")
unchanged.

NOTED, NOT CHANGED -- a deliberate deviation from this file's first
criterion. "Opening a database loads cell automatically, shown as a REMOVABLE
chip": the chip for the LAST remaining table is deliberately not removable
(`_rebuild_chips` passes `removable=len(self._tables) > 1`, and
`remove_table` refuses), because a Gate Editor with no table is a screen with
nothing on it. Recorded here so the next audit does not read it as drift.
