--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Three separate observations, one of which is serious.

  1. "Score" does not say WHICH score. The column is filled from
     `result.metric`, which is whatever criterion was chosen --
     trustworthiness, multi_objective, and so on. The header should say the
     name, not the word "score".

  2. "Fold SD" is always NA for UMAP. It is a cross-validation quantity and
     UMAP does not cross-validate -- there is one embedding per trial, so
     there is no fold to take a standard deviation over. A column that is
     structurally always empty for this module should not be shown by it.

  3. THE WALK DOES NOT SEEM TO IMPROVE. This is the one to chase. A Walk
     moves to the best configuration in each neighbourhood and stops when a
     round fails to beat the best score so far, so successive rounds should
     show non-decreasing best scores.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

(1) and (2) cost the user a guess and a wasted column. (3) would mean the
search is not doing the thing it is named after -- and a hyperparameter
search that reports scores without climbing is worse than none, because the
user trusts the winner it picks.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Name the column after the criterion. `SearchResult.metric` already
   carries it, so the header is a lookup, not new state.
2. Hide Fold SD for UMAP the way other module-specific columns are hidden.
   Do not fill it with a fake number.
3. CHASE THE CONVERGENCE, and instrument before concluding:
     * log the best-so-far after each round and confirm it is monotonic;
       `walk_search` only accepts a round when `gain > improvement_floor`,
       so if the table shows the best getting worse, the acceptance rule is
       not being applied to what the table displays;
     * check whether the TABLE is showing trials in arrival order rather
       than the walk's accepted centres -- arrival order legitimately goes
       up and down, since every neighbour is scored including the bad ones.
       That would make the display wrong and the search right, which is the
       most likely explanation and the cheapest to check;
     * confirm `_select_best` is choosing by the same metric the column
       shows, especially under `multi_objective`.
4. If the search really is not climbing, the note in `walk_search` about
   the FIRST round always being accepted (gain is infinite when there is no
   best score yet) is where to start reading.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

The table's score column is headed with the criterion name; Fold SD is
absent for UMAP; and a Walk over a real dataset shows a best-so-far that
never decreases, with the winner matching the highest value in the table.

--------------------------------------------------------------------------------
2026-08-09 - DONE. THE WALK WAS CLIMBING ALL ALONG.
--------------------------------------------------------------------------------

The file said to check the cheap explanation first -- that the table shows
ARRIVAL order rather than accepted centres -- and that is exactly what it
was. Measured on a landscape with a known optimum:

    arrival order   0.663 0.672 0.679 0.683 0.669 0.691 0.662 0.705 ...
    best-so-far     0.663 0.672 0.679 0.683 0.683 0.691 0.691 0.705 ...

Best-so-far is monotonic and the winner equals the table maximum. The
search is correct: a Walk scores every NEIGHBOUR of its centre, including
the ones it rejects, so the score column legitimately goes up and down. A
"best so far" column now shows the climb, which is the number the user was
looking for.

"SCORE" now carries the criterion's own name and follows the dropdown --
trustworthiness, continuity, and so on. A column headed "score" cannot say
whether it holds trustworthiness or a multi-objective blend.

"FOLD SD" is hidden for UMAP. It was structurally always NA -- one
embedding per trial means no folds to take a standard deviation over --
and a column of NA invites the reader to wonder what went wrong when
nothing did. Classify and ml_analyze keep it; they cross-validate.

A SIDE EFFECT WORTH KEEPING: inserting a column broke nine test assertions
that hard-coded column NUMBERS while being about parameters and status.
They now look the column up by NAME. The names are stable; the positions
never were.
