WHY IT MATTERS
--------------------------------------------------------------------------------

Not because three tests are red. Because a suite with known-red tests in it
trains everybody to read a failure list rather than a pass/fail, and the next
genuinely new failure in those files will be assumed to be one of these. Two
of the three concern the OUTLINE MODEL card, which is what tells a user
whether the outlines they are annotating against came from a model at all --
so if they are failing for a real reason, the thing being untested is a
correctness claim, not a cosmetic one.

Instruction 288 counts on `tests/qt` being green to mean something.

2026-09-02 — DONE. TWO STALE, ONE STALE FOR A DIFFERENT REASON.
--------------------------------------------------------------------------------

All three were STALE, and step 1's instruction to establish which side is
wrong before touching either was worth following: the code was right in all
three cases and in two of them was right for a reason the test could not see.

1 and 2. THE TWO TORCH-MODEL CARD TESTS. Both asserted against
`torch.cuda.is_available()`. Instruction 319 moved that question:
`_get_cellpose_outline_model` now asks `accelerator.cellpose_kwargs()`, which
asks `accelerator.resolve()` -- which answers for ROCm, Metal and XPU as well
as CUDA, is CACHED, and is documented as NEVER RAISING because every probe
inside it is individually guarded.

So the patch reached nothing. On this host the `[False]` case built `gpu=True`
and the `[True]` case passed by AGREEING WITH THE HARDWARE rather than by
being driven -- a false pass sitting next to the real failure, which is the
more expensive half.

Rewritten to fake the probe at the layer that owns it: `resolve` returns a
fake `Accelerator` for the mapping test, and `cellpose_kwargs` itself raises
for the `except Exception: kwargs = {"gpu": False}` arm. That arm is
UNREACHABLE through a broken driver -- resolve swallows it -- and reachable
through an accelerator module that fails to import, which is what the test now
says.

3. THE LATE-GUARD TEST. It compared source offsets: `df[annotation_column] =
None` against `rindex` of `if annotation_column not in df.columns:`, to assert
the column is created before a LATE guard that returned []. That guard has
since been DELETED and replaced by a comment, so `rindex` found the only
remaining occurrence -- the CREATING one -- and the test was comparing an `if`
against its own body. `assert 1750 < 1702` could not pass again whatever the
code did.

Replaced by two tests that pin what is now true: one DRIVES a frame with no
annotation column through `fetch_filtered_paths` and asserts unannotated rows
come back rather than [], and one asserts the guard string occurs exactly once
and is the creating one. Both mutation-checked -- deleting the creation kills
the first, and the count kills the second.

ALSO FIXED: the comment left where the guard was said "Line 1106 above CREATES
that column". The creation is at 1141 and 1106 is the function signature; the
number was stale by 35 lines. It now names the code instead of a line number.
