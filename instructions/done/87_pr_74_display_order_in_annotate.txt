THE PROBLEM IT DESCRIBES IS REAL AND IS ALREADY IN THIS REPOSITORY'S HISTORY.
Commit `341f446` corrected the crop channel order on disk, so `png_dims[0]`
is now the file's RED channel where cv2's BGR reading had put it in blue.
That fixed the format and silently mirrored what every pre-existing project
SEES: a parasite stain that was always red opens in Annotate as blue, nucleus
in red. The contributor's point about why this is not cosmetic is correct --
red/green overlap is legible and blue/green is not, so it is the difference
between judging colocalisation by eye and not.

THE PROPOSED FIX is a display-only permutation, "Display order", defaulting
to `r,g,b` (identity, a no-op) and running BEFORE normalisation and channel
filtering, so "Show channels" and "Normalize channels" keep naming the slots
the user is looking at. It does not touch the writer, the crop format or
`read_crop_png`. Seven new tests; 254 passing across the annotate suites.

2026-08-13 - IMPLEMENTED. THE MAINTAINER LEFT THE DESIGN TO ME; HERE IS THE CALL
--------------------------------------------------------------------------------

Requested: 2026-08-13 - "i am going to leave the PR#74 desision up to you,
           please implement what you think would be least confusing and most
           helpfull for the user."

NOT SUPERSEDED, which was checked first. Annotate's `stored_channel_order`
answers a different question, and conflating them is exactly what would
confuse:

    stored_channel_order   HOW WAS THIS FILE WRITTEN. A fact about the bytes,
                           resolved from the sidecar marker or the database.
                           Three values: rgb / legacy_bgr / auto.
    display_order          HOW DO I WANT TO LOOK AT IT. A preference, making
                           no claim about the file. Six values, default rgb.

THE DESIGN DECISION: two parameters, not one control that does both. A single
"channel order" that sometimes means the format and sometimes means a
preference is the version a user cannot reason about -- and the PR itself
names the cost of pretending a preference is a format: "Marking the folder as
format 2 gets the picture back by asserting something false about the bytes,
and the next reader believes it."

WHAT LANDED

  * `spacr/crops.py` -- `DISPLAY_ORDERS` (all six), `display_order_indices`
    and `apply_display_order`. In crops.py rather than in the Qt layer
    because it is the module that owns channel-order semantics, it is
    Qt-free, and instruction 89 (colourblind mode) needs the same seam.
  * `load_crop_image(..., display_order='rgb')` -- the one loader every
    annotate surface already goes through, so there is nowhere for a second
    implementation to appear.
  * FORMAT FIRST, PREFERENCE SECOND, asserted by a test. Reversing them would
    permute planes still in the wrong slots and compose into an order neither
    the file nor the user asked for.

DECISIONS WORTH KEEPING

  * The identity returns the SAME OBJECT, so the default costs nothing for
    the overwhelming majority who never set it.
  * A malformed order is REFUSED, not defaulted. Silently ignoring a typed
    order shows a picture the user did not ask for and does not know they are
    not getting -- which is the original bug in a new place.
  * A greyscale crop is left alone rather than refused: it has no three slots
    to permute, which is not an error.
  * `b, g, r` and ` BGR ` are accepted, because that is what a user types.

22 tests; 222 pass across crops, annotate and the crop-format suites.

--------------------------------------------------------------------------------
2026-08-13 (later) - THE CONTROL IS IN. 87 IS COMPLETE.
--------------------------------------------------------------------------------

A six-item combo in the Annotate settings dialog, placed as the NEXT ROW
after "Stored PNG order" on purpose: the two are adjacent because they are
easy to confuse, and being side by side is what makes the difference legible.
"Stored PNG order" says how the file was written; "Display order" says how
you want to look at it, and its tooltip says outright that it changes nothing
on disk and nothing measured.

The identity is labelled "R  G  B   (unchanged)" so the default reads as a
no-op rather than as a choice already made.

ONE THING THAT WENT WRONG AND IS WORTH RECORDING: adding the widget to the
screen's `install_api_tooltips` map BLANKED the tooltip. That map installs
the API help for a pipeline SETTING, and `display_order` is a view preference
no pipeline function takes -- so the lookup found nothing and replaced the
explanation with an empty string. A control with no tooltip is worse than one
with no map entry. It is out of the map, with a comment saying why.

31 tests; 89 pass across annotate and the display-order suites.
