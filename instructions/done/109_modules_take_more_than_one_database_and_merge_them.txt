================================================================================
IMAGE UMAP AND THE GATE EDITOR TAKE MORE THAN ONE DATABASE, AND MERGE THEM
================================================================================

Status:    2026-08-15: the shared mechanism is BUILT and the Gate Editor uses
           it. Image UMAP is NOT wired yet. See RESULT at the end.
Requested: 2026-08-15 - "add to instructions, make user that moduals like
           image UMAP and gate editor can take multiple databases and gerge
           them."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

One database per run. A screen that was acquired as three plates is three
separate sessions in the Gate Editor and three separate UMAPs, and the
comparison the user actually wants -- all of it in one embedding, one gate,
one figure -- cannot be made inside spaCR at all.

This is NOT instruction 41. That one merges TABLES within one database
(cell + nucleus + pathogen into one working set) and it is done. This is
merging DATABASES: the same tables, from different files, stacked.

They compose, and 41 is the foundation: once several databases are one
frame, 41's working-set and merge-rule machinery is what turns their tables
into the analysis frame. Build on it rather than beside it.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Plate-wise files are a normal acquisition boundary, not an analytical one.
Without a provenance-safe multi-database path, users cannot compare plates in
one embedding or gate without building an error-prone external merge.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. TAKE A LIST, NOT A PATH. Wherever a module accepts one database, accept
   several: add, remove, and see what is loaded. The Gate Editor already has
   the interaction vocabulary for this from 41 -- the little rounded box with
   an x per member of a working set -- so use it for databases too rather
   than inventing a second idiom for the same idea.

2. THE ROW MUST REMEMBER WHERE IT CAME FROM. Every row carries its source
   database, and that source is available as a grouping/colouring variable.
   A merged UMAP whose clusters turn out to be the three plates is the single
   most important thing this feature can show, and it cannot show it if the
   provenance was dropped at load time.

   This is also the batch-effect question, so it should compose with whatever
   `spacr/batch_correction.py` already does rather than duplicating it.

3. KEYS MUST NOT COLLIDE. Two plates both named `plate1` in two databases are
   two different plates, and `plate1_r1_c1_f1_o1` is one key. If the merge
   pools them, every per-well number afterwards is computed over two
   experiments at once, silently.

   REFUSE OR DISAMBIGUATE, NEVER POOL SILENTLY. If plate ids collide across
   the chosen databases, say so and make the user resolve it -- and note that
   `schema.KEY_ESCAPES` now gives a reversible way to qualify a plate id
   without breaking the key grammar, which is what a per-source prefix needs.

4. THE SCHEMAS WILL NOT MATCH. Databases written by different spaCR versions,
   or with different measurement settings, have different columns. Decide and
   state the rule: intersect (safe, silently drops), union with nulls (keeps
   everything, changes what "missing" means), or refuse. Show the user which
   columns are common and which are not BEFORE the merge, because that set is
   the analysis they are about to run.

   `schema.canonical_rename_plan` is the one canonicaliser to route through,
   so that a column spelled differently across two databases becomes one
   column rather than two.

5. IT MUST NOT LOAD EVERYTHING INTO MEMORY. Three plates is three times the
   rows. Whatever the current single-database path does about size, the
   multi-database path has to do more of it.

--------------------------------------------------------------------------------
WHICH MODULES
--------------------------------------------------------------------------------

The request names Image UMAP and the Gate Editor and says "modules LIKE"
them, so the pattern is the deliverable, not the two instances. Do those two
first, but put the loading and merging behind one shared thing so the next
module gets it for free -- if it lands as two private implementations, the
third module will be a third one, and they will disagree about key
collisions.

Everything that reads a measurements database is a candidate: the annotator,
the database browser, the classifier, the plots.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Three databases from three plates load into one Image UMAP; the embedding
  can be coloured by source database; a gate drawn on the merged embedding
  selects cells from all three.
* The same three load into the Gate Editor as a working set, removable
  individually, and 41's merge rules apply to the combined frame.
* Two databases that both contain a plate called `plate1` do NOT silently
  merge those plates. The user is told, and what they choose is recorded.
* Two databases with different column sets report what is common and what is
  dropped or nulled, before anything is computed.
* A per-source count after the merge equals the per-source count before it,
  for every source -- the test that catches silent pooling.

--------------------------------------------------------------------------------
RESULT (2026-08-15) -- mechanism done, one of two screens wired
--------------------------------------------------------------------------------

`spacr/multi_database.py` is the shared thing this instruction asked for, and
it is deliberately NOT in `spacr/qt/`: merging databases is data logic, and
the moment it lives in a screen the second screen writes its own.

    describe_merge(paths, table) -> MergePlan
    read_merged(paths, table, ...) -> one frame

`describe_merge` reads only sqlite metadata and the distinct plate ids, so it
is cheap enough to run while the user is still choosing files -- which is the
point of point 4: the answer has to arrive BEFORE they commit. The plan
reports total rows, the columns common to every source, the columns present
in only some (naming which), and any plate id that appears more than once.

Every requirement above, and where it landed:

  1. TAKE A LIST -- `read_merged(paths, ...)`. Merging one database is not a
     special case: it is the same frame plus provenance, so callers never
     branch.
  2. PROVENANCE -- every row carries `SOURCE_COLUMN` ("source_database"),
     labelled by the file's stem, disambiguated by parent directory when two
     files share one (every plate's database is often `measurements.db`).
  3. COLLISIONS -- refused by default, with a message naming the clashing
     plate ids. `on_collision='qualify'` prefixes each with its source using
     `schema.escape_filename_component`, so the qualified id cannot introduce
     the key separator and split the key into an extra component. THERE IS NO
     OPTION THAT POOLS, and 'merge'/'ignore'/'pool' are refused explicitly
     because they are what a caller would reach for.
  4. SCHEMAS -- `columns='common'` (safe, drops) or `'union'` (keeps, nulls).
     No default that is right for both, so the caller states it and the plan
     says what each costs. Both routes go through
     `schema.canonical_rename_plan`, so a column spelled differently across
     two databases becomes one column rather than two -- case-folded, so the
     merge cannot produce a frame SQLite refuses (instruction 100, C1).
  5. MEMORY -- `limit_per_source` caps rows per database in SQL.

THE GATE EDITOR is wired: its file dialog is `getOpenFileNames`, one file
behaves exactly as before, several go through the merge. A refusal is shown
in the source label and LEAVES THE EXISTING FRAME ALONE -- a screen that
blanks itself has punished the user for a question they are allowed to ask.

WHAT IS NOT DONE. Image UMAP is not wired, and the "add / remove / see what
is loaded" chip interaction from point 1 is not built for either screen --
today it is multi-select in the open dialog. Both are GUI work on top of a
mechanism that is finished and tested; neither changes any of the decisions
above.

16 tests, including the one that matters: a per-source count after the merge
equals the per-source count before it, for every source.


--------------------------------------------------------------------------------
2026-08-16 - THE PLATE-COLLISION ANSWER IS SUPERSEDED FOR SCREENS
--------------------------------------------------------------------------------

This file's `on_collision='qualify'` rewrites a colliding `plate1` to
`runA-plate1`. That was the right answer for the problem as stated here --
make the keys unique without losing data -- and it is the WRONG answer for
the case instruction 122 describes.

    "the screens would bothe have plates1,2,3,4 sh that would have to be
     fixed somewow, e.g. with a new metadataitem callsed screenID"

Qualification hides the screen INSIDE the plate id. The keys become unique,
which is all it was built to do, but the screen stops being analysable: you
cannot block on it, test for a screen effect, or colour by it without parsing
a string back apart.

So for two SCREENS the answer is a first-class `screenID` column beside
plateID, and `read_merged` should grow a screen-aware path that writes it.
Keep `qualify` for callers who genuinely want the plate id rewritten; stop
offering it as the recommended fix in the GUI.

Instruction 122 owns that work. This note exists so nobody reads the
collision section above and builds the qualification path into the
cross-screen feature.

RESULT (2026-08-18) -- BOTH SCREENS ARE WIRED, AND THE CHIPS EXIST
--------------------------------------------------------------------------------

The 2026-08-15 note above says "one of two screens wired". Verified before
building: the Gate Editor's `load_paths` did go through `multi_database`, and
the Image UMAP's `src` was a `_ScalarEdit` -- a single-line text box -- so the
GUI could not express more than one source at all, even though
`generate_image_umap` has always taken a list. Both are now done.

WHAT SHIPPED

1. THE CHIP WORKING SET, point 1's "add, remove, and see what is loaded", for
   both screens, in the idiom 41 established.

   * `spacr/qt/widgets/database_set.py` -- `DatabaseSetWidget`. Add button,
     one removable `TableChip` per source, and a summary line that runs
     `describe_merge` on every change. It says how many rows, how many columns
     are common, WHICH measurements are about to be dropped, and whether two
     databases claim one plate -- before anything is computed, which is the
     whole point of `describe_merge` being metadata-only.
   * The Gate Editor grew a second chip strip for its databases, above the
     table strip. Removing one re-merges the rest; down to one, the strip goes
     away and the session is the ordinary single-database one again.

2. IMAGE UMAP TAKES A LIST. `settings_model._widget_for` routes the umap
   `src` to `DatabaseSetWidget(mode='folder')`, so `collect()['src']` is now a
   list of project roots -- exactly the shape `generate_image_umap` builds on
   its first line -- and the panel follows the set as it is edited.

   COLOURING BY SOURCE IS REACHABLE. `color_by` is a free-text field with an
   SQL column picker, and `source_database` is not a column of any database:
   it is added at merge time, so the picker could never offer it and a user
   would have had to know the name and type it. The source control now carries
   a "Colour the map by source database" box, shown only when more than one
   source is chosen, which writes `source_database` into `color_by`.

3. A BUG THE LABELS HAD, which mattered more than it looks.
   `multi_database._label_for` disambiguated on the file's IMMEDIATE parent.
   spaCR writes every plate to `<plate>/measurements/measurements.db`, so the
   stem and its parent are the same string for every plate in a screen, and
   three plates were labelled `measurements`, `measurements/measurements` and
   `measurements/measurements (2)` -- three names that are distinct and name
   no plate, IN THE COLUMN THE MERGED EMBEDDING IS COLOURED BY. Replaced with
   `source_labels(paths)`, decided for the whole set at once: stems if they
   differ, else the nearest meaningful parent folder (skipping `measurements`
   and friends), else the old parent/stem rule with its numeric tail. Three
   plates are now `plate1`, `plate2`, `plate3` -- and identical to what
   `core._umap_source_label` produces, which the docstring had claimed all
   along. `tests/test_the_databases_in_the_measurements_tab.py` had pinned the
   old labels; that assertion is corrected, and it is the only file outside
   this instruction's territory that was touched.

4. RECORDED, not just told. `MergeDecision`, `decision_for`,
   `record_decision` and `decision_log_path` append one JSON line per merge to
   `~/.spacr/merge_decisions.jsonl`: the sources, their labels, the rows each
   held, the columns rule, what was dropped, the colliding plates, the
   outcome, and the resolution in words. The Gate Editor writes one when it
   merges, one when it refuses, and one when the user drops a database to
   resolve a collision -- which is the case that has no other trace, because
   the surviving frame cannot say which `plate1` it is. An unwritable log
   returns "" rather than taking the screen down.

5. THE 2026-08-16 SUPERSESSION IS HONOURED. `on_collision='qualify'` still
   exists for callers who want it and is no longer offered as advice anywhere
   a user reads: `_collision_message` now says "remove one of those databases,
   rename the plates, or say these are separate screens", and the widget says
   the same. Tests assert the word "qualify" is absent from both. The screenID
   path was NOT built -- that is 122's.

6. THE MULTI-DATABASE SESSION IS NOW A REAL SESSION. `load_paths` never
   filled the table picker or `self._tables`, so a merged frame had no table
   working set: nucleus could not be added to it, and `_reload_working_set`
   would have read only `paths[0]`. It now fills both, and
   `_reload_working_set` routes several databases through
   `plate_measurements.merge_plate_databases` -- the existing composition of
   41's per-table rules and 109's per-database stacking -- rather than a third
   set of rules.

TESTS. `tests/test_multi_database.py` +8 (labels, three-plate per-source
counts, `frame.attrs['source_rows']`, the decision log, the refusal wording);
`tests/qt/test_the_databases_are_a_working_set.py` is new, 14 tests, and
presses the actual controls -- it counts chips, CLICKS the x, and compares the
per-source counts the screen ended up with against the counts in the files.
Every one of them fails without the change.

WHAT REMAINS

* Dropping a folder on the Image UMAP REPLACES the source set rather than
  adding to it. `dnd_handlers._set_src_on` calls `set_value_for_key`, whose
  contract is replace -- correct for loading a settings CSV, wrong for a
  second drop. Making a drop add needs a branch in `spacr/qt/dnd_handlers.py`.
* The empty-state banner on the Image UMAP checks `isinstance(src, QLineEdit)`
  to decide whether a source is set, so it now shows even when three are
  chosen. `app_screen._build_empty_state_banner`, one line.
* The other modules the instruction names -- the annotator, the database
  browser, the classifier -- still take one database. The shared thing they
  need is built and now has two callers; giving a third module the control is
  the same three lines the umap `src` branch is.

A TRAP WORTH NOT REDISCOVERING. `python /some/script.py` puts THE SCRIPT's
directory on `sys.path`, not the cwd, so a check written to a scratch file
imported spaCR from a different checkout on this machine entirely and reported
that a just-made edit had not taken effect. `python -c`, or
`PYTHONPATH=<repo>`, or pytest -- but not a bare script path.

2026-08-18 -- THE TWO HANDOFFS ARE CLOSED, AND BOTH WERE MEASURED FIRST.
Commit f20f4a12.
--------------------------------------------------------------------------------

Both were the same mistake in two places: code still asking the OLD question
after `src` stopped being a text box on the merging modules.

1. A DROPPED FOLDER USED TO EVICT THE SET.  Measured on the real Image UMAP
   screen with the real handler, dropping plate1, plate2 and plate3 in turn:

       after drop plate1 -> ['/tmp/.../plate1']
       after drop plate2 -> ['/tmp/.../plate2']
       after drop plate3 -> ['/tmp/.../plate3']

   `_set_src_on` wrote through `set_value_for_key`, which calls `set_value`,
   which REPLACES. Two of the three merges the user asked for were discarded
   with nothing said, which is worse than a refusal.

   A drop is the same gesture as the control's own "Add project folders…"
   button, whose tooltip already promises "adds to the set rather than
   replacing it, so three plates can be gathered in three trips". So
   `_add_to_source_set` runs first now and calls `add_sources`. After:

       after drop plate3 -> ['.../plate1', '.../plate2', '.../plate3']
       collect src:        ['.../plate1', '.../plate2', '.../plate3']

   DROPPING A FOLDER ALREADY IN THE SET IS A SUCCESSFUL DROP. `add_sources`
   returns how many were NEW, which is a different question -- returning
   False there would raise "this module has no source field to receive the
   drop" at a user whose screen is pointing exactly where they pointed it.

   A module whose `src` IS a text box still gets REPLACE, and there is a test
   for it: dropping a second folder on Mask means "look at this one instead",
   because there is no set to join.

2. THE EMPTY-STATE CARD SAT ON TOP OF THREE LOADED DATABASES.
   `_build_empty_state_banner` decided "is src set?" with
   `isinstance(src, QLineEdit)`, so `existing` stayed `""` whatever was
   loaded and "Point image umap at some data" stayed up for the whole
   session. It asks `_settings_src_path()` now, which already knew how to
   read both shapes -- and asking IT is what stops the next control that
   replaces a QLineEdit reintroducing this.

   The auto-hide follows `value_changed` as well as `textChanged`, and it
   goes BOTH ways: removing the last database returns the screen to exactly
   the state the card describes, and a set can be emptied where a typed path
   cannot.

TESTS: tests/qt/test_a_dropped_folder_joins_the_source_set.py, 7 of them, on
the REAL Image UMAP screen and the real handler -- both bugs were invisible to
a double, because a double has a QLineEdit. Four of the seven fail at HEAD.

2026-08-20 -- THE THIRD HANDOFF, AUDITED RATHER THAN GUESSED. 109 CLOSES.
--------------------------------------------------------------------------------

"giving a third module the control is the same three lines the umap `src`
branch is" -- it is three lines in the PANEL, and that was the wrong place to
measure the cost. The question is whether the PIPELINE behind the panel can
read a list, and a control that produces a value some stage cannot read is
worse than a control that only expresses one source: the run fails somewhere
in the middle, having already written half its output.

COUNTED 2026-08-20, branches on a list-valued `src` per module:

    submodules.py   4        core.py         2        plot.py     2
    deep_spacr.py   1        io.py           1        measure.py  1
    utils.py        1

`core.generate_image_umap` is the one that handles it end to end, which is why
it is the module that got the control. `deep_spacr` has ONE branch and it is
in the prediction-merge at the very END of the run -- its docstring says
"root folder(s)" and the stages before that merge do not honour the plural.
Wiring the widget there would produce a settings value the tar build and the
dataset generation cannot read.

SO THE REMAINING MODULES ARE NOT A PANEL CHANGE. Each needs its pipeline
audited stage by stage first, which is a per-module instruction with its own
evidence rather than a line in this one. The shared control is built, has two
callers, and is ready for the module that earns it.

109's ask -- "modules take more than one database and merge them" -- is
delivered for the module the request was about, with `multi_database`'s
describe/merge underneath it and `spacr.tabular` canonicalising on the way in
(145).
