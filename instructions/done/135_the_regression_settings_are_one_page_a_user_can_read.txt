--------------------------------------------------------------------------------
A. ONE COLUMN, NOT TWO: `score_column` MERGES INTO `dependent_variable`
--------------------------------------------------------------------------------

They name the same thing and a user has to guess which one is read. Keep
`dependent_variable`; retire `score_column` the way `volcano` was retired --
an old settings CSV carrying it must still load, with its value moved over and
a line saying so, not dropped in silence.

AUDIT DONE 2026-08-17, and it says the request is right, with one boundary.

IN THE REGRESSION MODULE the two are already the same thing BY CONTRACT.
settings.py:1983 is `settings.setdefault('score_column',
settings['dependent_variable'])`, and the tooltip already says out loud that
they must agree: "It must name the same measurement as dependent_variable, or
the simulated min_cell_count describes a different quantity than the one the
regression fits and wells are kept or dropped on the wrong evidence." Having
both therefore offers the user a way to make the run wrong and nothing else.

Its ONLY reader on the regression path is `minimum_cell_simulation`, which
resamples the per-object score CSV to work out how many objects a well needs
before its mean stops moving. Substituting `dependent_variable` there is
exactly what the default already does.

THE BOUNDARY: `score_column` is NOT only a regression setting. In
`interpret_vision_model` (Explain CV) and in `hit_investigation.py` the same
key names the CNN score column, default 'cv_predictions'. It stays alive
there. What is retired is the regression module's duplicate -- the panel
control and the regression default -- not the key.

--------------------------------------------------------------------------------
B. A COLUMN THAT IS NOT THERE OFFERS THE COLUMNS THAT ARE
--------------------------------------------------------------------------------

Today a missing `dependent_variable` fails somewhere inside the merge, after
the whole score table has been read, with a message naming a column the file
does not have. Instead: READ THE HEADERS AND OFFER THEM.

The same behaviour in three places, because it is the same failure:

  * `dependent_variable`, against the score CSVs.
  * `filter_column`, against the same input CSVs -- and its button is an SQL
    button today, which is wrong: the regression module's inputs are CSVs.
    Replace it with a CSV button that reads the input CSVs. Give
    `dependent_variable` the same button.
  * THE COUNT COLUMNS, which the request is right about -- they are
    HARD-CODED and have no setting at all. Find them, give them settings, and
    give those settings the same offer-what-exists behaviour.

Headless too, not only in the GUI: a run that cannot find the column should
print the columns the file HAS. A message that lists the alternatives is the
difference between a two-minute fix and a re-run.

D. "IM NOT SURE I SEE A DIFERENCE WHEN I USE IT" -- BATCH CORRECTION
--------------------------------------------------------------------------------

MEASURED 2026-08-17, and the answer is outcome 1, not outcome 3. The
correction WORKS; what it did not do was say which of three things had just
happened.

    three plates, real offset   center  mean|delta| 0.4579   spread 0.527 -> 0.000
    three plates, real offset   zscore  mean|delta| 0.5421   spread 0.527 -> 0.000
    three plates, no offset     center  mean|delta| 0.0102   spread 0.011 -> 0.000
    ONE plate                   center  mean|delta| 0.000000 spread 0.000 -> 0.000
    any                         combat  raises, demanding a covariate

NOTHING WAS SILENTLY UNAPPLIED, which was the outcome that would have made
every run since wrong. On plates with a real offset the correction collapses
the between-plate spread to exactly zero and moves each value by about 0.46.

The single-plate case is an EXACT no-op -- mean|delta| = 0.000000, because
there is no between-batch variance to remove -- and it is almost certainly
what was seen. The old console line reported "0.000 -> 0.000 centroid
spread", which is indistinguishable from a correction that worked perfectly:
the centroid spread goes to 0.000 in every case that runs, including the ones
that change nothing.

FIXED by making the run say how far it moved the data -- the mean absolute
shift in the dependent variable, which is the number a user comparing two runs
is actually looking for -- and by saying outright when the answer is "nothing,
and it could not": fewer than two batches means there is nothing between
batches to remove, and `batch_correction='none'` gives an identical result.

STILL OPEN: greying the control out when the score table has one plate. The
dependency rules see only the settings dict, and how many plates a run has is
a fact about the DATA, so it needs a different mechanism from the 106 rule the
other controls use.

2026-08-20 -- THE LAST OPEN LINE. 135 IS CLOSED.
--------------------------------------------------------------------------------

"STILL OPEN: greying the control out when the score table has one plate. The
dependency rules see only the settings dict, and how many plates a run has is
a fact about the DATA, so it needs a different mechanism."

IT NEEDED NO NEW MECHANISM. `context['plate_count']` already exists, is filled
by the panel from the inputs the user dropped in, and `guide_permutation_block`
already uses it -- so the route was there and only this setting had not taken
it. All eight batch controls take it now.

Correcting BETWEEN batches when there is one batch removes nothing. The run
already says so out loud; saying it AFTER the run is saying it too late, and
the control is greyed before the user chooses.

TWO PROPERTIES MATTER MORE THAN THE GREYING:

  * UNKNOWN GREYS NOTHING. `plate_count` is None with nothing loaded or with
    inputs too large to scan cheaply, and a control disabled because a file
    was big is indistinguishable, to the person looking at it, from one
    disabled on purpose.
  * THE RULE COMBINES, never assigns. A setting is applicable only if EVERY
    rule that mentions it says so, and assigning over an existing one silently
    drops it -- which this file records happening once already, to
    `guide_permutation_block`. A test drives four plates with correction
    switched OFF and checks the OTHER reason comes back, not the plate one.

FOUND WRITING THE TEST: `batch_control_column` and `batch_control_values` are
read only by `control_center`, not by `combat`. Asking about them under combat
measures the rule that was already there rather than the one added here, so
each key is tested under the method that actually reads it.

34 tests in tests/test_batch_correction_is_greyed_on_one_plate.py.
