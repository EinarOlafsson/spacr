THE NONPARAMETRIC REGRESSIONS ARE OFFERED
================================================================================

Status:    closed in spaCR. The Qt panel now reads the same table, which was
           the last open half; see THE LAST HALF at the end. One line remains
           in `tools/`, named there -- the catalog builder has to collect
           `_REGRESSION_MENU_UI_SOURCES` before a regeneration can give the
           twenty new captions their rows.
Requested: 2026-08-21 -- "there are nonparametric versions of regression these
           should be included!"
Owner:     Regression

--------------------------------------------------------------------------------
WHY THIS SCREEN NEEDS THEM
--------------------------------------------------------------------------------

The data this module fits breaks the assumptions the current models make.
Fractions are bounded in [0, 1] and pile up at both ends; guide counts per
well are wildly unequal; and a screen's interesting genes are by definition
the outliers, which is precisely where a least-squares fit is least reliable
and where a single bright well can carry a coefficient on its own.

A nonparametric fit answers the question that follows every result on this
screen: IS THIS EFFECT THE DATA, OR IS IT THE MODEL? Two fits agreeing is
worth more than either alone, and where they disagree the disagreement is
itself the finding.

--------------------------------------------------------------------------------
WHAT TO OFFER
--------------------------------------------------------------------------------

Candidates, to be chosen from with the maintainer rather than all built:

  * QUANTILE REGRESSION -- the median (or any quantile) rather than the mean.
    The natural first one: statsmodels already provides it, it takes the same
    formula, and the median of a bounded skewed response is the estimate the
    mean was standing in for. It also asks a question no current model can:
    does the guide move the TOP of the distribution rather than its centre?
  * RANK-BASED / ROBUST FITS -- Theil-Sen and Huber, for a coefficient that
    a handful of extreme wells cannot set on their own.
  * A PERMUTATION TEST on the existing coefficients, which makes no
    distributional assumption about the null at all. Expensive, and the
    honest answer when a p-value has to survive scrutiny.
  * A RANK TEST per guide (Mann-Whitney / Kruskal-Wallis) for the simple
    comparisons, where a full model is more machinery than the question.

EACH ONE MUST FIT THE EXISTING PIPELINE, not sit beside it: the same formula,
the same coefficient table with the same column names, the same volcano, the
same multiple-testing correction. A model that produces a table the rest of
the screen cannot read is a model nobody will use twice.

WHERE A METHOD HAS NO p-VALUE, SAY SO rather than substituting a
normal-theory one -- that would put the assumption back in through the door
the method was chosen to close.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* At least one nonparametric fit is selectable beside the current models and
  produces a table the volcano, the correction and the export all accept.
* Its assumptions are stated where the user chooses it.
* On data that satisfies the parametric assumptions the two broadly agree --
  checked on generated data where the answer is known.
* On data with a planted outlier they DISAGREE, and the robust one is right.
* Nothing silently substitutes a parametric p-value for a method that has
  none.

--------------------------------------------------------------------------------
THE PREMISE WAS WRONG: THEY ARE ALL ALREADY THERE
--------------------------------------------------------------------------------

Checked 2026-08-21 before building anything. `_regression_type_choices`
offers nineteen families and FOUR OF THEM ARE WHAT THIS FILE ASKED FOR:

    quantile   quantile regression, with a settable tau (`quantile`, 0.5)
    rlm        robust M-estimator
    huber      Huber's loss, with a settable `huber_t`
    rra        robust rank aggregation -- rank-based, the standard
               nonparametric method for a pooled screen

And `inference='nonparametric'` has existed as an alias for
`analysis_mode='guide_permutation'`, a plate-blocked permutation test.

SO NOTHING WAS MISSING AND THE REQUEST WAS STILL REAL. The user could not
find them. Nineteen families in one flat alphabetical list, with no statement
of what any of them assumes, is a menu that hides its own contents.

--------------------------------------------------------------------------------
AND THEN THE REAL DEFECT, FOUND BY THE MAINTAINER'S NEXT QUESTION
--------------------------------------------------------------------------------

    "ok if they are nonparametric shouldnt they be available when
     nonparametric is chosen? which would mean that analasys mode should also
     have 2 options under nonparametric."

RIGHT, AND THE CAUSE IS A CONFLATION OF TWO INDEPENDENT AXES.

  * HOW THE EFFECT IS ESTIMATED -- least squares, a quantile, a robust loss,
    a rank aggregation.
  * HOW THE P-VALUE IS COMPUTED -- from the model's own distribution theory,
    or from a permutation null that assumes nothing.

THESE ARE ORTHOGONAL. Every pairing is meaningful, and the most conservative
one -- a robust estimator with a permutation null -- IS CURRENTLY
UNREACHABLE, because `inference='nonparametric'` selects
`analysis_mode='guide_permutation'`, and that path computes a fixed statistic
(`standardized_marginal_effect`) and never reads `regression_type` at all.

So choosing "nonparametric" today does not give access to the four families
above; it replaces them with one hard-coded estimator.

A CORRECTION TO THIS FILE'S OWN VOCABULARY, because the fix depends on
getting it right: `rlm`, `huber` and `quantile` ARE NOT NONPARAMETRIC. They
fit a linear model and are parametric in the coefficients; they are ROBUST
(insensitive to outliers) and, for quantile, distribution-free about the
ERROR term. `rra` is rank-based and genuinely nonparametric. Only permutation
inference is distribution-free about the null. Labelling all four
"nonparametric" in the UI would be wrong in a way a reviewer would catch.

--------------------------------------------------------------------------------
WHAT TO BUILD
--------------------------------------------------------------------------------

  1. THE PERMUTATION PATH TAKES ITS STATISTIC FROM THE CHOSEN FAMILY, so any
     estimator can be paired with a permutation null. That is the maintainer's
     "2 options under nonparametric", generalised: it is not two, it is one
     per family that can produce a coefficient.
  2. EACH FAMILY STATES WHAT IT ASSUMES, in the dropdown, in the three honest
     groups -- parametric, robust/semiparametric, rank-based. Nineteen
     unlabelled families is the discoverability failure that produced this
     instruction.
  3. Nothing is renamed. The stored values stay, so every settings CSV keeps
     meaning what it meant.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* `quantile` with a permutation null runs and reports a permutation p-value.
* The dropdown says what each family assumes.
* Nothing is described as nonparametric that is merely robust.
* A settings CSV written before this produces the same fit.

--------------------------------------------------------------------------------
WHAT WAS DONE, AND WHAT WAS DELIBERATELY NOT
--------------------------------------------------------------------------------

`grna_statistic` -- `'pearson'` (the historical default) or `'rank'`.
It reaches `guide_permutation.guide_freedman_lane_test` as its
`statistic=` argument.

THE INFERENCE WAS ALWAYS DISTRIBUTION-FREE; THE STATISTIC WAS NOT, and that
is the gap this closes. The permutation builds its own null, so the p-value
needs no assumption -- but the quantity being permuted was a partial
CORRELATION, which is a least-squares object. One extreme well moves it
exactly as it moves a regression coefficient. `'rank'` ranks the phenotype
before residualising, making the statistic a Spearman-type partial
correlation: monotone rather than linear, and unmovable by a single well
because a rank has nowhere extreme to go.

MEASURED ON THIS SCREEN, which is why it is not academic: the residuals came
back with excess kurtosis +8.89 and skew +1.64, 455 of 1,781 observations
above the leverage guide, and a maximum Cook's distance of 1.01. On a
synthetic screen with one planted outlier the rank statistic recovers an
effect more than twice the size the correlation reports -- the outlier
dilutes the correlation and cannot dilute the rank.

RANKED BEFORE RESIDUALISING, not after. Ranking the residual would rank a
quantity the nuisance fit has already shaped; ranking the phenotype first
makes the whole statistic a function of order, and the projection then
removes the block from the RANKS. There is a test that a strictly increasing
transform of the response changes nothing, which is the defining property.

A ROBUST REGRESSION WAS NOT OFFERED HERE, and the reason is arithmetic
rather than taste. Both statistics are ONE MATRIX PRODUCT across all guides
and all permutations at once, which is what makes 200,000 permutations
feasible. A quantile or Huber fit would need one fit per guide per
permutation -- 789 x 200,000 on this screen -- which is not a slower option,
it is a different program. `quantile`, `rlm` and `huber` remain available
as PARAMETRIC fits, which is where they can be computed.

Tests: `tests/test_the_permutation_can_use_ranks.py`, 8 passing.

AND SECTION 2, THE DISCOVERABILITY HALF, WHICH IS WHAT MADE THIS FILE GET
FILED FOR METHODS THAT ALREADY EXISTED

`spacr/regression_families.py` places all nineteen in the three honest
groups and gives each one a sentence saying what it assumes:

    parametric              mixed, ols, wls, glm, poisson, quasi_binomial,
                            beta, logit, probit, lasso, ridge, elasticnet,
                            horseshoe, group_lasso, hinge
    robust/semiparametric   rlm, huber, quantile
    rank-based              rra

`regression_family_choices()` returns (stored value, label) pairs in that
order -- parametric first, `mixed` at the head of it because it is the
default -- and the label leads with the stored value, so a user looking for
'quantile' still finds the word 'quantile'.

NOTHING IS RENAMED, which is a test: the values are exactly the fittable
inventory, so a settings CSV written before the grouping asks for the fit it
always asked for. NOTHING MERELY ROBUST IS CALLED NONPARAMETRIC, which is
also a test: `rlm`, `huber` and `quantile` are in the robust group and the
word does not appear in their labels; only `rra`, which reads nothing but the
order of the wells, is rank-based. AND A FAMILY WITH NO p-VALUE SAYS SO,
taken from `NO_P_VALUE_TYPES` rather than a second list that could disagree
with it.

`settings_spec._regression_type_choices` NOW RETURNS THE GROUPED PAIRS. It
built its own flat alphabetical list out of `REGRESSION_TYPES`; it asks
`regression_family_choices()` instead, so the panel that reads it shows
"quantile -- robust/semiparametric: a quantile of the response rather than
its mean, which assumes nothing about the shape of the errors" where it used
to show "quantile".

NOTHING IS RENAMED, and that is a test rather than an intention: the stored
value leads its own label, so a user looking for 'quantile' still finds the
word and every settings CSV asks for the fit it always asked for.

--------------------------------------------------------------------------------
THE LAST HALF: THE Qt PANEL READS THE TABLE TOO
--------------------------------------------------------------------------------

The `if key == "regression_type":` branch of `SettingsWidgets._widget_for`
built its own list -- `["auto", *REGRESSION_TYPES]` -- so the two routes over
one inventory could disagree about what a family is called and which kind it
is in, and they did: one showed nineteen unlabelled names, the other showed
them grouped and explained. It now asks `regression_family_choices()`, the
same function `settings_spec._regression_type_choices` asks, and 'auto' keeps
its own spelling as a bare pair at the head.

ASKED OF `spacr.regression_families`, NOT `spacr.ml`. Both re-export the same
function and either would have closed the item, but `spacr.ml` imports
`spacr.plot` and therefore torch -- 2.2 seconds and 900 MB on the GUI thread
to read a tuple of strings. The family table was split out of `spacr.ml` for
exactly that reason, and `tests/test_a_settings_panel_does_not_import_torch.py`
exists to stop the panel reaching back for it. So the branch is a lighter
import than the one it replaced as well as a shared one.

NOTHING IS RENAMED, and it is the widget that proves it rather than an
intention: every entry is added with `userData=<stored value>`, `_read_widget`
returns `itemData`, and `set_value_for_key` selects with `findData` before
`findText`. A settings CSV saying `quantile` opens the panel on quantile and
is written back as `quantile`.

AND A SILENT NO-OP CAME WITH IT, FOUND BY THE TESTS EITHER SIDE. Qt matches
`setCurrentText` against the CAPTION and, on a non-editable combo, does
nothing whatsoever when nothing matches -- no exception, no log. The moment a
caption stopped being its own value, every caller saying "choose ols" by name
became a no-op that left the control on whatever it was showing while the
caller believed it was set. Five tests caught it; production code would not
have. The builder now makes a `_ValueCombo`, which matches the caption first
-- Qt's own behaviour, unchanged -- and falls back to the stored value.

A CAPTION SHIPS WITH ITS ROWS, and these are composed at runtime, so the
literal-string extractor in `tools/build_i18n_catalogs.py` cannot see them at
the `addItem` call site the way it sees a quoted label.
`_REGRESSION_MENU_UI_SOURCES` declares all twenty for it -- deliberately NOT
folded into `_SETTINGS_MODEL_UI_SOURCES`, which
`tests/qt/test_external_i18n_catalogs.py` pins to exactly the templates the
model explainers render, so a menu caption in it fails a check on a string no
explainer has ever rendered.

MEASURED, NOT ASSUMED, about what happens until the catalogs are regenerated:
`tr()` returns all twenty unchanged in every one of the nine languages today.
`_term_translation` refuses a source over 80 characters or containing '/',
and nineteen of the captions are 85 to 200 characters; the twentieth, 'auto',
is 53 and contains no catalogued term. So none of them can come back as
half-English -- they stay English until the rows exist.

ONE LINE REMAINS AND IT IS IN A FILE THIS WORK DID NOT OWN.
`tools/build_i18n_catalogs.py` collects `_SETTINGS_MODEL_UI_SOURCES` at line
2832 and must collect `_REGRESSION_MENU_UI_SOURCES` beside it (adding the
name to the `from spacr.qt.screens.settings_model import (...)` block above
it), after which a catalog regeneration writes the twenty rows and their
source hashes into all nine catalogs.

Tests: `tests/test_the_qt_menu_reads_one_family_table.py`, 12 passing. The two
routes are compared pair for pair rather than as two sets, because the failure
this replaces was the same nineteen values carrying different labels; and one
test asserts every caption the menu shows is declared as a UI source, so a
family added to the inventory cannot reach the dropdown without reaching the
translators.

Tests: `tests/test_the_regression_menu_says_what_it_assumes.py`, 12 passing,
and four in `tests/test_analysis_mode_is_a_dropdown.py` that read the choices
off `convert_settings_dict_for_gui` -- every family states its kind and its
assumption, nothing merely robust is labelled nonparametric, the groups do
not interleave, and mixed still leads.
