================================================================================
A BUTTON THAT PICKS THE SETTINGS FOR YOUR DATA
================================================================================

Status:    DONE 2026-08-20. See the closing section.
Requested: 2026-08-20 -- "I also want a button to the left of inference
           alligned with the text box to the left in model & inference that
           if clicked picks the most correct and best settings for your data
           fills in those settings in teh settings fields. its fine if the
           button triggers a popup that asks the user questions about their
           data that cant be determined by reading the data that are relveant
           to the coice of settings. a question might be out of 1000
           perterbations genes how many are expected to be hitts?"
Owner:     regression module + Qt GUI

WHERE IT GOES: Model & Inference, immediately LEFT of `inference` and aligned
with its box.

--------------------------------------------------------------------------------
A. WHAT CAN BE READ FROM THE DATA, AND MUST BE
--------------------------------------------------------------------------------

Most of the choice is already sitting in the loaded tables, and spaCR already
computes several of these for other reasons -- the button should CALL those
rather than grow a second opinion:

    plate count               decides whether batch correction can run at all
                              (135: it greys on one plate)
    response range            a proportion in (0,1) wants a link-carrying
                              family; an unbounded response does not. This is
                              `_choose_glm_family`'s own question (182).
    response distribution     normality, skew -- what `check_distribution`
                              already recommends
    wells per guide           whether a guide-level fit is identifiable
    guides per gene           whether the gene level has any power
    design rank               `regression_levels` exists because the combined
                              design is rank-deficient; the same check says
                              whether `level='both'` is required
    counts vs fractions       Poisson with an exposure, or a bounded response
    cell counts per well      whether weighting is worth it (wls / var_weights)

--------------------------------------------------------------------------------
B. WHAT CANNOT, AND SO IS ASKED
--------------------------------------------------------------------------------

The maintainer's own example is the right shape: "out of 1000 perterbations
genes how many are expected to be hitts?" -- that is the PRIOR, and no amount
of reading the table supplies it.

    expected hit rate         drives the multiple-testing posture. A screen
                              expecting 5 hits in 1000 wants a strict FDR; one
                              expecting 200 is a different question and a
                              different alpha.
    what a hit MEANS          any change, or a change in one direction? Sets
                              whether the test is one- or two-sided.
    library composition       are there non-targeting controls, and what are
                              they called? Feeds `control_names` (184), which
                              already reads a gene or a guide in four
                              spellings.
    the cost of a false       a screen feeding an expensive follow-up wants
    positive vs a false       precision; a screen feeding a cheap one wants
    negative                  recall. This is the honest form of "how strict?"

KEEP IT SHORT. Four questions is a dialog; twelve is a form nobody finishes,
and every question that CAN be read from the data and is asked anyway is a
question that should not have been there.

--------------------------------------------------------------------------------
C. IT EXPLAINS ITSELF, AND IT DOES NOT LIE
--------------------------------------------------------------------------------

THE DANGER IS AN AUTHORITATIVE GUESS. A button called "best settings" that
silently fills fourteen fields is trusted far past what it can support, and
the user has no way to tell a measured choice from a default.

So every field it fills says WHY, in the same words the panel already uses
for a greyed control (106): "regression_type=glm because the response is a
proportion strictly inside (0,1)". A choice it could NOT make is left alone
and said out loud rather than filled with a default wearing the same
authority as the rest.

AND IT IS A PROPOSAL. Show what it would change, with the current value
beside the new one, and let the user accept or reject before anything is
written. A button that rewrites a carefully-tuned panel with one click and no
undo is a button people learn not to press.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Every field it sets carries a reason naming what in the data decided it.
* Nothing is written until the user accepts the proposal.
* A setting it cannot decide is named as undecided, not defaulted silently.
* On the reference screen it chooses a family and a level that a
  statistician would defend, and the reasons are checkable against the data.
* The questions it asks are only the ones the data cannot answer.

--------------------------------------------------------------------------------
2026-08-20 -- TWO ADDITIONS FROM THE SAME SESSION
--------------------------------------------------------------------------------

THE TRANSFORM IS PART OF WHAT IT DECIDES. "for the test regression button it
should also test how to transform the data." It is the same question as the
family (182): a link-carrying family and a link-like transform are two ways
of doing one job, and applying both fits logit(log(y)). So the button decides
`transform` and `glm_transform_conflict` TOGETHER with `regression_type`, and
says which of the two is doing the transforming.

THE INTERCEPT IS DEFINABLE. "i would also like if i could define the
intercept." Today the intercept is whatever patsy puts in -- the reference
level of the first categorical, which is an arbitrary guide. Naming it makes
every coefficient a contrast against something the user CHOSE, which is what
`spacr.baseline` already does for the volcano's y axis but not for the fit
itself. Candidates: the non-targeting controls (which `control_names` can now
resolve in four spellings, 184), a named guide or gene, or the grand mean.
Worth checking against `baseline.py` before building anything -- if the
volcano can already re-baseline a fitted table, the fit may not need to.

2026-08-20 -- DONE. "Settings for my data…", left of `inference`.
--------------------------------------------------------------------------------

`spacr/settings_advisor.py` is the whole argument and imports no Qt, so what
the window shows can be checked from a script against the same screen.

A. WHAT IS READ, AND WHAT IT COSTS.

The count tables are per well and small, so plates, wells, guides, genes,
wells-per-guide and guides-per-gene are EXACT -- and they come from
`fractions_from_counts`, which is `process_reads`' own arithmetic, so the
numbers are the ones the fit will see rather than a second implementation of
them.

The score table is per OBJECT and can be gigabytes -- 2.75 GB on the
maintainer's own screen -- so the response is read from a capped sample and
`Reading.sample_note()` says so on every number derived from it. A reading
that pretended to have seen the whole file would be the authoritative guess
this instruction is against.

MEASURED ON THE REFERENCE SCREEN (the four example plates): 8.5 s, and it
reads 4 plates, 1,536 wells, 1,380 guides, 452 genes, 3 guides per gene,
226,467 object rows, response strictly inside (0, 1), D'Agostino p = 2.8e-147,
skew +2.45.

AND THE RESPONSE IS READ AT THE WELL LEVEL, not the object level. A per-object
response is aggregated to wells before the model touches it, so the family
question is about the WELL means; the object-level spread is much wider and is
not the distribution being modelled. Asserted with a fixture where 400 uniform
draws per well average to 0.5 while the objects span the whole interval.

B. THE FOUR QUESTIONS, AND NO MORE.

The maintainer's own is the first and sets the shape. Each says what it buys,
because a user who cannot see that answers to make the dialog go away. The
direction question is DROPPED for a binary response, where "an increase" is
the only direction there is -- a question the data can answer is a question
that should not have been asked.

C. IT EXPLAINS ITSELF.

On the reference screen it proposes, each with the measurement that decided
it: beta (strictly inside (0,1)), no transform and untransformed (the family
carries its own link, and both would fit logit(log(y)) -- 182), level=both
(3 guides per gene across 452), combat (4 plates), plate position on (16 rows
x 24 columns), nonparametric (p = 2.8e-147 with 1,536 wells to permute),
fdr_bh at 0.05, and the controls as named.

Nothing is written until Apply, the current value sits beside the new one, and
an UNCHANGED row is shown greyed rather than hidden -- a proposal listing only
differences reads as "everything else is wrong", when most of a tuned panel is
usually already right. A setting it will not decide is listed with its reason
under "NOT DECIDED", and `advise` with no answers leaves `fdr_alpha` there
rather than inventing a prior.

Every value round-trips through `get_perform_regression_default_settings`, and
every regression_type it can propose is in `REGRESSION_TYPES` -- a proposal
spaCR would refuse is worse than no proposal.

D. THE INTERCEPT: ANSWERED BY `baseline.py`, AND NOT BUILT.

"Worth checking against baseline.py before building anything." It was, and the
answer is there in its own words, measured: "Re-fitting a planted effect with
the row reference moved from r01 to r03 shifts the intercept by 0.806 and
changes not one guide or gene coefficient. A control for it would be a control
a user could set, watch the volcano not move, and reasonably conclude was
broken."

Every guide and every gene gets a coefficient -- none is dropped as a
reference, because they appear only in interaction with a continuous term, so
full coding applies. What a user actually wants from "define the intercept" is
what the effects are measured FROM, and that is `spacr.baseline`, which is
already on the volcano's right-click menu, already saved in `plot_state` and
already restored with a run. Building a formula-intercept control would add a
knob that provably does nothing.

TWO BUGS FOUND WHILE BUILDING IT, both fixed:

  * `gene_of_guide` HARD-CODED FOUR TOXOPLASMA STRAINS. `PF3D7_0100100_1`
    returned `PF3D7` -- the organism -- for every guide in a Plasmodium
    library, pooling the entire screen into one "gene". That is instruction
    184's assumption reached by a different route. It reads the name's SHAPE
    now (`<organism>_<gene>_<guide>`, which is what `process_reads` writes)
    and takes a MEASURED prefix when a caller has the library in hand.

  * 185's PLATE MAP APPEARED ON NOTHING. The row builder hands
    `('Control wells', widget)` and the rule matched on the setting NAME, so
    `control_wells != 'Control wells'` and every field took the no-op branch.
    185's tests drove `pick_wells_for` and `PlateMapPicker` directly and both
    worked, so the instruction was closed while the button was unreachable.
    The key is read off the widget now, and
    tests/qt/test_the_plate_map_button_is_on_the_panel.py starts from the
    built panel -- which is the only kind of test that could have caught it.
