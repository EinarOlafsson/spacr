--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

spaCR has two ways to turn an image into numbers, and both require you to
already know what you are looking for.

  * MEASURED FEATURES. `spacr/measure.py` and the `spacr/measurement_*`
    family compute a fixed, hand-designed panel -- intensity, shape, texture,
    and the distances in `spacr/object_distances.py`. Excellent, auditable,
    and closed: it measures what somebody thought to name.

  * SUPERVISED CLASSIFICATION. `spacr/deep_spacr.py`, `spacr/classify.py` and
    `spacr/flowview/classify_blueprint.py` fine-tune ImageNet backbones --
    resnet18/34/50/101/152, convnext_tiny..large, efficientnet_b0..b7 and
    _v2_s/m/l, vit_b_16/b_32/l_16/l_32, maxvit_t. Every one of them needs
    labels, and labels need a phenotype somebody can already describe.

WHAT DOES NOT EXIST: any self-supervised or foundation-model embedding.
Grepped 2026-09-09 across the package -- no DINOv2, no OpenPhenom, no
SubCell, no scDINO, no CLIP-style image encoder used as a feature extractor.
Every backbone in the tree is a supervised ImageNet classifier being
fine-tuned.

WHAT ALREADY EXISTS AND WOULD CONSUME IT, unchanged: `spacr/umap.py` and
`spacr/umap_search.py`, `spacr/regression_backends.py` and the whole
regression family, `spacr/hits.py` and `spacr/hit_attribution.py`,
`spacr/batch_correction.py`, `spacr/anndata_export/`. The downstream is
already built for a wide numeric matrix keyed by object. It does not care
where the columns came from.

AND THE PLUMBING EXISTS TOO: `spacr/model_zoo.py` (published checkpoints with
checksums, per instruction 370), `spacr/torch_artifacts.py`,
`spacr/checkpoint.py`, `spacr/mixed_gpu.py`, `spacr/accelerator.py`.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A pooled CRISPR screen exists to find a phenotype nobody has named yet. Both
current paths make that hard in the same way: the measured panel finds only
what was designed in, and the supervised path finds only what was annotated.
A screen whose real hit is "the vacuole is subtly mislocalised in a way we
have no column for" returns nothing, and returns it confidently.

Self-supervised embeddings are the standard answer to that, and they need no
labels at all.

BUT DO NOT SELL THEM AS "BETTER", BECAUSE THE BENCHMARKS DO NOT SAY THAT --
corrected here 2026-09-10, because the first version of this file did say it
and it was wrong. The literature is genuinely split:

  * Cell-DINO (PLOS Comput Biol) beats a supervised ViT by ~20% on average on
    the Human Protein Atlas, and by ~70% using only 1% of the labels.
  * JUMP-lite, the compact reproducible benchmark of cell representations,
    puts CLASSICAL CellProfiler features in the leading aggregate tier,
    alongside MorphEM and ahead of several foundation models.

So the honest claim is COMPLEMENTARITY AND LABEL-EFFICIENCY, not superiority:
embeddings see structure the panel was never designed to encode, and they get
there without annotation. Which one wins depends on the task, and a screen
should be able to try both. Anyone who writes "embeddings outperform measured
features" into a paper on the strength of this file will be contradicted by
JUMP-lite, and should not be able to say the instruction told them so.

The cost of the gap is invisible, which is what makes it worth writing down:
you do not see the hits you had no column for.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. `spacr/embeddings.py` -- the engine. One entry point that takes the same
   crops the classifier path already produces (`spacr/crops.py`,
   `spacr/crop_source.py`) and returns a float32 matrix keyed by object id.
   No new cropping, no new I/O.

2. THE CHANNEL PROBLEM IS THE DESIGN PROBLEM, and it must be settled first.
   These encoders expect three channels; spaCR images routinely have four or
   five with no RGB meaning. Decide and record: per-channel encoding then
   concatenation (keeps channel identity, costs N forward passes), or a
   learned/fixed projection to three (one pass, mixes channels). Do not let
   this be decided implicitly by whatever the first backbone wants.

3. Register the encoder in `spacr/model_zoo.py` like any other published
   model, with its checksum. Instruction 370's scorecard applies: an
   embedding that ships without one is a black box twice over.

4. The column family in `spacr/measure.py` -- a documented prefix so
   embedding dimensions never collide with measured features, and so
   `spacr/columns.py` and `spacr/column_groups.py` can group them for the UI
   and for `spacr/attribution_columns.py`.

5. Only then the consumers, none of which should need changing: UMAP,
   regression, hit calling, anndata export.

6. A GUI SURFACE -- AND THIS IS NOT THE AFTERTHOUGHT IT LOOKS LIKE. Build the
   engine first, because it is useful from the API on day one and the screen
   can follow the way Dose-Response's did. But note what the survey of the
   field turned up on 2026-09-10: Cell-DINO, OpenPhenom and SubCell are ALL
   Python/CLI, and NO GUI PLATFORM EXPOSES ANY OF THEM. CellProfiler does not,
   napari has no maintained plugin for it, QuPath does not.

   That makes the screen the single largest adoption argument in this file.
   The engine serves this lab; the screen is what would make spaCR the only
   clickable route to a foundation-model embedding, for a Cell Painting and
   image-profiling community that currently has to write Python to get one.
   Weigh it that way when it is scheduled, rather than as polish.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

THE MEASUREMENT IS RETRIEVAL, NOT LOSS. Take a plate where the answer is
already known -- a positive control gene with a phenotype the measured panel
already detects. Embed it, then ask whether the control wells retrieve each
other: k-nearest-neighbour accuracy on gene identity, embeddings versus the
measured panel, same wells, same split.

  * SUCCESS: embeddings match or beat the measured panel on that retrieval.
  * THE INTERESTING RESULT: embeddings separate something the panel does not.
    That is the whole point and it needs a human to look at the crops before
    it is believed.
  * FAILURE THAT LOOKS LIKE SUCCESS: separation that tracks plate, batch or
    illumination rather than gene. Check against `spacr/batch_correction.py`
    and `spacr/plate_qc.py` BEFORE reporting any result. An embedding is an
    excellent batch detector and will happily hand you one.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

TRAINING AN ENCODER FROM SCRATCH. Use published weights. A lab-trained
encoder is months of compute to arrive somewhere near the public checkpoint,
and it cannot be compared to anybody else's result.

REPLACING THE MEASURED PANEL. Embeddings are added alongside, never instead.
The panel is interpretable and a reviewer can be told what a column means;
an embedding dimension has no such sentence. Instruction 364's question --
is this setting needed, is its name honest -- cannot even be asked of a
column called `emb_0347`.

PSEUDOTIME AND TRAJECTORY INFERENCE on top of the embedding. Considered and
rejected: these are fixed-cell endpoint screens, and a trajectory through
fixed cells is an ordering the data cannot support.

THE CONFOUND WAS THE POINT, AND IT DOES NOT DEFEAT THIS DESIGN. Gene identity
is perfectly confounded with plate column -- SAG1 is always c1, GRA14 always
c2, adjacent. So position was measured, not assumed:

  * C and D read CHANCE. Two adjacent pooled-library columns, 150-390 genes
    mixed in each, no systematic biology: 0.494 and 0.514 balanced.
  * EXTENDED TO A DISTRIBUTION. The identical measurement on all 20 adjacent
    library-column pairs c4..c24: embeddings mean 0.505 sd 0.009 (range
    0.488-0.521), panel mean 0.504 sd 0.024 (range 0.457-0.553). c1-c2 sits
    +22.0 SD (embeddings) and +16.5 SD (panel) above that null. ADJACENT PLATE
    COLUMN POSITION IS WORTH NOTHING HERE.
  * MATCHED N. C/D has a third of A/B's objects, so A/B was cut down to
    exactly C/D's size (2,818/3,112 over 16/13 wells, 5 resamples): embeddings
    0.713+/-0.005, panel 0.905+/-0.005. C is not at chance for want of data.
  * k=5/15/51 changes nothing: A 0.676/0.695/0.702, B 0.882/0.894/0.889,
    C and D stay inside 0.49-0.52.
  * The panel's 16 absolute-centroid columns alone score 0.510 on A/B. Field
    position carries no gene signal.

THE CHECKS THIS FILE DEMANDS BEFORE REPORTING, AND ONE NEAR-MISS.
`spacr.plate_qc.detect_edge_effect` on the whole plate, on the feature that
best separates c1 from c2 (cell_channel_2_shannon_entropy): NO edge effect
(Cliff's delta -0.03, p=0.71) but IT DOES FLAG A MONOTONIC COLUMN GRADIENT,
Spearman rho = -0.552, p < 1e-4, -12.7% across columns 1->24. Read on its own
that is this file's "failure that looks like success" arriving exactly on
schedule.

IT IS NOT ONE, AND THE PER-COLUMN PROFILE IS WHY. Column medians: c1 5.616,
c2 6.412, c3 5.590, then c4..c24 flat and slowly declining from 5.04 to 4.90.
c2 stands 0.80 ABOVE BOTH ITS NEIGHBOURS. A gradient is monotonic by
definition and cannot put a peak between two near-equal columns; the rho is
carried by the three control columns at the left edge being unlike the
library, not by a ramp. The 20-pair sweep above spans the steepest part of
that gradient (c4-c5, c5-c6, c6-c7) and reads chance. The gradient is real,
it is worth logging for any per-well aggregate analysis, and it does not
explain A or B.

`spacr.batch_correction.correct_batch_effects`, method='center', batch =
plate ROW -- a genuine position axis that is NOT confounded with gene, since
every row holds both a c1 and a c2 well. Batch centroid spread driven to zero
(panel 87.98 -> 0.0000, embeddings 0.0036 -> 0.0000) and the answer does not
move: A 0.696 -> 0.694, B 0.894 -> 0.891, C 0.503 -> 0.513, D 0.514 -> 0.501.
Correcting by COLUMN is not available and never will be on this layout: it
would delete the contrast, which is the NO_COVARIATE trap that module's own
docstring describes.

NOT A CHANNEL HANDICAP, WHICH WAS THE OBVIOUS EXCUSE. The crops carry
png_dims=[0,1,2]; the panel also measures channel 3 (40 of its 156 columns).
Restricting the panel to the same three channels does not close the gap, it
WIDENS it: 0.905 balanced versus the embeddings' 0.696. The encoder is not
losing because it was shown less.

WHAT THIS MEANS FOR THE CLAIM THIS FILE ALREADY REFUSED TO MAKE. The file was
right not to sell embeddings as "better", and this is the local version of
JUMP-lite: on the one retrieval task this screen can adjudicate, a classical
hand-designed panel beats an off-the-shelf ImageNet resnet18 by ~20 points of
balanced accuracy. What was measured is DEFAULT-SPEC resnet18, not
Cell-DINO/OpenPhenom/SubCell, and ImageNet-supervised ResNet features are the
weakest thing the module can be pointed at -- the complementarity and
label-efficiency argument is untouched, and a real self-supervised backbone is
the obvious next measurement. But nobody may now write "embeddings match the
measured panel in spaCR" on the strength of this file: on this plate, with
this encoder, they do not, and the number is 0.695 against 0.894.

STILL UNMEASURED, and deliberately not claimed here: "THE INTERESTING RESULT"
-- whether embeddings separate something the panel does not. That is not a
kNN number and this file already says it needs a human looking at crops.
Retrieval of a KNOWN phenotype is the wrong instrument for it: GRA14 is the
screen's top hit precisely because the panel already detects it.
