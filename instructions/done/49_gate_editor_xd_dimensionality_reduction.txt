--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not started. The gate editor has 2D / 3D / xD buttons. The request says
what xD was always meant to be and is not yet: a reduction of many
measurement columns down to the 2 or 3 axes actually plotted.

The engine for the hyperparameter tab already exists as of this session.
`spacr/hyperparam.py` has `walk_search`, `WalkAxis`, `walk_neighbourhood`
and `umap_walk_axes` -- an N-dimensional Walk over any subset of UMAP's
structural parameters, with per-axis resolution and a per-round cost cap.
`spacr/qt/screens/hyperparam.py :: HyperparamPanel` is the panel, already
shared by four modules, and `WalkAxesDialog` is its space picker.
Instruction 34 is that work; its last open part is the presentation grid.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Gating on two raw measurements at a time cannot find a population defined
by twenty of them, which is what a CRISPR screen's phenotypes usually are.
Reduction is how the user sees that structure at all; without it the gate
editor can only express hypotheses simple enough to have been guessed in
advance.

The column picker is the part that decides whether the reduction means
anything. A UMAP over every numeric column in the table mixes plate
identity, well position and object ID in with the biology, and the
structure that comes out is dominated by batch rather than phenotype.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. BUTTON SEMANTICS. 2D and 3D are mutually exclusive -- they are the
   output dimensionality. xD is INDEPENDENT and toggles reduction on. So
   the legal states are 2D, 3D, xD+2D, xD+3D, where the last two mean
   "reduce to two/three components and plot those". Today's grouping
   presumably makes all three exclusive; that is the bug.

2. METHOD. A dropdown: UMAP, t-SNE, and whatever else is available. Build
   the list from the INSTALLED libraries the way `umap_metrics()` does in
   `spacr/hyperparam.py`, with a literal fallback, so the panel still
   builds on a machine that cannot run the reducer -- configuring a run on
   a laptop and executing it elsewhere is ordinary here.

3. COLUMN PICKER, two ways into the same selection:
       individual  -- a searchable list of the table's numeric columns
       by category -- "cell", "channel_1", intensity, morphology, ...
   The categories are name-derived, so they need to be derived from the
   actual column names rather than hard-coded: measure writes predictable
   prefixes/infixes, and a channel picker ("channel i") selects the
   per-channel intensity family for one channel at a time.
   Whichever way the user picks, the RESULT is one explicit list of
   columns, shown back to them and saved with the gate. A reduction whose
   inputs are implied by a category name that later matches different
   columns is not reproducible.

4. TABS. The features section becomes one tab among several. One tab is
   the hyperparameter test, shown when the method has hyperparameters
   (UMAP, t-SNE). Reuse `HyperparamPanel` rather than building a second
   search UI -- it already carries the Walk, the metric dropdown, the
   axes picker and the cost estimate, and instruction 34 renamed the mode
   to "Walk" in BOTH modules specifically so this could be shared.

5. t-SNE HYPERPARAMETERS. `UMAP_WALK_PARAMETERS` is UMAP-only. t-SNE needs
   its own table (perplexity, early_exaggeration, learning_rate, n_iter)
   in the same shape, so `umap_walk_axes` generalises to
   `walk_axes_for(method, ...)` rather than being copied.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Turn on xD with 3D selected, pick UMAP, select the intensity columns for
channel 1 by category, and get a 3-component embedding plotted as a 3D
scatter that can be gated (instruction 48). The chosen columns are listed
back explicitly. Switch to t-SNE and the hyperparameter tab offers
perplexity rather than n_neighbors. 2D and 3D cannot both be active; xD
can be active with either.

2026-08-13 - AUDITED, AND THE COLUMN CHOICE IS BUILT
--------------------------------------------------------------------------------

The header says "not started". It is not: `reduce_to_components`
(qt/screens/gate_editor.py:585) already reduces and gates on the components,
reading `settings.reduction` and `settings.components`, and
`merge_tables.REDUCTIONS` offers pca / umap / tsne. The components come back
as ORDINARY COLUMNS, so every existing gate tool works on them unchanged --
which was the right design and is worth not re-deciding.

WHAT WAS ACTUALLY MISSING is the middle of the request. The reduction ran
over `plottable_columns(frame)` -- EVERY numeric column, with no way to
choose. A screen's phenotype usually lives in a subset, and reducing over all
400 columns buries it; worse, that set includes identifiers, and feeding a
plate id to UMAP embeds the plate, which is the batch effect rather than the
biology.

BUILT: `spacr/column_groups.py`, the Qt-free half of the picker.

    object      cell, nucleus, pathogen, cytoplasm, organelle
    channel     channel_0, channel_1, ...
    family      morphology, intensity, texture, correlation, moment

Three kinds because a table names a column three ways at once --
`cell_channel_1_mean_intensity` is a CELL measurement, a CHANNEL 1
measurement and an INTENSITY measurement -- and which one a user means
depends on the question. That is exactly the maintainer's own list: "cell, cor
channel_1 or intensity measurements ... or morphology measurements".

THE FAMILIES ARE NOT INVENTED HERE. They are
`feature_dict.FEATURE_FAMILIES`, classified by `feature_dict.parse_column` --
the dictionary that already documents every column. A second taxonomy would
be a second thing to keep in step with the measurement code and would
disagree first in the corners nobody checks.

DECISIONS WORTH KEEPING:

  * `meta` is not offered as a group, and no group selects an identifier --
    but an identifier can still be ticked by hand. Not offered is not the
    same as forbidden.
  * Groups and individual columns ADD UP; the request asks for both, not
    either.
  * The result is ordered by the TABLE, not by click order. A UMAP whose axes
    depend on which checkbox was clicked first is not reproducible.
  * Channels sort numerically, so channel_2 comes before channel_10.

20 tests, registered in `_SUBMODULES`, no display needed.

2026-08-13 (later) - TWO DIAGNOSTICS, FROM starplast, AND ONE OF THEM HAD TO BE
                     CHANGED TO CATCH spaCR's ACTUAL ARTEFACT
--------------------------------------------------------------------------------

Requested: 2026-08-13 - "for 49 and 52 take inspiration from starplast
           (/mnt/firecuda2/Claude/repo/starplast)"

starplast built the same picker against a different table and learned two
things worth not re-learning. Both are now in `spacr/merge_tables.py`:

`group_variance_share(frame, {group: columns})`
    How much of the projected variance each ticked group actually carries. It
    catches a group named as an input and contributing nothing -- starplast
    found one at 1.1% -- which nobody notices, because a projection ALWAYS
    produces a picture. Describes the INPUT matrix, prepared exactly as
    `reduce_dimensions` prepares it, so it is valid for UMAP and t-SNE too;
    those have no loadings to inspect but they see this same matrix.

`missingness_leak(components, frame, columns)`
    Does "was this object measured" predict where it landed?

THE SECOND ONE IS WHERE THE PORT STOPPED BEING A PORT. starplast reports a
CENTROID GAP -- how far apart the measured and unmeasured objects sit, in map
radii. Measured on a synthetic spaCR table with twelve pathogen columns and
35% uninfected cells:

    centroid gap        0.057 radii     <- essentially nothing
    dispersion ratio    0.105           <- the artefact

THE CENTROID STATISTIC ALONE WOULD HAVE MISSED IT. `reduce_dimensions` fills
gaps with the COLUMN MEDIAN, deliberately -- dropping the row instead loses
every measurement the object did have. But a median fill puts the uninfected
cells in the MIDDLE of the infected ones, not away from them, so the two
centroids nearly coincide while the uninfected collapse onto a single point
and keep a tenth of the spread. Displacement is starplast's artefact;
COLLAPSE is spaCR's, and they need different statistics.

Both are reported, with `severity` the worse of the two, and both artefacts
are pinned by a test built from constructed coordinates rather than from a
fitted reducer.

WHY THIS MATTERS AND IS NOT A NICETY: a projection that splits infected from
uninfected on the FACT of measurement is real, reproducible, and not a
phenotype. It is exactly the kind of split someone would write up. The
picker's whole risk is that reducing 400 columns buries the biology, and
these two say which columns are driving the picture and whether the answer is
an artefact.
