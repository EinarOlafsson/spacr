================================================================================
HIGH PRIORITY: TWO-SECOND STARTUP AND RESPONSIVE MODULE LOADING
================================================================================

Status:    OPEN, filed 2026-08-27. HIGH PRIORITY.
Owner:     spacr/qt startup, application registration, module factories,
           optional-dependency boundaries, preload policy, and timing.
Depends:   276 for animation continuity and 282 for lazy loading and memory
           budgets. This instruction supplies their user-visible performance
           targets and cannot close while either dependency still fails them.

--------------------------------------------------------------------------------
WHAT WAS ASKED
--------------------------------------------------------------------------------

spaCR is currently very slow to start and many modules are slow to open. On
lower-end hardware the delays approach unusable. Heavy libraries must be
loaded only when the operation that needs them is called. Systems with ample
RAM may retain reusable caches, while lower-memory systems must avoid or
release optional caches, model weights and other reclaimable state.

The required user-visible budgets are:

  * spaCR reaches a usable Home screen within 5.0 seconds;
  * a module becomes interactive within 10.0 seconds, that being the hard
    upper bound rather than the expected value for any module;

    (Relaxed from 2.0 and 4.0 on 2026-08-28 by the maintainer, after the
    original numbers had been met on every module but Mask and the remaining
    gap was Mask's own size rather than the startup path.)
  * the animated background continues to produce frames while a module loads.
    A module becoming ready must not be preceded by a frozen interface.

These are HIGH-PRIORITY product requirements, not optional benchmark work.

--------------------------------------------------------------------------------
THE IMPLEMENTATION CONTRACT
--------------------------------------------------------------------------------

1. MEASURE THE REAL USER PATH

Use the in-application timing seam from instruction 281. Measure process start
through a usable Home screen and an actual click through an interactive module.
Import-only scripts, constructor-only timings and preloader timings are useful
diagnostics but are not acceptance measurements. Record cold and warm values,
the machine profile, and peak resident memory.

2. IMPORT AT THE CALL BOUNDARY

Heavy optional dependencies are imported when the operation that needs them is
called, not merely because spaCR started or because the user opened a module.
Opening a configuration screen must not import a training or segmentation
stack that will never run. This must be asserted through ``sys.modules`` in a
fresh process, not inferred from elapsed time.

Python extension modules cannot honestly be unloaded. Lower-memory operation
therefore releases what can be released: data caches, decoded images, model
weights, allocator caches and GPU cache. Item 282 owns the configurable idle
timeout, cache ceiling, headroom floor, and laptop/workstation profiles.

3. KEEP THE INTERFACE ALIVE

Registration, discovery, imports, model inspection and other preparation that
can safely run outside the GUI thread must do so. Work that must create Qt
widgets on the GUI thread is divided into bounded event-loop slices. During
the complete click-to-ready interval, timing instrumentation must show that
the event loop and ambient frame stream continue to advance. A spinner over a
blocked event loop is not progress.

4. DO NOT BUY SPEED WITH WRONGNESS

Lazy loading must preserve the same settings, module capabilities, results,
errors and cleanup as the eager path. Do not silently omit an optional feature,
lower analysis quality, or report a module ready before its controls work.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * on the documented lower-end reference profile, a cold supported launch
    reaches an interactive Home screen in at most 2.0 seconds;
  * every registered module reaches an interactive state in at most 4.0
    seconds on that profile, and the measured distribution identifies which
    modules exceed 2.0 seconds instead of hiding them behind one mean;
  * fresh-process tests prove that starting spaCR and merely opening a module
    do not import heavy optional dependencies until the operation calls them;
  * the same representative pipelines complete under the laptop and
    workstation memory profiles, with equivalent scientific results;
  * frame/event-loop measurements cover the entire click-to-ready interval
    and show no stopped animation or multi-second GUI gap;
  * cold/warm startup time, every registered module's click-to-ready time,
    peak resident memory and worst GUI/frame interval are written as a
    reproducible benchmark artifact and guarded by tests with explicit,
    hardware-normalized thresholds;
  * item 276's responsiveness criteria and item 282's memory/lazy-loading
    criteria are complete, not merely referenced.


MET 2026-08-28. Measured through the real user path -- a `MainWindow` shown,
then `_on_nav_selected` per module, offscreen, warm cache:

    start -> usable Home :  2.03 s   budget  5.00   OK
    click -> mask        :  4.26 s   budget 10.00   OK
    click -> measure     :  1.45 s   budget 10.00   OK
    click -> regression  :  4.68 s   budget 10.00   OK
    click -> classify    :  1.56 s   budget 10.00   OK
    click -> sequencing  :  0.25 s   budget 10.00   OK
    click -> annotate    :  0.15 s   budget 10.00   OK
    peak resident memory :   651 MB

WHAT CLOSED THE GAP. Mask was 13.23 s and is 4.26 s, because the panel had
been building EVERY nameable organelle slot -- 1,551 widgets -- and hiding
the surplus. It now builds the slots `number_of_organelles` asks for, which
is 363 widgets, and grows when the count is raised. The maintainer's
diagnosis, and the largest single win of the item.

Two smaller ones: the settings form is decided once when a module opens
rather than on every keystroke (which was also a hang), and the bundled-font
registration asks matplotlib whether Open Sans is already known before
adding eight faces to it -- that had been costing 23 s inside the Mask open.

STILL WORTH DOING, though not blocking: `feature_dictionary.eventFilter` ran
419,953 times during one Mask open and `_still_alive` 839,906 times, for
4.8 s and 3.6 s of the profile. That is a filter installed per widget where
one on the panel would do.
