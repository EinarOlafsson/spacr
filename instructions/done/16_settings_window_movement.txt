================================================================================
SETTINGS WINDOW: DRAGGING IT UN-MAXIMIZES THE MAIN WINDOW
================================================================================

Status:    done - 2026-08-06, needs a look on the desktop
Requested: 2026-08-06 — "whenever i have a settings window up and try to move it the main app goes from full screen to boxed and the settings window is anchored to the middle of the window. i should be able to freely move the settings window irrespective of the main window state"

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not investigated. The symptom — a child moving its parent, and the child
being pinned to the parent's centre — is what happens when a dialog is a
frameless child QWidget with a hand-rolled drag handler, rather than a real
top-level window.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Two bugs in one gesture: the main window loses its maximized state, and the
dialog cannot be placed where the user wants it.

--------------------------------------------------------------------------------
WHAT WAS DONE
--------------------------------------------------------------------------------

The cause was not in the dialogs. A QDialog with a parent is transient-for
that parent, exec() makes it modal, and a WM implementing ATTACHED MODAL
DIALOGS (GNOME/Mutter, by default) glues that combination to its parent:
drawn centred on it, undraggable, and pulling at it manipulates the parent.

The user's own observation is what identified it: broken in Preferences and
Annotate settings, fine in the crop live settings, the Mask live preview
settings and Classify's hyperparameter settings. The first two are opened
with .exec(); every other one is opened with .show(). Modal vs modeless,
which is the WM's rule exactly.

spacr/qt/dialogs.py :: detach_from_window_manager clears Qt.Dialog from the
window type and sets Qt.Window, so the WM sees an ordinary top-level window.
Applied in preferences.PreferencesDialog and annotate._SettingsDialog.

Gotcha worth keeping: Qt.Dialog is (Qt.Window | 0x2), so clearing it clears
the Window bit too and it must be put back. Setting Qt.Window alone leaves
the dialog bit standing and changes nothing.

Parent kept and modality untouched, deliberately - see the module docstring
for what dropping the parent or going modeless would cost.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Maximize the main window, open settings, drag the dialog: the main window
stays maximized and the dialog lands where it was dropped.

--------------------------------------------------------------------------------
VERIFIED, AND WHAT IS NOT
--------------------------------------------------------------------------------

    QT_QPA_PLATFORM=offscreen python -m pytest tests/qt/test_dialog_detach.py \
      tests/qt/test_preferences.py tests/qt/test_preferences_reset.py \
      tests/qt/test_annotate.py -q -p no:randomly

green. Measured: an untouched QDialog(parent) reports window type Dialog;
both of these report Window, keep their parent, and still return Accepted
from accept().

NOT VERIFIED: where the window actually lands. That is the window manager's
decision and there is no window manager under QT_QPA_PLATFORM=offscreen.
The tests assert that spaCR has stopped ASKING to be attached. Someone has
to maximise the main window on a real desktop, open Preferences, and drag
it. If it still attaches, the next thing to try is dropping the parent and
managing stacking manually - the trade-offs are in the module docstring.
