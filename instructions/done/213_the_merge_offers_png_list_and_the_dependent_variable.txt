--------------------------------------------------------------------------------
B. HOW THE DEPENDENT VARIABLE JOINS, WITH TWO FALLBACKS
--------------------------------------------------------------------------------

    "in my cas the dependent variable has plate, row, col, field, object
     which is enough to join with cell table but it also necessarily has the
     path to each image with is necessarily plate_well_field_object which can
     be split into its parts and merged directly or well translated into row
     and column and (with the format r1 and c2) and merged into the cell
     table so the latter two can be backups if any of the plate, row, col,
     filed, object columns cant be found or are missed for wahtever reason."

THREE ROUTES, TRIED IN ORDER, and the order is the instruction:

  1. THE ID COLUMNS. `plateID`, `rowID`, `columnID`, `fieldID`, `objectID`.
     The direct join, used whenever all five are present.

  2. SPLIT THE IMAGE PATH. The path is necessarily
     `plate_well_field_object`, so the five parts can be recovered from it.
     Used when a column from route 1 is missing.

  3. TRANSLATE WELL TO ROW AND COLUMN. The well from the path becomes
     `r1` / `c2`, which is the spelling `png_list.rowID` already uses --
     `spacr/predictions.py` documents that this column returns `'r1'`,
     `'r2'` rather than a number, and a route that produced `1` would not
     match.

A FALLBACK IS A FALLBACK, NOT A SECRET. Which route was used goes in the
merge report, with the number of rows it matched. A join that silently
changed method is a join whose result cannot be reasoned about, and route 2
recovering what route 1 should have supplied is a fact about the data worth
knowing -- it means a column is missing upstream.

AND A ROUTE THAT MATCHES NOTHING IS A FAILURE, not an empty answer. The same
rule instruction 203 states for the object tables.

--------------------------------------------------------------------------------
C. THE COLUMN NAMES ARE THE IMPORT'S, EVERYWHERE
--------------------------------------------------------------------------------

    "these columns will of course be interperated as plateID, rowID,
     columnID, fieldID, objectID, as the import logic dictates for
     standardization (which should be true acress the board in spacr)."

`plateID`, `rowID`, `columnID`, `fieldID`, `objectID` -- the import's
spelling, applied here and ACROSS THE BOARD. The parenthesis is a general
instruction, not an aside about this dialog: a module reading `plate` where
the rest of spaCR writes `plateID` is a module that will silently match
nothing the first time it meets a real database.

So this instruction has a second half: find where the spellings disagree and
make them agree. `spacr/predictions.py` already records one trap worth
reading before starting -- `png_list` has a `rowID` column, and SQLite will
answer a query for it with the plate row rather than the row number, which
is how a test built by hand without that column passed while the real table
did not.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* `png_list` and the dependent variable are both boxes on the merge control
  and both merge.
* The dependent variable joins by the ID columns when they are there.
* Removing one ID column falls back to the path split and STILL JOINS, and
  removing the path falls back to row/column translation.
* The report names the route used and the rows matched.
* Zero matches is reported as a failure.
* The five identifier spellings agree across spaCR, checked by a test that
  greps for the wrong ones rather than by inspection.

DONE 2026-08-21

A. Both boxes are on the merge control. `png_list` is ticked by default --
it carries the classification score, which is in none of the object tables.

B. `spacr/dependent_join.py`. THREE ROUTES IN THE INSTRUCTION'S ORDER, and
the report names the one used with the rows it matched. A fallback is
labelled a fallback in those words, because the degradation is itself worth
knowing: it means a column is missing upstream.

THE OBJECT SIDE KEEPS ITS OWN COLUMNS when it has them. Making BOTH sides go
through the path because the DEPENDENT table was missing a column would
break a join the ID columns would have made -- only the side with something
missing falls back.

ZERO MATCHES RAISES. A route that matches nothing is a failure, not an empty
answer, and the message lists every route tried and why each failed.

THE WELL TRANSLATION PRODUCES 'r1' / 'c1', not 1 and 1.
`spacr/predictions.py` records that `png_list.rowID` returns 'r1', and a
route producing a bare number would match nothing -- a failure that looks
exactly like a screen with no overlap.

C. `objectID` WAS THE ONLY ONE OF THE FIVE WITH NO SCHEMA CONSTANT. That is
how `object_id` came to be a column name spelled several ways while
`plate_id`, `row_id`, `column_id` and `field_id` were all normalised.
`schema.OBJECT_KEY` now exists and `object_id` / `objectid` /
`object_number` canonicalise to it.

A BARE `object` COLUMN IS DELIBERATELY NOT ALIASED. In a measurement table
it as often means the object TYPE -- cell, nucleus, pathogen -- as the
object's number, and renaming that into an identifier would corrupt the join
it lands in rather than merely mislabel a column. That is the same trap the
`canonical_column_name` docstring already records for `c`.

THE WIDE AUDIT FOUND NO OTHER DEFECT. Every remaining `plate` / `row` /
`field` string literal in spaCR belongs to an internal dict the same module
built -- `sample_identity`'s parse result, the file-list table -- rather than
to a database read, so renaming them would have been churn.

`dependent_join` reads its names OFF `spacr.schema` rather than respelling
them, because a second copy of the names in this file is exactly the module
that silently matches nothing, waiting to happen.
