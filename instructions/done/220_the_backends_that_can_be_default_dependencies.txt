WHICH REGRESSION BACKENDS CAN BE DEFAULT DEPENDENCIES
================================================================================

MEASURED 2026-08-21, NOT ESTIMATED
--------------------------------------------------------------------------------

    backend     resolves        weight        requires-python   verdict
    pyfixest    0 new pkgs      installed     >=3.10            DEFAULT
    glum        0 new pkgs      installed     >=3.10            DEFAULT
    gpytorch    2 new pkgs      288 KB        >=3.10            DEFAULT
    numpyro     6 new pkgs      88 MB         >=3.11 (jax 3.12) EXTRA
    pymer4      1 new pkg       small         needs R           EXTRA, always

spaCR declares `>=3.9,<3.15`. TORCH ITSELF REQUIRES >=3.10, and so do
pyfixest and glum -- both of which are already installed in the development
environment, which is why the panel reports them "unavailable: no mixed
model" rather than "not installed". Their message is about a missing
CAPABILITY, not a missing package, and that distinction is worth keeping
visible.

  * gpytorch adds NO new floor beyond the one torch already imposes, and
    288 KB. It is the clearest case for promotion.
  * numpyro drags jax and jaxlib. jaxlib is 84 MB and requires Python >=3.12,
    so as a default it would be unavailable on half the interpreters spaCR
    supports while adding 88 MB for every user who never selects it.
  * pymer4 CANNOT be a default at any version gate. It needs R, rpy2 and
    lme4, and R is a system package pip cannot provide -- there is no R
    binary on this machine, so `pip install pymer4` would succeed and the
    backend would still not run. The panel already says "plus R, rpy2,
    lme4", which is the honest wording and should stay.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* pyfixest, glum and gpytorch are core dependencies, each gated
  `python_version >= "3.10"`.
* A 3.9 install still succeeds and still runs, without them.
* numpyro and pymer4 stay extras, and pymer4's message keeps naming R.
* The packaging metadata test covers the new gates.

--------------------------------------------------------------------------------
AND THE FLOOR ITSELF: >=3.9 IS HONEST, MEASURED 2026-08-21
--------------------------------------------------------------------------------

    "lets keep the 3.9 to 3.10 as long as 3.9 user are able to install older
     versions of torch with pip install spacr. if we have set torch>=2.0 cant
     we lower that in setup.py?"

NOTHING NEEDS LOWERING. `torch>=2.0,<3.0` already resolves on Python 3.9 --
torch shipped cp39 wheels through 2.8.0, which is comfortably inside the
range. A 3.9 user gets torch 2.8.0 rather than 2.13.0, which is exactly the
"older version" the question assumes and did not need arranging.

Every other core floor resolves on 3.9 too, checked against PyPI rather than
assumed:

    numpy         >=1.26.4  ->  2.0.2 on py3.9
    pandas        >=2.2.1   ->  2.3.3
    scipy         >=1.12.0  ->  1.13.1
    scikit-learn  >=1.5.0   ->  1.6.1
    torch         >=2.0     ->  2.8.0

So `requires-python = ">=3.9"` is a claim the dependency set can keep, and
lowering a floor would only widen the resolution space for interpreters that
already resolve.

WHAT THE FLOOR COSTS IN CODE IS ALMOST NOTHING: four files touch
`sys.version_info` and most only to REPORT it. There is no conditional
implementation to delete by raising it, so the case for raising is about
what it would unlock, and 3.11 unlocks nothing -- numpyro needs 3.11 but its
jax needs 3.12. The only floor that buys anything is 3.12, and the only one
that costs nothing is 3.10.

--------------------------------------------------------------------------------
WHAT WAS DONE
--------------------------------------------------------------------------------

`pyfixest`, `glum` and `gpytorch` are core dependencies, each gated
`python_version >= "3.10"` -- the floor `torch>=2.0` already imposes, since
torch's last cp39 wheel is 2.8.0. A 3.9 install does without all three and
still runs.

THE EXTRA NAMES SURVIVE AS ALIASES, with pins byte-identical to the core
ones. `pip install spacr[pyfixest]` keeps working for anyone scripting it,
and the identical string is required rather than tidy: there is a test
asserting an extra never contradicts core, because two pins for one package
is how an environment ends up with a version neither line asked for.

numpyro and pymer4 stay extras, and the reasons are in the table above.

Tests: `tests/test_the_gpu_falls_back_rather_than_failing.py` covers the
promotion and asserts the two exclusions stay excluded.
