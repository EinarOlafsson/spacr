--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Three separate features that share one screen. Build them separately.

Already exists and must be REUSED, not reinvented:
  * The GitHub auto-issue feature. `AppScreen` has "File as issue" and an
    opt-in already lives in AI Settings ("Report errors as GitHub issues").
    This task only moves the ASK to install time; the mechanism is built.
  * AI provider sign-in. The AI menu already has a provider picker and an
    install/login dialog. Same: move the ask, reuse the mechanism.
  * `spacr.qt.preferences` for anything persisted, and the run logs are
    already written per run -- `spacr.runctx.read_run_log(run_id)`, and
    `spacr/run_journal.py` writes a manifest beside them.

Nothing exists for sending logs anywhere.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Most spaCR faults are reported as a sentence and a screenshot. The run log
and the manifest answer nearly all of them and nobody has them. A user who
opted in once is a user whose next crash arrives already diagnosable.

The sign-in ask matters for a smaller reason: a user who has to find AI
Settings after their first crash usually does not.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

Read the CONSTRAINTS section below BEFORE designing the transport. It is
the part that is easy to get wrong and expensive to get wrong.

1. THE ASK. One installer page, three checkboxes, all defaulting to OFF:
   share logs / report errors as GitHub issues / sign in now. Each says
   in one sentence what it does and what leaves the machine. Every one is
   revocable later in Preferences, and the page says so -- an install-time
   choice that cannot be changed is a choice people decline.

2. LOG SHARING. Store the preference; do the sending from the APP, not the
   installer. An installer that mails something has no user to ask when it
   fails. Send on a real event -- a crash, or the user pressing "send" --
   never on a timer.

3. REDACT BEFORE SENDING, and show the user what will go. Run logs carry
   absolute paths, which carry usernames, and often the names of unpublished
   experiments. A preview with a "send" button is both the consent and the
   check.

4. ACCOUNTS. Reuse the existing provider login. Store tokens in the OS
   keyring (`keyring` is the standard; check whether it is already a
   dependency) and NEVER in QSettings, the settings CSV, or a run manifest
   -- the manifest is designed to be shared, which is exactly the problem.

5. THE ISSUE TOGGLE is the smallest of the three: it is one existing
   preference, asked earlier.

--------------------------------------------------------------------------------
CONSTRAINTS THAT DECIDE THE DESIGN
--------------------------------------------------------------------------------

DO NOT EMBED SMTP CREDENTIALS. Mailing spacr@gmail.com directly from the
client means shipping a password or an app token in the installer, where it
is readable by every user and revocable only by changing it for everyone.
It is also the kind of thing that gets an address rate-limited or closed.

Three transports that do not have that problem, in order of preference:

  a. THE GITHUB ISSUE PATH THAT ALREADY EXISTS. It is authenticated as the
     USER, it is already opt-in, and the report lands somewhere with a
     history. The log becomes an attachment or a fenced block. This is the
     cheapest correct answer and probably the right one.
  b. A COLLECTION ENDPOINT you control, posted to over HTTPS. Costs a
     service to run, but keeps the credential server-side.
  c. `mailto:` with the log attached, opened in the user's own mail client.
     No credential at all, and the user sees exactly what is sent before
     it goes -- at the price of them having to press send.

If the address in the request is a hard requirement, (c) reaches it without
shipping a secret and (b) can forward to it.

Also: whatever is chosen must fail QUIETLY and never block a run. Sending a
log is decoration in the sense of INVARIANTS 10 -- a failure to report a
crash must not become a second crash.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A fresh install shows the page with all three off. Opting in to logs and
then triggering a deliberate failure produces a preview naming the exact
file that would be sent, with paths redacted, and nothing leaves the
machine until the user presses send. Declining everything installs and runs
identically to today.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Nothing yet. Recorded here rather than in the code: the transport decision
above is the one to bring back to the maintainer before building, because
"send to this address" and "do not ship a password" pull in different
directions and only they can say which matters more.

2026-08-10 - THE DESTINATION IS DECIDED. THIS UNBLOCKS 45 AND 56.
--------------------------------------------------------------------------------

Requested: 2026-08-10 — "i want the destination to be the spacr repo issues i want option (a). the feature should be worded like these types of features normally are. in the installer there should be an agree to terms window where this is all explained."

DECISION: reports go to the PUBLIC spaCR repository's issues, opt-in, with
the consent taken in the installer.

That answers the question this file and instruction 56 have both been stalled
on since 2026-08-08. Option (a) was: a public repo, opt-in, with a clear
warning and a preview of exactly what is sent.

WHAT "WORDED LIKE THESE TYPES OF FEATURES NORMALLY ARE" HAS TO MEAN HERE, and
it is a higher bar than the phrasing suggests, because the destination is
public and permanent:

  * The installer shows an AGREE-TO-TERMS window explaining what is
    collected, where it goes, and that a GitHub issue is PUBLIC and
    world-readable. Opt-in means unchecked by default and usable if declined.
  * Say plainly that submissions cannot be unpublished. GitHub issues are
    indexed and mirrored; deleting one later does not retract it.
  * SHOW THE PAYLOAD BEFORE SENDING. Not a summary -- the actual text, in a
    scrollable, editable box, with a send button under it. A user who can see
    their absolute paths is a user who can remove them.
  * REDACT BY DEFAULT, then let them undo it. A crash report carries the OS
    username in every path (`/home/<name>/...`), plate and file names, and
    sometimes a data directory that names a collaborator or a grant. Replace
    the home directory with `~` and offer to strip filenames; do not rely on
    the user noticing.
  * No account, no telemetry, no background submission, and nothing sent
    without a click on that specific report.

WHAT ALREADY EXISTS AND MUST BE REUSED: instruction 56 fixed the issue URL
(it was 11,924 characters against GitHub's ~7,500 limit and produced a 404),
so the truncation logic is written. Whatever this builds must go through it
rather than assembling a second URL.

A CAVEAT WORTH KEEPING: an opt-in that is easy to click through is not
consent. The installer window is the right place BECAUSE it is a moment the
user is already reading and deciding, but the checkbox must not be
pre-ticked, and "Skip" must be as easy to press as "Agree".

2026-08-14 - COMPLETE: THREE OFF SWITCHES, EDITABLE PREVIEW, OFFICIAL CREDENTIAL OWNERS
--------------------------------------------------------------------------------

THE CONSENT SURFACE now exists in all installation paths. Windows has the NSIS
page; an interactive Linux/macOS bootstrap asks the same three questions; a
noninteractive package install records all three off and the installed app
shows the same page on first launch. The choices are:

    include redacted diagnostics in previews     OFF
    enable the public GitHub report action        OFF
    open account setup on first launch            OFF

The text says PUBLIC, world-readable, indexed/mirrored, and not reliably
unpublishable. It also says every choice is optional and revocable in
Preferences. Skip is the explicit keep-all-off action. The profile is applied
once to the existing runtime preferences; declining produces the same running
application as before.

THE REPORT PATH has one consent boundary per report. spaCR builds a sanitized
payload, strips filenames by default, and displays the exact editable title
and body. Cancel sends nothing. Only `Send report` hands that approved mapping
to the asynchronous transport. Diagnostic log lines are absent unless their
independent preference is on. Secret-shaped values, authorization headers,
home paths, database paths, and credential-named settings are redacted before
the preview. Transport failure is reported and never interrupts a scientific
run.

THE DESTINATION is the public EinarOlafsson/spacr issue tracker. An official
authenticated `gh` session can create the issue through GitHub's API; otherwise
spaCR opens the bounded pre-filled browser form. There is no SMTP secret and no
background telemetry. A test-process write guard prevents a forgotten mock
from ever filing another public fixture issue.

ACCOUNTS deliberately do not collect credentials inside spaCR. GitHub uses
`gh auth login`; Claude, GPT/Codex, and Gemini use their vendors' official
coding-agent CLIs. Those tools own their credential stores, and the provider
dialog is opened on first launch when requested. spaCR stores no durable PAT,
API token, password, QSettings credential, settings-CSV credential, or run-
manifest credential; insecure legacy QSettings PATs are erased when found.
This replaces the requested installer credential entry with the security-
correct setup step and avoids a screen that only appears to authenticate.
