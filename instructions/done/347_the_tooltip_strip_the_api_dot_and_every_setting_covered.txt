--------------------------------------------------------------------------------
FOUR THINGS
--------------------------------------------------------------------------------

1. TWO TOOLTIP SURFACES, ONE RULE EACH.

   A SETTING keeps its hover popup. A CATEGORY does not: its help text goes
   only to the strip at the bottom of the screen. Today both use the popup,
   and a category popup covers the rows the user is trying to read.

2. REGRESSION LOOKS LIKE IT ALREADY MOVED, AND THAT NEEDS CHECKING FIRST.
   The report is that regression's SETTING tooltips have already become
   bottom-of-screen text rather than popups. If that is real it is a
   regression against rule 1 and it is the half to fix first -- the maintainer
   likes the strip, but not INSTEAD of the setting popup.
   Establish whether regression differs from the other screens before
   changing anything: it may be one screen's layout, or it may be the shared
   path and the other screens have simply not been looked at.

3. THE LINK BECOMES TWO MARKS.
   "Open spaCR API documentation" is repeated on every row that has one,
   which is most of them, so the words carry no information and cost a line.
   Replace with:

       a TEAL DOT      -> the API documentation for that setting
       a PURPLE SQUARE -> the setting's animation

   Both must stay clickable targets, which is the constraint that killed the
   previous attempt at this: see the note in 3d below.

4. EVERY SETTING HAS A TOOLTIP. "make sure all settings have tooltipps" --
   this is a coverage claim and needs a test, not a sweep. `spacr.settings`
   already registers tooltips per module via `register_defaults`, and
   `tooltips` is NOT complete on import (HANDOFF 3c): six pipelines register
   their keys from their own module. Any audit that reads the dict cold will
   report false gaps and, worse, a tool that then writes "no description" is
   not missing a sentence, it is writing a WRONG one.

--------------------------------------------------------------------------------
WHAT IS ALREADY TRUE
--------------------------------------------------------------------------------

Instruction 336 (done) generated `spacr/qt/screens/setting_api_targets.py`, so
every setting's API link now points at the function that READS it, and
`exact=False` marks the ones whose only consumer is a closure. The dot should
use the same map -- and a setting with no addressable consumer should show NO
dot rather than a dot that goes nowhere.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* A control that vanishes takes its value with it (INVARIANTS 6, "greyed, not
  removed"). A dot that disappears when there is no target is fine; a dot that
  disappears because the lookup failed is not, and the two look identical.
* Two teal dots and two purple squares on one row would mean two sources of
  the same link. One source, `SETTING_API_TARGETS`.
* Colour alone is not a label. A teal dot and a purple square differ in SHAPE
  as well as colour, which is what makes this legible in the colourblind mode
  instruction 89 added -- keep both differences.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* Hovering a SETTING shows a popup; hovering a CATEGORY shows strip text and
  no popup. Asserted by driving the hover, not by reading the layout code.
* No row renders the words "Open spaCR API documentation".
* Every setting a built-in module offers has a non-empty tooltip, measured
  AFTER the modules that register them have been imported.
* A setting whose API target is unknown shows no teal dot.

2026-09-02 — PART 3 DONE: THE FOOTER IS A TEAL DOT AND A PURPLE SQUARE
--------------------------------------------------------------------------------

The popup footer already had two separate link widgets with accessible names,
so this was a rendering change and not a restructure: `_LinkWord("API")` and
`_LinkWord("Animation")` now draw `API_MARK` (●) and `ANIMATION_MARK` (■).

THE COLOURS SWAPPED, and the API mark is the one that moved. It used to carry
`palette['accent']` -- the theme blue -- and is TEAL now, with the animation
mark taking PURPLE. Both are named constants, so a theme switch cannot repaint
a colour the maintainer chose. `PURPLE = "#7C3AED"` is new; the palette has no
purple and `info` is only a second name for the blue accent.

SHAPE AS WELL AS COLOUR, and there is a test that says so. Instruction 89
added a colourblind mode: a dot and a square differ in FORM, so they stay
distinguishable when the colours do not. Two dots in two colours would be one
distinction where there are meant to be two.

THE WORDS DID NOT DISAPPEAR, they moved to where a reader can still reach
them: `accessibleName` stays "API" / "Animation" -- a screen reader announcing
"black circle" would be a regression -- and each mark now carries a tooltip
naming itself, so a pointer can still ask.

The marks are drawn four pixels above the prose size. At the popup's small
font a circle is a few pixels across, and these are click targets rather than
decoration.

FOUR TESTS WERE UPDATED, and one of them lost strength honestly rather than
quietly:

  * the footer test asserts the marks and the accessible names;
  * the colour test asserts teal/purple, still scored against the WRONG
    colour so it cannot pass for any two non-background inks;
  * the provenance test now records where purple comes from as well as teal;
  * THE UNDERLINE TEST CHANGED SHAPE. Its probe was "a near-full-width run of
    ink on one row is an underline", which is true of a WORD and false of a
    filled square -- ■ is a full-width run on every row it occupies and would
    trip the probe while being perfectly un-underlined. The marks are now
    checked on the font and the declared `text-decoration: none`, and the
    pixel probe is KEPT as a control against a real `<a href>` that Qt does
    underline. That control is what stops the file quietly losing the ability
    to detect one.

Six new tests in `tests/qt/test_the_tooltip_marks_replace_the_words.py`.
583 passed across every hover/tooltip/palette test; the 2 failures there are
306's catalog debt and fail identically at HEAD.

strip, whether Regression's SETTING tooltips have wrongly moved to the strip
