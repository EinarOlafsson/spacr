2026-08-09 - A SHORTCUT THAT DOES NOT WORK, RECORDED SO NOBODY REPEATS IT
--------------------------------------------------------------------------------

The build log from the first pass was lost in a machine crash, and a
rebuild is ~8 minutes, so I tried to regenerate the defect list cheaply by
running docutils directly over every docstring -- docutils being what
actually emits "Unexpected indentation" and friends.

IT DOES NOT REPRODUCE SPHINX'S FINDINGS, in two separate ways:

  5335 false "Unknown interpreted text role" -- :func:, :class:, :data:,
       :mod:, :meth:, :attr:. Those are SPHINX roles; bare docutils has
       never heard of them. Every one is correct markup.

   ~130 false "Unexpected indentation" / "Block quote ends without a blank
       line" -- these are GOOGLE-STYLE docstrings ("Args:", "Returns:"),
       which `sphinx.ext.napoleon` rewrites into field lists before
       docutils sees them. conf.py line 42 enables napoleon. Bare docutils
       sees the indented block raw and objects.

So the check reported 5466 findings, essentially all of them noise, and I
came close to rewriting 130 correct docstrings to satisfy a tool that was
not modelling the real pipeline.

THE LESSON, which generalises past this task: a cheaper substitute for a
build is only useful if it runs the SAME extensions. Sphinx's own numbers
already account for napoleon and its roles; a bare parser cannot, and its
disagreement is about the parser rather than the docstrings.

USE THE BUILD. It is eight minutes:

    python -m sphinx -E -b html --keep-going docs/source <out>

and its warnings are the authoritative list. Nice it down if the machine is
shared -- there is a concurrent session on this box that has taken ~15

DO NOT FIX THESE WITH A LINE-BASED REGEX. I tried, and it corrupted 203
files, because `"` is a legal rST underline character -- so a docstring's
closing `"""` matched the underline pattern and was "lengthened" to the
width of the line above it, producing `"""""""""`. Reverted with
`git checkout`; nothing was committed.

Two mistakes worth naming, since either alone would have caught it:
  * it ran over the whole package in one pass instead of one file first;
  * it checked `ast.parse` AFTER writing rather than before, when the check
    is cheap enough to gate every write.

THE SAFE SHAPE, for whoever does this: walk the file with `ast`, take each
docstring's own start and end offsets, edit only INSIDE that span, and
re-parse the file before writing it back. The closing quotes are then
outside the region being touched and cannot be mistaken for content.

2026-08-09 - "UNEXPECTED INDENTATION" HAS ONE CAUSE, AND IT IS FIXABLE
--------------------------------------------------------------------------------

It is not arbitrary bad markup. Every instance is a reStructuredText
DEFINITION LIST whose term wrapped onto a second line:

    ``ErrorPolicy``, ``resolve_error_policy``, ``SkipRecord``, ``SKIPPED``,
    ``ON_ERROR_STOP``, ``ON_ERROR_SKIP``, ``ON_ERROR_RETRY``
        The S9 machinery.

rST requires the term to be ONE line. A wrapped term is an ordinary
paragraph, so the indented definition under it is "unexpected", and the
whole entry renders as body text instead of a definition list. The fix is
to join the term onto one long line -- long lines being correct here, since
this is prose, not code.

FIXED: 4. Three in `spacr/runctx.py` by hand, one in `spacr/data_manager.py`
by `scratchpad/fix_defterms.py`, which joins wrapped terms and KEEPS the
change only when re-parsing shows the error count actually dropped and no
new error appeared.

WHY THE TOOL ONLY GOT ONE, recorded so nobody assumes it is broken:
`ast.get_docstring` returns the CLEANED docstring -- dedented, escapes
processed -- so for any docstring indented inside a class or function the
text does not appear verbatim in the source and the replace no-ops. It
works for module-level docstrings at column 0 and nothing else. Fixing that
properly means slicing the source by the node's own offsets, which is what
`tools/fix_rst_underlines.py` already does and what this tool should adopt
if anyone extends it.

2026-08-09 - "UNEXPECTED INDENTATION" IS TWO CAUSES, NOT ONE
--------------------------------------------------------------------------------

An earlier note here said every instance is a wrapped definition-list term.
That was true of the four fixed in `runctx.py` and `data_manager.py` and is
NOT true of the rest. Looking at four more:

    spacr/qt/ai/prompts.py     a bullet list with NO BLANK LINE after the
                               paragraph introducing it. rST requires one;
                               without it the bullets are an indented block.
                               FIXED -- 1 -> 0 errors.
    spacr/qt/settings_diff.py  a definition whose continuation is indented
                               DEEPER than the definition body
    spacr/qt/ai/providers.py   aligned continuation lines under a term
    spacr/qt/synthetic.py      a bullet whose continuation is indented

So the class splits roughly in two: MISSING BLANK LINE before a list, and
CONTINUATION LINES aligned by eye rather than by rST's rules. The first is
a one-character fix; the second needs someone to decide what the author
meant, because de-indenting changes which text belongs to which item.

The method that works for both, and is worth reusing: parse the docstring
with docutils, count "Unexpected indentation", apply the candidate fix,
count again, and keep it ONLY if the count dropped. That gate is what
distinguishes a fix from a plausible-looking edit, and it is cheap --
`errs(doc)` is four lines.

A DELETED MODULE KEEPS ITS PAGE UNLESS THE BUILD STARTS FROM AN EMPTY TREE
--------------------------------------------------------------------------------

The whole Tkinter interface is gone from the source -- `gui`, `gui_core`,
`gui_elements`, `gui_utils`, the seven `app_*` launchers, `download_models`,
and the `legacy_tk` package that briefly held them. Every one of them was
still on the API reference, in two different ways, and the two need
different remedies.

THE PAGES. Neither Sphinx nor autoapi removes output it no longer generates,
so an incremental build republishes the page, the search-index entry and the
module-index row of a module that no longer exists. The build directory on
this machine carried a module page for every one of them. The remedy is the
`rm -rf docs/_build docs/source/api` the docs workflow already runs before
`sphinx-build`; a rebuild that starts from those two empty trees emits a
module page per live module and none for the deleted ones -- and no
search-index entry either, which is the other way a retired page keeps being
found. That cleanup is now the subject of a test, because it looks like
tidiness and is actually the only thing that retires a page.

THE LOCALIZATION PAYLOAD, which is the half that does not fix itself. The
API catalogs under `docs/source/_static/i18n/api` are checked in rather than
generated at build time, so they kept 279 symbols per language -- 2,790
entries across the ten -- describing the deleted modules. Those are what the
page's language picker serves, so they were translated documentation for a
product that does not have the feature. Removed, in every language, as a
pure deletion: the catalogs round-trip byte-for-byte through the generator's
own `json.dumps` settings, so nothing else in a 10 MB file moved.

The rule that finds them is the module, not the symbol: a catalog key is
dead when the top-level module it names has no `.py` under `spacr/`. Reading
the package marker instead would have been wrong -- `spacr.resources` has
documented modules and no `__init__.py`, and an `__init__`-based rule
deletes all of them.

THE BUILD LOG NOW POINTS AT FILES THAT EXIST
--------------------------------------------------------------------------------

Two sections above describe the same obstacle: a fault is reported against
`api/spacr/<module>/index.rst:<line>`, autoapi deletes that file when it
finishes, and the line number is left pointing at nothing -- which is what
sent three separate attempts into reconstructing the list from bare docutils
and getting thousands of false positives instead.

`autoapi_keep_files = True` in conf.py ends that. The generated page stays on
disk, so every reported line opens directly on the docstring as the parser
saw it, which is the only form in which these faults are legible. Nothing
stale accumulates: the build clears `docs/source/api` first.
