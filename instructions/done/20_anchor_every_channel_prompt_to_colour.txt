--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Instruction 10 did this for ONE setting, png_dims -> png_channel_mapping,
and built spacr/qt/widgets/channel_mapping.py (three R/G/B fields) for it.
This task is the general rule: every remaining place that asks for channels
by list position.

Not yet surveyed. Known position-ordered channel settings include at least
`channels`, `train_channels`, `channel_of_interest`, `normalize_channels`,
and the annotator's r/g/b channel filter strings. Some of these are
genuinely "which channels to process" (a set, no colour involved) and some
are "which channel is shown as what" (a mapping). Those two are NOT the
same and only the second should become a dict - decide per setting, and
write down which is which.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

This is the root cause of the whole crop-colour episode, stated as a rule.
Position-ordered channel lists carry an unstated convention, and an
unstated convention gets read backwards - it did, for eleven days, and it
took a format version, a migrator and a repaired test suite to undo.

A dict cannot be read backwards. That is the entire argument.

--------------------------------------------------------------------------------
WHAT WAS DONE
--------------------------------------------------------------------------------

THE SURVEY, which was the whole of the difficulty. Every channel-related
setting spaCR has, classified, with the reason:

A SET of source channels - no colour involved, STAYS A LIST:
    channels        which channels are kept in merged/*.npy and measured
    channel_dims    recruitment: which channels the merged arrays hold

A NAMED ROLE -> one source channel - already explicit, the NAME decides
which stain and position decides nothing, STAYS A SCALAR:
    cell_channel, nucleus_channel, pathogen_channel, organelle_channel
    outside_channel, total_channel, channel_of_interest

A COLOUR MAPPING - the only kind that can be read backwards:
    png_channel_mapping   {r,g,b} -> source index. Done in instruction 10.
    train_channels        already names 'r'/'g'/'b' directly, so it was
                          never positional and needed no change.

NOT channel settings at all, despite the name: outline_color, point_color,
color_by are plotting colours.

CONCLUSION: png_dims was the only setting that encoded a colour by list
position, and it is already fixed. There was no second one. That is a real
finding and it is why this file closes with almost no code.

WHAT WAS FOUND AND WRITTEN DOWN:

`spacr/plot.py :: _plot_images_on_grid` colours the legend entry `i` with
['red','green','blue'][i]. That is correct for the FILE order it reads, but
a caller passing names in SOURCE order (['DAPI','GFP','RFP'] for channels
0,1,2) would get DAPI labelled red while it renders blue - and the figure
would look entirely reasonable. No live caller passes the argument (the one
call site passes channel_names=None), so this is a contract written down
before it is relied on, not a bug fixed. The docstring now says FILE order
and points at resolve_png_channel_mapping for the translation.

WHAT WAS ADDED:

tests/test_channel_settings_are_colour_anchored.py - eleven guards so a
future setting cannot quietly reintroduce the pattern. It carries the
classification above in CHANNEL_SETS and COLOUR_SETTINGS, so adding a
channel setting means deciding, in writing, which kind it is.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

No setting anywhere in the GUI asks for a colour by list position. Every
mapping round-trips: set {'r':2,'g':1,'b':0}, run, and the file's red slot
holds source channel 2.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Converting `channels` (the cellpose/measure channel selection) to a colour
dict. It selects which channels are PROCESSED; it has no colour semantics,
and forcing r/g/b onto it would invent a meaning that is not there.
