================================================================================
A REGRESSION THAT FAILS SAYS WHY
================================================================================

Status:    filed 2026-08-18.
Requested: 2026-08-18 -- "merge works and the regression runs, but failed for
           an unknown reason"

THE MESSAGE IS ITS OWN BUG, whatever the underlying failure was. A run that got
far enough to fail KNOWS: the settings it was handed, the shape of the frame it
built, how far it got, and the exception it hit. Reporting "failed" discards all
four and leaves a user with nothing to change.

This is the same defect as 153's "no summary", 154 E's "nothing to scan" and
155 A's "not read from a run folder" -- a sentence that names no cause and
offers no next step. Three of those have been fixed by saying the true thing;
this is the fourth.

WHAT EVERY FAILURE REPORTS:
  * THE STAGE IT REACHED -- reading the scores, joining the counts, building
    the design, fitting, writing the results. A failure in the join is a
    different problem from a failure in the fit and the user can act on the
    difference.
  * THE DESIGN IT HAD BUILT BY THEN: rows, wells, guides, genes, parameters.
    These are the numbers that make every other number readable, and 156 already
    collects them.
  * THE EXCEPTION, with its type, not flattened to a string.
  * WHAT TO CHANGE, where the failure has a known remedy -- a singular design,
    a missing column, a fit too wide for its data.

AND IT IS WRITTEN INTO THE RUN FOLDER, not only printed. A console scrolls and a
session ends; a run that failed is a run somebody will ask about tomorrow.

HOW TO KNOW IT WORKED
* Every regression failure names its stage, its design, its exception and a
  next step.
* The same text is in the run folder afterwards.
* No failure path reaches the user as the word "failed" alone.

--------------------------------------------------------------------------------
DONE 2026-08-19
--------------------------------------------------------------------------------

`spacr/regression_failure.py`. Every failure reports the stage reached, the
design it had built (rows, columns, distinct wells/guides/genes, and the
settings that decide the fit), the exception with its type, and what to change
where the failure is one of the recognised ones -- singular design, inf in a
predictor, an empty join, out of memory, a CUDA fault, a missing input, a
missing column. Matched on the message rather than the exception type, because
the informative part of a numpy or statsmodels error is almost always its text.

AN UNRECOGNISED FAILURE SAYS SO INSTEAD OF GUESSING, and a test holds it. A
wrong remedy sends a user to change the one thing that was not the problem.

Written into the run folder as `regression_failure.txt` as well as printed,
because a console has scrolled by the time somebody asks about that run.

TWO RULES THE MODULE IS BUILT AROUND, both tested:
  * NOTHING IN IT RAISES. A reporting path that can fail takes the real
    exception with it and leaves the user worse off than the bare message this
    replaced, so even a frame that refuses to describe itself is reported.
  * `perform_regression` RE-RAISES UNCHANGED. The reporter adds to a failure
    and must never replace one, or a caller handling a specific exception type
    stops seeing it.

WHAT IT COST, worth knowing before the next wrapper. The body became
`_perform_regression`, and `tests/test_regression_entry_points.py` scans the
PUBLIC name for settings reads, writes and their ordering -- so all four scans
had to follow the body. An earlier agent had already reported those two tests
as pre-existing red; they were not, they were this change, and the contract
caught precisely what it exists to catch.
