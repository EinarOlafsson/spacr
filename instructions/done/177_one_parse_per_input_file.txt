ONE PARSE PER INPUT FILE, NOT ONE PER PAIR ROW
================================================================================

Status:    closed. The reader, the intermediate, the silence AND the last
           producer -- the Measurements panel -- all go through the handoff;
           nothing writes a CSV that nothing reads back. Measured numbers
           under WHAT IT COST AND WHAT IT COSTS NOW.
Reported:  2026-08-19 -- "i merged the measurements and ran pathogen_area as a
           regression but it looks like it is not running while it does say
           that it is running ... do you see anything running?"

IT WAS RUNNING. Measured on the process itself rather than guessed:

    PID 489199, 28 minutes, 219% CPU
    the regression worker thread alone at 82%
    write_bytes  2,752,598,016   static
    read_bytes           1.4 MB  static
    files written in twelve minutes: none

A process that has written 2.75 GB and is now burning CPU with ZERO disk I/O
is re-reading that file out of the page cache. Four times: regression on a
measurement column writes the merged frame to one CSV and points EVERY pair
row's score at it, and `load_regression_input_pairs` parsed it once per row.

FIXED: each distinct path is parsed once and handed out as a copy -- a copy
because the caller assigns `plateID` onto what it gets and filters it down to
one plate, so sharing the frame would let the first pair row's edits reach the
second. Eight `read_table` calls become five on a four-plate screen.

AND THE LARGER HALF, THE INTERMEDIATE ITSELF: the frame is ALREADY IN MEMORY
when it is written, and writing it took 160 seconds before anything read it
back. Nothing requires that handoff to be a CSV.

`spacr/frame_handoff.py` is that handoff. A producer offers the frame under
the path it wrote, and `load_regression_input_pairs` takes the object instead
of parsing the file -- so the round trip costs nothing at all. The reference
is WEAK, so an offer cannot keep a multi-gigabyte frame alive after its owner
drops it, and a reader that was offered nothing reads the file exactly as
before. `frame_handoff.stage` writes the durable artefact COLUMNAR, because
the artefact is worth keeping (a user can open it, and every fit of a queue
then reads the same numbers) and only its format has to change.

MEASURED ON A 143 MB FRAME, which is the same shape as the screen one at a
twentieth of the size:

    csv       write 11.14 s   read 1.63 s   239.5 MB
    parquet   write  0.63 s   read 0.11 s   106.9 MB
    handoff   write     0 s   read    0 s   nothing written twice

THE LAST PRODUCER, AND IT IS NOW THROUGH THE MECHANISM. The reader half was
already complete and audited: `ml.load_regression_input_pairs` parses each
distinct path once, asks `frame_handoff.held(path)` first, prints what it was
handed and what it had to read, and falls back to `tabular.read_table` --
which reads Parquet -- when nothing was offered.

`spacr/qt/widgets/measurement_scan_panel.py::write_merged_frame` did
`frame.to_csv(path, index=False)` and offered nothing, which made the
Measurements queue the one producer the mechanism never saw. IT STAGES NOW:

    return stage(frame, folder, os.path.splitext(str(name))[0],
                 report=report)

`stage` creates the folder, offers the frame under the path BEFORE the write
returns, writes Parquet when an engine is installed and CSV when one is not,
and reports what it wrote and what it cost. `MERGED_FRAME_NAME` is still
'merged_measurements.csv' and only its STEM is used, so the artefact is
`merged_measurements.parquet` where pyarrow is present -- which is what
`merged_frame_path()` returns, what `column_run_settings` points every pair
row at, and what `tabular.read_table` dispatches on.

AND THE OFFER LIVES EXACTLY AS LONG AS THE QUEUE THAT READS IT.
`ColumnQueuePanel._finish_queue` releases `self._queue_score` after
`queue_finished` is emitted -- the references are weak, so this is not the
difference between a leak and none, but it makes the fallback to the file
DETERMINISTIC rather than dependent on when the merging panel's frame is
collected.

The release alone would have left only the FIRST queue over a merge taking
the object, so `start_regressions` offers the frame again before each queue,
through `_offer_frame`. The frame provider and the score provider are two
views of one merge -- the panel wires both to the merging panel, which sets
the frame and the path it wrote together -- and a provider that cannot give
a frame simply makes no offer, so the fits read the file as they always did.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Written down after the fact, because this file closed without the section the
ledger asks every task for. These are the promises the body above makes, in
the form they can be checked in:

  * Four pair rows pointing at ONE merged file cost ONE parse, not four --
    `ml.load_regression_input_pairs` asks `frame_handoff.held(path)` before it
    reads, keys its cache on the distinct path, and hands each row a COPY, so
    one row stamping `plateID` cannot reach the next.
  * A reader that was offered nothing reads the file exactly as before, so a
    headless run with no producer in the process is unchanged.
  * The offer is a WEAK reference: dropping the producer's frame must not be
    prevented by the offer, and the reader must fall back rather than raise.
  * `frame_handoff.stage` writes Parquet where an engine is installed and CSV
    where one is not, and offers the frame BEFORE the write returns.
  * The Measurements panel's `write_merged_frame` goes through `stage`, so the
    artefact it leaves is columnar and `merged_frame_path()` names the file
    that was actually written.
  * A SECOND queue over the same merge is handed the frame again rather than
    parsing, and a frame provider that fails costs a parse rather than the run.

Tests: `tests/test_the_merged_frame_is_handed_over.py`,
`tests/test_the_measurements_tab_reaches_a_regression.py`,
`tests/test_one_parse_per_file.py`.

--------------------------------------------------------------------------------
WHAT IT COST AND WHAT IT COSTS NOW
--------------------------------------------------------------------------------

Measured on a 200,000 x 83 frame, 159 MB resident, which is the same shape as
the screen one at about a twentieth of the size:

    to_csv + read back      write 13.33 s   read 1.89 s   316.7 MB
    stage(parquet)          write  0.90 s   read 0.20 s   149.8 MB
    handed over in memory                   read 2.8 us   nothing written twice

Through the real loader, four pair rows pointed at one merged frame:

    CSV on disk        3.14 s
    Parquet on disk    0.30 s
    handed over        0.16 s

Scaled to the four-plate screen's 2.75 GB of CSV (x8.7): the write goes from
about 116 s to about 8 s, and the parse in front of the first fit -- 16 s at
this machine's disk speed, minutes on the screen where it was diagnosed out
of the page cache -- goes to nothing at all, because nothing is parsed.

Tests: `tests/test_the_merged_frame_is_handed_over.py` (11) for the
mechanism, and in `tests/test_the_measurements_tab_reaches_a_regression.py`
the producer half -- the artefact is columnar and the frame is offered, an
empty merge offers nothing, the fit is handed the object rather than the
path, a second queue is handed it again, and a frame provider that fails
costs a parse rather than the run.

Instruction 140 asks for exactly this and does not cover this path.
