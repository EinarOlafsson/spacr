--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Documentation and translations are executable user contracts: an incorrect
default, parameter name, placeholder, or protected identifier can misdirect a
workflow or fail only in one locale while ordinary coverage remains green.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

DOCSTRINGS -- correctness, in this order, because the order is by how much
damage a wrong one does:

  * DOES IT DESCRIBE THE CODE UNDERNEATH IT? The failure mode this repository
    actually has is documented-behaviour-that-changed. Spot-check every
    module touched in the last month first; those are the ones whose prose
    has had the most chance to drift.
  * DO THE :param: NAMES MATCH THE SIGNATURE? Mechanically checkable, so
    check it mechanically rather than by eye, and keep the check.
  * DO THE CROSS-REFERENCES RESOLVE? `:func:` and `:mod:` targets that were
    renamed silently become dead links. There is already a guard for tooltip
    API links (`test_tooltip_api_links_resolve.py`) which SKIPS without a
    fresh docs build -- so it is not currently proving anything. Either make
    it run in CI with a built docs tree or stop counting it as coverage.
  * DOES IT NAME A DEFAULT THAT IS STILL THE DEFAULT? A docstring saying
    "defaults to 0" beside `param=None` is worse than no docstring: it is
    believed.

TRANSLATIONS -- the catalogs live in `packaging/i18n/*.json` (de, en, es, fr,
hi, ko, sv, zh_CN), and there is no `spacr/i18n/` runtime catalog directory,
so establish first WHERE the runtime actually reads its strings from before
auditing the wrong files.

  * SAME PLACEHOLDERS, EVERY LANGUAGE. A translated string that drops or
    renames a `{field}` throws at runtime in that locale only, which means it
    ships. Mechanically checkable across all eight; check it mechanically.
  * NO UNTRANSLATED-BUT-PRESENT ENTRIES. A key whose value is the English
    string is not translated; it is a placeholder that passes a coverage
    count. Distinguish deliberate ones (proper nouns, "spaCR") from the rest,
    and list the deliberate ones somewhere so the distinction survives.
  * THE TERMS THAT MUST NOT BE TRANSLATED. Column names, object types,
    settings keys, `prcfo`, the object roles. A translated `columnID` is a
    broken database, not a localised one.
  * THE NAME IS spaCR (instruction 85) in every locale, and the wordmark
    rule from `[[spacr_wordmark_styling]]` still applies where it renders.

--------------------------------------------------------------------------------
HOW TO DO IT WITHOUT IT BEING THEATRE
--------------------------------------------------------------------------------

Every check that CAN be mechanical must end as a test, not as a pass someone
did once. This sweep will be asked for again -- it already has been, for
work that was closed -- and the only durable answer is a guard that fails
when the prose drifts from the code.

Where a check cannot be mechanical (does this sentence describe what the
function does?), sample rather than pretend to be exhaustive, say what was
sampled and how, and put the unreviewed remainder in writing. "Swept" with
no statement of coverage is the claim this instruction exists to distrust.
