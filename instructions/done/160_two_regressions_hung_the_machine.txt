================================================================================
TWO REGRESSIONS HUNG THE MACHINE
================================================================================

Status:    filed 2026-08-18. NOT REPRODUCED. One guard shipped; the cause is
           still unknown and this file says so rather than guessing.
Requested: 2026-08-18 -- "i ran one ols then a mixed regression model and this
           hung my computer twice so i had to restart it"

A HUNG MACHINE IS NOT A HUNG APPLICATION, and the difference decides where to
look: a frozen window is 159, while a machine that stops responding is memory,
a driver, or a runaway process count.

WHAT IS KNOWN. None of it is a diagnosis.

  * `mixed_gpu` allocated a DENSE `n x q` design with no size check. GUARDED
    NOW (`design_bytes` / `available_memory` / a refusal naming both numbers),
    because an over-large request on Linux is answered by the OOM killer rather
    than by an exception -- it takes the session and everything else open.
  * THE GUARD IS NOT THE FIX FOR THIS REPORT. The maintainer's own merge is
    226,467 cells x 1,212 random effects = 2.2 GB, which FITS, and a test pins
    that it is not refused. So the reported hang was something else.
  * Four databases had just been merged, so a large frame was already live.
  * OLS ran FIRST: both results tables, both diagnostic sets and both figure
    sets were in memory when the second fit began.
  * `ml.py` carries an `n_jobs=-1` (the xgboost path). Not on the regression
    path, but worth ruling in or out with a process count rather than by eye.

WHAT TO DO NEXT, in order:
  1. LOG RSS AND GPU MEMORY PER FIT STAGE, into the run folder. The next report
     then arrives with a number instead of a description, which is the whole
     difference between this file and a fix.
  2. Count child processes during a fit. A hang with the fans up and the
     pointer dead is what unbounded process spawning looks like.
  3. Only then decide. Instruction 114 asked for a parameter search that cannot
     take the machine down; this is the same requirement for a single fit.

HOW TO KNOW IT WORKED
* An OLS followed by a mixed fit on the maintainer's own screen completes, with
  peak RSS and GPU memory recorded in the run folder.
* No sequence of fits available from the GUI can make the machine unresponsive.

--------------------------------------------------------------------------------
2026-08-19 -- CLOSED. Reproduced, diagnosed and fixed. Not by guessing.
--------------------------------------------------------------------------------

THE CAUSE WAS NOT MEMORY. It was `plt.show()` on the worker thread.

A regression runs on a JobRunner worker. `bridge` registers a matplotlib show
capture for that worker's thread id and unregisters it in a `finally` when the
run ends. Any `plt.show()` outside that window fell through to the REAL
matplotlib show, which under the Qt backend calls `start_main_loop` -- a Qt
event loop started on a worker thread. That is the `QBasicTimer::start` warning
the maintainer pasted before every crash, and the process aborts with no Python
traceback, which is why nothing in the logs ever named it.

Caught by running the maintainer's own four-plate screen headlessly under
`faulthandler.dump_traceback_later`, which printed the stack the crash never
did:

    matplotlib/backends/backend_qt.py  start_main_loop
    matplotlib/pyplot.py               show
    spacr/ml.py                        minimum_cell_simulation

FIXED in d95e0edb: the show router drops an uncaptured show off the GUI thread
instead of entering an event loop there, and `minimum_cell_simulation`
publishes through `figure_sink` rather than calling `plt.show()` at all. The
router closes the class for all 85 remaining `plt.show()` call sites, not just
that one.

THE MEASUREMENTS THIS FILE ASKED FOR, and what they say.

`fit_resources` was recording two stages -- "placing the results folder" and
"reading the counts" -- both BEFORE any fitting, and writing them only into a
FAILURE report. So the peak recorded was the peak of the setup, in the one case
where the machine had not hung. Four stage points now bracket the fit itself, a
run that COMPLETES writes `fit_resources.txt` beside its results, and the GPU
reading is `max_memory_allocated` rather than the live allocation -- the latter
is taken at a stage boundary, after the fit has freed its tensors, and read back
as 0.0 B for a fit that ran on the GPU.

HOW TO KNOW IT WORKED -- run on the maintainer's four-plate screen, one process:

    ols    137s   PEAK resident 1.9 GB    PEAK GPU 0.0 B
    mixed   24s   PEAK resident 2.6 GB    PEAK GPU 142.1 MB
    BOTH FITS COMPLETED IN ONE PROCESS

2.6 GB out of 125 GB. THE SEQUENCE REPORTED HERE NEVER EXHAUSTED MEMORY, and
the `mixed_gpu` size guard shipped earlier was, as this file already suspected,
not the fix for this report.

WHAT WAS ALSO TRUE AND IS NOT A BUG. `mixed` on the default statsmodels backend
took 24 SECONDS on `regression_backend='torch'` and was still inside scipy's
BFGS after thirty-two minutes on the same data -- silent throughout. A
CPU-bound fit that prints nothing for half an hour is not distinguishable from
a hung machine, and this report is what that looks like from the outside. The
fit now announces its measured cost and names the one setting that removes it.
The default is unchanged: statsmodels produced every existing result.

--------------------------------------------------------------------------------
2026-08-19, LATER -- THE CLOSE ABOVE NAMED THE WRONG CAUSE. Corrected here.
--------------------------------------------------------------------------------

The entry above closed this file on `plt.show()` reaching the real matplotlib
show on a worker thread. That was a real bug and the fix stands. IT WAS NOT
THIS ONE. The maintainer's application went on quitting after it, four more
times, each time milliseconds after "run closed [success]".

WHAT IT ACTUALLY WAS, and how it was found rather than guessed:

  1. `faulthandler` was installed at launch, writing every thread's stack to
     `~/.spacr/logs/spacr-crash.log` on a fatal signal. Until then there was
     no traceback at all, which is why three hypotheses in a row were plausible
     and wrong -- an off-thread `plt.show()`, pyplot building Qt canvases on
     the worker, and `quitOnLastWindowClosed`. Each cost a launch-and-reproduce
     cycle and none of them was it.
  2. The dump proved a real SIGSEGV, and then proved it was not where it
     looked: one crash inside the application-wide event filter, the next
     inside pandas' CSV parser. Two unrelated places is heap corruption; the
     crash site is wherever the next allocation gave way.
  3. `QObject.__init__` was wrapped to report construction away from the GUI
     thread. The next run named it outright:

         WidgetGroup was CONSTRUCTED on 'Dummy-2'
           bridge.py run  ->  perform_regression
           ->  _run_guide_permutation_analysis  ->  write_diagnostic_suite
           ->  plot_inference_diagnostics  ->  write_figure  ->  render_figure
           ->  build_scene

`build_scene` makes a `pg.GraphicsLayoutWidget`. A QWidget built on a worker
LIVES on that worker; every later touch, including Qt destroying it when the
thread ends, is undefined. This was the QC suite of EVERY regression, on the
run's own thread.

Gated in `pyqtgraph_ready`, which already existed to answer whether a scene
can be built here and now, and whose callers already write the matplotlib page
on a no. Confirmed working by the maintainer: "it finally worked with no
errors so far and i see the table".

THE WARNING WAS NEVER A RED HERRING, and it was called one twice in this
session. `QBasicTimer::start: Timers cannot be started from another thread` is
Qt reporting the ONE cross-thread access it can detect. It sat beside every
one of these crashes and it was the only true thing in the log.

WHAT THIS COST, recorded so it is not discovered as a surprise: instruction
139 wants the regression graphs in pyqtgraph, and on this path they are
matplotlib until the scene build is marshalled onto the GUI thread. A figure
drawn by the other renderer is still a figure; a widget on a dying thread is a
segfault somewhere else.

VERIFIED BY DISABLING THE GATE: `tests/test_a_worker_never_builds_a_qt_widget.py`
does not fail without it -- it HANGS, and has to be killed. That is the other
half of the original report, "this hung my computer twice so i had to restart
it", and it means a future removal of the gate announces itself.
