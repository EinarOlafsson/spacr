================================================================================
EVERY FIGURE IN THE PANEL OPENS WHEN IT IS CLICKED
================================================================================

Status:    filed 2026-08-21, DONE 2026-08-21.
Requested: 2026-08-21 -- "in the figure pannel. i am able to click on the
           colcano plot to open it but not the other pyqtgraphs. for the
           matplot lib graphs, i can not see #2 when i click on it this run."
Owner:     Qt GUI (figure grid, figure queue)

--------------------------------------------------------------------------------
A. THE PYQTGRAPH PANELS DO NOT OPEN
--------------------------------------------------------------------------------

The volcano opens on a click and its neighbours -- the residuals, the Q-Q,
the scale-location, the effect panels -- do not.

WHY THAT IS THE SHAPE OF THE BUG, and it is worth stating before anyone
looks: `_open_figure_from_grid` hands the index to
`FigureQueue.show_index`, which is the MATPLOTLIB queue. The pyqtgraph
panels are live widgets that live in the results panel's own tabs, not
entries in that queue. The volcano is reachable because it has a second
route of its own, not because the grid knows how to open it -- so every
panel that lacks such a route is a tile that looks clickable and is not.

A TILE THAT DOES NOT OPEN IS WORSE THAN NO TILE. It is drawn, it is in the
grid, it takes a click, and nothing happens: the user tries twice and
concludes the application is broken rather than that this particular picture
has no door. Instruction 106's rule, on a control that is not even greyed.

ONE ROUTE, not one per renderer. Whatever the tile holds -- a matplotlib
figure, a pyqtgraph panel, a saved image -- clicking it shows that thing
full size. Where a tile genuinely cannot be opened it should not be a tile.

--------------------------------------------------------------------------------
B. AND ONE OF THE MATPLOTLIB FIGURES SHOWS NOTHING           [REPORTED]
--------------------------------------------------------------------------------

    "for the matplot lib graphs, i can not see #2 when i click on it this
     run."

Figure 2 of that run opens to nothing. The tile has a picture on it -- it was
rendered, or there would be no tile (`set_pinned` refuses a null pixmap) --
so the raster exists and the full-size view does not show it.

CANDIDATES, in the order worth checking:

  * the live figure was SPILLED and could not be restored, so `figure_for`
    returned None and the detail view drew nothing. The cap is the user's
    number and a long run passes it;
  * the figure was CLOSED by whatever made it -- a `plt.close` in the
    producing code -- and the queue is holding a dead canvas;
  * the index the tile carries is not the index the queue holds, so #2 opens
    something that is not there.

WHICHEVER IT IS, THE VIEW MUST SAY SO. An empty panel where a figure should
be is the fault this instruction is about; "figure 2 could not be restored
from its spill" is an answer.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Clicking any tile in the figure panel opens that figure, whichever
  renderer drew it.
* A tile that cannot be opened is not drawn.
* Figure 2 of the reported run opens and shows its picture.
* A figure that genuinely cannot be shown says why, in the panel, rather
  than opening blank.
* A test drives the CLICK -- not the handler -- for one figure of each
  renderer, because a handler that works and a tile that does not reach it
  is exactly what was reported.

--------------------------------------------------------------------------------
WHAT WAS DONE
--------------------------------------------------------------------------------

A. THE PYQTGRAPH PANELS

The diagnosis in section A was right about the symptom and wrong about the
cause, and the difference mattered. The grid was NOT ignorant of the live
tiles: it photographs nine panels, gives each a key, and emits
`live_tile_activated(key)` when one is pressed. What was missing was the
receiver -- `app_screen` connected only `pinned_activated`, which the grid
emits for the volcano alone. Eight tiles reached a signal nobody listened
to.

The grid's own comment had predicted it: "a screen that has not yet learned
about the other panels must go on working". The screen never learned.

`RegressionResultsPanel.show_panel(key)` is the door. It names the SPLITTER
where a tab is a plot plus its table -- `setCurrentWidget` only accepts a
page the tab bar owns, so naming the inner plot would be a silent no-op,
which is the failure this was fixing. It returns False rather than guessing
when a key has no tab in this panel: the tab set is not fixed, and the
volcano and gene tabs are absent when the volcano is shown outside. The
screen says so in the console rather than going quiet. Right-click got the
same generalisation.

B. THE FIGURE THAT SHOWED NOTHING

Of the three candidates listed, the THIRD IS RULED OUT: `set_figures`
enumerates over the queue's own list and skips holes with `continue`, so a
missing figure does not renumber the tiles after it. There are tests holding
that, because it is the kind of thing a later tidy-up rewrites into a
filter.

The remaining cause is the first two, and they are now distinguishable
instead of silent. `show_index` called `set_pixmap` ONLY when it had a
pixmap -- so a figure it could not produce left the PREVIOUS figure on
screen. Clicking figure 2 showed figure 1. That is worse than blank: the
reader has no way to know they are looking at the wrong picture.

It now always sets something, and when there is no picture that something
says which of the three happened -- never saved, saved and gone, or present
and unreadable -- with the path, so it can be checked. Painted from the
palette, never a literal, per 178 and 198.

Tests: `tests/qt/test_every_live_tile_opens.py` (9) and
`tests/qt/test_a_figure_that_cannot_be_shown_says_why.py` (10). The first
drives the MOUSE rather than the handler, because what was broken was the
connection -- calling the handler would have passed against the broken
build.
