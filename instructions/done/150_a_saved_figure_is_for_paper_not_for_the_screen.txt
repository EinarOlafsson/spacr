================================================================================
A SAVED FIGURE IS FOR PAPER, NOT FOR THE SCREEN
================================================================================

Status:    filed 2026-08-18.
Requested: 2026-08-18 --

  "when a graph is saved and the user is in dark mode white elements are
   changed to black for saving (text lines, etc)."

Related: 136 is the house style. 118 is the figure preferences this becomes a
         setting in. 139 is every generated graph. 108/147 are the per-figure
         restyle menus it has to be reachable from.

--------------------------------------------------------------------------------
THE MECHANISM, FOUND 2026-08-18 RATHER THAN ASSUMED
--------------------------------------------------------------------------------

There is ONE source of figure colour and BOTH renderers read it:

    spacr.qt.preferences.get_figure_colors() -> (background, foreground)

    spacr/qt/widgets/fast_plots.py::_figure_colors   (pyqtgraph)
    the matplotlib renderer, same function

That shared source is a good design and is why a theme switch moves both. It
is also exactly why this bug reaches every figure at once: in dark mode
`foreground` is white, so the axes, ticks, tick labels, axis labels, title,
legend text and any annotation line are white -- and

    THERE IS NO EXPORT-TIME INVERSION ANYWHERE.

Grepped: `save_figure` decides format, font type and DPI, and says nothing
about colour. `_export_pdf` / `_export_svg` / `_paint_scene` render the scene
as it stands, and PNG -- the default -- goes out through pyqtgraph's own
`ImageExporter`, which does not paint the scene at all. So a figure saved from
a dark-themed session is white ink, and
white ink on a white page is a blank rectangle with some coloured dots in it.

WHY THIS IS WORSE THAN IT LOOKS. A PNG saved with a transparent background
looks fine in the file manager's dark preview and disappears when it is
pasted into a manuscript. The user finds out at the point of writing the
paper, which is the most expensive possible moment.

--------------------------------------------------------------------------------
A. THE CHROME FLIPS. THE DATA DOES NOT.
--------------------------------------------------------------------------------

THIS IS THE WHOLE OF THE DESIGN AND IT IS EASY TO GET WRONG. "Change white
elements to black" must mean the FIGURE'S FURNITURE and must not mean every
white pixel:

    FLIPS -- axes, spines, ticks, tick labels, axis labels, title, legend
             text and frame, grid lines, annotation text, the significance
             line, the zero line, arrows and leader lines.

    DOES NOT FLIP -- the data. A point coloured for its localisation, a
             heatmap's colour map, the up/down colouring on a volcano, the
             highlighted group in the house style. Those carry the CLAIM;
             inverting them changes what the figure says.

A blanket white->black would turn a white data point black, which on a
volcano is the colour of "not a hit". That is the failure this section exists
to prevent.

--------------------------------------------------------------------------------
B. THE BACKGROUND IS THE OTHER HALF, AND TRANSPARENT IS NOT THE ANSWER
--------------------------------------------------------------------------------

Dark ink on a transparent background is still unreadable on a dark slide, and
a figure saved for a manuscript is going onto white. So the saved figure gets
an EXPLICIT LIGHT BACKGROUND by default rather than a transparent one, and
transparency stays available for anyone compositing onto their own colour.

Three states, named, because they are genuinely different jobs:

    For print (default)   light background, dark chrome
    As on screen          exactly what the user is looking at
    Transparent           no background, chrome follows the print rule

--------------------------------------------------------------------------------
C. IT MUST REACH BOTH RENDERERS, AND THE CHECK IS THE SAME FOR BOTH
--------------------------------------------------------------------------------

matplotlib figures go through `spacr.plot.save_figure`, and it already scopes
`pdf.fonttype` with `rc_context` -- so the colour flip belongs in the same
`rc_context`, for the same reason: SCOPED TO THE SAVE. Nothing on screen may
change. A user watching a plot while it saves must not see it flash.

pyqtgraph figures go through `FastPlot._paint_scene`, which already sets
`setExportMode(True)` on every mark for the length of the render and puts it
back in a `finally`. That is precisely the shape this needs, and it is the
place to do it.

Both are covered by 139 C's rule that saved and visible are one event: the
tile in the gallery is the SCREEN version, the file is the PRINT version, and
the difference is deliberate rather than a disagreement.

--------------------------------------------------------------------------------
D. SAY WHEN A DATA COLOUR STOPS WORKING
--------------------------------------------------------------------------------

A palette chosen against a dark background can be illegible on white -- a pale
yellow that reads well on near-black has almost no contrast on paper. Since the
data colours deliberately do NOT flip (section A), this is a real possibility
and the figure must not simply become unreadable in a new way.

Measure the contrast of each data colour against the light background at save
time, and where one falls below the legibility floor, SAY SO rather than
silently substituting: the house style already has an accessible palette, and
a substitution the user did not ask for changes the picture. Naming the colour
and offering the swap is the honest version.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* In dark mode, save a volcano and OPEN THE FILE: the text and axes are dark,
  the background is light, and the dots are the same colours they were on
  screen. Measured on the pixels, not judged by eye.
* The plot on screen is byte-identical before and after the save.
* The same is true of a pyqtgraph export and a matplotlib one, checked
  separately, because they are two code paths.
* "As on screen" still produces the old behaviour for anyone who wants it.
* A data colour that would be illegible on the light background is named
  before the file is written.
* A saved PDF pasted into a white document is readable with nothing adjusted.

2026-08-18 -- THE MATPLOTLIB HALF IS DONE. THE DECISION IS SHARED; THE
              APPLICATION IS NOT.
--------------------------------------------------------------------------------

THE NAME THE PYQTGRAPH HALF WANTS:

    spacr.figure_style.saved_figure_appearance(mode=None) -> SavedFigureAppearance
                       (mode, ground, ink, grid, transparent, flip)

That is the whole decision and it is matplotlib-free and Qt-free, in the module
whose docstring already promised to stay that way (a test now asserts it). The
pyqtgraph exporter should call it in `FastPlot._paint_scene` inside the
`setExportMode(True)` / `finally` pair section C names, and repaint nothing it
does not have to. Beside it:

    spacr.figure_style.SAVE_MODES / PRINT_GROUND / PRINT_INK / PRINT_GRID
    spacr.figure_style.CHROME_CONTRAST_FLOOR / DATA_CONTRAST_FLOOR
    spacr.figure_style.contrast_ratio / relative_luminance / is_legible_on / to_rgb
    spacr.figure_style.figure_save_mode()        the preference, read defensively
    spacr.plot.print_ready(fig, mode, announce)  the MATPLOTLIB application
    spacr.plot.illegible_data_colours(fig, ground)   section D
    spacr.plot.save_figure(..., save_mode=, announce_colours=)

WHY IT COULD NOT ALL GO IN THE rc_context, MEASURED RATHER THAN ASSUMED. The
instruction points at `save_figure`'s existing `rc_context({"pdf.fonttype":
42})` and says the colour flip belongs in the same block. Half of it does and
half of it cannot: rcParams are read when an artist is CREATED, and by the time
`save_figure` runs the figure is already drawn, so `rc_context({"text.color":
"black"})` changes nothing that is on it. The only three rcParams matplotlib
reads at WRITE time are `savefig.facecolor`, `savefig.edgecolor` and
`savefig.transparent` -- those are in the rc block, and they cover the FIGURE
patch. Everything else is repainted artist by artist and restored in a
`finally`, which is what makes "the plot on screen is byte-identical before and
after the save" an assertion rather than a hope. The axes patch is a separate
artist from the figure patch and is one of the things the rc block misses; a
dark one left behind is a dark rectangle inside a white page.

THE HARD CASE IN "THE CHROME FLIPS, THE DATA DOES NOT" IS `ax.lines`. A
significance line, a zero line and a plotted series are all `Line2D`, so no
colour rule can separate them -- and section A names the first two as things
that MUST flip. They are told apart by their TRANSFORM: `axhline`/`axvline`
draw in a blended axes/data transform, a plotted series draws in
`ax.transData` itself. Verified on this matplotlib. That is a property of what
the line MEANS rather than of how it was coloured, so it survives a restyle.

WHAT DECIDES WHETHER A PIECE OF CHROME MOVES IS LEGIBILITY, NOT DARK MODE. An
artist is repainted only when its colour has less than `CHROME_CONTRAST_FLOOR`
= 2.0 contrast against the page. Two consequences, both wanted:
  * a LIGHT-MODE save changes nothing at all -- asserted -- which is what makes
    'print' safe as the default;
  * this never reads the theme, so it is independent of what `get_figure_
    colors()` answers and of the 152 work going on in that file at the same
    time. It reads the FIGURE.
Gridlines are chrome that is MEANT to be faint, so an illegible grid becomes
`PRINT_GRID` (#DDDDDD, the light-mode default) rather than the ink. A grid
repainted in the ink is a cage over the data.

SECTION D'S FLOOR IS SET FROM THE HOUSE STYLE, NOT FROM THE GUIDELINE, and this
is the one number worth recording. WCAG's 3.0 for graphical objects names the
house style's OWN greys on every save -- measured on `figures.style.ROLES`
against white:

    fill  #E8A88C 2.02      data #B4B4B4 2.07     control_negative #7F7F7F 4.00
    up    #2E7D4F 5.05      down #C4441C 5.01     highlight        #2E77BC 4.69

A warning that fires on every figure is a warning nobody reads, so
`DATA_CONTRAST_FLOOR` is 1.8: under everything the house style deliberately
puts on the page, over the colours that only work on a dark ground -- white
1.00, the pale yellow this instruction describes 1.03, Okabe-Ito yellow
#F0E442 1.32. `guide_permutation`'s "not a hit" grey #B8BDC5 is 1.89 and stays
quiet, which is right: it is de-emphasis, not a mark the reader has to find.
The colour is NAMED and never substituted.

MEASURED ON THE PIXELS, dark-themed volcano saved three ways, 100 dpi PNG:

    mode         corner pixel        darkest ink in    UP/DOWN/GREY   screen
                                     the title band    survive        unchanged
    print        (255,255,255,255)   (34,34,34)        yes            yes
    screen       (30,30,30,255)      (30,30,30)        yes            yes
    transparent  (255,255,255,  0)   (34,34,34)        yes            yes

`tests/test_a_saved_figure_is_for_paper.py`, 20 cases; 3 of them fail against
the pre-fix save path, checked by putting it back.

WHAT REMAINS ON THIS INSTRUCTION

  * SECTION C, THE PYQTGRAPH HALF. Untouched: `fast_plots.py` is another
    session's file. `saved_figure_appearance` exists precisely so that half
    does not invent a second answer.
  * THE PREFERENCE CONTROL. `figure_save_mode()` looks up
    `spacr.qt.preferences.get_figure_save_mode` BY NAME and falls back to
    'print', so adding the three-way control in Preferences (instruction 118)
    is a change in that file alone with nothing to wire here. Until it exists,
    `SPACR_FIGURE_SAVE_MODE=print|screen|transparent` selects the mode, which
    is also how a headless run or a test asks without a store.
  * THE PER-FIGURE RESTYLE MENUS (108/147) do not offer the mode yet.
  * The house style's own `savefig.transparent` is now overridden at write

    stated intent ("transparent is not the answer") but is a visible change
    for a published panel: a house-style figure that used to come out with no
    ground now comes out on white unless the mode is 'transparent'.

2026-08-18 (night) -- SECTION C: THE SHARED DECISION IS NOW PER-ARTIST, WHICH
                      IS THE PART THE PYQTGRAPH HALF ACTUALLY NEEDS
--------------------------------------------------------------------------------

The note above named `saved_figure_appearance` as "the name the pyqtgraph half
wants". Building against it showed that is only half a name. It hands both
renderers the same GROUND and the same INK; it does not hand them the rule
that turns those into a decision about ONE ARTIST -- is this thing legible,
and if not what does it become, and is it even allowed to change. That rule
lived inside `spacr.plot.print_ready`, i.e. inside the matplotlib
application, so the exporter would have had to write a second copy of it.
Two renderers deciding separately what "print" means is the same defect as two
engines deciding which statistical test applies.

THE NAME THE PYQTGRAPH HALF WANTS, and it is now the whole rule:

    spacr.figure_style.export_colour(current, kind, look=None) -> str | None

        kind is one of ARTIST_KINDS = ("ground", "grid", "chrome", "data")
        returns the colour to paint, or None for "leave this one alone"

    spacr.figure_style.ARTIST_KINDS
    spacr.figure_style.illegible_colours(colours, ground, floor=None) -> [hex]
    spacr.figure_style.illegible_colour_warning(names) -> str
    spacr.figure_style.saved_figure_appearance(mode=None)   (unchanged)

Called from `FastPlot._paint_scene` inside the existing
`setExportMode(True)` / `finally` pair, per section C. For each pen and brush
the exporter already touches: ask `export_colour(pen.color(), kind, look)`,
repaint when it answers, restore in the `finally`. The KIND is the exporter's
one judgement call and section A is the whole of it -- axes, ticks, labels,
title, legend, grid, annotation and reference lines are chrome; point
colours, colour maps, the up/down colouring and the highlighted group are
DATA and `export_colour` refuses to touch them whatever is passed as
`current`.

Section D from the same module: collect the DATA pen colours, hand the list to
`illegible_colours`, print `illegible_colour_warning` of the result. It takes
any iterable rather than a Figure precisely so the exporter can hand it pens,
and the alpha<0.5 "a wash is not a mark" rule is inside it, so the two
renderers cannot come to warn about different colours in one palette.

`spacr.plot.print_ready` now CALLS `export_colour` instead of keeping its own
branches, and `plot.illegible_data_colours` is the matplotlib harvest and
nothing else. That is what makes this a shared decision rather than a shared
constant: a change to the rule reaches the file and the tab together, and a
test asserts it by patching `export_colour` and watching the matplotlib
chrome move.

ONE CORRECTION MADE WHILE FACTORING IT. A colour is no longer "repainted" in
the colour it already is. The light-mode grid default IS `PRINT_GRID`, which
is 1.27 contrast on white -- correctly under `CHROME_CONTRAST_FLOOR`, and
already the answer -- so the old code set it to itself and recorded a restore
entry for it. Harmless, and it made "a light-mode save changes nothing at all"
true of the pixels but not of the artists.

`tests/test_the_save_decision_is_shared_by_both_renderers.py`, 21 cases.
Commit dabd9a66.

2026-08-18 (late) -- SECTION C: THE SHARED DECISION NOW REACHES A pyqtgraph
                     SCENE. THE GENERATED HALF IS DONE; THE TAB'S EXPORT IS
                     STILL ONE CALL IN SOMEBODY ELSE'S FILE.
--------------------------------------------------------------------------------

The two notes above built `saved_figure_appearance` and then `export_colour`
"precisely so that half does not invent a second answer", and both ended with
the same remaining item: nothing in pyqtgraph was CALLING it.

Something is now. `spacr/figures/scene.py` -- the generated-figure renderer
built for instruction 139 A -- asks `export_colour` for every pen, brush,
axis, label and text it puts into a scene, and it is in an unusually strong
position to answer section A's hard question. IT KNOWS THE KIND FOR CERTAIN,
because it is translating TYPED matplotlib artists rather than inspecting
pixels: a tick label is chrome because it IS a tick label, a scatter's brush
is data because it IS a scatter's brush. No colour rule has to guess.

So section A's rule holds on the pyqtgraph side with no new judgement:

    FLIPS      axes, spines, ticks, tick labels, axis labels, titles, legend
               text, annotations, the reference lines drawn by axhline/axvline
    DOES NOT   every scatter brush, every bar face, every colour map, every
               up/down colour

MEASURED ON THE PIXELS: a dark-grounded panel with a #C4441C mark exported in
'print' comes out with (255,255,255) as the page and (196,68,28) still on it.
A test patches `export_colour` and asserts the exporter asks it with kind
'chrome' and NEVER with kind 'data'.

NO RESTORE STEP, AND THAT IS NOT A SHORTCUT. This scene is built FOR the file
and never appears on screen, so the print look is applied as it is built. The
instruction's "the plot on screen is byte-identical before and after the save"
is satisfied trivially rather than carefully -- the matplotlib figure the
scene was translated from is never modified at all, and a test asserts that.

SECTION D, WITH ONE CALIBRATION THE MATPLOTLIB HALF DID NOT NEED.

  * A COLOUR MAP IS NOT A LIST OF MARKS. Sampling a ramp into the legibility
    check named RdBu_r's midpoint -- #F7F6F6, near white BY DESIGN, because
    that is what r = 0 looks like on a diverging map -- and would have fired
    the warning on every correlation panel ever written. Ramps are excluded
    and the reason is on the code.
  * A SEPARATOR IS NOT A MARK EITHER. The white edge a histogram draws between
    its bars is #FFFFFF and fired on every sheet in the diagnostic suite.
    Excluded, by `record=False`, and NOT flipped -- a bar edge repainted in
    the ink is a cage over the data, the same argument the grid already had.
  Both are the floor's own rule applied to itself: a warning that fires on
  every figure is a warning nobody reads.

2026-08-20 -- THE TAB'S OWN EXPORT. THE HANDOFF IS TAKEN AND 150 IS COMPLETE.
--------------------------------------------------------------------------------

`FastPlot.export` wears the print look for the length of the write and puts it
back in a `finally`, so all three formats obey the decision the matplotlib
half already made -- one `export_colour`, one `saved_figure_appearance`, two
renderers.

AROUND THE WHOLE EXPORT, NOT AROUND `_paint_scene`, and that was the first
attempt and it was wrong. PDF and SVG paint the scene themselves and would
have been covered; PNG goes through pyqtgraph's `ImageExporter`, which does
not, AND PNG IS THE DEFAULT. A rule covering two formats out of three is worse
than none, because the one it misses is the one everybody uses. Caught by
running it: the spy on `export_colour` recorded no calls at all for a PNG.

AND NOT AROUND `snapshot()`, deliberately: that render is the tile in the
gallery, which is the SCREEN version. 139 C -- the tile and the file differ on
purpose and the difference is the point.

THE PAGE. The exporter was passing a fully transparent background, and 150 B
says that is right only for the `transparent` mode -- dark ink on no
background is still unreadable on a dark slide, and a figure going into a
manuscript is going onto white. `print` writes `look.ground` (#FFFFFF),
`screen` keeps what is on screen, `transparent` keeps the old behaviour.

MEASURED ON THE PIXELS, as this file requires. A dark-session plot with a
#C4441C mark, exported and read back: the page is #ffffff, the chrome is dark,
and the data colour is still in the file. A test asserts `export_colour` is
asked with kind 'chrome' and NEVER with 'data' -- not passed with a different
kind, not passed.

RESTORED EVEN WHEN THE WRITE RAISES, which is the difference from the
generated half: that scene is built for the file and never appears, this one
is on screen. A test drives a failing write and checks the axis pen.

13 tests in tests/qt/test_a_saved_pyqtgraph_figure_is_for_paper.py.

STILL OWED, and both belong to their own instructions: the preference control
(118) and the per-figure restyle menus (108/147). 178 C.2's "Save styled…"
already gives a user the three choices per figure, so the preference is a
default rather than the only way in.
