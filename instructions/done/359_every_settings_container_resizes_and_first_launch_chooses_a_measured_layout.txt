================================================================================
EVERY SETTINGS CONTAINER RESIZES, AND FIRST LAUNCH CHOOSES A MEASURED LAYOUT
================================================================================

Status:    OPEN, filed 2026-09-02. AFTER the version update unless the
           maintainer explicitly promotes it; recording it does not change the
           current pre-update gate.
Requested: 2026-09-02 — in Regression's Measurements section, nested sections
           become illegible because their containers are too small; every
           container, subsection and sub-subsection must be height-resizable
           and collapsible. On an M4 Mac laptop, widening some settings
           containers did not widen their fields; fields must expand with the
           container, and every module must initially open wide enough that
           the right side of its settings is not cut off.
           Also requested: simulate screen/window/font sizes, measure cutoff,
           ship the resulting display map, and use first-run display metrics
           to select spaCR's best defaults.
Owner:     Qt layout/settings infrastructure, Regression's Measurements page,
           display-policy generation and packaged assets.

IS IT POSSIBLE, AND IS IT A GOOD IDEA?
--------------------------------------

YES, with one correction: screen resolution alone is not a sufficient key.
The same pixel dimensions can describe a low-DPI external monitor, a Retina
panel at 2x scaling, or an accessibility-scaled desktop. A static
``resolution -> font size`` table would choose incorrectly on exactly the M4
Mac that motivated this item.

The useful design is a GENERATED, SHIPPED BREAKPOINT POLICY derived from the
simulation matrix, combined at runtime with Qt's actual measurements:

* available screen geometry, not total geometry hidden behind a dock/menu;
* logical DPI, device-pixel ratio and operating-system scale;
* current application font and ``QFontMetrics``;
* widget ``minimumSizeHint``/``sizeHint`` and the real settings schema;
* window width/height, locale and platform chrome.

The policy may recommend an initial window size, settings-panel width, density
mode and a bounded starting font size. It must not defeat an OS accessibility
font or a user's saved choice merely to make text fit. When space is tight,
wrap, reflow, collapse and scroll before shrinking below the readable floor.

All detection and selection are local. This item does not authorise telemetry;
"capture" means reading Qt screen metrics into local preferences/evidence, not
sending hardware details anywhere.

PART 1 — EVERY NESTED CONTAINER CAN BE READ
-------------------------------------------

1. Inventory Regression -> Measurements through every subsection and
   sub-subsection. Replace fixed-height nesting with visible splitter handles
   or another accessible height-resize affordance at every level.
2. Give every section an explicit collapse/expand control with keyboard access,
   focus state and translated accessible name. Collapsing one section must
   release its space to siblings rather than leave a blank fixed-height box.
3. Preserve useful splitter heights and collapsed state while navigating the
   module. Reset/default layout must remain available so a dragged section can
   never be made permanently unreachable.
4. Size expensive previews/tables independently from their section header and
   controls. A nested scroll area must not consume wheel/keyboard events in a
   way that makes its parent impossible to reach.

PART 2 — SETTINGS FIELDS FOLLOW THEIR CONTAINER
------------------------------------------------

1. Audit the shared settings renderer used by EVERY module, not only
   Regression. Remove accidental fixed widths and maximum widths from ordinary
   fields; use expanding horizontal size policies and layout stretch factors.
2. When the settings panel grows by a measured amount, every field type that
   can use the space—line edit, combo, path picker, list/table, spin box and
   compound editor—must grow or deliberately allocate that space to its
   associated action button. Labels wrap or reflow without covering fields.
3. Initial module layout must derive a preferred settings width from real
   content size hints and font metrics, then clamp it to the available screen.
   The right edge of a field or action button must never begin off-screen.
4. If a form truly cannot fit the available width, use a visible, accessible
   fallback (reflow or scroll) rather than silently clipping it. A hidden
   horizontal scrollbar is not a passing result.
5. Recompute the responsive layout after a font, locale, theme, display scale,
   screen or window change. Moving a live window between monitors is part of
   the contract; first launch is not the only time the geometry can change.

PART 3 — MEASURE THE PARAMETER SPACE AND SHIP THE POLICY
--------------------------------------------------------

Build a deterministic offscreen layout harness that launches every module and
Regression's three nesting depths over at least:

* available geometries 1280x720, 1366x768, 1440x900, 1920x1080, 2560x1440,
  and current Apple-laptop Retina geometries including the reported M4 class;
* device-pixel ratios 1.0, 1.25, 1.5 and 2.0, with representative logical DPI;
* application font scales from the supported readable minimum through 200%;
* compact, default and expanded window widths/heights;
* English plus the locales with the widest measured labels, and at least one
  non-Latin locale.

Measure actual allocated/content rectangles after Qt finishes layout. Record
clipped text, truncated controls, overlap, off-window geometry, unusably small
nested panels, scrollbar visibility, and whether a field expands when its
parent expands. Do not infer success only from a screenshot or from the absence
of a Qt warning.

Generate a compact versioned policy artifact from those results—for example a
JSON breakpoint table in spaCR's packaged assets—and include the generator,
schema, source matrix and deterministic test. The artifact must be installed
in both wheel and sdist and loaded without importing heavy scientific or GPU
libraries.

FIRST-RUN AND ONGOING SELECTION
-------------------------------

On first run, read Qt's local screen/font metrics and choose the nearest safe
policy row. Store the resolved layout/density/font recommendation locally with
the metrics that justified it, while keeping the user's later changes
authoritative. On a materially different monitor or scale, recompute the safe
layout; do not overwrite a deliberate accessibility or font override.

The OS/app font is the primary accessibility signal. The generated map may
choose a starting font within tested bounds, but must prefer layout changes to
making the text smaller and must expose an immediate preview/reset in
Preferences.

HOW TO KNOW IT WORKED
---------------------

* Regression's Measurements page has automated and manual tests at all three
  nesting levels proving each container expands, contracts, collapses,
  reopens, reallocates space and remains keyboard reachable.
* On the reported M4-Mac profile, widening the settings container measurably
  widens every eligible field; fresh module windows show the complete right
  edge of settings and action buttons.
* Every registered module passes the generated geometry/font/DPI/locale matrix
  with no clipped text, overlaps, off-screen controls or unusable subsection.
  The registry drives the test so a new module cannot escape it.
* The same tests include positive controls that deliberately impose a fixed
  field width or too-narrow nested container and go red; an absence-only test
  that also passes broken layout proves nothing.
* First launch selects the expected versioned policy for measured profiles,
  window movement across different-DPI monitors triggers safe recalculation,
  and a user font/accessibility override survives both.
* Wheel and sdist installation tests prove the generated policy is present,
  schema-valid and usable from a neutral working directory.
* A real M4 Mac smoke test confirms the simulation before this item closes;
  simulated Retina metrics are necessary for the matrix but not sufficient
  evidence for the originally reported machine.

2026-09-10 -- WHY THE SETTINGS COLUMN CANNOT GROW: THE ARITHMETIC
--------------------------------------------------------------------------------

The note above records that `regression` wants 970 px of settings content and
the column's viewport is 832 px at a 2,560 px window. Here is why, because
the number is not a mystery and the fix is not a search.

`app_screen.py:1490-1514`, the body splitter:

    body.setStretchFactor(0, 1)     # settings
    body.setStretchFactor(1, 2)     # runtime
    body.setSizes([400, 800])

ONE THIRD. The settings column gets a third of whatever the window has, for
ever, at every width. 2,500 px of splitter divided 1:2 is 833, which is the
832 that was measured -- so the measurement and the arithmetic agree to one
pixel and there is nothing else to look for.

WHAT THAT MEANS FOR THE REPORT. "Widening some settings containers did not
widen their fields" is exactly right, and it is milder than the truth:
widening the window DOES widen the column, by a third of what was added, and
that third is never enough for the modules that need it. For `regression` to
reach 970 px of column the window would have to be 2,910 px wide, which is
wider than the display the report came from.

SO THE FIX IS PART 2's AND IT IS ONE OF THREE, all in that one call:

  1. DERIVE THE INITIAL SPLIT FROM THE CONTENT. This item already asks for
     it -- "Initial module layout must derive a preferred settings width
     from real content size hints and font metrics, then clamp it to the
     available screen". `[400, 800]` is a constant where a size hint
     belongs. NOTE that `setSizes` values are treated as PROPORTIONS when
     they do not sum to the splitter's width, so handing it
     `[wanted, 800]` does not give the column `wanted`; the pair has to be
     computed together against the real width.
  2. GIVE THE COLUMN A FLOOR, so the splitter cannot squeeze it below what
     its own content needs. The risk is the mirror image -- a floor wider
     than half the window crushes the runtime panel -- so the floor wants
     the same clamp the window size got: never more than about 45 %.
  3. OR MAKE THE CONTENT NARROWER. `PairedFileTableWidget`'s 750 px
     minimum is the single widest thing in regression's column, and a
     table that wide inside a settings form may simply belong somewhere
     else. That is a design question, not a layout one.

NOT DONE HERE. All three change what the user sees on every module screen,
and this session has no display. (1) and (2) are small and (3) is not, but
the reason they are not attempted is the same one this file gives for the
policy artifact: a layout change measured only offscreen is a change nobody
has seen.

2026-09-10 -- THE FIRST-RUN WIDTH IS NOW DECIDED ONCE, WITH ITS EVIDENCE
--------------------------------------------------------------------------------

"First-run selection stores nothing yet: the width is recomputed each launch
rather than resolved once and recorded with the metrics that justified it."
Done.

`preferences.get_layout_decision` / `set_layout_decision` store a small JSON
record -- the width chosen, the available geometry and the font scale it was
chosen from, and the artifact's own `why` in words.
`app._open_at_the_measured_width` reads it and re-derives ONLY when the
evidence no longer holds.

  A WIDTH ON ITS OWN CANNOT BE CHECKED LATER; a width beside the numbers it
  came from can be, and it can be seen to have EXPIRED. Move to another
  monitor or change the font scale and the record stops matching, which is
  the point: it is a decision ABOUT those numbers, so it expires when they
  do.

  A RECORD MISSING ITS EVIDENCE IS TREATED AS NO RECORD, at the storage
  boundary and at the caller. A half-read record is worse than none,
  because it would be compared against current metrics and could match by
  accident.

  THE "ONLY EVER GROWS" RULE IS UNCHANGED and still tested: a window
  already wider than the policy asks for is left alone.

Seven tests in `tests/qt/test_the_first_run_layout_is_decided_once.py`,
including that the second launch does not call `recommended_window_size` at
all.

2026-09-10 -- THE DPI AXIS IS NOT AN UNTESTED GAP. IT IS A NON-AXIS.
--------------------------------------------------------------------------------

THE RECORDED REASON WAS WRONG AND IT WAS MINE. This file said:
"`devicePixelRatio` is not something an offscreen platform lets a test set
per case, and faking it would measure the fake." Both halves are false.

QT SETS IT FROM THE ENVIRONMENT, offscreen included:

    QT_SCALE_FACTOR=1  ->  devicePixelRatio 1.00, available 800x800
    QT_SCALE_FACTOR=2  ->  devicePixelRatio 2.00, available 400x400

That is not a fake. It is the same mechanism a real 2x display uses, and
Qt halves the LOGICAL geometry exactly as a Retina panel does. A matrix
over it needs one process per ratio, which the harness already is.

SO THE MATRIX WAS RUN AT BOTH, 192 cases each, twelve minutes each:

    rows             identical
    minimum_width    identical   {1.0: 2100, 2.0: 2560}
    unfixable        identical   28 cases
    matrix           identical
    differing rows   0 of 192

BYTE-IDENTICAL, and the reason is worth more than the result. Qt lays out
in LOGICAL pixels. `devicePixelRatio` decides how many physical pixels one
logical pixel becomes -- it changes what the panel draws, not what the
layout computes. Font metrics, size hints, splitter arithmetic and the
sideways-scroll test are all logical, so none of them can move with it.

    WHAT DOES CHANGE ON A RETINA PANEL IS THE AVAILABLE GEOMETRY IN
    LOGICAL PIXELS -- 800 becomes 400 above -- and that axis the matrix
    has always covered, because it sweeps width from 400 to 2560. The
    "DPI axis" was the width axis wearing a different name.

THIS POINT IS CLOSED, and not by deciding it was too hard. It was measured
and it has no effect. The honest correction is that this file asked for an
axis that does not exist, and the thing it should have asked for -- narrow
logical widths -- was already in the harness on the day it was written.
