--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

  * Live-editing EVERY setting means some of them are expensive. Re-running
    the embedding on each keystroke would make the panel unusable; the
    display-only settings (colour, dot size, outlines) are cheap, the ones
    that change the embedding (n_neighbors, min_dist, the feature set) are
    not. Split them, and debounce or defer the expensive half rather than
    pretending they are all free.
  * The figure format follows the preference (PNG at its DPI, or PDF).
    `figure_path()` in the search grid already picks the PDF when one exists;
    the same rule should hold here so the two surfaces do not disagree.
  * Instruction 69 wants live views and searches standardised across modules.
    Anything built here should be the shape 69 would want everywhere, not a
    UMAP-only mechanism.

2026-08-12 - BUILT. WHICH GRID IT WAS, AND WHAT PROPAGATE MEANS.
--------------------------------------------------------------------------------

WHICH OF THE TWO GRIDS. Measured before removing anything, as this file
asked. There are exactly two on the Image UMAP screen:

  1. `SearchFigureGrid`, in the HYPERPARAMETER SEARCH card. Only reachable
     with the "Hyperparameter search" toggle on, and instruction 35's end
     state (grid + summary) lives there.
  2. `plot_clusters_grid` -> `plot_grid`, in the MODULE'S OWN OUTPUT. It is
     a second matplotlib figure -- one colour-bordered panel per cluster,
     each a montage of crops -- and `plot_grid` calls `plt.show()`, so the
     bridge emits it AFTER the embedding, and `FigureQueue.add_figure`
     jumps to the newest. Measured: a default run emits `['embedding',
     'grid']` and the view lands on the grid.

IT IS THE SECOND ONE, and the request settles it without needing to guess:
"the LIVE view is perfect ... the NON LIVE image UMAP figure settings ...".
On this screen "Live" is one named toggle -- the interactive explorer -- and
the search has its own, "Hyperparameter search". So live/non-live is
explorer/static-figure, and "the grid at the end" is the grid at the end of
the NON-LIVE surface. 35 IS NOT REVISED; nothing in the search card was
touched.

    spacr/settings.py  set_default_umap_image_settings
        plot_cluster_grids  True -> False

    The Tk GUI has always passed False (`gui_elements`), so this only makes
    the default agree with the one surface that already had it right. The
    figure is one checkbox away for anyone who wants it, and a test asserts
    that turning it on still draws it -- this is a change to the DEFAULT,
    not a removal from the module. The setting's tooltip and the notebook
    that documents it were updated with it.

THE NON-LIVE FIGURE SETTINGS NOW HOLD EVERY IMAGE UMAP SETTING, live.

    spacr/qt/widgets/umap_figure_settings.py   (new)
    spacr/qt/widgets/figure_queue.py           (_FigureSettingsDialog)

    31 settings, seeded from the run that drew the figure -- the payload
    `generate_image_umap` attaches now carries the settings it used and the
    labels it coloured by, so the window opens on 33 rather than on the
    package's 50.

    THE FIELDS ARE TIERED BY WHAT THEY COST, which is the part this file
    warned about. The tier is a fact about the artists and the data, so it
    lives beside the field:

      style   dot size, colour, opacity, outline width. Set on the
              collections already drawn. Nothing is re-read.
      redraw  figure size, image count, image zoom, which layers are drawn.
              Replotted FROM THE SAME EMBEDDING -- `redraw_umap_figure`
              reads `payload['embedding']` and never calls the reducer, so
              no point moves. Debounced (250 ms): a spin-box drag is one
              render, not thirty. Measured: four edits -> one apply.
      rerun   n_neighbors, min_dist, metric, eps, min_samples, clustering,
              reduction_method, the feature filter, row_limit, colour-by.
              These change the embedding. There is no honest live apply:
              recomputing moves every point and the arrangement the user
              was reading is the whole value of the projection. Editable,
              propagated, and the section says "applies on the next run".

    Cancel puts the figure back, because live apply with no way out is a
    trap -- the user drags a control to see what it does and there is no
    longer an "as it was".

    THE FORMAT FOLLOWS THE PREFERENCE, unchanged and now asserted: the
    re-render goes through `FigureQueue._render_figure` ->
    `render_figure_to_png`, which writes the PNG at the preference DPI and
    the sibling vector page in PDF mode. Same rule as the search grid's
    `figure_path`, so the two surfaces cannot disagree.

THE DOTS. Measured what was actually left, as this file asked:

    Image UMAP screen                     1  (the module header link)
    Image UMAP figure settings dialog     3  (one per figure control)

    The three in the dialog are gone -- `install_api_tooltips(...,
    api_dots=False)`, exactly what 57 did for the search dialog and
    live_preview did before it. Measured after: 0 dots, 34 labels carrying
    `href=` help (3 figure controls + 31 Image UMAP settings). The test
    that asserted the dot EXISTS was inverted, not deleted, and keeps its

    documentation had left with the decoration.

    THE MODULE HEADER DOT IS KEPT, deliberately. It is one link beside the
    module's description, not a column of texture beside a form, which is
    the distinction `install_api_tooltips` already documents ("anywhere the
    settings are sparse enough for a dot to look like an affordance rather
    than texture, leave it on"). It is also shared by every screen, so
    removing it is a decision about all 36 modules and not about this one.

PROPAGATE MEANS: THE SAME MODULE'S NEXT LAUNCH, VIA THE SETTINGS PANEL.

    Decided, and it is the existing seam rather than a new store, as this
    file suggested. `FigureQueue.set_propagate_callback` is wired by
    `AppScreen` to `_propagate_live_settings`, which is
    `SettingsWidgets.set_value_for_key` -- the same route the Mask live
    preview's "Propagate settings", the UMAP explorer's display window and
    the hyperparameter panel's Apply all take. The values land in the
    module's own settings panel, so they are what the next Run collects,
    what a settings CSV save writes, and what the run journal records.

    NOT cross-module, and not a new file. `point_alpha` means the same
    thing in Classify's plots, but a figure the user was looking at in
    Image UMAP is not evidence about what they want Classify to do, and a
    propagate that silently rewrote four other modules would be impossible
    to undo from the screen it was pressed on.

    Wired for every module, not only UMAP: the figure background, text
    colour and text size propagate the same way, and there is no reason for
    the button to exist on one screen only.
