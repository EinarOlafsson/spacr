================================================================================
THE MEASUREMENTS TABLE'S COLUMNS SAY WHAT THEY CONTROL
================================================================================

Status:    DONE 2026-08-21.
Requested: 2026-08-21 -- "for the measurements table tab, there needs to be a
           tooltip when the mouse is hovered over measurement, and level and
           plot and show and compare that explains what each field related to
           them controlls."
Owner:     Qt GUI (Measurements table tab)

--------------------------------------------------------------------------------
WHAT IS ASKED
--------------------------------------------------------------------------------

Five column headings -- MEASUREMENT, LEVEL, PLOT, SHOW, COMPARE -- each
govern a field in every row, and none of them says what its field does. A
heading that names a control without explaining it is a control the user
learns by trying, on a table where trying means redrawing a plot.

EACH TOOLTIP EXPLAINS THE FIELD, not the heading. "Level" is a word the user
can already read; what they cannot read off the screen is that it decides
whether a row is measured per cell, per well or per gene, and that changing
it changes what a datapoint IS on the plot below.

WRITE THEM FROM THE CODE. A tooltip that describes intent rather than
behaviour goes stale the first time the behaviour moves, and a wrong tooltip
is worse than none: it is believed.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* Hovering each of the five headings shows a tooltip that names what the
  field under it changes, in terms of what the user will see happen.
* The tooltips survive a rename of the heading text -- they are attached to
  the column, not matched by label.
* A test asserts each of the five has non-empty help, so a new column cannot
  be added without one.
* Same hover behaviour as instruction 208 asks for elsewhere: the tooltip
  does not vanish when the pointer moves onto it.

--------------------------------------------------------------------------------
DONE 2026-08-21
--------------------------------------------------------------------------------

`HEADING_HELP` in `gene_measurement_compare`, KEYED BY THE FIELD each
heading governs. A tooltip looked up by the heading's TEXT stops working the
moment somebody renames the heading -- and stops working SILENTLY, because
the label still draws and the help is simply gone. The test renames a
heading and asserts the help survives.

WRITTEN FROM THE CODE, and each says what the field CHANGES about what the
user will see:

  * `level` says a datapoint becomes a cell, a well or a plate, AND that
    this changes the statistics as much as the picture -- a screen
    randomises at the well, so testing across cells treats thousands of
    measurements of one well as independent evidence.
  * `show` says the statistics underneath do NOT follow it, because a test
    computed on one of two groups is not a comparison at all.
  * `compare` says the same cells under three contrasts give three
    different p-values, which is why it is a separate choice.
  * `plot` says it changes nothing about the values or the test.
  * `measurement` says the options come from the columns the tables have.

THE FILTER IS HELD ON THE PANEL. Qt keeps a bare pointer to an event filter,
so one that only the constructor referenced is collected as soon as the call
returns -- after which the heading stops responding and nothing says why.
The same trap instruction 228 records.

The tooltips never time out, which is what instruction 208 asks for
elsewhere: help that disappears when you reach for it cannot be read to the
end.
