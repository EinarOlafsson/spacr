================================================================================
THE INTENSITY RESCALE FACTOR IS PER FIELD, AND NOTHING RECORDS IT
================================================================================

Status:    done, 2026-08-14. Found while answering the dtype question of
           instruction 91.
Requested: 2026-08-13 - "the dtype matter for more than training it matters
           for measurements as well."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Measurement now plans one comparable intensity scale per plate before workers
start, records one auditable rescale row per field, retains the fixed normalized
float conversion, and explicitly marks any unavoidable per-field fallback as
non-comparable.

--------------------------------------------------------------------------------
THE DEFECT
--------------------------------------------------------------------------------

`measure._promote_merged_to_uint16` brings a merged stack that is neither
uint8 nor uint16 into the measure pipeline's working dtype. It is careful
work -- it rescales rather than truncating, and it uses ONE factor across all
intensity planes so the ratio between channels is untouched. The docstring
records the bug it was written to fix: `astype(np.uint16)` on a float32 stack
on [0, 1] truncated every pixel to 0 and measured a whole field as black.

BUT THE FACTOR IS CHOSEN FROM THE FIELD'S OWN MAXIMUM:

    if float and top <= 1.0:   factor = 65535.0          <- fixed, comparable
    elif top > 65535.0:        factor = 65535.0 / top    <- PER FIELD

and `_measure_crop_core` runs once per file. So when a stack's intensities
run past the 16-bit ceiling, a BRIGHT field is divided by more than a DIM
one, and `mean_intensity` for the same biological object comes out different
in the two. Every intensity feature, every recruitment ratio computed from
them, and every per-well aggregate is then comparing numbers that are not on
the same scale.

AND NOTHING SAYS SO. The factor is printed only when `verbose` is on, and it
is never written to the database. A user reading measurements.db has no way
to learn that the intensities in it were scaled per field, let alone by what.

--------------------------------------------------------------------------------
WHY IT MATTERS, AND HOW OFTEN
--------------------------------------------------------------------------------

The float-on-[0, 1] case -- which is what `io._normalize_img_batch` writes --
uses a FIXED 65535 and is comparable across fields. That is the common path
and it is fine.

The dangerous path is a merged stack whose values exceed 65535: raw float
data that was never normalised, a converted 32-bit acquisition, or anything
summed before merging. It is not the common case, which is exactly why it
would go unnoticed: the run completes, the numbers look plausible, and the
comparison between wells is quietly wrong.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

  1. RECORD THE FACTOR PER FIELD, in the database, beside the measurements it
     scaled. That is the minimum: a number nobody can see cannot be corrected
     for.
  2. WARN UNCONDITIONALLY, not only under `verbose`, when the factor is not
     1.0 and not the fixed 65535. A per-field rescale is a statement about
     comparability and belongs in the run's output whatever the log level.
  3. PREFER A PLATE-WIDE FACTOR. One maximum taken across the plate makes
     every field comparable again, at the cost of one pass over the merged
     arrays before measuring -- which is a read of the headers plus a max, not
     a second measure. The per-field factor should be the fallback for the
     case where that pass cannot be made.
  4. Consider REFUSING instead. A stack whose intensities exceed the 16-bit
     ceiling is arguably a conversion problem upstream, and silently
     compressing it is the kind of accommodation that hides the real fault.
     At minimum the pre-flight (`validate.describe_resources` already reads
     one array's dtype) should say so before the run rather than after.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Two fields of the same plate with different maxima produce intensities on the
same scale, or the database records the scale each was measured on; a run that
rescales says so whatever the log level; and a user comparing two wells can
tell from the artifact alone whether the comparison is valid.

--------------------------------------------------------------------------------
2026-08-14 - COMPLETE: ONE PLATE SCALE, ONE AUDIT ROW PER FIELD
--------------------------------------------------------------------------------

`spacr.intensity_rescale` now scans every merged field before the worker pool
starts, groups raw-valued fields by plate, and computes one factor from the
largest raw intensity on each plate. The scan covers the complete source even
on resume, so a resumed field cannot silently acquire a different scale from
fields already in the database. Normalised floating-point fields retain the
fixed x65535 conversion. Label planes are rounded but never scaled.

The plan copied into workers is O(number of plates), not O(number of fields):
workers already have to load their own array and recompute its maximum, so the
pool receives only plate maxima plus the exceptional filenames. If a file
could not be scanned, or became brighter between scan and measurement, that
worker makes a per-field fallback decision and explicitly marks it
non-comparable.

Every successfully processed field now upserts one row into
`measurements.db:intensity_rescale`. It records the canonical field keys,
source file, original dtype and maximum, factor, factor scope, plate maximum,
target dtype, and `comparable_within_plate`. The `prcf` primary key makes a
retry idempotent. The table is part of spaCR's schema and measure-resume
allow-list, so stale provenance is cleared with stale measurements and no
other module's rows are exposed to resume deletion.

A non-identity/non-normalised factor prints a `WARNING` regardless of
`verbose`, naming whether it is plate-wide or a non-comparable fallback and
pointing to the database table. `validate.describe_resources` performs the
same scan for a measure dry-run and reports values above 65535, the planned
plate factors, any scan failures, and where the provenance will be stored.

TESTED: two raw fields with different maxima share one factor; different
plates get independent factors; normalised float data keeps x65535; labels
retain their identities; malformed pre-pass input falls back explicitly; a
field changed after the scan cannot reuse an unsafe factor; dry-run reports
the uint16 overflow before writing; warnings ignore `verbose`; a real measure
worker writes a queryable provenance row. The focused measurement, resume,
schema, and validation suites pass: 506 tests.
