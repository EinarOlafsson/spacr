GROUP A -- CELLPOSE 3 LEFTOVERS. Four sites pass `channels=` to
`CellposeModel.eval`. Cellpose 4.0.7 logs "channels deprecated in v4.0.1+"
and never reads the value. `spacr.model_compare.IGNORED_ARGUMENTS` already

    spacr/object.py:1853      segment_cellpose          channels=[0, 1]

Mechanical. Delete the argument; select the planes before the handover, as

GROUP B -- align.py SILENTLY MIXES OR DROPS DATA. Five defects, two of them
verified by hand on 2026-08-15:

  B1. TWO WELLS BECOME ONE SITE  [VERIFIED]
      `_MERGED`'s (?P<plate>[^_]+) cannot match a plate token containing the
      separator, so the last-resort branch reads the WELL token as a channel:

          _parse_name('exp1_plate1_B07_001') -> ('','',1) as channel 1
          _parse_name('exp1_plate1_C08_001') -> ('','',1) as channel 8

      Both key to site ('','',1). `write_stack` composites well C08 into well
      B07's canvas as another plane, and every `align_coordinates` row carries
      an empty plateID/rowID/columnID, so nothing downstream can separate them
      again. Any plate named with an underscore contaminates across wells.

  B2. A 1536-WELL EXPORT KEEPS ONE TILE PER WELL  [VERIFIED]
      `_YOKOGAWA`'s (?P<well>[A-Za-z]?\d+) allows at most one letter, so
      'AA01' never matches; the trailing digits of the CHANNEL token become
      the field, and F001..F004 all key to the same site. Only the last file
      read survives. `spacr.schema.parse_well('AA01') == ('r27','c1')`, so the
      rest of spaCR handles 1536 plates -- only align's regex does not.

  B3. `scan_tiles(reference_channel=N)` is documented as "which channel drives
      registration" and stored as `Tile.channel`, but nothing in align.py ever
      reads `Tile.channel`. `estimate_offsets` uses its own parameter, default
      0. Choosing the reference channel at scan time silently does nothing.

  B4. `align_folder` applies `grid` to the whole folder and splits by well
      afterwards, so a per-well acquisition grid cannot be expressed: two
      wells acquired 2x2 are refused as "grid 2x2 has room for 4 tiles but 8
      were found". `scan_tiles` is called before `group_tiles`.

  B5. `estimate_offsets(max_open_tiles=1)` registers nothing. A pair needs
      both tiles open; `_ReaderCache` evicts and closes tile A while
      `_register_pair` still holds it. The AttributeError is swallowed into
      `PairResult.note`, every tile falls back to its stage position, and the
      run looks like a plate that simply would not register.

GROUP C -- schema.py KEY AND COLUMN HAZARDS. Four defects, one verified:

  C1. `canonicalise_columns` CREATES A COLLISION SQLITE REFUSES  [VERIFIED]

          canonicalise_columns(['row','rowid']) -> ['rowID','rowid']
          to_sql -> OperationalError: duplicate column name: rowid

      SQLite compares identifiers case-insensitively -- this is how a column
      named rowID once shadowed the implicit rowid and made a DELETE remove a
      whole table. The rename guard is exact while the collision it must avoid
      is case-folded. The fix must land in BOTH `schema.canonicalise_columns`
      and `utils.canonicalize_measurement_columns` in one commit, or the two
      frame canonicalisers disagree.

  C2. `compose_prcf(..., time="xy")` writes `p_r1_c1_f1_txy`, which
      `parse_prcf` refuses with "'txy' is not a field id". A preserved token
      round-trips in the FIELD slot but not the TIME slot.

  C3. `parse_field_stem` / `parse_object_stem` read a file name LEFT to right
      at fixed positions while `parse_prcf` reads right to left. So
      `parse_field_stem('my_plate_A01_3')` gives plateID='my', rowID='plate',
      and surplus components are dropped outright:
      `parse_field_stem('plate1_A01_3_junk') == parse_field_stem('plate1_A01_3')`.

  C4. `_sanitise_token` maps field 'a_b' and field 'a-b' onto one id, 'fa-b'.
      Two fields go in, one comes out -- via the escape hatch rather than via
      `_safe_int_convert`. Tier-2 path only, so QC-visible.

GROUP D -- RESOLUTION AND SHIPPED DATA. Two:

  D1. `generate_masks_from_imgs` discards the loader's `orig_dims`: on the

C3 -- THE REPAIR STATED ABOVE IS WRONG. DO NOT DO IT.

  "Parse the stem right to left like every other key parser" was tried and
  reverted. Two things kill it:

  * ``_check_plate`` REFUSES a plate id containing the separator, because
    ``my_plate_r1_c1_f1`` cannot be split back. So right-to-left parsing
    produces a plateID the composer then rejects -- the property test's own
    expectation, ``plateID == 'my_plate'``, is unsatisfiable by design.
  * spacr/ml.py:3191 already reasoned this out and chose left-to-right
    deliberately: "a prc is a KEY, which has a fixed number of components and
    is therefore parseable right to left; this is a crop FILE NAME, whose
    grammar is <plate>_<well>_<field>[_<time>]_<object> -- a variable-length
    tail with no right anchor, so the well can only be found by counting from
    the left." A file name is not a key, and the xfail's premise that it
    should parse like one is the error.

  THE REAL REPAIR, named in that same comment and marked "NEEDS FOLLOW-UP IN
  spacr/schema.py": fix the WRITER, not the parser. Either make the crop
  writer percent-escape the separator in the plate component -- the escape
  table is now :data:`spacr.schema.KEY_ESCAPES`, shared and reversible, so
  this is a smaller job than it was -- or record the plate-id length in the
  name. Until then a plate id holding '_' shifts every position and the
  grammar carries nothing that can undo it.

  The injectivity half ('plate1_A01_3_junk' == 'plate1_A01_3') would be fixed
  by refusing a stem with surplus components, which is independent of the
  above and is the smaller, safer half if it is wanted on its own. It does
  change 4-part names from silently-wrong to raising, so it is a decision
  about existing pipelines rather than a free repair.

C2 -- unchanged, still the owner's call: making a trailing t-token count as a
  timepoint widens what "timelapse" means for every reader of every database.

B4 -- per-well acquisition grid. Real, and the fix is a restructure rather
  than a patch: scan_tiles assigns grid positions across the whole folder
  before align_folder ever calls group_tiles, so the per-well layout cannot
  be expressed. Group first, then lay each group out.

D2 -- the maintainer's, unchanged. Which gene does a shared protospacer count

2026-08-15 - AN OPEN ASYMMETRY LEFT BY THE C3 ESCAPE. NEEDS A DECISION.
--------------------------------------------------------------------------------

C3 was fixed by escaping the plate id in the composer, which was the right
call. It left two spellings of one well key in the tree, and they are not
interchangeable:

    schema.compose_prc('exp1_plate2', 'rB', 'c3')  ->  exp1%5Fplate2_rB_c3
    ml.py's three hand-joins                        ->  exp1_plate2_rB_c3

Both parse. `_split_prc` now unescapes, so it reads either one correctly, and
`schema.parse_prcf` always did. Nothing is broken TODAY. But the two are
different strings for the same well, so anything that joins a key from one
source to a key from the other matches nothing, silently -- which is the
failure mode `prc` exists to prevent.

WHY IT WAS NOT JUST FIXED. Routing the hand-joins through an escaping
composer was implemented and reverted, because it changes the `prc` string
WRITTEN INTO DATABASES, and two tests assert the un-escaped form on purpose:

    test_an_underscored_plate_id_keeps_the_regression_qc_tables
    test_a_row_id_carrying_a_plate_whose_name_has_an_underscore

Those tests are not wrong; they encode the older contract, under which an
underscored plate is carried as a FOUR-component key and separated by the
row/column guard in `_split_prc`. The escape carries it as three. Both are
coherent designs. They cannot both be the stored format.

THE DECISION NEEDED, and it is the maintainer's because it is about data on
disk rather than about code:

  (a) ESCAPE EVERYWHERE. One spelling, three components always, and
      `_split_prc`'s four-component path becomes legacy-only. Databases
      written before this hold the old spelling, so it needs a migration or
      a reader that accepts both -- and `database_schema` already has the
      machinery for exactly that kind of rename.

  (b) HAND-JOIN EVERYWHERE. Revert the escape in `compose_prc`, keep the
      four-component key, and rely on the row/column guard. Cheaper today,
      but it is the design C3 was filed against: it cannot represent a plate
      whose name contains BOTH the separator and something that parses as a
      row/column pair.

(a) is the better end state and the more expensive one. Until it is chosen,
do not "tidy" the hand-joins -- that is the revert described above, and it
will look like a cleanup while changing what is written to disk.

--------------------------------------------------------------------------------
DECIDED 2026-08-16: (a). ESCAPE EVERYWHERE. DONE.
--------------------------------------------------------------------------------

The maintainer chose one spelling. `prc` is now always THREE components, and
a plate id holding the separator or a `%` is percent-escaped:

    exp1_plate2 / rB / c3  ->  exp1%5Fplate2_rB_c3

SEVEN hand-joins in ml.py -- not the three first found -- now go through
`_compose_prc_column`, the vectorised counterpart of `schema.compose_prc`.
Verified identical to it on canonical row/column tokens.

ROW AND COLUMN ARE STILL NOT CANONICALISED, deliberately. `compose_prc`
canonicalises them (`row_id('rB')` -> `'r470'`); the hand-joins never did, and
`_split_prc`'s docstring says why -- "a rewritten token would change the
identity rows are joined on". Only the PLATE escape changed.

OLD DATABASES STILL READ, which is what made (a) affordable: `_split_prc`
unescapes, and unescaping is a no-op on a key carrying no escape, so a
four-component legacy key parses exactly as before through the
`is_row_column_pair` guard. Accept both, write one.

ONE TEST CHANGED MEANING RATHER THAN BREAKING, and it is worth knowing:
`test_an_underscored_plate_id_keeps_the_regression_qc_tables` asserted that a
naive `prc.str.split('_')` RAISES on an underscored plate. It no longer does
-- the key is three components now, so the naive split succeeds and returns
the ESCAPED plate id. That is the improvement and the new trap at once, so
the test now asserts both halves: the naive splitter gets a plausible-looking
`exp1%5Fplate1` instead of an error, and only `_split_prc` gives back the
plate the user typed.
