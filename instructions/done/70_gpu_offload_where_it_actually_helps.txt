================================================================================
OFFLOAD THE COMPUTE THAT IS ACTUALLY GPU-SHAPED
================================================================================

Status:    not started. Under investigation 2026-08-10; findings go here.
Requested: 2026-08-10 — "Cupy is the GPU accelerated numpy and there are other GPU translations of python packages. Are there any aspects of any modules e.g. measure, annotate, image UMAP that could be accelerated and therefore made smoother and faster by offloading some compute to the GPU?"

--------------------------------------------------------------------------------
WHAT IS ALREADY TRUE
--------------------------------------------------------------------------------

Measured on the development machine, 2026-08-10:

    torch          2.9.1+cu128   INSTALLED, and already a hard dependency
    GPU            RTX 3090, 24 GB
    cupy           NOT installed
    cucim          NOT installed
    cuml           NOT installed
    pyclesperanto  NOT installed

That asymmetry is the most important fact in this task. `torch` is already
paid for -- it ships with the tool, Cellpose needs it, and every user with a
GPU already has a working CUDA stack for it. Anything expressible in torch
is nearly free to adopt. Anything needing cupy/cucim/cuml is a NEW
dependency with a CUDA-version coupling, and instruction 59 is trying to get
this package onto conda-forge, where every extra pinned CUDA dependency is a
packaging problem. So the bar for "add cupy" is much higher than the bar for
"use the torch already imported".

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Two different goals are hiding in the request, and they need separating:

  THROUGHPUT -- measure runs over a whole plate and takes as long as it
  takes. A 2x here is real but nobody is watching.

  SMOOTHNESS -- annotate and the UMAP search are INTERACTIVE. A stall is
  felt. But a stall is only GPU-fixable if it is compute; if it is disk I/O
  or work on the Qt event loop then a GPU does nothing, and instruction 55
  has already found that most spaCR stalls were the event loop.

Do not accept "make it faster with the GPU" as a goal. Each candidate needs
a measurement first, and the honest answer for some of them will be that the
bottleneck is elsewhere.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. MEASURE BEFORE MOVING ANYTHING. The rule instruction 55 arrived at the
   hard way applies exactly: fix what the profile names, then A/B the fix in
   fresh processes, because the profiler itself distorts call-heavy library
   code. A GPU port that is not A/B'd is a guess with extra dependencies.
2. Prefer torch to cupy wherever both would work, for the packaging reason
   above. Per-label reductions (`scatter_add` over label ids), distance
   transforms, convolutions, histograms and morphology-by-max-pool are all
   expressible in torch.
3. Watch the transfer cost. These are per-field images and int32 label
   masks; a kernel that saves 5 ms and costs 8 ms of PCIe transfer is a
   regression. Batch per field, not per object.
4. Keep the CPU path. A GPU path that is not optional makes the tool
   unusable on a laptop, and the test suite runs headless in CI without one.
   Every offload needs a fallback and a test that exercises it.
5. Say where GPU is the WRONG lever, and put that in this file too. That is
   as useful an answer as a speedup, and it stops the question being asked
   again.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A measured before/after on a real plate for throughput work, and on the tick
monitor for interactive work — with the CPU fallback still passing its
tests, and no new hard dependency that conda-forge cannot carry.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Nothing yet. Related: instruction 55 owns the interactive stalls and has the
tick-monitor method; 59 owns the conda-forge packaging constraint that makes
new CUDA dependencies expensive; 71 is the measurement-expansion question

--------------------------------------------------------------------------------
2026-08-10 - INVESTIGATED AND MEASURED. THE ANSWER IS MOSTLY "NOT THE GPU".
--------------------------------------------------------------------------------

Full findings: `instructions/data/70_gpu_investigation.txt`. 70 agents, 45
findings survived independent fact-checking against the source.

THE HEADLINE, and it is the opposite of what the question assumed: almost
nothing here is compute-bound in the way that makes cupy pay. The three
things that actually make spaCR feel slow are

  (a) accidental O(objects x image) loops in measure.py -- a whole-field
      pass run once per object;
  (b) a Qt paint path that re-composites the layer stack in numpy on the
      GUI thread;
  (c) PNG inflate in annotate.

None of the three is a GPU problem. (a) becomes 25-87x faster on ONE CPU
core once it stops touching the whole field per object, (b) is fixed by
QPainter, and (c) has no CUDA decoder available here.

MEASURED CPU WINS, all bit-identical to the current output, all needing only
`find_objects` added to the scipy.ndimage import already there:

    _calculate_radial_distribution   22.07 s -> 0.254 s   87x   (per field)
    _outside_intensity                3.04 s -> 0.041 s   74x   (per mask/chan)
    colocalization pair loop           3.28 s -> 1.36 s  2.4x   (per field)
    percentile batching in
      _extended_regionprops_table     4.9 s of 48,816 calls -> 1 call, 7.3x

That is ~25 s per field of pure waste. On a 2048^2 field with ~800 pairs the
radial family alone was measured at 360-490 s.

WHERE THE GPU DOES WIN, and it is narrow: torch is already a core dependency
(`setup.py:205`, torch>=2.0,<3.0), so it costs nothing to use. A verified
exact port exists -- five iterations of
`torch.maximum(F.max_pool2d(x,(1,3),1,(0,1)), F.max_pool2d(x,(3,1),1,(1,0)))`
is BIT-IDENTICAL to `binary_dilation(mask, iterations=5)` across 200
randomised shapes including border-touching ones. But batched over 196 crops
it is only 2.3x the FIXED CPU version, which does not repay a ~300 MiB CUDA
context inside a multiprocessing worker.

THE DECISIVE OBSTACLE for the radial family: torch has no exact Euclidean
distance transform, in core or in nn.functional, and the EDT is the per-
object cost. Moving that to the GPU means writing one.

TRAP FOR ANYONE PORTING PERCENTILES: `torch.quantile` raises
"input tensor is too large" above exactly 2**24 = 16,777,216 elements, on
CPU as well as CUDA -- so there is no fallback, though it is testable in CI.
A 2048^2 2-D field is 4.2M and fine; a 40-plane 1024^2 stack is 42M and
raises. `torch.sort`/`torch.kthvalue` have no cap but are nearest-rank while
numpy interpolates, so a faithful swap needs the floor/ceil lerp.

DEPENDENCY VERDICT: add neither cupy nor cucim/cuml. cupy is a ~100 MB wheel
(~500 MB installed) pinned to the CUDA major version, which puts a
CUDA-coupled variant matrix into the conda-forge recipe (instruction 59);
cucim/cudf/cuml would add the rapidsai channel to the install instructions.
After the CPU fixes there is nothing left for them to accelerate.

DO THE CPU FIXES FIRST. They are the whole win, they need no dependency, and
each is guarded by a before/after DataFrame-equality test since all four are
claimed bit-identical.

--------------------------------------------------------------------------------
2026-08-10 - CLOSED BY THE MAINTAINER. NO GPU OFFLOAD, NO NEW DEPENDENCY.
--------------------------------------------------------------------------------

Decided 2026-08-10 — "GPU offload - is cloased, we will not ofloade anything
to the GPU and will not install cupy or cucim".

That matches what the investigation found: the expensive work is
O(objects x image) full-field passes inside Python loops, and `measure` runs
one field per CPU worker through `mp.Pool`, so N workers would contend for
one device and each would carry its own ~300 MiB CUDA context. The GPU would
turn parallel work into queued work.

WHAT SURVIVES THIS DECISION, and it is the whole win: the CPU fixes are
independent of it and were all measured bit-identical.

    _calculate_radial_distribution   22.07 s -> 0.254 s   87x
    _outside_intensity                3.04 s -> 0.041 s   74x
    colocalization pair loop           3.28 s -> 1.36 s  2.4x
    percentile batching             48,816 calls -> 1     7.3x

They need only `find_objects` added to the `scipy.ndimage` import already
there. They are NOT closed by this decision and are the reason the GPU was
never needed. They belong to instruction 71 and to whoever next touches
measure.py.

Full findings kept at `instructions/data/70_gpu_investigation.txt` so the
reasoning survives the decision -- including the two facts most likely to be
re-asked: torch has no exact Euclidean distance transform (the EDT is the
per-object cost), and `torch.quantile` raises above 2**24 elements on CPU as
well as CUDA.
