--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not started. `spacr/qt/widgets/gate_editor.py` owns `GateCanvas`, which
extends `GraphCanvas` (`spacr/qt/widgets/graph_builder.py`) and pins the
axes while gating -- `RESCALE_ON_FILTER = False`, because rescaling to the
rows a gate kept moves the view out from under the gate being dragged.

Gating today is 2D: a shape drawn in data coordinates on the one pair of
axes on screen. There is no plane selection, no extrusion to a third
dimension, and no composition between gates.

Instruction 31 (gate editor redesign) is the neighbouring open task; read
it before starting, as the two touch the same panel.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A 3D scatter the user cannot gate is a picture rather than a tool. Every
population question in a screen -- "the bright, small, round ones" -- is
three measurements at once, and answering it today means gating twice on
two 2D plots and intersecting the results by hand, which is both slow and
unrecorded: the intersection exists only in whatever the user did next.

Composition and per-gate thresholds are what make the result reproducible.
A gate that is "this cylinder MINUS that box, with intensity above 400" is
a statement someone else can re-run; the same population arrived at by two
sequential 2D gates is not.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. PLANE SELECTION. In 3D mode, clicking one of the three planes (XY, XZ,
   YZ) selects it as the anchor and gives it a blue hue aura. The aura is
   the affordance: it says which surface the next shape lands on, before
   the user commits to drawing. Selection must be visible from any camera
   angle, so it is a translucent filled quad on the plane rather than an
   edge highlight.

2. DRAW ON THE ANCHOR PLANE. Three tools, all drawn in the anchor plane's
   2D data coordinates:
       circle    -> extrudes to a CYLINDER along the plane's normal
       rectangle -> extrudes to a BOX
       polygon   -> extrudes to a PRISM
   Extrusion happens when the gate is generated, not while drawing, so the
   drawing interaction stays 2D and reuses the existing gate geometry.

3. EXTENT ALONG THE NORMAL. A shape on a plane is infinite along the third
   axis until told otherwise; that is what point 4's thresholds are for.
   The default has to be a decision rather than an accident -- suggest
   full extent of the data along the normal, so a drawn gate initially
   means exactly what the 2D gate on that plane would have meant, and
   narrowing it is an explicit act.

4. PER-GATE THRESHOLDS. Each gate carries a threshold per measurement it
   is defined by, editable in the gates panel. For an extruded shape that
   includes the normal axis, which is how the user bounds the cylinder's
   height.

5. COMPOSITION. A new gate on the same graph is either its own gate, or
   ADDS to / SUBTRACTS from the gates currently in view and selected in
   the gates panel. Model this as an ordered list of (gate, operator)
   rather than a tree: the user's words are "subtracting or add from/to
   the other gates in view and that are chosen in the gates panel", which
   is a running composition over a selection, and an ordered list is what
   can be shown back to them as a sentence.

6. PERSISTENCE. A composed 3D gate has to round-trip through whatever the
   gate panel saves, or the reproducibility argument above is lost. Check
   what `gate_editor` writes today before designing the record.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

On a 3D scatter: click a plane, it takes a blue aura; draw a circle on it;
the gate selects a cylinder of points, verified by comparing the selected
row count against the same predicate evaluated in pandas. Draw a second
shape, set it to subtract, and the count drops by exactly the number of
rows in the intersection. Reopen the saved gate and get the same rows.

asked for: `CylinderGate.from_ellipse` and `PrismGate.from_polygon` take the

2026-08-13 (last) - COMPOSITION IS BUILT, AND TWO OF THE THREE PHANTOM
                    SETTINGS NOW TURN SOMETHING
--------------------------------------------------------------------------------

COMPOSITION (point 5). `CompositeGate` -- union, intersect, subtract over
other gates.

    OPERANDS ARE NAMES, NOT COPIES, and that is the whole design decision.
    Copies would make `mask` self-contained, which is tidier, and would mean
    that adjusting one of the gates being combined left the composite showing
    the OLD shape, silently, for as long as nobody looked. One source of truth
    costs a resolver; two sources cost a wrong answer.

So `CompositeGate.mask` cannot work alone and SAYS SO rather than guessing;
`GateSet.mask` resolves the names. An operand carries its OWN ancestors,
because a gate drawn inside another means the pair -- combining it as the
shape alone would include rows its parent excluded.

SUBTRACT KEEPS THE ORDER IT WAS GIVEN. A minus B is not B minus A, and a set
that sorted its operands would silently change which one the user meant.

NOT THE SAME THING AS `parent`, and both exist because both are asked for. A
parent is SEQUENTIAL gating -- draw inside what you already kept -- which is
always an intersection and always a tree. This is set algebra between
siblings, which is neither. A composite can still have a parent.

What it refuses, each with the reason: fewer than two operands, a gate
combining itself, the same operand twice (a gate unioned with itself is
itself and subtracted from itself is empty -- neither is likely to be meant),
an unknown operation, a deleted operand (it must not quietly become the union
of what is left), and a loop, which is a sentence naming the loop rather than
a RecursionError.

THE PHANTOM SETTINGS. This file set the bar itself: "GateEditorSettings
should end this instruction with ZERO fields that nothing reads." Two of the
three now read:

  snap_to_axis   read on button RELEASE, not during the drag -- snapping
                 mid-turn would fight the user's hand, and the point is only
                 about the final view. Only in 3D, and only when the view has
                 actually been turned: snapping a volume nobody rotated would
                 move a view someone set deliberately.
  spin_speed     matplotlib has no public setting for this -- Axes3D turns
                 the drag straight into degrees inside `_on_move` -- so the
                 method is WRAPPED rather than reimplemented. The wrapper
                 scales the reported cursor movement and lets matplotlib do
                 the rest, which keeps the rotation matplotlib's and the
                 speed ours. Guarded end to end: a matplotlib whose internals
                 moved leaves the rotation at normal speed, which is a
                 setting not taking effect rather than a volume that will not
                 turn. At 1.0 nothing is wrapped at all.

`voxel_bins` IS THE ONE LEFT. It needs the volume to aggregate rather than
scatter, which is a rendering change and not a wiring one, so it keeps its
"saved but not yet in effect" note honestly.

2026-08-13 (later again) - POINT 4 IS DONE: PER-GATE THRESHOLDS
--------------------------------------------------------------------------------

`Gate.thresholds()` and `Gate.with_threshold(column, low, high)`, plus a row
per measurement in the gates panel under the hierarchy.

`thresholds()` AND `range_filters()` ANSWER TWO DIFFERENT QUESTIONS, and
which is which is the whole design here. `range_filters` is "what does this
gate FILTER on" -- an unbounded axis filters on nothing and is rightly
absent from it. `thresholds` is "what can the user SET", and an axis they
cannot see in the panel is an axis they cannot bound, which is exactly point
4. So an unbounded cylinder still offers its normal, at (None, None).

NOT NAMED `bounds`. `PolygonGate.bounds()` already exists and returns that
shape's bounding box as a 4-tuple; overriding it would have changed what a
caller of the old one got back. `thresholds` is also the word the request
uses.

A CYLINDER OFFERS ITS NORMAL AND NOT ITS OVAL, which is right twice over:
the oval is not a conjunction of ranges (a bounding box for it would quietly
include the corners, the same reason a polygon offers nothing), and the
normal is precisely the axis the request names -- "for an extruded shape
that includes the normal axis, which is how the user bounds the cylinder's
height".

BLANK MEANS UNBOUNDED, NOT ZERO, and the tooltip says so. A cylinder with no
bound on its normal is the 2D oval extended through the volume; one bounded
0..0 selects nothing. Those are opposite answers and the field must not
confuse them.

THE ROWS REMEMBER WHICH GATE THEY BELONG TO rather than re-reading the
selection when an edit lands. If the selection moved between a field being
filled in and `editingFinished` firing, re-reading would put the number on a
different gate -- silently, and on the gate the user was looking at LAST.

A gate that cannot take a threshold on a column REFUSES rather than ignoring
it, naming what it can take instead: a gate that silently swallowed the edit
would leave the panel showing a number the gate does not honour.

2026-08-13 (last) - DONE. THE POLYGON GESTURE AND voxel_bins CLOSE IT.
--------------------------------------------------------------------------------

THE POLYGON ON THE ANCHOR PLANE. `event.xdata` in the volume is a PROJECTED
SCREEN COORDINATE and means nothing in data units -- the 2D click path would
have placed vertices at numbers that look plausible and are not measurements.
The 3D path reads clicks through `screen_to_volume`, the same reader the drag
tools use, and closes into a `PrismGate` on the plane the clicks were made on.

TURNING THE VIEW MID-POLYGON ABANDONS IT. Vertices clicked on two different
planes are not one shape, and quietly mixing them would produce a prism whose
outline nobody drew. The plane is remembered with the pending vertices, and a
click on a different one starts over.

Unbounded along the normal, like every other shape drawn here: they said
nothing about depth.

voxel_bins IS READ. Above `VOXEL_THRESHOLD` points the volume draws OCCUPANCY
VOXELS instead of dots -- a marker where objects are, sized by how many.

  * Occupancy rather than a surface: a surface implies a boundary the data has
    not got, while sized markers say "this many here", which is the same claim
    the 2D density plot makes.
  * AREA tracks the count, not radius. A marker whose radius was the count
    would exaggerate a busy voxel by its square.
  * Only occupied voxels are drawn: an 8^3 grid over a real cloud is mostly
    empty, and drawing the empties is drawing nothing.
  * Below the threshold the dots ARE the better picture, because an individual
    object can be seen and clicked. The threshold is not taste: past it every
    dot is drawn over by the ones in front of it, so the picture stops
    improving and only the frame rate changes.
