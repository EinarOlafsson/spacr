3D GATES DRAWN ON A CHOSEN PLANE, COMPOSED WITH EACH OTHER, WITH THRESHOLDS
================================================================================

Status:    not started
Requested: 2026-08-08 — "for the gate editor . in 3d mode when setting the gate , the mechanism should be that the user clicks one plane then that plane gets a blue hue aura to it and this is the side that the gate is anchored to. in 3D mode the user should be able to pull a circle (wuich becomes a cylinder gate), a square/ rectangle, or draw a pollygon on this chosen 2d plane, which gets translated to 3 dims when the gate is generated. if the user draws another gate on the same 3d graph they should be able to set the new gate as being its own gate, subtracting or add from/to the other gates in view and that are chosen in the gates panel. the user should also be able to set thresholds for each individual gate for the measurements they are defined by."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not started. `spacr/qt/widgets/gate_editor.py` owns `GateCanvas`, which
extends `GraphCanvas` (`spacr/qt/widgets/graph_builder.py`) and pins the
axes while gating -- `RESCALE_ON_FILTER = False`, because rescaling to the
rows a gate kept moves the view out from under the gate being dragged.

Gating today is 2D: a shape drawn in data coordinates on the one pair of
axes on screen. There is no plane selection, no extrusion to a third
dimension, and no composition between gates.

Instruction 31 (gate editor redesign) is the neighbouring open task; read
it before starting, as the two touch the same panel.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A 3D scatter the user cannot gate is a picture rather than a tool. Every
population question in a screen -- "the bright, small, round ones" -- is
three measurements at once, and answering it today means gating twice on
two 2D plots and intersecting the results by hand, which is both slow and
unrecorded: the intersection exists only in whatever the user did next.

Composition and per-gate thresholds are what make the result reproducible.
A gate that is "this cylinder MINUS that box, with intensity above 400" is
a statement someone else can re-run; the same population arrived at by two
sequential 2D gates is not.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. PLANE SELECTION. In 3D mode, clicking one of the three planes (XY, XZ,
   YZ) selects it as the anchor and gives it a blue hue aura. The aura is
   the affordance: it says which surface the next shape lands on, before
   the user commits to drawing. Selection must be visible from any camera
   angle, so it is a translucent filled quad on the plane rather than an
   edge highlight.

2. DRAW ON THE ANCHOR PLANE. Three tools, all drawn in the anchor plane's
   2D data coordinates:
       circle    -> extrudes to a CYLINDER along the plane's normal
       rectangle -> extrudes to a BOX
       polygon   -> extrudes to a PRISM
   Extrusion happens when the gate is generated, not while drawing, so the
   drawing interaction stays 2D and reuses the existing gate geometry.

3. EXTENT ALONG THE NORMAL. A shape on a plane is infinite along the third
   axis until told otherwise; that is what point 4's thresholds are for.
   The default has to be a decision rather than an accident -- suggest
   full extent of the data along the normal, so a drawn gate initially
   means exactly what the 2D gate on that plane would have meant, and
   narrowing it is an explicit act.

4. PER-GATE THRESHOLDS. Each gate carries a threshold per measurement it
   is defined by, editable in the gates panel. For an extruded shape that
   includes the normal axis, which is how the user bounds the cylinder's
   height.

5. COMPOSITION. A new gate on the same graph is either its own gate, or
   ADDS to / SUBTRACTS from the gates currently in view and selected in
   the gates panel. Model this as an ordered list of (gate, operator)
   rather than a tree: the user's words are "subtracting or add from/to
   the other gates in view and that are chosen in the gates panel", which
   is a running composition over a selection, and an ordered list is what
   can be shown back to them as a sentence.

6. PERSISTENCE. A composed 3D gate has to round-trip through whatever the
   gate panel saves, or the reproducibility argument above is lost. Check
   what `gate_editor` writes today before designing the record.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

On a 3D scatter: click a plane, it takes a blue aura; draw a circle on it;
the gate selects a cylinder of points, verified by comparing the selected
row count against the same predicate evaluated in pandas. Draw a second
shape, set it to subtract, and the count drops by exactly the number of
rows in the intersection. Reopen the saved gate and get the same rows.

DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Nothing yet -- not started. Two questions to settle BEFORE writing code,
because both change the data model rather than the drawing:

  * Arbitrary planes, or only the three axis-aligned ones? The request
    says "one plane", and axis-aligned is what a click can unambiguously
    select. Arbitrary planes need a normal in the record and make the
    thresholds in point 4 stop being per-measurement.
  * Does composition apply across gates on DIFFERENT plane anchors? The
    geometry allows it and the sentence does not exclude it.

2026-08-11 - THREE SETTINGS FOR THIS FEATURE ALREADY EXIST, AND ARE INERT
--------------------------------------------------------------------------------

Found while sweeping every settings dataclass for fields nothing reads. Of
`GateEditorSettings`'s 35 fields, seven had ZERO readers outside
`gate_settings.py`. Four were clustering and are fixed (see instruction 48).
The other three belong to THIS instruction:

    voxel_bins: int = 64      "Voxels per axis in the 3D workspace."
    snap_to_axis: bool = True  snap the camera when a spin ends, so a 3D
                               gate is finally read from a square-on view
    spin_speed: float = 1.0

All three are declared, given a widget, saved and reloaded -- and read by
nothing. `GateEditorPanel.apply_settings` says why in its own docstring:
"the 3D ones belong to a workspace that does not exist yet".

NOT DELETED, deliberately, and this is the one place that reasoning differs
from the standing "remove settings nothing uses" rule. These are not
leftovers from something removed; they are the settings THIS instruction
needs, written in advance. Deleting them would mean writing them again, and
`snap_to_axis` in particular encodes a real decision about how a 3D gate is
finally read -- square-on, so the shape drawn is the shape stored.

WHAT IS STILL WRONG TODAY: they are SHOWN. A control that turns nothing is a
promise the app does not keep, which is the same defect as the clustering
ones and is why they turned up in the same sweep. Until this instruction
lands, the 3D group should either be hidden or carry a visible "not yet
connected" note -- and when it lands, these three are the first things to
wire, because the settings are already there.

The count to hold this to: `GateEditorSettings` should end this instruction
with ZERO fields that nothing reads.

--------------------------------------------------------------------------------

This file says, of its own four settings:

    "Until this instruction lands, the 3D group should either be hidden or
     carry a visible 'not yet'."

Carrying the "not yet", not hidden. Hiding them would silently lose a user's
3D setup the first time they opened the tab -- the values ARE saved,
reloaded and carried in the settings, and only the DRAWING is missing. So
`voxel_bins`, `snap_to_axis` and `spin_speed` keep their controls, gain a
line in their tooltip saying the value is saved but not yet in effect, and
the tab carries one sentence to the same effect.

That is the whole of the phantom-control defect: a control that turns
nothing is a promise the application does not keep, which is what instruction
77's sweep was about. It is now a control that says what it does.

THE INSTRUCTION ITSELF IS STILL OPEN. The volume, the plane-anchored gates
and the snap-on-release behaviour are not built. What changed is that the
