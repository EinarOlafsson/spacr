--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

spacr/regression_diagnostics.py already has design_report(),
collinear_guide_pairs(), variance_inflation_factors(), residual_report() and
write_diagnostic_suite(). A normal run calls some of it; a sweep row records
almost none of it.

A sweep row today carries the settings, a hit count, and seconds. That is not
enough to choose between two runs: it cannot say whether a fit with more hits
had a worse-behaved residual, a rank-deficient design, or simply threw data
away.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The point of a sweep is to CHOOSE a configuration. A row that reports "10
hits" and nothing else forces the user to open every trial folder by hand,
which is the work the sweep was supposed to remove. The nightly run showed
exactly this: min_cell_count=50 reported MORE hits than 100 while quietly
losing GRA14, and no column in the table said so.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

Every row gets, where the fit can supply it:

  FIT QUALITY        r_squared, adjusted r_squared, aic, bic, log-likelihood,
                     residual standard error, condition number
  RESIDUALS          Breusch-Pagan and White for homoscedasticity,
                     Durbin-Watson, Jarque-Bera and Shapiro for normality,
                     the residual/fitted trend slope
  DESIGN             rank, whether it is identifiable, max VIF, the number of
                     collinear guide pairs, n_wells / n_guides / n_rows
  CONTROLS           the positive control's rank, p and q; the negative
                     control's; and the separation between them. If the user
                     has named a positive control, IT is the yardstick a
                     configuration should be read against.
  CALIBRATION        genomic inflation at the median, the p-value histogram's
                     first-bin excess
  GUIDE SUPPORT      how many hits rest on a single guide

Every one of these gets a saved figure, in the trial folder AND in a normal
run's output folder. The user asked for both, and a diagnostic that only
exists during a search is one nobody looks at.

--------------------------------------------------------------------------------
HOW TO KNOW IT IS DONE
--------------------------------------------------------------------------------

Sorting the sweep table by the positive control's rank puts the best
configuration first, and every figure named above exists on disk after an
ordinary run with no sweep involved.

WHAT SHIPPED

  THREE ENTRY POINTS, THREE DIFFERENT TABLES. This is what "a sweep row
  carries settings, a hit count and seconds" actually was:

    run_sweep(contained=True)   the full set already, via sweep_child
    run_sweep(runner=...)       hit counts only -- not even the design summary

                                AND THIS IS THE ONE THE GUI CALLS
                                (qt/screens/parameter_sweep.py -> start())

  So the same sweep produced different columns depending on how it was
  launched, and the launch path a user actually takes produced the fewest.
  All three now go through summarise_trial.

  spacr/trial_metrics.py  design_diagnostics(), the missing DESIGN block:
  design_rank, n_parameters, non_identifiable_directions,
  residual_degrees_of_freedom, design_identifiable, wells_per_parameter,
  max_vif, n_vif_above_10, n_collinear_pairs, max_abs_predictor_correlation.

  Nothing is recomputed that the fit already knows. statsmodels computes the
  rank at fit time and keeps it on model.model.rank; regression_diagnostics'
  design_report answers the same questions but wants the well-by-guide matrix
  and pays for a fresh matrix_rank plus a full SVD, which a sweep row does not
  need to buy twice. Field names match design_report's so the two read the
  same in a trial folder.

  IDENTIFIABILITY IS THE ONE THAT MATTERS. A fraction design is rank deficient
  the moment the guide fractions sum to 1 in every well, which is collinear
  with the intercept; statsmodels answers with a pseudo-inverse rather than
  refusing, so the coefficients come back looking like any other fit while
  being one of infinitely many solutions. Nothing else in the output said so.

  VIF WITHOUT ONE EXTRA REGRESSION. regression_diagnostics'
  variance_inflation_factors regresses each guide on every other -- measured
  0.53 s for twenty-five of four hundred guides -- and truncates at
  max_guides, so on a wide design the largest VIF is usually not among the
  ones it looked at. For a fit with an intercept the standard errors already
  imply it exactly: VIF_j = se_j^2 / sigma^2 * (n-1) * var(x_j). Matched
  against that reference to 2e-15 relative error over ALL columns, in 9 ms at
  1,213 parameters, and covering every column rather than the top 200.
  Omitted, not reported, when the design is rank deficient -- VIF is not
  defined there and the identity would produce a meaningless number.

  THE POSITIVE CONTROL, READ FROM spaCR'S OWN ANNOTATION. spacr.ml.regression
  already writes 'pc'/'nc' into the coefficient table's `condition` column.
  control_recovery reads that first and falls back to the substring match for
  tables that carry none (a permutation run writes none), so a row and its
  volcano cannot disagree about which coefficient the control is.

  AND A PERCENTILE BESIDE THE RANK. Verified on the real screen table
  (results/plate1_dv/ols/list/results.csv): 1,213 coefficients, and it MIXES
  823 guide-level rows with 389 gene-level rows. The positive control lands at
  rank 3 of 1,212 there. A sweep varies exactly the settings that change how
  many coefficients exist, so rank 3 of 400 and rank 3 of 1,213 are not the
  same recovery, and a table sorted on the raw rank quietly favours whichever
  trial fitted fewest things. rank_trials() therefore sorts on the percentile.

  An absent control gets *_control_found = False and NO rank. Checked against
  the real screen: the default negative control 233460 does not occur in it at
  all, so this is the normal case, not the edge case.

  spacr/parameter_sweep.py  rank_trials() orders the table best-first and
  sorts the trials that LOST the control to the bottom rather than dropping
  them -- min_cell_count=50 reporting more hits than 100 while losing GRA14 is
  the finding, not a row to hide. summarise_sweep() now names the best trial,
  its rank, and how many trials recovered the control at all.

  A MEASUREMENT IS NO LONGER FED BACK AS A SETTING. Found while wiring this,
  and it was already live. settings_for_trial()'s rule is "anything not in
  _BOOKKEEPING_COLUMNS was a setting the user chose" -- which is what lets a
  custom sweep axis round-trip -- but that set had never been updated for the
  metrics. Reopening a contained trial therefore handed r_squared, aic,
  durbin_watson, genomic_inflation, breusch_pagan_p, positive_control_found
  and n_rows_fitted to perform_regression as though they had been typed in.
  _BOOKKEEPING_COLUMNS is now sourced from trial_metrics.METRIC_COLUMNS so the
  two cannot drift, and a test fails on drift instead of leaking.

2026-08-18 (night) -- RESULT: EVERY PANEL NOW CARRIES ITS OWN VERDICT
--------------------------------------------------------------------------------

The two RESULT sections above shipped the panels (normal runs) and the scalars
(sweep rows). Both left the SAME step to the reader: deciding, per panel,
whether the number is fine. That is the "and scored" in this instruction's own
title, and it was the half that had not been done. A quantile correlation of
0.982 printed beside a Q-Q tells a statistician something and tells everybody
else nothing; twenty-three of those is twenty-three judgements a user is
quietly expected to make, which is how a run with a rank-deficient design gets
reported as "the QC looked fine".

WHAT SHIPPED, commit cf7bcd39, all in `spacr/regression_qc.py`:

  score_panel(name, stats) -> PanelVerdict(level, headline, detail, score,
                              statistic)
  draw_verdict(ax, verdict)         the badge, bottom-left, in a box
  worst_verdict(verdicts)           the suite's own verdict
  VERDICT_LEVELS / VERDICT_WORDS    unknown < pass < check < fail

  * ONE SCORER PER PANEL, all 23, and a test asserts `_SCORERS` and
    `PANEL_ORDER` have the same keys -- a panel added without a scorer would
    silently go back to being a picture with a number on it.
  * SCORED AFTER IT DREW, STAMPED BEFORE IT IS WRITTEN. The verdict is read
    off the statistics the panel just returned, so it cannot disagree with the
    numbers printed beside it, and the axes is still open, which is what lets
    the judgement go ON the panel. The combined page redraws the panel and
    stamps THE SAME verdict rather than re-scoring -- a second opinion there
    would let the page and the file disagree about one panel.
  * QCPanelResult carries it; the manifest gains `verdicts`,
    `verdict_counts`, `verdict` and `verdict_level`; the text report prints
    the verdict FIRST, then the statistic it was read off, then a "means:"
    sentence. The run's stdout names every CHECK and FAIL by panel.
  * THE SUITE'S VERDICT IS ITS WORST PANEL. Nineteen passes and one aliased
    predictor is a run whose coefficients are one of infinitely many
    solutions; "95% passed" is the summary that loses exactly that.
  * A SKIPPED PANEL HAS NO VERDICT. "The panel is not there" and "the panel
    is fine" must not look the same, which is the rule this module already
    followed for status.

THE THRESHOLDS ARE THE CONVENTIONAL ONES and are cited in each `detail`
string: VIF 5/10, Belsley's scaled condition number 30/100, Cook's D 0.5/1,
p >= 0.05 for a diagnostic test, hat 0.2/0.5, |r| 0.7/0.9, ECE 0.05/0.10, AUC
0.7/0.6. A threshold invented here would be a number a reviewer cannot check.

THE DIRECTION IS THE COMMONEST WAY TO READ ONE WRONG: a LARGE p is the GOOD
outcome for every test these panels run, because the null is "the assumption
holds". `_diagnostic_p` is the only place that is written down and each
sentence says which way it read.

TWO CALIBRATIONS FOUND BY DRIVING IT ON REAL FITS, NOT BY READING THE CODE.

  * A SPIKE AT ZERO IN THE p-VALUE HISTOGRAM IS A PASS. It is what real hits
    look like, and scoring it as a fault would flag every successful screen.
    `uniform` and `uniform-with-spike` pass; `excess-large` checks;
    `anti-uniform` and `u-shaped` fail.
  * DFFITS IS SCORED ON THE FRACTION ABOVE THE LINE, NOT THE MAXIMUM.
    2*sqrt(p/n) is a SCREENING threshold that a correctly specified model is
    EXPECTED to cross for a few percent of its observations. Measured on a
    clean 400-well Gaussian fit with nothing wrong with it, the largest
    |DFFITS| was over twice the threshold -- so the obvious rule flagged a
    clean fit, which is a warning nobody reads. `_panel_dffits` now also
    returns `n_points` so the fraction is computable.

fail, 2 not scored). The same design made collinear and heteroscedastic fails
five panels BY NAME -- residual_distribution, scale_location, vif,
condition_number, predictor_correlation -- and the suite verdict is FAIL. The
badge is on the pixels: the FAIL ink is present in the bottom band of a
failing panel's PNG and absent from a passing one's.

`qc_design`, `qc_inference` and `qc_verdict` are columns on every trial row.

WHY A ROW NEEDS THEM. A sweep is a table ranked by hit count, and hit count is
exactly the number a broken fit inflates -- a rank-deficient design will
happily report more significant guides than an identifiable one. Without a
verdict beside it, the trial that WINS a sweep is sometimes the trial that is
most wrong, and nothing on the row said so.

SCORED FROM THE ROW'S OWN STATISTICS, at no extra cost. `score_design` and
`score_inference` read plain dicts -- `wells`, `wells_per_parameter`,
`design_rank`, `condition_number`, `genomic_inflation`, `tests` -- and
`summarise_trial` has already measured every one of those under spaCR's own
column names. Only the names are translated, so the scorers stay the one
judgement; re-deriving the verdicts with fresh rules would be a second
opinion about the same numbers, which is what a sweep table can least afford.

THE WORST, NOT A PASS RATE, for the reason `worst_verdict` already gives.
And the OBJECTS are passed to it, not their levels: it asks each verdict
`worse_than`, which a string cannot answer -- the string version lives in
`qt/widgets/qc_summary.py` and importing it here would drag PySide6 into a
deliberately headless module.

ON `METRIC_COLUMNS` OR THEY BECOME SETTINGS. `settings_for_trial`'s rule is
"anything not bookkeeping was a setting", so a column missing from that list
is fed back into `perform_regression` as though the user had typed
`qc_verdict='fail'`. A test asserts nothing is emitted that is not declared.

RESIDUALS ARE NOT SCORED HERE, deliberately and said out loud: `score_residuals`
reads a residual report the row does not carry, and computing one per trial
would put the 5.8-second suite back into a sweep that exists to be fast.
