--------------------------------------------------------------------------------
THE MEASUREMENT
--------------------------------------------------------------------------------

Taken 2026-08-18 on a well-conditioned gene-level design, `regression_model`
called directly so nothing else is in the timing:

    40 genes x 400 wells     ols 0.03 s     mixed  1.62 s     54x
    80 genes x 600 wells     ols 0.16 s     mixed 10.66 s     67x

THE RATIO GROWS WITH THE SCREEN. Doubling the genes cost OLS 5x and mixed
6.6x, and that is the GENE-LEVEL design alone -- 40 to 80 columns. The mixed
fit the module actually runs adds a random effect PER GUIDE nested in gene, so
on the maintainer's screen (823 guides, 389 genes, 610 wells) the expected
range is tens of minutes to hours.

Nothing is wrong. statsmodels' MixedLM is an iterative REML optimisation and
it is SINGLE-THREADED, so 100% of one core is exactly what a healthy fit looks
like -- and it will not use the other cores however long it runs.

--------------------------------------------------------------------------------
A. THE MODEL BOX SAYS WHAT IT COSTS
--------------------------------------------------------------------------------

132's box states the formula and what is modelled. It does not say that the
default is roughly sixty times the cost of the alternative and rising with
screen size. A user who picks the default -- which is everybody, that is what
a default is -- has no way to know that before they wait.

Put it in the box, beside "what you do not get": the order of magnitude, that
it is single-threaded, and what to choose instead when the answer is wanted
now (`ols` with `level='both'` is the pre-2026-08-17 behaviour; `rra` needs no
joint fit at all).

Say it as a MEASURED RANGE, not "this may be slow" -- the numbers above are
what make it actionable.

--------------------------------------------------------------------------------
B. A LONG FIT REPORTS WHERE IT HAS GOT TO
--------------------------------------------------------------------------------

An hour of silence at 100% CPU is indistinguishable from a hang. That is not a
guess about how it feels; it is the question that was asked, twice, while the
fit was running correctly.

The run should say, before it starts, what it is about to do and roughly how
long that is for a design of this size -- and then report progress while it
does it. statsmodels exposes the optimiser's iterations; at minimum the run
can print that it has entered the mixed fit, the number of parameters and
random effects, and a heartbeat.

WHAT NOT TO DO: a spinner with no content. The useful line names the design --
"fitting 389 genes and 823 guide random effects over 610 wells" -- because
that is also the line that tells a user their filters did something
unexpected.

--------------------------------------------------------------------------------
C. AND IT MUST BE INTERRUPTIBLE
--------------------------------------------------------------------------------

A fit that will run for an hour has to be stoppable from the GUI without
killing the application, and a stopped fit must leave the run folder in a
state the user can see. spaCR has `spacr.cancellation` for exactly this; the
mixed branch should honour it.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* The model box states the measured cost of `mixed` and names the faster
  choices.
* Starting a mixed fit prints the design it is fitting before it blocks.
* A fit longer than a few seconds reports progress.
* Cancelling one stops it and says what was written.

--------------------------------------------------------------------------------
2026-08-18 -- A, B AND THE GUI HALF OF C SHIPPED. Commit 62b61338.
--------------------------------------------------------------------------------

A. THE BOX STATES THE COST. `mixed`'s box gains a WHAT IT COSTS section beside
WHAT YOU DO NOT GET, and for the same reason: both are things a user could
otherwise only find out by having already spent the afternoon.

ONE COPY OF THE NUMBERS, and this is the part worth not undoing.
`settings_model.MIXED_COST_ANCHORS` holds the measurement as data --
(40, 400, 0.03, 1.62) and (80, 600, 0.16, 10.66) -- and `mixed_cost_note()`
builds the paragraph FROM it, including the 54x and the 67x. The box reads that
function and so does the console. A measurement written out twice is two
numbers, and the second one to be edited is the one nobody believes afterwards.

B. THE RUN SAYS WHAT IT IS DOING BEFORE IT BLOCKS. Three lines, each a different
question: WHAT IS RUNNING (model, level, backend, read off the settings the run
was started with, so a re-fit describes the re-fit); WHAT IT COSTS (the note
above, for `mixed` only); HOW BIG THE DESIGN IS.

THE DESIGN SCAN GOES THROUGH `JobRunner`, not the GUI thread. Reading a
500,000-row count CSV to warn somebody about a slow fit would be its own freeze.
`regression_design_scan(settings)` never raises -- it runs beside a fit that is
already starting, and a scan that threw would take the run's own message with
it. What it could not work out comes back as None with a reason.

AND IT SAYS WHICH NUMBER IT IS. This is the design as THE COUNT FILES HOLD IT:
before the merge with the scores, before `fraction_threshold`, before the well
filters. That is deliberate and it is the useful reading -- it is the number to
compare the run's own post-cleaning counts against, and two numbers that differ
is a filter having done something. Two numbers that both claim to be "the
design" and disagree is a bug report, which is why the sentence names itself.

The gRNA split is the pipeline's own POSITIONAL rule (`process_reads`:
`<org>_<gene>_<guide>`, every name the same width). Names of another shape get
a guide count and NO gene count, with the reason -- a gene total from a rule the
fit will not apply is a number that disagrees with the fit.

THE HEARTBEAT is sparse and widening: 30 s, then 1, 2, 5, 10, 20, 30, 45, 60
minutes, then every half hour. A line every thirty seconds is 120 lines in the
hour this exists for, which is the same silence with more scrolling. The line
interprets the observation the user could not -- "cpu at 100 percent" -- by
saying that one core at 100% with the others idle is what a healthy
single-threaded REML fit looks like, and that Stop is live.
`_due_heartbeat(elapsed)` is separate from the timer so the last entry can be
driven directly; an entry nobody checks is the one that is wrong.

C. STILL OPEN, AND IT IS ml.py's HALF -- ANOTHER TERRITORY TODAY.
`grep -n "cancellation\|raise_if_cancelled\|is_cancelled" spacr/ml.py` returns
NOTHING. There is no cancellation check anywhere in the module, so
`worker.request_cancel` cannot land inside a mixed fit however long it runs.
What makes it interruptible today is `_force_stop`, which PARKS the thread
(`bridge.drain_thread`) and gives the window back while the fit finishes in the
background -- and says so rather than claiming it stopped. The fix is a
`spacr.cancellation` check between REML iterations, plus writing the run folder
in a state the user can see when it is abandoned. It is in `handoffs`.

WHAT THIS COST ELSEWHERE, so it is not rediscovered as a mystery:
`tests/test_the_model_box_is_short_enough_to_finish.py` held the longest box at
under 1,400 characters and the cost section takes `mixed` to 1,795. The ceiling
is 1,900 now with the reason written into the constant, plus a second ceiling on
`mixed` alone so the section that bought the raise cannot quietly grow past it.

--------------------------------------------------------------------------------
2026-08-20 -- C IS DONE. 140 IS COMPLETE.
--------------------------------------------------------------------------------

`spacr.ml` now has a cancellation check, and the mixed fit answers Stop.

THE HOOK IS `loglike`, NOT `fit(callback=)`, and that is the whole finding.
statsmodels accepts a callback and calls it once per optimizer ATTEMPT rather
than per iteration -- measured at TWO calls for an entire fit, on a
2-predictor design and on a 30-predictor one. Two chances to notice Stop in an
hour is the same silence this instruction exists about. `loglike` is evaluated
by the optimiser on every step, which is the granularity a user pressing a
button expects. The test counts the two against each other on the SAME model
rather than against a number somebody picked.

ON THE INSTANCE, NEVER ON THE CLASS. Patching statsmodels would put a spaCR
checkpoint inside every model any library in the process fits.

`PipelineCancelled` PROPAGATES OUT OF SCIPY UNCHANGED -- checked, not assumed,
because an optimiser that swallowed it would leave the fit running with the
user told it had stopped, which is worse than not offering to stop at all.

AND THE FOLDER SAYS WHICH IT WAS. `open_run` recorded every BaseException as
"failed", so a run the user deliberately stopped was indistinguishable in the
manifest, the Runs tab and `recent_runs` from a screen that broke the model --
and those are different things to do next. It records "cancelled" now, keeping
the traceback, because where a long fit was interrupted is exactly what a user
asks afterwards.

`_force_stop` stays. It is the answer for a fit that is somewhere this check
cannot reach, and it has always said it parks rather than claiming to stop.

8 tests in tests/test_a_long_fit_can_be_stopped.py.
