# spaCR agent rules (Codex, Claude and others)

Read `spacr/resources/AI/HANDOFF.md`, section "CURRENT HANDOFF FOR CODEX AND OTHER AGENTS", first.

1. Origin has only `main` and `nightly`. Work from `nightly`; push only with `git push origin HEAD:nightly`.
2. Create new branch worktrees under `/mnt/wd4tb/spacr-worktrees/`; scratch in `/mnt/wd4tb/scratch/`. Preserve existing transferred worktrees while their assigned work finishes.
3. Never `git stash`. Never reset, check out or clean a shared checkout. Update the shared checkout only with `git merge --ff-only origin/nightly`; never create commits or merge commits there, and never push its local preservation commits.
4. Commits carry no `Co-Authored-By` or AI trailer; the hook refuses them.
5. Items from `features/future/` ship alpha: register in `ALPHA_FEATURES` with a literal `setObjectName`.
6. Alpha organisms (all but Toxoplasma) sit behind "Show alpha species" (`ALPHA_SPECIES`).
7. Tutorials show only the current layout and no alpha content except lessons 86/87; record with `--fresh`. Lane owner: spacr-d7.
8. User strings through `tr()`. No `#` comments in `spacr/`. No new modules under `spacr/`.
9. Tables via `spacr.tabular`; figures via `spacr.plot.save_figure`, styled by `spacr.figures.style._apply_user_style`.
10. Regenerate generated artefacts with their tools; never hand-merge them or raise a ratchet ceiling.
11. Tests: `CUDA_VISIBLE_DEVICES='' QT_QPA_PLATFORM=offscreen tools/run_capped.sh 8G python -m pytest`, `-n 4` at most, never the whole suite.
12. Keep RAM under 110 GB (`tools/run_capped.sh`). GPU only via `tools/gpu_turn.sh`. Chrome and its graphics processes must NEVER count as compute jobs or block any GPU queue, even when `nvidia-smi` lists them. Verify this exclusion in the actual scheduler used by every new run, including older worktrees.
13. Never touch livecell or cellposeTIME jobs; they belong to another session.
14. `einarolafsson/models` on Hugging Face is a DATASET repo.
15. Item state is in each item file's dated trailing notes and `features/00_INDEX.txt` (generated).
16. Stay responsive: never run anything that can take over ~1 minute in the foreground (pytest, sphinx, builds, renders, training, sleep/until/wait loops). Use Bash `run_in_background: true` (you are notified when it ends) or hand it to a subagent; the main session must always be free to answer. A local hook blocks foreground pytest/sphinx/long sleeps; mark a known-short command with `# fg-ok`.
17. Tutorials ship one lesson at a time, end to end, before the next starts: record it on the GNOME capture host (real app, real pointer, every clip through the smoothness gate; re-record failures once), synthesize audio only for changed sentences, translate only changed sentences into every lesson language, stage and render, publish (HF, Pages, verify `--published`, record), then commit and push to nightly. Never encode or upload while a recording runs; recordings run alone on an idle machine.

## Delivery and persistent goals

18. Keep the entire maintainer goal active until its actual completion criteria are met. Finishing one subtask, receiving a worker result, reporting progress or reaching a context boundary is not permission to stop. Continue with the next authorized action without asking the maintainer to say "continue".
19. Finish one numbered item end to end: implementation, necessary related tests, normal artefact generation, commit and one push. Delegate disjoint subtasks of that item when agents are available; integrate their results before moving on. Do not invent work merely to occupy agents. Respect explicit ownership and priority order.
20. Ship product rather than paperwork. No evidence packets, receipts, inventories, hash-proof commits or new `features/data` files unless an existing test/tool requires that exact file or the maintainer explicitly requests it. Item notes are at most five dated lines describing the change/commit and what remains.
21. Run the smallest relevant test cohort once. After a fix, rerun affected failures; retain passing results unless source, dependencies or a concrete new finding invalidates them. Do not repeat full inventories, audits, builds or generators for reassurance. Use the normal generators once against the final integrated source, then rely on CI for broader coverage. Never weaken assertions or raise ratchets to get green.
22. Waiting must follow a verified live session, process or CI handle. Check its authoritative state with bounded background polling; keep the main session responsive. A timeout, quiet log or unchanged counter is not proof of failure. Do not restart working jobs or dispatch duplicate CI. When a job finishes, consume its result and immediately take the next authorized action.
23. For unattended goals, enable the host's supported persistent-goal mechanism. Where a session-state/control interface is available, start or reuse one background supervisor per goal to check actual goal/session state periodically, identify idle unfinished sessions and resume authorized work through that interface. Monitor delegated workers as well as the root; stop obsolete monitors after completion or an explicit pause. Never use heartbeat files, repeated chat messages or a monitor's own activity as proof of product progress.
24. A supervisor must respect explicit stops, pauses, approval requests, usage limits and safety controls; never auto-dismiss or bypass them. If no supported session-control interface is available, disclose that limitation promptly instead of claiming guaranteed continuation or creating a fake keepalive. Repository instructions alone cannot restart a terminated host session.
25. Do not voluntarily end autonomous work while an authorized actionable step remains. Completion requires the requested product state, not just green narrow tests. If an item genuinely needs credentials, payment, unavailable hardware or human/scientific approval, write the exact maintainer steps once, mark that item `BLOCKED ON MAINTAINER`, and continue other authorized work. Stop only for goal completion, an explicit maintainer stop/pause, an unavoidable host interruption, or a genuine blocker after all other authorized work is exhausted; report the actual reason without claiming completion.
26. Report only verified worker activity and published results. Do not claim all agents are working, another machine received a message, or overnight work continued without checking its actual session/job state. Never count bookkeeping or partial scopes as finished items.
27. Only completion of a whole numbered item from `features/new/` or `features/future/` automatically triggers a progress/completed-items table in chat. Whenever any agent finishes such an item, immediately print the full table before moving to the next item. This includes items completed by delegated agents: the coordinating agent must report their verified completion in the user-facing chat. Keep one row per unfinished numbered item in the current maintainer goal and put recently completed green-ticked items first; omit other 100% items from the displayed table while retaining their history in the underlying Progress List. Use these columns in this order: **Item | Percent done | Time left | Owner | Description**. Mark recently completed whole items with a green tick (`✅`) and `100%` in the Percent done column; "recently" means completed since the previous table. Reserve `100%` for items whose required implementation, validation, generation, publication and acceptance steps are all complete. Label other percentages as estimates. Give remaining time in hours, using `0 h` for completed items; distinguish estimated work from external waiting, and write `Unknown` with the blocker when a defensible estimate is unavailable. Owner names the responsible agent/team or maintainer for the next step, without implying an idle agent is actively working. Description explains what the feature does, what has been delivered and the remaining work or blocker in one to three concrete sentences. Subtasks, worker turns, individual tests or CI jobs, documentation edits and progress updates do not trigger a table unless they finish the whole numbered item.
28. An agent or pair assigned to an item owns it end to end: implementation, necessary validation, normal generated outputs, publication and required acceptance. Continue with the next authorized step until the whole item is complete; a scoped review, subtask result, worker-turn ending or blocker report is not item completion. Minimize context-gathering cost: scope once where possible, retain findings, decisions, ownership and passing results, and give the same agents successive related tasks using follow-ups containing only the new information and next action. Reuse existing agents across as many useful authorized tasks as possible before spawning replacements or retiring them. Re-scope only the affected portion when requirements, source or evidence materially change; do not repeat broad inventories, known-blocker checks or already-valid analysis to occupy workers. Before spawning, confirm concrete ready work exists and no suitable existing agent can take it. If a genuine external prerequisite blocks an item, report the exact blocker once, retain the pair's ownership and context, and reuse those agents for other ready authorized work where possible; resume the original item with the same pair when unblocked. Do not keep agents busy with polling or invented work merely to appear active. Retire an agent only when its assigned work is complete and no useful authorized follow-up remains, or an explicit stop, ownership transfer or unavoidable host limit requires it; report unfinished ownership accurately.

29. When the maintainer requests work related to an existing item in any feature list, update that item first with the new requirements, acceptance criteria, priority and ownership changes, then implement them. Preserve relevant existing requirements and dated history; new maintainer instructions supersede conflicting older notes. Record blockers without treating them as completion. Use the normal generator for affected indexes, and keep dated trailing updates to at most five lines.
30. Reuse agent context as much as possible: send a running or finished agent the next related task as a follow-up instead of spawning a new one, keep its scope and findings, and re-scope (re-read, re-inventory, re-analyse) only what genuinely changed. Spawn a fresh agent only when no existing agent's context fits the work.

31. Keep all retained agents active on concrete, ready, authorized work. Reserve one agent lane at all times for small, easy tasks that can be delivered end to end; assign the other agents longer, harder items. Maintain a short queue of ready small tasks and give the same agent its next useful task immediately after delivery or an external blocker. Reuse existing context and passing results, keep ownership through publication and acceptance, and report actual activity accurately.

32. Use persistent task coordinators and reuse their workers: one or two coordinators for easy items (under 30 minutes to implement and finish), each with up to five workers assigned one ready item each; one to three coordinators for difficult features (over 30 minutes), each with up to five workers; and one or two coordinators for the approved repository cleanup, with one worker per ready cleanup task. Coordinators retain scope, decisions, passing results and ownership through integration and publication. Separate independent work so these teams can progress concurrently; do not spawn workers for completed tasks, external waits or invented work. Respect the session's shared concurrency limit, queue excess work and report actual staffing.
33. Keep a separate maintainer-input coordinator with up to five reusable workers in total. It asks concise, item-specific questions only when an unanswered maintainer decision blocks work. After an answer enables concrete work, assign a worker to finish that item and advance to the next decision. Preserve prior approvals; never treat elapsed time as approval. Distinguish decisions from missing hardware, credentials or scientific inputs, and do not claim those prerequisites are supplied by an answer alone. Route asynchronous answers to the owning coordinator, update the item before implementation, and retain ownership through validation and publication.

34. Commit messages must describe the actual changes clearly and specifically. Do not prefix, append or otherwise add spaCR issue/feature-file numbers to commit subjects or descriptions. Keep item tracking in the feature files instead.

35. Questions and approval requests block only the specific actions that depend on their answers. Ask asynchronously, retain the pending question and its owner, and immediately continue independent authorized work with the other agents. Never pause the entire goal or team while ready work remains; reuse a waiting worker on a disjoint task where useful, preserving its original context. Do not treat silence as an answer or proceed with an action that still requires approval.

36. Maintainer authorization for the current Progress List goal (2026-10-21): use the maintainer's standing affirmative answer for routine outstanding decisions within that authorized goal. Hold newly arising questions until 2026-10-21 21:10 UTC (approximately 17:10 America/Detroit); continue independent ready work throughout. This does not supply missing facts, credentials, hardware or scientific acceptance, or override explicit stops, safety controls or later instructions.
