## Concrete causes of an older app remaining active

### macOS online package: new bundle does not upgrade an existing runtime

- packaging/online/build_macos_online.sh:55–74 embeds the requested release in the app's plist, and122–126 runs the version-pinned standalone shell installer only through the first-user helper.
- Its actual package postinstall at136–142 only creates /usr/local/bin and rewrites the symlink to /Applications/spaCR.app/Contents/MacOS/spaCR. It never verifies or upgrades any existing per-user runtime.
- packaging/online/macos_launcher.c:19–26 derives `~/Library/Application Support/spaCR/venv/bin/python` and asks only whether it is executable. If it exists, lines39–44 immediately run `python -m spacr.qt`. The launcher never compares the runtime's package/code version with the newly installed plist release.
- Consequently, installing a newer .pkg over an older installation can update the native launcher/plist while launching the old Python package. This is a direct source-level route to the user's reported behavior. The first-user helper is skipped precisely when the older runtime exists.
- tests/test_macos_online_update_n627.py:185–201 intentionally verifies that an older native launcher starts an already newer runtime rather than reinstalling its old embedded pin. Preserve that desirable no-downgrade behavior. The missing case is the inverse: **newer package, older existing runtime must upgrade before launch**, with final imported code identity verified.

### Linux frozen Debian and online launchers compete

- packaging/build_debian.sh:44–51 installs the frozen payload under /opt/spacr and an absolute /usr/bin/spacr wrapper that executes /opt/spacr/spacr. It uses the shared desktop entry packaging/linux/io.github.olafssonlab.spacr.desktop:5, whose `Exec=spacr` resolves through the desktop environment's PATH rather than naming the owned wrapper.
- An earlier ~/.local/bin/spacr, /usr/local/bin/spacr or activated environment can therefore win command resolution. Installing the .deb does not run any cross-layout cleanup or normalize alternative launchers: builder lines71–72 deliberately rely on dpkg ownership. This is a concrete source-level ambiguity, not a demonstrated native desktop resolution order on the user's machine.
- The online Unix installer writes a fixed-runtime launcher at install_spacr_unix.sh:562–570 and an absolute `Exec=$LAUNCHER` desktop entry at579–592, which avoids ordinary PATH competition for that newly written entry. It never changes shell profiles/PATH, clears shell command caches or discovers every other desktop/command entry. Its final launch uses that exact new launcher at624–625, whereas a later typed `spacr` or another desktop entry may select a different copy.
- `_find_unix_online` in spacr/install_cleanup.py:870–916 discovers known standard roots and launchers only in XDG_BIN_HOME, ~/.local/bin, and /usr/local/bin on macOS. It can infer a custom root from a recognized launcher and its uninstall script. It does not scan every PATH directory, /usr/local/bin on Linux, arbitrary --launcher-dir values, Desktop launchers or every XDG application directory. Records in an unknown root with an unknown launcher can remain undiscovered.
- `_find_environments` at991–1051 lists known Conda/venv/pipx/user-site environments and skips source checkouts. `remove_install` at1411–1416 leaves user environments unless explicitly ticked. The standalone installer does not supply ticks. An older package in a user environment is therefore intentionally left installed and may still be first on PATH. Removing the entire environment would violate the preservation requirement; N703 should distinguish an app package removal choice from deleting shared Python environments.

### Alternate macOS app locations and inherited import paths

- `_find_macos_apps` at801–817 checks standard /Applications names plus the exact currently running frozen bundle. It does not enumerate ~/Applications, Downloads, arbitrary renamed copies or every LaunchServices registration. All copies share the package's bundle identifier at build_macos_online.sh:63. Whether Finder selects a stale alternate copy is a native acceptance question; this audit does not claim an observed LaunchServices selection.
- The private-runtime macOS launcher and generated Unix launcher use `python -m spacr.qt` without -I or environment sanitization, while Unix installation validation uses -I at509–510. Inherited PYTHONPATH/user-site or an old source checkout as cwd can change Python's imported package despite a correct venv. This is an isolation gap to test; no live environment was inspected or changed. qt_ci also found generic helper relaunches inherit environment, and relaunch from the helper workdir.
- The old frozen DMG builder packaging/build_macos.sh:81–90 creates a drag-to-Applications image, not an installer with an upgrade/discovery step. It provides no cross-layout cleanup. Current frozen macOS in-app replacement is more careful: install_cleanup.py:2213–2274 verifies and atomically exchanges bundles, retains the complete previous tree in a private transaction and publishes a journal. Its relaunch at2508–2525 uses an exact target path. Preserved rollback trees are intentional safety records, not proof that a stale app was selected. N703 must not erase unverified/failed rollback state or unknown files merely to claim no old apps remain; distinguish active launches from retained recovery evidence and prune only after a verified policy/choice.

## macOS terminal questions are an explicit architectural behavior

macos_launcher.c:26–30 executes `/usr/bin/osascript` to activate Terminal and run `/Library/Application Support/spaCR/install-for-user.sh` whenever the runtime is missing. The helper at build_macos_online.sh:102–133 holds a mkdir lock, runs the Unix bootstrap and only then uses `open -a /Applications/spaCR.app`.

The Unix script's TTY branch at243–253 asks three optional privacy/account questions through `read` at232–237. The package helper passes neither `--consent-collected` nor answer flags, so a Terminal bootstrap can ask those questions after the native .pkg window has completed. sudo authorization can also be requested by the shell path at465–467; Linux system-dependency setup has its own elevation. This is not a stray Qt dialog: the current package intentionally separates native payload install and user-runtime setup. packaging/README.md:297–302 documents the Terminal-after-package design.

The first-user lock at build_macos_online.sh:113–115 returns success when the lock already exists, without waiting for completion or proving that the process owning it still lives. An interrupted process can leave a stale lock despite traps not covering SIGKILL. Missing-runtime launches can then show “already running” and still have no runnable app. This needs an owned PID/token state and readiness result, not removal of arbitrary lock files.

Meeting “all questions inside the installer window” requires changing that UI/lifecycle boundary. A native graphical setup controller must collect all app options, show download/install/cleanup progress and errors, support cancellation/retry, and remain open until verified activation. It can launch privileged package operations through a native authorization mechanism while keeping app questions in its own window. Simply suppressing `read` or launching Terminal minimized does not satisfy the request. Custom PackageKit UI versus a signed native setup controller is an implementation choice needing native proof; do not rely on a long network job in a time-limited package postinstall. Operating-system authorization/security UI remains OS-owned and must not be replaced with terminal passwords or credential capture.

## Preservation and cleanup do not match the requested default

Unix script408–475 bootstraps an independent cleanup Python, then runs `install_cleanup remove` before downloading/installing the application dependencies. It preserves only the install log and macOS .installing lock, plus the freshly installed shared macOS payload/command link. `remove_install` at1419–1432 passes whole recognized application roots to `_delete`; `_delete` at1143–1173 recursively removes them except explicit keep paths.

Known external user-data roots are protected by `_user_data`1056–1073, including ~/.spacr, XDG cache/state/config, demo/tutorial roots, Hugging Face and macOS preference plist. **Installer-local cache is not protected**: install_spacr_unix.sh:283 names `$INSTALL_ROOT/cache`, and removal of the root deletes it, private Python/bootstrap and unknown sibling contents as well. The installer-local bundled test_data may also be deleted by removal, and the offline path explicitly replaces it with `rm -rf` at548–550. User-written files inside an application root are not individually checked by `_refusal` during recursive deletion. Normal uninstall helpers likewise remove the entire install root (Unix:611–613), while the mac helper removes app/shared support (build_macos_online.sh:95–97).

The staged environment validation at507–526 precedes the later venv rename at528–534, but it occurs **after the earlier cleanup already deleted the discovered old installation**. tests/test_online_installers.py:170–179 only compares validation with the rename, so it does not establish full rollback safety. tests/test_install_cleanup.py:1047–1103 explicitly expects the old copy to be gone even when new pip installation fails. This is current tested behavior; N703 acceptance should instead specify what remains runnable on a failed reinstall while protecting data.

Existing `purge` is unsuitable as the requested cache/temp-only GUI choice. `_purge_targets`1217–1244 groups caches with logs, runs, models, backend environments, settings, demos and tutorial/user data; `_purge_command`1308–1346 prints paths and asks for terminal `purge`. It does not present categorized folder contents in an installer window. _user_data's default preservation list also does not bind every custom SPACR_HOME, model/cache relocation or CELLPOSE_LOCAL_MODELS_PATH; qt_ci is auditing the shared policy details.

Needed N703 separation: remove verified app-owned executable/runtime payload and stale app-owned launch registrations; retain caches, models, settings and project data by default; expose optional cleanup as a GUI inventory of exact folders and contents, with explicit selection and a pre-delete identity check. Delete only session-owned staging/temp required for replacement. Existing work_dir/stage_venv/stage_profile cleanup at395–406 is appropriately confined to the current transaction's paths, subject to ownership validation. Do not implement broad TMPDIR/home searches or erase user environments, rollback journals or cached resources by filename alone.

## What is actually shipped, and what existing tests prove

- release.yml:271–283 invokes online-installers.yml. Current normal release artifacts are Linux Online.run and macOS Universal Online.pkg, built by build_linux_online.sh:13–16 and build_macos_online.sh:41–51. Both embed the current install_cleanup module through packaging/i18n/render.py; changes to the source alone do not rewrite already published historical artifacts.
- Frozen DMG/.deb paths remain in build_macos.sh/build_debian.sh and frozen-installers.yml as legacy native acceptance. No RPM builder/artifact/registration adapter was found in the inspected packaging tree. The Unix script supports dnf/zypper as system-dependency installation, which does not mean a spaCR RPM is shipped or upgrade-cleaned. Do not claim RPM coverage.
- online-installers.yml Linux acceptance at65–81 overrides package-spec with the current checkout, installs into a temporary fresh root and probes direct Python with -I. It does not establish later shell/desktop PATH identity with mixed old copies.
- macOS acceptance at263–285 installs the .pkg using `sudo installer`, then directly runs install-for-user.sh with SPACR_PACKAGE_SPEC=current checkout and SPACR_NO_RELAUNCH=1. It checks direct private-runtime imports. It bypasses the native missing-runtime Terminal launch and the interactive .pkg window, and does not test installing a new package over an old user runtime.
- test_online_installers.py:522–541 structurally pins the Terminal-capable launcher and requires no shell install in postinstall. N703 needs to replace that obsolete behavior contract while preserving signing, universal architectures and user privilege boundaries.
- test_macos_online_update_n627.py covers same-runtime in-app upgrade, readiness, version probe, failures and newer-runtime launch using controlled POSIX executables. Those are not actual native Installer/Finder acceptance.
- test_install_cleanup.py covers legacy layouts, custom roots inferred through known launchers, protected external data, refused paths and fake-tool Unix shell sequencing. Extend the actual data cases rather than loosening removal assertions.
- test_frozen_macos_update.py covers bundle identity, atomic exchange/rollback, preserved unknown files, committed recovery and exact relaunch. Retain those safety proofs and add active launcher inventory separately.
- test_frozen_debian_update_acceptance.py:61–77 checks a temporary-root dpkg replacement/rollback and old-only payload removal. It does not simulate an earlier Conda command or desktop entry. test_native_installer_workflow.py verifies fresh artifact smoke runners cannot borrow the build checkout; useful, but different from mixed-install upgrade acceptance.
