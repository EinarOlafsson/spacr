Proposed wire contract

Keep every ordinary setting and its value, including the original model path.
Keep N693's two-column Key,Value CSV and sibling settings-object JSON. Append
one reserved setting, model_metadata, whose value is the following object:

  {"schema_version": 1, "settings": {"<model-setting>": {
    "requested_value": "<exact current setting string>",
    "key": "<stable exact zoo key>",
    "version": "<exact declared opaque version>" OR null,
    "version_status": "declared" OR "unspecified",
    "sha256": "<64 lowercase hexadecimal characters>",
    "kind": "<exact catalogue checkpoint kind>",
    "filename": "<published catalogue name>"
  }}}

schema_version is integer 1, never bool or a string. All seven per-setting
fields are required; additional metadata/record properties are rejected in
version 1. settings may be empty. Records apply only to string-valued model
inputs known to the module/consumer registry. Each requested_value must equal
the effective setting with both type and text equality after migration and
overrides. No trimming, case folding, environment expansion or numeric
coercion is allowed in this binding comparison. Filesystem lookup may expand
the effective request later. SHA256 is a byte identity, not proof that an
untrusted setting file's publisher labels are authentic.

model-metadata.schema.json defines structural validation. The semantic rules
in this document additionally require setting existence, current binding,
registered consumer kind/backend, trusted catalogue agreement and uniqueness.
The structural schema cannot prove these relationships or actual file hashes.
Settings may have their usual unrelated properties outside model_metadata.

CSV uses str(metadata) as a Python literal in one properly quoted value cell;
JSON uses an object. Do not put JSON null/true into the literal CSV cell. Do
not flatten versions or hashes into separate scalar CSV rows. Both current
CLI and tabular parsers reparse the top-level dict's direct values, but return
the already-parsed nested settings dict intact: strings such as "01", "1e-05",
"true" and digit-only hashes remain opaque in per-setting records. No app
parser has been executed in this evidence. Fixtures were read only with
stdlib csv, ast.literal_eval and json; current-parser behavior is source-bound.

Exact version without guessed lineage

This refines Home's preliminary 2026-10-13 all-string version proposal.
ModelEntry.version mixes a catalogue declaration, the default "1", and a
local collision suffix. _entry_from_mapping uses str(data.get('version') or
'1'); the 19 current BUNDLED_REMOTE_MODELS records have no version field.
Neither the resulting "1", a key ending _v4, a filename ending r7 nor a cache
name ending _v2 establishes a publisher-declared release version.

version_status=declared requires a nonblank string copied from an explicit
trusted raw catalogue declaration, unchanged. "01" differs from "1". An
explicit, trusted publisher version "1" is valid; normalized ModelEntry "1"
alone is insufficient evidence. version_status=unspecified requires version
null and an exact key+filename+kind+SHA256 pin. It records exact bytes without
claiming a release number. A record carrying version "1" with no status, a
numeric version, a null declared version, or a guessed suffix is rejected.
Do not rewrite existing ambiguous recorded versions to null automatically:
ask for explicit re-export/reconciliation against trusted raw provenance.

For missing files, declared version candidates must have a trusted explicit
declaration with exact string equality. Unspecified candidates must be
explicitly recognized as lacking a declared version; matching just the
normalizer's default is forbidden. Raw-declaration provenance must survive
catalogue ingestion, since ModelEntry alone currently loses this distinction.
Pinning a checksum never authorizes contradiction of another recorded field.

Export and GUI preservation

Keep write_settings_file a faithful generic serializer. A shared lightweight
enrichment step in the existing model_zoo module prepares a deep-copied
metadata object for form Export, Submit remote snapshots, snapshot Save CSV
and interested non-GUI callers. Capture at Submit, not only when saving a
snapshot. A trusted picker selection can pin the intended catalogue model
even when its weights are absent on the laptop. A same-basename local file
does not prove it has those bytes. Verified picker/cache provenance or a
worker-computed hash can establish a local match; do not hash large files on
the GUI thread, run a model, scan disks, call plugins or refresh the network
as part of Export. Unresolved/custom paths remain unchanged without a zoo
record and receive a clear export diagnostic; never fabricate a partial pin.

Declare metadata as a reserved internal dictionary in type/validation paths
and every form's hidden defaults, including slot retention/filtering. Preserve
it through Import/apply/collect/export. On model-widget edit remove that
setting's record or recompute from trusted provenance; validate again during
collect/export so an overlooked edit cannot retain a stale pin. Preserve
inactive records only while their setting survives unchanged in the exported
payload; do not acquire inactive model weights. Removing an organelle slot
also removes dangling identities. Do not create a provenance form control.

DistributedJobs.configure_submission currently makes a shallow copy. Nested
metadata must be deep-copied/frozen on submission and save, so later form
edits cannot mutate the submitted identity through shared nested objects.
Changing the snapshot module triggers registry/backend revalidation, not
automatic reinterpretation of a same-named setting in a different module.

Current recursive remote mapping rewrites both a model setting's absolute
request and its nested requested_value by the same rule when under the
dataset root, preserving their equality. Paths outside the root and Windows
paths on Linux generally remain unchanged. Keep this paired transformation;
validate binding before and after mapping. Key/version/hash/kind/filename
must remain unchanged. Retain the original exported payload separately in
the job/run provenance; requested_value in the mapped payload means the
effective mapped request, not an immutable origin path. Existing mapping
does not guarantee cross-platform re-rooting. Published filenames used in
metadata must be relative catalogue names, never absolute paths or URIs.

CLI --set, queue overrides and migration

Apply defaults, migrate the file's own keys, overlay the file, then coerce all
overrides using today's existing rules. Migration must also migrate an
identity's setting key with a proven one-to-one equivalent rename, and verify
its value; conflicting old/new identities are an error, not first-wins.
Retired or transformed semantics cannot inherit an old identity without an
explicit trusted reconstruction. Apply the same path in batch inline/file
settings and queue override_args; changing only resolve_settings misses batch.

Collect explicitly overridden model-setting keys. After overrides finish,
invalidate those records even if the last value equals the old value (the
override is an explicit new selection). Remove only their records, preserve
unaffected pins, and announce each invalidation. Multiple repeated overrides
cannot revive the old pin if the value later returns to its original text.
Do not simply update requested_value while retaining the old hash. Rebuild a
pin only from a fresh unique exact trusted catalogue match, without network
during resolution/planning. Rebuilding is recorded as a new selection; an
unrecognized new custom path remains unpinned. A backend change revalidates
all affected model records against the resulting active backend; it cannot
reuse a pin of the wrong kind. --set src=... preserves model pins unless the
model value is actually transformed through an explicit root mapping.

Reserve model_metadata against generic --set replacement/dotted mutation:
fail with a clear use-a-settings-file/export instruction. Current coerce_value
accepts literal dict overrides for known/current dict settings; future
reservation therefore needs an explicit guard. All supplied metadata must
validate before it is used. Stale metadata loaded from a hand-edited file
fails even if preflight is disabled; --force and --no-preflight cannot bypass
pin integrity, version conflicts, checksum verification or acquisition policy.
Intentional edits through GUI/--set can invalidate records, whereas a stale
record silently present in an imported file must never be silently repaired.

Missing weights, local priority and legacy files

Validate schema/binding/active-consumer compatibility first. A supplied local
regular file wins; when pinned, hash its bytes and refuse mismatch. A known
catalogue contradiction is an error; an offline catalogue absence does not
prevent use of matching locally supplied pinned bytes, but unverified label
provenance must remain identified as recorded rather than catalogue-verified.
An unpinned existing custom path retains current behavior. Stock models,
backend prefixes, True/False well_detection, disabled models and architecture
names follow their existing consumer-specific semantics; they are not all
downloadable file references. A joblib classifier directory is not a single
checkpoint; a resume checkpoint still needs optimizer/state validation.

If absent, resolve pins as conjunctions of exact key, version status/version,
kind, filename and hash from a trusted bounded catalogue. Identical duplicate
records may collapse only when their full identity agrees; two distinct
identities are an ambiguity error. Prefer verified cache bytes with the
expected hash. Wrong-hash existing files are preserved and not reused.
Only actual permitted execution workers may acquire weights. Recheck under
an OS-backed cross-process lock keyed by cache namespace+hash, verify the
completed file and atomically preserve provenance. Existing fetch/_claim
prevents overwrites but does not prove one download across processes. Cache
collision suffixes are storage locations, never versions. Download logs must
distinguish given-local, cache-hit and actually-downloaded and name setting,
request, key, declared version or 'unspecified', hash and actual destination.

Legacy files without metadata retain their current parser and explicit-path
behavior. A missing path can use a unique exact published basename (lexically
handle POSIX and Windows separators), or a unique exact zoo key; never fuzzy
substring, latest/default replacement, cache suffix stripping or generic URI
basename. Hash pin the selected current declared entry before acquisition and
log that the legacy input supplied no historical identity. This reproduces
the selected current catalogue bytes, not proven past laptop bytes. A legacy
file that separately records a conflicting/ambiguous version must fail and
request reconciliation; absence of metadata is not permission to ignore it.
Unknown names/hashes/custom paths and ambiguous records give setting/path,
constraints and candidate key/version/hash or copy-file guidance.

Offline metadata and planning

Proposed SPACR_MODEL_DOWNLOAD=off is a hard no-network policy for weights AND
catalogue traffic. A settings policy cannot override env off. Accept only
documented policy values; invalid values fail. All dry-run, validation and
GUI enrichment paths use a strict planning mode independent of that env.
Unknown schemas and stale pins fail in planning; missing exact files can be
reported as would-acquire or offline copy requirements without fetching or
claiming executable readiness. Plan before required-path refusal on N702-
eligible missing models; only exact resolution can replace that refusal.

catalogue(remote=True, block=False) currently starts a background refresh;
catalogue(remote=False) also omits declared built-in remote and explicit local
catalogue rows. Neither call supplies the proposed complete offline index.
Future pure selection must consume raw built-ins, explicitly loaded trusted
local catalogue and deliberately persisted trusted catalogue records, with
no shared_catalogue refresh or arbitrary plugin/provider calls. The present
shared cache is process memory, not a fresh-node offline metadata store.
metadata in settings gives identity constraints, not download-source authority:
this schema accepts no arbitrary URL. A shared-only missing model on a fresh
offline node needs a copied trusted local catalogue plus weights, or copied
matching weights at the requested path. If exact bytes are cached they work
offline; otherwise name filename/hash and expected destination to copy.

Checksums ensure which bytes arrive, not that historical bytes remain hosted.
Current HF URLs resolve main. Source deletion/change is an availability error,
never permission to substitute newer bytes. Future immutable revision URLs
belong in trusted catalogue provenance, keeping the required checksum.
