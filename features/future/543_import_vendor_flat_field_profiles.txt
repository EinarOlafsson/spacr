WHAT TO BUILD
    Read the illumination/flat-field correction files vendors write
    (PerkinElmer Harmony/Operetta FFC profiles, Zeiss ZEN shading
    references, Nikon/Olympus where documented) and use them in spaCR's
    illumination correction instead of estimating one.

DONE WHEN
    An Operetta export's FFC profile is applied and matches Harmony's
    corrected output on the same field.

ALPHA: 2026-09-27. One new setting, illumination_vendor_profile (registered
    in ALPHA_FEATURES[543]; hidden unless Preferences -> Show alpha features
    is on, and a saved value still reaches the run). It sits under
    every Illumination Correction heading (Measure, External Masks) and under
    Correction Model on the Illumination screen.

WHAT WAS BUILT (2026-09-27, CPU only)
    spacr/illumination.py: a non-empty illumination_vendor_profile replaces
    the estimate in prepare_illumination_model (illumination_model still
    wins over both). Read by _vendor_illumination:
      * Harmony XML (Operetta / Opera Phenix Index.idx.xml, Index.xml or a
        saved FFC profile): every *FlatfieldProfile element, JSON or the
        bare-key spelling. Foreground polynomial = gain, Background
        polynomial = spatial offset, both at Harmony's own scale, so
        corrected = (raw - background) / foreground. Merged channel c takes
        Harmony channel c + 1. Polynomial convention: x = (col - Origin[0]) *
        Scale[0], y = (row - Origin[1]) * Scale[1], sum_i sum_j C[i][j] *
        x**(i-j) * y**j (as described in the image.sc thread).
      * Shading reference image (.tif/.tiff/.czi/.npy; ZEN, Nikon, Olympus):
        plane c = channel c, one plane serves all; illumination_dark
        subtracted, normalised to mean 1.
    IlluminationField gained an optional spatial darkfield, saved/loaded in
    the .npz, so the Harmony background survives into worker processes and
    segmentation-input correction.
    Tests: tests/test_vendor_flat_field_profiles.py (synthetic Operetta
    export; spaCR's corrected field equals an independently computed
    Harmony output, JSON and bare-key forms, npz round trip, TIFF reference)
    and tests/qt/test_vendor_flat_field_alpha_gate.py.

2026-10-01 — EXPLICIT VENDOR CHANNEL ASSIGNMENTS
    illumination_vendor_channel_map is an optional string, default empty.
    For example, 0:2,1:1 maps persisted intensity-axis position 0 to Harmony
    channel 2 and position 1 to Harmony channel 1. Persisted intensity
    positions are zero-based; Harmony IDs and reference-image planes are
    one-based. This supports subsets, reordered acquisitions and noncontiguous
    Harmony IDs without assuming that current array order is vendor order.

    Every corrected intensity channel needs an assignment when the setting
    is nonempty. Extra assignments may remain when selecting a subset.
    Malformed pairs, duplicate intensity keys, missing assignments, zero
    vendor IDs and unavailable profiles/planes fail clearly. Explicit maps
    never fall back to another profile or a single reference plane. A blank
    mapping preserves legacy c -> c+1 behavior and single-plane broadcasting.
    Both the gain and spatial background follow the assigned Harmony channel;
    image reference planes retain the existing dark subtraction/normalization.

    The setting reaches prepare_illumination_model and is used only when a
    vendor profile is selected. A saved illumination_model still wins. Model
    metadata records the resolved vendor_channel_map plus whether it was
    explicit; both survive NPZ save/load. The existing model digest therefore
    binds channel assignments in segmentation application provenance.

    Validation: 34 focused CPU tests passed under a 4 GiB cap, hidden CUDA
    and at most two numerical threads. Independent synthetic gain/background
    equations confirm reordered correction; tests cover subset/noncontiguous
    channels, shading references, invalid mappings, unchanged blank defaults,
    saved-model priority, NPZ provenance and raw-field preservation. No
    acquisition images were changed and no GPU jobs were run.

    This closes the channel-assignment implementation gap. Comparing a real
    Operetta/Harmony original and its corrected export, and reading proprietary
    embedded CZI/ND2/Olympus shading formats, remain open. Status stays alpha.

    Settings integration: the new string key is registered with a blank
    default, alpha visibility, help and all four existing illumination
    settings groups. The API-consumer and settings-flow artifacts were
    regenerated from source. The mapping field is inactive unless correction
    is on and a vendor profile is selected without an overriding saved
    model; disabling or hiding it retains its saved value. Thirteen focused
    alpha, real-form visibility, value-retention and dependency/layout
    checks passed under the same 4 GiB CPU/offscreen cap.

2026-10-03 — REAL-DATA CHECK (lane 2, CPU)
    Data: scPortrait example parsing dataset, Harmony 5.2 export of one
    Operetta well (16 fields, 2 channels, 1080x1080), with and without
    Harmony flat-field correction: zenodo.org/records/14193689 (raw) and
    zenodo.org/records/14973295 (corrected), both CC-BY-4.0. Scripts:
    /mnt/wd4tb/scratch/543/work/cmp.py, fit.py.
    Result: FAILS on real data. Both channels' FlatfieldProfile carry ONLY a
    Background polynomial (no Foreground), so _vendor_illumination raises
    "contains no Harmony FlatfieldProfile with a foreground polynomial".
    The polynomial convention itself is confirmed: x = column, y = row,
    Origin/Scale as implemented (transposed surface fits worse).
    Harmony's actual correction for a Background-only profile is additive:
        corrected = raw - Mean * (B(x, y) - 1)
    with Mean the profile's Background.Mean. Against Harmony's own output
    over 16 fields: median |error| 0.41 / 0.37 counts, p95 1.8 / 1.8 counts
    (ch1 Hoechst / ch2 Alexa 488; uint16 rounding). The multiplicative
    reading raw / B gives median 0.40 / 13.7 counts, p95 31 / 257 counts.
    Harmony adds no further rescaling (corrected mean = raw mean to 0.01%).
    LEFT (code): accept Background-only profiles and apply them additively
    with Mean as above; real Foreground+Background profiles still unseen.
