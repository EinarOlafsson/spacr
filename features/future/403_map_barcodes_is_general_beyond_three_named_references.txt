WHAT IS STILL FIXED, MEASURED 2026-09-14
--------------------------------------------------------------------------------

THE PIPELINE STILL NAMES EXACTLY THREE REFERENCES, even though the search no
longer does. `spacr/settings.py:3445-3448` declares `column_csv`, `grna_csv`
and `row_csv` as three separate string settings, and settings.py:537 says so
in prose: "by ``column_csv``, ``grna_csv`` and ``row_csv``, exactly as every
...". So a screen that can find seven barcodes hands them to a mapper that has
three slots with three names.

That is the same shape as the organelle registry before item 76: a fixed
vocabulary of roles, where the general case is "N of them, named by the run".
It is worth noting that 76's answer -- interpolate a registry -- had a cost
that took a year to surface (see 284: 702 roles times one widget each), so the
lesson for this item is to make the COUNT come from the data rather than from
a maximum.

THE ALPHABET IS DNA AND ONLY DNA. `barcode_search.py:136` is
`_COMPLEMENT = str.maketrans("ACGTNacgtn", "TGCANtgcan")`. Reverse-complement
matching is therefore nucleotide-only. That is correct for every assay spaCR
runs today and it is an assumption rather than a general rule -- protein tags,
amino-acid barcodes and non-ACGT alphabets would all silently take the wrong
path rather than be refused.

THE TUNING CONSTANTS ARE MODULE-LEVEL, not per-run: `DEFAULT_SAMPLE_READS`
20000, `DEFAULT_CHUNK_READS` 2000, `MIN_ENRICHMENT` 3.0, `MIN_USABLE_RATE`
0.10, `MAX_OFFSET_SPAN` 6, `OFFSET_WINDOW_COVERAGE` 0.80,
`MIN_READS_FOR_VERDICT` 500 (`barcode_search.py:120-133`). Every one is a
judgement about a library, and a library that differs in read depth or barcode
length gets someone else's judgement with no way to say so.

--------------------------------------------------------------------------------
WHAT "GENERALIZABLE" SHOULD MEAN HERE
--------------------------------------------------------------------------------

  * A RUN DECLARES ITS REFERENCES, as a list with names it chooses, rather
    than filling three slots the code named in advance. `row` and `column`
    are plate geometry and `grna` is a library; a different screen may have
    two of those, or five, or none.
  * THE MAPPING READS THAT LIST. `generate_barecode_mapping` is the legacy
    helper and the place this stops being cosmetic.
  * THE ALPHABET IS DECLARED OR THE INPUT IS REFUSED. Silently reverse-
    complementing something that is not DNA is worse than saying no.
  * THE THRESHOLDS ARE SETTINGS with the current values as defaults, and
    each says what it is judging.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

A run with TWO references and a run with FIVE both map end to end, on planted
data, with no setting named `row_csv`, `column_csv` or `grna_csv` anywhere in
either. A non-ACGT alphabet is refused with a message naming the character.
And the existing three-reference screens still run unchanged from their
current settings files -- a generalisation that breaks every saved settings
file is a rewrite, not a generalisation.

NOTE FOR WHOEVER TAKES IT: `grna` (the setting, not `grna_csv`) is being
retired under item 364 as a setting no pipeline reads. Do not confuse the two.
`grna_csv` is the live one.

2026-09-15 -- TWO OF THE FOUR BUILT, AND ONE CORRECTION TO THIS FILE

FIRST, THIS FILE WAS WRONG ABOUT THE FIRST TWO REQUIREMENTS. The section above
titled "WHAT IS STILL FIXED, MEASURED 2026-09-14" opens with "THE PIPELINE
STILL NAMES EXACTLY THREE REFERENCES". It does not, and it did not on the day
that was written. `spacr/settings.py:321` already holds `BarcodeSet`, the
`barcode_set` settings key already exists, `spacr/sequencing.py` already
iterates the set at four sites, and
`tests/test_a_barcode_set_is_any_number_of_barcodes.py` already proves five
barcodes each get their own columns and that one barcode is a whole set. 160
barcode tests pass against it.

The three `*_csv` settings the section points at are still declared -- but as
the COMPATIBILITY PATH for saved settings files, which is what the acceptance
criterion below asks for ("the existing three-reference screens still run
unchanged from their current settings files"). Reading three declarations as
"the pipeline names exactly three references" was a measurement of the
settings file rather than of the pipeline.

Requirements 1 and 2 are therefore DONE, and were done before this item was
filed. Recorded rather than quietly struck out, because an item that claims
unbuilt work that is already built sends the next session to build it twice.

THIRD REQUIREMENT, "THE ALPHABET IS DECLARED OR THE INPUT IS REFUSED" -- BUILT.

  `NUCLEOTIDE_ALPHABET` is now declared beside `_COMPLEMENT`, and
  `BarcodeTable.oriented()` refuses to reverse-complement a table containing
  anything else, naming the offending characters and saying to search it with
  `AS_GIVEN` instead.

  THE REFUSAL IS IN `oriented()` AND NOT IN `reverse_complement()`, which is
  the whole design decision and is easy to get backwards. `reverse_complement`
  is permissive ON PURPOSE -- its docstring says so -- because it runs on
  READS, where an uncertain base should still be reversed rather than have the
  read refused. `oriented()` runs on REFERENCE TABLES, where a non-nucleotide
  sequence flips to its own letters reversed, matches nothing, and is reported
  ABSENT. That last step is why silence is worse than an error here: the run
  does not fail, it produces a confident wrong conclusion about the data.

  ONE BAD ROW REFUSES THE WHOLE TABLE. A per-sequence check would flip 999
  rows correctly and pass the thousandth through unchanged, and the search
  would then miss exactly one reference with nothing in the report to say so.

FOURTH REQUIREMENT, "THE THRESHOLDS ARE SETTINGS" -- HALF BUILT.

  `SearchThresholds` is a frozen dataclass carrying all five verdict
  thresholds, defaulting to the constants that were there before, threaded
  through `_decide`, `_build_finding`, `_SearchState`, `iter_barcode_search`
  and `search_barcodes`. Each field's comment says WHICH QUESTION it judges,
  as the requirement asks: sample size, distinguishable from coincidence,
  enough to map from, and one position rather than scattered.

  It validates on construction. A `min_enrichment` of 1.0 makes the
  coincidence rate itself clear the bar and reports EVERY table PRESENT --
  a failure that is invisible downstream and looks like a spectacular result,
  which is why it is caught where the number is set rather than where it
  misbehaves.

  THE TWO READ-BUDGET CONSTANTS WERE ALREADY SETTABLE. `DEFAULT_SAMPLE_READS`
  and `DEFAULT_CHUNK_READS` have been function parameters with defaults all
  along; only the five VERDICT thresholds were read from module globals.

  WHAT IS LEFT: wiring the five to the settings surface, so the screen offers
  them rather than only the library accepting them. That is deliberately not
  done in the same change -- `test_settings_tooltip_quality::test_real_default
  _claims_have_no_unrecorded_drift` is RED right now at 667 vs 666, and adding
  five settings while that counter is already wrong makes my delta
  indistinguishable from the existing one. The reds come first.

HOW EACH CLAIM ABOVE WAS CHECKED: every new test was run against a REVERTED
fix. The alphabet guard, deleted, reddens two of the four tests written for it
-- the other two assert the guard does NOT over-reach and correctly pass
either way. The threshold threading, made to ignore what it is handed,
reddens three of five. A test that cannot tell the two versions apart is not
evidence about the fix.

AND ONE RATCHET MOVED WITHOUT BEING REGENERATED. The four new public symbols
take `DOCUMENTATION_API_SYMBOL_COUNT_RATCHET` from 10,536 to 10,538. It was
ALREADY red at 10,536 against a pinned 10,534 before this change, and
`test_documentation_api_catalog_inventory_and_hashes_are_current`'s own
docstring says the API catalogs may be stale during ordinary work and are
rebuilt once, immediately before the version is cut. So it was left stale
deliberately, and is recorded here so the release rebuild knows why it moved.

2026-09-15 -- REQUIREMENT B BUILT, AND REQUIREMENT C CHECKED RATHER THAN BUILT
--------------------------------------------------------------------------------

B, "LOADING TEST DATA LOADS THE REFERENCE TABLES" -- BUILT (b3fc54fb3).

  `spacr.settings.fill_missing_barcode_references` fills only EMPTY reference
  settings and returns the ones it filled. A table the user already chose is
  never replaced: that failure does not announce itself, it completes and
  reports numbers mapped against the wrong guides.

  `ensure_bundled_barcode` checks the local copy FIRST, so the ordinary path
  touches no network -- the three CSVs ship inside the wheel. The GitHub
  fetch exists for an install whose package data was stripped. It is pinned
  to the release TAG rather than a branch (a branch URL returns whatever the
  file is today, which would fail the hash check and report an integrity
  problem when the real problem was the address), verified against a pinned
  sha256 BEFORE anything is written, and staged-then-moved so an interrupted
  fetch cannot leave a half-written CSV that parses as a short barcode table.

  THE HASH PIN CANNOT GO STALE SILENTLY, which is the part worth keeping. A
  test recomputes every hash from the file that ships beside it, so editing a
  CSV without editing the pin is a red test here rather than a rejected
  download on a user's machine months later, blaming the network. That is the
  exact failure shape of the hand-written BLOCKED dict in
  `tools/build_instruction_index.py`, and one of those is enough.

  It is wired into `_apply_demo_to_screen` by asking whether the loaded
  settings DECLARE the reference keys, not by app key. A Mask settings file
  therefore cannot gain three path settings that mean nothing to it, and the
  tutorial runner -- which calls the same method -- gets the behaviour
  without being told about it.

C, "THE AUTOMATIC SETTINGS MODE LIKE LIVE MODE IN MAKE MASKS" -- CHECKED, AND
IT IS NOT THAT MODE. NOT BUILT, because the answer needs one word from the
maintainer first and the two readings differ in a way that matters.

  WHAT LIVE PREVIEW ACTUALLY DOES, read from `spacr/qt/widgets/live_preview.py`:
  a toggle turns it on, and every control on the panel re-renders it --
  `toggled.connect(self._refresh_canvases)`, `valueChanged.connect(...)`,
  `currentIndexChanged.connect(...)`. It updates continuously and it WRITES
  NOTHING. It is a view.

  WHAT THE SEARCH DOES, read from `spacr/qt/screens/map_barcodes.py:1618`:
  `search_button.clicked` starts it. It is then PROGRESSIVE while running --
  `iter_barcode_search` yields a full report after every chunk, so the rates
  settle rather than jump -- and when it finishes it enables an Apply button.
  So it is live in one narrow sense, during a run, and not live in the sense
  the maintainer's sentence points at, which is re-running by itself.

  THE COST IS NOT THE OBSTACLE, and this was worth measuring rather than
  assuming, because assuming it was expensive was wrong. A full search over
  the default 20,000-read sample takes 0.27 s on an uncompressed synthetic
  file, and 0.07 s on a 32 MB gzipped file holding 2,000,000 reads -- the
  sample is bounded, so the reader stops at 20,000 and never decompresses the
  rest. The first chunk lands in 0.03 s. That is comfortably inside
  live-preview territory; a Cellpose preview segmentation takes longer.

  SO THE ONLY REAL QUESTION IS WHAT "AUTOMATIC" IS ALLOWED TO TOUCH, and 399
  already answered half of it deliberately. `apply_proposal`'s docstring says
  so in its own words: "Nothing calls this on its own. A search that finishes
  enables the button and stops there, because a panel that quietly replaced
  values somebody typed would be a worse failure than the one it exists to
  prevent."

  THE TWO READINGS OF THE REQUEST:

    1. THE SEARCH BECOMES LIVE. It re-runs by itself when its inputs change
       -- the sequencing folder, the reference tables, the anchor -- and the
       settings it derives are shown continuously as a PROPOSAL. Apply stays
       a deliberate click. This is exactly Live preview's shape: continuously
       shown, never written. Cheap, and it contradicts nothing.

    2. THE APPLY BECOMES LIVE. Derived settings are written into the form as
       the search revises them. This is the thing 399 refused on purpose, and
       the refusal is right: a verdict can move from INDETERMINATE to PRESENT
       to ABSENT as the sample grows, so a live apply would rewrite the
       user's form two or three times during one run, including over values
       they typed themselves.

  RECOMMENDATION: build reading 1, and only after he confirms it is what he
  meant. The sentence "the automatic settings mode should be like live mode
  in make" fits both readings, and the difference between them is whether the
  user's typed settings can be overwritten without a click. That is not a
  question to settle by inference. Filed as a question in HANDOFF section 1.

2026-09-15 -- C IS ANSWERED. LIVE SEARCH, APPLY BY CLICK.
--------------------------------------------------------------------------------

Asked through the question tool and answered, verbatim: "Live search, Apply by
click (Recommended)". The option he chose read: "The search re-runs whenever a
setting changes, like Live preview, and the results update as you go. Your form
values only change when you press Apply, so nothing you typed is overwritten."

That is reading 1 of the two above, and it settles the only part that was
genuinely ambiguous. BUILD IT.

WHAT THAT MEANS CONCRETELY, against the code as it stands:

  * THE SEARCH RE-RUNS ON A SETTINGS CHANGE. Today `search_button.clicked`
    is the only trigger (`map_barcodes.py:1618`). It gains the Live preview
    shape: the inputs `plan_barcode_search` actually reads -- the sequencing
    folder, the reference tables, the anchor -- re-trigger it when they
    change. Those are the inputs and not "every setting on the screen":
    re-running because someone changed `comp_level` would be a search that
    cannot produce a different answer.

  * IT IS DEBOUNCED, and this is not optional. A path field emits on every
    KEYSTROKE, so an undebounced live search starts a run per character and
    the last one to finish wins -- which is a race whose winner is not
    necessarily the one matching what is now on screen. A single-shot QTimer
    restarted on each change, and the in-flight search cancelled, is the
    shape; `cancel_button` already exists, so cancellation is not new work.

  * APPLY STAYS A CLICK, unchanged. `apply_proposal` already says "Nothing
    calls this on its own", and the maintainer's answer now agrees with that
    docstring in his own words: "nothing you typed is overwritten". Do not
    weaken it.

  * THE PROPOSAL IS SHOWN CONTINUOUSLY even while the verdicts move. A
    verdict legitimately travels INDETERMINATE -> PRESENT -> ABSENT as the
    sample grows, so the panel has to be readable mid-flight rather than
    flickering between three answers. `iter_barcode_search` already yields a
    complete report per chunk whose counts only ever grow, which is what
    makes that possible.

  * IT IS AFFORDABLE, measured rather than assumed: 0.27 s over the default
    20,000-read sample uncompressed, 0.07 s on a 32 MB gzipped file holding
    2,000,000 reads. The sample is bounded, so file size barely matters.

HOW IT WILL BE CHECKED: changing a reference table with the panel open
re-runs the search without a click and updates the verdicts; changing an
unrelated setting does not; typing a path one character at a time starts ONE
search rather than one per character; and the form's values do not change
until Apply is pressed -- that last one asserted by typing a value into the
form by hand, letting a live search complete with a different proposal, and
requiring the typed value to still be there.

2026-09-15 -- C BUILT: THE SEARCH FOLLOWS THE FORM, AND ONLY APPLY WRITES IT
--------------------------------------------------------------------------------

WHAT IT DOES. Once a search has been asked for, changing any setting the
search reads -- `src`, `column_csv`, `grna_csv`, `row_csv`, `barcode_set`,
`target_sequence` -- starts it again after the form has been still for 600 ms.
The list is derived from `_SHIPPED_REFERENCE_KEYS` and what
`plan_barcode_search` reads, so a table added there is watched automatically.
Settings the search does not read never start one. Apply is unchanged: the form
changes only when it is pressed. That is the maintainer's answer, "Live
search, Apply by click", in code.

THREE DECISIONS THE SENTENCE DID NOT MAKE, recorded so they can be reversed
on purpose rather than by accident:

  1. THE FIRST SEARCH IS STILL ASKED FOR. Opening Map Barcodes and typing a
     folder is not a request to read it. After the first search, every change
     to its inputs is. A search on open would be a one-line change if wanted.
  2. A SEARCH REPLACED BY A NEWER ONE IS DROPPED QUIETLY. Nobody pressed
     Cancel, so the status line does not say they did.
  3. APPLY ADOPTS WHAT IT WROTE. `propose_map_barcodes_settings` can write a
     reference table's path, which is a search input. Without adopting the
     post-Apply inputs, Apply would start a second search that repeats the
     first and wipes the "wrote these settings" summary off the screen.

A SHARED WIDGET GAINED A SIGNAL. `FilePathListWidget.set_value` never emitted
`value_changed`, deliberately: that signal marks a screen dirty and re-writes a
settings file, so a load must not emit it. The consequence was that a settings
load replacing a reference table was invisible to anything that follows the
value. `contents_changed` now fires on any change to the list, including
`set_value`; every user edit still emits both. A test pins that a load emits
`contents_changed` and NOT `value_changed`.

HOW IT WAS CHECKED -- `tests/qt/test_the_barcode_search_follows_the_form.py`,
ten tests, each mutation run against the real code and restored:

      the form is never listened to        4 red
      no pause before searching            2 red
      the inputs are not compared          1 red
      a load does not announce itself      4 red
      Apply does not adopt its own writes  0 red at first, then 1 red

THAT ZERO WAS THE USEFUL RESULT. The Apply test wrote only the read window,
which starts no search whether or not Apply adopts anything, so it passed
against both versions. It now writes the anchor, a setting the search reads,
and fails without the adoption. A test that cannot tell two versions apart is
not evidence about either.

API SURFACE. The three barcode-reference helpers from requirement B are now
private -- `_fill_missing_barcode_references`, `_ensure_bundled_barcode`,
`_bundled_barcode_url` -- because only `spacr.qt.app` calls them, and a public
name is a contract translated into nine languages. `SearchThresholds` stays
public: `search_barcodes(thresholds=...)` takes one.
