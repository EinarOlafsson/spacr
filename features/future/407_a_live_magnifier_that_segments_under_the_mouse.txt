--------------------------------------------------------------------------------
WHAT IS WANTED
--------------------------------------------------------------------------------

A toggle on the Make Masks editor. While it is on:

  1. A square box follows the mouse over the image and shows the region
     around the cursor, slightly MAGNIFIED.
  2. That region -- the enhanced crop, not the whole image -- is passed
     through a LIGHTWEIGHT segmentation model, and the objects it finds are
     drawn over the box LIVE, as the mouse moves.
  3. A CLICK commits the objects currently shown in the box into the
     image's mask. They stay there when the toggle goes off, when the user
     saves, when the user moves to the next field -- they are ordinary mask
     objects from that moment on, editable and erasable like any other.

Settings the maintainer asked for, by name:

    mode          which lightweight model runs on the region ("there should
                  be options")
    size          the diameter, in image pixels, of the region of interest
    zoom          the magnification -- and the MOUSE WHEEL CHANGES IT LIVE
                  while the feature is on
    sensitivity   the model's acceptance threshold, "like cellpose cell
                  probability score"

--------------------------------------------------------------------------------
WHY
--------------------------------------------------------------------------------

Curation is where mask quality is actually decided, and today a missed
object means drawing it by hand. This turns "the model missed three cells in
the corner" into three clicks, with the model working at a magnification
where small or dim objects are visible, and with the user choosing exactly
which objects to accept. It is also the natural front end for the
curation queue in 396: fields come from the queue, and missed objects are
added here rather than by a full re-run.

--------------------------------------------------------------------------------
DESIGN NOTES -- NOT DECISIONS
--------------------------------------------------------------------------------

THE MODEL NEVER RUNS ON THE GUI THREAD. HANDOFF and 284 are unambiguous that
a module screen must stay responsive; a model call on every mouse move is
the fastest possible way to break that. Inference belongs on a worker, with
only the NEWEST request kept -- a mouse that has moved on makes every queued
region stale, so a request superseded before it starts is dropped, not run.

THE REGION IS SMALL, WHICH IS WHAT MAKES "LIVE" POSSIBLE. A 128-256 px crop
is a few milliseconds on a GPU for the models below and tolerable on a CPU.
Throttle to the worker's own pace rather than to a fixed rate, and show the
last completed result with a subtle "updating" mark rather than blanking.

CANDIDATES FOR `mode`, all already adjacent to spaCR:

    Cellpose (cyto / nuclei, the small models)  -- spaCR's existing path;
        `sensitivity` maps directly onto cellprob_threshold
    DINOCell            -- future item 404; predicts Cellpose-style flows, so
                           the same post-processing applies
    SAMCell / MobileSAM -- future item 405; prompt-free on a crop, and a
                           natural fit for a click-to-accept interaction
    classical           -- threshold + watershed, for machines with no model
                           installed; also the fallback when a model import
                           fails, so the feature never simply does nothing

MAGNIFICATION IS FOR THE EYE AND POSSIBLY FOR THE MODEL, AND THOSE ARE TWO
DIFFERENT SETTINGS. Upsampling the crop before inference helps small objects
under models trained at a fixed object diameter; showing it magnified helps
the user see them. `zoom` should control the view; whether the model sees the
zoomed or the native-resolution crop needs measuring, not assuming.

COMMITTING IS A MASK EDIT, AND IT SHOULD GO THROUGH `mask_engine`. New label
ids must not collide with existing ones; an object overlapping an existing
object needs a rule (skip, replace, or clip to background) -- and the rule
should be a visible choice, not a hidden default. One click should be one
undo step.

COORDINATES. The box, the crop, the magnified view and the mask all live in
different coordinate systems; every commit should be tested for an off-by-one
at the crop edge and at the image border, where the region is clipped.

2026-09-14 -- A FIRST VERSION EXISTS, ON BRANCH wip/407-live-magnifier

WHAT IT DOES

  * A checkable "Magnifier" button in the tool row (beside Cellpose-SAM
    detect) and a "Live magnifier" card on the settings panel: Mode, Size
    (px), Zoom, Sensitivity, Overlap.
  * While on, a box follows the cursor: the region contrast-stretched on its
    own and drawn zoom x the canvas's display scale, with the pixel under
    the cursor kept under the cursor. The last completed result stays drawn
    where ITS region lies; the frame goes dashed with "Updating..." until
    the result for the current region arrives.
  * The wheel changes the magnifier's zoom (at the canvas's Zoom per notch)
    and not the view. Right-button sweep and Shift/Alt pan still work.
  * A click pastes the objects the box outlines into the mask through
    `mask_engine._paste_region_objects`: ids start one past the top id, one
    click is one undo step and one "magnifier" ledger entry. A click on a
    region not yet segmented PINS that request on the worker, so moving on
    cannot supersede it, and its objects go in when it arrives.
  * Committed objects are ordinary mask edits: they survive the toggle going
    off and a save. Moving to the next field without saving still discards
    them, exactly as it discards a brush stroke -- navigation was not changed.

DECISIONS TAKEN FOR THE FIRST VERSION -- THE OPEN QUESTIONS ABOVE STILL STAND

  * Modes on day one: classical and Cellpose. Classical is Otsu when the
    region is two clear populations and a noise floor (median + 4 robust
    deviations, after sigma-1 smoothing) otherwise, then a watershed; it is
    also what runs, with a status-line note, whenever a model cannot load.
    Cellpose uses the Cellpose-SAM card's model and diameter. Adding
    DINOCell or SAMCell is one function in `_MAGNIFIER_SEGMENTERS`.
  * A click commits ALL objects the box outlines. Objects touching an edge of
    the box that lies inside the image are not offered (the recrop rule: an
    object cut by the box is not that object); objects at the image border
    are.
  * Overlap is a visible choice, default Clip (keep only unlabelled pixels,
    largest piece). Skip and Replace are the other two.
  * Sensitivity reads the way the word does: higher accepts more. For
    Cellpose it is cellprob_threshold with the sign reversed.
  * Defaults: size 128 (32-512), zoom 2.0 (1-8), sensitivity 0 (-6..6).
    Nothing persists between sessions, like every other setting on the panel.
  * Zoom is for the eye only; the model sees the native-resolution crop.
    Whether upsampling helps a model was NOT measured.

WHAT EACH PART OF THE ANSWER DOES NOW

  1. KEPT. Under "Region under the mouse" (still the default) a left click
     adds every object the box outlines, one undo step, one "magnifier"
     ledger entry.
  2. "Exclude objects touching the box border", a checkbox on the Live
     magnifier card, ticked by default (the old behaviour). Unticked, an
     object the box's INNER edge cuts is offered and added as far as the box
     saw it. Objects at the IMAGE border are offered either way. Toggling it
     does not call the model again: the region worker keeps the model's last
     answer for the region and only re-filters it.
  3. "Segment: Whole image", a new row beside Mode. The chosen model runs ONCE
     on the entire field, on a second newest-only worker, with a busy bar and
     a Cancel button on the card. The box then draws its slice of those
     objects (the object under the cursor filled more strongly) with no model
     call per move.
       LEFT CLICK adds the one object whose label covers the clicked pixel,
       through the Overlap rule, as one undo step and a "magnifier" ledger
       entry with scope="image". A click on no object adds nothing and the
       status line says so.
       RIGHT CLICK removes the mask object under the click, whatever put it
       there, as its own undo step and a "delete" ledger entry with
       tool="magnifier". A right click on background changes nothing,
       records nothing, and says so.
       Changing a setting the model reads (Mode, Sensitivity, the Cellpose-SAM
       model and diameter, Bright, Min area) discards the whole-image objects
       at once, says so, and starts a new run. Size, Zoom and Overlap do not.

DECISIONS THAT HAD TO BE MADE

  * A whole-image click adds the WHOLE object, including any part outside
    the box: the whole image was segmented, so nothing cut it. The border
    checkbox is greyed out under Whole image for that reason.
  * A right click under Whole image removes one object at the press and does
    not sweep, so it removes exactly what was clicked.
  * A click before the run finishes adds nothing and is NOT pinned, unlike
    the region mode. A run can take minutes on a CPU, and an object going in
    long after the click would be a surprise.
  * Progress is an indeterminate busy bar. Neither classical nor Cellpose
    reports steps, and tiling the field to get real progress would cut
    objects at tile seams.
  * Cancel cannot interrupt a model call already running. It drops a waiting
    run and discards a running run's answer when it arrives. Moving the mouse
    does not restart a cancelled or failed run; a click or a setting change
    does.
  * A setting change restarts the run automatically. The worker keeps only
    the newest request, so a burst of changes costs at most one extra run.
  * Turning the magnifier off leaves a run going, so its objects are ready
    when it comes back on. Leaving Whole image for the region mode drops the
    run; objects already found are kept and offered again if nothing the
    model reads has changed.
  * A field change drops the whole-image objects and segments the new field
    when it loads. Coming back to a field segments it again.
  * Three existing captions became untrue and were reworded: the card
    subtitle, the Size tooltip and the Magnifier button tooltip. Their nine
    old reviewed records were retired (deleted, as the runtime lane requires).
  * "Magnifier added {n} object(s)" moved from an f-string to a tr() template
    so it is catalogued. It is shared by both modes.

       region  objects  clip                skip               replace
       128 px       10    0.4 ms (was 0.3)    0.3 (0.3)          0.3
       256 px       30    1.3 ms (was 7.2)    1.1 (1.2)          0.9
       512 px       60    5.2 ms (was 44.8)   4.4 (6.1)          3.6
      1024 px      200   29.3 ms (was 595)   22.2 (60.5)        17.4
      2048 px      500  117.9 ms (was 6085)  87.4 (821)         72.1

     It is counted once over the pixels now, in
     `mask_engine._surviving_region_objects`, which the paste calls and the
     box draws. The ids added are identical at every size above, and
     `test_the_overlap_rule_agrees_with_the_rule_it_replaced` runs the old
     rule written out object by object beside the new one over random
     regions, for all three rules and three Min areas. That guard earned its
     keep at once: the first version used `scipy.ndimage.label`, which labels
     connected runs of TRUE, so two touching objects became one piece; it
     failed on two pixels of one seed. `skimage.measure.label` labels
     connected runs of one VALUE, which is what a piece of an object is.

  4. THE OVERLAP PREVIEW, under Region under the mouse. The pixels the rule
     would take away keep a quarter of their alpha: solid is what a click
     adds, ghosted is what it does not. Nothing is computed under Replace,
     which takes nothing away, or over an empty mask. Changing the rule asks
     no model and does not discard the whole-image objects.
     IT IS BUILT ON THE WORKER, beside the outlines, since 2026-09-20 -- the
     first version ghosted inside paintEvent. See the second note of that
     date.

  5. AN ETA ON THE BUSY BAR, from a measurement and only from one: the
     seconds per megapixel the last run under this mode and model took. The
     FIRST run of a session promises nothing and the bar stays indeterminate,
     which is honest and also right -- on a cold model most of a first run is
     the load, measured here on 2026-09-15 at 10.3 s against 3.9 s for the
     same field with the model cached. An estimate that runs out goes back to
     indeterminate rather than counting past zero.

  6. A PER-FIELD CACHE OF THE WHOLE-IMAGE OBJECTS. Leaving a field and coming
     back re-ran the model: 3.7-10.3 s on the RTX 3090 by this item's own
     measurement, minutes on a CPU, and a curator walking a plate goes back
     and forth. A finished answer is kept under the FIELD and every setting a
     model reads, so a settings change still discards it. The field could not
     be named before -- a run key opens with a generation counter that counts
     LOADS -- so `set_field` names it by the image file's path. What is kept
     is bounded by `memory_budget.what_to_drop`, the policy every other cache
     in the application is trimmed by: the user's idle timeout releases a
     field nobody went back to, and the ceiling is the lower of the user's
     cache ceiling and 256 MB.

Decided: the maintainer asked on 2026-09-19 for both feature lists to be
finished; this pass is the review of the note above, applied. Nothing here
changes what was asked for -- it fixes what the last pass got wrong, and
measures the one thing it had measured in the only case where the answer is
free. Same branch, home/407-magnifier-polish, rebased onto origin/nightly.

1. THE HARNESS WAS WRITING TO THE MAINTAINER'S OWN SETTINGS. `measure_
   magnifier` drives a real Make Masks screen, and opening a folder is
   remembered: `_open_folder` ends in `prefs.push_recent_source`, which
   writes $HOME/.config/spacr/qt.conf. The row runs by default and the tool
   documents itself as `python tools/perf_paint.py`, so a run by hand put the
   harness's own TemporaryDirectory at the head of the recent-folder list and
   left `last` pointing at a path that had already been deleted. Every
   measurement now runs inside `_settings_elsewhere`, which points QSettings
   at a throwaway folder and puts each format's location back afterwards --
   reversible rather than an env var, so a harness called from a test session
   leaves that session's sandbox where it found it.
   `test_the_magnifier_row_leaves_the_users_own_settings_alone` pins it, and
   was calibrated the way this harness's other tests are: with the isolation
   neutered it fails.

2. THE BOX'S PROMISE IS BUILT ON THE WORKER NOW. The ghost -- the rule's
   answer, drawn as faded pixels -- was computed inside paintEvent, over the
   box's pixels, per delivered result. The rule is the same one whose cost is
   in the table above: 125.5 ms at 2,048 px under Clip, on the GUI thread,
   while the mouse moves. It is `_ghosted_overlay` on the region worker now,
   beside the outlines it fades; the mask crop it needs travels in the
   request, as the image crop always has, and one QImage is still built per
   result because the ghost IS the picture rather than a layer over it.
   A rule change or an edit to the mask under the box makes that promise
   stale: the request carries the rule and a mask generation number, the box
   notices when it is drawn, the frame goes dashed -- the vocabulary it
   already had for "not up to date" -- and the region is asked for again. The
   model is not: the worker keeps its last raw answer for the same box and
   settings. A drag's frames ask for no ghost at all, since nobody draws
   them.

3. THE HARNESS COULD NOT SEE ANY OF THAT, which is why the last note could
   say "no budget breach" and be wrong. It wrote one field and no mask file,
   so `load_image_and_mask` made a mask of zeros, so the rule had nothing to
   take away and the preview never ran in any harness run; and it measured
   one box size, 128 px, when item 417's whole point was that the Size box
   goes as high as the field is wide. The field is opened with half of every
   object already painted in now, and the largest box is a row of its own.
   Measured, 2048 px field, 40 moves, load 11, Otsu, Clip, ghost built:

     box      before this note              after
     128 px   median  6.7 ms  worst  12.1   median  3.9 ms  worst   8.8
     2048 px  median 183.9 ms  worst 391.2   median 53.4 ms  worst 110.9
                          23 frames dropped               6 frames dropped

4. WHAT THE 2,048 px ROW ACTUALLY WAS, and it was not the ghost. The box is
   not bounded by the window: its side is the Size box's value in IMAGE
   pixels and the lens draws it `zoom` times larger again, so on that field
   most of the lens is off the widget -- and every pixel of the box was being
   percentile-stretched, blended with the mask and handed to Qt on every
   move. `_visible_part` cuts that to the part of the box that is on the
   canvas, and `_stretch_for_box` splits "read the levels" from "rescale
   these pixels": the levels still come from the WHOLE region the box
   magnifies, from at most 262,144 of its pixels on a grid, so the box does
   not change contrast as it slides off the canvas edge. At a box the window
   holds, every pixel is sampled and every pixel is returned and the answer
   is `normalize_uint16`'s to the byte --
   `test_a_box_that_fits_is_stretched_exactly_as_it_always_was`.

5. STILL OVER BUDGET AT THE LARGEST BOX, and this is the honest end of it.
   53.4 ms is three frames, not one. Profiled at 2,048 px, per move, the
   remainder is `mask_engine.overlay_mask` over the 1.4 Mpx of box that IS on
   the canvas: 41.5 ms of float passes over 4.2 M elements, against 6.8 ms
   for the stretch, 0.4 ms for the model's crop copy and 0.2 ms for the mask
   crop. A magnifier set to the width of the field is the whole window, and
   rendering a megapixel per mouse move is what that means. THE FIX IS NAMED
   AND NOT DONE: at that size the box is CONSTANT -- `_magnifier_box` clips
   to the field for every cursor -- so the picture could be built once per
   (box, mask, levels) and every later move would be a clipped blit of a
   sub-rectangle instead of a re-render. It is left out of this pass because
   the miss that builds it is a 150 ms frame of its own and choosing when to
   pay it is a design question, not a patch.

6. THE ETA NO LONGER LEARNS ITS PACE FROM THE RUN THAT LOADED THE MODEL.
   `_note_pace` kept whichever run finished first under a (mode, model), and
   on a model that loads, that is the cold one: 10.3 s against 3.9 s for the
   same field, this item's own measurement. The second run of a session --
   the first one that shows a countdown -- therefore counted down from an
   estimate about 2.6x too long and finished while the bar still promised
   seconds. A mode that loads a model now spends its first measurement
   learning that the model is in memory; the bar stays indeterminate through
   the second run and counts down from the third. The Otsu mode loads
   nothing, so its first run is still its pace.

7. `_tick_magnifier_eta` reached into `_magnifier._image_estimate` for the
   other half of an answer it had just been given publicly.
   `estimated_seconds()` is beside `remaining_seconds()` now.
