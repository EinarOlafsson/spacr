--------------------------------------------------------------------------------
DOES IT MAKE SENSE? YES FOR THE PIPELINE, PARTLY FOR THE GUI
--------------------------------------------------------------------------------

WORTH DOING. The headless half of spaCR is exactly what containers are for:

  - The install is heavy and version-sensitive -- torch, CUDA, cellpose,
    PyQt6, and now optional SAMCell and DINOCell backends that each pin their
    own torch. "It works on my machine" is a real cost here, and the install
    is the single most common thing to go wrong for a new user.
  - A reviewer re-running an analysis a year from now needs the environment,
    not just the code. An image tagged with the spaCR version is a far better
    answer than a requirements file.
  - Cluster and cloud runs want an image, not a conda environment.

LESS CLEARLY WORTH DOING. The GUI. spaCR is a Qt desktop application, and a
containerised Qt app needs the host's display socket passed in (X11 or
Wayland), which works on Linux, is awkward on macOS, and is a support burden
out of proportion to the benefit. The GUI is not the part users struggle to
install -- the CUDA stack is.

SO: build the image for the CLI and the pipeline, treat GUI-in-a-container as
a documented extra for Linux users who want it, and do not promise it works
everywhere.

--------------------------------------------------------------------------------
SHAPE
--------------------------------------------------------------------------------

  - Base on an official CUDA runtime image matching the torch build, not on a
    bare python image with pip-installed CUDA wheels of unknown provenance.
  - Two tags at least: one CPU-only (small, works anywhere, for testing and
    for the measure/regression half that does not need a GPU) and one CUDA.
  - Models are NOT baked in. A cpsam checkpoint is ~1.2 GB and the Model Zoo
    exists to fetch them; baking them makes the image enormous and stale. Mount
    a models directory instead, and let the zoo's download folder point at it.
  - Data is mounted, never copied in.
  - Run as a non-root user with a matching UID, or every output file the
    container writes will be owned by root on the host. This is the single
    most common complaint about scientific Docker images.
  - Build it in CI on a tag, publish to a registry, and test that `spacr
    --version` and one small pipeline run work in the built image before it is
    pushed.

--------------------------------------------------------------------------------
OPEN QUESTIONS -- ANSWER BEFORE BUILDING
--------------------------------------------------------------------------------

  - Which CUDA version is the floor? The box this was written on runs CUDA 13
    with torch 2.13; the image has to serve users on older drivers, and the
    driver is on the HOST and cannot be containerised away.
  - Do the optional backends (SAMCell, DINOCell) go in the image, or stay an
    install step inside a running container? They conflict on torch, which is
    an argument for separate tags rather than one image with everything.
  - Where does the measurements database live -- mounted, or in a volume?
  - Is the image published to Docker Hub, GHCR, or both, and who owns the
    namespace?
  - Does conda-forge packaging (already done) cover enough of this need that
    the image is only worth it for cluster users?

WHY IT IS FILED RATHER THAN BUILT
--------------------------------------------------------------------------------

2026-09-19 -- BUILT. TWO TAGS, MOUNTED MODELS, NON-ROOT, SMOKE-TESTED BEFORE PUSH
--------------------------------------------------------------------------------

Decided: Einar Olafsson, 2026-09-19, through the question prompt -- "Yes, as
recommended": a CLI and pipeline image, GUI-in-a-container documented as a
Linux-only extra, two tags (CPU and CUDA 12.4, host driver 550+), SAMCell and
DINOCell NOT in the image, models and data mounted rather than baked, a
non-root user with a matching UID, built and smoke-tested in CI on each
release tag (`spacr --version` and one small pipeline run in the built image)
and published to GHCR under the repository owner.

EVERY OPEN QUESTION ABOVE IS NOW ANSWERED:

  Which CUDA version is the floor?   12.4, host driver 550 or newer. The
                                     driver is on the host and cannot be
                                     containerised away, so the floor is the
                                     promise and the Dockerfile says so.
  SAMCell / DINOCell in the image?   No. They pin PyTorch versions that
                                     conflict with spaCR's and with each
                                     other. The Model Zoo's isolated-
                                     environment install (423) is the answer
                                     inside a running container.
  Where does the database live?      Mounted. Nothing is baked in and no
                                     volume is declared -- a VOLUME line
                                     creates anonymous volumes nobody
                                     collects.
  Docker Hub, GHCR, or both?         GHCR, under the repository owner:
                                     ghcr.io/einarolafsson/spacr.
  Does conda-forge cover it?         No. conda-forge answers "install spaCR
                                     into an environment I control"; the
                                     image answers "run spaCR on a node I do
                                     not control, identically, in five years".

MEASURED, on this box, 2026-09-19 (Docker 29.1.3, legacy builder, no buildx)

  BUILD. `docker build -f packaging/docker/Dockerfile.cpu .` from the
  checkout: 20 minutes, almost all of it downloading wheels. Final image
  4.0 GB, of which the virtualenv is 3.6 GB.

  THE THREE RELEASE CHECKS, run inside the built image:

    docker run --rm IMG spacr --version            -> 1.5.0.8
    docker run --rm IMG id                         -> uid=1000(spacr)
    docker run --rm IMG python3 /opt/spacr/smoke_pipeline.py
                                                   -> 7/7 checks passed

  The pipeline check is a real run: external_masks on a 32x32 synthetic
  field with a cell and a nucleus mask, writing merged/*.npy and a
  measurements.db holding cell, cytoplasm, intensity_rescale, nucleus,
  png_list, run_status, settings and settings_history, with one measured
  object in `cell` and one in `nucleus`.

  A FOREIGN UID WORKS. `--user 4242:4242` gets HOME=/ from Docker, which it
  cannot write to; the entrypoint says so on stderr, relocates HOME to
  /tmp/spacr-home-4242 and `spacr --version` answers normally.

  /models IS WIRED TO BOTH READERS, and that is not a detail. Cellpose reads
  CELLPOSE_LOCAL_MODELS_PATH. spacr/model_zoo.py resolves
  Path.home()/".cellpose"/"models" and Path.home()/".spacr"/"models"
  DIRECTLY (default_local_roots, and again in the stock-model listing), which
  no environment variable reaches. Setting only the variable would have left
  the zoo listing an empty folder and looked like it worked. With a folder
  mounted on /models, inside the container:

    zoo roots:          ['/home/spacr/.cellpose/models',
                         '/home/spacr/.spacr/models']
    cellpose MODEL_DIR: /models
    and the file put on the host is visible through the zoo root.

  THE BYTECODE HAD TO BE PUT BACK, and the first build is why this is
  written down. It ended with `find $VENV -name '*.pyc' -delete`, which
  looked like housekeeping and is not: /opt/spacr/venv is root-owned and the
  process runs as `spacr`, so a container that starts without .pyc files
  recompiles what it imports on EVERY run and can never keep the result.
  A/B inside one container, compiling in place between the two halves:

    import spacr.measure, torch, cellpose   no .pyc   6224 / 6030 / 6346 ms
                                            .pyc      3084 / 3075 / 3110 ms
    spacr-run --list                        no .pyc          510 ms
                                            .pyc             278 ms

  Confirmed on the rebuilt image: 18,068 .pyc, 3255-3455 ms, 278 ms. The
  cost is 0.4 GB (3.61 GB -> 4.0 GB), which is 11% of the image for half the
  start-up of every run. pip compiles on install whatever
  PYTHONDONTWRITEBYTECODE says -- measured separately in a throwaway
  container, 493 .pyc either way -- so the deletion, not the variable, was
  the whole of the defect.

  ONE NVIDIA WHEEL IS IN THE CPU IMAGE AND IT IS NOT A LEAK. `xgboost`
  declares `nvidia-nccl-cu13` (252 MB) on Linux x86-64. torch is clean: the
  build log records `torch 2.14.0+cpu` already satisfied when spaCR
  installs, which is the CPU index doing its job. The separate `xgboost-cpu`
  distribution would drop it and would also stop the image satisfying
  `xgboost>=2.0.3,<4` as setup.py declares it; an image whose dependency set
  quietly differs from the package is the worse problem.

  THE CUDA IMAGE'S PACKAGE LISTS WERE CHECKED WITHOUT BUILDING IT. An
  `apt-get install --dry-run` of every name in Dockerfile.cuda, run in a
  plain ubuntu:22.04 container with the deadsnakes PPA added, resolves all
  of them and offers python3.12 at 3.12.13-1+jammy1. That is not a build,
  and it is not claimed as one.

  THE PROVING BUILD was run from these files. The only edits after it are
  prose in packaging/docker/README.md and in this file, neither of which is
  copied into the image.

  /models IS WIRED TO BOTH READERS, and that is not a detail. Cellpose reads
  CELLPOSE_LOCAL_MODELS_PATH. spacr/model_zoo.py resolves
  Path.home()/".cellpose"/"models" and Path.home()/".spacr"/"models"
  DIRECTLY (default_local_roots, and again in the stock-model listing), which
  no environment variable reaches. Setting only the variable would have left
  the zoo listing an empty folder and looked like it worked.

  NO BuildKit FEATURE IS USED. The first attempt used
  `RUN --mount=type=cache` and `# syntax=docker/dockerfile:1`; the Docker on
  this box has no buildx component, and the legacy builder FAILS on the
  directive rather than ignoring it ("unknown flag: --progress" was the same
  lesson arriving first). Two tags that only build on some installations of
  Docker is not a Docker image, so both Dockerfiles are plain and pip runs
  with --no-cache-dir.

WHAT IS LEFT

  1. The CUDA image has never been built. Its apt lists are dry-run clean on
     jammy (above), but nothing has resolved its Python dependency set or run
     a line of code in it. The first release tag builds it in CI, and
     gpu_queue/425-docker-1.md is the job that would build it here and ask
     the card the one question CI cannot.
  2. The workflow has never run. Nothing was pushed to GHCR by this work and
     nothing should be until a release tag reaches it.
  3. GHCR CREATES A NEW PACKAGE PRIVATE. After the first successful release
     the owner has to flip
     https://github.com/users/EinarOlafsson/packages/container/spacr/settings
     to public, once. No workflow permission does this.
  4. A GPU run in the CUDA image is unproven by construction: a hosted runner
     has no GPU, so CI proves the CUDA image is a working CPU install and
     nothing more. `docker run --gpus all ... spacr-doctor` on a real card is
     the check, and it needs a machine with one.

WHY IT MOVES TO features/new ONLY AFTER A GREEN TAGGED BUILD. Points 1 and 2
are not writing; they are one release away. Moving the file now would record a
publishing pipeline as finished before it had ever published anything, which
is exactly the shape HANDOFF section 0a is about.
