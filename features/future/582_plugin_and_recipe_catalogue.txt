A PLUGIN AND RECIPE CATALOGUE BROWSER

Status: IMPLEMENTED AS ALPHA 2026-09-27.
Owner: unassigned. From the 2026-09-26 non-GPU list. Ships as an ALPHA feature (features/README.md, item 569): hidden unless Preferences -> Show alpha features is on.

REQUEST (the maintainer, 2026-09-26, verbatim)
    "Also add to future features list the items in the non GPU list that would be valuable!"

EVIDENCE
    No image.sc thread; from general practice.

WHAT TO BUILD
    Browse, install and update community plugins and assay templates
    (recipes) from a catalogue, napari-hub style, built on spaCR's plugin
    SDK, with versions, authors and licences shown and installs isolated
    where plugins need their own dependencies.

DONE WHEN
    A test catalogue lists plugins and recipes; one installs, loads and
    uninstalls cleanly.

ALPHA: 2026-09-27. The Preferences "Plugins" tab is built only with Show alpha
features on (ALPHA_FEATURES[582]: PluginCatalogueHelp, PluginCatalogueSource,
PluginCatalogueLoad, PluginCatalogueTable, PluginCatalogueInstall,
PluginCatalogueUninstall, PluginCatalogueStatus). The command line and the
plugin loader never consult the gate: a catalogue plugin installed while the
tab is hidden still loads.

WHAT WAS BUILT (2026-09-27)
    spacr/plugins.py (private helpers):
      _read_catalogue / _catalogue_rows - a catalogue is JSON ("plugins" and
        "recipes" lists; key, name, version, author, licence, summary,
        homepage, source, entry, api_version, requirements, app, settings,
        sha256), read from a file, its folder or an http(s) address, or
        $SPACR_PLUGIN_CATALOGUE. Rows carry installed version and status
        (available / installed / update available / incompatible SDK).
      _install_from_catalogue - a plugin is pip-installed --no-deps into
        its own folder under ~/.spacr/plugins/site/<key> ($SPACR_PLUGIN_HOME),
        its declared requirements into the same folder; the folder is appended
        to sys.path, so spaCR's own packages always win and are never upgraded.
        Installed into a staging folder, loaded and validated there, then
        swapped in: a failed install or update keeps the previous version.
        Local catalogues install offline (--no-index --find-links). Optional
        sha256 is checked. A recipe is written to recipes/<key>.json, a file
        spacr.cli.load_settings_file and the settings loaders read.
      _uninstall_from_catalogue - removes the folder or file, drops its
        modules from sys.modules and reloads the registry.
      Discovery (_installed_sources) also yields catalogue installs recorded
        in <home>/installed.json.
    spacr-plugins: new catalogue, install <key>, update <key>, uninstall <key>
      commands, with --catalogue and --json.
    Preferences > Plugins tab (alpha): catalogue field, table with type,
      name, version, installed, status, author, licence (summary as tooltip),
      Install or update and Uninstall buttons.
    Tests: tests/test_plugin_catalogue.py (a real wheel built on the spot,
      installed by pip offline, loaded, updated, uninstalled; failed update
      rollback; checksum and SDK refusal; CLI) and
      tests/qt/test_plugin_catalogue_alpha_gate.py.

WHAT IS LEFT
    - Plugins needing conflicting dependency versions still share spaCR's
      interpreter; running such a plugin's apps in a separate environment
      (as _segmentation_backends does) is not built.
    - No hosted community catalogue exists yet; the maintainer has to publish
      one (and decide on signing beyond the optional sha256).
    - Background catalogue installation is implemented in the 2026-10-01
      follow-up below; focused verification passed.
    - The recipe Open action and its focused runtime verification are
      complete (see the dated note below).

2026-09-27 — INSTALLED RECIPE OPEN ACTION (focused verification passed)
    Preferences > Plugins now offers Open for installed recipes. It reads
    the installed registry's module and settings file, not a newer offered

    The existing settings loader applies the values without starting a run;

2026-10-01 — BACKGROUND CATALOGUE MUTATIONS
    Install/update and uninstall run in a non-daemon Python worker with no Qt
    objects. Preferences polls the result and updates widgets on the GUI thread;
    controls stay disabled during work and reuse the existing Working caption.
    Closing or destroying the dialog leaves the requested operation running,
    without destroying a live QThread or updating deleted controls. Interpreter
    exit waits for the operation rather than abandoning a partially written
    install. Catalogue refresh after a mutation also runs off the GUI thread;
    a refresh failure is distinguished from a failed installation.

    A dedicated reentrant mutation lock serializes installs, removals and
    registry reloads. The registry lock protects only reading and publishing
    snapshots, so existing app/model/report lookups remain available while pip
    or discovery is busy. The previous complete snapshot remains published
    until its replacement is ready. Existing staging and failed-update behavior
    is preserved. No new public API or captions are introduced.

    Scope boundary: conflicting dependency isolation, hosted catalogue
    publication and signing policy remain
    open. This follow-up does not claim the full feature is complete.

    Validation (CPU, one thread, 1 GB cap): the six named catalogue/plugin
    test files first produced 144 passes and one existing test that still
    assumed synchronous uninstall. After changing that assertion to wait for
    observable completion, the corrected case passed separately (1.29 s);
    production code was unchanged. All seven new cases passed, covering
    registry reads during blocked pip/discovery, mutation serialization, failed
    staging cleanup, event-loop responsiveness, dialog destruction, worker
    errors, and committed install/uninstall state after catalogue refresh fails.
    An attempted combined rerun ended after 90 passes at the test guard's
    0.9 GB ceiling (exit 3), not a completed suite result. Existing real offline
    wheel install/update/uninstall, failed-update rollback, alpha visibility
    and installed-recipe Open cases passed in the first run. Backend and new
    tests pass Ruff; edited legacy UI files introduce no additional findings.

2026-10-01 — BACKGROUND CATALOGUE LISTING FOLLOW-UP
    Initial listing when Preferences opens and explicit List/refresh now use
    the same Qt-independent worker. The request snapshots its source, clears
    the previous rows and disables conflicting actions while it runs. Only
    the GUI timer renders the completed snapshot. If the source changed
    programmatically, neither stale results nor stale errors are applied.
    A destroyed dialog also destroys its timer while the read finishes safely
    without touching widgets. Read failures clear stale rows and show the
    actual catalogue error; existing translated captions are reused.

    Validation: 17 focused Qt tests passed in 10.44 seconds under a 1 GB,
    single-thread CPU cap. These cover blocked initial/explicit fetches with
    a live GUI heartbeat, dialog destruction, stale success/error rejection,
    failed loads, the preceding mutation-worker cases, alpha gating, real
    offline installation/uninstallation and installed-recipe Open behavior.
    Backend and public API contracts are unchanged. Hosted publication,
    signing policy and conflicting-dependency isolation remain out of scope.
