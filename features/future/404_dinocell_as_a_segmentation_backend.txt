--------------------------------------------------------------------------------
WHAT DINOCELL IS, READ FROM THE REPOSITORY 2026-09-14
--------------------------------------------------------------------------------

An automated cell-segmentation model for LIVE CELL microscopy. A DINOv2 ViT
encoder pretrained on 1.2B images, domain-adapted on 130k unlabelled cell
images. MIT licence. `pip install dinocell`. A Python entry point
`segment(img_path)` returning `output_segmentations`, and a CLI
`dinocell segment image.png --output results/`.

THE DETAIL THAT MAKES THIS CHEAP RATHER THAN A REWRITE: it predicts
CELLPOSE-STYLE FLOWS rather than binary masks. spaCR's whole mask path already
consumes Cellpose flows, so a backend that emits them plugs into what exists
instead of needing a second post-processing pipeline beside it.

Its README claims it outperforms Cellpose-SAM and SAMCell on both held-out
test sets and zero-shot cross-dataset evaluation, and claims zero-shot
generalisation to novel cell types and microscopes. THOSE ARE ITS CLAIMS AND
NOT MEASUREMENTS OF OURS -- see below.

NOT STATED IN THE REPOSITORY and needing a look before anyone builds: the
image modality it expects, channel count, whether it is 2-D only, and where
its checkpoints come from. The README does not say.

--------------------------------------------------------------------------------
WHY IT IS WORTH HAVING
--------------------------------------------------------------------------------

Every model in the zoo today is Cellpose or a YOLO detector, and all three
entries are Toxoplasma-specific (`toxoplasma_pv_v1`, `toxoplasma_plaque_v1`,
`toxoplasma_well_detector_v1`). A model whose selling point is zero-shot
generalisation to cell types it has not seen is the opposite of that, and is
what a user with an unfamiliar assay actually needs on day one.

Live-cell microscopy is also exactly where spaCR is weakest: the Cellpose
models in the zoo are trained on fluorescence, and timelapse work is often
label-free.

--------------------------------------------------------------------------------
WHAT TO BUILD
--------------------------------------------------------------------------------

  * A `kind` FOR IT IN THE MODEL ZOO. `ModelEntry.kind` is already the
    discriminator -- 'cellpose' and 'detector' both exist -- so this is an
    addition to an existing mechanism rather than a new one. If its flows are
    genuinely Cellpose-shaped it may not even need a separate mask path.
  * AN OPTIONAL DEPENDENCY, not a core one. `dinocell` pulls a ViT and its
    weights; a user who never opens it must not pay for it. spaCR's
    lazy-import discipline (item 282) is the standard to meet, and
    `tests/test_perf_guard.py` is what enforces it.
  * A SCORECARD BEFORE A RECOMMENDATION. `spacr/scorecard.py` exists and
    scores a segmentation against ground truth with Dice, IoU, boundary F1
    and AUPRC. Item 370 asks that every published model carry one. A vendor's
    benchmark is not evidence about a user's images, and the whole point of
    370 is that the comparison is run on OUR held-out set, not quoted.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

DINOCell segments a spaCR project end to end through the ordinary Mask path,
with no import of `dinocell` in a process that does not use it -- proved the
way 282 proves it, by asserting the module is absent from `sys.modules` after
the Qt launch path. And a scorecard on THE SET 370 AUTHORISED -- with
`toxoplasma_pv_v1` re-scored on that same set in the same run, because the
published 0.867 was measured on something else and two numbers from two sets
are not a comparison.

NOT BLOCKED ANY MORE, as of 2026-09-14. 370 asked whether a labelled held-out
set existed and the maintainer answered "Label a new set for the purpose", so
the set is authorised and its requirements are written down in 370's last
section -- including that it be WIDER THAN TOXOPLASMA, which exists because of
this item and 405. Read that before scoring anything.

The order is unchanged and still matters: the INTEGRATION can land before a
single field is labelled, the RECOMMENDATION cannot. "DINOCell generalises
zero-shot" is the vendor's claim, and until it is measured on our set it stays
the vendor's claim in this file's own words.

BUILD IT WITH 405, NOT AFTER IT. Both were approved in one sentence and both
extend `ModelEntry.kind`. DINOCell emits Cellpose-style flows and may need no
new mask path at all; SAMCell emits masks through its own pipeline and is the
one that decides whether a second path is needed. Settle THAT question once,
across both, before writing either -- two backends added a month apart is how
one mechanism becomes two.

2026-09-19 — RUN FOR REAL: THE ENVIRONMENT, THE FIELD, AND WHERE THE 383 MB WENT
--------------------------------------------------------------------------------

Decided: "Isolated env per backend! But with the addition of adding cellpose
3 and its cyto, nucleus, and cyto2 and cyto3 models. The cellpose 3 backend
will allow more models from the biomass.io to be added to the model zoo."
-- the maintainer, 2026-09-19, answering item 423's open questions.
("biomass.io" is bioimage.io.) 423 built that machinery and said plainly in
its own Left list that "DINOCell and SAMCell have never been installed for
real: their install plans and adapters are exercised with stand-ins only".
This note is DINOCell's half of that, done.

WHAT WAS RUN, in a sandboxed HOME with SPACR_BACKENDS_DIR under the
scratchpad, on the CPU, against the real packages on PyPI. Nothing of the
maintainer's configuration, cache or data was written to; the one real plate
field named below was read for its dimensions and nothing else.

  1. spaCR's own installer, `_install_backend('dinocell')`, built the
     environment: 541.2 s and 1,797,510,073 bytes. It picked spaCR's own
     Python 3.12.13 (inside DINOCell's 3.11-to-3.14 range) and installed
     dinocell 0.74, torch 2.10.0+cpu, torchvision 0.25.0, numpy 2.4.3 and
     cellpose 4.0.9. The self-test loaded the package and the marker was
     written; the row read "installed".

     SPACR_BACKEND_TORCH_INDEX was set to the CPU wheel index to keep the
     download small. Left alone on this machine it would have been PyPI's
     CUDA build, which is the GPU job below.

  2. `generate_cellpose_masks_sam` with segmentation_backend='dinocell' on a
     256 x 256 field of nine discs: 9 of 9 objects, mask uint16 at the
     field's own shape, `object_counts` row
     ("plate1_A01_1.npy", "cell_before_filtration", 9). 180.7 s cold --
     the 383 MB checkpoint download, the interpreter start and the ViT load
     -- and 15.7 s for a second field in the same worker. THE 15.7 s IS THE
     SEGMENTATION; the rest happens once per worker, which is why the worker
     is kept alive between fields.

     spaCR's own Cellpose 4 was never constructed: the run held a
     `CellposeModel` that raises if anything builds it, and nothing did.

  3. Uninstall: the environment and everything in it gone, the row back to
     "installable".

THE FLOWS DO REACH THE MASK PATH, which is this item's whole architectural
claim ("it predicts CELLPOSE-STYLE FLOWS rather than binary masks... a
backend that emits them plugs into what exists"). The adapter returns
Cellpose's own `(masks, flows, styles)` triple, `parse_cellpose4_output` read
it unchanged, and merge/split/filter, the object-count database and the save
all ran as they do for Cellpose. Confirmed against dinocell 0.74's own
source: `FlowsPredictionHead` returns [dx, dy, sigmoid(cell probability)] at
the 512 crop, and spaCR stacks them (dy, dx) for `compute_masks` exactly as
DINOCell's `cells_from_flows` does.

TWO THINGS THE REAL RUN FOUND THAT THE STAND-INS COULD NOT

  * THE 383 MB CHECKPOINT WAS LANDING IN THE PERSON'S OWN CACHE. DINOCell
    fetches `KadenStillwagon/DINOCell` with `hf_hub_download`, which writes
    to ~/.cache/huggingface unless HF_HOME says otherwise. Measured: a run
    put 402,337,098 bytes there and nothing inside the environment. That
    breaks two of 423's promises at once -- "Uninstall deletes the
    environment and everything downloaded into it", and a preflight that
    refuses an install when the BACKENDS FOLDER has less than the spec's
    3 GB free while the weights go to a different filesystem.
    `_worker_env` now sets HF_HOME inside the environment, the way Cellpose
    3's CELLPOSE_LOCAL_MODELS_PATH already was. Measured after: the same
    402,337,098 bytes inside the environment, 0 in the user cache, and
    Uninstall took both. The environment with its checkpoint is
    2,199,847,171 bytes, under the 3 GB the row claims.

    AND HF_HOME ALONE WAS NOT ENOUGH -- caught in review, fixed the same
    day. `_clean_env` forwards the whole inherited environment, and
    huggingface_hub reads HF_HUB_CACHE from it BEFORE deriving anything
    from HF_HOME: HF_HUB_CACHE falls back to the legacy
    HUGGINGFACE_HUB_CACHE, which falls back to $HF_HOME/hub. Measured
    against huggingface_hub 0.36.2 on 2026-09-19: with HF_HOME inside the
    environment and HF_HUB_CACHE=/mnt/elsewhere/hf, constants.HF_HUB_CACHE
    is /mnt/elsewhere/hf; the legacy name alone does the same. So the one
    person the redirect is FOR -- whoever moved their Hugging Face cache
    off a full home disk -- was the one person it missed. `_worker_env`
    now drops `_HF_CACHE_VARIABLES` (both hub names, both assets names,
    the xet cache) beside setting HF_HOME, and
    `test_a_relocated_hugging_face_cache_does_not_win_over_the_environment`
    exports all five and fails if any survives. Proved by reverting the
    drop: the test then names all five.

    SAMCell IS NOT CHANGED HERE -- it is item 405's, and 405 should measure
    it rather than inherit an untested line -- but 405 should know that
    TORCH_HOME alone will not finish it. SAMCell downloads TWO models, not
    one: `samcell-generalist.pt` through torch.hub (TORCH_HOME moves it;
    375,043,010 bytes in ~/.cache/torch on this machine), and, because
    `_SamCellBackend` builds `FinetunedSAM(_SAMCELL_BASE_MODEL)` and
    samcell's FinetunedSAM is `SamModel.from_pretrained(...)`,
    facebook/sam-vit-base through transformers into the SAME Hugging Face
    cache DINOCell's checkpoint was just moved out of (374,986,732 bytes in
    ~/.cache/huggingface on this machine). About 750 MB across two caches;
    setting only TORCH_HOME would move half of it and read as finished.
    Both numbers are `du -sb` on existing caches, not estimates, and
    neither has been measured through an isolated environment.

  * THE SELF-TEST DID NOT IMPORT WHAT THE ADAPTER IMPORTS. 423 learned this
    with Cellpose 3 and `packaging` and fixed that one instance; DINOCell
    had a second waiting. The adapter calls `cellpose.plot.dx_to_circ` to
    build the flow image, and `cellpose.plot` was not in its probe, so an
    environment missing it would have passed the install and failed on the
    first field. Added, and the lesson is now a ratchet rather than a habit:
    `test_every_module_an_adapter_imports_is_in_its_self_test` parses each
    adapter's own source and fails when a module it imports is absent from
    its probe. Run against the probe as it was, it names `cellpose.plot`
    exactly; torch and numpy are exempt and the test says why.
