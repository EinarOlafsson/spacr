================================================================================
A SEARCH FIELD BESIDE THE HELP DROPDOWN
================================================================================

Status:    NOT STARTED. Filed 2026-09-18 from a spoken specification, with the
           explicit instruction not to implement it. Nothing below has been
           built or prototyped.

Shape:     A search box beside the Help dropdown. The user types the name of a
           module, a function, a setting or a preference and gets a list of
           clickable results. What a result DOES when clicked depends on what
           kind of thing it is -- that is the whole feature.

--------------------------------------------------------------------------------
WHAT IT IS FOR
--------------------------------------------------------------------------------

spaCR has a large surface: modules, functions, hundreds of settings across
collapsible categories, and a preferences tab. A user who knows the NAME of the
thing they want has no way to get to it. They currently have to know which
module owns a setting and which category it sits under, which is knowledge the
GUI should supply rather than demand.

--------------------------------------------------------------------------------
RESULT KINDS AND WHAT A CLICK DOES
--------------------------------------------------------------------------------

The list is mixed: one query can return several kinds at once, and each kind
has its own click behaviour.

  API REFERENCE ENTRY
      Opens the API entry in a browser.

  MODULE
      Opens that module in the GUI.

  SETTING
      This is the interesting one, and it returns TWO kinds of result for the
      same query:
        - a link to the API entry of each function that takes that setting, and
        - an item that opens each module which exposes that setting.
      When it opens a module, it should open with ALL setting categories
      COLLAPSED EXCEPT the category containing the setting searched for, with
      that setting visible. Dumping the user into a fully expanded settings
      panel and leaving them to find the row is the failure mode this exists to
      prevent.

  PREFERENCE
      Opens the Preferences tab, scrolled or focused to the preference searched
      for.

  "AND SO ON"
      The specification explicitly leaves the list open. Whatever else is
      addressable by name should be reachable the same way. Adding a kind
      should mean registering a provider, not editing a switch statement.

--------------------------------------------------------------------------------
THE PART THAT WILL DECIDE WHETHER THIS IS GOOD
--------------------------------------------------------------------------------

The index. Every kind above needs a name-to-destination map, and a map that is
hand-maintained will drift the first time a setting is renamed, at which point
the search box sends users to the wrong place -- worse than not having it,
because a search result is believed.

So the index should be GENERATED from what already exists: the settings spec,
the module registry, the API doc build, the preferences schema. If a setting
cannot be found by search, that should be a fact about the generator, not about
whether somebody remembered to add a row.

--------------------------------------------------------------------------------
OPEN QUESTIONS -- ANSWER BEFORE BUILDING
--------------------------------------------------------------------------------

  - Is matching exact, prefix, fuzzy, or full-text over descriptions too? A
    user who does not know the exact name is the user who needs this most.
  - One setting can appear in several modules. Does the result list show one
    row per module, or one row that then asks which?
  - What happens when the API reference is not reachable -- offline, or an
    older build whose docs are not published? A dead link is worse than a
    result that says the page is not available locally.
  - Does opening a module discard unsaved settings in the module currently
    open? A search box that silently loses work will be used once.
  - Does the search box also search values -- a user looking for the module
    where `cell_diameter` is 30 rather than for the setting itself?

--------------------------------------------------------------------------------
WHY IT IS FILED RATHER THAN BUILT
--------------------------------------------------------------------------------

Requested 2026-09-18 with the instruction to add it to the list and push, not
to implement it.
