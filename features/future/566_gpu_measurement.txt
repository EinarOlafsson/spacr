WHAT TO BUILD

ALPHA: 2026-09-27
    Setting measure_gpu (bool, default False) under "GPU Measurement
    (Alpha)" on Measure, registered as ALPHA_FEATURES[566]; hidden until
    Preferences -> Show alpha features. With it on, a visible CUDA device and
    PyTorch installed, _intensity_measurements and _morphological_measurements
    compute three blocks with vectorised PyTorch kernels in spacr/measure.py,
    all objects of a field at once:
      - _torch_intensity_table: the full _extended_regionprops_table (weighted
        centroids, min/max/mean, integrated, std, median, skew, kurtosis,
        mode, range, IQR, CV, Gini, frac_high90/low10, entropy, percentiles),
        from one (label, intensity) sort plus segment sums;
      - _torch_homogeneity: GLCM homogeneity without building matrices (mean
        of 1/(1+(a-b)^2) over each bounding box's horizontal pairs, with
        skimage's per-object 0-255 rescale reproduced);
      - _torch_zernike: the Mahotas Zernike moments, with Mahotas' unit-disk
        boundary decided exactly.
    Anything else (3-D, voxel spacing, non-finite or negative intensities,
    non-default intensity props, no torch, no CUDA) runs the unchanged
    NumPy/scikit-image/Mahotas path, which stays the default.
    Validation: the same kernels run on a CPU torch device in
    tests/test_gpu_measurement.py against the CPU functions: homogeneity and
    Zernike agree to 1e-12 absolute, the intensity table to float32 rounding
    (rtol 1e-5), dtypes and column order identical. On a loaded 32-core
    machine with torch limited to one thread, a 1024x1024 field with ~900
    objects took 1.8-2.3 s (CPU table) vs 0.13-0.22 s, 2.4-3.8 s (homogeneity)
    vs 0.66-0.81 s, 0.43 s (Zernike) vs 0.26 s, before any GPU.
    GPU timing: queued 2026-09-27 as `tools/gpu_turn.sh 566-timing python
    /mnt/wd4tb/scratch/566/gpu_timing.py` (2048x2048 field, ~3000 objects,
    CPU vs CUDA with max relative error); output goes to
    /mnt/wd4tb/scratch/566/gpu_timing.log. Not yet run: the GPU was held by
    another session's training.
    Optional dependency for the maintainer: PyTorch with CUDA (already used
    by spaCR's deep-learning paths). CuPy/cuCIM were not installed here, so
    the kernels are written in PyTorch rather than CuPy.

2026-10-04 — cuCIM MORPHOLOGY RUNS ON THE GPU; PLATE 2.6x FASTER THAN THE OLD CPU RUN
    Why cuCIM fell back: (1) cupy-cuda12x/cucim-cu12 sit beside PyTorch's
    CUDA 13 wheels; the CUDA path finder hands CuPy NVRTC 13 and
    nvidia/cu13/include headers, so every fresh kernel compile failed
    (NVRTC_ERROR_COMPILATION in cuda_fp8.hpp). Earlier runs only got past
    this through ~/.cupy/kernel_cache. (2) cuCIM's batch regionprops raise
    "No coordinates to process" on label images with gaps (every filtered
    mask). (3) cuCIM returns convex_area last, so the column-order check
    rejected every table. (4) cuCIM's area_filled and feret_diameter_max
    differ from scikit-image (up to 20x and 11 % on plate1).
    Fixes (spacr/measure.py): _preload_matching_nvrtc loads the NVRTC of
    CuPy's own CUDA major and pins the cudart header lookup to it, in-process
    only; labels are made sequential for cuCIM and mapped back; columns are
    reordered; area_filled and feret_diameter_max come from scikit-image
    (_CUCIM_DIFFERS); a failure is reported once per process.
    Proper environment fix for the maintainer (not done; shared env):
    install cupy-cuda13x + cucim-cu13 to match torch 2.13 (CUDA 13); the
    `gpu` extra and IMPORT_TO_DIST would then name the cu13 wheels.
    Profile (one 1994^2 field, CPU): 51 s; object_distances.maxima_distances
    23 s because local_maxima ran peak_local_max on the whole field per
    object. Now searched in each object's bounding box with the whole-field
    threshold (identical peaks): 31 s. scipy pearsonr per object replaced by
    _pearson_r (same value to 1e-13). With measure_gpu on, the object-distance
    EDTs run on CuPy (exact, 0.2 s -> 0.01 s per transform).
    Plate (tools/gpu_turn.sh 566-plate-final, RTX 3090, 4 plate1 fields,
    n_jobs 2): GPU 67 s wall vs CPU 99 s with this commit and 177 s before
    it -> 1.5x over the new CPU path, 2.6x over the old. compare_sorted:
    max relative difference 9.3e-08 (equivalent_diameter_area), 0 columns
    over 1e-3 in cell/nucleus/pathogen/cytoplasm. New CPU vs old CPU: 1.5e-13.
    LEFT: cuCIM morphology itself is no faster than scikit-image on these
    fields (0.1-0.3 s per mask) and first-use NVRTC compiles cost ~20 s per
    fresh worker without a kernel cache; remaining CPU time is intensity
    (correlation medians, periphery/radial EDTs, blur). "Several times
    faster" holds against the pre-566 CPU run only.
