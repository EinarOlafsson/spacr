WHAT TO BUILD
    Let a user lock an analysis before unblinding (with item 544's blind
    scoring): the settings, gates, models and thresholds are hashed and
    timestamped into the run journal; any change after unblinding is shown
    as post-hoc in reports and exports.

DONE WHEN
    A locked analysis re-run unchanged verifies against its hash; a post-hoc
    change is flagged in the report.

NOTE 2026-09-26 -- BUILT, AS AN ALPHA FEATURE (with item 544)

What was built
    API, in the existing spacr/run_journal.py (no new module):
      lock_analysis(settings, app_key=, hypotheses=, thresholds=, files=,
          note=)   writes ~/.spacr/analysis_locks/<lock id>.json: the
          settings (without "_"-prefixed run-only keys and hash_inputs),
          the plan (hypotheses, thresholds and gates, note), the full
          SHA-256 of every file that a setting whose key names a model,
          gate, checkpoint, weights or threshold points at (plus files=),
          who, when (UTC, microseconds), and any unblinding already
          recorded on the folder; then a SHA-256 over all of it ("sha256").
      check_analysis_lock(settings, app_key=, lock=)   finds the newest
          lock for the pipeline and src, re-hashes the lock itself (an
          edited lock is "tampered"), compares every setting (values_equal,
          so "[0, 1]" == [0, 1]) and re-hashes every locked file. Status:
          verified; deviation (changed, no unblinding since the lock);
          post_hoc (changed, and a blinding key on the folder, or on a
          folder inside or around it, was unblinded after the lock --
          item 544's record); not_preregistered (unchanged, but locked after
          an unblinding); tampered; or unlocked. With the changed keys
          (locked and current values) and a one-line summary.
    Later runs: open_run checks every journalled run (GUI, CLI and
      spacr repro all go through it). When a lock applies, manifest.json
      carries "analysis_lock" (the verdict); anything but verified is also
      appended to provenance_warnings. A run with no lock writes exactly
      the manifest it wrote before. The GUI console prints the verdict
      under "Reproducibility manifest:", and the CLI logs it (a warning
      unless verified).
    Reports and exports: spacr.report lists each run's verdict under
      Provenance and states every non-verified one at the top of the report
      (the run status section). The methods export (spacr.methods_export)
      carries the verdict into the digest's run and adds a caveat the
      methods text may not leave out ("run exactly as preregistered" /
      "the changes to X are post-hoc" / "X changed after the lock" / "not
      preregistered" / "lock no longer matches its hash").
    GUI: a "Lock analysis..." button (AnalysisLockButton) beside "Import
      settings..." on every settings screen. Its dialog states how the
      settings on the form stand against the newest lock, takes the
      hypotheses, the thresholds and gates, and a note, and Lock freezes
      them (the console says "Analysis locked: <hash> at <time>").

DONE WHEN, checked
    A locked analysis re-run unchanged verifies against its hash:
    test_an_unchanged_rerun_verifies_against_the_lock, and a journalled run
    carries "verified" in its manifest. A post-hoc change is flagged in the
    report: test_the_report_and_the_methods_text_flag_a_post_hoc_change
    (the report's top note and its Provenance line say POST-HOC; the
    methods caveat names the changed key).

Tests

    hash, verification, deviation against post-hoc around an unblinding,
    not_preregistered, a changed model file, an edited lock file, the

    tests/qt/test_544_573_blind_scoring_and_lock_on_screen.py (the dialog

Not done
    Gates drawn in the Gate Editor are locked only when the settings name
    their file (a key containing "gate"); gate objects kept elsewhere are
    not collected. Models are covered the same way (setting keys naming a
    model, checkpoint or weights file), not through Run.record_model,
    which runs after the check.
    A lock covers one pipeline on one src; a plan spanning several
    pipelines needs one lock per pipeline. Locking again supersedes (the
    newest lock wins) and the older lock stays on disk.
    A change counts as post-hoc when the RUN comes after an unblinding;
    when the setting itself was edited is not known.
    Run History and Run compare do not show the verdict yet (it is in the
    manifest they read). The HTML report was checked through
    collect_report and render_text, not opened in a browser.
    The English API manifest (docs/source/_static/i18n/api/en.json) and the
    UI catalogs were not regenerated in this lane; the new captions are in
    tests/qt/test_i18n_caption_ratchet.py's _AWAITING_CATALOG_REBUILD.

ALPHA: widgets AnalysisLockButton (the "Lock analysis..." button on every
settings screen, and with it its dialog); no settings keys, choices, apps or

(item 569's gate), applied when the button is placed and live by the app

2026-09-30 -- THE AUDIT'S REMAINDER: GATES, MODELS, PIPELINES, POST-HOC
TIMING, HTML (item complete; still ALPHA)

    Gate Editor gates. lock_analysis(gates=) takes a GateSet, its dict, a
    saved gate file, a list, or {label: one}; any setting whose value is a
    gate file is taken too, whatever its key is called. Gates are hashed as
    parsed, canonical gates (per gate by name), not bytes, so re-saving or
    reformatting is not a change and a change names the gate ("changed
    big", "added x", "removed y"). A locked gate file is re-read on every
    check; gates locked as objects are compared when check_analysis_lock
    (gates=) hands them over under the same label. Gate files no longer go
    into "files". The Gate Editor says after Save and Load whether the file
    matches every lock holding it, or how it differs (deviation / post-hoc).
    The lock dialog has a "Gate files" row (paths separated by ";").
    Models. Run.record_model now re-judges the run against its lock: a
    model locked by name (lock_analysis(models={name: path})) whose file
    differs, or an unnamed model when the lock names models, is a
    "model:<name>" deviation, and the manifest's verdict and warning are
    replaced, not duplicated. A model the lock cannot speak to is listed as
    uncovered_models (summary and methods caveat) without changing the
    status. The dialog locks the models the newest journalled run of that
    module on that src recorded (_recorded_models).
    Several pipelines. lock_analysis(pipelines={app_key: settings}) writes
    one lock (schema 2, "pipelines") whose every pipeline is checked
    against its own settings on its own src; an unblinding on any folder of
    the plan counts for all. Schema-1 locks still check.
    Post-hoc by edit time. Every difference is stamped with when it was
    first seen (<lock id>.seen.jsonl beside the lock, written by the first
    check, run or dialog, that met it); it is post-hoc only if first seen
    after the unblinding. An edit made blind stays a deviation in later
    runs; mixed runs name each key "(before/after unblinding)", and the
    methods caveat separates them. The 2026-09-26 test that expected the
    same pre-unblinding edit to turn post-hoc now expects deviation, and
    a new edit after unblinding to be post-hoc.
    HTML report. Parsed with html.parser: one doctype, html > head+body,
    every end tag matches, unique section ids equal to the TOC links, no
    script, the POST-HOC run flagged in the first section and both
    verdicts under "Preregistered analysis lock".

2026-10-01 — GATE EDITOR EXPORT CHECK AND ATTACHED PROVENANCE
Implemented the explicit remaining filters-export check. The screen retains the
last saved/loaded strategy path and snapshots the live GateSet at export. Locks
holding that path are checked against the live gates, including changes not saved
to disk, using the existing lock digest and first-seen/post-hoc verdict helpers.
The export feedback displays the resulting gate-specific verdicts. No matching
strategy lock produces no verification claim; existing verdict policy is preserved.

Successful gate columns receive a receipt in filter_export_provenance alongside
filters: export time, source table, saved strategy path, exact exported gates,
merge definition when applicable, written columns/object counts and lock verdicts.
The receipt explicitly scopes verification to the exported gating strategy; it
does not claim verification of unrelated settings or unrecorded merge mappings.
Failed gate writes never receive receipts. Receipt insertion is atomic, after the
established filter writer commits; these are separate transactions because the
existing filter writer owns its connection. Receipt failure is reported explicitly.

2026-10-01 — FIRST-SEEN CHECKS ON COMMITTED LIVE GATE EDITS
The Gate Editor now checks a saved/loaded strategy when its committed gates change,
including threshold edits, completed drawing changes and hierarchy edits. Unsaved
edits are compared in memory immediately; the existing journal first-seen policy
therefore records a blind edit before a later unblinding or export. The source line
shows the current gate-specific verdict, replacing obsolete save/load notes. An
unsaved strategy or a strategy with no matching lock makes no verification claim.

Identical duplicate change signals reuse their feedback. Pointer motion and adding
unfinished polygon vertices do not run these checks. Live comparisons use the
already-canonical strategy path and narrow gate coverage before comparison, so
other locked gate files and the source strategy file are not reopened on an edit.
Switching strategy files binds the new path before its load emits a gate-change
signal, preventing a false difference from being recorded against the old file.
A failed lock check leaves the edit intact and reports the failure explicitly.

2026-10-01 — SAVE/LOAD NOTES USE THE SAME FIRST-SEEN POLICY
The inherited gate-file notes now call the same scoped gate comparison and
_lock_verdict policy as live edits, exports and runs. Saving or loading a gate
change first observed before unblinding continues to say deviation afterward;
a distinct change first observed after unblinding says post-hoc. Save/Load itself
records a first-seen observation when no earlier edit check has seen that change.
Matching gates no longer imply a verified lock when its digest was tampered with
or the lock was created after unblinding: those statuses are shown explicitly.
Only the selected strategy is compared, without reading unrelated locked files.
Existing normal match/difference phrasing remains compatible.

2026-10-01 — FIRST-SEEN OBSERVATIONS ON COMMITTED SETTINGS EDITS
The remaining settings-form timing gap is closed. Valid text edits are observed
when committed, while checkbox choices, completed list/row-exclusion edits and
numeric arrow steps are observed immediately. Numeric typing and editable-combo
text remain drafts until committed; a private input-event guard distinguishes
numeric text from arrow/wheel changes without changing keyboard tracking.

Existing and deferred controls use the same observation hook, installed before
form-shaping callbacks so a replacement cannot lose an edit. Imported settings
are observed after their complete bulk application. A source switch binds the
complete valid snapshot to the new source's existing lock, never the old one.
Invalid types, numeric ranges, incomplete numeric lists and invalid barcode
expressions stay untouched and produce no false first-seen entry. An invalid
bulk snapshot also produces no entries for its other partially applied values.

Observation is explicitly limited to committed settings. It finds the existing
pipeline/source lock, checks the lock record's own digest, and calls the same
first-seen journal policy used by subsequent runs. It never reads or hashes
model/checkpoint/gate files and never returns or displays a verified verdict.
The normal run/dialog checks still perform complete verification. Duplicate
signals do not duplicate first-seen records. Journal failures preserve the edit
and report the failure through the existing console error channel.
