WHAT TO BUILD
    Offer PostgreSQL (multi-user labs, concurrent writers) and
    DuckDB/Parquet (very large screens, >100M objects) as alternatives to
    SQLite for measurements, behind the same read/write layer so every
    module works unchanged; migration tools both ways.

DONE WHEN
    The measurement, classification and regression test suites pass on each
    backend, and a 100M-row table queries within stated times on DuckDB.

ALPHA: 2026-09-28 -- measurement_backend and measurement_backend_target on
    Measure, under "Measurement Backend (Alpha)", hidden until Preferences ->
    Show alpha features is on (ALPHA_FEATURES[576]).

BUILT 2026-09-28
    spacr.tabular now reads and writes four stores through the same funnel,
    chosen by locator: SQLite (default, unchanged), a .duckdb file, a
    .parquetdb folder (one subfolder of Parquet parts per table) and a
    postgresql:// connection string. read_table, read_database,
    write_database, database_tables and table_columns all dispatch; append
    adds missing columns. Private helpers: _migrate_database (any store to
    any store, chunked, both ways), _query_store (SQL on any store; a
    Parquet store is queried through in-memory DuckDB views), _iter_chunks.
    duckdb and psycopg are imported only when such a store is opened;
    setup.py extra "databases" = duckdb, psycopg[binary].
    Measure: with measurement_backend != sqlite, a finished run copies every
    table of measurements.db into the chosen store (blank target = beside
    measurements.db, or PG* environment variables for PostgreSQL).

TESTED 2026-09-28
    tests/test_measurement_backends.py: DuckDB 1.5.6 in-process and Parquet
    (pyarrow 14) round trip, append-with-new-column, limit, errors, query,
    migration both ways incl. empty tables. PostgreSQL 18.4 was tested
    against a REAL local server (conda, no sudo, unix socket) via
    SPACR_TEST_POSTGRES_DSN; without that variable the Postgres cases skip
    and a mocked psycopg checks column types and COPY rows.
    tests/qt/test_measurement_backend_alpha_gate.py: the alpha gate.

100M-ROW DUCKDB TIMINGS 2026-09-28 (CPU, 8 threads, 1.8 GB file, 7 columns)
    COUNT(*) 0.03 s; per-well mean over 1008 wells 2.0 s; filtered
    per-plate count 2.9 s; fetch one well's 99k rows 6.1 s (55.6 s when the
    query adds LIMIT, which DuckDB runs order-preserving). Build 110 s.

LEFT
    measurements.db stays the working store: the measurement writer
    (io._save_to_db and other direct sqlite3 sites), classification and
    regression still read and write SQLite, so their suites have not been
    run on each backend. Next: route those sites through write_database /
    read_database with the chosen store, then run the suites per backend.
    A Settings-side migration button (SQLite <-> store) is not built.
