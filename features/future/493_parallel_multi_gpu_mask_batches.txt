493 — PARALLEL MULTI-GPU MASK BATCHES
====================================
Status: IN PROGRESS, requested2026-09-23. Manifest, device allocation, process
workers and resume helpers implemented; pipeline/control integration and real
multi-GPU validation remain open.
Scope: Cluster Distribution and Mask Generation. Filed for later work;
this request does not add a prerequisite to the1.5.1.0release plan.

Let the user select several compatible GPUs and process image batches on
them in parallel. Prepare the temporary NPZ batches first, then dispatch
each NPZ to one GPU, or partition the NPZ paths into per-GPU lists that
independent workers process concurrently. Each batch belongs to exactly
one worker; preserve field identities and the existing mask/output layout.

1. Prepare inputs once using the current preprocessing/normalization path.
   Generate a manifest of the temporary NPZ files and their source fields
   before dispatch. Avoid repeating preparation separately on every GPU.
2. Discover eligible devices and let the user choose participating GPUs.
   Expose the same option in Mask Generation when multiple compatible
   GPUs are detected. Otherwise keep it greyed out with an explanation.
   In Cluster Distribution, use the devices actually allocated to the job.
3. Run separate workers bound to their assigned GPU, with one loaded model
   per worker. Support a batch queue or disjoint per-GPU NPZ lists so that
   multiple devices segment concurrently without duplicate output writes.
4. Show per-GPU progress and overall completed/failed batch counts. Make
   cancellation, failures and resume preserve completed outputs and report
   unfinished work. Delete temporary inputs only after their outputs have
   been committed successfully, respecting existing retention settings.
5. Validate on a real multi-GPU system: simultaneous execution on selected
   devices, every input processed exactly once, results consistent with the
   equivalent single-GPU path, restart after interruption, mixed device
   memory limits, and no accidental use of unselected devices. Verify the
   disabled control on zero/single-compatible-GPU systems as well.

Implementation owns the scheduler, device binding and runtime controls.
The separate documentation lane owns resulting API descriptions, settings
help, tutorials and translations once the runtime contract is implemented.

byte sizes, exact output filenames and channel counts. Duplicate fields
within/across batches, paths escaping the mask folder, hidden outputs,
unreadable/legacy pickled identities and mid-inspection file changes are
refused before scheduling. Source archives are unchanged. The existing
header inspector accepts an explicit field axis for time-stack manifests.

2026-09-24 — Allocated-device discovery and worker environment preparation
Private accelerator helpers now enumerate the process-visible CUDA/ROCm
ordinals, names and memory without tensor allocation. Explicit single-device
or CPU overrides disable parallel discovery. A worker environment selects
one allocated ordinal, preserves CUDA UUID/MIG identifiers and ROCR limits,
and does not mutate the parent environment. Conflicting HIP/CUDA aliases,
invalid ordinals and changed/disabled visibility are refused. These helpers
are not yet wired to controls or model workers; no GPU execution is claimed.
79 discovery/allocation/existing accelerator checks pass with mocked devices.

2026-09-24 — Persistent process workers and cooperative stop
Private spacr._mask_workers now balances disjoint archive lists by stored
bytes and spawns one persistent model process per nonempty device assignment.
Each child binds its environment before loading the generator, checks that
exactly one GPU is visible, and forwards logs and completed-archive events.
The parent reports independent per-device progress snapshots, rejects duplicate
completion, detects exceptions/native crashes/missing final events, and stops
peers cooperatively. Completed outputs and all prepared inputs are retained.
72 worker/assignment/manifest/device/inventory checks pass; the new module has
94.12% combined statement/branch coverage. Real spawned CPU workers verify
concurrency and process isolation; this is not a real multi-GPU inference
acceptance. Persistent resume provenance, shared finalization, controls and
Mask/Cluster Distribution integration remain open.
