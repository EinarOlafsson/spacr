WHAT IS THERE
--------------------------------------------------------------------------------

`instructions/` held files in THREE places: `open/`, `done/`, and its own top
level. The rename carried all three across --

    instructions/open/  -> features/future/
    instructions/done/  -> features/new/
    instructions/*.txt  -> features/*.txt

-- and the third is the problem. The index generator scans `new/` and
`future/` only (`build_instruction_index.py:154-155`), so the eleven files at
`features/` top level appear in NO index, and the index's own header, which
tells a reader it is generated from the files themselves, is true only of the
two folders it looks in.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The index header says "THE TRAILING NOTES AT THE END OF EACH FILE ARE THE
CURRENT STATE. The header often says 'not started' when it is done -- eight
files have been wrong about themselves this week." That warning is about a
file disagreeing with ITSELF. This is worse: two files with the same name
disagreeing with EACH OTHER, where the one a reader is more likely to open --
it is one directory shallower -- is the wrong one, and the index that would
correct them cannot see it.

It is also invisible to every check that exists. The index is generated from
`new/` and `future/`, so a top-level file can never make it stale. Nothing
counts these eleven. They were found by grepping for a path that no longer
exists.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

  * DECIDE THE NINE AS A GROUP, not one at a time: they are all the same
    event. Either delete them as superseded, or move them somewhere named
    for what they are.
  * KEEP A RECORD IF THEY GO. Several carry dated history their counterparts
    may not -- 07 and 08 are 470 and 468 lines. Check before deleting rather
    than after; a `diff` against the counterpart says in a second whether
    anything is only in the stale copy.
  * THE TWO SINGLETONS NEED A HOME OR AN OWNER, separately. The tutorial one
    is not this list's to decide.
  * MAKE THE GENERATOR SAY SO. Whatever is decided, the index should either
    scan the top level or state in its header that it does not, so the next
    reader is not told it is generated "from the files themselves" when it is
    generated from two thirds of them.

DO NOT DELETE THE NINE TO MAKE THE FOLDER TIDY WITHOUT READING THEM. That is
the same error 397 warns about from the other direction: the count is not the
defect, and a file nobody has read is not evidence of anything yet.
