--------------------------------------------------------------------------------
WHAT IS THERE
--------------------------------------------------------------------------------

`instructions/` held files in THREE places: `open/`, `done/`, and its own top
level. The rename carried all three across --

    instructions/open/  -> features/future/
    instructions/done/  -> features/new/
    instructions/*.txt  -> features/*.txt

-- and the third is the problem. The index generator scans `new/` and
`future/` only (`build_instruction_index.py:154-155`), so the eleven files at
`features/` top level appear in NO index, and the index's own header, which
tells a reader it is generated from the files themselves, is true only of the
two folders it looks in.

NINE OF THE ELEVEN HAVE A COUNTERPART IN `features/new/` WITH THE SAME NAME,
AND EVERY ONE OF THE NINE IS THE STALER COPY:

TWO ARE NOT DUPLICATES and must not be swept up with the nine:

    segmentation_qc_field_browser.txt   156 lines, no counterpart
    update_tutorials_README.txt         273 lines, no counterpart, and it is

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The index header says "THE TRAILING NOTES AT THE END OF EACH FILE ARE THE
CURRENT STATE. The header often says 'not started' when it is done -- eight
files have been wrong about themselves this week." That warning is about a
file disagreeing with ITSELF. This is worse: two files with the same name
disagreeing with EACH OTHER, where the one a reader is more likely to open --
it is one directory shallower -- is the wrong one, and the index that would
correct them cannot see it.

It is also invisible to every check that exists. The index is generated from
`new/` and `future/`, so a top-level file can never make it stale. Nothing
counts these eleven. They were found by grepping for a path that no longer
exists.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

  * DECIDE THE NINE AS A GROUP, not one at a time: they are all the same
    event. Either delete them as superseded, or move them somewhere named
    for what they are.
  * KEEP A RECORD IF THEY GO. Several carry dated history their counterparts
    may not -- 07 and 08 are 470 and 468 lines. Check before deleting rather
    than after; a `diff` against the counterpart says in a second whether
    anything is only in the stale copy.
  * THE TWO SINGLETONS NEED A HOME OR AN OWNER, separately. The tutorial one
    is not this list's to decide.
  * MAKE THE GENERATOR SAY SO. Whatever is decided, the index should either
    scan the top level or state in its header that it does not, so the next
    reader is not told it is generated "from the files themselves" when it is
    generated from two thirds of them.

DO NOT DELETE THE NINE TO MAKE THE FOLDER TIDY WITHOUT READING THEM. That is
the same error 397 warns about from the other direction: the count is not the
defect, and a file nobody has read is not evidence of anything yet.

NO NUMBER IS WRITTEN ANYWHERE IN IT. The names come from
`_unscanned_top_level()` (build_instruction_index.py:203), which globs
`features/*.txt` on each run and excludes only the index itself -- a file
cannot be an input to its own generation. A pinned count is precisely what
this item keeps being caught by. CHECKED RATHER THAN ASSERTED, because the
first version of this paragraph got it wrong: the WORD "eleven" is in this
file's own title and in
`tests/test_a_ledger_file_does_not_contradict_itself.py::_ledger_files`
(line 125) -- two places, not three. The third is the same ratchet in another
form: `tests/test_a_ledger_file_is_not_shadowed_by_a_staler_twin.py` never
writes the count, it PINS the eleven NAMES, nine in `KNOWN_SHADOWED` and two
in `KNOWN_UNIQUE`, and says "Nine of them" in its docstring. All three go
wrong on the day somebody resolves one file. The header is the one place that
cannot.

TWELVE NAMES, NOT ELEVEN, AND THE DIFFERENCE IS NOT A DRIFT. The glob prints
what is there: the eleven ledger files this item is about, plus `TEMPLATE.txt`,
which is structural rather than a ledger item but is just as unscanned. The
header claims only that they are in neither list, which is true of all twelve,
and points at this item for "what becomes of the LEDGER ones". Hiding
`TEMPLATE.txt` would have meant a hand-maintained exception list, which is the
same defect one level down.

THE FOLDERS ARE NAMED ONCE, IN CODE, SO THE HEADER CANNOT DRIFT FROM THE SCAN.
`SCANNED = ("future", "new")` (line 55) is what `_files_for_number`,
`_duplicate_numbers` and the header all read, and `render` now builds its rows
as `{folder: _entries(folder) for folder in SCANNED}` (242), so a folder READ
and not named, or dropped from `SCANNED` and still named, is a KeyError on the
next run rather than a header that quietly describes the wrong scan. THE ONE
DIRECTION THAT IS NOT CAUGHT, measured rather than assumed: ADDING a third
folder to `SCANNED` prints its glob in the header and globs its files, and its
rows then go into no list, because `render` still unpacks `rows["future"]` and
`rows["new"]` by hand. A third folder needs a list of its own below, and the
comment at 242 now says so.

THE GAP THIS ITEM COMPLAINED OF IS NOW CLOSED FROM BOTH ENDS. "Nothing counts
these eleven" was true when this was filed;
`tests/test_a_ledger_file_is_not_shadowed_by_a_staler_twin.py` closed the
count on 2026-09-13, and printing the names closes the other half: `--check`
compares the committed index against a fresh render, so a file arriving at
`features/` top level now makes the index STALE and CI says so. A top-level
