294 — Verbose logging must be cheap before it can be the default

Status:    DONE 2026-09-19. The whole application was measured with verbose
           on against 284's budgets and it costs nothing a benchmark can see;
           the tooltip states the measured figures; DEFAULT_VERBOSE_LOGGING is
           True. The two defects the first 2026-09-19 note left open are
           FIXED in the same landing (second 2026-09-19 note): launch() now
           runs setup_logging before the preferences, and the Logging tab
           holds the DEBUG file switch while verbose is on and stores the
           user's own choice. The two pre-existing findings are FIXED
           2026-09-25 (last entry): is_verbose() reads the preference, and
           Reset to defaults resets the Logging switches. Left, for the docs
           lane: the translation pass for the changed strings, listed there.

Asked 2026-08-28: "verbose logging should be on by default".

MEASURED THE SAME DAY, with verbose on: spaCR wrote three 5 MB log files
inside one minute and the interface became "supper laggy". `spacr.trace` logs
every function ENTRY and EXIT, and that includes the backdrop's per-frame
paint path -- `ambient._with_alpha` entered and left thousands of times a
second, each one formatted and written to disk.

So the ask cannot ship as it stands. Make verbose cheap first:

* never trace the per-frame paint path (ambient, the fractals, anything on
  the animation timer);
* the trace hook costs nothing when the level is not enabled -- check before
  formatting, not after;
* keep the log bounded, and say in the tooltip what it costs.

THEN turn it on by default.

NOT the cause of the crashes: the crash log holds `Segmentation fault` and
`Aborted` entries from before verbose was enabled. See 295.

THE COST THAT WAS LEFT, AND IT WAS ON EVERY TRACED CALL
--------------------------------------------------------------------------------

`_trace_one_event` runs on EVERY Python call AND return in the process while
verbose is on. It called `os.path.realpath(frame.f_code.co_filename)` on each
one, to decide whether the frame is inside the spaCR package.

`os.path.realpath` IS NOT A STRING OPERATION. It resolves every component of
the path against the filesystem. Measured on this machine:

    os.path.realpath        11,739 ns/call
    a dict hit                  45 ns/call
                               261x, on a step taken twice per traced function

At a conservative ten thousand Python calls a second in a Qt application, that
is roughly a quarter of a core spent resolving the same few hundred paths over
and over.

FIXED by `_traced_realpath`, a dict keyed on `co_filename`. END TO END, on real
traced spaCR work rather than the isolated step:

    with the cache             1.1 ms
    bypassing the cache        3.9 ms
                               3.6x

BOTH NUMBERS ARE REPORTED because they answer different questions and quoting
only the larger one would be dishonest: 261x is what the step costs, 3.6x is
what the work costs, and the second is the one a user would feel.

The cache is unbounded on purpose and takes no lock. The key space is the set
of Python source files the process executes -- a few hundred, fixed after
import, already all resident in `sys.modules` -- so an eviction policy would
guard a dictionary that cannot meaningfully grow, and a lock would serialise
every traced call in the process to protect against two threads writing the
same string.

LEFT -- TWO DEFECTS, BOTH PRE-EXISTING, BOTH MADE COMMONER BY THE FLIP:

  1. THE STARTUP UNDOES THE PREFERENCE FOR THE `spacr` LOGGER. `launch()`
     calls `apply_preferences_to_app(app)` and THEN `setup_logging()`
     (spacr/qt/app.py, "from .logging_util import setup_logging"), and the
     package `setup_logging` sets `spacr` to INFO and the master file's
     filter to INFO and above. Probed with the real functions in that order,
     verbose stored on:

         after apply_preferences_to_app   spacr DEBUG  spacr.io DEBUG
         after setup_logging              spacr INFO   spacr.io INFO
                                          (spacr.qt and its children DEBUG)
         after apply_preferences_to_app   spacr DEBUG  spacr.io DEBUG
         again, which is what Save runs

     So until the first Save, DEBUG from every non-Qt module is dropped at
     the logger, and a user's own Logging-tab choice is overridden the same
     way whether or not verbose is on. The likely fix is to call
     `setup_logging()` before `apply_preferences_to_app(app)`, so the
     preferences land last. docs/notes/spacr/qt/preferences.md already says
     the per-level switches "have to be the one that lands last"; at startup
     they are not. Not done here: it is a startup-order change with its own
     tests to write, and it is not a cost.

  2. A SAVE STORES VERBOSE'S DEBUG AS THE USER'S OWN LEVEL. The Logging tab
     builds its switches from `get_log_file_levels()`, which ORs DEBUG in
     while verbose is on, and Save writes the switches back. Driven through
     the real dialog, default flipped, fresh store:

         fresh start                   stored levels None   verbose True
         Save, nothing touched         stored "DEBUG,INFO,WARNING,ERROR,CRITICAL"
         untick verbose, Save          stored the same      verbose False
                                       effective file levels still include
                                       DEBUG; `spacr` logger still DEBUG

     get_log_file_levels' docstring promises "DEBUG goes away again when
     they turn verbose off"; after any Save made with verbose on, it does
     not. With the default on, that is every user who presses Save. The cost
     measured above is nil either way, so the harm is a switch that stops
     doing half of what it says. A fix has to decide what an untouched DEBUG
     switch means while verbose is on -- the stored bit, not the displayed
     one, is the likely answer -- and that is a UI decision, so it is
     recorded rather than made.

2026-09-19 -- REVIEW: BOTH DEFECTS FIXED BEFORE THE FLIP LANDS
--------------------------------------------------------------------------------

The review of the two commits above held the flip back until both defects
were fixed. Its argument: defect 2 is not "Save, then later untick". It
happens on the very first untick-and-Save. And every Save made while verbose
is on writes DEBUG into the user's stored levels, where a later fix could no
longer tell it apart from a DEBUG the user chose. So both are fixed in the
same landing as the flip.

DEFECT 1, THE LAUNCH ORDER. Reproduced through `launch()` itself rather than
by calling the two functions in order. The probe runs the real launch() in a
fresh process and HOME. It emits records once the event loop is running,
quits, and reads the log files. Before, verbose on by default, no Save:

    spacr, spacr.io      INFO       (the preference had set DEBUG)
    cellpose             WARNING    (the tooltip says it reports its model)
    master log filter    CRITICAL, ERROR, INFO, WARNING
    spacr.io DEBUG       in no log file

`launch()` now calls `setup_logging()` BEFORE `apply_preferences_to_app(app)`,
so the package defaults go in first and the preferences land on top. After:

    spacr, spacr.io      DEBUG
    cellpose             INFO
    master log filter    DEBUG, INFO, WARNING, ERROR, CRITICAL
    spacr.io DEBUG       in spacr.log, spacr-debug.log, spacr-YYYYMMDD.log
    cellpose INFO        in spacr.log and spacr-info.log

With verbose off and the user's own file levels INFO,WARNING, the master
filter is now INFO,WARNING from launch. Before, it was INFO and above whatever
the Logging tab said. This part was wrong whether or not verbose was on.

`apply_verbose_logging(False)` now also puts `cellpose` back to WARNING. It
used to leave cellpose at INFO for the rest of the session once verbose had
been on.

DEFECT 2, THE SAVE. The Logging tab's DEBUG "Log file" switch is held on, and
disabled, while the verbose toggle is ticked, because verbose writes DEBUG
whatever the switch says. Save stores the user's own DEBUG choice, which is
remembered from before verbose held the switch, never the held value.
Unticking verbose gives the switch back with that choice. The switch's hint
says why it is held. `set_log_levels` now clamps the console against the
levels the files actually keep, and applies those levels to the live
handlers. Without that, a console DEBUG ticked under verbose would be
dropped at Save, because the stored file levels no longer carry DEBUG.
Driven through the real dialog and the real Save button:

    fresh store, untick verbose, Save
      before  stored "DEBUG,INFO,WARNING,ERROR,CRITICAL"  spacr DEBUG
      after   stored "INFO,WARNING,ERROR,CRITICAL"        spacr INFO,
              cellpose WARNING
    fresh store, Save with nothing touched
      after   stored "INFO,WARNING,ERROR,CRITICAL"; files keep DEBUG while
              verbose is on
    stored DEBUG the user chose, Save with verbose on, then untick verbose
      after   DEBUG kept both times; the switch comes back ticked
    verbose on, tick the console DEBUG switch, Save
      after   stored console includes DEBUG; the console shows DEBUG

2026-09-25 -- is_verbose() READS THE PREFERENCE; RESET RESETS THE LOGGING TAB
--------------------------------------------------------------------------------

1. `verbose_logger.is_verbose()` now returns a module flag, `_verbose`, that
   `apply_verbose_logging(on)` sets -- the preference as last applied --
   instead of `_handler.level == DEBUG`, which `apply_console_levels` holds
   at DEBUG in every session. So with verbose off the ~20 `log_call`
   pipeline wrappers and `log_button_press` really do nothing: a new test
   passes an object whose __repr__ records being called, through a wrapped
   call, with verbose off and DEBUG shown in the console -- no repr built.
   `test_is_verbose_follows_the_handler_level` pinned the old reading; it is
   now `..._follows_the_preference_not_the_handler_level` and also asserts
   that `apply_console_levels({DEBUG, INFO})` leaves is_verbose() False. The
   vlog fixture snapshots `_verbose` with the other singletons.

2. Reset to defaults now resets the Logging tab. After the verbose switch,
   it sets `_chosen_debug` to the default store's DEBUG choice (off), puts
   every file switch at the default file levels (with verbose's default on,
   DEBUG is held on and greyed, as the tab already does), re-syncs each
   console switch's enabled state and sets it from the default console
   levels. Read through the same empty-store getters as every other reset
   control, so no second table of defaults. Three tests in
   tests/qt/test_preferences_reset.py: switches go back; after reset,
   turning verbose off gives back DEBUG OFF (the default), not the drifted
   choice; reset then Save stores DEFAULT_FILE_LEVELS / DEFAULT_CONSOLE_LEVELS.
