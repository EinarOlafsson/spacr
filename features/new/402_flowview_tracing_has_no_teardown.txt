FLOWVIEW'S COLLECTOR IS A PROCESS-WIDE GLOBAL THAT NOTHING PUTS BACK
================================================================================

Status:    OPEN, filed 2026-09-14. Not blocking. PRE-EXISTING -- it is not a
           regression from any of tonight's 21 commits, and the measurement
           that establishes that is below.
Requested: not requested. Surfaced by the work session's clean full-suite
           sweep, batch 1.
Owner:     unassigned. `spacr/flowview/trace.py`, and every test that calls
           `trace.enable(...)`.

--------------------------------------------------------------------------------
THE SYMPTOM
--------------------------------------------------------------------------------

    FAILED tests/flowview/test_classify_ui_integration.py::
           test_open_failure_is_recoverable_and_never_costs_the_fold_strip
    ERROR  tests/flowview/test_the_panel_is_a_box_you_can_resize.py  (7 tests)
    AttributeError: '_Live' object has no attribute 'drain'

`_Live` is a stub collector defined in a DIFFERENT test file. It reaches these
tests because nothing removes it.

--------------------------------------------------------------------------------
THE MECHANISM, EXACTLY
--------------------------------------------------------------------------------

`spacr/flowview/trace.py`:

    _collector = _new_collector()          # module global, set at import

    def enable(collector=None):
        global _collector, _enabled
        with _STATE_LOCK:
            if collector is not None:
                _collector = collector     # process-wide, and permanent
            _enabled = True
            return _collector

    def disable() -> None:
        global _enabled
        with _STATE_LOCK:
            _enabled = False               # does NOT restore _collector

So `enable(x)` installs `x` for the life of the process and `disable()` does
not undo it. The tests restore it BY HAND -- `trace.enable(previous_collector)`
appears in four files -- which works only when the test reaches that line. A
test that raises, skips, or takes an early return leaves its stub installed for
everything that follows.

`monkeypatch` CANNOT SAVE THIS, and that is the part worth understanding.
`monkeypatch.setattr(trace, "get_collector", ...)` is undone at teardown, so
the files that patch the FUNCTION are safe. The leak is a `global` assignment
INSIDE a function, which is not an attribute set and which monkeypatch has no
way to observe. Three modules also do `from .trace import get_collector` at
module scope, so patching one binding leaves the others -- a second, separate
hazard in the same area.

No conftest restores `_collector`. There is no teardown at all.

--------------------------------------------------------------------------------
WHY IT LOOKS LIKE A REGRESSION AND IS NOT
--------------------------------------------------------------------------------

The work session measured this carefully enough to be worth repeating, because
the first three measurements all said "regression introduced tonight":

  * Both files PASS alone. `tests/flowview/` as a directory failed on the
    current tree and passed on 49c1189f7. Two trees, clean difference.
  * `git bisect` named a973af6a4 (a regex lookaround change) as first-bad.
    Checked explicitly rather than believed: a973af6a4 tests GOOD and its
    PARENT tests BAD -- the inverse. THE PROPERTY IS NOT MONOTONIC, SO BISECT
    CANNOT ANSWER IT. A bisect result on a flaky property is noise with a
    commit hash attached.
  * A linear scan of all 21 commits was scattered, and included a25269741 --
    a pure ledger-text commit touching one .txt file under features/future/.
    Nothing in it can reach flowview. That is what killed the hypothesis.
  * Direct measurement: same two files, same unchanged commit, 15 runs across
    two worktrees, 0 failures. The earlier reproductions were real
    observations of a test sensitive to machine load, not to source.

The rule that follows: A RED RECORDED WHILE THE MACHINE WAS BUSY IS A WORKLIST
ITEM, NOT A FINDING.

2026-09-15 -- THE ROOT GUARD MET A STAND-IN, AND NOW STEPS AROUND IT
--------------------------------------------------------------------------------

On the first CI run after 324524948 the guard itself produced four teardown
ERRORs: "module 'spacr.flowview.trace' has no attribute 'get_collector'" in
test_cov_r8_ml_flowview_gate (x3) and test_cov_r7_deep_spacr. Those tests put
a STAND-IN at that sys.modules key on purpose -- a hand-built ModuleType, or
an object with only `is_enabled` -- and monkeypatch, set up by an earlier
autouse fixture, undoes the swap only AFTER this guard tears down. So the
guard asked the stand-in for its collector.

Fixed in f59b5903a: the guard restores the module it SNAPSHOTTED, whatever
sys.modules holds at teardown, and ignores anything that is not the real
tracer (a real import has a `__spec__`; `types.ModuleType(...)` does not).
4 errors -> 0; the 402 guard tests plus tests/flowview: 38 passed.
