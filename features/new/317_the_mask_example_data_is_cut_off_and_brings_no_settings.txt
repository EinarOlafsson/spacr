THREE THINGS, AND THEY ARE NOT THE SAME BUG
--------------------------------------------------------------------------------

1. THE PROGRESS DIALOG CLIPS ITS OWN TEXT.

   `hf_download.download_toxo_mito_demo` builds its QProgressDialog with
   the label "Preparing..." and then replaces it with

       f"Downloading {name}\n({done}/{total} files)"

   A QProgressDialog sizes itself from the label it was CONSTRUCTED with
   and does not grow when the text gets longer. A Hugging Face filename
   is far longer than "Preparing...", and the second line carries the
   count -- so the name is clipped and the "(n/m files)" line, which is
   the only progress a user can read, is cut off with it.

   The fix is a minimum width that fits a real filename, a word-wrapping
   label, and a re-fit when the text changes.

2. THE MASK EXAMPLE BRINGS NO SETTINGS FROM THE DATASET.

   `mask.load_the_example_images` writes a SYNTHETIC plate and applies
   `synthetic.demo_settings("mask", src)` -- values invented to match the
   generated images. That is right for the synthetic plate and wrong for
   the real one: the maintainer is asking about the toxo_mito data, for
   which a settings pack already exists.

3. THE SETTINGS PACK IS ALREADY DOWNLOADED AND ONLY THE E2E DEMO USES IT.

   [CORRECTED 2026-09-14: "the only reader" was true when this was written
   and is not true now. There are two, they read DIFFERENT FILES out of the
   same folder, and only one of them migrates. See the 2026-09-14 section at
   the foot of this file.]

   `hf_download.SETTINGS_REPO` is `einarolafsson/spacr_settings`, and the
   worker already fetches every file in it beside the dataset. The only
   reader is `_run_e2e_chain._settings_for`, a closure inside
   `MainWindow`, which reads `{app_key}_settings.csv` and merges it over
   the app defaults.

   THAT READER IS NOT SAFE TO REUSE AS IT STANDS. It merges every key it
   finds, so a settings file written against an older spaCR carries keys

   are either ignored silently or land on a control that means something
   else now. That is the "might need to be reformated" the maintainer
   names, and it is the substance of this item.

2026-09-15 -- A CACHED EXAMPLE LOADS THE USER'S OWN RUN SETTINGS, NOT THE PACK
--------------------------------------------------------------------------------

Found by the other session's 358 tutorial capture, which could not photograph
the Mask form until it moved two stale settings files aside. The form was
showing Source `<src>` and settings that were not the pack's -- flow_threshold
100, cellprob -1/0, no diameter.

THE MECHANISM IS WRITTEN DOWN IN THE CODE, as a feature.
`AppScreen._EXAMPLE_SETTINGS_FILES` (app_screen.py:3528) lists the files an
example may ship, "best first":

    "mask": ("gen_mask_settings.csv", "gen_masks_settings.csv"),

and the comment directly above it says, correctly:

    a mask run saves `gen_mask_settings.csv`, the older pack shipped
    `gen_masks_settings.csv`

SO THE FIRST CANDIDATE IS THE NAME A RUN WRITES. `utils.save_settings` puts a
completed run at `<src>/settings/<name>.csv` with `name='gen_mask_settings'`
(core.py:344), which is the same folder shape and the same filename the
example loader searches. On a FRESH download the pack is the only file there
and everything works; once the user has run Mask on the example, their output
sits in that folder under the preferred name and wins forever, because a
cached example is never re-fetched.

That is why it looks intermittent and why it only bites returning users: it
cannot happen until you have actually used the thing once.

WHAT MAKES IT AWKWARD TO FIX, and why this is recorded rather than patched
tonight: you cannot tell the two apart by NAME. `settings_pack.PACK_FILES`
lists `gen_mask_settings.csv` as a SHIPPED pack name too, so the published
sets and the run outputs genuinely share a namespace. Reordering the tuple
would only move the problem to whichever set uses the other spelling.

FIXED 2026-09-15, AND IT WAS SMALLER THAN THE THREE OPTIONS BELOW.

The options were written before tracing the caller, and tracing it made all
three unnecessary. `_put_the_example_images_in_place(self, images, settings)`
RECEIVES the settings location, prints "Compatible example settings: <path>"
to the console with it, and then calls
`apply_settings_that_came_with(images)` -- passing the plate and discarding
the pack. The download had already separated them properly: the plate unpacks
to `<dest>/plate1` and the pack to `<dest>/settings`, a sibling no run writes
into. The information was being handed over and thrown away.

So no download-time manifest, no change to the published archive layout. The
loader takes an optional `pack_folder`, prefers it, and falls back to the
plate -- because three of the four callers pass none, and their archives
really do carry settings inside the plate.

REPORTING THE RIGHT PATH WHILE READING A DIFFERENT ONE is why this survived.
The console told the user the shipped pack had been applied, so the evidence
in front of them said it had worked.

Four tests, and both mutations caught: ignoring `pack_folder` (the defect) and
letting it REPLACE the plate (the over-correction).

THE OPTIONS AS THEY WERE WRITTEN, kept because the reasoning is still right
for a case where the caller does NOT already know -- none of them was needed
here:

  * REMEMBER WHAT WAS DOWNLOADED. Record the pack's path when the example is
    fetched and read that, rather than searching a folder by name. A shipped
    file is known at download time; a run output is not.
  * SEPARATE THE NAMESPACES. Put the shipped pack somewhere a run cannot
    write -- `<dest>/example_settings/` rather than `<dest>/settings/`. This
    changes what the published archives have to contain, so it is a decision
    about the Hugging Face layout and not only about this code.
  * PREFER THE OLDEST FILE, or the one whose `src` still points at the
    publisher's machine before `reanchor_example_paths` rewrites it. Both are
    heuristics and both will be wrong eventually.

The first is the only one that stops guessing, and it is the one I would
build. It needs the download path and the loader to agree on a record, which
is more than a name-ordering change.

NOT FIXED HERE. Recorded with the mechanism so the next session starts from
