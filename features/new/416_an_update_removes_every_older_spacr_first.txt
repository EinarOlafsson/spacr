--------------------------------------------------------------------------------
WHAT IS THERE NOW
--------------------------------------------------------------------------------

The updater (spacr/updater.py; Help -> "Check for updates") upgrades spaCR
INSIDE the environment it is running from -- `uv pip install --upgrade
--python sys.executable` on a desktop install (`find_uv`, `upgrade_command`),
`python -m pip install --upgrade` otherwise. It never looks for, or removes,
any other installation. A user whose old install cannot be uninstalled
therefore cannot get past it, and the maintainer has such a machine now.

(packaging/ at tag v1.5.0.1) -- every later layout must be added to this list:

  Windows, online installer (spacr_online_installer.nsi +
  install_spacr_windows.ps1):

  macOS, offline: /Applications/SpaCR.app
  Linux, offline: the `spacr` .deb package (build_debian.sh)
  Any system: pip / conda environments that contain the `spacr` package.

cache) are NOT an old version and are kept -- the 1.5.0.1 unix uninstaller
already said "User-created data and preferences were left in place".

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

  * Before an update or install completes, FIND every older spaCR
    installation on the machine from the list above (and every later layout),
    and remove it: files, launchers, shortcuts, menu entries and uninstall
    registrations. Afterwards exactly one spaCR is installed, the new one.
  * It must work from EVERY old version, 1.5.0.1 included, even when that
    version's own uninstaller is missing or broken -- which is the case that
    blocks the maintainer today. Removal cannot depend on the old version's
    code.
  * An install cannot delete itself while running (Windows locks open files).
    The removal of the running environment belongs to a separate process or
    the installer, which replaces the old install after spaCR has exited, and
    restarts the new one.
  * Keep preferences and user data unless the maintainer decides otherwise.
  * User-created Python / conda environments that happen to contain spaCR are
    not the installer's to delete wholesale -- see OPEN QUESTION.
  * Report what was removed, where, in the console and the install log.

THE SEQUENCE, in the maintainer's words (2026-09-15, a follow-up message):
           "for 3 i need several new behaviours:

           if  update spacer is activated in the spacr aplication, the sequence
           should be:

           find old spacr files --> delete old spacr files --> install new
           spacr

           if the installers are used the sequence of events should be :

           find old spacr files --> delete old spacr files --> install new
           spacr"

  So there are TWO entry points with the SAME three steps, and the order is
  the requirement -- find, then delete, then install; never install over or
  beside an old copy:

      in-app "Check for updates" -> update   the native installers
      ---------------------------------------  ---------------------------------
      1. find old spaCR files                  1. find old spaCR files
      2. delete old spaCR files                2. delete old spaCR files
      3. install new spaCR                     3. install new spaCR

  Both entry points use ONE finder and ONE remover (one list of locations),
  so a layout added for one is never missed by the other. In the in-app path
  the running spaCR is itself an old copy, so steps 2-3 run in a separate
  process after the app exits (see above), then start the new version.

DECIDED (asked with the question tool, 2026-09-15): what the updater does with

verbatim: "List them and ask (Recommended)" -- "Remove every installer-made

WHAT THE FINDER AND REMOVER COVER -- spacr/install_cleanup.py, standard
library only, imports nothing from spaCR, one implementation for both entry
points.
  * find_old_installs: every layout above. On Windows, the registry (the
    Uninstall key's InstallLocation and Software\spaCR InstallRoot) plus the
    default roots; both capitalisations everywhere, deduplicated by device and
    inode so a case-insensitive volume lists one folder once; a registered
    copy whose folder is already gone. A launcher, menu entry or shortcut is
    claimed only when it names the copy's root, so a `spacr` command or
    .desktop that starts a conda environment is left alone -- exactly the
    case on the maintainer's workstation. User environments come from
    ~/.conda/environments.txt, common conda bases and their envs/,
    ~/.virtualenvs, ~/.venvs, ~/venvs, pyenv, pipx, the user site and the
    running environment; editable installs are reported as checkouts. A
    record carries kind, layout, platform, root, version, launchers,
    shortcuts, menu_entries, registrations, python, running, needs_admin and
    notes (for example "its own uninstaller is missing").
  * remove_install never runs the old uninstaller. It deletes the folder,
    launchers, shortcuts, menu entries, app bundle and registry entries; a
    .deb only through dpkg, reported as "needs administrator rights; run: sudo
    dpkg -r python3-spacr" when sudo is not allowed. It refuses shared folders
    (home, applications, ~/.local/bin, Program Files, /Applications ...) and
    keeps ~/.spacr, ~/.cache/spacr, ~/.local/state/spacr, ~/spacr-demos,
    ~/spacr-tutorials, the Hugging Face cache, ~/.config/spacr,
    com.spacr.qt.plist and the registry settings key; `keep` spares the new
    install's own log. A user environment is touched only when ticked, and
    then only `pip uninstall spacr` runs in it -- never in the running
    environment. Checkouts are skipped. The running copy is refused ("in use;
    it is removed after spaCR closes"). It returns removed, failed (with the
    reason) and skipped.
  * run_update_sequence: find, then delete, then install; install is not
    called when any installer-made copy failed.
  * start_update_helper, for a running spaCR that is itself installer-made:
    writes plan.json and a copy of the module to a temporary folder, picks an
    interpreter outside the copy (the current one when it survives, otherwise
    the copy's uv copied out, running `uv run --python 3.12`), and spawns it
    detached. The helper waits for the PID, downloads the release installer
    before deleting anything, deletes every old copy including the one that
    was running, runs Setup.exe /S /D=<root>, the .run with --install-root
    <root> --no-launch --skip-system-deps, or opens the .pkg, then relaunches,
    and writes ~/.spacr/logs/update.log.

WHAT THE INSTALLERS NOW DO
  install_spacr_unix.sh (the .run, and the macOS package's install-online.sh):
  starts its log in the root, fetches uv and a private Python into a temporary
  folder, writes the module there (render.py embeds it in the standalone
  script between the @SPACR_CLEANUP_MODULE_BEGIN@ and END markers), runs
  `install_cleanup.py remove` keeping install.log and the .installing lock
  (and, from the package's first-launch helper, the package's own app, link
  and support folder), with --sudo in a terminal; exits 6 with a message if an
  installer-made copy remains; only then moves uv into bootstrap/ and installs
  as before.
  install_spacr_windows.ps1 does the same, keeping install.log, spacr.ico and
  nsis-bootstrap-status.txt; NSIS ships install_cleanup.py beside it.
  The downloads come before the delete, so a network failure deletes nothing;
  a failure after the delete (resolver, validation) leaves no spaCR, which is
  the cost of the required order.

IN-APP: Check for updates -> Yes -> find (in a worker) -> a dialog listing the
copies to remove, with a tick box per environment the user made ->
run_update_sequence (delete, then run_pip_upgrade) in a worker, or
start_update_helper and close when the running copy is installer-made.
tests/qt/conftest.py stops every Qt test from reaching the real finder,
remover or helper.
