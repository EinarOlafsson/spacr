--------------------------------------------------------------------------------
THE MODEL, STATED ONCE
--------------------------------------------------------------------------------

EVERY OBJECT TABLE IS ANCHORED TO THE CELL. That is the invariant the whole
merge rests on, and it is currently nowhere written down:

    cell        the anchor.                       key column: object_label
    cytoplasm   cell minus its interior objects.  key column: object_label
    nucleus     belongs to one cell.              key column: cell_id
    pathogen    belongs to one cell.              key column: cell_id
    organelle   belongs to one cell.              key column: cell_id
    png_list    one crop of one cell.             key column: cell_id

So the key is ONE CONCEPT UNDER TWO NAMES. `object_label` in cell and
cytoplasm, `cell_id` everywhere else. Any merge that does not translate
between them is joining on a coincidence.

CARDINALITY FOLLOWS FROM THAT. cell and cytoplasm are ONE ROW PER CELL;
nucleus, pathogen, organelle and png_list are MANY ROWS PER CELL. A merge
that does not aggregate the many side first fans the cell's own measurements
out across its children and multiplies every per-cell number by the child
count.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. NAME THE KEY IN ONE PLACE. A registry -- like `spacr.object_roles` does for
   the object vocabulary -- saying which column carries the cell anchor for
   each table, and a function that returns it. Every merge site reads that
   instead of spelling `object_label` or `cell_id` itself.

2. DUPLICATE COLUMNS ARE COMPARED, NOT SILENTLY PICKED. When two tables being
   merged carry the same column name:
     * index both on `prcfo`;
     * where the values AGREE, keep ONE copy;
     * where they DISAGREE, that is a real inconsistency -- warn on the
       console naming the column and showing offending keys, or stop the
       analysis. Do not let a suffixed `_x`/`_y` pair through, and do not let
       one silently win.
   The existing `_merge_grouped` already does something like this for the
   acquisition-metadata columns (`acquisition_conflict`); this generalises
   that to every shared column.

3. AGGREGATION IS PER COLUMN KIND, and this is the part that matters more
   than the join type:

       areas / counts        SUMMED     four pathogens in a cell contribute
                                        one total pathogen area and a count
                                        of four.
       summary statistics    MEAN       intensities, ratios, correlations,
                                        eccentricity -- averaging is the only
                                        thing that means anything.
       identity / metadata   FIRST      plate, row, column, field: identical
                                        across the group by construction,
                                        and if they are NOT, see (2).

   Getting this wrong is worse than a wrong join: a summed intensity is not a
   number that is merely from the wrong rows, it is a number with no meaning.

4. THE JOIN TYPE, now decided:
       png_list   INNER, always.
       nucleus    INNER, always.
       cytoplasm  does not matter -- tertiary to cell, one row per cell.
       pathogen   INNER when the analysis is recruitment-to-pathogen, where
                  an uninfected cell is not a unit of analysis. OUTER when
                  the user asks to KEEP UNINFECTED cells. So this one is a
                  SETTING, not a constant, and the setting has to reach the
                  merge.

5. CYTOPLASM IS CELL MINUS EVERY INTERIOR OBJECT, not just nucleus and
   pathogen: `cell - nucleus - pathogen - organelle - organelle_1 - ...`.
   This is the same requirement instruction 76 records, and the two should
   land together.

6. FIX IT WHEREVER IT LIVES, not only in merge_tables. The user named
   `spacr.io`'s readers specifically -- `_read_and_merge_data`,
   `_read_and_join_tables`, `_read_db` and whatever else joins these tables.
   The aggregation rules belong in one place that all of them call.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A synthetic plate where the answer is known by construction: N cells, a known
number of pathogens per cell with known areas and intensities. After the
merge, the per-cell pathogen area is the SUM, the per-cell pathogen intensity
is the MEAN, the pathogen count is the COUNT, and every per-cell measurement
appears exactly once at its original value -- not multiplied by the child
count. Then the same plate with a column deliberately made inconsistent
between two tables, and the run says so instead of picking one.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Every number in a screen comes through this merge. A fan-out multiplies
per-cell values by the child count; a wrong aggregation replaces a
measurement with something that is not a measurement of anything. Neither
raises, both look like data, and the figure downstream is drawn from them.
