THE DOWNLOAD PROGRESS LINE IS NEVER CUT OFF

Status: DONE 2026-09-25 (filed 2026-09-24).
Owner: Claude (worktree agent), 2026-09-25.

REQUEST (the maintainer, 2026-09-24, verbatim)
    "usually when downloading the text e.g. step 1 of 3 or 10% is cutt of, fix
    that so it is not cut off."

WHAT TO BUILD
Wherever spaCR reports a download or an install in progress -- the backend
installer's step line, the example-data and model-zoo downloads, the
installer dialogs -- the whole line is readable: "step 1 of 3", the
percentage, the speed and the time left. Find every widget that shows one
(the progress dialogs under spacr/qt/widgets, hf_download.py's dialog, the
model-zoo picker's status, the backend install dialog) and make the text fit:
elide the changing part rather than the count, give the label the room it
needs, or wrap. A number the user is watching must never be the part that is
cut.

DONE WHEN
Every progress line shows its step count and percentage in full at the
smallest window spaCR supports (1366x768 at 100 % GUI scale, and at 50 %),
checked in a rendered screenshot rather than by reading the code.


NOTE 2026-09-25 -- DONE (Claude, branch worktree-agent-abd2c370aae461d2e)

ROOT CAUSE. spacr/qt/theme.py's QProgressBar rule (`height: 8px;
max-height: 8px`) applies to every bar. A bar with textVisible (Qt's default)
paints its caption -- "step 2 of 3", "%p%", "312 MB / 690 MB (45%)" -- into
those 8 px: an 18 px line of text, of which only the top rows reach the
screen; at 50 % GUI scale the track is 4 px.

THE FIX, the maintainer's "thin bar + label". ProgressLine
(spacr/qt/widgets/eliding.py:252, next to ElidingLabel, which it uses; a new
module would have moved the coverage denominator pinned in .github, which this
lane may not edit): the slim bar paints no text; the count and the percentage
sit in a label beside it (horizontal policy Minimum, so a layout cannot give
it less than its text) or, with count_below=True, on their own line under the
bar at the left; an optional detail line below elides the changing part and
displayed_text() reports what is painted. It answers the QProgressBar calls
the sites already make (setRange, setValue, setFormat with %p/%v/%m, format(),
setTextVisible, isTextVisible ...), so each site changed one line and the
existing tests that read .format() / .isTextVisible() still hold. A template
without %p gets " · NN%" appended while the bar has a range. No size is
computed from font metrics and handed to a size setter, so the GUI-scale layer
scales each size once.
