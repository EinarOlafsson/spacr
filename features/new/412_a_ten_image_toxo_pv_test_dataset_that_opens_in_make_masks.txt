================================================================================
A TEN-IMAGE TOXO PV TEST DATASET THAT OPENS IN MAKE MASKS
================================================================================

Status:    BUILT, ON NIGHTLY (20199e598), 2026-09-15. Ten in-house Toxo PV images and
           their curated masks are on Hugging Face
           (datasets/einarolafsson/spacr-example-make-masks); Make Masks'
           "Load test data…" downloads them off the GUI thread and opens the
           first image, translated in nine languages; the module is at 100%.
           The owed press with an empty cache was made 2026-09-25 (note at
           the foot): download, open on the first image, cached second press.
           Made on the offscreen Qt platform, not watched on a display.
Requested: 2026-09-15, by the maintainer, in these words:
           "also based on 10 images in the toxo PV training set uploade these
           images to huggingface and make a small test dataset for make masks,
           then add a button for loading this dataset which automatically
           triggers opening the first image with make masks."
Owner:     Claude home session.

--------------------------------------------------------------------------------
WHAT IS ASKED -- THREE PARTS
--------------------------------------------------------------------------------

  1. TEN IMAGES from the Toxoplasma PV training set
     (/mnt/wd4tb/af3/projects/toxoplasma_pv_model/data/), uploaded to Hugging
     Face under the maintainer's account (einarolafsson).
  2. A SMALL TEST DATASET FOR MAKE MASKS: laid out the way Make Masks opens a
     folder (the nested layout, `<stem>.<ext>`, with `masks/` beside the
     images), with a dataset card that states where the images came from.
  3. A BUTTON that loads the dataset and then opens its FIRST image in Make
     Masks by itself, with no second click and no folder picker.

--------------------------------------------------------------------------------
DEFAULTS TAKEN (each a reversible choice, stated so it can be overruled)
--------------------------------------------------------------------------------

  * IN-HOUSE IMAGES ONLY. The training set mixes the lab's own acquisitions
    (data/toxoplasma_pv) with figures harvested from published papers
    (data/toxoplasma_pv_literature). Publishers' figures are not ours to
    re-publish, so the ten come from the in-house manifest, and each one's
    provenance row travels with it.
  * NEVER A HELD-OUT IMAGE. Nothing from holdout_round3/, the 11 held-out
    in-house wells, or any curation hold-out queue, even though publishing
    would not train on them: a demo image copied into a scorecard later would
    quietly break the never-train rule.
  * THE IMAGES OPEN UNSEGMENTED; the curated masks ship beside them. The
    training masks go in `ground_truth_masks/`, a folder Make Masks does not
    read, so the editor opens on raw fields (the live magnifier of item 407
    has something to do) and the truth is there to compare against.
  * THE SAME HOSTING PATTERN AS THE EXISTING TEST DATA. The dataset lives
    where, and is fetched how, the other "Load test data" packs are. Cached
    after the first download, off the GUI thread.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * The Hugging Face dataset page lists ten images, their masks, and a card
    naming each image's in-house source.
  * On a machine with an empty cache, pressing the button downloads the
    dataset, and Make Masks shows the first image (by name order) with no
    further input. A second press opens from the cache without a download.
  * The button's label and tooltip are translated in all nine languages.
  * Tests prove the load-then-open sequence with the download mocked (no
    network in tests), and prove the button does nothing harmful offline:
    it says why, rather than failing silently.

2026-09-25 -- THE OWED PRESS, WITH AN EMPTY CACHE

What was done. `MakeMasksScreen()` built from this checkout (spacr imported
from the worktree), shown, and its real `_btn_test_data` clicked once --
`QPushButton.click()`, so the same `clicked` signal a mouse press sends, the
real `load_the_test_data`, the real `_MakeMasksTarWorker`, the real network.
HOME, XDG_CACHE_HOME/CONFIG/DATA and HF_HOME all pointed at a fresh scratch
folder, so `make_masks_example_folder()` did not exist before the press and
the maintainer's own ~/.cache/spacr was verified unchanged after it. CPU only.

What happened, in order:

  * On the press: button disabled, relabelled "Fetching test data…", status
    line "Downloading the Make Masks test data".
  * 22.9 s later (download, unpack and first-image decode together): 22
    files, 37,883,223 bytes -- ten `plateN_WELL_F.tif` fields, their ten
    masks under `ground_truth_masks/`, `README.md`, `manifest.csv`. No `.part`
    file left behind. No warning raised.
  * The screen was on the unpacked folder with the ten fields listed, on
    `plate1_A02_12.tif` -- the first by name, as asked -- showing a
    1994 x 1994 uint16 image; status "plate1_A02_12.tif  (1/10)". The button
    was back to "Load test data…" and enabled.
  * A second press opened from the cache: no download, no "Fetching" label,
    same first field.

The one qualification. It ran on Qt's offscreen platform, so the progress
dialog and the canvas were drawn but not looked at on a monitor; everything a
test could only mock (the Hugging Face fetch, the tar stream, the unpack into
an empty cache, the hand-off to `_open_folder` and the decode) was real. The
driver is kept outside the repository (scratch), since it is a one-off
receipt rather than a test: a test that downloads 38 MB is not one the suite
should run.
