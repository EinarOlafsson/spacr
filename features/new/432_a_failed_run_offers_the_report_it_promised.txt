WHAT THE STATE IS
--------------------------------------------------------------------------------

The console the user pasted into #117 shows what happened. Everything below
is either in that paste or was reproduced headless on 2026-09-19.

THE AI WAS ASKED. The paste contains

    === spaCR user ===
    An error occurred — asking spaCR AI to explain it. ...
    === spaCR AI ===
    (nothing)
    === spaCR output  —  mask  —  preprocess_generate_masks ===
    ...run closed [failed]...
    ✗ Failed — see traceback above
    Failed to authenticate: OAuth session expired and could not be refreshed

so the route fired. Test mode, the retry policy and macOS were all ruled
out. The crash left `runctx._give_up` by `raise exc`, reached
`bridge.PipelineWorker.run`'s `except Exception`, and was emitted on
`worker.error` like any other failure (bridge.py, the `self.error.emit(tb)`
after `LOG.exception("Pipeline worker failed")`). `_on_pipeline_error` then
called `open_error_flow`. Nothing on this path reads `test_mode`, and
there is no fingerprint dedupe before the AI flow.

WHAT WENT WRONG IS THE PROVIDER'S ANSWER. The `claude` CLI's sign-in had
expired. It printed the expired-session line and exited.
`providers._stream_process` never read the exit status, so the worker
emitted `finished(True, "Failed to authenticate: ...")`. The console took
that as the reply:
  * No "[AI error]" line, and nothing telling the user to sign in again.
  * `_ai_error_explanation` was set to that line. `ai_explanation_of` gave
    it to the bug reporter, and issues #118 and #121, filed from the same
    machine 11 and 26 minutes later with "File as issue", each carry
    "Failed to authenticate: OAuth session expired and could not be
    refreshed" under "spaCR AI's analysis of this error".
  * The reply sat under "spaCR output", not "spaCR AI". The error flow
    draws the heading and the reply block at once. The run's closing
    lines (workspace, macro, "run closed", "✗ Failed") came before the
    CLI's first line. `_on_chunk` then opened a new reply block with no
    heading, so the "spaCR AI" heading stayed empty. Read top to bottom,
    that looks like the AI was never asked.

MEASURED, 2026-09-19: Claude Code 2.1.274 in an empty HOME. `claude -p
"say hi"` prints `Not logged in · Please run /login`, exit status 1. The
expired-OAuth wording in #117 needs an expired session, which could not be
produced here, so its exit status is NOT measured. The fix does not depend
on the wording.

NO ISSUE WAS FILED BECAUSE NONE EVER IS WITHOUT A CLICK. That is deliberate.
Until 807ba9e0a (2026-08-14, "installer: make acceleration and consent
explicit", instruction 45), `_on_pipeline_error` called `_on_file_issue`
itself when the setting was on. That commit removed the call: reports go
to the PUBLIC tracker, and each one stops at an editable preview until
Send is pressed (instruction 45's 2026-08-10 decision section). The test
`test_opt_in_reveals_button_but_never_auto_submits_on_crash` in
tests/qt/test_cov_app_screen.py pins it. What was missing was any word of
it where the user looks. The only sign was "File as issue" appearing in
the button row under the console. The AI Settings caption also still
described the pre-August flow: a "File as GitHub issue" button that
"opens your browser", and "one-click issue filing from the error dialog".
There is no error dialog.

REPRODUCED HEADLESS BEFORE THE FIX with a probe script that was not
committed. TestIssue117EndToEnd in
tests/qt/test_a_failed_run_offers_the_report_it_promised.py drives the
same path and is the reproducible form of it. The probe used the real Mask

sign-in line under "spaCR output". Also: the button was enabled, 0 reports
were submitted, 0 previews were opened, and `ai_explanation_of(tb)`
returned the sign-in line.

WHAT WAS DONE
--------------------------------------------------------------------------------

1. spacr/qt/ai/providers.py: a CLI that exits non-zero raises the new
   `ProviderFailed(RuntimeError)` after its last line has streamed. The
   message quotes the last three non-blank lines (at most 400 characters)
   and, when the provider is known, its `login_command`, as in the
   Providers dialog. For Claude that is now `claude auth login`; see the
   2026-09-19 review note at the end for why it is no longer
   `claude setup-token`. Cancel,
   `terminate_all_streams` and the reader's own escalation mark the Popen
   before they signal it, and a marked child is never reported as failing.
   That matters on Windows, where `terminate` exits the child with 1.
   `manuscript.generate_sections` already catches exceptions from
   `stream_chat` and falls back with "The <provider> provider failed: ...".
   It now gets that fallback, not "the reply carried neither heading".
2. spacr/qt/ai/worker.py: an exception that arrives after Cancel reports
   "Cancelled.", not the exception.
3. spacr/qt/widgets/console_panel.py `_on_chunk`: a recreated reply block
   opens its own "spaCR AI" heading. An uninterrupted reply still has one.
4. spacr/qt/screens/app_screen.py: when the report action is on and
   reporting is not set to 'never', `_on_finished` writes directly under
   "✗ Failed":
       [issue] Nothing was sent to GitHub. Reports are public, so spaCR
       files one only when you press File as issue and then Send report.
   It is said once per failure. A stopped run drops it.
5. spacr/qt/widgets/ai_chat_panel.py: the AI Settings caption and toggle
   now describe the flow as it is, including "Nothing is sent
   automatically".

DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

* Filing automatically. The maintainer's consent decision (instruction 45)
  forbids it. The console now says so; nothing more was changed.
* THE 'always' CHOICE IS INERT, AND IT IS A PROMISE. First-run setup
  (spacr/qt/setup_screen.py `questions()`, "One-click issue filing")
  offers ask / never / always. Item 56 defined 'always' as "file without
  prompting". Since 807ba9e0a nothing reads it: `_on_file_issue` checks
  only for 'never', so 'always' behaves exactly like 'ask'. A user who
  picked 'always' was told spaCR would file without asking. The new
  console line now tells them at the failure that it did not. Whether
  'always' should open the preview by itself when a run fails (still no
  send without the click) or be removed from the choices is the
  maintainer's decision. Removing it also touches the setup slides, the
  catalogs and the `_issue_prompt_does_not_block` fixture in
  tests/qt/conftest.py, which sets 'always' for every Qt test.

  though a click filed it, which is every time now (issue_report.py
  `build_report`). Not changed here: the same line carries the
  fingerprint that `github_auth.find_issue_by_fingerprint` searches issue
  bodies for, so rewording it is a change to the dedupe as well.
* A FINDING, not fixed: the tooltip for `route_errors_through_ai` in
  spacr/settings.py says "Default False". The getter
  `spacr.qt.ai.settings.get_route_errors_through_ai` defaults to True.
* The annotate screen's console (`note_console_error`) gets no "nothing
  was sent" line. It reveals its button on a console error, not on a
  failed run, and #117 did not reach it.

The review returned FLAWED, with one should-fix and five nits.

SHOULD-FIX, FIXED: THE SIGN-IN COMMAND DID NOT SIGN IN. The hint after
`[AI error]` named `ClaudeCliProvider.login_command`, and that has been
`claude setup-token` since f3506ff13 (2026-07-21). Measured against the
Claude Code 2.1.274 on this machine:
`claude setup-token --help` says "Set up a long-lived authentication token".
The binary's strings show that after the browser step it prints "Long-lived
authentication token created successfully!", "Store this token securely.
You won't be able to see it again." and "export
CLAUDE_CODE_OAUTH_TOKEN=<token>". So it mints a token for an environment
variable and leaves `claude` itself signed out. The #117 user could follow
the hint, ask again, and fail the same way. `claude auth --help` lists
`login` as "Sign in to your Anthropic account", which is the command-line
form of the `/login` that the CLI itself asks for. The attribute is now
`claude auth login`. That fixes all four places that read it: the
`[AI error]` hint, the Login row of the Providers dialog, first-run
setup's "Sign in now" (which runs the command in a terminal), and the
manuscript writer's advice. Neither command was taken through its
browser step here, because that needs an account.
