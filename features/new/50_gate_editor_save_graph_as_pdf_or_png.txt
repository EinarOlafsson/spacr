================================================================================
SAVE THE GATE EDITOR'S GRAPH AS PDF OR PNG
================================================================================

Status:    DONE 2026-09-25 -- print style decided and built; see the closing section.
Requested: 2026-08-08 — "for the gate editor. the user should be able to save the graph as a pdf or png."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not started. The gate editor draws onto `GateCanvas`
(`spacr/qt/widgets/gate_editor.py`), a matplotlib canvas via `GraphCanvas`
in `spacr/qt/widgets/graph_builder.py`. There is no export.

Everything needed already exists elsewhere:
`spacr/qt/widgets/figure_queue.py :: render_figure_to_png` renders a
figure honouring the preferences, and `_export_vector_pdf` writes a true
vector PDF rather than a raster wrapped in one.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A gated population is a figure panel. Without export the user screenshots
the window, which loses the vector text a journal needs and bakes in the
application's theme colours.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. A save action on the gate editor that writes the current graph.
2. Format and resolution come from the EXISTING preferences --
   `get_figure_format()` and `get_figure_png_dpi()` in
   `spacr/qt/preferences.py`. Do NOT add a second setting; instruction 35
   makes the same point for the search figure grid, and two places to set
   "am I making PDFs" is one too many.
3. Offer an explicit choice at save time as well, since "save as" is when
   a user thinks about format, but let the preference be the default.
4. Reuse `render_figure_to_png` / `_export_vector_pdf` rather than calling
   `savefig` directly -- they already handle the theme colours, and a plot
   exported with the dark theme's white-on-black is unusable on paper.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Save a gated graph as PDF and the text in it selects as text in a PDF
reader. Save as PNG and the resolution matches the preference. Both open
with readable, print-appropriate colours regardless of the app theme.

Nothing yet -- not started.

--------------------------------------------------------------------------------
2026-08-08 - DONE
--------------------------------------------------------------------------------

A "Save graph..." button beside "Export gates...", and `save_graph()` on
the screen.

NO SECOND SETTING, which the instruction was explicit about. The default
format is `get_figure_format()` from Preferences and the resolution is
`get_figure_png_dpi()`; the file dialog offers the other format first in
its filter list so a single save can differ, because "save as" is when a
user thinks about format.

It goes through `render_figure_to_png` rather than `savefig`. That helper
restyles the figure for print before writing, and in PDF mode writes a
genuine vector PDF beside the PNG via `_export_vector_pdf`. Calling
matplotlib directly would export the dark theme's colours -- white text on
black -- which is unusable on paper, and that restyle is the entire reason
the helper exists.

MEASURED on a scatter of 60 points:

    graph.png   44,460 bytes
    graph.pdf   10,039 bytes

The PDF being four times SMALLER is the evidence it is vector rather than a
raster in a wrapper; a wrapped raster comes out at least as large as the
PNG. The test asserts that relationship rather than a byte count.

An empty canvas writes NOTHING and says so in the console, rather than
producing a blank file that looks like a result.

`GraphCanvas.figure()` is new -- a public accessor, so the screen does not
reach into `_figure`. 6 tests; 72 pass across the gates, console and export
suites.

2026-08-25 -- RE-AUDIT: TWO OF THREE CRITERIA HOLD; THE PRINT-COLOUR ONE DOES NOT
--------------------------------------------------------------------------------

MEASURED, driving the real screen with a 60-point scatter.

  PDF TEXT IS TEXT.       The written page carries /Font objects and
                          `pypdf` extracts the axis prose straight out of
                          it. `_export_vector_pdf` forces `pdf.fonttype=42`
                          for the save, so the glyphs are embedded TrueType
                          rather than Type 3 outlines. HOLDS.

  PNG RESOLUTION.         `get_figure_png_dpi()` is 300 and the written
                          PNG carries 300 dpi, 1947x1215 px. HOLDS.

  PRINT-APPROPRIATE       DOES NOT HOLD at the default preference.
  COLOURS REGARDLESS
  OF THE APP THEME.       With the theme set to dark, `get_figure_colors()`
                          returns ('none', '#ffffff'): the exported PNG's
                          corner pixel is (255,255,255,0) -- fully
                          transparent -- and the title and axis labels are
                          #ffffff. Composited onto white by a PDF reader, a
                          printer or a browser, the text is invisible.

WHY, AND WHY IT IS NOT A SIMPLE BUG. Two later decisions moved underneath
this file:

  * `preferences.auto_figure_colors` resolves "auto" to a TRANSPARENT
    background rather than the theme's window colour -- the fix for the
    opaque black slab behind every plot, and what lets the page-opacity
    preference reach a figure.
  * `figure_queue._export_vector_pdf` states in its own docstring that the
    background deliberately STAYS the app theme's, because
    `FigureQueue._request_pdf_refinement` rasterises that same PDF and
    swaps it in as the on-screen pixmap; a white page would make every
    figure flash from dark to light. It also notes that `facecolor="white"`
    alone would be worse, not better, because the artists are already
    painted for the dark theme.

So the export follows the theme ON PURPOSE, and this file's acceptance
criterion was written before that was true. The escape hatch exists: setting
the figure background and text colours EXPLICITLY (rather than leaving them
on "follow the theme") gives a print-ready file, and re-renders both.

CORRECTED HERE: `GateEditorScreen.save_graph`'s docstring claimed
`render_figure_to_png` "restyles the figure for print first" and that a dark
export would be "white text on black, which is unusable on paper". The
second sentence is the symptom the code now produces, not one it prevents.
The docstring now says what the helper actually applies and where the
print-colour decision is made.

NEEDS A DECISION, NOT A PATCH: whether saving a graph to a file the user
opens outside spaCR should take a print restyle that the on-screen
refinement path does not. That spans `render_figure_to_png`,
`_export_vector_pdf` and the figure-queue pixmap swap, so it is not a
one-line change and is left for the coordinator.

2026-09-25 -- DECIDED AND BUILT: SAVED GRAPHS GET A WHITE PRINT STYLE
--------------------------------------------------------------------------------

Maintainer decision (2026-09-25): "saved graphs (PDF/PNG) get a WHITE PRINT
STYLE (white background, dark text/axes/lines) whatever the screen theme".
Screen rendering unchanged.

WHAT WAS BUILT (spacr/qt/widgets/figure_queue.py):

  * `render_figure_to_png(fig, png_path, *, for_print=False, write_pdf=None)`.
    `for_print=True` goes through the new private helper
    `_render_print_copy`: the figure is copied (the save-figure dialog's
    pickle round trip, `copy_figure`), the COPY is styled with
    `PRINT_BACKGROUND` "#ffffff" and `PRINT_INK` "#000000" for text, spines
    and ticks, and the PNG is written opaque at the full DPI preference (no
    display cap -- a saved file is not a screen raster). A figure that
    cannot be pickled is styled in place, written, and then put back to the
    screen colours in a `finally`.
  * `_export_vector_pdf` is unchanged in behaviour: it paints the page it is
    handed. Its docstring now says the print path hands it a white page on a
    print-styled copy, and the gallery path still hands it the theme page.
  * THE PIXMAP SWAP is untouched and cannot see a white page: the print
    files are written where the user asked, never beside a gallery PNG, so
    `FigureQueue._request_pdf_refinement` only ever rasterises the
    theme-coloured sibling page. No flash from dark to light.
  * `write_pdf` lets a save dialog decide the PDF from the chosen
    extension; `None` still follows the figure-format preference.

GATE EDITOR: `GateEditorScreen.save_graph` passes `for_print=True` and
`write_pdf=(suffix == ".pdf")`, so picking PDF under a PNG preference now
writes a PDF too (before, only the PNG appeared and was reported). The
docstring no longer tells the user to set explicit colours as a workaround.

TESTS (tests/test_figure_pdf_output.py, tests/qt/test_cov_gate_editor_screen.py,
tests/qt/test_cov_wf_qt_screens_gate_editor.py):
  * dark theme ("none", "#ffffff") -> saved PNG corner (255,255,255,255),
    dark ink present, sibling PDF written;
  * the on-screen figure's face and title colours are identical before and
    after a print save; the uncopyable fallback restores them too;
  * the gallery path still paints the theme page;
  * save_graph passes for_print=True.
  280 passed across the figure-queue and gate-editor suites.
