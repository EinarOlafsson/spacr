================================================================================
THE REPRODUCIBILITY HASH SHOULD BE OPT-IN
================================================================================

Status:    done 2026-08-08 - off by default, toggle on the Performance tab, `input_hashing` stated in the manifest, --hash-inputs/--no-hash-inputs on the CLI. Measured ~0.55 s/GB warm.
Requested: 2026-08-06 - "there is a reproducibility hash that sometimes takes a very long time. i would like this to be opt in, with a setting in preferences to activate this feature."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not investigated yet. spacr/run_journal.py writes a per-run manifest -
version, git hash, settings, INPUT HASHES, timings - and the input hashes
are the suspect: hashing every input file of a plate is O(bytes on disk),
which on a real screen is tens of GB.

Find the actual call site before changing anything. Candidates:
run_journal.py, spacr/repro.py / cli_repro.py, and anything calling a
hashing helper over `src`.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A user waiting minutes on a hash they did not ask for, at the START of a run
they wanted to watch. Worse, it is invisible: the run looks hung.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Find where the hash is computed and how long it actually takes - MEASURE
   it on a real plate rather than assuming, so the default can be argued
   from a number.
2. Add a preference (spacr/qt/preferences.py has the store AND the dialog;
   see get_*/set_* pairs there for the pattern) defaulting to OFF.
3. The pipeline must not import Qt (ARCHITECTURE: a `from PySide6 import` in
   a pipeline module makes the package unimportable on a cluster). So the
   preference is read in the GUI and passed down as a setting, or the
   pipeline reads a plain config value - NOT the QSettings store.
4. When off, the manifest must still be written, and must SAY that hashing
   was skipped rather than omitting the field silently. A manifest that
   quietly lacks hashes is indistinguishable from one whose hashes matched.
5. The CLI needs the same switch, or a headless run cannot reproduce a GUI
   run.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

With the preference off, a run's manifest appears promptly and records that
hashing was skipped. With it on, the hashes are present and identical to
what is written today. Timed on the same plate both ways.

--------------------------------------------------------------------------------
2026-08-26 - RE-AUDIT: THE DEFAULT MOVED, BY A LATER REQUEST
--------------------------------------------------------------------------------

The acceptance criteria hold, driven rather than read:
tests/test_hash_inputs_opt_in.py passes (6), a run opened with no
`hash_inputs` setting writes `input_hashing: skipped` and
`performance.input_files: 0`, one opened with `hash_inputs: True` writes
`input_hashing: on` and counts the files, and `--hash-inputs` /
`--no-hash-inputs` are both on the CLI.

WHAT THIS FILE NOW SAYS WRONGLY: the status line above reads "off by
default". The PIPELINE default is still off -- `run_journal` reads
`settings.get("hash_inputs", False)`, so a headless or cluster run hashes
nothing unless asked -- but the GUI PREFERENCE ships ON:
`preferences.DEFAULT_HASH_INPUTS = True`. That was changed deliberately by
instruction 248 ("make sure all booleans are on by default:
reproducability hash / AI assistant on at launch / include recent logs in a
report -- should all be on"), and the reason is recorded beside the
constant: a result that cannot be traced back to its inputs is worth less
than the minutes, and the cost is refusable in one click.

So the feature is opt-in in the sense this file was filed for -- there is a
switch, the manifest states which way it went, and the CLI carries it -- and
the shipped GUI default is the opposite of what the status line claims.

NOT RE-MEASURED: "timed on the same plate both ways". That needs a real
plate; the ~0.55 s/GB warm figure in the status line stands on the earlier
measurement recorded in the test module's docstring.
