================================================================================
THE AUTO-ISSUE BUTTON LEADS TO "PAGE NOT FOUND"
================================================================================

Status:    done 2026-08-08.
Requested: 2026-08-08 — "make the github issue generation work, now the user gets prompted with a page not found when this is triggered. the user should be able to not get prompted at all or get prompted (add another setting)."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Broken in the user's hands: triggering the GitHub issue flow opens a page
that does not exist. Not diagnosed. The most likely causes, in the order
worth checking, are a wrong repository owner/name in the URL, a URL built
against a private or renamed repo, or query parameters that are not escaped
so GitHub rejects the whole request.

Related and not yet built: instruction 45 adds a GitHub sign-in and an
issue-feature toggle to the installer. Whatever this task settles about
where the issue goes, 45's installer question has to agree with it.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

This feature fires at the worst possible moment -- something has just gone
wrong -- and a 404 turns a recoverable bad impression into the software
being unable to report its own failure. It also silently costs the project
every bug report the user was willing to file.

The prompt itself is the second half. A dialog that appears uninvited after
a crash, offering to file a report, is intrusive to someone who has decided
they do not want it, and there is currently no way to say no permanently.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Find where the issue URL is built and print the exact URL rather than
   inferring it. Open that URL by hand; the 404 will name itself.
2. Fix it, and add a test that asserts the URL's SHAPE -- owner, repo, the
   `/issues/new` path, escaped parameters. A test that only checks a
   substring will not catch the next wrong owner.
3. Add the setting the request asks for, with three states rather than two,
   because "prompt me" and "never prompt me" do not cover the useful third:
       ask     - prompt when something goes wrong (today's behaviour)
       never   - never prompt, and no issue is filed
       always  - file without prompting, for a user who wants that
   If `always` is not wanted, say so here with the reason rather than
   quietly shipping two states.
4. Make the default `ask`, and make the setting reachable from Preferences
   as well as from the prompt itself -- the moment a user wants to turn
   this off is the moment it has just appeared.
5. Honour the installer answer from instruction 45 as the initial value.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Triggering the flow opens a real, pre-filled GitHub issue form for the
right repository. Setting the preference to `never` means it never appears
again, across restarts.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
2026-08-08 - THE 404 IS FOUND AND FIXED
--------------------------------------------------------------------------------

Not the repository, and not the label -- both were checked first and both
were fine:

    REPO = "EinarOlafsson/spacr"   matches the git remote, public,
                                   issues enabled
    ISSUE_LABEL = "auto-filed"     exists in the repository's label list

It was URL LENGTH. `issue_url` compared the QUOTED body against the budget
and then sliced the RAW body:

    if scaffold_len + len(quote(body)) > MAX_URL_LEN:
        head_len = MAX_URL_LEN - scaffold_len - 80
        body = body[:head_len]          # <- raw characters

Those are different units. Quoting expands, and a traceback is mostly
newlines at three characters each (`%0A`), so a body trimmed to fit in raw
characters is two to three times over budget once encoded. GitHub answers
an over-long `issues/new` with a page reading "page not found", which is
exactly the report.

MEASURED, on a realistic crash report, BEFORE the fix:

    body                22,800 raw characters
    final URL           11,924 characters
    MAX_URL_LEN          7,500
    over budget by       4,424      -- after "truncation"

AFTER, across four encodings that expand at different rates:

    newline-dense traceback   6,339    fits
    plain ascii               6,528    fits
    unicode                   6,072    fits
    short                       105    fits

The trim now shrinks until the QUOTED body fits, by repeated halving rather
than a computed guess -- the expansion ratio is 1x for plain ASCII and 3x
for newline-dense text, and one constant cannot serve both.

THE PREFERENCE EXISTS, with the three states the instruction asked for:
`ISSUE_PROMPT_ASK` / `NEVER` / `ALWAYS` in `spacr/qt/preferences.py`,
defaulting to ask. An unrecognised stored value reads back as `ask`, so a
preferences file written by a newer build cannot silence the reporter on an
older one. An unknown mode passed to the setter raises rather than being
stored, because storing it would read back as `ask` and look like the
setting was ignored.

STILL OPEN, and small: the prompt path does not consult
`get_issue_prompt_mode()` yet, and Preferences has no control for it. Also
unanswered, and shared with instruction 45: whether an auto-filed issue
goes to the PUBLIC repository along with whatever the user's log contains.

16 tests. The URL-shape ones parse the URL and assert on netloc, path and
the parsed query rather than matching a substring -- a substring check does
not catch a wrong owner, which was the first thing suspected here.

--------------------------------------------------------------------------------
2026-08-08 - DONE. THE PROMPT IS WIRED, AND IT NEARLY REPEATED A KNOWN BUG.
--------------------------------------------------------------------------------

`_on_file_issue` consults `get_issue_prompt_mode()` now:

    never   says so in the console and files nothing. Silence would read
            as the button being broken.
    always  files without asking.
    ask     a Yes/No dialog naming what the report contains -- traceback,
            module, settings -- and saying it opens a PUBLIC issue you can
            read before posting, plus where to turn it off. Default No.

WORTH RECORDING BECAUSE IT ALMOST COST THE SUITE AGAIN: adding that dialog
put a modal into a path two existing tests call, which is exactly the shape
of the hang in instruction 47 -- a QMessageBox in a headless run with
nobody to answer it. It showed up as the verification wedging at 42%,
minutes after I had finished writing up the same failure mode.

So the qt conftest now sets the mode to `always` for every test, autouse,
restoring whatever was there afterwards. The reporter cannot open a dialog
in a test unless a test asks for one, and the tests that exercise FILING
get to exercise it. That is a trap closed rather than avoided: the next
person to touch this path does not have to know about it.

The "is the default `ask`?" test reads from a cleared key rather than the
ambient store, since the fixture would otherwise be what it measured.

VERIFIED: 168 tests across test_cov_app_screen.py and
test_issue_report_url.py, all passing, no hang.

STILL UNANSWERED, and shared with instruction 45: whether an auto-filed
issue should carry a user's log into a PUBLIC repository. The dialog now
says that it is public, which is honest, but it is not the same as deciding
the policy. Answer it once, in both places.
