Asked 2026-08-28, while spaCR was crashing on launch: "there should be a start
spacr in safe mode triggered by safespacr that turns everything it can off and
just starts the bare minimum, so settings can be changed and resaved e.g."

A console entry point `safespacr` beside `spacr` and `spaceout`. It brings up
the least that can still show and save settings, and turns OFF everything that
is not needed to do that:

* no animated backdrop, no fractal, no OpenGL of any kind -- the crash log
  points at the GL path (295), so safe mode must never create a GL context;
* no preloading, no background import thread;
* no verbose tracing, whatever the saved preference says (294);
* no GPU probe, no CUDA import;
* plain widgets, default font, no theme animation.

WHY IT MATTERS: when a saved preference is what makes spaCR die on launch,
there is currently no way in. Safe mode has to be reachable without reading
the preference that is breaking it -- so it must not load the same preferences
path that a normal start does, or it inherits the fault it exists to escape.
It reads settings, lets the user change and RE-SAVE them, and exits.

Verify by making a normal start impossible -- write a preference that crashes
it -- and asserting `safespacr` still opens and can rewrite that value.

2026-09-15 -- THE TWO PREFERENCES.PY GAPS, CLOSED

1. SAFE MODE NO LONGER IMPORTS THE BACKDROP MODULE. apply_ambient_preferences
   imported spacr.qt.widgets.ambient to look for widgets to hide before it
   asked whether the backdrop was on. It now returns first when the backdrop
   is off and the module is not in sys.modules: no widget of a class whose
   module was never imported can exist. test_safespacr_does_not_import_the_
   backdrop_module is a plain test now. Negative control, early return
   removed: it fails with the module back in the list.

2. A SAFE-MODE SAVE KEEPS WHAT THE USER DID NOT TOUCH. The dialog now shows
   the STORED values: PreferencesDialog.__new__ points the store the getters
   read at the real one for the synchronous build only (the move
   _reset_to_defaults makes towards an empty one) and puts the shadow back
   afterwards. Untouched controls write back exactly what is stored. The
   START still reads nothing from the store, and apply_preferences_to_app
   after Save still reads defaults, so the running safe session never takes
   on the stored values.

   the repair in this very test (Cells back to the default, Blobs) is a
   choice of the value already on screen, so it would have written nothing
   and the next start would die again. And a dry-run of the save to find
   what changed would push the stored theme, log levels, font weight and
   performance level into the live safe process, because those setters
   apply as well as store.

   test_safespacr_opens_anyway_and_saves_the_repair now requires the dialog

2026-09-19 — CLOSED: SAFE MODE KEEPS THE DEFAULT THEME AND FONTS

The last verdict above read "PARTLY, unchanged: the default theme stylesheet
and bundled fonts load ... not asked for in this round". It was asked this
round. Put to the maintainer through the question prompt on 2026-09-19, the
answer was: "Safe mode keeps the default theme and fonts".
The quoted wording is the answer as the session that asked recorded it
and relayed it to this one; the prompt itself is not in the repository.

WHY THAT IS NOT A HOLE IN SAFE MODE, as this file already recorded: the
default theme and fonts are not read from any stored preference, because
safe mode answers every preference read with its default
(`preferences.enable_safe_mode`). A broken saved theme or font scale
therefore cannot reach a safe-mode start; what loads is the built-in default,
which is what the maintainer chose to keep.

Checked in the tree today: spacr/qt/safespacr.py `main` calls
`enable_safe_mode()`, sets SPACR_NO_GL and SPACR_NO_BACKDROP, and hands over
to `spacr.qt.run` with `--no-setup`, so the ordinary theme path runs on
default values. Nothing was changed in code and no test was run for this
note.
