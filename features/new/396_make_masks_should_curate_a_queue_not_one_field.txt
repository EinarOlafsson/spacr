--------------------------------------------------------------------------------
WHAT PROMPTED IT
--------------------------------------------------------------------------------

The maintainer curates Toxoplasma PV masks with a BESPOKE 1,900-line Qt tool
living outside spaCR, in another project's `code/tools/curate_masks_qt.py`,
and asked the obvious question: why not use Make Masks?

The answer today is that Make Masks is the better EDITOR and the bespoke tool
is the better WORKFLOW, and neither is both.

MAKE MASKS ALREADY HAS THE EDITING. `save_curated_mask`, brush, erase, erase
object, wand +/-, draw, divide, recrop, undo -- nine tools, and it loads
images with `<folder>/masks` and saves `uint16` TIFFs. It also already carries
the six-decimal percentile fix from 391 part five, which the external tool did
not.

WHAT IT DOES NOT HAVE IS A QUEUE, and that is what makes a 329-image curation
session survivable rather than exhausting:

    --folder <dir>          a queue of bundles rather than one folder
    --order easy|prob|value|name    work the easy ones first, or the most
                            uncertain first; ordering IS the productivity
                            feature, because a curator's judgement is worth
                            more on the hard ones and they should not spend
                            it on the first hundred easy ones
    --limit N               stop after N, so a session has an end
    curate_status.csv       done / skip per stem, written into the queue
                            folder, so the work RESUMES -- and because that
                            file syncs, resumes across machines

    Measured 2026-09-12: 500 bundles, 366 done, 29 skip, 105 remaining. None
    of that state can be expressed in Make Masks today.

AND IT CANNOT BE STARTED FROM A TERMINAL. `spacr/cli.py:732` refuses by
design: "Make Masks is a manual mask editor; run it in the GUI (spacr-qt)."
That is defensible for a mouse-driven tool, but it means a curation session
cannot be scripted, pointed at a folder, or resumed from a shell -- which is
how the maintainer actually works, over SSH, on two machines.

--------------------------------------------------------------------------------
WHAT TO BUILD
--------------------------------------------------------------------------------

  * A FOLDER ARGUMENT that reaches Make Masks, and a CLI entry point that
    opens it there. The refusal at cli.py:732 becomes "opens the editor on
    this folder" rather than "use the GUI".
  * A RESUMABLE STATUS FILE beside the images, with done and skip as distinct
    states. Skip is not a lesser done: it records "this one cannot be
    curated", and losing that distinction means the same unusable field is
    offered again every session.
  * ORDERING, and `easy` as the default because that is what the external
    tool chose after use.
  * A LIMIT, so a session is a bounded piece of work.

ONE LAYOUT MISMATCH TO SETTLE FIRST. Make Masks documents `<folder>` holding
images with `<folder>/masks` beneath. The curation sets in the field are laid
out as SIBLING `images/` and `masks/` directories. Whichever wins, the other
has to be accepted or converted, and silently assuming one is how a folder
full of work gets loaded as empty.

--------------------------------------------------------------------------------
WHY IT IS WORTH DOING RATHER THAN LEAVING TWO TOOLS
--------------------------------------------------------------------------------

The external tool is unmaintained by anyone but its author, untranslated,
untested, and outside the repository -- so its defects are found by the
maintainer in the middle of a curation session rather than by CI. One was
found that way on the day this was filed: the contrast percentile appeared to
stop responding above 99.99. It turned out NOT to be a widget rounding bug at
all -- the control already accepted 13 decimals -- but a saturated bright end
on 69 of 253 images, where no number of decimals can subdivide identical
pixels, and a control that said nothing about it. Inside spaCR that class of
thing is caught by the tooltip-quality gates and the percentile tests.

Two tools also means two answers to the same question. spaCR's Make Masks and
the external tool disagree about defaults, about what a percentile means, and
about whether a mask is saved as it is edited -- and a curator moving between
them carries assumptions that are true in one and false in the other.

IN PLACE, AND WHY IT IS SOUND (so there is no convert step)
  * SIBLING differs from nested only in where the masks folder is. The editor
    opens <root>/images and every mask read and write is given
    masks_dir=<root>/masks (spacr/qt/mask_engine.py: load_image_and_mask,
    mask_save_path, save_mask, write_recrop, recrop_child_name,
    retire_recropped_original all take it; MakeMasksScreen._layout_kwargs
    passes it only for a sibling session, so the nested calls are the same
    calls as before). A recrop child's image joins images/, its mask joins
    <root>/masks.
  * SEG: the editor's file list names the bundles, and a name ending in
    _seg.npy is read and written as a bundle. Save loads the dict, replaces
    `masks` with canonical_labels (ids kept, as for TIFFs), redraws
    `outlines` if the bundle had one, resizes `ismanual` to the new largest
    id (old flags kept, new ids flagged manual), keeps every other key, and
    writes through a dot-named temp file and a rename. That is what the
    external tool did to the same files (np.save of the loaded dict with
    masks replaced), less its stale outlines. The image shown is, in the
    external tool's order: the original named by `source_image`, looked for
    BY NAME beside the bundle (the stored absolute path is never touched --
    it is another machine's mount); the embedded `img`; a <stem>.<ext>
    display image beside it. A recrop of a bundle writes a bundle,
    <base>__rNN_seg.npy, in the external tool's form, because a TIFF child
    would make the folder two layouts at once and the queue refuses those.
  * A convert step would have been a second copy of every field, and the
    curator would have had to know which copy was the truth.

WHAT THE REVIEW FOUND (should-fix), AND IT WAS RIGHT
  The note above said "the editor shows them in its status line when the
  session opens". On the maintainer's sets it did not. A field of 8 MB or
  more loads on a background thread and lands AFTER `open_queue` returns,
  and `_apply_loaded_pair` then wrote `<file> (1/N)` over the notice.
  Every real bundle is over that line (curate_single 14-17 MB, round3_queue
  about 12 MB), so the "N of M field(s) have no probability" warning showed
  for a fraction of a second. The tests used 256x256 fixtures, which load
  on the GUI thread and never took that path. The load-time size filter
  wrote over the line as well, whenever it dropped something.

  Fixed in `spacr/qt/screens/make_masks.py`: `open_queue` keeps the notice in
  `_session_notice` while the first field is still loading, and
  `_apply_loaded_pair` adds it to the status line AFTER the load-time filter
  has written there. It is shown once, with whichever field lands first.
  Opening any other folder drops it.

THE NITS, FIXED WHERE THEY WERE CHEAP
  * The partial-scores notice said `easy` "ranks them below every scored
    field". That is `prob`'s rule. Under `easy` an unscored populated draft
    comes BEFORE a scored empty one. The easy sentence now says populated
    drafts still come first, and that within each group the unscored come
    last. A test pins both the order and the words.
  * "resuming from <name>_status.csv ... progress is written back there" was
    printed to the terminal only. It is now one of `CurationQueue.notices`,
    so the editor tells the curator that saves update a file outside the
    folder they opened.
  * `QueueLayout.status_path` said it returned `curate_status.csv`. It now
    says it may return the external record.
  * The external tool looks for a bundle's original by name in
    `<project>/new_originals/`, then `<project>/training_data/`, then beside
    the bundle (`_load_original`, curate_masks_qt.py:1193, where `<project>`
    is the queue folder's parent). spaCR looked only beside the bundle, so
    for a set whose originals are in one of those folders it showed the
    8-bit embedded `img` where the external tool showed the 16-bit original.
    `_bundle_image` now searches all three, in the tool's order. It still
    never stats the stored absolute path. On the two real sets neither
    folder exists beside the queue (checked with `ls`, read-only), so what
    they show does not change.
