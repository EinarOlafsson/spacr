--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

The original 267-entry chrome-only catalogue translated about 4% of the
strings on a representative Mask screen. The new source-derived catalogues
cover 3,011 current runtime entries in every non-English language: 697 setting
labels, 697 authored setting tooltips, 159 category explanations, 1,369 static
or dynamic UI phrases and 54 module summaries.

English function docstrings remain in the Python source. Nine separate
symbol-keyed API catalogues under docs/source/_static/i18n/api each cover all
6,101 current public docstrings and carry the SHA-256 of the corresponding
English source. The two docstrings changed concurrently during finalization
use exact English fallback text because the local models produced technically
unsafe mixed-language drafts; all other source-current entries remain in the
external language catalogues.

README translations and language navigation exist for Swedish, German,
Spanish, Simplified Chinese, Portuguese, Hindi, Korean, Icelandic and French.
All ten installer locales contain the exact same 57 keys. Windows, macOS and
Linux builders generate their platform resources from those JSON files,
select the operating-system locale and fall back to English.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

Changing the language now changes the working surface rather than only its
menus. Scientific text is more dangerous when mistranslated than when it is
left in English, so format fields, identifiers, code literals, URLs and option
values are immutable and low-confidence changed API prose falls back safely.
The terminology sweep explicitly corrects software and microscopy senses of
screen, run, crop, mask, flow, plate, well, cell, guide, hit and gate.

WHAT WAS DONE
--------------------------------------------------------------------------------

* Added external generated runtime catalogues and wired them into widget-tree
  retranslation, settings, authored tooltips, accessible text and module help.
* Added reviewed domain-term and source-conditioned false-friend corrections,
  including regression tests for known errors such as French l'criblage.

  selector and freshness/structure audits; no translated prose was inserted

* Added a reproducible coverage report at docs/i18n/COVERAGE.md and kept
  generated installer intermediates out of version control.
* Made API generation incremental: a current source hash preserves reviewed
  text and only new or changed symbols are sent to a model.

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

Raw worker output, logs, tracebacks, user paths, database values, annotations,
measurements, predictions and saved scientific results remain canonical data
and are not translated. A new public docstring may temporarily use English
fallback until a technically sound translation is available; its source hash
makes that state explicit and prevents stale prose from being displayed.

2026-09-13 -- THE GATE WAS THROWING AWAY CORRECT CHINESE AND KOREAN, AND THE
FIX WAS ALREADY WRITTEN ONE PATTERN BELOW IT
--------------------------------------------------------------------------------

Four settings tooltips had sat untranslated in zh_CN for weeks --
`barcode_set`, `organelleb_background`, `organellec_background`,
`organelled_background` -- and every repair pass reported them as MADLAD
failures with `reasons=['protected_syntax']`. Read that way it is a translation
problem, and the obvious response is the one this item has used before:
shorten the English and split it until the model copes.

THAT WAS THE WRONG DIAGNOSIS. MADLAD had been producing correct Chinese the
whole time and the checker could not see it.

`_syntax_preserved` protects snake_case identifiers so a translation cannot
mangle a setting name. Its rule was

    \b[A-Za-z][A-Za-z0-9]*_[A-Za-z0-9_]+\b

and CJK and Hangul are WORD CHARACTERS to Python's `re`, so `\b` never fires
between them and an ASCII letter:

    "the floor that remove_background_organelle 4 clips"   -> matched
    "地面remove_background_organelle,4个剪辑"               -> NO MATCH

The identifier is there, byte for byte. The protector counts it as missing,
concludes the model dropped a protected token, and rejects the translation.

  CHINESE DOES NOT SPACE-SEPARATE WORDS AND KOREAN PARTICLES ATTACH DIRECTLY,
  so this fires on essentially any caption in those languages that names a
  setting. Measured: 677 of 5,176 English captions contain a snake_case
  identifier, 567 of them SETTING_TOOLTIPS -- against 2 of the 9 languages.

THE REPAIR WAS ALREADY IN THE FILE, TWELVE LINES LOWER. The class-name pattern
beside it reads

    (?<![A-Za-z0-9_])[A-Z][A-Za-z0-9]*(?:Error|Exception|...)(?![A-Za-z0-9_])

with the comment: "ASCII identifier boundaries are intentional: Korean case
particles commonly attach directly to the class name and remain translatable
prose rather than part of the Python identifier." Somebody met this exact
problem, solved it correctly for one pattern, wrote down why, and the
neighbouring pattern kept `\b`.

VERIFIED IN THREE DIRECTIONS rather than just made green:

    correct translation, identifier abutting CJK     now ACCEPTED
    translation with the identifier MANGLED          still REJECTED
    ASCII source against itself                      unchanged

and controlled against the suite: 4 failed / 169 passed with the change,
4 failed / 169 passed without it -- the same four, already red beforehand.

  I FIRST MEASURED 13 FAILURES AND NEARLY REVERTED. Two of my changes were
  live at once, and the other one -- an English tooltip rewrite -- invalidates
  catalogs by itself. Splitting them is what showed the regex was innocent.

THE PAYOFF, measured after one repair pass: the untranslated list went from
FOUR keys to ONE. `barcode_set` gained 132 Chinese characters,
`organellec_background` and `organelled_background` 43 each.
`organelleb_background` remains and is a separate question.

WHAT THIS SAYS ABOUT THE ITEM'S HISTORY. Any earlier count of "captions this
model cannot translate" was measuring the gate as much as the model, for the
two languages whose script has no spaces. A re-audit of zh_CN and ko coverage
is worth doing now that the instrument reports what the model actually
produced.

2026-09-13, LATER -- A ONE-LINE WRAPPER HID 117 STATUS MESSAGES FROM THE
EXTRACTOR, AND THIS ITEM'S COVERAGE NUMBERS NEVER COUNTED THEM
--------------------------------------------------------------------------------

The entry above fixed the gate that was REJECTING correct translations. This is
the other half, found the same afternoon by chasing a single red in Map
Barcodes: a class of caption that never reached the catalogs to be translated
at all.

TWENTY-THREE SCREENS WRITE THEIR STATUS LINE THROUGH A WRAPPER:

    def _set_status(self, text: str, error: bool = False) -> None:
        set_translatable_text(self.status, text, ...)

and call it with a literal -- `self._set_status("Choose a destination folder
first.")`. The extractor walks `set_translatable_text` calls, so it reads the
FORWARDING line, sees a parameter named `text`, and records nothing. The
literal is one frame away and invisible.

    UI sources   2871 -> 2988      new 117      removed 0

  THESE ARE NOT EDGE CASES. They are what the screen says while it works:
  "A comparison is already running…", "Choose a coefficient table.",
  "Add at least one mask folder -- a spaCR project without object masks has
  nothing to measure." Every one of them has been English in all nine
  languages for as long as the wrapper has existed. The heaviest users are
  db_browser (33 call sites), foreign (30), model_zoo (27), image_import (24),
  batch (23), convert (20).

WHAT THIS DOES TO THIS ITEM'S HISTORY. Every coverage percentage recorded here
was computed over the captions the extractor could see. 117 user-facing strings
were outside that set, so the denominator was wrong -- not by much against
2,871, but the missing ones were concentrated in exactly the text a user reads
while waiting for something to finish.

  TWO BLIND SPOTS, ONE AFTERNOON, OPPOSITE DIRECTIONS. The `\b` bug REJECTED
  translations that existed. This one never ASKED for translations at all. Both
  were invisible in the coverage report, because a caption the extractor cannot
  see is absent from the numerator and the denominator alike.

THE FIX NAMES THE WRAPPER rather than removing it. `_set_status` is in
`builder._TEXT_METHODS` with its template as the first positional argument, and
the static-template guard exempts a forwarding call whose parameter belongs to
a wrapper the extractor already covers -- so the exemption exists exactly where
the call sites are reachable, and every other call stays strict.

WHAT REMAINS: the nine-language rebuild for the 117, running when this was
written. Until it lands the catalog audits are red, and that is the honest
state -- the strings were always untranslated, and are now visibly so rather
than silently so.
