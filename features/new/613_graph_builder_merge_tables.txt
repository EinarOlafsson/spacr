WHAT TO DO AND HOW TO KNOW IT WORKED

Add table merging to **both Graph Builder and Gate Editor**, using Regression's existing table-merging capability as the starting point.

### Interface and default spaCR merge behavior

Add a **Merge tables** button immediately to the right of the table dropdown in each interface. It must open a popup styled like the other spaCR windows, using the shared theme, controls, fonts, spacing, and window behavior.

**Provide an established default merging mechanism, consistent with the existing table-merging behavior elsewhere in spaCR.** Inspect Regression and the other current merging paths to identify the shared/default implementation. Reuse that behavior rather than inventing different join rules for Graph Builder and Gate Editor. Where existing callers intentionally use different observation levels, preserve those distinctions and select the appropriate existing convention for the requested output. Document the actual defaults after inspecting the code; do not assume particular column names or aggregation rules in advance.

For a compatible spaCR database, the ordinary workflow must work without manually configuring join keys or relationships. Prepopulate the relevant base/observation level, identifiers, relationships, join behavior, and type-appropriate aggregation defaults using the existing mechanism. Show a readable summary of these defaults rather than hiding how the data will be combined.

The popup must allow the user to:

- Tick multiple available tables, including cell, nucleus, cytoplasm, pathogen, organelle, and other compatible tables in the selected data source.
- Inspect the default output observation level and merge configuration, with ordinary supported choices where appropriate.
- Choose aggregation methods appropriate to different data types, with per-column overrides where needed and existing spaCR defaults selected initially.
- Name the merged result and inspect a preview or summary before creating it.
- Open a separate **Customize merging** button to change the default mechanism when needed, particularly for databases not generated by spaCR.

Numeric options should include appropriate supported methods such as mean, median, sum, minimum, maximum, and count. Provide suitable categorical/text/Boolean handling rather than treating every column as a continuous measurement. Make deterministic behavior and incompatible operations clear.

### Customize merging for alternative and non-spaCR databases

The **Customize merging** button must be available in the merge popup in both Graph Builder and Gate Editor. It must open an advanced configuration panel or dialog using the same spaCR styling. It must change the actual merge configuration, not merely display informational text. Ordinary spaCR users must not be forced through this advanced workflow.

Show a clear warning on entering customization and require explicit acknowledgment before applying a customized merge. Suggested text:

> Custom merging changes spaCR's standard table relationships and aggregation rules. It is intended for non-spaCR databases or deliberately different schemas. Incorrect settings can link unrelated objects, duplicate or omit observations, and change measurements used in plots and gates. Check the join keys, output level, aggregation, and preview before applying.

Keep the warning visible or readily accessible while editing, and clearly indicate when custom rather than default rules are active. Canceling customization must leave the previous configuration unchanged. Provide **Reset to spaCR defaults** to restore the established mechanism.

The advanced controls must support the actual configurable merge model, including:

- Mapping alternative table and column names to the roles required by the merge without renaming or modifying source tables.
- Selecting the base table/output observation level and explicit join keys, including composite keys when needed.
- Configuring supported relationships, join types, and aggregation rules for different column types, with per-column overrides where needed.
- Inspecting how unmatched records, missing values, and duplicate keys will be handled under the selected configuration.

Validate both the selected schema and the resulting merge. Preview relevant input/output row counts, unmatched records, duplicate-key/cardinality problems, and representative output before applying. Do not silently fall back to default spaCR assumptions when required keys are missing from a non-spaCR database. Explain what mapping is required instead. A warning acknowledgment must not disable validation or permit a silently invalid join.

Preserve source data and record the custom configuration with the derived table so the result is reproducible. Scope saved configurations to their data source/schema, revalidate them on reuse, and do not silently apply one database's custom mapping to another. Keep plotting and gating functional for compatible custom results. Where external data lack image/object provenance needed for a particular navigation or linking action, explain that limitation and disable only the unsupported action rather than inventing those associations or rejecting otherwise valid tabular analysis.

### Merge correctness

- Reuse Regression's backend or extract shared functionality as needed. Preserve Regression's existing behavior and add tests against regressions there.
- Discover available tables and their schemas from the selected data source. Do not hard-code only the example tables named above.
- Determine relationships from the real schema. Do not assume that object IDs alone are globally unique or that identically named IDs in different object tables refer to the same objects.
- Make the output observation level explicit. For one row per base object, aggregate one-to-many child tables to the correct composite join keys before joining.
- Prevent accidental many-to-many joins and Cartesian multiplication. Multiple pathogens and organelles associated with one cell must not multiply that cell's measurements or inflate aggregates.
- Keep identifiers and required provenance separate from measured columns. Do not average or sum IDs as though they were measurements.
- Handle missing values and mixed types deliberately. Do not silently replace missing measurements with zero or coerce incompatible values into misleading results.
- Give overlapping columns deterministic, unambiguous names, such as table-prefixed names.
- Reject incompatible combinations or unavailable relationships with an actionable explanation rather than silently producing an invalid merge.
- Preserve the original tables. Reuse the existing virtual/derived-table or persistence pattern instead of overwriting source measurements.

### Use the merged result

After merging, the named result must appear in the table dropdown and be selected or immediately selectable. It must be a functional data source, not just a dropdown label.

Graph Builder must be able to plot its columns. Gate Editor must be able to create and apply gates using its columns while retaining correct links to the underlying objects. Preserve the identifiers and metadata needed for those operations.

Integrate merged-table definitions/results into the existing data-source lifecycle. Keep them available through ordinary interface refreshes, do not reuse them incorrectly after switching databases, and retain enough configuration to reproduce the merge. Where saved graphs or gates reference a merged result, save or reconstruct the required merge definition rather than leaving a broken reference.

Use the same merging behavior in both interfaces rather than maintaining divergent implementations.

**Acceptance:** In both interfaces, verify that a standard spaCR database merges using the existing default mechanism without advanced configuration. Test the customization button, warning and acknowledgment, cancel behavior, reset to defaults, and the visible default/custom state. Use a representative non-spaCR test database with alternative table/column names to verify that valid explicit mappings actually work. Test one-to-one and one-to-many relationships, multiple child tables, repeated IDs across images, overlapping column names, missing data, incompatible tables, aggregation choices, source-table preservation, and actual plotting/gating. Test missing image provenance without fabricated object links. Include regression tests proving equivalence to the applicable existing default merge and proving that joins do not duplicate base observations or inflate aggregates. Verify saved custom configurations are reproducible and do not leak between databases.
