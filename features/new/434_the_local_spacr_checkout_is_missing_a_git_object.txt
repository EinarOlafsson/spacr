--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

The ledger is how the concurrent sessions coordinate, and it only works if
every session can fetch nightly. From this checkout:

  * `git pull` / `git fetch` fail outright, so no session working here sees
    what the others have pushed.
  * `origin/nightly` is frozen at a commit from last year, so anything that
    compares against it (diffs, `--not --remotes`, promotion tooling) reasons
    about a branch that no longer exists.
  * A push from here is made without knowing the current tip, which invites
    rejected pushes or, worse, work rebuilt on a stale base.

It is also silent until someone fetches: status, diff and local commits all
still look normal.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

Do step 1 before anything else, whichever route follows. Sixty files of other
sessions' work are uncommitted in this checkout, and neither route may lose
them.

1. Snapshot the working tree, independent of git (so a damaged object store
   cannot block the backup):

       R=/home/carruthers/Documents/repo/spacr-claude
       B=/media/carruthers/mnt3/claude/spacr_backup_$(date +%Y%m%d_%H%M)
       rsync -a --exclude .git "$R"/ "$B"/worktree/
       cp -a "$R"/.git "$B"/dotgit
       git -C "$R" status --porcelain > "$B"/status_before.txt

2. ROUTE A — preferred, touches nothing but the object store.
   `git fetch --refetch` re-downloads every object reachable from the remote,
   which restores 984b725 without touching the working tree or the index.
   It needs git >= 2.36, and the system git is 2.34.1. A newer git from
   conda-forge avoids changing the system install:

       conda create -y -n gitnew -c conda-forge git
       G=/home/carruthers/anaconda3/envs/gitnew/bin/git
       $G -C "$R" fetch --refetch origin
       $G -C "$R" fsck --connectivity-only

   If fsck is clean, stop here and go to HOW TO KNOW IT WORKED.

3. ROUTE B — only if route A fails: re-clone and transplant.

   a. Export commits that exist only locally (they are not on any remote and
      would otherwise be lost):

          git -C "$R" log --oneline spacr-claude --not --remotes
          git -C "$R" format-patch --binary -o "$B"/local_commits \
              $(git -C "$R" merge-base spacr-claude origin/main)..spacr-claude

      If format-patch fails because a local-only commit needs the missing
      object, record which commit and recover its content from "$B"/worktree.

   b. Fresh clone, recreate the branch, replay the local commits:

          git clone https://github.com/EinarOlafsson/spacr.git "$R".fresh
          git -C "$R".fresh checkout -b spacr-claude origin/nightly
          git -C "$R".fresh am "$B"/local_commits/*.patch

   c. Restore the uncommitted state exactly, from the rsync snapshot:

          rsync -a --exclude .git "$B"/worktree/ "$R".fresh/

   d. Swap, keeping the damaged copy until verified:

          mv "$R" "$R".damaged && mv "$R".fresh "$R"

   Tell the other sessions before step d: their paths do not change, but a
   session with a file open mid-swap will be writing into the old directory.

2026-09-20 -- THE OBJECT WAS HERE ALL ALONG, AND IT TRAVELS AS TEXT
--------------------------------------------------------------------------------

THE FIRST THING TO CHECK WAS NOT CHECKED WHEN THIS WAS FILED: whether the
other machine has the object. It does.

    $ git cat-file -t 984b725b5a11346ebf011808812d562a43869fc7
    commit
    $ git log -1 --format='%h %ad %s' --date=short 984b725b5
    984b725b5 2026-07-21 test(qt): 46 pytest-qt tests covering theme, widgets...

It is UNREACHABLE here -- on no branch, local or remote -- which is why
nothing on this machine ever noticed. It is still what the server's packs
delta against, which is why the work box cannot fetch.

WHY IT TRAVELS AS TEXT RATHER THAN AS A PACKFILE. A single-object packfile
was made first and works: 840 bytes, and `git index-pack --stdin` in an
empty repository makes `git cat-file -t` answer `commit`. It is not what
was committed, because the object is a COMMIT -- a few lines of text -- and
git names an object by the SHA-1 of `"<type> <length>\0<content>"`. So the
commit written back byte for byte gets the name it had:

    $ git hash-object -t commit -w --stdin < 984b725b....commit
    984b725b5a11346ebf011808812d562a43869fc7

PROVED, not assumed: done in a fresh `git init` directory, and the name it
printed is the name in the file. A text file is reviewable in a diff,
verifiable by anyone, and -- the part that decides it -- downloadable
through a web browser on a machine whose `git fetch` does not work. Which is
precisely the machine that needs it.

WHERE IT IS: `tools/repair/984b725b5a11346ebf011808812d562a43869fc7.commit`,
1,708 bytes, with `tools/repair/README.md` beside it.

WHAT TO DO ON THE WORK BOX, and the download must NOT be a git fetch --
that is the broken thing:

    cd /home/carruthers/Documents/repo/spacr-claude
    git hash-object -t commit -w --stdin < 984b725b....commit
    git cat-file -t 984b725b5a11346ebf011808812d562a43869fc7    # -> commit
    git fetch origin nightly                                     # works again

IF THE NAME IT PRINTS IS NOT THE NAME IN THE FILE, STOP. The file was
altered in transit and writing it has put a DIFFERENT object into the
store, which is a new problem rather than a fix.

GUARDED: `tests/test_a_missing_object_can_be_put_back.py` recomputes the
name from the bytes in the repository, so a file that rots fails in CI
rather than on the machine that has no other way to get it. It also holds
that the README still says fetch is the broken thing -- without that
sentence the first thing a reader tries is the one thing that cannot work.

Nothing here can reach that machine.
