meets this on their first run concludes the application is broken.

It also silently invalidates 284's badge. An instruction that closed on a
green ratchet, whose behaviour has since regressed without the ratchet firing,
means the ratchet is not running on the path the user actually takes.

MEASURED: A COLD LAUNCH COMPOSED THE STYLESHEET FIVE TIMES
----------------------------------------------------------
Found while working the failing-test list, not by looking for it.

`register_widget_qss` re-applied the whole application stylesheet the moment
a block was registered. That is right for one screen module arriving on its
own long after startup -- it must be styled before it can paint -- and it is
quadratic for a run of them. Building MainWindow imports four such modules,
so `launch` composed the sheet five times where one is owed:

    1  app.py:4608          launch, before the window
    2  shortcuts.py         imported by MainWindow.__init__
    3  settings_search.py   imported by shortcuts.install
    4  recipes.py           imported by shortcuts.install
    5  screens/map_barcodes.py  imported by shortcuts.install

Four of the five were thrown away by the next one.

Fixed with `theme.batched_widget_qss()`, a reentrant scope that collects the
names and restyles once on the way out. `launch` opens it around the
MainWindow construction, which is safe because the window has not been shown
yet, so the single flush still lands before first paint. Cold launch: 5 -> 2.
The two that remain are both owed -- one before the window so its widgets are
built against the right palette and font metrics, one after to fold in the
blocks its modules brought.

HONESTLY, THOUGH: THIS IS NOT THE HANG.
`apply_preferences_to_app` measures at a median of 5 ms (min 5, max 6, n=7,
warm, all registrars loaded). Removing three of them is worth about 16 ms.
That is worth having and it is three orders of magnitude short of the
multi-second delay reported here. Recorded so that nobody reads the 5 -> 2 as
the explanation and stops looking. The cause of the reported hang is still
open; what this closes is a real inefficiency found on the way past, and a
guard against it coming back.

The guard is tests/qt/test_the_window_comes_before_the_dialog_filters.py
::test_the_theme_is_resolved_twice_and_not_once_per_screen_module. It counts
the blocks registered while the window is built ALONGSIDE the restyles,
because a restyle per registering module and one restyle for all of them are
indistinguishable if you only count restyles.

THE TWO PATHS THAT COULD BLOCK THE GUI THREAD ARE ALREADY GUARDED, so
whoever picks this up does not spend the afternoon finding that out:

  * `AppScreen._install_ambient` checks `_heavy_lock_is_free()` and
    defers on a 120 ms timer rather than waiting. The comment there
    records the original measurement -- 83% of a 3148 ms block was the
    backdrop constructor waiting for a lock the startup preloader held.
  * `fractal_travel` acquires the same lock with a TIMEOUT and raises
    `_HeavyImportInProgress` rather than blocking.
  * The preloader itself runs on a WORKER thread. It holds the lock
    through each import, which is what the two guards above exist for.

So the freeze this instruction describes has a known mechanism and that
mechanism is handled. What is reported now is either a different one or a
regression in those guards.

A GUARD NOW EXISTS FOR THE SHAPE ITSELF:
`tests/qt/test_opening_things_does_not_hang.py`. Instruction 314's own
observation is that 284's ratchet fails a module at ten seconds and a
hang has no number, so the ceilings there are deliberately generous --
20 s for a module, 10 s for a Preferences build, against measured costs
of 1.34 s and 0.42 s. It is watching for stuck, not for slow. It also
pins that `_install_ambient` still checks the lock and still retries,
because that check is what a refactor would quietly remove.

WHAT IS STILL NEEDED, and it can only come from the machine that saw it:

  1. WHICH MACHINE, and whether it was the first launch after an install
     -- the preloader's imports are slowest with a cold disk cache, and
     that is when the lock is held longest.
  2. WHETHER THE WINDOW WAS RESPONSIVE during the hang. A frozen window

     appearing is a worker that never finished, and they have different

  3. `~/.spacr/logs/spacr.log` from that session. The timing spans are
     logged, so the slow step names itself.
  4. Whether Preferences was slow ONLY the first time. It builds in

     are different faults.

the event loop can interleave, or off the GUI thread entirely. The

2026-09-01 (later still) — THE STACK-DUMP ATTEMPT, AND HOW TO MAKE IT WORK
--------------------------------------------------------------------------------

Step 3 of this instruction says to attach
`faulthandler.dump_traceback_later` and take the stack while it hangs.
Attempted; it half worked, and the half that did not is worth writing
down because it will stop the next attempt in the same place.

  THE BENCHMARK RUNS THE APP IN A CHILD. `_run_worker` does
  `subprocess.run([sys.executable, "-c", WORKER])`, so a faulthandler
  armed in the parent only ever catches the parent blocked in
  `subprocess.communicate`. Twenty-one identical dumps of nothing.

  THE CHILD'S ENVIRONMENT IS REBUILT, and `_worker_environment` sets
  `PYTHONPATH` to the repo root outright rather than extending it -- so
  a `sitecustomize.py` on PYTHONPATH does not reach the child either.
  Putting one at the repo root does, because that IS the child's
  PYTHONPATH. Remove it afterwards; it is not something to commit.

  THE DUMP FILE MUST BE UNBUFFERED. faulthandler writes to the file
  descriptor, and a plain `open` held most dumps in memory until exit:
  three landed out of an expected twenty.

  AND SOMETHING RE-ARMS IT. Even unbuffered at a 1 s interval, only five
  dumps landed across a ~45 s run. spaCR installs its own fatal-signal
  handler at launch -- the log line "fatal-signal stacks will be written
  to ..." -- and arming faulthandler there cancels an externally armed
  `dump_traceback_later`. THAT is the thing to solve first next time:
  either have spaCR's own handler leave an existing periodic dump alone,
  or drive the dump from outside with SIGQUIT.

WHAT THE FIVE DUMPS DID SHOW, none of which is the regression stall:
two consecutive seconds inside `iconset.reink` / `_load_rgba` during
HOME construction, and later frames in the ambient renderer's own
thread. Chasing the icon lead: a cold icon cache costs 1.90 s at
MainWindow construction against roughly 1.0 s warm, and changes module
opening not at all -- regression is 0.86 s either way. So icon theming
is a startup cost worth knowing about and is NOT this defect.

ELEVEN CAUSES NOW ELIMINATED. Added since the last note: the Qt
translators (`install_qt_translations` returns False here and regression
stays at 0.82 s), pressing the real sidebar button rather than calling
the handler (0.85 s), draining the event loop until genuinely idle
rather than for a fixed number of turns (0.82 s -- so the harness was
not stopping its clock early), and a cold icon cache (0.86 s).

2026-09-03: THE STACK, TAKEN WHILE IT WAS STALLED. STEP 3 DONE.
--------------------------------------------------------------------------------

`faulthandler.dump_traceback_later(1.2, repeat=True)` around
`MainWindow._on_nav_selected("regression")`. Four samples landed inside the
freeze; the main thread was in two places, and BOTH are ordinary synchronous
GUI-thread work rather than anything waiting on IO or a lock:

  SAMPLE 1, about 1.2 s in -- BUILDING THE SCREEN.

      app.py:5151   _on_nav_selected
      app.py:5404   _build_screen
      app.py:5514   _build_screen_timed
      app_screen.py:1366   AppScreen.__init__
          -> body.addWidget(self._build_runtime_panel())
      app_screen.py:5658   _build_runtime_panel
          -> left.addTab(self._results_split, "Results")

  SAMPLE 2, about 2.4 s in -- INSERTING IT INTO THE STACK.

      app.py:5169   _on_nav_selected
          -> self._stack.addWidget(self._screens[key])

THE SECOND ONE IS THE SURPRISE AND IS WORTH SAYING PLAINLY: `addWidget` on a
`QStackedWidget` is not free. It reparents the screen, which polishes it --
Qt walks the whole widget tree resolving the stylesheet against every child.
Regression's tree is the largest in the application, and this is a single
statement that no reading of the code would flag as a cost.

  The line above it is `self._theme_screen(...)`, wrapped in a try because
  "decoration must never stop a screen from opening". The sample landed on
  the line AFTER it, so the reparent-polish is its own cost and not theming
  spilling over -- but the two are adjacent and both walk the same tree, so
  measure them together before attributing.

THE OTHER THREAD WAS IDLE THROUGHOUT -- `ambient.py:4389` in
`threading.Event.wait`, which is the backdrop animation parked correctly.
Nothing here is lock contention.

WHAT THIS MEANS FOR THE FIX, and why it is not attempted tonight: both
hotspots are the ordinary construction path of the most-used screen in the
application. Making them cheaper means either building less at construction
(the runtime panel's Results tab is built whether or not anybody opens it)
or paying the polish somewhere the user is not waiting. Both are design
changes to the path every module open takes, and instruction 364 records the
same warning about the same screen: worth doing deliberately, not at two in
the morning.

  A CHEAP FIRST MEASUREMENT FOR WHOEVER TAKES IT: time
  `_build_runtime_panel` alone, then time `addWidget` alone, on Regression
  and on Annotate (0.20 s, the fastest module). The ratio between those two
  screens will say whether the cost is per-widget -- in which case building
  less is the fix -- or a fixed cost per open, which points somewhere else
  entirely.
