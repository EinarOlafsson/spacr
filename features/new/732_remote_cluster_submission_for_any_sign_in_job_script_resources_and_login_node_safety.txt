--------------------------------------------------------------------------------
WHAT THE STATE WAS
--------------------------------------------------------------------------------

The failed job used the SSH backend: spaCR ran `spacr-run mask --settings
<path>` directly on whatever host the ssh connection reached, which was a
Great Lakes login node. Exit code 127 is the shell's "command not found":
`spacr-run` was not on PATH there, because nothing ran `module load mamba` and
`mamba activate spacr` first. The profile had one "spaCR runner" field, the
Slurm script was fixed (`exec RUNNER MODULE --settings PATH`), resources could
only be typed as raw sbatch flags, nothing stopped compute on a login node,
and the job details and log tail sat in a separate read-only pane.

--------------------------------------------------------------------------------
WHAT WAS BUILT (spacr/remote_execution.py, spacr/qt/screens/distributed_jobs.py,
spacr/cli_remote.py; no new modules)
--------------------------------------------------------------------------------

1. Sign-in for any mechanism (ExecutionProfile.auth_mode; blank follows the
   old ssh_interactive switch, so saved profiles keep working):
   - openssh: the system ssh with the user's SSH config (Host aliases,
     ProxyJump, Include), keys and agent. A ControlMaster without a
     ControlPath now gets a private socket in spaCR's state folder, so the
     connection really is reused. "Copy terminal sign-in command" gives
     `ssh -o ControlMaster=auto -o ControlPersist=4h ... -fN HOST`: sign in
     once in a terminal (password, Okta, Duo) and spaCR reuses it.
   - interactive: the existing in-spaCR session (699) - password and
     keyboard-interactive prompts (Duo, Okta, any MFA) shown verbatim in the
     GUI, optional OS keychain for the password only.
   - gssapi: OpenSSH with GSSAPIAuthentication and credential delegation, for
     a Kerberos ticket from kinit.
   - custom: the user's own ssh command (ExecutionProfile.ssh_command) with
     {host} and {command}; the command is appended when {command} is absent.
     A command naming sshpass or containing "password" is refused: passwords
     never go into a profile.
2. A user-editable job script (ExecutionProfile.job_script, env_setup):
   - A code editor in the module's "Job script" card, with presets (Slurm
     sbatch, PBS/Torque qsub, LSF bsub, plain ssh), environment presets
     (module load mamba + mamba activate spacr, conda activate, venv, pip
     install spacr, pip install --upgrade spacr) and an Insert-placeholder
     list: {settings_path} {job_dir} {module} {job_name} {log_dir}
     {log_path} {workdir} {job_id} {gpus} {cpus} {mem} {time} {partition}
     {account} {qos} {env_setup} {scheduler_directives} {run_command}
     {runner_check} {runner}. Shell ${VAR} is left alone; an unknown
     placeholder is refused when the profile is saved.
   - Nothing is appended: the template decides the command. The default
     template still runs `exec spacr-run MODULE --settings PATH` after the
     environment lines and a runner check that, if spacr-run is missing,
     ends with 127 and says which setup lines to add.
   - Preview: the "Preview" button prints the rendered script to the
     console, and Submit shows it for confirmation before anything is sent.
     The rendered script is kept on the job record and as job.sh in the
     local job folder.
   - New PBS/Torque (qsub/qstat -x -f/qdel) and LSF (bsub/bjobs/bkill)
     backends sit beside SSH, Slurm and custom command.
3. User-defined resources per profile (ExecutionProfile.resources): a
   "Resources" card with partition/queue, account, QoS, GPUs, GPU type, CPUs
   per task, memory, wall time, nodes, mail type and address, and extra
   scheduler lines, rendered as #SBATCH / #PBS / #BSUB lines. Values are
   validated so none can become two arguments. "Read cluster" fills the
   partition, account, QoS and GPU-type lists with the cluster's real values;
   "Check against cluster" (and every save) lists requests the reported
   nodes, time limits or accounts cannot meet.
4. Login-node safeguard:
   - spaCR inserts a guard after the scheduler lines of every script: with
     no SLURM_JOB_ID/PBS_JOBID/LSB_JOBID, a host name matching *login* or
     the profile's "Login hosts" patterns, or any installed sbatch/qsub/bsub,
     it refuses with exit 97 and a clear message. The ssh launch runs the
     same guard before it starts anything, and a direct-run profile whose
     host matches a login pattern is refused before any connection.
   - "Run directly over ssh (no scheduler)" is an explicit, warned opt-in,
     SSH backend only, for private workstations and clusters with no
     scheduler.
   - Start allocation: a Slurm allocation with the profile's resources
     (a held batch job, so the request never blocks spaCR in a busy queue).
     When it is running, "Run inside" lists it and jobs run in it as srun
     steps on the compute node; cancelling one cancels only its step.
     "Copy shell command" gives `ssh -t HOST srun --jobid=ID --overlap --pty
     bash -l` for interactive work on the node.
5. UI:
   - The jobs table is in a Card (the glass panel: rounded, translucent).
   - The details/log pane is gone; a standard ConsolePanel prints job events
     (submitted, status changes, the script, a selected job's summary).
     A failed job goes through append_error, so spaCR AI explains it as it
     does any error; problems the user can fix are amber warnings.
   - Log following: active jobs' logs stream into the console at the poll
     interval over the same connection (ControlMaster or the in-spaCR
     session); the remote side reports the byte offset, so nothing repeats
     or is skipped, and following stops when the job ends.
   - A System panel shows what the profile reaches on the cluster, from
     read-only queries (sinfo, sacctmgr show assoc, qstat -Q, bqueues,
     nproc, free, nvidia-smi): partitions with nodes, CPUs, memory and GPUs
     per node, GPU types and time limits, and the user's accounts and QoS.
     The last reading is remembered per profile.
   - The profile editor gains Preset (one is "Slurm with module load mamba
     and mamba activate spacr (Great Lakes style)"), Sign-in method, Custom
     SSH command, Copy terminal sign-in command, Login hosts and Run
     directly over ssh.
6. spacr-remote: `profile add` takes --auth-mode, --ssh-command,
   --resource KEY=VALUE, --env-setup, --job-script-file, --login-hosts and
   --direct-run; new `script` (print the rendered script), `resources` (read
   the cluster, check the profile), `allocate`, `submit --allocation`, and
   `watch --follow` (stream the log).
7. Exit 127 and 97 on a failed job are explained in the job's error.

     spacr (Great Lakes style)", SSH host gl (or greatlakes.arc-ts.umich.edu),
     Sign-in method "Sign in in spaCR" (Kerberos password + Okta), Login hosts
     gl-login*, Remote work directory /home/<you>/spacr, Save.
  2. Test connection: hostname, then sinfo, with one Okta approval.
  3. Read cluster: the System panel lists Great Lakes partitions (standard,
     gpu, largemem, ...), GPUs per node and your accounts; pick your account
     in Resources, set GPUs/CPUs/memory/time, Save resources: no warnings.
  4. Job script: Preview; check that module load mamba / mamba activate
     spacr come before `exec spacr-run mask --settings ...` and the #SBATCH
     lines match your own script. If spacr is not installed in that env, add
     "pip install spacr" from the environment presets.
  5. Submit a small mask job; confirm the preview; the console shows the
     Slurm id, then the log lines as the job runs, and the final state.
  6. Make one deliberate failure (remove the mamba lines, submit): the job
     fails with exit 127 and the console's spaCR AI error names the missing
     environment setup.
  7. Login-node check: make an SSH-backend profile for the same host with
     Run directly over ssh OFF and submit: spaCR must refuse ("cluster login
     node") and run nothing.
  8. Start allocation (GPU 1, 1 hour), wait for "running", choose it under
     Run inside, submit; on the cluster `squeue -s -u $USER` shows the srun
     step on a compute node. Copy shell command opens a shell on that node.
     Cancel the allocation when done.
  9. Optional: Sign-in method OpenSSH + "Copy terminal sign-in command" in a

--------------------------------------------------------------------------------
DELIBERATELY NOT DONE
--------------------------------------------------------------------------------

- No `tail -f` process is left running on the cluster: the log is read in
  offset-checked chunks at the poll interval over the existing connection.
  A long-lived tail would hold a remote process and a channel per job and
  die silently with the connection; chunks resume after a reconnect and
  stop by themselves when the job ends.
- Allocations use a held sbatch job rather than a blocking `salloc
  --no-shell`: salloc waits in spaCR while the queue is busy. The srun
  steps and the interactive `srun --pty` shell are the same as with salloc.
- PBS and LSF have no allocation button: their interactive forms
  (qsub -I, bsub -Is) need a terminal; the message says so.
- OpenSSH password prompts are not proxied into the GUI (that would need an
  SSH_ASKPASS helper program, i.e. a new module): use "Sign in in spaCR" or
  sign in once in a terminal and reuse the ControlMaster.
- The profile fields are not spaCR module settings (spacr/settings.py), so
  they have no setting labels or consumer-map rows; their captions and
  tooltips are runtime UI text with nine-locale reviewed records.
