--------------------------------------------------------------------------------
THE SUSPECT, BEFORE MEASUREMENT
--------------------------------------------------------------------------------

A tooltip popup is a new top-level window. spacr/qt/theme.py installs an
application-wide event filter (`_SheetsEveryWindowThatAppears`) that sheets
every window as it appears. If that re-sheet or re-polish reaches the module
screen's layout containers, they lose the transparent tag set by
`AppScreen._clear_page_surfaces`, fall back to the blanket
`QWidget { background-color: bg }` rule, and paint `bg` -- #000000 on the dark
theme -- over the backdrop. Leaving and returning re-runs the sweep through
`refresh_ambient_background`, which is why it heals.

over a settings row, and assert zero pure-black samples down the settings
column AND the AI chat panel, while the tooltip is visible and after it
hides -- without leaving the module. And the test must be seen to FAIL on the
current code first.

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Reported by the user, not yet reproduced in a debugger by the filer. The
affected tooltip is the POPUP kind — the "tooltips box", gated by
`get_tooltips_box_enabled` / `get_tooltips_bottom_enabled`
(spacr/qt/preferences.py:3063, 3104) — NOT the inline per-object setting
tooltips, which the user says are fine. When that box appears, a black
rectangle shows up behind:
  * the left settings container, and
  * the AI Console (chat) box.
Leaving to Home or another module and coming back rebuilds those screens and
the black box is gone, so it is a live paint-state problem, not persisted.

Both panels are deliberately backdrop-transparent so the animated backdrop
shows through them: the settings container is tagged with `theme.make_transparent`
(wrapped in spacr/qt/prerun.py:309-318), and the AI Console likewise. Their
translucent, rounded fill is drawn by `theme.paint_panel` (spacr/qt/theme.py,
def near line 2432), which COMPOSITES over the backdrop and only works while the
widget stays `WA_TranslucentBackground` / unfilled.

`paint_panel`'s own docstring names this exact failure mode (theme.py:2440-2450):
an opaque `fillRect(self.rect(), surface)` — or the backdrop simply not reaching
the widget — makes it "read as a bare dark hole punched through the page." The
black box is that hole: for the duration the popup is up, these two panels stop
compositing the backdrop and paint opaque black instead.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

It is in front of the user constantly. Mask and Measure are the most-used
screens; the settings the user is reading and the chat they are typing into sit
on a black slab the moment a tooltip pops, and stay there until they navigate
away and back. It undermines the whole themed/backdrop look and reads as a
render crash. Cheap symptom, high visibility.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

1. Reproduce. Open Mask (or Measure), enable the tooltips box in preferences,
   hover a setting whose description shows in the box, and watch the settings
   container + AI Console background go black. Confirm the inline per-object
   tooltips do NOT trigger it (user's distinction).

2. Locate the tooltips-box show/hide path (the reader of
   get_tooltips_box_enabled / get_tooltips_bottom_enabled). Decide which of two
   mechanisms is at work:
     (a) showing the popup raises / re-parents a top-level that pulls the
         animated backdrop out from behind these panels, or
     (b) the popup's appearance triggers a paintEvent on the panels that takes
         an opaque fill path instead of `theme.paint_panel`.
   A quick check: log the panels' testAttribute(WA_TranslucentBackground) and
   autoFillBackground() before and during the popup.

3. Fix (verify the mechanism first). Smallest safe change: when the tooltips box
   shows/hides, re-assert the transparent-panel invariant on the affected panels

2026-09-15 -- FOUND BY THE WORK SESSION: A CROSS-FILE ENVIRONMENT LEAK
--------------------------------------------------------------------------------

The one-backdrop skips were real and could not be reproduced from one file,
because the cause is another file. Verified here after the work session found
it:

    test_one_backdrop_for_the_window.py alone             5 passed, 0 skipped
    test_crash_recovery_drops_the_backdrop.py first,
      then that file, one process                          5 SKIPPED
      (at :70, :95, :120, :158 and :223, all "the ambient backdrop is off")

MECHANISM. `take_the_backdrop_out_of_this_launch` (spacr/qt/crash_recovery.py
:141-142) writes SPACR_NO_GL and SPACR_NO_BACKDROP straight into os.environ,
and `get_ambient_enabled()` reads the environment ahead of the stored
preference. The crash-recovery test's "cleanup" is what keeps it: its
`monkeypatch.delenv("SPACR_NO_BACKDROP")` runs while the variable EXISTS, so
monkeypatch records the value and restores it at teardown. The work session
also found that a function-scoped restore fixture cannot fix it (it snapshots
pollution an earlier test in the same file already made); it has to be
module-scoped. Fixed by the work session in 60386cf08.

WHAT IT MEANT. The one-backdrop rule was checked when that file ran alone and
on CI runs where xdist put the two files on different workers, and was
silently unchecked -- green, asserting nothing -- in any process where the
crash-recovery file ran first. This file leans on that rule, so the guard it
cites was not always running.

THE PREFERENCE-FORCING CHANGE PREPARED HERE WAS DISCARDED, and it would not
have worked: forcing the stored preference on cannot beat an environment
variable read ahead of it, so under the leak it would have turned five skips
into five failures without fixing the cause.

SAME SHAPE, UNCHECKED: `spacr/qt/laptop_mode.py:196` also writes
SPACR_NO_BACKDROP into os.environ, and `spacr/qt/safespacr.py:31` writes
SPACR_NO_GL. Whether their tests leak the same way has not been measured.

WHY THE EARLIER PROBES SAW NOTHING: WA_StyleSheet stays True on the broken
widgets, the tag stays True, and no widget is built -- only the attributes
above move.

THE CAUSE, split out of the Enter handler part by part. Only `_write_hint`
does it (the bottom strip; `tooltips_bottom=true`), and only the first time:

  1. `_hold_the_hint` connects its new timer to `self._release_the_hint`, and
     PySide grows AppScreen's metaobject for it (50 -> 51 methods, a new
     pointer). Qt's next `ensurePolished` sees a different metaobject and
     polishes the screen again.
  2. That stylesheet polish raises PaletteChange on the screen, and
     `changeEvent` -> `refresh_ambient_background` -> `_install_ambient`
     (window backdrop shared) -> `_clear_page_surfaces` -> `make_transparent`
     runs INSIDE `QStyleSheetStyle::polish(screen)`.
  3. Qt's recursion guard refuses a polish nested in ANOTHER sheet style's
     call, and has no guard on unpolish. A widget with a sheet of its own
     (ConsoleSplit, ConsoleScroll, CategoryHintStrip) has its own
     QStyleSheetStyle, so it and its subtree -- the chat row and the chat
     input -- were unpolished and never polished again.

The popup looked like the trigger because the same hover shows it. Deferring
the handler one event-loop turn also keeps the chat box (measured), but the
handler is pinned synchronous by test_ambient_wiring and
test_a_module_screen_is_built_once_not_twice, so it is not what shipped.
RULED OUT: activation or focus (above), and a re-sheet of the main window --
only the popup is sheeted.

FIX: `make_transparent` skips a target whose tag is already in force (tagged
AND WA_StyleSheetTarget), so there is no unpolish left for Qt to half-refuse.
A widget a nested unpolish did reach has WA_StyleSheetTarget cleared, so it is
still re-polished, and heals at the next sweep as before. Every palette-event
sweep also stops re-polishing containers that are already transparent.
