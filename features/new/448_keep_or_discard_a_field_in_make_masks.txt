================================================================================
KEEP OR DISCARD A FIELD IN MAKE MASKS, AND A CSV THAT RECORDS THE VERDICT
================================================================================

Status:    BUILT 2026-09-20, the same day it was filed. Both buttons, the
           CSV and the rewrite rule are in, with 15 tests. The one open
           question was answered before the build: see the trailing note.

Requested: 2026-09-20 -- "in make masks there should be the ability to flag
           images as good or bad so a two new buttons keep and discard.
           clicking these makes a csv in the image/mask folderand annotates
           the image filename and masksfilename with a true or false in the
           keep column (image path, mask path, object count, keep; these are
           the columns in the csv.)"

WHAT IT IS FOR. Curation. A user walking a folder of fields in Make Masks
can already draw, split, merge and filter; what they cannot do is say "this
field is no good" in a way anything downstream can read. The verdict has to
leave the screen as data, not as a memory of which ones looked wrong.

WHAT TO BUILD
--------------------------------------------------------------------------------

TWO BUTTONS, Keep and Discard, beside the annotation tools in Make Masks --
the same place the FEATURES button of item 421 went, which is where a user
already goes to act on the field as a whole rather than on one object.

ONE CSV, with exactly the four columns the request names and in its order:

    image path, mask path, object count, keep

  * `image path`  -- the field that is open.
  * `mask path`   -- `mask_engine.mask_save_path(folder, filename, ...)`,
                     not a path rebuilt at the call site. That function
                     exists precisely so the ledger and the written file
                     agree on one name, and this CSV is another ledger.
  * `object count`-- `make_masks._object_count(labels)` over the mask as it
                     stands when the button is pressed, so a field curated
                     after hand editing records what the user saw.
  * `keep`        -- true for Keep, false for Discard.

WHERE IT GOES. The request says "in the image/mask folder". Make Masks knows
`self._folder` (the images) and resolves the masks folder through
`_layout_kwargs()`, and the two are not always the same place -- a run with
`masks_dir` set puts them apart. This needs the maintainer's answer before
it is built; see the open question below.

WHAT A SECOND PRESS DOES. Pressing Keep and then Discard on the same field
must leave ONE row for that field, with the later verdict, rather than two
rows that disagree. The CSV is read, the row for that image path is
replaced, and the file is rewritten -- and it is written the way spaCR
writes files it must not corrupt: to a temporary name in the same folder,
then renamed, so a reader never sees half of it.

HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * Keep then Discard on the same field leaves one row, keep false.
  * The object count in the row equals what the module's own readout says
    after an edit, not what the mask held when it was loaded.
  * A folder whose masks live elsewhere writes the mask path that
    `mask_save_path` returns, and the CSV lands where the answer below says.
  * The file is never observed half-written, and a CSV a user has open in
    another program does not cost them the verdict.
  * The buttons say what they did -- a field already marked shows its
    current verdict rather than looking unpressed.

OPEN QUESTION FOR THE MAINTAINER
--------------------------------------------------------------------------------

WHICH FOLDER, when the images and the masks are not in the same one? The
choices are the image folder (where the user pointed the module), the masks
folder (where its output goes), or both. Asked rather than guessed, because
a curation file in the wrong place is one nobody finds again.

RELATED. Item 421 put FEATURES in the same row of controls and writes its
own table from the same fields; whoever builds this should read how 421
resolves folder, filename and mask path rather than resolving them again.
Item 396 curates a QUEUE of fields, which is the other half of this idea --
a verdict per field is what a queue would consume.


--------------------------------------------------------------------------------
2026-09-20 -- BUILT, AND THE LAYOUT QUESTION ANSWERED
--------------------------------------------------------------------------------

THE ANSWER, through the question prompt: "the masks should alwasy be kept
with the images as /images/masks and the csv should live in images/csv a new
folder." So there is no branch for a split layout at all -- the masks are
where `masks_folder` already put them by default, and the CSV goes in a new
`csv/` folder beside them.

WHAT WAS BUILT

  spacr/qt/mask_engine.py
      CURATION_COLUMNS      the four the request names, in its order
      CURATION_CSV_NAME     keep_discard.csv
      curation_folder       <images>/csv
      curation_csv_path     <images>/csv/keep_discard.csv
      read_curation         every verdict, keyed by image path
      curation_verdict      one field's verdict, or None
      record_curation       writes one row, replacing the field's own

  spacr/qt/screens/make_masks.py
      Keep and Discard beside Features, both checkable so a field that is
      already marked shows it; `_on_curate`, `_curation_paths`,
      `_show_curation_verdict`, `_refresh_curation_buttons` and
      `_note_curation`. `_apply_loaded_pair` refreshes the pair when a
      field is opened, so walking back to a field shows the verdict it has.

THREE THINGS DECIDED WHILE BUILDING, each with its reason:

  * THE COUNT IS READ AT THE PRESS. `_objects_now()` counts the mask on the
    canvas, so a field curated after hand editing records what the user was
    looking at rather than what the file held when it was opened. A test
    deletes an object and checks the recorded count follows.
  * ONE ROW PER FIELD. Keep then Discard rewrites the field's row rather
    than appending a second one that disagrees with the first. Whoever
    reads this downstream cannot tell which press came last, and a CSV does
    not say.
  * A BROKEN CSV COSTS THE VERDICTS, NOT THE FOLDER. `read_curation`
    answers a missing, empty or corrupt file with no verdicts rather than
    raising. This is a curation aid; refusing to open a folder because
    somebody edited its CSV in a spreadsheet would be the wrong trade.

DISCARD DELETES NOTHING, and a test says so: the image, the mask and the
objects are all still there afterwards. The status line says
"discarded -- nothing was deleted" for the same reason.

WRITTEN THE WAY THE BUNDLES ARE: to a dot-name in the same folder, then
renamed over the target, so a reader never sees half a file. A test watches
`os.replace` to hold that.

MEASURED. 15 new tests (9 at the engine, 6 driving the screen) and 159
passed over the Make Masks and mask_engine selections with the no-comments
gate.

WHAT IS NOT DONE: the nine-language catalogs owe the two button captions,
their tooltips and the status sentence. Translations are low priority by
the maintainer's instruction of this date, so they go with the consolidated
pass.

2026-09-20 (later) -- A VERDICT NOW MOVES TO THE NEXT FIELD, AND THE BUTTONS MOVED
--------------------------------------------------------------------------------

Two follow-ups from the maintainer the same day:

  "also for hte keep discard button, pressing either should take the user
   to the next image"
  "so the buttons should also be beside preveous, next , discard, keep"

WHERE THEY ARE NOW. Out of the tools row beside Features, into the
navigation row, in the order the request names: Prev image, Next image,
Discard, Keep, then Save mask. They also joined `_sync_button_states`, so
they are disabled until a folder is open like every other control that
acts on a field -- they were the only two in that row that were not.

PRESSING EITHER ADVANCES. `_on_curate` ends in `_advance_after_verdict`,
which calls `_on_next` rather than moving the index itself, so there is one
definition of what next means: it retires a recrop first, and it stops at
the end of the folder instead of wrapping.

THE STATUS LINE HAD TO BE REBUILT, not appended to. `_note_curation` used to
read the status line, split it, and put "kept" after the field's name. That
cannot survive the move: loading the next field rewrites the line, so a
verdict appended before the move is gone a moment later, and one appended
after the move reads as a verdict on the field that just OPENED -- the
opposite of what happened. The name of the judged field is carried into
`_advance_after_verdict` and the sentence is built there:
"a.tif kept  —  now on b.tif", or "... that was the last field in this
folder" when there is nowhere to go.

WHAT THIS COSTS, and it is worth saying because it was free this morning:
KEEP THEN DISCARD NO LONGER CORRECTS A VERDICT. The first press has already
moved on, so the second marks the NEXT field. Changing your mind now means
walking back to the field and pressing again -- the buttons still show the
verdict a field already has, and the row is still replaced rather than
duplicated. `test_changing_the_verdict_replaces_the_row` was rewritten to
do exactly that, and it is the test that would have caught this being
silently lost.

FOUR TESTS ADDED, TWO REWRITTEN, in
tests/qt/test_keep_and_discard_mark_the_field.py: that a verdict moves to
the next field and is written for the field that WAS open rather than the
one it moved to; that the last field is still marked and the screen stays on
it; that the status line names the judged field and the new one; and the two
above that assumed a press left you where you were. 772 pass across the 27
Make Masks and magnifier files.

MEASURED AGAINST REAL DATA, not only the fixture: the engine was driven
against a staged folder of the live_cell project on /mnt/wd4tb (the sibling
layout, images/ and masks/ in different folders, which is the case this
item's open question was about). curation_folder resolves to
<images>/csv, mask_save_path returns the sibling mask, and keep-then-discard
on one field leaves one row reading false.

STILL NOT DONE, and now slightly larger: the nine-language catalogs owe the
two captions, their tooltips -- both reworded to say the press moves on --
and the status sentence.
