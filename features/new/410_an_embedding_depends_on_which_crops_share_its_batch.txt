--------------------------------------------------------------------------------
THE DEFECT, EXACTLY
--------------------------------------------------------------------------------

`EmbeddingSpec.normalize` (default True) is documented as "divide each channel
by its own 99th percentile". `_scaled` does that to whatever plane it is given
(spacr/embeddings.py:250-254), and `embed_array` gives it
`array[..., channel]` (lines 282 and 291) -- where `array` is the WHOLE BATCH,
shape (n, height, width, channels). So the percentile is taken over every crop
in the batch at once, not over each crop.

The consequence is that the same object is scaled differently depending on
its neighbours. Measured on one c1 crop from methods_paper plate1, channel-1
input mean after scaling:

    the crop alone                     0.311
    batched with other c1 crops        0.076
    batched with c2 crops              0.094

About a 4x change in input for an unchanged object, and a different change
for a c1 batch than for a c2 batch -- so a batch that is sorted by condition
leaks the condition into the scaling. With `normalize=False` the output is
identical alone or batched.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

An embedding is supposed to be a property of the object. When it is a property
of the object and its batch-mates, any comparison built on it -- retrieval,
kNN phenotype scores, clustering, Image UMAP -- can separate conditions for a
reason that is not biology. The 2026-09-12 run behind item 386 fed batches
sorted by column, so its resnet18 inputs were partly scaled per column; that
is one more reason item 395 was rerun from scratch rather than compared
against those numbers.

--------------------------------------------------------------------------------
WHAT TO DO -- A DECISION, THEN A SMALL CHANGE
--------------------------------------------------------------------------------

Three honest options:

  a. PER-CROP percentile. Each crop scaled by its own 99th percentile. Simple
     and batch-independent, but it throws away absolute intensity: a dim
     object and a bright one come out alike, which hurts any phenotype that
     IS brightness.
  b. A FIXED SCALE PER CHANNEL, carried by the spec and estimated once per
     plate from a random sample. This is what the 395 harness did (85, 79 and
     198 for channels 0-2, from 2,048 random crops) and it keeps relative
     intensity while removing the batch dependence. Needs a way to estimate
     and store the scale with a run.
  c. Keep batch scaling but shuffle batches. Reduces the condition leak and
     does not remove the dependence. Not recommended.

Whichever is chosen, the docstring of `EmbeddingSpec.normalize` changes, and
that block is pinned in the nine API catalogs, so the change ships with its
translations in the same push.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

A test that embeds one crop alone and the same crop inside two differently
composed batches, with the default spec, and asserts the scaled input and the
embedding are identical across all three -- and that fails on the current
code first.

--------------------------------------------------------------------------------
2026-09-15 -- THE MAINTAINER CHOSE A FIXED SCALE PER PLATE
--------------------------------------------------------------------------------

Asked through the question tool with the three options above. Chosen: "Fixed
scale per plate -- estimate one scale per channel from a random sample of the
plate, store it with the run, apply it to every crop. Keeps relative
brightness, removes the batch dependence." This is option (b), and it is what
the 395 benchmark harness already did (85, 79 and 198 for channels 0-2 from
2,048 random crops). Building it on its own branch; the batch-independence
test above is the acceptance check.


--------------------------------------------------------------------------------
2026-09-15: BUILT ON wip/410-plate-scale -- OPTION b, A FIXED SCALE PER PLATE
--------------------------------------------------------------------------------

Decided by the maintainer tonight: "Fixed scale per plate -- estimate one
scale per channel from a random sample of the plate, store it with the run,
apply it to every crop."

WHAT WAS BUILT, all in `spacr/embeddings.py`:

  * `EmbeddingSpec.channel_scale: Optional[Tuple[float, ...]] = None`, one
    value per ENCODED channel in encoding order. Validated where the spec is
    built (coerced to floats; finite and >= 0; refused with normalize=False;
    length checked against `channels` when they are named) and again against
    the crops in `_prepare` when `channels` is None. Zero is legal: it is what
    a channel blank across the plate estimates to, and it scales to zeros.
    `fingerprint()` appends the scale ONLY when set, so every unscaled spec
    keeps its pre-410 fingerprint (the default is still ee13fbde21d1062c,
    386's recorded run).
  * `_scaled(plane, scale)` never derives a scale from the plane it is given
    any more. That derivation WAS the defect: the plane is a whole batch.
  * `_estimate_channel_scale(crops, channels=None, *, sample_size=2048,
    seed=0, read_batch=256)`: the 99th percentile of every pixel in a random
    sample drawn without replacement by default_rng(seed), read in sorted
    index chunks of `read_batch` (works on an ndarray, memmap or HDF5
    dataset). A plate no larger than the sample is used whole, so the result
    is exactly the whole-plate percentile.
  * `_embed_plate(crops, spec, *, encoder, record, ...)`: THE PLATE PATH.
    Estimates once for every channel of the plate, writes
    `record["channel_scale"] = {"0": .., "1": ..}` and
    `record["channel_scale_sample"] = {percentile, size, seed, n_crops}` into
    the run's JSON-serialisable record, and reuses a record that already has
    one -- another backbone, batch size, channel subset or crop order sees
    the same numbers without re-estimating. A record missing a channel the
    run encodes is refused rather than topped up from a second sample.

WHERE THE PLATE IS EMBEDDED. There is no plate-embedding pipeline in spacr/
(395 already noted the retrieval harness was never committed). The one run in
the package is the Embeddings screen: `EmbeddingsScreen.embed` now calls
`_embed_plate` with a per-screen record that `set_crops` resets, so every
Embed on one loaded stack uses the scale the first one estimated, and
`screen._result.spec.channel_scale` carries it.

DIRECT CALLERS. `embed_array(crops, spec)` with normalize=True and no scale
treats the stack it was handed as the plate: it estimates the scale from a
random sample of that stack, applies it to every crop, logs a WARNING naming
the numbers, and returns them on `result.spec.channel_scale`. Chosen over
(i) raising, which breaks `embed_array(crops)` with the default spec in the
tutorial, the screen tests and every existing caller, and (ii) per-crop
scaling, which is option a -- the one the maintainer did not pick. For a stack
of up to 2,048 crops the numbers are IDENTICAL to pre-410 (asserted), so no
existing result moves; what changes is that the scale is visible and can be
passed on. The dependence on call composition remains for a caller who splits
one plate across calls without passing the scale on, and the warning and the
docstring both say so.

the pre-410 API failed on the arithmetic itself:
