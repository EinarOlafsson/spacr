--------------------------------------------------------------------------------
WHAT WAS ASKED
--------------------------------------------------------------------------------

spaCR is currently very slow to start and many modules are slow to open. On
lower-end hardware the delays approach unusable. Heavy libraries must be
loaded only when the operation that needs them is called. Systems with ample
RAM may retain reusable caches, while lower-memory systems must avoid or
release optional caches, model weights and other reclaimable state.

The required user-visible budgets are:

  * spaCR reaches a usable Home screen within 5.0 seconds;
  * a module becomes interactive within 10.0 seconds, that being the hard
    upper bound rather than the expected value for any module;

    (Relaxed from 2.0 and 4.0 on 2026-08-28 by the maintainer, after the
    original numbers had been met on every module but Mask and the remaining
    gap was Mask's own size rather than the startup path.)
  * the animated background continues to produce frames while a module loads.
    A module becoming ready must not be preceded by a frozen interface.

These are HIGH-PRIORITY product requirements, not optional benchmark work.

--------------------------------------------------------------------------------
THE IMPLEMENTATION CONTRACT
--------------------------------------------------------------------------------

1. MEASURE THE REAL USER PATH

Use the in-application timing seam from instruction 281. Measure process start
through a usable Home screen and an actual click through an interactive module.
Import-only scripts, constructor-only timings and preloader timings are useful
diagnostics but are not acceptance measurements. Record cold and warm values,
the machine profile, and peak resident memory.

2. IMPORT AT THE CALL BOUNDARY

Heavy optional dependencies are imported when the operation that needs them is
called, not merely because spaCR started or because the user opened a module.
Opening a configuration screen must not import a training or segmentation
stack that will never run. This must be asserted through ``sys.modules`` in a
fresh process, not inferred from elapsed time.

Python extension modules cannot honestly be unloaded. Lower-memory operation
therefore releases what can be released: data caches, decoded images, model
weights, allocator caches and GPU cache. Item 282 owns the configurable idle
timeout, cache ceiling, headroom floor, and laptop/workstation profiles.

3. KEEP THE INTERFACE ALIVE

Registration, discovery, imports, model inspection and other preparation that
can safely run outside the GUI thread must do so. Work that must create Qt
widgets on the GUI thread is divided into bounded event-loop slices. During
the complete click-to-ready interval, timing instrumentation must show that
the event loop and ambient frame stream continue to advance. A spinner over a
blocked event loop is not progress.

4. DO NOT BUY SPEED WITH WRONGNESS

Lazy loading must preserve the same settings, module capabilities, results,
errors and cleanup as the eager path. Do not silently omit an optional feature,
lower analysis quality, or report a module ready before its controls work.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * on the documented lower-end reference profile, a cold supported launch
    reaches an interactive Home screen in at most 2.0 seconds;
  * every registered module reaches an interactive state in at most 4.0
    seconds on that profile, and the measured distribution identifies which
    modules exceed 2.0 seconds instead of hiding them behind one mean;
  * fresh-process tests prove that starting spaCR and merely opening a module
    do not import heavy optional dependencies until the operation calls them;
  * the same representative pipelines complete under the laptop and
    workstation memory profiles, with equivalent scientific results;
  * frame/event-loop measurements cover the entire click-to-ready interval
    and show no stopped animation or multi-second GUI gap;
  * cold/warm startup time, every registered module's click-to-ready time,
    peak resident memory and worst GUI/frame interval are written as a
    reproducible benchmark artifact and guarded by tests with explicit,
    hardware-normalized thresholds;
  * item 282's memory/lazy-loading criteria are complete, not merely
    referenced. (This bullet also named item 276; see the header -- 276 has
    never existed, and its criterion is the "no stopped animation or
    multi-second GUI gap" bullet above.)

2026-09-15 -- WHAT THE REMAINING STALLS ARE, AND IT IS ONE FUNCTION
--------------------------------------------------------------------------------

The note above leaves regression at 8,307 ms and mask at 5,469 ms and says
they are "the screen-build cost every heavy module pays". THAT WAS TRUE AS FAR
AS IT WENT AND IT WAS NOT THE END OF THE ROAD. Leave-one-out across the nine
application-wide event filters names one of them:

    spacr/qt/theme.py  _SheetsEveryWindowThatAppears.eventFilter
        76.9% of mask's module open        2,717 ms
        70.9% of regression's              3,783 ms

THE MECHANISM IS NOT THE FILTER'S EXISTENCE. It is that QT CALLS A PARENTLESS
WIDGET A WINDOW -- `QWidget::isWindow` is `window_flags & Qt::Window` and Qt
forces that flag on when the parent is null. So a `QSpinBox()` built on its own
line, one statement before `layout.addWidget(it)`, IS a window for as long as
it takes to reach the next statement, and a filter installed on the
QApplication hands it all ~49 KB of the composed sheet for a window it is
about to stop being.

    one offscreen registry sweep, 45 modules
    the whole filter                                   10,518 ms
    widgets that are windows only for want of a parent  3,817 ms

and OVER HALF OF THAT IS ONE MODULE SCREEN SHEETED THREE TIMES, because a
screen is built parentless and collects Polish events all through its own
construction: 11 x 7 ms while it is still empty, then 11 x 255 ms and
10 x 291 ms once it has grown ~1,500 widgets. The sheet is byte-identical all
three times; what makes the repeat cost 255 ms rather than 7 ms is the widgets
that arrived in between.

FIXED in "A parentless widget is not a window, and 3,817 ms says so", which
skips the Polish for a widget that is parentless, never shown, has no native
handle and whose windowType is Window -- and skips NOTHING else. Menus,
tooltips, dialogs and real windows all keep their Polish sheeting, and a
module page is sheeted on its Show because `_a_page_joined_the_stack` marks it
as a sheet target before it joins the stack.

IT ALSO FIXED A BUG NOBODY HAD FILED. Qt resolves QSS from the NEAREST
stylesheet first, so a copy of the sheet left on an intermediate widget beat a
more specific rule on the screen root -- and those copies carry the GLOBAL
sheet only, because `register_widget_qss` blocks live on the root alone. Every
widget a registered block named was therefore painted the plain `fg`. 31
widgets change colour with the copies gone, every one of them TO the colour
its own block asks for, and 42 move because a label sized by its own block is
a different height. No test held any of those colours in either direction;
one does now.

THE QUADRATIC DUPLICATE CHECK. `settings._advanced_family_members` skipped

files 37,165 setting keys across 706 object roles, so that list grows to

  A set now answers the membership question. The list still decides the
  ORDER, which is the contract -- the Advanced panel lays keys out object then
  suffix, and swapping the list for a set would reshuffle every panel while
  passing a timing test.

      family                            before    after
      Image preprocessing (per object)  52.5 ms   2.9 ms
      Object filtration                 72.9 ms   2.5 ms

MEASURED, interleaved arms, with `sys.path` pinned to the tree under test:

      import spacr.settings        413 ms -> 156 ms   (4 rounds each)

AND THE INSTRUMENT WAS WRONG FIRST, which is the part worth writing down.
The profiler and the timing harness lived in `/tmp` and were run as
`python /tmp/.../harness.py`. That puts `/tmp` on `sys.path[0]`, so
`import spacr` resolved to the INSTALLED package in the main checkout rather
than to the worktree, and every screen-open number taken that way measured
code the edits had never touched. It surfaced as a contradiction -- a direct
import 257 ms faster while the screen open was unchanged to the millisecond --
and a contradiction that sharp is a broken instrument, not a surprising
result. The harness now asserts `spacr.__file__` starts with the tree it was
given. ANY benchmark run from a script outside a worktree has this bug.

WHAT THIS DOES NOT DO: 205 ms is 13% of one module's open. The ceiling needs
13x on regression. The item stays open, on the same ceiling, for the same
reason -- what is left is the rest of the screen build, and the profile says
~1.0 s of the remaining 1.33 s is IMPORTS pulled in on the click path. That is
the next thing to look at, and it is a question about WHEN those imports
happen rather than about making them faster.

WHAT CHASING THE IMPORTS SHOWED, and it is the most useful thing here.

  After `_outlier_criteria` stopped importing pandas, the profile said

  `spacr.settings_advisor`. After that, `spacr.cell_montage`. Each fix was

  THE MODULE COUNT DOES NOT MOVE: 729 before and after all three fixes. So

  answer to the stall.

  THE ANSWER TO THE STALL IS ABOUT THE 729, not about which module is
  unlucky enough to be first. Two directions, and the next session should
  pick one deliberately rather than resume whack-a-mole:

    1. IMPORT FEWER MODULES PER SCREEN. A regression screen should not need

    2. MOVE THE IMPORTS OFF THE CLICK. Python imports are thread-safe, and
       these are pure-Python and data modules with no Qt objects, so they can
       be warmed on a BACKGROUND thread after launch. This does not make the
       work smaller; it takes it off the main thread, which is exactly and
       only what the 500 ms ceiling measures.

  forbids a multi-second GUI gap, not a multi-second total.

  DO NOT MEASURE ANY OF THIS FROM A SCRIPT OUTSIDE THE WORKTREE. See the
  harness note above.

2026-09-15 -- THE FIRST FIX THAT IS ABOUT A SCREEN RATHER THAN A LIBRARY

WHAT A MASK OPEN WAS DOING: `ast.parse`, 73 times, 0.71 s of a 2.05 s
profiled open. `fold_strip._host_declarations` reads each fold host's SOURCE
and parses it -- deliberately, because importing fifteen hosts would load
pandas and scipy before Home paints -- and nothing kept the answer.

tests call twice expecting a different second answer after they replace
`_host_declarations` -- replacing it bypasses the cache, which is what they
need, and they still pass.

      first `folded_modules()`    14 parses

      open Mask                   1.43-1.86 s -> 1.02-1.24 s  (3 interleaved
                                  rounds, taken under suite load, so the range
                                  matters more than either end)

The guard COUNTS parses rather than timing them -- how many times is an

2026-09-20 -- THE LEVER IS PULLED: A MENU IS SHEETED WHEN IT IS ABOUT TO OPEN
--------------------------------------------------------------------------------

THE DECISION. Put to the maintainer through the question prompt with both
routes and what each costs, and answered: sheet menus at `aboutToShow`. The
other route -- letting a parented popup inherit its page's sheet -- would
also have covered a QComboBox's popup, which is a QFrame with no such
signal, but it would have let a page's registered blocks reach inside its
menus, and that is a change to the picture rather than to the speed.

WHAT CHANGED, all in spacr/qt/theme.py:
  `_sheets_itself_before_it_shows` is new. At a menu's `Polish` the filter
  connects its `aboutToShow` once, through a weak reference, and leaves the
  polish alone. Qt emits `aboutToShow` from `popup()` and `exec()` BEFORE it
  measures the menu, so a menu sheeted there has the geometry it would have
  had sheeted at its polish, and a menu nobody opens is never sheeted.
  `Show` REMAINS THE BELT TO THAT BRACE: a menu opened with `show()` emits
  no `aboutToShow` and is sheeted at its `Show` like any other window.

THE CONTRACT THAT MOVED, and it moved on purpose. `test_a_menu_is_still_
sheeted_before_it_can_be_shown` asserted `ensurePolished()` then sheeted.
What the test's NAME promises is unchanged -- the menu wears the sheet
before it can be shown -- so the test now drives the real property: not
sheeted at the polish, sheeted when `aboutToShow` fires, and not visible at
that moment. Three tests join it: a menu shown with `show()` is sheeted
anyway, five polishes connect once, and a menu nobody else holds is still
collectable, which is what the weak reference is for.
