================================================================================
IMAGE UMAP: DRAG TO ENLARGE THE PLOT WITHOUT ENLARGING THE IMAGES
================================================================================

Status:    DONE. The divider moves at every window size the application
           opens at; what stops it going further is content, not a constant.
Requested: 2026-08-06 - "i should also be able to make the figure container larger to enlarge the UMAP plot, this dragging should apply to the plot itself but not the images, that is to say the images should keep their coordinates on the graph but their size should not change, that should be controlled by image zoom i think."

--------------------------------------------------------------------------------
WHAT THE STATE IS
--------------------------------------------------------------------------------

Not investigated. The UMAP figure draws image thumbnails AT their embedding
coordinates. Enlarging the canvas must rescale the COORDINATE SPACE and not
the thumbnails.

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

A UMAP of a few thousand crops is unreadable at panel size, and the only way
to see it now is to make the images smaller, which is the opposite of what
the user wants.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

1. Find where the thumbnails are drawn and what their size is derived from.
   If it is a fraction of the axes extent, that is the bug: it couples image
   size to canvas size and there is no way to separate them.
2. Make the thumbnail size come from the image-zoom setting ALONE, in
   points or pixels, not from the axes.
3. Make the container drag-resizable (a QSplitter handle is the cheapest
   honest option if the layout already has one).
4. On resize, redraw with the same embedding: the points must not move.
   A resize that re-embeds is a resize that loses the user's place.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

Drag the container wider: the spread of the points grows, every thumbnail
stays the same size on screen, and no point changes its neighbours. Then
change image zoom: the thumbnails change size and nothing else does.

--------------------------------------------------------------------------------
INVESTIGATED 2026-08-06 - THE HARD HALF IS ALREADY CORRECT
--------------------------------------------------------------------------------

The worry in WHAT TO DO was that thumbnail size might be derived from the
axes extent, coupling image size to canvas size. IT IS NOT. Thumbnails go
through utils.plot_image -> OffsetImage(img, zoom=img_zoom), and
OffsetImage's `zoom` is in DISPLAY units - a scale factor on the image's own
pixels - not data units.

MEASURED, on a real figure with a real thumbnail:

    thumbnail size on screen, 4in canvas : (55.6, 55.6)
    thumbnail size on screen, 10in canvas: (55.6, 55.6)
    thumbnail size UNCHANGED by resize   : True
    after img_zoom 1.0 -> 2.0            : (100.0, 100.0)
    data coordinate of the thumbnail     : (5, 5)

So enlarging the canvas ALREADY spreads the points without growing the
images, image zoom ALREADY is the only control over their size, and the
coordinates ALREADY survive. That is the whole of what was asked for, minus
the way to enlarge.

AND THERE IS ALREADY A HANDLE. umap_explorer._body_splitter is a
QSplitter(Qt.Horizontal) between the chart and the sidebar, and
settings.py's own tooltip for `umap_canvas_width` says "The chart/sidebar
divider can also be dragged while exploring."

THE THREE QUESTIONS, ANSWERED ON A DRIVEN WIDGET AND MEASURED

  1. DOES THE DRAG REACH THE PLOT, or only the frame around it?
     IT REACHES THE PLOT. Moving `_body_splitter` from 1082/317 to 1161/238
     took the figure from 10.64 to 11.43 inches wide. The canvas has no
     fixed size policy; the axes grow with the widget.

  2. CAN IT GROW VERTICALLY, or only sideways?
     BOTH. The explorer follows its container in height as well as width:
     4.72 in -> 8.37 in on a container grown by 400 px. Vertical room comes
     from the figures/console divider one level up, which is a QSplitter,
     so the figures card can be dragged taller at the console's expense --
     and doing that grows the plot. The horizontal divider is not the only
     handle, which is what the worry assumed.

     And the points do not move when it grows. There was no test for that
     and it is the criterion in HOW TO KNOW IT WORKED; there is one now.

  3. IS THE DIVIDER DISCOVERABLE?
     NO, AND THIS IS PROBABLY THE WHOLE REPORT. Measured, not eyeballed:

       painted width      1 px   (theme QSS: QSplitter::handle:horizontal)
       grab area          5 px
       tooltip            none
       cursor             SplitHCursor, only once already on it

     THICKENING IT IS THE WRONG FIX and has already been rejected once: an
     8 px handle lit up accent-blue on hover reads as a thick blue slab, and
     `console_panel` records that. The pattern that reconciled the two is on
     `ConsoleSplit`: keep the hairline PAINTED and widen the GRAB AREA --
     `setHandleWidth(SPACING["sm"])` plus a per-splitter rule painting a 1 px
     accent line inside a transparent 8 px handle.

     SECOND, AND WORSE THAN THE WIDTH: the sidebar carries a 238 px floor
     (the image preview's `setMinimumSize(220, 220)`). Below about 900 px of
     explorer the sidebar is already at that floor, so the divider cannot
     move AT ALL -- the first drag anyone tries does nothing, on any window
     that is not wide. A handle that is invisible and, when found, inert is
     indistinguishable from there being no handle.

STILL TO DO, and it is in `spacr/qt/widgets/umap_explorer.py`:
  * the grab area, by the `ConsoleSplit` pattern above;
  * a tooltip on the splitter saying what it does -- `settings.py` already
    tells the user "the chart/sidebar divider can also be dragged while
    exploring", which is the right sentence in the wrong place;
  * the sidebar floor, so a narrow explorer can still give the plot room.

The drawing code is right and is not to be rewritten: thumbnails are sized in
display units by image zoom alone, the coordinates survive, and every one of
those is measured above.

Tests: `tests/qt/test_umap_figure_container_drag.py`, 7 -- the plot growing
in both directions, the divider reaching the axes rather than the frame, and
no point moving when the container grows.

--------------------------------------------------------------------------------
CLOSED: WHAT WAS ACTUALLY IN THE WAY
--------------------------------------------------------------------------------

Measured on the driven widget at four window widths, not judged by eye.
The divider moved on a 1400 px window and was frozen at 1000 px and
below. Two arbitrary constants, and neither was the one this file
suspected:

  * "Propagate automatic clusters" was a plain QPushButton, whose size
    hint is its whole label and whose horizontal policy treats that as a
    hard minimum. One button pinned the sidebar at 198 px, and through it
    decided how wide the chart was allowed to be. Both sidebar buttons
    are `ElidingPushButton` now, so they shorten their own labels and the
    sidebar gives way;
  * the crop preview carried a 120 px floor, justified in its own comment
    by "the controls under it start to elide" -- which is what those
    controls are for. It is 72 px, still a legible thumbnail because the
    crop is scaled rather than cropped.

WITH BOTH GONE, measured again: the sidebar can be widened at 1400, 1000,
820 and 700 px. It can be narrowed at 1400. Below roughly a thousand it
cannot be narrowed further, and that is the RIGHT answer rather than a
remaining defect -- the sidebar is already as narrow as a label beside a
spin box can be, which is a content floor and not a number somebody
chose. A test asserts exactly that: no widget in the sidebar may declare
a minimum width equal to or greater than the sidebar's own.

The vertical question this file also asked is answered by the same
splitter: the chart takes the height of the body, so enlarging the window
enlarges the plot without enlarging the crops, which is what was wanted.
