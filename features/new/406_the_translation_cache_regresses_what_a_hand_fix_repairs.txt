--------------------------------------------------------------------------------
WHY: A HAND EDIT TO A CATALOG IS NOT AN INPUT, IT IS AN OUTPUT
--------------------------------------------------------------------------------

`_translate_unique` keeps a cache outside the repository:

    cache_dir  = model_root / ".spacr_translation_cache"
    cache_path = cache_dir / f"{language}.json"        # 58,837 entries for zh_CN

The bad values are IN it, keyed by English source:

    'Pca whiten'        -> 白色白色
    'Surrogate model'   -> 超越模型
    'Guide permutations' -> 导游转换

So the repair pass that produced them also wrote them there, and every
subsequent build prefers the cache to whatever is in the committed catalog.
Editing `spacr/qt/i18n_catalogs/zh_CN.py` by hand fixes the SHIPPED ARTIFACT
and changes nothing the builder reads. The next person to run a build undoes
it without being told.

  THE CACHE IS NOT IN THE REPOSITORY, WHICH CUTS BOTH WAYS. CI builds from
  empty and cannot be poisoned by it, so the committed catalogs are what
  ship and this is not release-blocking. But it also means the damage is
  invisible to every check in the repo and lives only on the machine that
  ran the repair.

--------------------------------------------------------------------------------
WHAT WAS DONE
--------------------------------------------------------------------------------

The only durable override is a reviewed record: those are read from the
repository and beat the cache.

Every row where a fresh build differs from the good committed catalog was
measured -- 88, across SETTING_LABELS (10), SETTING_TOOLTIPS (19), UI (54)
and the category help (5) -- and each was pinned at its GOOD value in
`docs/i18n/reviewed/runtime/zh_CN/2026-09-14-cache-regression-pins.json`.

TWO DETAILS THAT COST TIME AND ARE WORTH KNOWING:

  * The records spell tables in lower case and NOT after the catalog
    attribute. `CATEGORY_HELP` rows belong to the table named `categories`;
    passing `category_help` raises "no table 'category_help'; known tables:
    categories, installer, module_summaries, setting_labels,
    setting_tooltips, ui". Five rows were skipped this way on the first
    pass and are easy not to notice, because the tool reports them and
    exits 0.

  * Pinning the whole diff pinned `Resume` at the value it was being fixed
    AWAY from, and the builder refuses that outright: "conflicting reviewed
    runtime targets for 'Resume'". A pin of a row you are simultaneously
    repairing is a contradiction, and the builder is right to say so.

--------------------------------------------------------------------------------
WHAT IS NOT DONE
--------------------------------------------------------------------------------

THE CACHE STILL HOLDS THE BAD VALUES. Nothing removed them, and they will be
offered again for any source string that is not pinned. The pins cover the
88 that were measured against zh_CN; another locale, or a new English
string that happens to hash to one of those sources, is not covered.

Three options, none taken, because deleting 58,837 cached entries to fix 88
is not obviously right and costs a full retranslation:

  a. Delete the affected keys from the cache file, so the next build
     re-decodes them. They would probably come back the same -- that is
     where they came from.
  b. Never write a repair pass's output to the cache. That is a real change
     to the builder and needs its own reasoning.
  c. Leave it, and rely on reviewed records. This is what is in effect now.

2026-09-15 -- FIXED IN THE BUILDER. A COMMITTED ROW NOW OUTRANKS THE CACHE.
--------------------------------------------------------------------------------

Branch wip/406-committed-rows. `tools/build_i18n_catalogs.py`,
`_seed_cache_from_catalog`, and
`tests/test_a_committed_row_outranks_the_translation_cache.py`.

THE MECHANISM WAS ALREADY THERE. IT LOST TO THE CACHE BY ONE WORD.

How the builder decides "source unchanged" today, measured rather than
assumed: every generated catalog carries `SOURCE_HASHES`, keyed
`(TABLE, key)` -> sha256 of the English it was built from, and
`_seed_cache_from_catalog` compares that entry with the current English per
row (`hash_is_current`). It also requires the catalog's `MODEL` to match
`MODEL_SPECS`, the value to pass `_translation_candidate_valid`, and the
source to be outside `skip_sources` -- the repair force set plus the
authoritative tables. Rows that pass are offered to selection as cache
entries. No other path carries committed rows forward: the "compact" tier in
`_translate_batches` is `spacr.qt.i18n.CATALOGS`, the hand-written `_ROWS`
inside `i18n.py`, not the external catalog.

The seed wrote with `cache.setdefault(...)`. The cache already held the
repair pass's output for exactly those sources, so `setdefault` did nothing
and the cached value was selected. That is the whole reason the zh_CN
rebuild did not carry the hand fixes forward.

THE RULE, NOW IMPLEMENTED

  * PLAIN BUILD. A committed row with a current per-row source hash that
    passes the gates REPLACES the cached value for its source. Only new or
    changed sources reach the cache or the model.
  * REPAIR MODES unchanged. `--repair-invalid-only` and
    `--repair-untranslated` put their targets in `force_sources`; forced
    sources are not seeded and not read from the cache, so they are
    re-decoded, which is the deliberate way to re-translate a current row.
  * REVIEWED RECORDS still beat the committed row, the cache and the model,
    in both modes; selection checks them first.
  * A committed row that FAILS the gates is not carried forward (an English
    fallback left in the file is not a hand fix), so a valid cached value
    can still fill it.

Selection order after the change: identity text > `REVIEWED_UI_TRANSLATIONS`
> reviewed runtime record > no-prose identity > compact `_ROWS` >
hash-current committed row > cache > model. Among committed rows that share
one English source the first table in seed order still wins, as before,
because translations are keyed by source.

TESTS, WITHOUT A MODEL

Twelve tests drive `_translate_batches` with a temporary model root (an
empty model folder), a temporary cache file, a temporary reviewed-record
directory read by the REAL loader, and a stub `transformers`. None of them
touches the real cache.

    before the change   3 failed, 9 passed
    after the change   12 passed

The three red ones are the regression itself: (a) for de and for the real
zh_CN row ('Pca whiten': committed Pca 白化, cached 白色白色), and the same
rule tested directly on the seed. The other nine were green before and stay

source takes the cache value or the stub's output, (c) a repair re-decodes

result, (d) a reviewed record wins plain and forced in both languages, a
committed row that fails the gates does not outrank the cache, and a
precondition that every fixture value passes the gates, so only precedence
can decide which value comes out.

SHOULD A REPAIR PASS STILL WRITE TO THE CACHE? YES, UNCHANGED.

  1. The harm was never the write, it was the precedence. A cached value can
     no longer displace a hash-current committed row, so a repair's output
     only matters where there is no current committed row: a new or changed
     source, or a checkout whose catalog lacks the row.
  2. Not writing it would not remove it from the world. The output is gate-
     passing model output for that source; the next decode of the same
     English with the same model produces the same candidates. Option (a)
     above makes the same observation.
  3. It costs a repair nothing: a repair re-run forces its targets past the
     cache anyway. That also means the cache does NOT let an interrupted
     REPAIR resume, so resumability is not an argument for keeping it; it
     does help an interrupted plain build over new rows.
  4. A mode-dependent cache contract ("repairs don't checkpoint") is one
     more rule for the next person to forget, for no gain after point 1.

DOES THE CACHE STILL NEED CLEANING? NOT FOR THE ROWS THAT SHIP.

Measured read-only against the shared file: 297 hash-current zh_CN rows (280
sources) have a cached value different from the committed one. After this
change none of them can reach a plain build. The seed also writes the
committed value over the cached one, and that reaches the file at the next
checkpoint of any build that decodes something, so those entries clean
themselves as builds run. What is left exposed:

  * cached values keyed by English that is no longer in any catalog. They
    resurface only if that exact English returns without a committed row;
  * any checkout WITHOUT this commit (every lane until it is merged) still
    prefers the cache. KEEP THE 86 PINS until it has reached every tree that
    builds; they cost nothing and are the only protection there.

RISKS FOR THE NEXT FULL BUILD

  * A plain build no longer repairs a wrong-but-gate-passing committed row
    from the cache. It carries it forward. Re-translation of a current row
    is now ONLY a repair mode or a reviewed record, which is the point, but
    anyone used to "rebuild and it gets better" should know.
  * A hand fix must change EVERY row that shares its English source. The
    first table in seed order wins and `write_language` makes the rest
    agree. Measured today: zero zh_CN sources with disagreeing committed
    values.
  * A decoding build writes committed runtime values over bare cache keys.
    That includes an API-lane build of the same language (its own keys are
    namespaced and unaffected) and a checkout on an older branch, which
    writes ITS committed values. Under this rule a cached value for a
    source never outranks a current committed row, so this is noise rather
    than damage.
  * A catalog whose `MODEL` no longer matches `MODEL_SPECS` is not seeded at
    all, as before, so a model change turns carry-forward off entirely.

--------------------------------------------------------------------------------
2026-09-15 -- WHY REVIEWED RECORDS ARE KEYED BY SOURCE TEXT, SHOWN BY A COLLISION
--------------------------------------------------------------------------------

Reviewed records bind to the English SOURCE of a block, not to the symbol that
carries it, so one record covers every block with the same English. The cost
of that design is usually invisible; its benefit showed tonight. Cataloguing
the new `spacr.graph_types.mark_to_start_on` added a record for its
`:param shape:` block, "one of the keys of :data:`DATA_SHAPES`.", and the same
sentence already documents `chosen_for`, `default_for` and `start_for`. The
rebuild moved all four in seven languages, and the move was a correction: fr
had "une des touches" (keyboard keys) where the sentence means dictionary keys,
now "l'une des clés"; sv "till" became "i". A per-symbol key would have left
the three old blocks wrong. When a rebuild moves symbols whose English did not
change, check for a shared-source record before calling it collateral damage.

2026-09-15 -- THE API LANE HAS THE SAME FAULT ONE LEVEL UP. A REWRITTEN

Found integrating wip/integ-0815. The runtime fault above was a cache that
outranked a committed row. This one is the API lane's cousin: the committed

WHAT HAPPENED

Item 63 fixed inline markup in 42 docstrings. The batch then ran, in order:

    03:00Z  build_documentation_i18n.py --sources-only       (rewrites en.json)
    03:11Z  build_documentation_i18n.py --repair-api-blocks  (nine locales, cuda)

Every locale printed `historical_reused=0` with `relaid_symbols=42`, and 17
blocks came back exact English. ELEVEN OF THE SEVENTEEN HAD NOT CHANGED
(zh_CN 1, pt 8, ko 2). They sit in a symbol where 63 edited a DIFFERENT
block, and the audit of pt, ko and zh_CN at 8f4171fd9 exits 0 with them.

THE MECHANISM, FROM THE CODE PATH

`repair_api_translations` reuses a block in two ways:

  * POSITIONALLY, when the translated record's `source_sha256` equals the
    current English. A changed docstring fails this, by design.
  * HISTORICALLY, for a changed docstring, through
    `_historical_api_block_translations(english_record, translated_record)`.
    It returns an unchanged paragraph's old translation only when the
    English manifest's record and the translated record carry THE SAME
    `source_sha256` -- the proof that the old paragraph was translated from
    this very English.

`english_record` is read from `docs/source/_static/i18n/api/en.json`, the
working tree's manifest, taken to be the PREVIOUS English. `main()` keeps
that true for its own run ("Keep the previous English manifest available
until every locale has repaired") by writing en.json only after the last
locale. Nothing else keeps it true. `--sources-only` had already written
the NEW English there, so for all 42 symbols the manifest's hash was the
new one, the catalog's was the old one, and the historical path returned
nothing. What is left is the namespaced cache and the model.

EVIDENCE, THE BUILDER'S OWN FUNCTIONS ON THE ELEVEN

    old manifest (8f4171fd9's en.json)       11/11 blocks returned
    manifest --sources-only wrote            0 blocks: {} for all 11 symbols
    namespaced cache key for the block       absent for all 11
    block index and block count              identical old/new, all 11

So neither remaining route could carry them. The model got them again and
failed the gates, and a failed decode stays English. The other paragraphs of
the same 42 symbols survived only because they were in the cache
(`cache_recovered` pt 437, ko 393, zh_CN 473).

THE SAME FAULT HAS A SECOND DOOR. `--repair-api-blocks --languages <some>`
writes en.json after those languages, which advances the manifest for the
languages it did not repair.

THE FIX (small, in the builder)

`_committed_english_api_symbols()` reads `HEAD:./docs/source/_static/i18n/
api/en.json` through git. For a changed symbol whose working-tree manifest
does not match the translated record, `repair_api_translations` now offers
the committed record as the second candidate, BOUND BY THE SAME HASH: a
manifest describing any other English cannot match, and every reused block
still passes the same gates. At the time of this batch HEAD's manifest was
8f4171fd9's (d745347fb did not touch en.json), so the fallback had the
right history. The summary line gains two counters:

    history_from_head=N   symbols whose history came from the commit
    history_unproven=N    stale symbols no manifest could prove

`history_unproven` is the part that was silent before: a non-zero count
means paragraphs of changed docstrings are going to the cache and model.

    tests/test_documentation_i18n.py::
        test_api_repair_recovers_history_after_the_manifest_was_rewritten

A temporary git repo commits the old manifest and catalog, then the working
tree gets the new manifest, as `--sources-only` did.

                     historical_reused=0 unresolved=1
    after the fix    green; the three neighbouring historical/cache tests
                     unchanged green

The reviewers' corrections for those three were rejected by the gates. In
