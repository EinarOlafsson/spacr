================================================================================
THE EVALUATION SETTINGS ARE SPLIT BY CATEGORY, AND BY ML VS CV
================================================================================

Status:    DONE 2026-09-25 -- split on the Classify panel (decision); see the closing section.
Requested: 2026-08-21 -- "the evaluation section of classify has too many
           setting please devide them on category and machine learning vs
           computer vision and ther subcategories ther, best is if these
           settings can be added to categories that already exist. shared
           settings should not moove to cv or ml specific setting
           categories."
Owner:     Qt GUI (classify settings panel), spacr.settings category map

--------------------------------------------------------------------------------
WHAT IS ASKED
--------------------------------------------------------------------------------

The Evaluation section is one long list. Split it TWO WAYS at once:

  * BY CATEGORY -- the ordinary grouping every other section has.
  * BY ML VS CV -- a setting that only the classical-ML path reads and one
    that only the computer-vision path reads are not the same question, and
    a single list makes the user work out which of the two they are looking
    at from the name.

PREFER AN EXISTING CATEGORY. "best is if these settings can be added to
categories that already exist" -- a new heading is a new place to look, and
the panel already has headings that several of these belong under. Only
invent a heading where nothing existing fits.

THE ONE HARD RULE: A SHARED SETTING STAYS SHARED. A setting both paths read
must NOT be filed under a CV-specific or ML-specific heading. Doing so tells
the user it applies to one path when it applies to both, and they will set
it in one module and not the other. When in doubt about whether a setting is
shared, CHECK WHAT READS IT rather than guessing from its name -- that audit
is the work of this item.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

* No section of the classify panel is a long undifferentiated list.
* Each moved setting's new heading is justified by what actually reads it,
  and a test asserts the ML-only and CV-only lists against the modules that
  consume them rather than against a hand-written list that can drift.
* Every setting read by BOTH paths is under a shared heading -- asserted,
  because this is the failure the item names.
* The number of NEW headings is small, and each one is there because nothing
  existing fit.
* No setting is lost in the move: the set of keys the panel renders is the
  same before and after.

--------------------------------------------------------------------------------
DONE 2026-08-21 -- AND THE AUDIT CORRECTED THE SPLIT
--------------------------------------------------------------------------------

THE AUDIT WAS THE WORK, exactly as this item says, and it overturned the
obvious answer. `classify.FAMILY_SETTINGS` is the authoritative table of
what each family reads EXCLUSIVELY, and against it only `n_top_examples` is
CV-only and only `save_to_db` is ML-only.

ELEVEN OF THE FIFTEEN ARE SHARED. The first attempt split them by what their
NAMES suggest -- `classifier_evaluation`, `evaluation_calibration`,
`evaluation_bins`, the four leakage settings, `score_threshold` all sound
like computer-vision settings -- and filed them under "Computer Vision
Evaluation". That broke this item's one hard rule on eleven settings out of
fifteen, and it broke it invisibly: every name in that heading looked right.

So the split is BY CATEGORY, with NEUTRAL headings:

  Model Evaluation   how the model is VALIDATED -- whether cross-validation
                     runs, into how many folds, grouped by what
  Evaluation Reports what is WRITTEN OUT -- the bundle, the calibration
                     curve and its bins, the score column and threshold
  Leakage Audit      whether train and test share objects

THE LEAKAGE AUDIT IS ITS OWN HEADING because it is a check on the SPLIT
rather than on the model. A reader looking for it among the metrics would
not find it, and a model scored on cells it was trained on is not scored at
all.

THE TWO EXCLUSIVES WENT TO FAMILY HEADINGS THAT ALREADY EXIST -- "best is
if these settings can be added to categories that already exist" -- so only
two headings were invented, and each because nothing existing fit.

THE TEST ASSERTS AGAINST `FAMILY_SETTINGS`, not against a hand-written list.
It checks that no SHARED setting sits under a path-named heading, that no
neutral heading NAMES a path, and that the two exclusives are exactly the
two the table says they are -- so the split and the families cannot drift
apart.

NO SETTING IS LOST AND NONE IS IN TWO PLACES, both asserted.


--------------------------------------------------------------------------------
RE-AUDIT 2026-08-26 -- THE SPLIT IS IN THE TABLE THE PANEL DOES NOT READ
--------------------------------------------------------------------------------

THE AUDIT WAS RIGHT AND IT LANDED IN THE WRONG TABLE. `settings.categories`
does carry Model Evaluation, Evaluation Reports and Leakage Audit, and
`tests/test_the_evaluation_settings_are_split.py` asserts the split against
`classify.FAMILY_SETTINGS` exactly as this item asks. But the classify panel
does not render `settings.categories`: `settings_model.categories_for_app`
overrides it for `classify` and `classify_merged` with its own literal, and
that literal still holds ONE heading called "Evaluation & Results".

Measured through `categories_for_app`:

    classify         24 keys under "Evaluation & Results"
    classify_merged  28 keys under "Evaluation & Results"

So "no section of the classify panel is a long undifferentiated list" is
false on the panel, and the test that proves the split proves it about a
table the panel overrides -- the same "a hand-written list that can drift"
failure this item names, one layer up.

NOT HALF-FIXED HERE. Re-splitting the panel literal is a layout decision:
the three headings account for thirteen of the twenty-four keys, and the
remaining eleven (plot, tensorboard, intermedeate_save, pin_memory,
random_seed, n_jobs, verbose, strict_errors, max_failure_rate, and the two
family exclusives) have no heading on this panel to go to, so any split
invents at least one more. "The number of NEW headings is small" is a
judgement this re-audit is not the place to make.


--------------------------------------------------------------------------------
2026-09-25 -- DECIDED AND BUILT: "EVALUATION" AND "RESULTS & FIGURES"
--------------------------------------------------------------------------------

Maintainer decision (2026-09-25): split Classify's "Evaluation & Results"
settings heading into "Evaluation" (metrics, validation, thresholds) and
"Results & figures" (outputs, plots, exports) -- categories_for_app /
settings category map, with category blurbs.

BUILT IN THE TABLE THE PANEL READS, which is the one the 2026-08-26 re-audit
found unsplit: `settings_model.categories_for_app` for `classify` and
`classify_merged`.

  Evaluation (13)          cross_validation_enabled, cross_validation_folds,
                           cv_group_by, holdout_plate, nested_cv_inner_folds,
                           score_threshold, classifier_evaluation,
                           evaluation_calibration, evaluation_bins, and the
                           four leakage-audit keys
  Results & figures (4/8)  n_top_examples, plot, tensorboard,
                           intermedeate_save; classify_merged adds cmap,
                           heatmap_feature, grouping, min_max
  Runtime & Reliability    random_seed, n_jobs, pin_memory, verbose,
                           strict_errors, max_failure_rate

THE SIX RUN KNOBS were the re-audit's "eleven with no heading" minus the
five that now have one. They are neither evaluation nor results, and
leaving them to the "Additional Settings" catch-all is the failure
test_classifier_evaluation_screen names ("curated by nobody"). They go to
"Runtime & Reliability", an EXISTING spaCR heading (shared blurb and catalog
rows in all nine languages already), so the decision's two headings are the
only new ones.

classify_merged: the shared tail is now ("Evaluation", "Results & figures",
"Runtime & Reliability"), unprefixed, after both families.

BLURBS: CATEGORY_TOOLTIPS gains "EVALUATION" and "RESULTS & FIGURES";
CATEGORY_TOOLTIPS_BY_APP gains a classify / classify_merged
"RUNTIME & RELIABILITY" override that names the seed and the loader
workers. The old "EVALUATION & RESULTS" blurb is kept for any saved layout
still naming it.

spacr/settings.py `categories` (Model Evaluation / Evaluation Reports /
Leakage Audit) is unchanged: it is the notebook-side map with its own tested
split (tests/test_the_evaluation_settings_are_split.py), and the panel does
not read it for Classify.

TRANSLATION FOLLOW-UP (not done here; the i18n catalogs are another lane):
"Evaluation" and "Results & figures" have no catalog rows yet, so the
headings show in English under another UI language until the catalogs are
regenerated. "Runtime & Reliability" is already translated.

Tests: tests/qt/test_cov_r9_settings_model_group_order.py (split present in
both apps, exact Evaluation keys, Results & figures follows Evaluation, no key
twice, run knobs curated rather than left over, a written blurb for each
heading), tests/qt/test_cov_r6_screens_forms_and_masks.py and
tests/qt/test_classifier_evaluation_screen.py updated to the new names.
