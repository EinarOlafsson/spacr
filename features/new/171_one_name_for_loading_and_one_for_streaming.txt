THE TWO NAMES

    LOAD IMAGES     read the crops already in `data/`     -- THE DEFAULT
    STREAM IMAGES   cut them from `merged/` as it goes

And nothing else. Today spaCR has THREE vocabularies for this one choice, and
a user reading two panels cannot tell they are the same question:

    spacr.crops.resolve_crop_source   'auto' | 'png' | 'merged'
    the training / classify settings  'pre_generated' | 'on_demand'
                                      | 'generate'
    the Cells tab (170, as filed)     two more, renamed twice in one day

That is instruction 145's failure in its plainest form: one idea, three
spellings, and the panels that use them cannot be compared by a reader.

THE RULES

A. LOAD IMAGES IS ALWAYS THE DEFAULT. Not 'auto', and not whichever folder
   happens to exist. `set_annotate_default_settings` ships `crop_source='auto'`
   today, which silently takes the PNG folder whenever there is one -- the
   right answer for the wrong reason, and unaskable when a user wants the
   other. The default becomes a NAMED mode that a user can see and change.

B. IF IT FAILS, ALWAYS TRY THE OTHER. Either direction: LOAD IMAGES with no
   `data/` streams instead, STREAM IMAGES with no `merged/` loads instead.
   A screen that has one of the two folders always draws.

C. AND IT SAYS WHICH ONE DREW. This is the condition on B, not a decoration.
   170 first argued AGAINST a fallback on the ground that a silent one makes a
   user believe they are looking at a crop they are not; the fallback is now
   asked for, so the silence is what has to go. The panel states the route
   that produced what is on screen, every time, the way the figure writer
   already reports `"matplotlib"` and the reason when pyqtgraph could not
   draw.

D. THE STORED VALUES DO NOT CHANGE. 'png' and 'merged' are what
   `resolve_crop_source` reads and what every settings file already on disk
   carries. These are LABELS. The training vocabulary
   ('pre_generated' / 'on_demand' / 'generate') is the one that has to be
   migrated onto them, and 'generate' is a third thing -- it WRITES a crop set
   -- so it stays as an action rather than being forced into a two-way naming
   that does not fit it.

E. 'auto' IS RETIRED FROM THE PANELS, not from the code. It remains the
   answer to "what is available here", which is what
   `resolve_montage_crop_source` computes; it stops being an answer a user is
   given when they asked which mode to use.

HOW TO KNOW IT WORKED

* Every panel offering this choice offers LOAD IMAGES and STREAM IMAGES, in
  those words, with LOAD IMAGES selected.
* A screen with only `data/` and a screen with only `merged/` both draw,
  whichever mode was asked for.
* Each says which route drew, and the fallback is visible in that sentence.
* No settings file written before this changes meaning: 'png' and 'merged'
  still mean what they meant.
* A grep for 'pre_generated' finds a documented migration onto the two names,
  not a fourth spelling.

AND D'S SECOND CLAUSE: THE TRAINING VOCABULARY IS MIGRATED, NOT SET BESIDE
--------------------------------------------------------------------------------

`crop_source.py` declared its own three names and nothing else did. A reader
grepping for 'pre_generated' found a mapping in one settings tooltip, which
sets two vocabularies side by side; it does not migrate one onto the other.

IT NOW RESOLVES ONTO THE TWO NAMES. `CROP_SOURCES` is ('png', 'merged',
'generate') and `CROP_SOURCE_ALIASES` is the migration itself: 'pre_generated'
and 'load_images' and 'auto' all mean LOAD IMAGES, 'on_demand' and
'stream_images' mean STREAM IMAGES, and 'generate' keeps its own name because
it is an ACTION -- it WRITES a crop set -- exactly as D says. The stored
values are unchanged, so every settings CSV in existence still means what it
meant, and `CROP_SOURCE_OPTIONS` offers the panel the same two sentences the
viewers use, LOAD IMAGES first.

ONE TABLE, TWO READERS. `io.CROP_SOURCE_ALIASES` is built from it rather than
hand-kept beside it, with the two entries that genuinely differ written down:
'generate' is an action to training and a source to the viewers, and 'auto'
stays 'auto' for `resolve_crop_source`, which is the thing that computes what
is available.

AND IT WAS NOT COSMETIC. The training panel had been renamed to write
'load_images' / 'stream_images'; the reader still knew only the older three.
Every computer-vision run refused at the door with

    CropSourceError: crop_source='load_images' is not one of
    ['pre_generated', 'on_demand', 'generate']

naming three spellings no user had ever seen. Reproduced through
`classify()` before the change and gone after it, and there is now a test
that every value the settings normaliser can produce resolves here -- the
claim that would have caught the rename, and the twin of the one `spacr.io`
already had.

TWO MORE REFUSALS ON THE STREAMING BRANCH, found the same way and fixed with
it: the planes are read from `channel_arrays` as well as the older
`extract_channels`, and a SINGLE `coordinate_columns` entry is accepted --
it names the object's identifier column, which is what spaCR derives from
`object_array`, and demanding a row and a column refused the value spaCR had
written itself. Both training modes now validate from the panel's own
defaults, which is a test.

AND THE LAST PLACE THE OLD WORDS SURVIVED: THE TOOLTIP
--------------------------------------------------------------------------------

`crop_source.py` resolved the training vocabulary onto the two names and the
tooltip in `spacr/settings.py` went on TEACHING it -- "Training uses
'pre_generated' for existing crops, 'on_demand' to cut during training". That
is the failure this file names in its own words: a mapping in one settings
tooltip sets two vocabularies side by side, it does not migrate one onto the
other. A user reading the annotation panel and the training panel still met
two different sets of words for one question, in the one place they would go
to find out what the setting means.

IT NOW READS IN THE TWO NAMES AND NOTHING ELSE. LOAD IMAGES ('png') reads the
crops already exported to `data/`; STREAM IMAGES ('merged') cuts them out of
`merged/*.npy` as the run goes; either falls back to the other and says which
route drew. 'generate' is named as an ACTION rather than a third source,
exactly as rule D says. Training's own spelling is named as what it is --
`image_source` writes 'load_images' / 'stream_images', and both resolve here
-- so a reader meets one vocabulary and a pointer to where the aliases live.

THE RETIRED SPELLINGS ARE RETIRED FROM THE WORDING, NOT FROM THE READERS.
'pre_generated' and 'on_demand' are still in `crop_source.CROP_SOURCE_ALIASES`
and `settings._IMAGE_SOURCES`, which is where a grep lands and where the
migration is written down; every settings CSV in existence still loads.

AND THE STALE COMMENT BESIDE IT IS GONE. A note above the entry said
"crop_source.CROP_SOURCES is ('pre_generated', 'on_demand', 'generate')",
which stopped being true when this instruction shipped -- CROP_SOURCES is
('png', 'merged', 'generate'). A comment that documents the old vocabulary as
the current one is a fourth spelling with a footnote. What it was actually
recording -- that a DUPLICATE 'crop_source' key in the same dict was silently
shadowed, so which tooltip showed depended on the order of the literal -- is
kept, because that is a fact about the file that is still worth knowing.

Tests: `tests/test_load_images_and_stream_images.py`. The test that required
'pre_generated' IN the tooltip is replaced by its reverse, with the reason in
its docstring, and the replacement is stricter: it also asserts both retired
spellings are still ACCEPTED by both alias tables, so retiring the wording
cannot quietly retire the reader.

2026-09-14 -- AND THE PANEL THE MIGRATION WAS FOR
--------------------------------------------------------------------------------

RE-CHECKED AGAINST THE TREE, NOT AGAINST THIS FILE. Both directions were
verified: what still uses an older synonym, and whether the default and the
fallback are implemented rather than merely described.

THE FALLBACK IS REAL, IN BOTH DIRECTIONS AND FROM BOTH DOORS. Verified, not
taken from the note above: `crops.resolve_crop_source` returns kind 'merged'
with a reason naming both routes when LOAD IMAGES is asked for and there is
no `data/`, and the mirror image for STREAM IMAGES with no `merged/`. The
TRAINING door reaches the same code -- `io.open_crop_source` ->
`io._canonical_crop_source` -> `crops.resolve_crop_source` -- so the value
the training panel writes falls back too, and prints which route drew. Two
new tests drive it through `open_crop_source` rather than through
`resolve_crop_source`, because the door is where the rename broke it before.

BUT THE TRAINING PANEL HAD NO CONTROL FOR THE CHOICE AT ALL. `image_source`
is absent from `_APP_HIDDEN_KEYS`, so the Classify and Classify (merged)
screens laid out a row for it -- and a key absent from `_APP_COMBO_OPTIONS`
gets whatever widget its default's TYPE implies, which for a string is a
free-text box. Reproduced before the change:

    SettingsWidgets('classify')._widgets['image_source']
        -> _ScalarEdit('load_images')       # a text field

So the one panel this instruction's own "the training vocabulary is
migrated" section is about was the one panel where a user could type a
fourth spelling -- and a typo, or a remembered 'pre_generated', is exactly
the input that produced the refusal that section documents. The first line
of HOW TO KNOW IT WORKED -- "Every panel offering this choice offers LOAD
IMAGES and STREAM IMAGES, in those words, with LOAD IMAGES selected" -- was
false for it.

IT IS A COMBO NOW. `_IMAGE_SOURCE_OPTIONS` offers ('load_images', "load
images - crops already in data/") and ('stream_images', "stream images - cut
from merged/"), LOAD IMAGES first and selected, wired into
`_APP_COMBO_OPTIONS['classify']` and `['classify_merged']`. The sentences
are word-for-word `_CROP_SOURCE_OPTIONS`', which is the point: one question,
one wording, two panels. It is a SECOND table rather than a reuse because
the STORED values differ and may not move -- the viewers persist
'png'/'merged' and training persists 'load_images'/'stream_images' -- and
rule D says stored values do not change. Both spellings resolve through
`crop_source.CROP_SOURCE_ALIASES`.

'generate' IS NOT OFFERED, AND IS STILL ACCEPTED. Rule D: it is an ACTION,
and the training panel already has `generate_training_dataset` for it.

AND AN OLD SETTINGS FILE PUT A THIRD, RETIRED SPELLING IN THE PANEL. Found
while testing the above, not predicted by it: a combo whose stored value
matches no item keeps that value as a new first item, so a settings CSV
carrying 'on_demand' rendered

    ['on_demand', 'load_images', 'stream_images']

-- the retired word, shown to the user, selected, in a panel whose whole
purpose here is that there are two names. 'png', 'merged', 'auto',
'generate' and 'pre_generated' all did the same.
`_image_source_the_panel_offers` resolves the stored value through
`settings._canonical_image_source` -- the table the PIPELINE reads, so the
panel and the run cannot disagree -- and lands anything unrecognised, 'auto'
included (rule A, rule E), on LOAD IMAGES. Every retired spelling still
loads; it now SELECTS the mode it has always meant instead of being
displayed as a third one.

AND IT IS NOT A LABEL WITH AN ARROW. `settings.setting_dependencies` gates
`stream_method` and the rest of the streaming-only settings on
`image_source`, and `_rules_for_this_panel` fires a rule only when the
setting it reads is on the panel. Driven in a test: `stream_method` is
disabled at LOAD IMAGES and enabled at STREAM IMAGES.

Tests: `tests/test_load_images_and_stream_images.py`, eight new tests (20
cases; the file collects 36, up from 16). Each was proved non-vacuous by breaking the source and watching it
redden: unwiring `image_source` from `_APP_COMBO_OPTIONS` (15 red), removing
the panel normaliser (7 red), wording the labels 'pre-generated'/'on demand'
(3 red), offering STREAM IMAGES first (16 red), adding 'generate' as a third
source (15 red). The three that cross into `spacr/crops.py` and `spacr/io.py`
were reddened without editing those files: dropping 'load_images' from
`io.CROP_SOURCE_ALIASES` reproduces the exact refusal this file records --
"crop_source='load_images': crop_source must be 'auto', 'png' or 'merged'" --
and renaming `crops.STREAM_IMAGES_LABEL` breaks rule C's sentence.

2026-09-14 -- ADVERSARIAL REVIEW OF THE ABOVE
--------------------------------------------------------------------------------

The combo is real and the panel is driven; verified independently, not read
off the section above. Both Classify screens build a `_ValueCombo`, open on
LOAD IMAGES, and every retired spelling written into `image_source` SELECTS
its mode instead of appearing as a third item. Re-running the unwiring and
the panel-normaliser mutations reproduced 16 and 7 failures respectively
(the section says 15 and 7; the extra one is the second `classify_merged`
entry). `open_crop_source` with BOTH folders present still returns 'png' for
LOAD IMAGES and 'merged' for STREAM IMAGES, so the two fallback tests bind
to the fallback rather than to a constant.

TWO DEFECTS FOUND AND FIXED.

1. THE GREYING TEST DROVE THE REFRESH ITSELF, so it proved only that the
   rule CAN read the combo, not that the combo reaches the rule. Skipping
   `image_source` in `_connect_setting_dependency_signals` -- which in the
   app leaves the streaming settings greyed out for a user who has just
   asked to stream -- left all 36 tests in the file passing, and
   `tests/qt/test_no_control_is_inert.py` and
   `tests/qt/test_greying_is_not_regression_only.py` passing with it. The
   test now calls no refresh by hand, runs on both panels, and drives the
   return trip to LOAD IMAGES; that mutation now reddens it (2 failed).

2. THE COMMENT ON `_IMAGE_SOURCE_OPTIONS` DOCUMENTED THE BEHAVIOUR THE SAME
   CHANGE DELETED. It said 'generate' "is still ACCEPTED here, because a
   combo whose stored value is not among its items keeps that value as its
   first item ... so a settings file carrying it still loads and still shows
   what it holds". `_image_source_the_panel_offers` is what stops that
   happening: 'generate' resolves to 'load_images' and is NOT shown.
   Rewritten to say what the code does, and why -- it is what
   `deep_spacr_defaults` turns 'generate' into before any run, so the panel
   shows the source the run will read. This is the failure mode the file's
   own "AND THE STALE COMMENT BESIDE IT IS GONE" section names.

ONE GAP LEFT, REPORTED RATHER THAN FIXED (pre-existing, not introduced
here). `_image_source_the_panel_offers` reads `image_source` only. A
settings file written BEFORE that key existed carries `crop_source` alone --
which is exactly the file the migration is for -- and `crop_source` is in
`_APP_HIDDEN_KEYS['classify']`, so it reaches no control:

    SettingsWidgets('classify', current={'crop_source': 'on_demand'})
        -> the combo opens on LOAD IMAGES
        -> collect() -> image_source='load_images', crop_source='on_demand'
        -> deep_spacr_defaults then sets crop_source='load_images'

The same file run headlessly streams, because `deep_spacr_defaults` seeds
`image_source` from `settings.get('crop_source')`. So "the panel and the run
cannot disagree about what an old file means" holds for every value of
`image_source` and not yet for the older KEY. Closing it means mirroring
that seed at panel-build time, which needs `SettingsWidgets` to know which
keys came from `current` rather than from the shipped defaults -- a larger
change than this item, and a choice about which key wins when a file carries
both.

Also latent, and unreachable today: `settings._IMAGE_SOURCES` has no entry
for `crops.STREAM_FROM_DB` ('merged_db'), so `_canonical_image_source` would
resolve it to LOAD IMAGES -- the wrong-direction answer that entry table was
fixed to stop giving. Nothing writes 'merged_db' into `image_source`
('merged_db' appears in neither `settings.py`, `io.py`, `crop_source.py` nor
`settings_model.py`), so it is a trap for whoever adds the database mode to
training, not a bug on screen.

NOT THIS ITEM'S FAULT: `tests/test_api_i18n_extractor.py` has two failures
in this tree (`10_696 - len(docs) == 218` is off by 52). They come from

2026-09-25 -- BOTH GAPS ABOVE CLOSED.
--------------------------------------------------------------------------------

1. A FILE CARRYING `crop_source` ALONE now opens on the mode the run reads.
   It did not need `SettingsWidgets` to tell shipped defaults from file
   values, which is what the note above feared: `__init__` already holds the
   file's values separately as `current`, before they are laid over the
   defaults. `settings_model._image_source_seeded_from_crop_source` mirrors
   `deep_spacr_defaults`' `setdefault('image_source', crop_source)` --
   IMAGE_SOURCE WINS when a file carries both, as it does headlessly, and an
   empty `crop_source` seeds nothing -- and resolves the value through
   `_image_source_the_panel_offers`, so a retired spelling selects its mode.
   It runs in two places, because an old file reaches the panel two ways:
     * `SettingsWidgets(app, current=...)`, for apps whose shipped defaults
       have `image_source` (classify, classify_merged) -- the rebuild path;
     * `app_screen._translate_legacy_setting_keys`, which every
       "Import settings CSV" goes through before any value reaches a widget.
       Without the seed there, the combo is handed nothing to change and
       keeps LOAD IMAGES even when the form is not rebuilt.
   Measured through the real panel for on_demand, merged, merged_db (stream)
   and pre_generated, png (load), each against `deep_spacr_defaults` on the
   same dict: the two agree for all five.

2. `merged_db` (`crops.STREAM_FROM_DB`) is in `settings._IMAGE_SOURCES` as
   `stream_images`: a database stream is a stream, and the unknown-value
   fallback would have answered it with LOAD IMAGES.
