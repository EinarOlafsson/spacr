--------------------------------------------------------------------------------
2026-09-08, LATER — `--audit` IS NOT HUNG. IT IS SLOW, AND HERE IS WHERE.
--------------------------------------------------------------------------------

The note above said the flag "stalled at 0% CPU and produced nothing" and
was worth diagnosing. Diagnosed, with `faulthandler.dump_traceback_later`
rather than by inference:

    audit()                     build_documentation_i18n.py:6272
      syntax_contract()                                    :6039
        _syntax_preserved()     build_i18n_catalogs.py     :4509
          matches()                                        :4496
            Counter(<genexpr>)                             :4496

It is computing, not blocked. `_syntax_preserved` builds a `Counter` per
PROTECT pattern per block, and the audit runs it over every symbol in every
locale -- roughly 10,243 x 9, each against ~20 patterns, on prose. There is
no deadlock, no missing model, and no I/O wait to find.

WHY IT LOOKED HUNG, and this is the transferable part: `ps -o pcpu=` reports
the average over the process's LIFETIME, not what it is doing now. A process
that spent its first minutes importing and reading before settling into a
tight loop can read low, and I twice took "0.0" as evidence of a block when
the process was busy. Two sessions spent 2026-09-08 finding instruments that
hid the result they were built to show; this is another, and it is in a tool
everyone reaches for.

CONSEQUENCE FOR WHOEVER PICKS THIS UP: budget for it rather than killing it.
The numbers in this file came from the per-locale logs of
`--repair-api-blocks`, which prints the same audit per locale as it goes, so
there is a cheaper route to the same figures. Prefer it.

NOT OPTIMISED HERE. The obvious fix -- hoist the per-pattern Counter, or
short-circuit once a contract is known broken -- touches the gate that every
translation decision goes through, and it is not the sort of change to make
in a release window on a tool whose only symptom is that it is slow.

A LOOK AT ~/.cache/huggingface IS NOT A LOOK AT THE MODELS. That cache holds
metadata-only stubs for several of these -- 12 K directories with no weights
-- and I nearly filed a second wrong conclusion from it. The builders load
from `--model-root` with `local_files_only=True` and never consult the hub
cache. A test script of mine that used hub IDs instead started re-downloading

WHAT IS ACTUALLY REJECTING THE TRANSLATIONS. MADLAD is already tried: the
repair logs show it running and being turned down. Of 72 rejections recorded
across the nine locales,

    52   caller_gate
    11   semantic
     7   protected_syntax
     2   degenerate

and `caller_gate` does not mean "bad translation". It is set only for a
candidate that passed EVERY shared gate -- syntax, semantics, target script,
degeneracy -- and then failed the caller's extra contract. The comment at the
definition is explicit that it is reported "only for an otherwise viable
candidate so a structural or semantic failure cannot be mislabeled as
caller-only".

The caller here is `api_repair_candidate_valid`, and its contract is the
thing to understand before touching any of this: one translation must be
valid for the contextual form AND for EVERY canonical source that shares that
context. Several symbols can carry the same English block with slightly
different canonical text, and a candidate that suits one and not the others
is refused. That is the wall the 359 are behind.

MEASURED, on eight Icelandic blocks m2m100_418M could not translate:
madlad400-7b clears 6 of 8. But that was scored against
`_reviewed_api_block_valid`, the gate for HUMAN-REVIEWED evidence, not
against the generation contract above -- so it is not a 75% fix, and quoting
it as one would be the same error as the title of this file.

THE PATH THAT LOOKS OPEN AND IS NOT. Generate with madlad-7b, score against
the reviewed gate, write the survivors into `docs/i18n/reviewed/api/` as
reviewed records. It would work mechanically and it is forbidden: 357's
guideline 4 forbids claiming a review nobody gave, and
`reviewed_api_block_translations` calls its own inputs "evidence, not
catalogs". Model output filed as review is a lie that would be believed by
every later reader and by the coverage report.

SO THE REAL BLOCKER IS REVIEW CAPACITY, NOT A CHECKPOINT. Two honest routes:

  1. A fluent reader per locale, working the ranked list. This is what 316
     has always said the nine catalogs lack.
  2. Relax `api_repair_candidate_valid` so a block shared across canonical
     forms is translated per canonical rather than once. That is a real
     design change to the generation contract, it would raise the accepted
     rate, and it must not be done in a release window by an agent that
     found it at two in the morning.
