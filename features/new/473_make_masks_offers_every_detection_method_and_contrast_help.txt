MAKE MASKS OFFERS EVERY DETECTION METHOD, AND WAYS TO MAKE OBJECTS EASIER TO SEE
================================================================================

Status:    RUNTIME IMPLEMENTED. Detection methods, enhancement, Compare/Apply
           and request provenance are built and tested. Later notes carry the
           current contracts; API/tutorial/translation follow-up belongs to411.
Owner:     Claude (spacr/qt/screens/make_masks.py and the detection engine).
Requested: 2026-09-22, by the maintainer, in these words:

           "in the make mnasks modual, in addition to the otsu, and cellpose
           options i would like to add all the options that are available for
           organell detection. i would also like to add aoption to enhance
           contrast in the image and other strategies to potentially make
           objects easier to detect on the image."

WHAT IS THERE TODAY (nightly, 2026-09-22)
--------------------------------------------------------------------------------

* Make Masks' magnifier and whole-image detection offer these modes
  (spacr/qt/screens/make_masks.py, `_MAGNIFIER_SEGMENTERS` ~2608): "otsu",
  "cellpose", and the installable backends in `_MAGNIFIER_BACKENDS`
  (Cellpose 3 cyto3/cyto2/cyto/nuclei, DINOCell, SAMCell).
* Organelle detection already implements eight methods
  (spacr/settings_spec.py:287, `organelle_method`; engine in spacr/object.py
  ~1437; guidance per morphology in spacr/organelle_types.py, whose
  LEGAL_METHODS says which suit which shape): otsu, adaptive, log, dog,
  ridge, hysteresis, cellpose, unet.
* Make Masks can already detect on the normalised image or not (the
  "detect on the normalized image" option added 2026-09-21) and invert for
  detection (item 419 point 9c).

WHAT TO BUILD
--------------------------------------------------------------------------------

1. EVERY ORGANELLE METHOD IN MAKE MASKS. Add adaptive, log (Laplacian of
   Gaussian), dog (difference of Gaussians), ridge, hysteresis and unet to
   the Make Masks mode box beside Otsu and Cellpose, for the magnifier and for
   whole-image detection alike. REUSE the organelle engine in spacr/object.py
   rather than a second copy, so a method means the same thing in both
   places. Each method brings its own parameters (block size and offset for
   adaptive; sigma(s) for log/dog; scale and threshold for ridge; low/high
   for hysteresis; the model for unet), shown only when that method is
   chosen, with the organelle_types guidance on what each suits (spots,
   puncta, tubules/networks, blobs). The Otsu mode's smoothing / correction /
   fill-holes / split options stay as they are.
2. CONTRAST ENHANCEMENT before detection, as options the detection reads
   (and the magnifier box shows, the way it already shows the normalised
   image), chosen independently of the method:
     * percentile stretch (already there as normalisation -- keep, name it);
     * gamma correction;
     * CLAHE (contrast-limited adaptive histogram equalisation), with tile
       size and clip limit;
     * global histogram equalisation.
3. OTHER STRATEGIES TO MAKE OBJECTS EASIER TO DETECT, each an option in the
   same pre-detection chain:
     * background subtraction (rolling ball / top-hat, radius in pixels;
       spaCR already has background-removal settings for Mask -- reuse them);
     * denoising (Gaussian, median, and non-local means or bilateral where
       scikit-image provides it);
     * sharpening (unsharp mask);
     * morphological opening/closing to separate touching or join broken
       objects;
     * a distance-transform / watershed split for touching objects (Otsu
       already has "split"; offer it to the other threshold methods);
     * invert (already there; keep).
   The chain applies in a fixed, documented order (e.g. background ->
   denoise -> contrast -> sharpen -> detect -> morphology -> split), and the
   whole chain is saved with the mask's provenance so a mask can be
   regenerated.
4. SHOW WHAT THE DETECTOR SEES: the magnifier and the canvas can show the
   enhanced image (not only the raw one) so the user can judge each step; a
   one-click "compare" (raw vs enhanced) is enough.
5. PERFORMANCE: every step runs on the magnifier's box region live, as today;
   whole-image runs stay off the GUI thread with progress and cancel (item
   407's whole-image machinery). Heavy steps (non-local means, unet) say so.

WHAT TO BE CAREFUL WITH
--------------------------------------------------------------------------------

* Whether the enhancement chain also belongs in the Mask module's own
  pre-processing (so a model trained on enhanced masks sees the same input at
  inference) -- ask the maintainer before wiring it into Mask; within Make
  Masks it only changes how objects are detected for curation.
* New captions and tooltips are translated strings in nine languages: list
  them for the catalog lane rather than regenerating spacr/qt/i18n_catalogs.

DONE WHEN
--------------------------------------------------------------------------------

* Make Masks' mode box offers otsu, cellpose, the backends, and adaptive,

* Contrast enhancement (gamma, CLAHE, histogram equalisation, percentile

WHAT THE NUMBERS SAY, beyond "it runs"

* THE CHAIN IS THE BIGGEST EFFECT ON THIS DATA. Gamma 0.5 more than doubles
  Otsu's F1, 0.297 -> 0.639, and histogram equalisation does nearly as well
  (0.605). Both lift the dim end of a 16-bit histogram whose vacuoles sit
  just above a bright host-cell haze, which is exactly the complaint the
  item was filed about. Neither changes a pixel on disk.
* AND IT CAN ALSO HURT. The unsharp mask halves Otsu's F1 (0.297 ->
  0.157): it puts a rim round every vacuole and a moat outside it, and the
  threshold lands on the rim. A top-hat at r40 changed nothing here and
  cost 27 s a field. The card is a set of things to TRY on the box before
  the button, which is why the magnifier shows what they did.
* HYSTERESIS IS THE BEST BARE METHOD ON VACUOLES (0.523) and the fastest
  (0.4 s a field): two percentile levels suit a bright, well-separated
  object on a dim field. Its thresholds are percentiles, so a monotone
  contrast curve cannot move them -- "hysteresis + gamma 0.5" is the same
  mask to the object, which is a true fact about the pair and not a bug.
* ADAPTIVE FINDS THE MOST VACUOLES (recall 0.649) and pays for it in false
  positives (154); one morphological closing at r3 turns that into the best
  precision in the table (0.850) at F1 0.596. That pair -- a permissive
  detector and a cleanup step -- is what the chain's post-detection half is
  for.
* THE BLOB DETECTORS ARE THE WRONG TOOL HERE AND SAY SO. LoG and DoG are
  spot detectors; a 40 px vacuole is not a spot. With the spot watershed on
  they score 0.000, because _blobs_to_labels grows a watershed over
  everything above the 20th percentile and one object swallows the field;
  with it off they stamp discs and reach 0.154 and 0.266. The Detection
  methods card's "Split touching spots" is therefore the box that matters
  most for those two, and the organelle_types guidance on the row already
  says they suit "small round spots and puncta".
* RIDGE IS THE WRONG TOOL AND SAYS SO TOO (0.133): its guidance reads
  "Suits filaments, tubules and networks", and a vacuole is neither.

That is the point of the row's guidance sentence: the box now offers eight
ways of looking, and the numbers above are what each one is for.

THE MAINTAINER REPORTED THREE THINGS
--------------------------------------------------------------------------------

  "the rolling ball if i choose it crashes the program right away, th
   comparison window is to small to see, i need to be able to enlarge the
   window and the images in it with the window, and i need to be able to

1. THE ROLLING BALL "CRASH" WAS A DENOISER NOBODY ASKED FOR.
   Measured before guessing, on plate1_A02_12 (1,994 px, uint16, CPU):
   ``skimage.restoration.rolling_ball`` alone costs 0.3 s at radius 5,
   0.9 s at 10, 4.1 s at 25 and 14.5 s at radius 50 -- the default -- and
   peaks at 103 MB. Slow, but not a crash and not a memory problem.

   The crash was :func:`spacr.qt.detect_chain._denoise`. Its final
   ``else`` was reached by ``denoise="none"`` as well as by ``"nlm"``, so
   ANY active chain ran non-local means over the whole field. Choosing a
   background made the chain active; the readout, which is re-read on every
   mouse move, then called it on the GUI thread. Three fixes, each a
   separate property now under test:

   * every step returns its input UNTOUCHED when it is off, rather than
     falling through to a default. ``_contrast`` also used to make the trip
     to the unit interval and back with nothing switched on, which moved
     the bottom bits of every pixel;
   * the readout reads :meth:`_MaskCanvas.detection_base` -- the percentile
     stretch -- and never the chain. That is what the readout was always
     for: the value under the cursor, as loaded or as stretched;
   * the canvas's enhanced picture is built on a worker thread
     (:class:`_NewestRequestWorker`, the magnifier's own) and never waited
     for. The first ask hands back the field as loaded; the picture arrives
     on ``_MaskCanvas.enhanced_ready`` and the canvas redraws.

   THE MAINTAINER THEN CHOSE HOW TO MAKE IT FAST: "compute on a
   downscaled copy, have a setting that controlls how downscaled, and
   default to 0.5". Done, as :attr:`Chain.background_scale` and a
   "Background scale" box, 0.10 to 1.00, default 0.50. The background is
   estimated on a copy at that scale and the surface is scaled back up and
   subtracted from the full-size image -- sound because a background is by
   definition what varies slowly, so it is the one thing that survives
   being looked at smaller. Measured on the same field, rolling ball at
   radius 50: 14.49 s at scale 1.00, 1.07 s at 0.50, 0.28 s at 0.25. The
   top-hat, which gets the same treatment: 35.89 s, 2.30 s, 0.23 s.
   AT SCALE 1.00 NOTHING IS SCALED and the call is scikit-image's own; the
   test asserts that to the bit, for both the ball and the top-hat.
   Below :data:`MIN_BACKGROUND_SIDE` (64 px) a region is not scaled at all,
   because a magnifier box is small already.

   The heavy warning now reads the radius AND the scale, so the default
   (effective radius 25, about a second) does not warn and the exact path
   at radius 50 does.

2. THE COMPARE WINDOW opened at 780x440 with two 360 px thumbnails. It now
   opens at 1100x700, has a size grip, grows its pictures with it, carries
   Zoom out / Zoom in / Fit, and remembers the size it was left at under
   ``make_masks::compare``.

3. THE TWO ZOOMS ARE ONE ZOOM. The QC field browser's ``_FieldView`` --
   fit on load, wheel zoom, drag pan, re-fit on resize -- moved to
   ``spacr/qt/widgets/zoom_view.py`` as ``ZoomableImageView`` and the

   to one transform and one scroll position: zooming or panning either
   picture moves both, because a difference between the two is what the
   window is for and a difference in where they point is the one
   difference that is not information.

TEN MORE CPU ALGORITHMS, AND PROPAGATION
--------------------------------------------------------------------------------

  "add cross entropy and any othe rcommonly used algorithms for object
   detection on the cpu. also add the appropreate settings"

Li's minimum cross entropy, Yen, Triangle, IsoData (Ridler-Calvard),
Mean, Minimum, Multi-Otsu, Sauvola and Niblack. Each is ONE LINE in
:data:`spacr.qt.mask_engine.GLOBAL_THRESHOLDS` or
:data:`LOCAL_THRESHOLDS` -- the name of a scikit-image function that
returns a level -- and everything around the level is the code Otsu
already went through: the smoothing, the threshold correction, the bright
or dark side, filling holes, the watershed split, the border rule and the
minimum area. A test asserts that: Li's mask equals Otsu's mask run with
a correction of Li's level over Otsu's.

NOT ADDED, ON PURPOSE. Local MEAN and local GAUSSIAN thresholding are the
Adaptive threshold mode, which runs the organelle engine's ``adaptive``
branch with a block size and an offset. Local OTSU is the "Local
threshold (uneven illumination)" switch, which every global algorithm can
be combined with. Adding either again would be two controls for one
operation. Sauvola and Niblack ARE added, because their level is a
window's mean minus a multiple of its standard deviation, which neither
of those computes.

MAXIMA + PROPAGATE implements the maintainer's
four numbered steps with a setting each: blur (its own sigma, separate
from the chain's denoise and the tooltip says why), find the local maxima
(minimum spacing, a seed level that is a percentile by default or an
absolute intensity, optionally excluding the border), grow by a seeded
watershed on the blurred intensity, and stop by one of four rules -- a
fraction of THIS seed's own peak (the default; an intensity ratio, not a
quantile), an absolute intensity, a percentile
of the image, or one of the global thresholds' levels. It says how many
centres it found, on the status line, because that is the number the
settings are tuned against. CellProfiler's LAMBDA is not offered:
``skimage.segmentation.watershed`` has no distance/intensity mixing
parameter and writing that cost would be a second segmentation engine to
keep. This is intensity watershed, not CellProfiler's Propagation or its
lambda-zero case. The correction is supported by the distinct methods in
the IdentifySecondaryObjects manual:
https://cellprofiler-manual.s3.amazonaws.com/CPmanual/IdentifySecondaryObjects.html

  isodata  823   0.80 %                    triangle 193   1.75 %
  mean      36  10.58 %                    yen     6368   0.01 %
  minimum 25776  0.00 %                    multi-otsu class 2 is above 6010

* LI IS THE RESULT. 0.717 against Otsu's 0.291, on the same settings with
  one number changed. Li does not assume two equal populations, and a
  field that is 99 % background is exactly where that assumption costs
  Otsu the dim half of its objects. This is the algorithm the maintainer
  asked for by name and it is now spaCR's best CPU threshold on this data.
* TRIANGLE IS NEARLY AS GOOD (0.687) and for the same reason: one
  dominant background peak with a shoulder is what it is built for.
* OTSU AND ISODATA cut at 823, four times Li's level, so they keep only
  the bright cores; recall 0.216 and 0.307. They are not broken -- they
  are answering a question this field does not pose.
* MEAN (0.279) takes a tenth of the field and merges neighbours; it is
  the baseline it says it is.
* YEN (0.000) cuts at 6,368 and keeps 0.01 % of the pixels: every
  survivor is under the 200 px floor, so it finds NOTHING. On a field with
  a long bright tail it is a reasonable algorithm; here it is the wrong
  one, and the number says so rather than hiding it.
* MINIMUM (0.000) cuts at 25,776 -- it smooths the histogram until two
  humps remain and on this data the second hump is the hot-pixel tail. A
  poor fit, honestly reported.
* MULTI-OTSU (0.000 for class 2 of 3) puts its upper level at 6,010, so
  the top class is Yen's problem again. Class 1 of 3 would be the band to
  take here; the control for that is on the card.
* SAUVOLA (0.000) keeps whole background windows: its level is a window's
  mean adjusted by that window's standard deviation, and an empty window
  has almost no deviation, so the level sits just under the background it
  is measuring. It is a document-binarisation algorithm and it assumes
  there is ink in every window. NIBLACK (0.176) does the same thing more
  willingly -- recall 0.738, precision 0.100, 6,048 false objects. Both
  are for uneven illumination with detail everywhere, which this is not.
* LOCAL OTSU (0.479) beats global Otsu here, which is the uneven-
  illumination case behaving as advertised.
* THE PROPAGATION IS DENSITY-DEPENDENT, and its per-field numbers are the
  interesting part of the table rather than its pooled 0.418. At one
  setting (sigma 6, spacing 20 px, seeds above the 99th percentile, stop
  at 30 % of each peak) it scores 0.81 and 0.80 on the two sparsest fields
  (18 and 23 vacuoles), 0.62 on two middling ones (45 and 57), and 0.20 on
  the densest (218). One seed spacing cannot serve fields whose object
  density differs twelve-fold: on the dense fields 20 px between centres
  is wider than the vacuoles are apart, so they are under-seeded and
  recall collapses. That is what the "Min centre spacing" box is for, and
  it is why the status line reports the centre count. On the three sparse
  fields alone the same settings score 0.697, second only to Li.
  Its precision is the highest of any method on this data at 0.623: what
  it does find, it finds correctly, which is the property that matters
  when a curator is accepting objects one click at a time.
* The stop rule matters as much as the seeds: per-centre fractions
  (0.390-0.418) beat the whole-field rules (0.265-0.288), because a bright
  vacuole and a dim one are then measured the same way.

THE TABLE FROM THE EARLIER SECTION IS SUPERSEDED IN ONE ROW. Those
numbers were taken before the ``_denoise`` fall-through was found, so
every row of it that switched a chain step on was also running non-local

2026-09-22 — LOCAL THRESHOLD HELP NOW MATCHES THE DETECTORS
--------------------------------------------------------------------------------
The API lane correctly flagged wrong source explanations. Corrected the
Sauvola/Niblack guidance, CpuParams.local_k and engine docstrings, the Local k
and Threshold correction tooltips, and MethodParams/adaptive Offset help.
No detector implementation, parameter default or saved-setting key changed.

Niblack is T=m-k*s; increasing k lowers the threshold, admitting more bright
pixels and fewer dark pixels. The earlier claim that negative k keeps more
bright pixels was reversed. Sauvola is T=m*(1+k*(s/R-1)), a different formula.
The engine passes float32 without range rescaling, so scikit-image uses R=1.
Its direction depends on m and s/R; a constant positive window with k=0.2
has T=0.8*m and can be entirely foreground. No claim that blank windows are
automatically rejected remains in these help strings.

Adaptive offset is subtracted from a Gaussian-weighted local mean. Raising
it lowers the threshold and admits more foreground before cleanup; the old
help again said the opposite. Its units are those of the processed image:
smoothed intensity in Adaptive, ridge response in Ridge/adaptive. A value
suited to raw intensity can overwhelm a normalized ridge response.

The correction-factor help now distinguishes global/local Otsu correction
from Sauvola/Niblack's direct level multiplication and mentions Multi-Otsu's
moving class boundaries. This documents current behavior rather than silently
changing an existing workflow while the API lane documents it.

Niblack k=-0.2 ->0.2 changes bright foreground428 ->538 pixels and dark
foreground533 ->423. A positive constant Sauvola field is entirely foreground
at k=0.2 and empty at k=0. Increasing Sauvola k lowers the local thresholds on
the 0.2-to-0.8 field but raises them after100x intensity scaling. Real adaptive
