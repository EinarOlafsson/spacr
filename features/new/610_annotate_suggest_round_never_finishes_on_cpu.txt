WHAT THE STATE IS
--------------------------------------------------------------------------------

Fixed in spacr/qt/screens/annotate.py (_SuggestWorker and the Suggest
handlers) and spacr/classifier_evaluation.py (a typed refusal).

CAUSE. Not compute. The recording (logs in
/mnt/firecuda2/codex/scratch-docs/rerec-b/logs/ann09.log, private database
in /mnt/wd4tb/scratch-docs-overflow/rerec-b/st09/example_data) labelled ten
crops of class 1 and ten of class 2 on one page of the example plate
(2,341 crops). All ten class-1 crops were in well r12c2; class 2 was in
r12c2 and r5c2. retrain_round's held-out split is grouped by well and
refuses when a class lives in one well ("Independent groups per class:
{'0': 1, '1': 2}"), so the round raised after about 7 s. The failure slot
then called QMessageBox.warning -- a BLOCKING box with a nested event loop.
The recorder was pumping events (settle/processEvents) while it waited for
the run to end, so the slot ran inside its wait and the box sat there,
unanswered, until the run was killed at 21:19 (started 17:24, 3 h 55 min;
ann09.exit = 143). The log stops right after round_features' messages, and
the database has no round and no suggestion, which is what the refusal
leaves.

Reproduced offscreen on a copy of the cached example database with the
same kind of labels (scratch: /mnt/wd4tb/scratch/item-610, gui_repro*.py):
the main thread's stack sits in _on_suggest_failed -> _blind_warning ->
QMessageBox.warning indefinitely. The suspects in the brief were checked
and are not it: there is no torch or image embedding in this path (it fits
HistGradientBoosting on the 1,143 measurement features), no per-image model
load, png_path is indexed so the per-row UPDATEs are not O(n^2), and the
same round run outside Qt takes ~7 s (round_features 5.6 s, fit 0.7 s,
rank+write 0.1 s).

FIX.
1. A suggestion does not need a well-separated score. When the grouped
   split is impossible (now raised as classifier_evaluation's
   _GroupedSplitImpossible, a ValueError subclass, so existing callers are
   unchanged) the Suggest worker refits the round with group_by="none"
   (a stratified random split). The round's split rule then says it is
   not grouped, and the console says why and that the accuracy reads
   high. The Retrain button keeps the refusal: its product IS the
   accuracy.
2. The failure box is opened non-blocking (QMessageBox.open(), object name
   AnnotateSuggestFailedBox), so no worker failure can trap a caller in a
   nested event loop.
3. Visible progress: the worker emits progress(n, 5, stage) before each of
   its five steps -- clear outstanding suggestions, read measurements, fit,
   rank, write -- and the status line reads
   "Suggest: step n of 5 — <step>…".
4. Cancel: a Cancel button (AnnotateSuggestCancel) beside Suggest, shown
   only while a run is going. It calls requestInterruption(); the worker
   stops at the next step boundary and emits cancelled instead of done.
   Measurements are now read as their own step (round_features, then
   retrain_round(features=...)), so a cancel during the slowest step stops
   before the fit.

BEFORE / AFTER on the example set, CPU only (CUDA_VISIBLE_DEVICES=''):
before, the round never ends (blocked in the box; the recording was killed
after 3 h 55 min); after, the same GUI path writes its suggestions in
13.9 s (offscreen repro, unanswered page of 21 crops; 1 suggestion), with
no box.

SAME SUGGESTIONS. Where the grouped split works, nothing changes: three
fixed-seed rounds on the example database with labels spread over wells
(compare.py) gave identical suggestions and identical probabilities
(max |diff| 0.0) between the old procedure and the new worker.

DECISIONS (maintainer busy, taken here):
- Fall back to a random split for Suggest only, with a console note,
  rather than refusing; the tutorial narration promises suggestions from
  ten labels of each class on one page.
- Cancel stops at step boundaries, not inside a fit. The fit is about a
  second here; interrupting sklearn mid-fit would need a thread kill,
  which this application never does (bridge.drain_thread).
- A cancel after the fit keeps that round's scores (they only reorder
  the queue) and writes no suggestions; a cancel after step 1 has already
  cleared the outstanding suggestions, and the cancel line says so.
- Not alpha: this is a fix to an existing feature, not a features/future
  item. Lesson 09's layout at rest is unchanged (Cancel is hidden when no
  run is going), so no tutorial re-record is needed.

TESTS. tests/qt/test_610_suggest_round_finishes_and_cancels.py: the
recording's label layout is refused by the grouped split; the worker still
suggests, within a 60 s bound (takes about 1 s), naming steps 1..5; the
screen runs the whole menu path on a real thread without a blocking box;
Cancel during step 2 of 5 ends the thread as cancelled with no fit and no
suggestion; Cancel with no run does nothing. Existing Suggest tests were
updated for the separate features step and the non-blocking box.

2026-10-01 — CANCELLATION AT THE FINAL WRITE AND ATOMIC PROPOSALS
A follow-up audit found that a Cancel request arriving during step 5 could
be checked after write_suggestions returned and emit cancelled, despite the
new suggestions already being saved. The worker now honors cancellation at
the existing boundary before step 5 and reports done after a successful
write, including a cancellation that arrived during that write.

The writer also relied on the SQLite connection context plus db.commit(),
but the shared connection factory uses autocommit. Each UPDATE could become
durable independently, leaving a partial new proposal batch if a later row
failed. write_suggestions now wraps only its final updates in the existing
database_concurrency.transaction helper. Body/commit errors roll back the
whole new proposal batch; human annotation protection (IS NULL) is retained.
No global connection setting or schema changes.

Earlier phases remain separately committed: old pending suggestions can
already have been cleared and round scores can already have been updated.
The failure dialog no longer says Nothing was written. It states that no
new suggestions from this round were saved and names the earlier changes
that may remain. The cancellation notice likewise no longer claims that
old proposals were necessarily cleared when cancellation preceded step 1.
The failure dialog remains nonblocking.
