--------------------------------------------------------------------------------
WHAT WAS MEASURED HERE
--------------------------------------------------------------------------------

Driving it offscreen with sound switched on, the engine started through
`apply_preferences_to_app` (what Save does), and the Preferences dialog built
and `exec()`d three times, the run prints:

    QSocketNotifier: Socket notifiers cannot be enabled or disabled
                     from another thread            (x5)
    QThread: Destroyed while thread 'spacr-sound' is still running
    ... the process then dumped core at exit

The dialog itself did not hang offscreen -- there is no sound server to
connect to in that environment, and the GUI is not a real window -- but the
threading violation is the same one, and it is undefined behaviour: on the
maintainer's workstation (PipeWire, real window) it presents as the GUI thread
stopping with an empty Preferences frame and GNOME offering to force quit.

--------------------------------------------------------------------------------
THE CAUSE -- confirmed, and it was worse here than filed
--------------------------------------------------------------------------------

Re-driven before anything was changed. With the sound cache ALREADY WARM,
so that the effects are really built rather than still being synthesized,
this is not five warnings and a dirty exit: it is
`Fatal Python error: Segmentation fault`, three runs out of three, with the
audio thread inside `_make_effect` and the GUI thread inside
`PreferencesDialog._page` -- the dialog the maintainer watched fail to fill
itself in. The filing's cold-cache run and its five QSocketNotifier lines
reproduce as recorded.

`_AudioWorker._make_effect` (sound.py:~320) calls

    QMediaDevices.defaultAudioOutput()

ON THE AUDIO THREAD, and the module's own docstring explains why: measured on
2026-09-19, doing it on the GUI thread stopped the interface for 180-320 ms
while the sound server was connected, and this moved that cost onto the audio
thread.

It is the right instinct and the wrong mechanism. Qt Multimedia's device
handling belongs to the thread that owns the application's event loop: with
the FFmpeg backend it installs socket notifiers, and a notifier enabled from
another thread is exactly what Qt warns about above. So a 300 ms hitch was
traded for undefined behaviour that can wedge the whole application -- and
does, on the machine it was measured on.

--------------------------------------------------------------------------------
WHAT TO DO
--------------------------------------------------------------------------------

Keep the synthesis off the GUI thread and bring the DEVICE work back onto it.
Rendering a sound set is numpy and takes as long as it takes; playing one is
`play()`, which returns immediately. Concretely:

  1. `QMediaDevices` and every `QSoundEffect` are created and used on the GUI
     thread. Nothing in Qt Multimedia is touched from the audio thread.
  2. The audio thread keeps doing what it is good for: synthesizing WAVs into
     the cache (`ensure_rendered`), which is the only part that is slow.
  3. Pay the first connection ONCE, and not while a user is waiting for a
     dialog: when sound is switched on, warm the device on the GUI thread at
     a moment of the application's choosing (after the window is up, or on an
     idle timer), and say in the log what it cost.
  4. The thread must end cleanly: "QThread: Destroyed while thread
     'spacr-sound' is still running" is a second defect visible in the same
     run, and a process that dumps core at exit loses whatever the run
     journal had not flushed.

--------------------------------------------------------------------------------
HOW TO KNOW IT WORKED
--------------------------------------------------------------------------------

  * With sound on, opening and closing Preferences ten times in a row prints
    no QSocketNotifier warning and does not wedge -- asserted by a test that
    drives the dialog, not by opening it once by hand.
  * No Qt Multimedia symbol is constructed or called from any thread but the
    GUI thread -- pinned by a test that fails if `_make_effect` or the device
    listing moves back.
  * Quitting with sound on ends the audio thread before the process exits: no
    "Destroyed while thread is still running", no core dump.
  * The first sound after switching sound on still costs about what it costs
    today, and the cost is logged rather than felt at a dialog open.

THE WORKAROUND THIS ITEM NEEDED, KEPT FOR THE RECORD
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
FIXED 2026-09-19. WHAT WAS BUILT
--------------------------------------------------------------------------------

`spacr/qt/sound.py` is two halves now, and which thread each is on IS the
fix:

  * `_SoundPlayer` owns `QMediaDevices` and every `QSoundEffect`. It is a
    child of the engine, so it lives on the GUI thread -- the thread that
    owns the application's event loop, which is the thread Qt Multimedia's
    device handling attaches its socket notifiers to.
  * `_SoundRenderer` lives on the `spacr-sound` `QThread` and does the one
    slow thing: `ensure_rendered`, numpy and file writes. It imports
    nothing from Qt Multimedia and never will.

They talk in one direction each: the player asks for a file it has not got
(`needs`), the engine forwards that to the renderer, the renderer answers
with `rendered`, carrying BOTH the stems it tried and the ones it produced.
Both lists are needed, and finding that out cost a bug: the feedback set
and the music bed are two separate renders, and a delivery that closed out
requests it never carried reported the bed unrenderable and left it silent.

The device connection is paid ONCE, on the GUI thread, `DEVICE_WARM_DELAY_MS`
(400 ms) after sound is switched on -- after Save has closed its dialog, or
after launch has its window up. `_SoundPlayer.warm` logs the cost at INFO.

`_stop_at_exit`, registered with `atexit` the first time an engine is built,
ends the audio thread for a process that never reaches `aboutToQuit`.

That is the whole trade, and it is the answer to the 180-320 ms the

is still on the GUI thread, but it is paid once, at a moment nobody is
waiting on, and everything a user can trigger afterwards is under a seventh
of a millisecond. There is nothing left worth moving off the GUI thread.

--------------------------------------------------------------------------------

`tests/qt/test_sound_on_does_not_wedge_the_preferences_dialog.py`, five
tests, all against the REAL Qt Multimedia stack in child processes -- a
stand-in cannot install a socket notifier and cannot crash, and a test that
cannot survive its own subject says nothing about the run it killed. All
five were run against the pre-fix module and all five fail there, with the
five QSocketNotifier lines above:

  * the dialog is asked what it CONTAINS on the second and third opening,
    because "not populated with preferences" is the shape that was
    reported;
  * every `QSoundEffect.thread()` and `QMediaDevices().thread()` is the GUI
    thread and none of them is the audio thread;

  * a process that never reaches `aboutToQuit` ends it too.

thread of every stand-in call; `test_the_device_is_connected_once_and_before_the_first_effect`
and `test_switching_sound_on_warms_the_device_on_an_idle_timer` replace

ITEM 427 PART B LANDED WHILE THIS WAS BEING BUILT, AND IT IS FOLDED IN
--------------------------------------------------------------------------------

427 part B (music beds, a music file of the user's own, and the Resonance
visualiser) touched the same class, from the other side: it added the
analysis the backdrop is driven by, and it put that work on the audio
thread. Rebased onto it and integrated by hand rather than textually --
twelve conflicting hunks in one rewritten class is not a merge anybody
should trust.

THE SPLIT IS NOT "EVERYTHING MOVES TO THE GUI THREAD". It is "Qt
Multimedia moves to the GUI thread and everything slow stays off it", and
427's work is the proof that the distinction is the right one:
`resonance.ensure_analysis` runs a few thousand FFTs and
`resonance.set_now_playing` reads the analysis file, and BOTH say in their
own docstrings never to call them from the GUI thread. So:

  * `_SoundRenderer` (audio thread) resolves the bed's file -- the user's
    own WAV when they named a readable one, spaCR's synthesized bed
    otherwise -- then runs `wav_seconds` and `ensure_analysis` on it, and
    owns `set_now_playing`. The analysis now happens as the file is
    RESOLVED rather than just before `play()`, so it is off the path a
    user waits on entirely.
  * `_SoundPlayer` (GUI thread) owns the `QSoundEffect`, so it is what
    asks `isLoaded()`, connects `loadedChanged`, and takes the
    `time.monotonic()` stamp at the instant playback really starts. The
    stamp travels on `bed_started`, so the queue hop cannot skew it --
    which is what 427 part B took care over and this keeps.
  * A stop is said twice on purpose: `_forget_bed()` directly, because a
    stop the user can see must not wait behind a render, and `bed_stopped`
    queued to the audio thread, because that is what makes a stop land
    after the start it follows.

Three tests in `test_the_resonance_plate_answers_the_music.py` reached
into `engine._worker._effects`; they now read `engine.player()._effects`,
which is where the effects are. Nothing else in 427's work changed.
All 31 of its resonance tests and all 20 music-bed tests pass.

EXACT STEPS FOR THE MAINTAINER (the one thing still open)

  1. Update and start spaCR normally on the desktop, from a terminal so the
     log is visible:
         conda activate spacr
         cd ~/Documents/repo/spacr && git pull && python -m spacr.qt
     (or however spaCR is normally launched).
  2. Preferences -> Sound tab -> switch sound ON (and the music bed, if
     that is how it is normally used) -> Save.
  3. Wait two seconds. The terminal/log should show ONE INFO line from
     `spacr.qt.sound` giving the cost of the sound-server connection
     (about 0.3 s here). That is the only time the device is touched.
  4. Reopen Preferences, look at any two tabs, press Save. Reopen, press
     Cancel. Repeat until it has been opened ten times.
  5. PASS if every opening shows all its tabs filled in, nothing greys out
     and GNOME never offers "Force Quit", and the terminal never prints
     "QSocketNotifier: Socket notifiers cannot be enabled or disabled from
     another thread". Then quit spaCR from its menu: PASS if the terminal
     does not print "QThread: Destroyed while thread 'spacr-sound' is still
     running" and there is no core dump.
  6. If it DOES wedge: from another terminal, before force-quitting, run
         py-spy dump --pid $(pgrep -f spacr.qt | head -1)
     (pip install py-spy into the spacr env if absent) and paste the output
     into this file -- which thread is where is the whole diagnosis. Then
     recover by putting
         [sound]
         enabled=false
     in ~/.config/spacr/qt.conf (QSettings("spacr", "qt"), key
     `_KEY_SOUND_ENABLED` = "sound/enabled"; the "[ai]/sound_enabled" in THE
     WORKAROUND above is not the key the code uses) and starting again.
