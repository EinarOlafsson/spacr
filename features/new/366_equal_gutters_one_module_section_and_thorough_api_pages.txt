PART 1 -- THE VERTICAL GUTTER MUST MATCH THE HORIZONTAL ONE  [DONE 2026-09-02]
--------------------------------------------------------------------------------

MEASURED ON THE REAL PAGE, which this file insisted on and was right to: the
maintainer reported the gap between rows as "~2.5 to 3x the gap between
columns". That number identifies the cause without ambiguity -- GitHub's
paragraph bottom margin is about 16px and the tiles' own padding renders at
about 9px a side, so a row that is its own PARAGRAPH carries both while a
column carries only the padding.

FIXED BY APPROACH (a)'s HALF THAT KEEPS THE ROW LENGTH: the grid is emitted
as an RST LINE BLOCK, one line per row. A line block has no paragraph
margin, so what separates two rows is the line box and the only space left
is the same transparent padding that makes the horizontal gap. The two
gutters become one measurement rather than two numbers that happen to be
close.

  NOT the flowing single paragraph this file proposed first. That also drops
  the margins, and it hands the row length to the browser -- a narrow
  viewport or a different font size gives five or seven per row. The line
  block keeps six ours, so the "6 per row" and "equal gutters" requirements
  stop being in conflict.

  A test now fails if a grid row goes back to being a bare paragraph, naming
  the symptom, because the difference is one character in the source and
  three times the gap on the page.



362 made every tile identical and six to a row. The HORIZONTAL gutter is
solved and solved deliberately: each tile is `TILE_SIZE` centred in a
`BUTTON_SIZE` canvas with `TILE_PADDING` transparent margin, rows are joined
with RST's zero-width `\ ` separator, so two margins meet between
neighbours and the gap is exactly `2 * TILE_PADDING`.

THE VERTICAL GUTTER IS NOT CONTROLLED AT ALL. Each row is its own RST
paragraph, so the space between rows is the browser's paragraph margin plus
the line box -- a number nothing in this repository sets, and one that has
no reason to equal `2 * TILE_PADDING`.

  DO NOT GUESS AT IT. Measure the rendered gap on the real GitHub page
  before and after. GitHub's own stylesheet is what decides this, a local
  docutils render will not show it, and 362's part 1 was preceded by two
  confidently wrong measurements taken against a page that had not settled.

  THREE APPROACHES, in the order they should be tried:

  a. ONE PARAGRAPH, NO BLANK LINES between rows. All 21 substitutions in a
     single flowing run, wrapping naturally at six because 6 x 16% = 96% and
     a seventh does not fit. Vertical spacing then comes from the line box
     rather than paragraph margins. RISK: the wrap is the browser's decision,
     not ours, so a narrow viewport or a different font size can produce five
     or seven per row. The 6-per-row requirement and this approach may be in
     direct conflict -- establish which the maintainer wants more before
     building it.

  b. AN RST TABLE, one tile per cell. Puts both gutters under the same
     mechanism. RISK: GitHub styles table cells with borders and padding of
     its own, which may be worse than the problem.

  c. BAKE THE VERTICAL MARGIN INTO THE CANVAS. If the residual paragraph
     margin proves to be a constant, reduce `TILE_PADDING` and add the
     difference to the canvas height so the drawn gaps come out equal. Ugly,
     exact, and the only one that does not depend on GitHub's CSS staying
     put. Record the measurement if this is chosen, because the number is
     otherwise unexplainable.

NEW: spacr/crop_loader.py, Qt-free, 11 public symbols. PLANNING IS NOT
LOADING, and that split is the whole design:

  * plan_crops() asks which objects match and reads NO PIXELS -- a COUNT and a
    SELECT of identifiers, or one scandir. That is what lets a screen answer on
    a click and say what it found before committing to read any of it. The
    claim is asserted rather than asserted-in-prose: the test patches
    read_crop_png, extract_crop and extract_crops to raise, and plans anyway.
    The trap was checked to be live -- loading under the same patch hits it.
  * load_crops() then reads in pages, calling progress(done, total) after each
    and checking cancelled() before each, so a stop costs at most one page and
    keeps what it read.

Three ways to choose from a measurements database -- object class, plate, and
an SQL condition over png_list -- or every PNG in a folder. The pixels are NOT
read by new code: resolve_crop_source() picks between the crops under data/ and
cutting from merged/*.npy exactly as every other consumer does, and
CropSource.get_many() is what opens each .npy once per page.

FOUR THINGS THE TESTS FOUND THAT READING HAD NOT:

1. ASKING FOR NUCLEI OUT OF A CELL png_list RETURNED EVERY CELL IN IT. The

   matches nothing and the empty state names the classes there are. A table
   with no class columns at all is the separate case and still loads.

AN EMPTY RESULT IS A SENTENCE, NEVER AN EMPTY ARRAY, and there are five of
them because they send a reader to five different places: an empty crop table
(with what to run), a plate that is not in the screen (naming the plates that
are), a class the table does not carry (naming the classes it does), a filter
nothing satisfies, and -- for a folder -- no PNGs but some .tif, which is the
commonest miss and says so. The screen shows the loader's own sentence
unedited; wrapping it in "load failed" would bury the plate names that are the
whole answer.

A CAP IS PART OF THE ANSWER, NOT A FAILURE TO LOAD EVERYTHING. 60,000 crops of
96x96x3 is 1.6 GB before a backbone has seen one, so the panel's "At most"
defaults to 2,000 and the screen says "the first 5 of 12 that matched -- raise
'At most' to take more". A subset that reads as the whole plate is the failure
being avoided.

CROPS OF TWO SIZES ARE PADDED, NOT RESCALED, and the count is recorded.
Rescaling changes the apparent size of the object, which is a phenotype;
zero-padding changes the background, which is not, and it is what
crop_source.crop_at already does to a box that runs off the edge of a field.
Two crops with different CHANNEL counts are refused instead -- padding a
missing channel would invent a stain.

2026-09-20 -- REVIEW OF THE CROP LOADER: FOUR DEFECTS FIXED, AND A FIFTH THE
FIX'S OWN TEST TURNED UP

The 2026-09-19 unit above was reviewed before landing and came back FLAWED.
Nothing in the REQUEST changed and nothing was rebuilt; what follows is what
the review found and what was done about it. 366's two leftovers are
untouched and are still the only things open under it.

1. A COMPLETE ANSWER READ AS A CAPPED ONE, which is the promise of "A CAP IS
PART OF THE ANSWER" running backwards. CropPlan.matched was the pre-join SQL
COUNT and CropPlan.rows was what survived crop_rows_from_png_list, which on
the merged route drops every row it cannot cut ('omulti' / 'onone', or no
merged array recorded). So `capped` -- matched > count -- was true whenever
the join dropped anything, with no limit anywhere near it, and the panel
printed "the first of 10 that matched -- raise 'At most' to take more" for a
load that had taken everything there was. Raising 'At most' returns the same
rows and reprints the same sentence, so the instruction was one the user
could not act on.

MEASURED: a png_list of 10 rows, 3 of them 'omulti', merged route, limit
2,000. Before: matched 10, count 7, capped True, "the first 7 of 10". After:
capped False, dropped 3, "7 of the 10 crops matching ... -- 3 cannot be cut
and are left out".

THE FIX IS A THIRD NUMBER, because two different things remove rows and they
ask the reader for different things. CropPlan now carries `selected` -- what
the LIMIT left of `matched` -- so `capped` is matched > selected and the new
`dropped` is selected - count. They reach the panel as separate clauses and
only the cap one says "raise 'At most'". The record gains `selected` and
`dropped`. _loaded_sentence is driven by record['capped'] rather than by
loaded < matched, which were never the same thing.

2. A STOP THE USER PRESSED CAME BACK AS A FAILURE. Pressing Stop while the
plan job was in flight, or during the first page, put "Crops could not be
loaded" over the panel: the screen telling somebody their machine refused the
thing they had just cancelled, which sends them looking for a broken
database. _on_planned now checks the flag before submitting the load at all
(planning is one count and one select and cannot be interrupted, so it is
answered when it returns), and _on_job_failed tells a stop apart from a
refusal by the flag the USER set rather than by reading the message. Both
head it "Loading stopped". A stop still unloads nothing and the panel still
says so.

3. A GLOBAL FLAG WAS BEING CLEARED FOR EVERY OTHER READER IN THE PROCESS.
The loader turned spacr.crops.PRINT_CROP_PATHS off for the duration of a
load, correctly saving and restoring it -- but it is one switch for the whole
process, and a load of a plate on a network mount holds it for minutes. Any
other screen reading crops in that window silently lost its "<- NOT ON DISK"
line, which is the only reason the flag defaults to on, so a missing crop
there read as a success. spacr.crops gains quiet_crop_paths(), a thread-local
context manager; the global flag is left alone. Tested with a second thread
that checks what it can see while the load holds the quiet.

4. A STAT ON THE GUI THREAD, on every edit of the path box AND at the end of
every load -- when the user had done nothing at all. os.path.exists against a
hung or unmounting NFS share blocks until the mount gives up, and the next
method along already moved its two cheap indexed reads to a worker for
exactly this reason. The stat moved to the same worker. Load is now offered
for any non-empty path and the answer comes from pressing it: plan_crops
names the path it could not find, which is a better sentence than a greyed
button and is said from a worker thread. A half-typed path answers with
nothing to offer rather than raising, so the status line is not written on
every keystroke.

5. FOUND BY THE FIX'S OWN TEST, NOT BY THE REVIEW, and worse than any of the
four: ONE 'omulti' ANYWHERE IN A SELECTION FAILED THE ENTIRE MERGED LOAD.
crop_rows_from_png_list writes None for each row it is about to drop, which
makes the whole object_label column float64; the rows that survive then carry
3.0 where they carried 3, and spacr.crops.object_label refuses a float
outright -- int('3.0') raises. So a plate with any overlapping crop in it
loaded nothing, with a message about a label that was perfectly good. The
dtype is pandas bookkeeping and _plain_row now undoes it where the row is
made ready for spacr.crops, rather than by loosening what counts as a label
everywhere else. THE REASON THIS SURVIVED THE FIRST ROUND: every fixture in
the original tests was a clean plate, and a clean plate is the one case that
never sees it. The new fixture has 'omulti' rows in it on purpose.

TESTS: +4 in tests/test_choosing_crops_is_not_reading_them.py (29 -> 33) and
+4 in tests/qt/test_the_embedding_screen_loads_its_own_crops.py (17 -> 21),
including a real streaming fixture -- merged/*.npy, an object table and a
png_list with 'omulti' rows -- so the drop is produced rather than
