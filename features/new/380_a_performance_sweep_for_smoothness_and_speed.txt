================================================================================
A PERFORMANCE SWEEP: STARTUP, THEMES, MODULES, WIDGETS AND SETTINGS
================================================================================

Status:    THE HARNESS EXISTS AND IS CALIBRATED, 2026-09-09; THE THEME
           DEFECT IT NAMED IS FIXED, 2026-09-11. Two of the five areas
           were already covered by tooling nobody had connected to this
           item; the two the request judges "smoothness" by were not, and
           are now. The largest single defect the harness found -- a
           preference save repolishing every widget in every hidden
           screen -- went 10.2 s -> 3.1 s -> 1.7 s in two steps, both
           recorded below. Filed 2026-09-07.
Requested: 2026-09-07, verbatim -- "do an in depth performance sweep to check
           and fix any performance defects in starting spacr, running the
           themes, or starting the moduals and handelling the widgets and
           settings in the moduals and on the home screen. this should all be
           optimized for smoothness and speed (on all platforms) while not
           comproon functionallity."
Owner:     spacr/qt/** -- startup, theme, screens, widgets, settings panels.

THE LAST CLAUSE IS THE CONSTRAINT, NOT A PLEASANTRY. "while not compromising
functionality" rules out the cheap wins: dropping the backdrop, lowering the
frame rate, lazy-loading a panel so it appears blank, eliding text that then
cannot be read. A change that makes spaCR faster by making it do less is not
an answer to this item unless the maintainer agrees the thing removed was not
wanted.

--------------------------------------------------------------------------------
WHY THIS IS FILED SEPARATELY, AND WHAT IT IS NOT
--------------------------------------------------------------------------------

Performance work has been done here in pieces, always reactively, and each
piece was found by the maintainer noticing something rather than by anyone
looking. That is the pattern this item exists to break.

  315  THE FORCE-QUIT DIALOG. "Force quit window still appears at each
       modular start." Root-caused 2026-09-05: two comprehensions in
       `settings.py` rebuilt constants inside inner loops (1932 ms -> 484 ms),
       plus a 30-second `urlopen` on the GUI thread. The desktop offering to
       kill spaCR is the most severe symptom this class of defect has, and it
       was shipped for weeks.
  378  HOLD Z AND SCROLL. Measured `app.setStyleSheet` + re-polish at 587.5 ms
       on 847 widgets, against 107 ms for the visible screen alone. That
       number was measured because one feature needed it, and it describes
       every theme change spaCR makes, not just that one.
  305  LOAD TIME WITHIN RESOURCES. Filed, deferred to after the version bump.
  327  THE BACKDROP CAMERA. "the fullscreen mode fractal is super choppy while
       the normal background one is super smoothe."
  The one-backdrop fix, 2026-09-05: TWO full-size animated fields were being
       shaded and blitted per frame on a 4K screen -- 950 paints/s, 393 Mpx/s,
       idle GUI-thread CPU at ~16% of a core, for a picture nobody could see.

SO THIS ITEM IS THE SWEEP, not another instance. Its output is a MEASUREMENT
HARNESS plus the defects that harness finds, in that order. An audit that only
records "this felt slow" produces a list nobody can act on, and the four
entries above show the causes are unrelated to each other.

--------------------------------------------------------------------------------
WHAT TO MEASURE, AND THE FIVE AREAS THE REQUEST NAMES
--------------------------------------------------------------------------------

1. STARTING SPACR. Cold import to first painted frame, broken down: which
   imports, which registry builds, which file reads. `spacr-doctor` and the
   preloader already exist and should be read before anything new is written.
   THE TARGET IS THE SLOWEST STEP NAMED, not a total -- a 3-second startup
   with one 2.4-second step is a different problem from thirty 100 ms steps.

2. RUNNING THE THEMES. Frames per second and paint cost per theme, at 1080p
   AND at 4K, because the cost is counted in pixels and 327 was reported from
   a 3840x2160 machine. Include the fullscreen screensaver path, which 327
   says is choppy where the windowed one is smooth -- that gap is a defect
   with a cause, not a fact of life.

3. STARTING A MODULE. Registry lookup to first painted settings panel, per
   module, since 315 showed one module's settings build can dominate. Every
   declared app, not a sample: the four that were sampled in 350's sweep all
   passed and the sixteen added later found nothing, but that was luck rather
   than method.

4. HANDLING THE WIDGETS AND SETTINGS. The interactions, which is where
   "smoothness" is actually judged: expanding a section, typing in a field,
   scrolling a long settings column, dragging a splitter, hovering the grid.
   Measure INPUT LATENCY and DROPPED FRAMES, not wall-clock -- a 200 ms
   hitch on a keystroke is felt, and a 200 ms total spread over ten frames
   is not.

5. THE HOME SCREEN. Named separately by the maintainer, and it is the one
   surface every user sees before anything else.

--------------------------------------------------------------------------------
"ON ALL PLATFORMS", WHICH IS THE HARD PART OF THIS ITEM
--------------------------------------------------------------------------------

The maintainer said all platforms and it cannot be waved through, because
this project has already shipped two defects that were invisible on the
machine they were written on:

  * the packaging failure (331/PKG) reproduced only where setuptools was >= 77,
    and the home workstation has 69.5.1 -- so a green build there was never
    evidence about anything;
  * the label-contrast failures in issue #6 were reported as a macOS problem
    and were really a light-theme one, because macOS defaults to the light
    appearance far more often than Linux does.

A PROFILE FROM ONE MACHINE IS A FACT ABOUT THAT MACHINE. So the harness has
to run in CI on all three platforms and record numbers, even if the fixing is
done locally. Scale matters too: font scale, screen resolution and HiDPI all
multiply paint cost, and 04 already records that the tests measured a font
scale no user has.

--------------------------------------------------------------------------------
HOW TO DO IT
--------------------------------------------------------------------------------

1. WRITE THE HARNESS FIRST, and prove it catches a defect that is already
   known before trusting it on anything else -- 350 did exactly this against
   the Annotate instance and it is why that sweep is believable. The
   one-backdrop regression is the ideal calibration case: a harness that
   cannot see 950 paints/s for an invisible layer is not measuring paint.

2. RECORD A BASELINE and commit it, so later work can be shown to have moved
   the number rather than asserted to have.

3. FIX BY CAUSE, NOT BY SYMPTOM, and record which cause each fix addressed.
   The four known instances had four unrelated causes -- work in an inner
   loop, a blocking call on the GUI thread, a whole-application re-polish,
   and a duplicated layer -- and a list organised by symptom would have
   grouped none of them correctly.

4. RATCHET WHAT IS FIXED. A performance defect with no test comes back; 315
   came back three times. Prefer a ceiling assertion ("first paint under
   N ms", "no more than one animated layer") over a benchmark that fails on
   a loaded machine.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* MEASURE ON THE MACHINE THAT CANNOT COPE, not the one that can. The
  maintainer's report that started 315 was "It's like my computer has an
  unusually low tolerance for applications loading." That is the environment
  to optimise for.
* DO NOT MEASURE WITH `QWidget.grab()`. It does not capture the GL-backed
  AmbientWidget, so a grab-based check reports a black window and cannot tell
  a working backdrop from a broken one. Found the hard way on 2026-09-07,
  after an A/B across two commits came out byte-identical for that reason.
* RAM IS PART OF PERFORMANCE HERE. This machine has been taken down twice by
  spaCR's own test suite; a "faster" change that raises peak RSS is not
  obviously a win.
* THE FIRST RUN AFTER AN INSTALL IS THE ONE USERS JUDGE. Warm-cache numbers
  flatter every result in this file.

2026-09-09 -- WHAT ALREADY EXISTED, AND THE TWO HALVES THAT DID NOT
--------------------------------------------------------------------------------

"READ THEM BEFORE ANYTHING NEW IS WRITTEN" was the right instruction and it
saved most of this item. `tools/spacr_startup_benchmark.py` is 988 lines and
already covers three of the five areas properly:

    1. STARTING SPACR      cold and warm, fresh interpreter per run,
                           real entry point, isolated home
    3. STARTING A MODULE   every live sidebar app pressed, time to ready
    5. THE HOME SCREEN     Home ready as its own budgeted number

with a 5 s Home budget, a 10 s module budget, a 500 ms event-loop stall
detector and a JSON schema. It also states, correctly, that a hosted CI
runner is not release performance evidence: no real display, no compositor,
no hardware profile, shared-host scheduling.

  SO AREA 1, 3 AND 5 NEED RUNNING AND WATCHING, NOT BUILDING. What this
  item adds there is the discipline of step 2 -- record a baseline and
  commit it -- rather than another harness.

AND A THIRD TOOL WAS MISSED ON THE FIRST PASS, which is worth recording
because this item's whole argument is that reading first is cheaper than
writing. `tools/measure_the_backdrop.py` (instruction 327, 255 lines) is
AUTHORITATIVE for area 2's cost half: the CPU kernel per surface at the
adaptive scale's top and at its 0.58 floor, the whole pipeline through the
real widget, and each GPU shader into an offscreen framebuffer with a real
GL context. It was found an hour after `perf_paint.py` was written, and the
overlap is now stated in that file's own docstring rather than left for
somebody to trip over: measure_the_backdrop answers what a frame COSTS,
perf_paint answers what the RATE is per theme, and neither replaces the
other. Anyone extending this should grep `tools/` before adding a fourth.

WHAT WAS MISSING IS EXACTLY THE TWO THE REQUEST JUDGES SMOOTHNESS BY, and
`tools/perf_paint.py` is those two:

    2. RUNNING THE THEMES  backdrop paints/s per theme at 1080p AND 4K,
                           and the cost of a whole-application theme change
                           with the widget count beside it
    4. WIDGETS AND SETTINGS  input latency for expanding a section, typing
                           a character and scrolling the settings column,
                           reported as FIRST and REPEAT with dropped frames

IT COUNTS PAINTS RATHER THAN GRABBING PIXELS, per this file's own WATCH
list: `QWidget.grab()` does not capture the GL-backed `AmbientWidget`.
`ambient.total_frames_painted()` already existed and counts the thing that
costs.

CALIBRATED FIRST, WHICH IS THIS FILE'S OWN RULE.
`tests/qt/test_the_paint_harness_can_see_a_second_layer.py` reproduces the
one-backdrop regression deliberately -- two layers must read as at least
1.5x the paints of one -- and asserts the ratio rather than a frame count,
because the count moves with the machine's load and the ratio does not. It
also pins two mistakes the harness made while being written, so neither can
come back silently:

  * `app.findChildren(QWidget)` reported 1 widget where `app.allWidgets()`
    reports 1,050. A top-level window is not a CHILD of the application
    object, and a per-widget cost over a denominator of one reads as a
    flattering result rather than as a broken measurement.
  * a bare `AmbientWidget()` measures the DEFAULT theme however the row is
    labelled: the look is read at construction. Four identical numbers
    under four theme names were the only clue.

THE FIRST BASELINE, 2026-09-09. TAKEN UNDER LOAD, AND SAYING SO.
--------------------------------------------------------------------------------

`docs/perf_baseline.json`, offscreen, while the full test suite was running
in another process -- the record carries the load average and the Qt
platform for exactly that reason. Every number here is a CEILING on the
speed rather than the speed.

    BACKDROP     24.7 fps at 1080p and 24.7 at 4K, every theme
                 51 Mpx/s at 1080p, 205 Mpx/s at 4K

    THEME CHANGE 299-340 ms over 1,050 widgets, all four palettes

    INTERACTION  expand a section   47.6 ms first, 4.2 ms repeat, 2 frames
                 collapse           12.3 ms first, 3.8 ms repeat
                 type a character    0.06 ms
                 scroll              0.01 ms

THREE THINGS THE FIRST RUN ALREADY SAYS:

  1. THE FRAME RATE IS THE SAME AT FOUR TIMES THE PIXELS, which means the
     cap is holding and the per-frame COST is what varies -- 4x the
     megapixels for the same 24.7 fps. So a 4K machine is doing four times
     the shading work per second for the same picture, which is consistent
     with 327 being reported from a 3840x2160 screen and is the thread to
     pull on next.
  2. THE THEME CHANGE IS STILL A THIRD OF A SECOND. 378 measured 587.5 ms
     on 847 widgets; this is 299-340 ms on 1,050, on a loaded machine and
     offscreen. The shape is unchanged: every theme change repolishes the
     whole application.
  3. EXPANDING A SECTION DROPS TWO FRAMES THE FIRST TIME AND NONE
     AFTERWARDS. That is work done once per section, and the first time is
     the time a user meets it. Typing and scrolling are free, which is
     worth recording precisely so that nobody optimises them.

WHAT THIS BASELINE IS NOT. It is one machine, offscreen, under load. "On
all platforms" is unanswered and needs the harness in CI on all three, per
this file's own argument about setuptools 77 and the light theme. And the
fullscreen screensaver path -- 327's actual complaint -- is not measured
yet: it needs a real display, and this session has none.

2026-09-09 -- FIRST FIX LANDED: THE LANGUAGE IS RESOLVED ONCE PER BUILD, NOT
ONCE PER TRANSLATED STRING
--------------------------------------------------------------------------------

Found while measuring something else -- the backdrop freeze of 385 -- which is
the pattern this item exists to break, so it is recorded here rather than
there.

THE DEFECT. `i18n.current_language()` reaches into `QSettings` on every call,
and `tr()` calls it once per string. Profiling one `PreferencesDialog(...)`
build:

    346 tr() calls -> 347 get_language() -> 415 QSettings reads   18 ms of 55

Every one of those 415 reads returns the same answer. Nothing runs between
them: it is one synchronous build.

WHY IT SURVIVED. A scope for exactly this already existed in TWO places and
neither covered `tr`. `settings_model.language_resolved_once` memoises what
*that* module resolves and is what took the Mask screen's build down from
3,516 lookups for 1,538 settings. And `i18n._RESOLVED_LANGUAGE` -- a
ContextVar read by `current_language` on both arms -- was declared, read, and
**set nowhere in the package**. `tests/qt/test_cov_r8_i18n_current_language.py`
had pinned that dead state deliberately, with a test asserting no setter
exists and a note that a future caller wiring it up "has a description to
check against".

THE FIX, three small pieces:

  * `i18n.ui_language_resolved_once()` -- a context manager that opens the
    ContextVar scope. Nested scopes share the outermost dict and only the
    outermost resets it, so a screen wrapping its build and a helper
    wrapping itself do not drop each other's cache.
  * `settings_model.language_resolved_once` opens it too, so ONE scope
    covers both mechanisms and callers do not have to know there are two.
  * `PreferencesDialog.__new__` wraps its build in it. The body moved to
    `_build_the_dialog` unchanged rather than being re-indented, so the
    diff is the wrapper and nothing else.

MEASURED, same machine, same dialog, imports already warm:

    before   55 ms   415 QSettings reads   current_language 4th by cumtime
    after    30 ms    70 QSettings reads   current_language absent from the
                                           top 28 entirely

45% off a build that happens every time the user opens Preferences.

FUNCTIONALITY IS NOT COMPROMISED, which is this item's constraint. The scope
is per-build, not per-process: a language change between two builds is seen
by the second, because the dict is discarded when the outermost scope exits.
The `SPACR_LANGUAGE` environment override still wins -- `current_language`
consults it before filling the scope -- and there is a test for that.

TESTS. `test_cov_r8_i18n_current_language.py` grew from 8 to 15: the
dead-cache class became `TestTheContextVarCacheThatIsNowOpened`, and the
"nothing sets it" assertion became "exactly `i18n.py` sets it" -- which is
the assertion worth keeping, because a SECOND setter would have both scopes
resetting the same ContextVar and each dropping the other's cache, with no
failure anywhere, only a silent return to reading the store. Plus the read
count as a test, nesting, an exception inside the body, the environment
override, and settings_model opening it. 160 tests across
`test_preferences.py`, `test_cov_s1_preferences_edges.py`,
`test_ambient_wiring.py` and `test_ambient_none.py` pass unchanged.

STILL OPEN, AND BIGGER: the FIRST `PreferencesDialog(...)` in a session costs
**902 ms**, against 55 ms (now 30) for the second. The difference is import
work -- `figure_settings`, the settings model, the catalogs -- paid on the
GUI thread at the moment the user asks for Preferences, with the backdrop
frozen for all of it. 385 has the paint counts. The backdrop's own heavy
import is already warmed off the GUI thread (`_HeavyImportInProgress`); this
one is not, and the same treatment applies.

2026-09-10 -- DEFECT 2 MEASURED PROPERLY, AND THE OBVIOUS FIX IS RULED OUT
--------------------------------------------------------------------------------

The baseline's second finding -- "THE THEME CHANGE IS STILL A THIRD OF A
SECOND" -- is now decomposed. This is a NEGATIVE result and it is worth
more than a guess: it closes the optimisation everybody reaches for first.

WHERE THE TIME IS. One theme change on a Mask screen, 1,049 live widgets,
offscreen:

    stylesheet() composition          0.7 ms
    app.setStyleSheet(sheet)        262 ms
    the whole apply                 307 ms

Composing the sheet is FREE. All of it is the one Qt call. And there is
exactly ONE such call per preference change -- traced, not assumed; an
earlier count of two was this measurement's own clearing call being
counted with it. So there is no redundant apply to remove.

WHAT THE COST IS NOT: THE SHEET. The sheet is 71,472 characters, 389
blocks, ~655 selectors. Measured on the same 1,049 widgets:

    empty sheet                       0.8 ms
    ONE rule (`QWidget { color }`)   89.2 ms
    half the sheet, by characters   182.6 ms
    base only, 196 blocks, 382 sel  199.2 ms
    the whole sheet                 204.6 ms

Dropping the 42 registered widget-QSS blocks -- 25,195 characters and 273
selectors, 42 % of the sheet by size -- saves FIVE MILLISECONDS of 205.
Going from 655 selectors to ONE saves 56 %. So the curve is a step, not a
slope: there is a large fixed cost for having any sheet at all, and after
that the sheet's size barely matters. TRIMMING OR SPLITTING THE SHEET IS
NOT THE LEVER, and an afternoon spent shrinking it would buy single-digit
milliseconds.

WHAT THE COST IS: THE WIDGET COUNT. Same sheet, a window filled with plain
labels:

        1 widget       1.0 ms
      250 widgets      9.6 ms      38 us/widget
      500 widgets     19.9 ms      40 us/widget
    1,000 widgets     46.8 ms      46 us/widget
    2,000 widgets    132.0 ms      66 us/widget

Linear at first and worse than linear by 2,000. A real module screen costs
more per widget than a QLabel does -- 1,049 of them come to 205 ms, not the
50 the label curve predicts -- because they are nested, named and styled.

SO THE ONLY LEVER IS NOT REPOLISHING EVERYTHING, which is what 378 already
measured from the other side: 107 ms for the visible screen against 587 for
the application. The change that would do it is to stop setting the sheet on
the QApplication and set it per top-level window, marking hidden module
screens dirty so their `showEvent` applies it.

NOT ATTEMPTED HERE, and the reason is this item's own constraint rather than
timidity. `app.setStyleSheet` covers every widget that exists AND every one
created later -- dialogs, popups, menus, a screen built after the change.
Per-window application has to reproduce that, and the failure mode is a
dialog opening in the previous theme, which is exactly "compromising
functionality". It needs a display to verify and a session that can watch
it happen.

WHAT IS WORTH KNOWING BEFORE THAT IS TRIED: `apply_preferences_to_app`
already has a signature guard that skips the whole rebuild when nothing
visual changed, and it already clears and reinstalls screen-local QSS
overlays around the global call. Whoever does the per-window version
inherits both, and the overlay mechanism is the half that already knows how
to give one screen its own sheet.

2026-09-10 -- FINDING 3 WAS THE HARNESS, NOT THE APPLICATION. WITHDRAWN.
--------------------------------------------------------------------------------

"EXPANDING A SECTION DROPS TWO FRAMES THE FIRST TIME AND NONE AFTERWARDS"
is not true, and this item's own rule -- write the harness first and prove
it catches a defect that is already there -- is what caught it, one step
late.

WHAT THE 47.6 ms WAS. `AppScreen` translates arriving subtrees from an
event filter that defers the work A TURN LATER; `_on_arrivals_in` says so
in its own docstring. `tools/perf_paint.py` built the screen, called
`app.processEvents()` ONCE, and started timing. That single call does not
drain a queue whose entries are posted for the next turn, so the build's
own deferred passes ran inside the first interaction measured and were
billed to it.

MEASURED BOTH WAYS, on the same panel, same machine, minutes apart:

    one processEvents() after the build   146.3 ms   "2 frames dropped"
    drained until quiet                     0.5 ms first, 0.1 ms after

    and through the corrected harness, which alternates collapse/expand:

    action                        first_ms  repeat_ms  frames
    expand a section                  4.23       3.80       0
    collapse a section                3.62       2.75       0
    type one character                0.07       0.01       0
    scroll the settings column        0.01       0.00       0

THE 146 ms IS REAL WORK AND IT IS NOT THE INTERACTION'S. Profiled, it is
four `retranslate_widget_tree` passes over 18,307 widgets making 88,388
`QObject.property()` calls -- the cost of BUILDING the panel, collected by
whatever ran next. Reporting it as the cost of expanding a section sends
someone to optimise a toggle that already takes a fifth of a millisecond,
which is exactly the "fix by symptom" this file forbids.

THE HARNESS IS FIXED, not worked around: `_drain_until_quiet` runs before
the first timed interaction, and its docstring carries both numbers so the
next reader can see why it exists. The `timed()` docstring's own example --
"typing the first character measured 39 ms, two dropped frames" -- was the
same artefact and is corrected in place; the same keystroke measures 0.07 ms
cold once the queue is drained.

  THE PRINCIPLE SURVIVES THE EXAMPLE. A cold number and a warm one are
  different questions and work done once per widget is real. But a "first"
  measured before the build has settled is not that work, it is the build.

WHAT THIS CHANGES ABOUT THE ITEM. Interaction latency is NOT a defect on
this screen -- nothing a user does to a settings panel costs a frame. The
two findings that survive the first run are the ones already recorded: the
theme change repolishing the whole application (a third of a second), and
the backdrop shading four times the pixels at 4K for the same frame rate.
BUILDING the panel is now a third candidate, with a number attached: 146 ms
of deferred translation, four full-tree walks, on a panel whose widgets were
already translated once as they were constructed.

2026-09-10 -- THE BUILD'S 146 ms, LOCATED: THE TREE IS TRANSLATED THREE TIMES
--------------------------------------------------------------------------------

Following the number the correction above freed up. Instrumented
`_LateCaptionTranslator._translate` and counted every pass and every
descendant it walked, building one Measure screen:

    pass  batch  root                 descendants
      0      1   AmbientWidget                  1
      1      1   ModuleHeader                   6
      2      1   Divider                        0
      3      1   QSplitter                  8,034
      4      6   QWidget                    7,389
      5      6   QScrollArea                  641
      6      6   QSplitterHandle                0
      7      6   QSplitterHandle                0
      8      7   QSplitter                  7,327
      9      7   Card                          31
     10      7   QWidget                       20
     11      7   QLabel                         5
     12      7   QLabel                         0

    13 passes, 23,454 widget visits, of which THREE PASSES ARE 22,750.

THE THREE BIG ONES ARE NESTED AND IN DIFFERENT BATCHES -- 1, 6 and 7. Each
is a near-root walk triggered when another large container is parented in,
so the tree is translated roughly three times over as it is assembled, and
every widget in it was already translated once as it was constructed.

WHY THE OBVIOUS FIX DOES NOT WORK. Deduplicating roots WITHIN one
`_on_arrivals_in` batch would save nothing: the three expensive passes are
in three different batches, an event turn apart. The saving needs a marker
that survives between turns -- "this subtree was translated at generation
N" -- so a later overlapping pass skips what is already done and redoes it
only when the language actually changes.

NOT ATTEMPTED TONIGHT, and the reason is the risk rather than the work. The
failure mode of getting it wrong is a widget left in English in one of nine
locales, which is invisible on this machine and to this test suite. It IS
verifiable headlessly -- capture every translated widget's text after a
build, apply the change, compare the sets -- and that verification is the
first half of the job, not an afterthought.

    WHOEVER TAKES IT: the cost is build-time only. Interaction latency is
    now measured as clean (4 ms to expand, 0.07 ms to type, no dropped
    frames), so this is about how long a module screen takes to appear, not
    about smoothness once it is there.

2026-09-10 -- THE GUARD FOR THE PER-WINDOW STYLESHEET, WRITTEN FIRST
--------------------------------------------------------------------------------

This item's own method is "WRITE THE HARNESS FIRST, and prove it catches a
defect that is already there". The remaining lever -- setting the sheet per
top-level window instead of on the QApplication -- has not been written
because of a named risk: "the failure mode is a dialog opening in the
previous theme, which is exactly compromising functionality", and "it needs
a display to verify and a session that can watch it happen".

THE SECOND HALF OF THAT IS TRUE OF BEAUTY AND NOT OF THIS. Whether a theme
LOOKS right needs a display. Whether a widget created after a theme change
is painting the PREVIOUS theme does not: a stylesheet colour resolves into
the widget's palette, and an offscreen widget reports it.

    QLabel { color: rgb(200,100,50) }  ->  palette WindowText #c86432

measured on this box, offscreen, after `ensurePolished()` and one
`processEvents()`.

SO THE GUARD IS IN, BEFORE THE CHANGE:
`tests/qt/test_a_dialog_never_opens_in_the_previous_theme.py`. Five cases,
holding exactly one property and nothing about aesthetics -- a widget
created AFTER a theme change resolves to the SAME theme as one created
before it:

  * a plain widget made after the change;
  * one that existed across it;
  * A DIALOG opened after it, which is 380's own sentence for the risk and
    is its own top-level window -- precisely what a per-window sheet has to
    remember;
  * a whole QMainWindow built after it, which is the module screen the fix
    would mark dirty and re-sheet on `showEvent`.

AND A NEGATIVE CASE THAT MAKES THE OTHER FOUR MEAN SOMETHING. Under

2026-09-11, THE SAME EVENING -- THE LEVER COST THREE DEFECTS, ALL OF ONE KIND,
AND THE REACH MEASUREMENT COULD NOT HAVE FOUND ANY OF THEM
--------------------------------------------------------------------------------

The section above records the change as taken and its reach as "207
sampled, 161 sheeted, 46 inside a hidden page, 0 genuinely missed". THAT
MEASUREMENT WAS TAKEN THE WRONG WAY ROUND. It opened its modules and THEN
applied the sheet. spaCR applies the sheet at launch and the user opens
modules afterwards, so the measurement sampled the one ordering in which
the change works.

THREE DEFECTS, and they are one defect wearing three coats: CODE THAT
ASSUMED THE APPLICATION CARRIED THE THEME.

  1. A MODULE OPENED AFTER LAUNCH WORE NO SHEET AT ALL. `stylesheet_roots`
     marks the pages that exist when it runs, and it runs while a sheet is
     being applied. A page created later was never marked and the window is
     deliberately bare, so it inherited nothing. A probe under a newly
     opened module resolved to `#000000` on the dark theme -- black text on
     a dark screen, a whole module wide. That is the ordinary path, not an
     edge.

     Fixed by marking at each of the three places a page joins the stack,
     so the event filter sheets it on `Polish` or `Show`.

  2. MARKED, SHEETED, AND THEN WIPED. Marking alone did not fix it, and the
     trace said why in two lines: the filter sheets the screen while it is
     still PARENTLESS during `__init__` -- a parentless widget is a window --
     and `AppScreen._sync_page_palette` then calls `setStyleSheet("")` on
     its own root. Correct when the application carried the theme and a
     screen's own sheet was a local suffix; fatal now the screen carries
     the whole 73 KB.

     TWO FIXES, because the two halves fail at different times.
     `_sheet_one_window` now compares a DIGEST of the text it last applied
     against the widget's current stylesheet, so a sheet replaced by anyone
     is repaired at that widget's next polish. And `_sync_page_palette`
     writes through `set_a_sheeted_widgets_own_rule`, which replaces the
     screen's OWN rule and re-applies the window sheet under it -- because
     a page that is already on show never gets another polish, and the
     digest alone left it black until the next theme change.

       A CACHE KEY THAT RECORDS WHAT WE DID RATHER THAN WHAT IS TRUE WILL
       EVENTUALLY BE WRONG. Nothing in Qt promises that a stylesheet we set
       is the stylesheet that is there.

  3. THE LATE-BLOCK SEAM STOPPED WORKING ENTIRELY, and this one was
     invisible to every test. `ensure_widget_qss_applied` -- the thing that
     puts a block registered at a screen's import onto that screen before
     it paints -- began:

         app_sheet = app.styleSheet()
         if not app_sheet:
             return False

     on the reasoning that a caller who never opted into spaCR styling is
     not opted in by constructing one of its widgets. Per-window sheeting
     takes the application sheet DOWN on purpose. So in every production
     run that guard read "nobody opted in" and the function did nothing.

       MEASURED: opening one module registers four blocks -- `SettingsBox`,
       `ClassEditor`, `SettingAlphabetChip`, `TableChip` -- and NOT ONE of
       the four reached the screen that had just imported them. That is
       precisely the defect `tests/qt/test_widget_qss_is_complete.py`
       exists for, reintroduced from underneath by a change to who owns
       the sheet.

     `test_a_late_registered_block_reaches_its_screen_before_first_paint`
     could not see it: its fixture applies the theme with
     `app.setStyleSheet`, so the old question still had the old answer
     there. The seam now asks `app.styleSheet() or window_stylesheet(app)`,
     and a new guard applies the theme the way the application does.

WHAT THIS SAYS ABOUT THE SWEEP, and it is the same lesson as the per-window
step one size up. A change whose blast radius is "who owns a piece of
global Qt state" is not tested by the tests written for the change. The
per-window step moved seven tests, one a real regression. This one shipped
three defects, all found within the hour, all by guards written for it --
and the first was live on nightly for about an hour before it was found.

  THE GUARD FOUND TWO AND THE THIRD NEEDED A DIFFERENT QUESTION. Asking
  "does every widget wear the sheet" catches 1 and 2. Nothing about the
  cascade catches 3, because the block that never arrived was not
  overridden -- it was never written, and a widget with no rule looks
  exactly like a widget whose rule says nothing.

STILL WORTH IT, on the numbers, and the numbers are unchanged by the three
fixes: nominated roots ~1,671 ms against ~3,739 ms for the whole window,
same process, same window, four modules open. But the honest price of the
4.8x is an evening of defects in code that had no reason to expect the
change, and any future step in this direction should budget for that rather
than for the diff.

2026-09-11 -- THE CAUSE, NAMED AND PRICED: 135,800 EVENTS PER MODULE OPEN,
MULTIPLIED BY EVERY APPLICATION-WIDE EVENT FILTER
--------------------------------------------------------------------------------

The section above leaves the 8x gap as an open question and says the next
attempt should put the watchdog INSIDE `launch` rather than reach in from
outside. Done -- `spacr/qt/stall_watch.py`, behind `SPACR_WATCH_GUI_STALLS`,
one `os.environ.get` when off -- and it answered.

FIRST IT EXPOSED A FLAW IN ITSELF, which is worth recording because it is
the same shape as the evening's other instrument errors. One snapshot per
stall gave FOUR STALLS WITH FOUR DIFFERENT LAST FRAMES: an event filter, a
screen constructor, a settings-search install, another event filter.

  ONE SNAPSHOT NAMES WHERE THE THREAD WAS, NOT WHERE THE TIME WENT, and
  those are different questions whenever the stall is a LOOP rather than a
  single blocking call. A list of four suspects reads like an answer.

So the watch now samples for as long as the stall lasts and counts the
innermost frames. Six stalls, 63 samples, aggregated:

    IN AN APPLICATION-WIDE EVENT FILTER   32 of 63 = 50.8 %

       14   22.2 %  live_zoom.py:192 eventFilter
        5    7.9 %  dialogs.py:800 eventFilter
        4    6.3 %  field_fade.py:231 eventFilter
        3    4.8 %  feature_dictionary.py:858 eventFilter
        2    3.2 %  i18n.py:4491 eventFilter
        2    3.2 %  module_hints.py:142 eventFilter
        1    1.6 %  button_roles.py:247 eventFilter
        1    1.6 %  theme.py:3540 eventFilter

EIGHT DISTINCT FILTERS, and an application-level filter sees EVERY event
for EVERY object in the thread. That also explains the 8x: an in-process
`MainWindow` installs TWO of them, because the other six are installed by
`launch`.

THEN THE CONTROLLED VERSION, because the above is a correlation. One
process, one screen, the NUMBER of filters as the only variable, each
extra filter doing nothing but counting and returning False:

    + 0 filters   measure opens in   2.53 s
    + 6 filters                      2.60 s
    +24 filters                      4.86 s
    +96 filters                     14.65 s

    135,800 EVENTS ARE DELIVERED DURING ONE MODULE OPEN -- counted, not
    estimated: each passenger filter saw 135,776-135,867 of them.

That is ~126 ms per application-wide filter per module open, or 0.93 us
per event per filter, for a filter that does NOTHING. The real eight do
work.

  THE DEFECT IS NOT ANY ONE FILTER. It is that opening a screen delivers a
  hundred and thirty-five thousand events, and every one of them is
  multiplied by the length of a chain that only ever grows. Eight filters
  is ~1 s of pure dispatch before any of them does anything useful, and
  nothing in the code says the chain has a cost, so the ninth will be added
  the same way the eighth was.

AND IT IS AREA 4 AS WELL AS AREA 3. The request judges "smoothness" by
typing, scrolling and hovering, and every one of those events pays the same
multiplier. A filter chain is a tax on input latency that does not show up
in any per-screen measurement.

WHAT TO DO ABOUT IT, in the order this file's method requires -- measure,
then fix by cause:

  1. THE EVENT COUNT IS THE BIGGER HALF. 135,800 events to build one
     screen is the number to attack first; halving it halves every
     filter's bill at once. Nobody has yet asked WHICH events those are,
     and the same sampling hook can answer it.
  2. THEN THE CHAIN. Several of the eight are narrow enough to be
     installed on a widget rather than on the application -- `field_fade`
     and `feature_dictionary` both filter for one widget's benefit --
     and a filter installed on the widget it serves costs the application
     nothing.
  3. `live_zoom` IS 22.2 % ON ITS OWN and is the one to read first.
