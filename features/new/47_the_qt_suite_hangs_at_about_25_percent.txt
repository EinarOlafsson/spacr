2026-08-09 - pytest-xdist INSTALLED, AND IT WORKS ON THE QT SUITE
--------------------------------------------------------------------------------

Step 2 of WHAT TO DO, done. `pip install pytest-xdist` (3.8.0, with
execnet 2.1.2). Measured on a five-file qt subset, same machine, same load:

    serial      44 s
    -n 4        17 s        2.6x, 0 failures

THE QUESTION THIS ANSWERS is not the speed -- it is whether the fixtures
survive being distributed. This file worried that the session-scoped
`qt_theme_applied` fixture would fight xdist. It does not: xdist gives each
worker its OWN session, so a session-scoped fixture runs once per worker
rather than once, which is exactly what a per-process QApplication needs.
That is the property that makes a Qt suite parallelisable at all, and it is
why `-n` works here when it often does not for suites sharing a database.

Used `--dist load` (the default), so tests are handed out as workers free
up. If an order-dependent failure appears under `-n` that does not appear
serially, `--dist loadfile` keeps each FILE on one worker and is the first
thing to try -- that distinction matters here because instructions 03 and 46
are about order-dependent failures, and xdist changes the order.

A FULL `tests/qt` RUN AT `-n 4` IS IN FLIGHT as this is written, with
`--timeout=300` so a single hung test names itself instead of stopping the
run at a wall clock. That run is the actual success criterion for this task
-- "one run reaches its summary line" -- and its result belongs in the next
entry here.

Note the machine is NOT idle (load ~18 from the concurrent tutorials
session), so `-n 4` rather than `-n 8`: the standing constraint is 16 cores

2026-08-10 - THE SWEEP AUDITED ITSELF, AND THAT IS WHERE THE VALUE WAS
--------------------------------------------------------------------------------

The stale/ordering sweep took its eleven suites from 48 failures to 3, but
the useful output was its SELF-AUDIT: every agent's work was checked by a
second agent that ran mutation tests against the new assertions. It found
several of its own edits had produced tests that could no longer fail.

TWO DEAD ASSERTIONS, both now repaired and both mutation-proven in each
direction:

  `assert not bar.clipped_items()` (twice in test_cov_qt_app) could NEVER
  fail. `clipped_items()` reads `_elided`, which is only ever set in
  `resizeEvent`, so a widget that was never shown reports nothing clipped
  however narrow it is. Proven by mutation: a sidebar column 52 px too narrow
  for its own text passed all six sidebar tests. One of the two was
  pre-existing -- the sweep had merely copied it into a second parametrised
  test. Both now lay the widget out first, and a WIDTH_MAX of 150 makes them
  fail as they should.

  `test_the_classes_setting_gets_the_class_editor` asserted shape with
  `all(isinstance(rule, dict) for rule in value.values())`, which is
  VACUOUSLY TRUE over an empty dict -- an editor that dropped every class
  passed. It now pins the two default class names.

AND A REAL PRODUCT BUG, found by an agent following the "if the change looks
accidental the test is right" rule rather than editing the assertion:

  A settings CSV stores `repr(value)`, so `classes` comes back as the TEXT
  `"['nc', 'pc']"`. `ClassEditorWidget.set_value` handled Mapping and list
  and nothing else, so the string matched neither arm, fell through to an
  empty table, and REPORTED SUCCESS: `apply_settings_dict` returned
  `applied=1` while `collect()['classes']` was `{}`. Because `{}` is a
  Mapping, `classify_classes.normalize_settings` then skipped its own
  legacy-translation branch, so nothing downstream recovered them.

  Every other list-shaped key survived that round trip. This was the one that
  decides WHAT GETS TRAINED, and losing it was silent. Fixed, with the
  corrupt-string case tolerated rather than raising out of an import.

THE LESSON, which is why the audit stage is worth its cost: a sweep that
updates failing assertions will, left unchecked, produce a green suite that
tests less than the red one did. Three of the weakenings here were
introduced by the very pass that fixed the failures, and none would have been
visible in a summary line. Mutation testing -- change the product, confirm
the test screams -- is the only check that catches it.

TWO MORE FINDINGS RECORDED, NOT FIXED:

  `verbose_logger.apply_console_levels()` mutates a process-global forwarder
  and has NO counterpart that restores or removes the filter. Fine for a GUI
  that launches once; it means the console gate is unrestorable by design,
  and the test fixture now has to reach into `_handler.filters` to undo it.
  A small restore/reset API would let the fixture stop touching privates.

  A flake, not reproducible on demand: constructing `AppScreen` leaves a
  QThread alive ("QThread: Destroyed while thread '' is still running"), and
  one run in ~5 segfaulted with a background PipelineWorker importing
  matplotlib concurrently with pytest-qt's GC on the main thread.

`tests/qt/test_ambient_none.py` was carried here as a hanging test under the
CI serial tail, with its neighbours costing about 50 s each. Run exactly as CI

THE FAILURE MODE THAT IS REAL, and that every guard in this file misses: the
run finishing its tests and then never reporting them. `--timeout` is a
PER-TEST guard, so once the last test is done it is gone. Anything that stops
the interpreter exiting then stops the run between the final test and the
summary line, with no test to blame and no output to read -- and under `-n`
the workers have already written their results and sit on a core apiece while
the controller waits.

Python joins every NON-DAEMON thread before it finalises, which is what turns
one forgotten thread into an unbounded wait. So `tests/conftest.py` now, at
`pytest_sessionfinish`:

  * NAMES every non-daemon thread still alive, with its target, while the run
    can still print. Daemon threads are left out deliberately -- they cannot
    delay finalisation, and this suite ends with a handful every run, so
    listing them would bury the one that matters.

  * ARMS A WATCHDOG. If shutdown has not finished inside the budget (300 s by
    default, `SPACR_PYTEST_SHUTDOWN_WATCHDOG_S=0` turns it off), every
    thread's stack is dumped and the process exits non-zero. An endless
    shutdown becomes a diagnosis.

Armed at `pytest_sessionfinish` because that is the last hook guaranteed to
run: `pytest_unconfigure` is on the far side of the stall it exists to catch.

Demonstrated rather than asserted, in `tests/test_shutdown_watchdog.py`: a
generated one-test run that leaks a parked non-daemon thread. Without the
hook that run prints nothing at all and never returns -- killed at 25 s with
no summary, which is exactly the reported shape. With it, the leaked thread
is named in the run's own output and the process dies with every stack
printed.

WHAT IS NOT ANSWERED, and it needs a distributed run to answer: WHICH object
holds a worker open. No `-n` run was available here, and the wedge does not
appear serially -- a 40-file Qt chunk under `--cov`, the thread-heavy files
(`test_ai_shutdown`, `test_qt_worker_teardown`, `test_force_quit`,
`test_bridge`, `test_console_thread_safety`, `test_worker_stack_size`,
`test_threading_cancellation_audit`, `test_cov_4_shutdown`) and the serial
tail all exit cleanly, leaving nothing but daemon `Dummy-*` threads, which are
QThreads that have run Python and cannot delay finalisation. spaCR itself
starts no non-daemon thread: the three `threading.Thread` call sites in the
package all pass `daemon=True`.

So the next distributed run answers it for free -- the wedged worker now
prints its stacks and its lingering threads instead of spinning silently, and
that output is the name of the culprit.

THE WEDGE WAS OUTSIDE THE WATCHDOG'S BUDGET, AND THAT IS WHY IT PRINTED
NOTHING
--------------------------------------------------------------------------------

THE TWO ITEMS THIS FILE WAS CARRYING, re-measured on this tree:

    the interleaved reproduction from 25     149 passed, 0 errors, 59 s

THE LIVE ONE. A distributed run wedges after every worker has WRITTEN ITS
COVERAGE DATA and before anything prints a summary, spinning at 100% CPU with
no test to blame. The watchdog installed here for exactly that shape did not
fire, and the reason is hook order rather than anything about Qt:

    pytest-cov stops and SAVES coverage from the tail of its own
    `pytest_runtestloop` WRAPPER -- before a single `pytest_sessionfinish`
    implementation runs anywhere. Its source says why: "we need to wrap
    pytest_runtestloop. by the time pytest_sessionfinish runs, it's too late
    to set testsfailed".

    xdist's worker reports itself finished from the tail of its
    `pytest_sessionfinish` wrapper.

    this file's watchdog was armed from a `pytest_sessionfinish`
    implementation marked `trylast` -- after every other implementation of
    that hook.

So the interval between "coverage on disk" and "summary printed", which is
where the evidence puts the wedge, was the one interval nothing was armed for.
A stall there produces no stack dump, no exit code and no name, which is
exactly what was reported.

FIXED by starting the budget when the last test ends. tests/conftest.py now
arms the watchdog from the post-yield of an INNERMOST `pytest_runtestloop`
wrapper, so it covers the rest of that hook's wrappers (the coverage write
included), every `pytest_sessionfinish`, `pytest_unconfigure`, `atexit` and
interpreter finalisation. `pytest_sessionfinish` re-arms, so a shutdown that
is honestly slow is measured from the point the reporting plugins have
finished rather than from the last test.

That reporting phase gets its own, longer budget --
`SPACR_PYTEST_REPORT_WATCHDOG_S`, four times the shutdown one, and off when
the shutdown watchdog is off. It holds the one operation here that is
legitimately slow, combining and reporting a distributed run's coverage, and
bounding that at the shutdown budget would have shot the runs this guard
exists to protect. A distributed WORKER gets the SHORT budget instead: a
collocated worker saves its coverage data and stops, the combining and
reporting are the controller's job, and a worker that then goes quiet is the
process most worth shooting quickly -- the whole run is waiting on it and
until it says something there is nothing to read.

Driven both ways in tests/test_teardown_watchdog_arming.py: a plugin that
stalls in `pytest_sessionfinish` and one that stalls in the tail of a
`pytest_runtestloop` wrapper are each dumped and killed with the stalling hook
named in the stack, and switching the loop-end arming off restores the endless
wait, so the hazard and the guard are both demonstrated rather than asserted.

    PySide::destroyQCoreApplication()
      Shiboken::BindingManager::visitAllPyObjects(...)
        QWidget::~QWidget / QObjectPrivate::deleteChildren()   x5, through
        QStackedWidget::~QStackedWidget()                      the tab stack
          Shiboken::Object::destroy(SbkObject*, void*)
            Shiboken::BindingManager::releaseWrapper(SbkObject*)   <-- SIGSEGV

A Python wrapper is released a second time while the application destroys the
widget tree: an ownership bug, not an arithmetic one. The two `AppScreen`s are
built with no parent, `QTabWidget.addTab` then transfers ownership to the tab
stack, and `self._screens` keeps holding them -- which is the shape that
produces exactly this, and `QStackedWidget` sitting in the middle of the trace
is the tab widget's own stack. This is a product crash in
`spacr/qt/screens/train_cellpose.py` reachable by a user closing that screen,
not a test artefact, and it is left for whoever owns that file.

IT IS ALSO THE ONE CANDIDATE ON THE WEDGE LIST THAT IS REAL HERE. "A
QApplication never destroyed" was on the list of things to rule out; what this
tree actually has is a QApplication whose destruction walks into a released
wrapper. That path -- `destroyQCoreApplication` -> `visitAllPyObjects` -> the
whole tree -- runs at the end of EVERY Qt process, worker included, and it is
the only place found so far where the amount of work at exit depends on the
state the tests left behind.

WHICH OBJECT HOLDS A WORKER OPEN IS STILL NOT NAMED, and the honest answer is
that it is not visible serially. Every serial run measured here -- the
thread-heavy Qt files, the ambient files, the mixed-ordering set -- reaches
its summary and the interpreter is gone within half a second of it. What the
candidates cost was measured rather than assumed, and three of them are ruled
out as the shape being chased:

    a live QThread at exit          ABORTS in 1.7 s (signal 6). Qt's
                                    "Destroyed while thread is still running"
                                    is fatal, whether the thread is spinning
                                    or blocked in C++. Loud, not silent.
    a retained widget tree          60,000 widgets built and torn down in
                                    ~5 s. Proportional, not unbounded.
    a parked non-daemon thread      0% CPU, and already named and bounded.

None of those produces a process burning a core with nothing to read, which
is what was reported. What does fit is work inside the teardown window itself,
and that window is now inside the budget and dumps its stacks. So the next
distributed run answers the question for free: the wedged process prints every
thread's stack and names whatever Qt state it is still holding, instead of
spinning unwatched.
