  The real pipelines are already within 1.5x; the 4-18x of item 638
  reproduces only with very chatty output (the synthetic row), which is
  what was fixed:
  - PipelineWorker emitted line_ready once per printed line; every line
    became a queued slot call, a console append, a RunHandle update and a
    Home banner refresh. Output is now joined into one chunk per 50 ms
    (first line after a quiet spell still goes out at once; order kept;
    drained before errors and before finished).
  - The console trimmed its 200k-char head one paragraph per cursor
    operation (qtpy's patched movePosition) on every line; now one edit.
  - INFO/DEBUG log records reach the console batched every 50 ms; a
    warning or error flushes first.
  - RotatingFileHandler stats the log file and formats each record twice
    per emit; spaCR's handlers now do that only near the size limit
    (logging_util._quicken). Rollover point unchanged.
  - The first run in a process enumerated every installed distribution
    for the manifest (0.5-1 s on the worker); package versions are now
    memoised and read on the post-startup background thread.
  - Found while measuring and fixed before commit: the first version of
    the output coalescing held its lock while emitting on the GUI thread,
    so a DataLoader worker forked at that moment inherited it held and the
    Classify run hung. The lock now never spans an emission.
  Classify's remaining gap is matplotlib writing six progress PDFs per
  epoch (35 % of the worker's samples) while sharing the interpreter lock
  with the GUI thread at the 1 ms switch interval.
  Remaining GUI overhead on the chatty case is the file logging the GUI
  turns on (spacr.log, per-record flush) and interpreter-lock sharing with
  the GUI thread at the 1 ms switch interval; the fixed per-run cost is
  ~0.4 s (git hash for the manifest, thread start).

   Sum of all 54: 44.3 s -> 41.1 s; geometric mean ratio 0.95 (an earlier
   interleaved set of 5 at load 29: 31.9 -> 29.6 s, ratio 0.91). Single
   modules move +-30 % between pairs at this load (Mask 2.7 vs 3.2 here,

   Causes found (GUI-thread samples summed over the 11 slowest modules):
   - Preference reads, 10-13 % under load: every get_font_scale /
     get_theme / _get_show_alpha_features built its own QSettings (25 us
     idle, several thousand per open). The module open now runs inside
     preferences._one_store(): one store, 1 us a read.
   - The cursor policy's Show handler, 7.6 %: one cursor read per child
     widget shown. A widget without WA_SetCursor (and no override cursor)
     is now passed over.
   - PySide's per-import probe (shibokensupport.feature._mod_uses_pyside)
     ran inspect.getsource on every newly imported module (tokenised read,
     kept in linecache), 3-4 %. Replaced at launch by a raw-bytes test of
     the same substring; modules without a .py file still go to PySide's.
   - categories_for_app re-expanded every setting key 5-6 times per open
     (2-3 % of Mask): memoised per module against the category table's
     shape, fresh copies handed out.
   - close_mark_side rasterised its glyph (tightBoundingRect) at every
     style change: measured once per font.
   - The data-library thread's run-environment read (0.8 s of metadata
     parsing sharing the interpreter lock with the second and third opens)
     parsed each distribution twice; once now (0.16 s).

   Looked at and left:
   - Settings categories already build on expand (item 380's waiting
     headings plus SettingsWidgets.wait_for for plain controls); what is
     left of _build_sections is the open categories' own widgets.
   - Previews: none is built before shown in the 11 slow modules' samples.
   - QSS: each screen gets the sheet once, at its Show (380); the
     remaining _sheet_one_window cost (0.25-0.35 s on Mask / Make Masks,

   - The walkthrough offer (3.5 %) runs only on a user's first visit.
   - The rest of a slow open is Qt's own C++ work inside the breaths and
