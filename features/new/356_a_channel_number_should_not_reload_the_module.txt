--------------------------------------------------------------------------------
TWO CASES, AND THE MAINTAINER HAS ALREADY SEPARATED THEM
--------------------------------------------------------------------------------

CASE 1 -- AN OBJECT CHANNEL. Typing a number into `nucleus_channel`,
`cell_channel` or `pathogen_channel` should SHOW that object's settings
category; clearing it should hide it. The settings already exist either way.
This is a visibility toggle and needs no rebuild at all.

CASE 2 -- `number_of_organelles`. The settings do not exist yet, so they have
to be SPAWNED. The maintainer's own words: "the settings themselves have to be
spawned, but if this can be done smoothely with out reloading that would be a
better user experience". So the CATEGORY behaves like case 1; only the new
rows are built, and only the ones that are new.

--------------------------------------------------------------------------------
WHY THIS IS WORTH REAL CARE
--------------------------------------------------------------------------------

REBUILDING THE FORM IS WHAT COSTS THE 1,263 ms IN INSTRUCTION 315. That item
measured a module build and found 54 `setStyleSheet` calls on already-
populated subtrees, each sending ~1,330 events to its descendants, plus an
event filter dispatched 109,410 times. Every one of those is paid again on a
reload. So this is not only a smoothness request -- it is the same cost 315 is
trying to remove, being paid on a keystroke.

AND A REBUILD LOSES STATE. Instruction 335 was "live preview loses the image
after a settings change", and instruction 349 -- fixed 2026-09-02 -- was a
path being written and then overwritten by a rebuild. A form that rebuilds
on a keystroke is the same hazard: anything the user typed and has not
committed, any scroll position, any expanded fold.

--------------------------------------------------------------------------------
WHERE TO LOOK
--------------------------------------------------------------------------------

`AppScreen` builds its sections through `settings_model`, and there is already
machinery for showing and hiding rows: `_lay_out_the_rows_that_are_back` is
named in instruction 310's last entry as the thing that brings conditional
object sections back, and the Pathogen/Nucleus/Organelle sections are already
described there as "conditional on the run having that object". So the
conditional-visibility concept EXISTS. The question is whether the current
path re-enters a full build to apply it.

FIND THE REBUILD FIRST, and do not assume it is a deliberate `rebuild()` call
-- it may be a signal connected to a slot that happens to reconstruct. 310's
entry records that setting `pathogen_channel` through the widget did NOT bring
the rows back, which suggests the current wiring is already partly broken and
is worth understanding before adding to it.

--------------------------------------------------------------------------------
WATCH
--------------------------------------------------------------------------------

* GREYED, NOT REMOVED (INVARIANTS 6) applies to a control another mode does
  not read. Hiding a whole CATEGORY the run has no object for is different
  from hiding one control, and is what is asked for here -- but the values in
  it must survive being hidden, exactly as lowering `number_of_organelles`
  keeps the higher slots' values today.
* SPAWNING ONLY WHAT IS NEW. Going from 2 organelles to 3 should build one
  slot, not rebuild three. Going 3 -> 2 should hide, not delete.
* Instruction 326 has just made the slot count exact -- a run configured for N
  carries N slots' keys -- so the spawn boundary is now well defined.

--------------------------------------------------------------------------------
HOW IT WILL BE CHECKED
--------------------------------------------------------------------------------

* Typing a channel number reveals that object's category and clears it hides
  it, with NO widget outside that category destroyed and rebuilt -- asserted
  by identity (`is`) on a sample of widgets taken before and after, not by
  timing.
* Raising `number_of_organelles` from 2 to 3 leaves slots 1 and 2's widgets
  the same objects and adds slot 3's.
* A value typed into an unrelated field survives both.
* The GUI-thread block for a channel keystroke is measured and reported here,
  against 315's 1,263 ms module build as the thing being avoided.

--------------------------------------------------------------------------------
2026-09-02: DONE FOR CASE 1, AND THE REBUILD IS KEPT FOR CASE 2 ON PURPOSE
--------------------------------------------------------------------------------

FOUND BY MEASURING, as this file asked. The reload is not a `rebuild()` call
anyone would find by reading: `_watch_the_settings_that_decide_the_form`
connects every form-shaping key's commit to `_rebuild_the_form`, which calls
`window.rebuild_app_screen` -- and that builds a NEW SCREEN and puts it in
the window's stack. Measured on Mask, committing a value into
`nucleus_channel`:

    before   1 rebuild, 455 ms, `_screens['mask']` is a different object
    after    0 rebuilds,  18 ms, same object

Not one row was added or removed by that rebuild. The panel already builds a
control for every object it can name, so the whole 455 ms bought a change of
VISIBILITY -- and took every uncommitted edit, scroll position and expanded
fold with it, which is instruction 335's and 349's failure mode as well as
315's cost.

THE MACHINERY WAS ALREADY THERE, exactly as this file suspected.
`SettingsWidgets.refresh_object_visibility` decides every gated row and calls
`_hide_the_headings_of_slots_the_run_lacks`, which is the category toggle the
request asks for. It was being reached the long way round, through a rebuild.
The change is to route the two kinds of key to two different slots:

    number_of_organelles  -> _rebuild_the_form            (rows must EXIST)
    nucleus_channel etc.  -> _show_the_objects_the_run_has (rows must SHOW)

CASE 2 IS NOT AN OVERSIGHT AND IS PINNED. Raising `number_of_organelles` from
1 to 2 spawns 52 `organelleb_*` controls that were not on the form -- measured
-- so there is nothing to reveal and the rebuild is what creates them. The
request says so itself: "the settings themselves have to be spawned". A test
asserts that rebuild still happens, because losing it would be a slot with no
settings and nothing saying why.

DOING CASE 2 WITHOUT A REBUILD is what is left of this instruction, and it is
the "if this can be done smoothely" half rather than the requirement. It
needs the panel to add rows to a built form -- the same spanning-composite
problem 364's table mount ran into -- and 364's per-object table would remove
the need entirely, since a new organelle there is a COLUMN and not 52 rows.
Worth doing after that table is mounted rather than before.

Also repaired here: `test_cov_r4_app_screen` asserted a failed download
restores the caption "Load the example images", which the button has not said
since the three example-data buttons became one "Load test data…". It was
pinning a name that had moved rather than the behaviour it is about.


--------------------------------------------------------------------------------
2026-09-25: CASE 2 DONE -- THE COUNT SPAWNS ITS SLOTS WITHOUT A RELOAD
--------------------------------------------------------------------------------

The count's commit now goes to `AppScreen._follow_the_organelle_count`
instead of `_rebuild_the_form`:

  * LOWERING, or raising within slots already built: the same in-place
    object-rule pass a channel gets (`_show_the_objects_the_run_has`); the
    rule already hides slots above the count, and `collect()` already
    drops them unless they hold something.
  * RAISING PAST THE BUILT SLOTS: `SettingsWidgets.organelle_keys_to_spawn`
    names the keys first, the screen checks it has a heading for every
    category they fall in, then `spawn_organelle_slots` builds exactly those
    controls (values from `_defaults` when a file already carried the slot,
    otherwise cloned from the shipped first slot -- the rebuild's rule) and
    wires each new role's type/diameter/preset signals once
    (`_connect_the_signals_of_role`, split out of
    `_connect_object_visibility_signals`). `grow_to_fit_the_organelle_count`
    used to REPLACE `_defaults` with the shipped ones, which would have
    dropped imported hidden values; it now only adds missing keys.
  * PLACEMENT: a flat category gets the new rows inserted beside the slots
    before them in declared order, as "waiting" rows -- the field spans a
    form row and the object rule captions it in place when the slot's
    channel is set, the mechanism rows of absent objects already use. A
    category split by object gets a new sub-heading per slot. A category
    still waiting to be opened is opened first. A top-level category with no
    heading at all -- Mask's two organelle categories at a count of 0 -- is
    built by the normal section path and inserted where the layout lists
    it. The new slot's channel is watched like the panel's own switches,
    and a mounted per-object table (364) is reseeded, so the slot is a new
    COLUMN there.
  * FALLBACK to the full rebuild only when a run owns the screen (it defers
    as before), the panel is drawn as tabs, or a nested category has no
    heading to receive rows.

MEASURED on Mask, offscreen: 0->1 479 ms, 1->2 585 ms, 2->3 583 ms, 3->1
78 ms, all the same screen object; a full rebuild at 3 took 1,795 ms. The
47 organelleb_* controls spawned in place are exactly the set a rebuild
builds (compared key for key).

The checks this file set: slots 1 and 2 keep their widgets and slot 3's
are added (tested); a value typed into an unrelated field survives (every
control that existed before the raise is the same object after, and an
uncommitted spin-box value is kept). The pinned
`test_the_organelle_count_still_spawns_its_settings` is replaced by the
in-place tests; test_cov_r4_app_screen's two watcher tests now expect the
count's slot to be `_follow_the_organelle_count`.

Tests: tests/qt/test_a_channel_number_reveals_rather_than_reloads.py 11
passed (7 new: in-place spawn with every prior control unchanged, 2->3,
the new channel row captioned next to slot 1's, the new channel revealing
its settings, lowering in place, the per-object table gaining a column,
the run-in-flight fallback). Every other tests/qt file naming
number_of_organelles (23 files) passes except test_settings_search's two,
which fail identically on nightly without this change (cellpose3 rows
unreachable; an order-dependent size check).
