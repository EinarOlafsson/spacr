--------------------------------------------------------------------------------

  nucleus_flow_threshold, cell_flow_threshold and pathogen_flow_threshold
  with 100. get_default_test_cellpose_model_settings and
  get_default_apply_cellpose_model_settings filled FT with 100, and

  accepts every candidate".
* spacr/validate.py _check_numeric_sanity warned on any flow threshold
  outside 0 to 3 with the fix line "Cellpose's own default is 0.4; spaCR
  ships 1.0. Values above 3 disable the filter entirely." So it fired on
  spaCR's own default on every Mask run, and the "ships 1.0" in it had been

* spacr/qt/synthetic.py demo_settings('mask') set cell_flow_threshold 1.0.

* The Qt side had no default of its own. The Mask form builds from
  settings.py, and the live preview and Make Masks already opened at 0.4.

History of the default: 100 (2024-07-18), 1.0 (4b9fef8b9, 2025-07-02),
100 again (df753075e, 2026-09-02; released in 1.5.0.5 to 1.5.0.8).

--------------------------------------------------------------------------------
WHY IT MATTERS
--------------------------------------------------------------------------------

At 100, Cellpose's flow check still runs but rejects practically nothing,
so every mask Cellpose proposes is kept, however misshapen. Every user got a
warning on every run about a value they had not chosen. The warning's
explanation was wrong, and an issue was filed from it.

2026-09-19 -- REVIEWED; THREE CORRECTIONS
--------------------------------------------------------------------------------

The review of this item found one red test, one wrong measurement and one
docstring that disagreed with its code. All three are fixed in this item's
commit.

* tests/test_v2_takes_declared_defaults.py still pinned the declared
  cell_flow_threshold at 100 and went red (assert 0.4 == 100). It passed on
  nightly, and it was missed because it was not in the list of tests run.
  It now pins 0.4; its docstring and comment say the declared default and
  the v2 inline fallback are both 0.4 now. 5 passed.
* The demo figure above was first written from stock cpsam called directly
  on the raw demo images, which skips spaCR's preprocessing: "0.4 loses 4 of
  16 cells in one field". That is not what the demo runs. The reviewer ran
  tests/test_demo_pipelines.py::test_mask_demo_segments_every_object_it_drew
  at 0.4 (passed), and I repeated the pipeline run at 0.4 and at the old
  1.0/100/100, which gave the table above. The paragraph, the note in
  docs/notes/spacr/qt/synthetic.md, and the draft #123 comment (which had
  repeated the wrong figure) are corrected. The advice to consider 1.0 for
  the demo is withdrawn.
* validate._flow_threshold_problems said in its docstring that 0 is
  reported; the code reports only below 0, and both fix lines called 0 part
  of the filtering range. Cellpose skips its check at 0 (and its own log
  tells users to type 0 to switch it off), so 0 stays unreported, taken as
  meant, and the fix lines now say "values above 0 and up to 3 filter" and
  "above 0 and at most 3". The docstring says what the code does.

two warnings; indexing 428 in 00_INDEX.txt; the example pack

2026-09-25 -- DECIDED AND DONE: THE EXAMPLE PACK MOVES TO 0.4; REAL-DATA RUN
--------------------------------------------------------------------------------

Maintainer decision (2026-09-25): the example pack
spaCR_settings/1_generate_masks_settings.csv moves flow_threshold
(nucleus_/cell_/pathogen_FT) from 100 to 0.4, matching the default; run the
example Mask on real test data with 100 and with 0.4 (CPU) and record
objects per class and F1 vs ground truth if available.

THE PACK: nucleus_FT, cell_FT, pathogen_FT are 0.4. Loading it no longer
draws the "such a value comes from an old saved file" warning.
tests/test_the_flow_threshold_default_is_cellposes_own.py gains
test_the_example_pack_carries_the_default_flow_threshold (the three keys are
0.4 and `_flow_threshold_problems` is silent on each).

THE REAL-DATA RUN. Data: /home/olafsson/datasets/plate1, field E01 F001,
all four channels, a centred 512 x 512 crop of the 1994 px field (a whole
field is hours per class on the CPU with Cellpose 4's cpsam). Settings: the
example pack as loaded by `spacr.cli.load_settings_file`, with src, the
plate's own channel map (nucleus 0, cell 1, pathogen 2 -- the pack's cell
channel 3 is a different stain on this plate), plot off, batch 1 -- and the
three FT keys set to 100 or 0.4. spaCR's `preprocess_generate_masks`,
Cellpose 4 cpsam, CUDA_VISIBLE_DEVICES='' (CPU), 8 GB cap. Driver and outputs:
/tmp/spacr-dec2-scratch/ft428/ (drive_ft.py, f1.py, ft100/, ft04/).

GROUND TRUTH: none exists for plate1. The comparison is against the masks
the recorded plate1 run kept (masks/*_mask_stack/plate1_E01_1_1.npy, Cellpose
3 cyto/nuclei at FT 100), cropped identically -- an AGREEMENT score with an
earlier segmentation, not accuracy. A match is IoU >= 0.5, one-to-one.

    objects in the merged array (reference in the crop), F1 vs reference

                  FT 100              FT 0.4
    cell          46  (3)  F1 0.041   2  (3)  F1 0.400
    nucleus        1  (6)  F1 0.286   1  (6)  F1 0.286
    pathogen       1  (1)  F1 1.000   1  (1)  F1 1.000
    CPU time      778 s               608 s

    Before the merge, the pipeline's own log: cell 53 objects/FOV at an
    average 394 px2 (FT 100) against 2 at 7,539 px2 (FT 0.4).

WHAT IT SAYS. At FT 100 Cellpose keeps every mask it proposes, and on this
crop that is 53 small fragments (about 22 px across at a configured cell
diameter of 160 px): 1 of 46 matches a reference cell. At 0.4 the flow-error
filter rejects the fragments and the two cells kept include one that
matches. Nucleus and pathogen come out identical at both thresholds -- the
filter rejected nothing there -- and the nucleus plane is poor at both (1 of
6), which is the pack's nucleus settings (background 500 subtracted, CP_prob
0) on this plate rather than the threshold.

CAVEATS, stated so the numbers are not over-read: one 512 px crop of one
field, few objects (3 reference cells), a reference that is itself a
segmentation by a different network, and the pack's own diameters and
thresholds rather than the plate's recorded ones. It is enough to say 0.4
does not lose the objects that were really there on this crop and removes
the fragments 100 lets through; it is not a benchmark.
