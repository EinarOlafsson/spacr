In settings there is a DEFAULT GRAPH TYPE -- Bar, Jitter, Bar+Jitter, Box,

2026-09-15 -- THE TWO-STEP IS NOW ONE CALL, AND A MUTATION DELETED MY OWN CODE
--------------------------------------------------------------------------------

ml.py and settings.py both had to do the same two-step -- ask `start_for`, then
translate with `mark_for` -- so it is one function now,
`graph_types.mark_to_start_on(shape, fallback_mark)`. It takes the fallback in
MARK vocabulary, because that is the spelling a call site already has written
down, and answers in the same, so a caller never touches the other vocabulary
at all. That is the whole reason 293's "one-line change" was not one line.

AND THE MUTATION PASS DELETED CODE I HAD JUST WRITTEN. The first version
reverse-looked-up the fallback through `MARKS` before handing it to
`start_for`, on the reasoning that `start_for` speaks graph-type vocabulary.
Reverting that loop changed no test result at all -- 11 passed either way --
and reading `start_for` says why: with no preference stored it answers the
fallback AS GIVEN, unvalidated, because "a widget knows what it can draw".
The loop was dead.

IT WOULD STOP BEING DEAD the day a caller passes `counts`. `start_for` uses
the fallback a second time on the too-thin-for-a-distribution path, where
`fits(shape, fallback)` chooses between the caller's form and the table
default -- and a MARK spelling fails `fits`. No caller here has counts: these
are settings defaults, built before any data is read. That is written into the
function so whoever adds counts knows they are also adding the mapping back.

A mutation that cannot tell two versions apart is not a weak test; it is an
answer about the code. Deleting the loop was the honest response to it.

2026-09-15 -- THE GRAPH BUILDER ASKS, AND SAYS SO WHEN IT CANNOT COMPLY
--------------------------------------------------------------------------------

THREE OF FOUR HOLDOUTS ARE NOW DONE -- ml.py's QC figures, settings.py's
pipeline defaults, and the Graph Builder. The fourth, `plot.py`'s spacrGraph,
was never a caller to change: it takes what it is handed, which is correct for
a drawing primitive.

THE SECOND WAY A CHOICE CAN BE REFUSED, which this item had not noticed.
`chosen_for` already drops a saved type that does not FIT the data shape -- a
scatter of grouped data is a different graph of different data. But the Graph
Builder has a NARROWER vocabulary than the preference:

    categorical_continuous fits   box_jitter, bar_jitter, bar, jitter, box, violin
    the Graph Builder draws       bar, box, violin

So `box_jitter`, `bar_jitter` and `jitter` are legitimate answers for the data
and are not charts this module renders. A user who asked for the five numbers
AND the observations gets the box -- and is TOLD so, in `describe()`, the one
line that becomes the chart's caption and the window title.

That is the difference between a considered fallback and a silently ignored
setting, and it is the same rule `start_for` already follows for thin data.

THE PIN STILL BEATS THE SETTING. A pin is the user asking for this chart now;
the preference is a standing answer. If the setting could override a pin,
right-click-to-change would stop working the moment somebody set a default.

AND THE SHAPES WITHOUT A CHOICE ARE LEFT ALONE. A bar of counts (one
categorical) and a contingency heatmap (two categorical) are not a choice
between pictures of the same data -- there is no second form to prefer -- so
the preference never reaches them.

Six tests, three mutations, each caught: ignoring the setting, dropping the
can-this-builder-draw-it check, and swallowing the note.
