================================================================================
A SEARCH FIELD BESIDE THE HELP DROPDOWN
================================================================================

Filed as 413 on 2026-09-18; renumbered 2026-09-19 because 413 also names features/new/413_the_font_zoom_floor_is_ten_percent.txt.

Status:    BUILT 2026-09-19, reviewed and corrected the same day. All five
           result behaviours work and are driven by tests that type into the
           real field; the three new modules are at 100% statement and branch
           coverage. Four should-fix defects came out of review -- the i18n
           seam, an English-only result list, a coverage claim that was not
           true, and the Essentials choice still being rewritten by a lookup
           -- and all four are fixed. NOT DONE: values are not searched (v1,
           as decided), and the nine-language catalogs owe rows for the
           field's captions and for the words a result row is built from -- a

           2026-09-19 notes at the end.

Shape:     A search box beside the Help dropdown. The user types the name of a
           module, a function, a setting or a preference and gets a list of
           clickable results. What a result DOES when clicked depends on what
           kind of thing it is -- that is the whole feature.

--------------------------------------------------------------------------------
WHAT IT IS FOR
--------------------------------------------------------------------------------

spaCR has a large surface: modules, functions, hundreds of settings across
collapsible categories, and a preferences tab. A user who knows the NAME of the
thing they want has no way to get to it. They currently have to know which
module owns a setting and which category it sits under, which is knowledge the
GUI should supply rather than demand.

--------------------------------------------------------------------------------
RESULT KINDS AND WHAT A CLICK DOES
--------------------------------------------------------------------------------

The list is mixed: one query can return several kinds at once, and each kind
has its own click behaviour.

  API REFERENCE ENTRY
      Opens the API entry in a browser.

  MODULE
      Opens that module in the GUI.

  SETTING
      This is the interesting one, and it returns TWO kinds of result for the
      same query:
        - a link to the API entry of each function that takes that setting, and
        - an item that opens each module which exposes that setting.
      When it opens a module, it should open with ALL setting categories
      COLLAPSED EXCEPT the category containing the setting searched for, with
      that setting visible. Dumping the user into a fully expanded settings
      panel and leaving them to find the row is the failure mode this exists to
      prevent.

  PREFERENCE
      Opens the Preferences tab, scrolled or focused to the preference searched
      for.

  "AND SO ON"
      The specification explicitly leaves the list open. Whatever else is
      addressable by name should be reachable the same way. Adding a kind
      should mean registering a provider, not editing a switch statement.

--------------------------------------------------------------------------------
THE PART THAT WILL DECIDE WHETHER THIS IS GOOD
--------------------------------------------------------------------------------

The index. Every kind above needs a name-to-destination map, and a map that is
hand-maintained will drift the first time a setting is renamed, at which point
the search box sends users to the wrong place -- worse than not having it,
because a search result is believed.

So the index should be GENERATED from what already exists: the settings spec,
the module registry, the API doc build, the preferences schema. If a setting
cannot be found by search, that should be a fact about the generator, not about
whether somebody remembered to add a row.

--------------------------------------------------------------------------------
OPEN QUESTIONS -- ANSWER BEFORE BUILDING
--------------------------------------------------------------------------------

  - Is matching exact, prefix, fuzzy, or full-text over descriptions too? A
    user who does not know the exact name is the user who needs this most.
  - One setting can appear in several modules. Does the result list show one
    row per module, or one row that then asks which?
  - What happens when the API reference is not reachable -- offline, or an
    older build whose docs are not published? A dead link is worse than a
    result that says the page is not available locally.
  - Does opening a module discard unsaved settings in the module currently
    open? A search box that silently loses work will be used once.
  - Does the search box also search values -- a user looking for the module
    where `cell_diameter` is 30 rather than for the setting itself?

--------------------------------------------------------------------------------
WHY IT IS FILED RATHER THAN BUILT
--------------------------------------------------------------------------------

to implement it.

--------------------------------------------------------------------------------
2026-09-19 — BUILT, AND THE INDEX IS GENERATED FROM FOUR REGISTRIES
--------------------------------------------------------------------------------

Decided: the maintainer answered all five open questions above on 2026-09-19,
in these words: "Build as recommended" — fuzzy matching over names AND
descriptions; one result row per module where a setting appears; offline, show
the local docstring and say the web page isn't reachable (no dead links);
opening a result never discards the current module's settings (they stay in
memory — verify that is true and make it true if not); values are not searched
in v1. A result opens its module with only the matching category expanded and
the setting highlighted; API entries open the right API page; preferences open
the right Preferences tab. Keyboard: focus shortcut, arrows, Enter, Esc.

WHERE IT IS. The field is the first widget in the menu bar's top-right corner
strip — the strip that follows the last menu, which is Help, and which already
holds the minimise, full-screen and close marks because this window has no
title bar. Ctrl+Shift+H focuses it. Ctrl+F was not reused: it already means
"find a setting on THIS module", and a key that means two things depending on
what is on screen is a key nobody trusts.

WHAT IS IN THE INDEX, AND WHERE EACH ROW COMES FROM. Measured 2026-09-19:

    kind         rows     read from
    module         39     spacr.qt.app.APPS, filtered by app_is_visible
    setting       767     resolve_default_settings + categories_for_app
                          per module, described by get_tooltips
    preference    116     the REAL Preferences dialog, built once by the
                          generator in a sandboxed child process. The
                          generated table holds 129; the 13 Fractal rows are
                          offered only while that backdrop is on, because
                          that is the only time the tab exists. It was 121

                          Sound page.
    api        10,326     the API manifest the published pages are built
                          from (docs/source/_static/i18n/api/en.json)

                          with the fractal backdrop on

Nothing is typed by hand. `tools/build_help_search_index.py` writes
`spacr/qt/help_api_index.py` and has a `--check` mode that fails when it is
stale.

THE PREFERENCES HALF WAS BUILT TWICE AND THE FIRST WAY IS WORTH RECORDING. An
AST walk of `preferences.py` — the obvious answer, since the dialog has no
schema — found 60 of the 121 rows the dialog actually renders. It missed every
row whose caption is a variable (`Starfield direction`), every row a loop
builds from a table (the four Performance budget buttons), and every row
inside a nested panel with a form of its own (40 rows on the Figures tab
alone). It also emitted a row captioned `First graph — {shape}`, which is a
template and not a caption. Building the dialog and reading the rows off it
answers all of that by construction.

AND A FINISHED PREFERENCES DIALOG HAS NO TOOLTIPS AT ALL. `explain_every_row`
moves a row's sentence onto its label and
`_everything_explains_itself_in_the_strip` then moves every remaining one into
the hint bar, deliberately, so a control explains itself once. Reading the
built dialog therefore found a description for 0 of 121 rows. The generator
wraps that sweep and keeps a copy on the way past: 121 of 121 now.

THE RANKING, and the two measurements behind it. An exact name beats a word of
the name beats a prefix beats a substring beats a fuzzy subsequence beats a
description hit. A description hit that outranked a name hit buried
`cell_diameter` under the twenty settings whose help text mentions it. The
fuzzy band needed a ceiling: without one, `clldiam` matched
`spacr.qt.folder_metadata.save_filename_map` — every letter, in order, spread
over forty characters — and ranked it above `cell_diameter`. The span is now
capped at three times the term and matched against the last dotted component
only. A per-kind cap of 8 keeps the list mixed: 10,326 API symbols against 39
modules is otherwise an API list with the occasional module in it.

REVEAL, NOT FILTER. Opening a setting result collapses every category except
the one holding the row, scrolls to it and outlines it for four seconds.
Measured on Mask: 1 section open, 21 collapsed, and all 190 settings still on
the form. Typing the key into the per-module search strip instead — which
already collapses what does not match — was rejected: it HIDES the
neighbouring rows, so a user who arrived from a search and then wanted to look
around has to work out what happened to the panel. The mark is a static border
rather than anything that moves, so it owes nothing to the Animation
preferences and is not lost on a reader who turned motion off.

NO DEAD LINKS. `_DocsReach` has three states, and `"unknown"` is treated as
"do not claim the link works": the offline view opens with its **Open the web
page** button disabled, and the button becomes live if the probe then says the
site is there. The probe is a daemon thread started only when an API result is
actually opened — spaCR does not reach the network because somebody typed. The
offline docstring is read from the source with `ast`, not by importing the
module, so the offline path does not drag the scientific stack into the
process; a subprocess test asserts `spacr.core` is not in `sys.modules`
afterwards.

SETTINGS SURVIVE, AND ALWAYS DID. The maintainer asked for this to be verified
and made true if it was not. It was already true: `_on_nav_selected` keeps
every screen it has built in `self._screens` and switches the stack rather
than rebuilding, and the only path that replaces a screen is
`_rebuild_for_scale`, which answers a font-scale change and not a navigation.
Nothing had to change; the behaviour is now pinned by a test that types 77
into Mask's `cell_diameter`, opens Measure from the search field, comes back
and reads 77.

TESTS. 80, all passing, in three files (29 when this was first built; the
review of 2026-09-19 added 51, and the three new modules are at 100% statement
and branch coverage as a result — see the trailing note):
  tests/qt/test_the_help_search_field_lands_where_it_says.py   47
  tests/test_the_help_index_is_generated_not_typed.py          22
  tests/qt/test_a_preferences_row_can_be_landed_on_by_name.py  11
Every GUI test drives the real control — it types into the box and then asks
the WINDOW what happened. Among them: the field is beside Help and in front of
the window marks; `cell_min_size` returns one row per module that shows it;
Return opens the module with exactly one category open; the API result opens
the right URL when the docs answer and the local docstring when they do not;
Ctrl+Shift+H, Down, Up, Return and Esc alone get there; and every indexed
preference is a row the built dialog really has, which is the drift guard the
instruction's central worry asks for.

NOT DONE, honestly:
  - VALUES ARE NOT SEARCHED. Decided, v1.
  - The nine-language catalogs owe rows for this field's captions; see
    i18n_owed in the handover. The caption ratchet is red for these sources
    and only these, which is expected until the consolidated pass.
  - A Fractal preference cannot be found at all while that backdrop is off.
    That is the deliberate choice over the alternative -- offering a row that
    opens Preferences and then cannot find its own tab -- but it does mean
    search cannot tell a user that the setting exists somewhere behind a
    switch. `_CONDITIONAL_TABS` in help_index.py is where that is decided.
  - The API summaries are the first paragraph of a docstring cut at 140
    characters, so a word that only appears later in a docstring does not
    match. Widening that means shipping more than 1.3 MB of generated index.

2026-09-19 — after review: four defects fixed, and what is still owed
--------------------------------------------------------------------------------

Decided: the maintainer, 2026-09-19, "Build as recommended" — fuzzy matching
over names AND descriptions; one result row per module where a setting
appears; offline, show the local docstring and say the web page isn't
reachable; opening a result never discards the current module's settings;
values are not searched in v1.

Reviewed on the branch and four should-fix defects came back. All four are
fixed here; three of them were things the first pass had claimed were right.

1. THE I18N SEAM WAS WRONG, AND ITS OWN DOCSTRING SAID SO. `_localize` in
   help_search.py stored the English source with `setattr(widget, prop, text)`
   — a plain Python attribute — and never wrote the `<prop>_last_rendered`
   companion, while the `settings_search` seam it says it reuses writes both
   with `setProperty`. `i18n._translate_qt_text` reads them back with
   `obj.property(...)`, which cannot see a Python attribute: on a built field
   `field.property("_spacr_i18n_placeholder")` was None. The field is created
   from `stack.currentChanged`, after the window's language pass, so it is
   born rendered in the current language; the next pass would have adopted
   that rendering as the canonical English and translated a translation,
   freezing the placeholder, the tooltip, the accessible name and the API
   dialog's three notes. Masked only because the catalogs do not yet carry
   these rows and `tr()` is currently the identity. Fixed, and held by two
   tests: one reads the properties off the installed field, one builds a
   field against a stub catalog answering in another language and brings it
   back to English through `retranslate_widget_tree`.

2. THE RESULT LIST WAS ENGLISH-ONLY, and the words in it were in no list that
   the consolidated pass reads. "API reference" is the subtitle of 10,121 of
   the 11,248 rows and "Module" of 39, and those strings were built as data
   in help_index.py — no `tr()` call for the caption ratchet's extractor to
   find, and absent from i18n_owed. A Korean user got an English list.
   Each entry now carries the English TEMPLATE its subtitle and description
   were built from, and the row renders it through `tr` when it is drawn —
   which is every keystroke, so a language change mid-session is picked up by
   the next letter. The index itself stays English because it is the haystack
   the query is matched against, and help_index still imports no Qt and no
   catalog: the translator is passed in. The five new sources are in the
   catalog list below.

   Still English, deliberately: the `Mask ▸ Cell Segmentation` half of a
   setting's subtitle. Those are the module caption and the category heading
   as the registry spells them; they have catalog rows of their own elsewhere,
   and translating them here means translating a value rather than a template,
   which the conservative term-matcher can mangle. Written down rather than
   half-done.

3. "REGRESSIONS: NONE" DID NOT ACCOUNT FOR THE PER-MODULE COVERAGE GATE.
   `tools/verify_module_coverage.py` rule (c) fails a shipped module that is
   not in the baseline and is not at 100%, and the three new modules were at
   help_search.py 74.18%, help_index.py 88.54% and preferences_navigation.py
   79.63% — with nothing anywhere exercising `_IndexLoader._work` or
   `_DocsReach._probe`, the worker thread and the network probe, because the
   only file that touches them stubs `start` out. 51 tests were added and all
   three modules are now at 100% statement AND branch coverage, measured with
   `--cov-branch` over the three files:

       spacr/qt/help_search.py             464 stmts  98 branches  100.00%
       spacr/qt/help_index.py              256 stmts  74 branches  100.00%
       spacr/qt/preferences_navigation.py   80 stmts  28 branches  100.00%

   They are tests, not coverage filler: the worker really builds off the GUI
   thread and hands the list back over a signal; the probe really asks the
   docs root on a thread of its own with the socket stubbed, and answers
   "unreachable" for a 502 as well as for a refused connection; a preference
   result really drives `show_preferences_on`; and each of the four ways
   `reveal_setting` can be refused is one a user could hit.
   `spacr/qt/settings_search.py` is in the baseline at 0 uncovered branches,
   so the change to it (below) was deliberately written without a conditional
   — a `level` parameter would have added a branch nothing takes and failed
   rule (a). NOT FIXED and not this item's to fix: the gate cannot currently
   run at all — `--expected-file-count 572` against 584 shipped files is rule
   (e) — and 15 other modules in flight today are also absent from the
   baseline. Item 288 owns that.

4. THE ESSENTIALS CHOICE WAS STILL BEING REWRITTEN. The paragraph above
   headed ONE LATE NARROWING says this was fixed; it was only narrowed.
   `reveal` still called `set_level(ALL)`, which sets the toggle, which fires
   `_on_disclosure_toggled`, which calls `remember_disclosure` — a persistent
   QSettings write. Most settings are not essentials (Mask renders 190 rows
   against a handful), so looking one up still moved the module out of
   Essentials for good on the common path. `reveal` now goes through
   `_show_all_without_remembering`, which blocks the toggle's signal while the
   button, the level and the caption move, so the form shows the row and the
   store keeps the level the user chose. Clicking the switch still remembers.
   The test now reads the store back with `disclosure_for` instead of only
   asking the strip what level it is on.

THREE NITS, two fixed and one written down:

  - The `DEBOUNCE_MS` note quoted 15 ms — "a sixth of a frame" — as the cost
    of a search. That is the best case. Measured here over the real 11,248-row
    index: 16-24 ms for a word or a phrase, but 34 ms for a single letter and
    41 ms for two, because a term below the fuzzy band's three-character floor
    is matched by substring against every row. The shortest query is the
    dearest one and it is the first thing typed. The note now says so.
  - `_open_preference` discarded `show_preferences_on`'s answer and reported
    "{name} in Preferences ▸ Fractal" even when the tab was gone — a row built
    at start-up can name a page that is no longer built, since the Fractal tab
    exists only while that backdrop is on. It now reports what happened; the
    new string is in the catalog list below.
  - THE PER-KIND CAP CLIPS "ONE ROW PER MODULE" AND THE LIST DOES NOT SAY SO.
    Measured over the 767 (module, setting) pairs: exactly two settings have
    more module rows than the cap of 8 — `src`, in 36 modules and offered for
    8, and `verbose`, 8 of 10. Every other setting is in six modules or fewer
    and is answered in full. The honest fix is a row reading "and 28 more",
    which is a tenth user-visible string for nine catalogs, so it is recorded
    in `PER_KIND_LIMIT` and here rather than half-built.

ALSO WRITTEN DOWN, not fixed: the index is built once a session, so
`_tab_exists` and `app_is_visible` are snapshots. Turning the fractal backdrop
on mid-session does not make its 13 rows findable until the next launch, and
turning it off leaves 13 rows whose page has gone — which is why the opener
now reports what it did rather than what it was asked to do.
