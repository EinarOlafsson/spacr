WHAT IS THERE TODAY (read on nightly e2f082bf8)
-----------------------------------------------

* A FONT scale exists and nothing else scales: spacr/qt/preferences.py
  FONT_SCALE_MIN = 0.10 and FONT_SCALE_MAX = 2.00 (~540-541), clamped at
  ~3625 and ~3631, with its slider at ~5504. No whole-GUI scale exists
  anywhere in spacr/qt (no QT_SCALE_FACTOR, no scale-factor preference), which
  is why widget sizes, paddings, icons and fixed pixel sizes stay put while the
  text shrinks.
* The console already collapses its own topic sections
  (spacr/qt/widgets/console_panel.py collapse_section ~1647, toggle_section
  ~1662; sections start expanded, ~1665), but the console panel itself, the
  System container and the button section under System do not auto-collapse,
  and the button section cannot collapse at all.
* The live previews the maintainer names are spacr/qt/widgets/live_preview.py
  (Mask), measure_preview.py (Measure) and the image-UMAP views
  (umap_explorer.py, umap_search_viewer.py, annotation_umap_tab.py); the same
  shape recurs in motility_preview.py, plaque_preview.py and
  timelapse_preview.py. The figures panel is figure_grid.py /
  figure_grid_view.py / figure_queue.py. Screen layout is in
  spacr/qt/screens/app_screen.py.
* Item 417 (the magnifier's second round) made Make Masks' settings
  categories collapsible; that is the nearest existing pattern to reuse.

WHAT TO BUILD
-------------

1. "GUI scale" in Preferences, beside font scale: 10% to 200%, default 100%,
   scaling every GUI element -- widget sizes, spacing, icons, fixed pixel sizes
   -- not only text. Each live preview gets its own scale slider as well.
2. When a live preview opens, it takes the whole screen height: the console,
   the System container and the button section below System auto-collapse, and
   the settings collapse to the left. The button section needs a collapse
   control it does not have today.
3. The same when figures appear: console, System and the buttons auto-collapse
   and the settings collapse to the left.
4. The user can collapse the figures panel and the live preview panel, and can
   expand anything again at any time. Auto-collapse never removes the user's
   ability to undo it.
5. Every section inside the figures and live preview containers collapses.
6. Wherever possible, every GUI element -- a figure, a table -- is
   collapsible, in every module.
7. A collapsed element locks to the BOTTOM of its container. Today the console
   collapses to the middle of its container; that is the bug this point fixes.

WHAT TO BE CAREFUL WITH
-----------------------

* A true whole-GUI scale in Qt is either a startup-time scale factor (needs a
  restart to change) or every size routed through one scaled helper (live, but
  every hard-coded pixel size must go through it). Decide which before
  building, and say in the setting which it is. The font scale and the GUI
  scale must compose, not fight: 50% GUI at 200% font is a real combination.
* Auto-collapse must not fight the user: once they expand something by hand,
  it stays expanded for that view until they leave it.
* 10% is very small. The screen must stay usable and recoverable there (the
  same survival test item 413 added for the 10% font floor).
* New captions (GUI scale, the collapse controls) are translated strings in
  nine languages: list them for the catalog lane rather than regenerating
  spacr/qt/i18n_catalogs.

DONE WHEN
---------

* At GUI scale 50% on a laptop-sized window, Mask live preview, Measure live
  preview and image UMAP show everything, and 100% looks as it does today.
* Opening a live preview or figures collapses console, System, the buttons
  and the settings, and each can be expanded again.
* Every figure and table in every module can be collapsed.
* A collapsed element sits at the bottom of its container, the console
  included.

2026-09-22 — SLICE A LANDED: THE GUI SCALE AND THE PREVIEW SCALE (point 1)
--------------------------------------------------------------------------------

Slice A is point 1 only. Points 2-7 and the drag-to-resize addendum are other
slices and are not touched here.

THE MECHANISM, DECIDED BY AN AUDIT. A live scale would have to route every
hard-coded pixel size through one helper. Counted on nightly across the 328
modules under spacr/qt: 470 setContentsMargins, 489 setSpacing, 179
setMinimumWidth/Height, 67 setMaximumWidth/Height, 74 setFixed*, 30
setMinimumSize, 56 QSize(...), 64 resize(...), 6 setIconSize -- about 1,420
geometry calls in 181 files -- plus 486 "px" literals in style-sheet text in
64 files (177 of them in theme.py). Too invasive, and every size added later
would have to remember the helper. So the GUI scale is a HYBRID:

* GUI scale (Preferences, beside Font scale; 10-200 %, default 100 %) is a
  startup-time Qt scale factor. spacr/qt/gui_scale.py writes it into
  QT_SCALE_FACTOR before the QApplication exists (called from launch() in
  spacr/qt/app.py), so Qt scales every logical pixel: widget sizes, fixed
  sizes, margins, spacing, QSS paddings, icons, pictures, text. A change
  needs a restart; the row says so, shows "N% after a restart (now M%)" and
  offers Restart now, which saves the dialog and restarts through the same
  record Force restart writes (the module and its settings come back; a run
  in progress is asked about first). At 100 % nothing is written, so a
  default launch is byte-for-byte today's.
* Font scale ("Zoom") stays live, on top. They multiply: 50 % GUI at 200 %
  font gives half-size widgets with text at its usual size on screen
  (tested in a child process: body text 26 logical px = 13 device px, a
  100 px box = 50 device px).
* A user's own QT_SCALE_FACTOR is kept (SPACR_GUI_SCALE_BASE) and a restart
  does not compound it. SPACR_GUI_SCALE=1 overrides the stored value for one
  launch; safespacr reads it as its default, 100 %.
* The window keeps its physical size at any GUI scale
  (fit_window_to_gui_scale), so the room gained goes to the content.
* matplotlib's toolbar icon engine multiplies the device ratio in twice;
  below a ratio of 1 the pan/zoom icons drew 3 px tall at 50 %.
  gui_scale.mend_matplotlib_icons() holds the engine's ratio at >= 1 (only
  when running below 100 %); measured 11 px, and no change at ratio 1 or 2.

EACH PREVIEW'S OWN SCALE, live. spacr/qt/widgets/preview_scale.py (re-exported
from preview_controls.py) is one implementation used by Mask
(live_preview.py), Measure (measure_preview.py), Plaque, Timelapse, Motility
and the three image-UMAP views (umap_explorer.py, umap_search_viewer.py,
annotation_umap_tab.py). A 10-200 % slider scales, inside that preview only:
style-sheet sizes it inherits and its widgets set (font sizes, paddings,
margins, min/max sizes, radii; border widths left alone), min/max/fixed
widget sizes, layout margins and spacing, button icon sizes, and through a
hook what the panel draws itself (Measure's crop thumbnails, the UMAP
figure's dpi). Bases are remembered per widget so it never compounds, a size
the code sets later becomes the new base, and at 100 % nothing is touched at
all. Saved per preview under prefs/preview_scale/<name>. The slider sits in
the preview card's title row beside Refresh (placed on first show) -- in the
toolbar row it raised the column's minimum and the settings column lost
68 px at 100 %. It is exempt from its own scale; double-click its value for
100 %.

SURVIVAL AT 10 %. Ctrl+Alt+0 (free in shortcuts.py; Cmd+Option+0 is not a
macOS-reserved combination) puts GUI scale, font scale and every preview
scale back to 100 % and asks to restart with Restart now as the DEFAULT
button, so Ctrl+Alt+0 then Enter recovers without reading anything. Tested
on a real MainWindow built at 10 % in a child process (the binding exists,
Preferences still opens with the row at 10, Enter restarts). Honest limit:
at 10 % Preferences itself is a ~60 px postage stamp on a 1366x768 screen --
reachable, not usable by mouse; the keyboard route is the way back.

CHECKED. At GUI 50 % on 1366x768 and 1280x800 (offscreen), Mask live
preview, Measure crop preview and image UMAP show every control, the image
canvases and the figure. At 100 % the screens pixel-compare against nightly
at ec09c3608 (slice B landed): Home identical (0 px); Mask, Measure and
image UMAP differ by 683 px each, all inside the new slider's own box.
Tests: tests/qt/test_the_gui_scale_fits_a_laptop.py (23). The shipped-module
ratchet moves 606 -> 608 for the two new modules.

NEW CAPTIONS for the catalog lane (not translated here): "GUI scale",
"Restart now", "Later", "Restart spaCR?", "GUI scale reset",
"{wanted}% after a restart (now {running}%)",

2026-09-22 — SLICE B LANDED: THE SHELL COLLAPSES AND EVERY EDGE DRAGS
(points 2, 3, 4, 7 and the DRAG AN EDGE addendum)
--------------------------------------------------------------------------------

Commits 01ac8a80b (the mechanism), ec09c3608 (the shell), e37f9e347 (the
module at 100 % branch coverage). Points 5-6 (every section, figure and table
inside every screen) are slice C, and slice C builds on the primitive below.

ONE MECHANISM. spacr/qt/widgets/collapsible_splitter.py. A QSplitter already
gives a draggable handle and a child that can be taken to zero, so collapse is
the limit of dragging, not a second system.

* CollapsibleSplitter(orientation, parent=None, *, persist_key="") -- a
  QSplitter whose children are named panes:
    add_pane(widget, name, *, folder=None, mode=None, stretch=1, extent=0,
             minimum=None, focus=False, fold_key="", index=None) -> Pane
    pane(name), panes(), is_collapsed(name),
    set_collapsed(name, collapsed, *, by_user=False), toggle_pane(name),
    rebalance(), extents(); signal pane_toggled(name, collapsed, by_user).
  Pane kinds:
    HEADER (give it a Folder from widgets/foldable.make_foldable) -- folds
      to its heading, and the heading is LOCKED TO THE BOTTOM of the room the
      pane has (a stretch goes in above it). A folded HEADER pane is held at
      its heading's height by a maximum, so no window resize or drag hands it
      a gap. When nothing that stretches is left open, the first folded
      heading takes the spare room, so every folded heading stacks at the
      bottom of the container.
    EDGE (mode=EDGE) -- folds to nothing; the handle beside it is the strip:
      it carries an arrow, a click on it folds or restores the pane, a drag
      resizes it. fold_key remembers the user's fold across restarts.
    plain (no folder, no mode) -- resizes, never folds.
  Dragging an open pane past its minimum collapses it (Qt's own collapse,
  turned into the pane's fold). Sizes are remembered per pane NAME (not
  index) under persist_key in the preferences store (layout/panes/<key>), so
  adding a pane to a screen does not scramble the old layout. A drag never
  moves anything the user did not move; a width change re-fits only
  fixed-size panes that wrap (the Run row), since no handle is held then.
  A widget that is later wrapped in a container put in its place (the
  settings search strip does this) hands its registration to the container.
* FocusCollapse(parent) -- watch(widget) a FOCUS widget, target(splitter,
  name) a pane; while any focus widget is shown the targets fold, and when
  the last is hidden the ones it folded open again. begin_view()/end_view()
  and is_pinned(splitter, name). It reads hidden flags only: nothing is
  shown, measured or built to register it.
* lock_folded_to_bottom(container, folder, orientation=Qt.Vertical) -- the
  bottom-lock on its own, for a fold that is not in a splitter (a section
  in a scroll area). This is the piece slice C applies to sections.
* Folder.set_shut(shut, *, by_user=True), Folder.toggle(*, by_user=True),
  Folder.add_listener(cb(shut, by_user)), Folder.last_change_by_user. A fold
  made on the user's behalf (by_user=False) is never persisted.

FOR SLICE C: to make a panel collapsible, give it a heading and
make_foldable(heading, body, name=..., persist_key="<module>/<panel>"); if its
siblings should trade height with it by dragging, put them in a
CollapsibleSplitter and add_pane each with its folder; otherwise call
lock_folded_to_bottom(panel, folder). Card(title=..., foldable=True,
fold_key=...) already gives a Folder on the title.

THE SHELL (spacr/qt/screens/app_screen.py).
* The runtime column is ONE vertical CollapsibleSplitter, top to bottom:
  Figures, the module's preview (Mask/Plaque Live preview, Measure Crop
  preview, Timelapse Track preview, Motility preview) or its Parameter sweep
  / Hyperparameter search card, Console, System, and the new buttons section
  ("Actions": the Run row, whatever is mounted above it -- chaining strip,
  QC banner, diameter panel, map-barcodes strips -- and the two hover-help
  strips). Every one of them resizes by its edge and folds by its title; the
  buttons section has a heading it did not have before. A folded one is its
  heading at the bottom: the console no longer folds to the middle.
* The settings column is an EDGE pane of the body splitter: click its handle
  (or drag it to nothing) and it collapses to the LEFT; click or drag again
  and it comes back at its old width. Ctrl+F opens it first if it is folded.
* Keys: runtime sizes under "<module>::runtime", the column under
  "<module>::body"; folds under "<module>/Console", "/System", "/Actions",
  "/Settings" (Console and System keep their existing keys).
* The four "above the Run row" inserters (prerun, chaining, preview_registry,
  map_barcodes) now follow the Run row into its section; a preview mounted
  by preview_registry is adopted (adopt_runtime_pane) as a focus pane.

AUTO-COLLAPSE (points 2-4).
* FOCUS panes: the figures card and every preview card, including registry
  previews. When one is shown -- a Live switch turned on, the first figure of
  a run, the image-UMAP explorer -- Console, System, the buttons section and
  the settings column fold, and the focus takes the height. When the last is
  hidden, whatever the auto-collapse folded opens again; what the user had
  folded stays folded.
* The user can fold the figures panel and the preview by their titles, and
  open anything at any time. A focus pane the user folded opens again when it
  is next shown (switching Live on means "show me the preview").
* NEVER FIGHTS THE USER. A target the user opens by hand WHILE a focus is
  shown -- clicking its heading or its handle, or dragging it open -- is
  PINNED: no later auto-collapse folds it again during the view. Opening a
  pane when no focus is shown overrules nothing and is not a pin.
* THE VIEW is one visit to one module screen: from the screen's showEvent to
  its hideEvent (going to another module or screen). Spontaneous events
  (minimising the window) do not end it. Returning to the module starts a new
  view: pins are forgotten and, if a preview or figures are still showing,
  the surroundings fold again.

2026-09-22 — SLICE A, SECOND ROUND: THE GUI SCALE IS LIVE, AND EVERY SCALE
CHANGE ASKS KEEP OR REVERT
--------------------------------------------------------------------------------

In the maintainer's words:

    "the GUI scale is only adjusted after startup. please make this work with
    out restarting. and if either font or GUI scale are modified the user
    should be prompted with a Keep or Revert popup."

WHAT CHANGED. The startup Qt scale factor of the section above is gone. The
GUI scale is now applied live by a scaling layer over Qt's own setters
(spacr/qt/gui_scale.py, install_scaling_layer, called from launch() before
the first widget exists). No restart path is left in Preferences.

HOW THE LAYER WORKS, and why it is not 1,420 edits. It replaces the setters
themselves on the Qt classes -- QWidget's setMinimum/Maximum/Fixed
Width/Height/Size and setStyleSheet, the layouts' setContentsMargins,
setSpacing, setHorizontal/VerticalSpacing and addSpacing, every setIconSize
in QtWidgets, QSplitter.setSizes -- and each replacement:

  * remembers on the object the value the code asked for, its size at 100 %;
  * hands Qt that value times the current scale;
  * answers the matching getter in 100 % units, so the theme's sheet
    digests, slice B's persisted splitter sizes and any code that reads a
    size and sets it again keep working in one unit and never compound.

set_gui_scale_live() then walks every live widget and layout, puts the
remembered values back at the new scale, rebuilds what a sheet cannot reach
(refresh_theme: the window chrome and the Home tiles' painted pixmaps) and
asks the windows to lay out again. Widgets built later are scaled as they
are built, so the lazily built panels (284/380) and the settings categories
that wait off the page need nothing of their own.

STYLE SHEETS. scale_qss_text rewrites only the values of size properties --
font-size, font, padding, margin, min/max width and height, width, height,
spacing, border radii -- in place, by regex, leaving selectors, colours,
borders and url(...) data untouched. The theme's sheet goes through the
same replacement, which is how font scale and GUI scale compose: a font
size is base x font scale x GUI scale. A user's own QT_SCALE_FACTOR is not
touched and still multiplies on the outside.

WHAT ELSE FOLLOWS. Matplotlib figure dpi (base x GUI scale x that preview's
own scale), matplotlib toolbar icons and any other icon size the style
supplies rather than the code, Measure's crop thumbnails, and the preview
sliders of the first round, which compose with it.

WHAT STILL DOES NOT FOLLOW, named rather than hidden: text and shapes a
widget paints at fixed pixel coordinates, pixmaps scaled to a number a
widget computed, setFont with an explicit size, move/setGeometry positions,
header section sizes, a Python sizeHint override that returns a constant,
style metrics the theme's sheet does not restate, and pyqtgraph's axis
text. A size computed from font metrics is scaled once by the font and
again by the setter; the layer keeps a base that looks like its own scaled
value (within 6 %) rather than re-basing, which is what stopped the window
chrome coming back half size after a round trip.

KEEP OR REVERT. change_scales() applies the new GUI and font scale at once
and opens "Keep these settings?" without blocking, counting down 15 s.
Revert, Esc, closing the window and the end of the countdown all put the
old values back; Keep leaves them. The question is exempt from the scale
(EXEMPT property on its window) and states its own text sizes, so it stays
readable at 10 % GUI and 10 % font -- which is the recovery that matters,
and the Z + wheel gesture now ends with the same question. Ctrl+Alt+0
remains the backup and no longer restarts anything.

CHECKED. tests/qt/test_the_gui_scale_fits_a_laptop.py (27) covers a live
change reaching widgets already built and widgets built afterwards, the
zero-drift round trip 100 -> 50 -> 170 -> 10 -> 100 on every recorded size,
the re-measuring widget that must not re-base, the exempt window, the
composition of the two scales, the sheet rewrite leaving borders and data
URIs alone, the countdown's auto-revert, Keep, Revert, Esc, the readable
question at 10 %, the Preferences slider applying live and asking, the
reset key, and the figure dpi following both scales. 919 tests across the
preferences, zoom, theme, shell, preview and figure suites pass beside it.

Screenshots at 1366x768, offscreen: mask/measure/umap at live100, live50
and live100b (one process, scale changed under a running window) and the
Keep question at 50 %. Going back to 100 % is pixel-identical on all three
