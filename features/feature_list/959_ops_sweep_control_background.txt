PROBLEM
Since item 953 a published comparator's non-targeting rows count in the
Fisher background of its CORUM and KEGG shares, but spaCR's own sweep rows
(score_partitions) were scored against the targeting genes only, so one sweep
table mixed two backgrounds.

BUILD
- One shared helper, _score_controls_row (was _score_published_row), scores a
  sweep row and a comparator row: control rows join the Fisher background of
  the CORUM and KEGG shares only; they are never cluster members, enrichment
  members or STRING pairs; complex metrics use the scored genes.
- score_partitions(..., control_prefix='nontargeting',
  controls_background=False): True adds the run's control rows (names with the
  prefix that are not scored genes) to that background; every row records
  background_rows and control_rows_in_background. The shuffled-label control
  draws the same permutations (scored genes only, controls keep their labels).
- score_published(..., record_background=False): True adds the same two
  columns to the comparator rows.
- published_record(..., sweep_controls=None): the legend states that the sweep
  rows count the run's control rows and, when the comparators keep theirs,
  that every row of the table uses one background rule.
- cluster_sweep_phase reads ops_cluster_sweep_controls_background (bool,
  default True, alpha). False (and files stamped before 945) writes
  byte-identical files to nightly 084bac13fa.

ACCEPTANCE
tests/test_ops_sweep_control_background_959.py: the CORUM share with controls
equals a hand-written Fisher test with the background grown by the control
rows (and the old share without); STRING, complex and count metrics
unchanged; a sweep row and a comparator row of the same partition are equal
(one helper, one background); the shuffled controls use the same draws; off
is the pre-959 scoring byte for byte; the phase default writes the columns
and the legend, False writes the pre-959 files; files stamped 944 or older
load False.
