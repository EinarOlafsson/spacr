A user reports duplicate objects after repeatedly running Measure on the same
folder. Reproduce the existing behavior with temporary inputs, tracing the real
measurement writer, and report whether a repeated run duplicates object rows.
Never modify the reporting user's data or attempt to untangle historical mixed
populations automatically.

Before a fresh Measure run would write to populated object tables in an existing
measurements.db, show a GUI warning explaining that prior tables will be renamed
to keep runs and object labels separate. Allow cancellation without database
changes. Archive prior related tables coherently, including png_list and other
run-derived outputs, using cell_1, cell_2, etc. without overwriting any existing
archive. Apply the same protection to all object types, dynamic organelles and
headless/API runs. Preserve prior data, annotations and provenance; do not rotate
archives again or rename SQLite internals. Keep explicit resume behavior safe
and distinguish continuation from a new run. Protect against concurrent writers,
partial archive failures and repeated startup calls. Only archive at actual run
startup, after validation; dry runs, failed validation and cancellation must not
rename tables. Validate repeated-run behavior, archive collisions and rollback,
GUI cancel/confirm, and downstream canonical-table isolation. Archive run-derived
user tables together; retain independent acquisition/import/stitch/watch and
image-annotation provenance, explicitly saved annotated tables, and SQLite/write
queue internals. Existing views remain bound to the preserved old population.
Do not overwrite old PNG/array crops while preserving their archived list rows;
new populations use distinct crop locations, including after explicit Resume.
