PROBLEM
run_ops always stitched the whole well and fitted the round-well layout
from the highest site present. A folder with only some tiles failed
("no round well holds exactly 168 fields ..."), and objects and decode ran
on every placed site, so a tile-level benchmark had to run the whole well.

BUILD
- ops_sites (str or list, default None, alpha): the sequencing sites the
  stitch, objects and decode phases run on, as '46,148,160-167' or a list.
  Empty or None runs every site; outputs are unchanged.
- stitch (_stitch_sites): the layout is fitted from every file name in
  genotype_source (max site + 1), only the listed tiles are read. Listed
  neighbours are registered and solved together; each group is shifted so
  its lowest site sits on the layout grid (pitch = tile - ops_raster_overlap),
  a lone tile is placed on the grid directly. ops_geometry holds only the
  listed sites; the report says placement 'ops_sites' with
  placement_sources per site ('registered' or 'layout_grid'). No placement
  file is written. With ops_placement_seed the seed places the listed sites
  (the 940 path, restricted to them).
- A folder whose highest site fits no round well is refused, naming both
  ways out: genotype_source on the whole acquisition, or ops_placement_seed.
- objects: composes only the listed placements.
- decode: only the listed fields decode; each nucleus belongs to the nearest
  tile centre among every placed site, so on a whole-well stitch the well's
  territories are kept. Unplaced unlisted sites are not reported as skipped.
- reports: ops_report.json, the decode report, its FDR report and
  results/ops_decode/decode_fdr_<well>.json carry ops_sites.
- Listed sites without a nuclear tile, non-numbers and negative sites are
  refused before any pixel is read.
- Library column: a guide library CSV without a prefix, barcode or sequence
  column is refused with the columns it has (and 'no rows' when empty).
- No default changes, so no DEFAULT_CHANGES row.
