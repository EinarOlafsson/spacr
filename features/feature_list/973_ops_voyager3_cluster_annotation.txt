PROBLEM
Brieflow ends its OPS analysis with MozzareLLM: one LLM prompt per cluster
(genes plus UniProt FUNCTION text) that names the cluster's pathway, a
confidence from the share of genes that fit, and the uncharacterised genes
worth following up. spaCR had no such step; the plate A annotation was done by
session agents outside spaCR.

BUILD
- spacr.voyager3: fetch_gene_facts (reviewed UniProt entries through
  spacr.uniprot and its cache: protein names, function, GO process /
  component / function, pathway, location, annotation score; batches of
  100, 0.5 s apart, release headers recorded), build_cluster_prompt (English
  template voyager3-1, not translated), parse_cluster_answer (never raises;
  statuses ok / partial / unparsed / no_answer; non-member genes dropped and
  counted; priority 1-10 checked; support fraction and the 70/50/30 % rule
  recomputed by spaCR), run_voyager3, voyager3_replay.
- Provider: injected, or ops_voyager3_provider, or Preferences > AI: any
  provider there, spaCR AI (free) included (maintainer decision 2026-11-17);
  "none" is refused. The report and provenance name the provider, model and
  CLI arguments, and a quality note says when the free provider answered
  (and how many answers came from its smaller "light" model). No vendor
  SDK, no API key, no batch API.
- Outputs in results/ops_voyager3/: voyager3_clusters.csv,
  voyager3_candidates.csv, voyager3_gene_facts.csv, voyager3_report.md,
  voyager3_provenance.json (system text, every prompt, template version,
  provider and model, UniProt release and fetch date, facts, every attempt
  and raw answer). The tables are written from the provenance by the same
  code the replay uses.
- Resume (maintainer decision 2026-11-17): each answer is saved as it arrives
  to <ops_voyager3_answers_dir or results/ops_voyager3/answers>/<sha256 of
  template version, model, system text and prompt>.json (raw text, model ids,
  reported cost, seconds; temporary file then rename). ops_voyager3_resume
  (default True) replays saved answers and asks only the missing ones; a
  changed model, template or prompt asks again; failed or timed-out calls are
  not saved. The provenance records each cluster's answer_source (replayed /
  asked) and the counts; progress lines and the GUI status say
  "n replayed, m asked". The Claude CLI provider keeps its last result
  object (last_result) so model ids and cost can be saved.
- ops_voyager3_shuffle_control: the same cluster sizes with the genes
  permuted (seed 20261117), kind "shuffled" in the tables.
- Phase "voyager3", last of the profile phases; also after cluster_sweep,
  cluster_consensus or cluster_bench_test when ops_voyager3_enabled is on.
  runtime.json records the ops_voyager3_* keys only when it ran.
- Settings (OPS phenotype category, last OPS step): ops_voyager3_enabled,
  _clusters, _cluster_column, _cluster_ids, _organism, _context, _provider,
  _model, _timeout, _shuffle_control, _resume, _answers_dir. For item 969: a subcategory
  "Cluster annotation (Voyager3)" after the clustering subcategory.
- GUI: "Annotate clusters (Voyager3)" button, progress bar and status line in
  the section holding ops_voyager3_enabled, behind Show alpha features; runs
  only the voyager3 phase through make_thread; the bar reads the standard
  Progress lines.
