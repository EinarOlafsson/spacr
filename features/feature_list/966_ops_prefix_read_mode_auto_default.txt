PROBLEM
The spacer-prefix decode read the LoG-filtered pixels with fixed thresholds by
default. On PERISCOPE CP186A Well1 (75 held-out sites) that is 3.9-6.8 points
behind PERISCOPE's reads at matched decoy FDR (<= 1 % / <= 0.1 %). With item
952's auto read and per-well decoy tuning spaCR ties or leads.

BUILD
- Defaults (OPS_DEFAULTS and settings_spec), schema 944:
  ops_prefix_threshold_tuning 'none' -> 'per_well_decoy';
  ops_prefix_decoy_k 0 -> 4; ops_prefix_fdr_target_pct 0.1 -> 1.0;
  ops_prefix_tuning_grid unchanged (None = built-in grid).
- ops_read_mode is shared by both decodes, so its default is per path: the
  registered default is empty (None). spacr.ops_prefix._prefix_read_mode reads
  empty as 'auto' while the prefix decode tunes and 'log' without tuning;
  spacr.ops_sbs._read_mode_setting (the OPS barcode decode) reads empty, or
  'None', as 'log'. An explicit 'log', 'raw' or 'auto' is used as set on both
  paths. The combo offers log, raw, auto and None.
- DEFAULT_CHANGES[944] = {'ops_read_mode': 'log', 'ops_prefix_threshold_tuning':
  'none', 'ops_prefix_decoy_k': 0, 'ops_prefix_fdr_target_pct': 0.1}: settings
  files stamped before 944 rerun with the old values.
- Direct API calls keep the engine's own fallbacks (no tuning, no decoys), as
  item 946 did; a direct call that turns tuning on without a read mode now
  reads 'auto'.
- Run summary: with tuning, run_prefix_decode returns well_choices and sends
  one line per well last: read mode (and whether auto chose it), read
  threshold, read quality, mismatches, decoy FDR on the tuning sites and on
  the report sites, target met.
- Tooltips of the four settings name the new defaults and which decode reads
  which read-mode default; release note; reproducibility manifest row;
  readiness row; 918-923 arrival contract re-pinned for run_prefix_decode.
