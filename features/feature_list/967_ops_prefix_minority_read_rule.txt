PROBLEM
Under ops_prefix_quality_method 'recipe_simple' (the "simple" classes of the
pooled Cell Painting recipe that PERISCOPE used) a cell with more than one
exact barcode is bad. One stray exact read of a second barcode removes the
call: on CP186A Well1 (75 held-out sites) 4,897 cells that PERISCOPE calls are
lost this way, and in 2,585 of the 2,643 cells where the main barcode leads the
competitor is a single read.

BUILD
- Setting ops_prefix_minority_min_reads (int, default 0 = off; 1 also changes
  nothing). From 2 up, inside a cell a barcode with fewer reads than this is
  left out of the call when another barcode of the cell has strictly more
  reads (spacr.ops_prefix._minority_ignored). Ties still block the call; a
  decoy-top cell is still flagged and never genotyped.
- spacr.ops_prefix.prefix_cell_calls(minority_min_reads=...): both quality
  methods. Under 'spacr' no call changes ('great' can become 'perfect').
  With the rule on, the cell table gains minority_ignored (reads left out)
  and minority_rescued (called only because of the rule).
- The per-well decoy tuning, the shuffle calibration and the cell calls all
  count calls with the same rule (_called_counts).
- Reporting: site_summary.csv gains cells_minority_rescued (genotyped cells
  rescued), the run result gains minority_rescued per well, one log line per
  well, and quality_classes.json records the setting. With 0 none of these
  appear, so the run writes what it wrote before.
- The matched-FDR sweep (item 955) is unchanged; its maxcount rule already
  ignores minority barcodes.
